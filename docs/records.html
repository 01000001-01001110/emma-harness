The project

Records & house rules

The repository keeps a small set of written records. Each has one job; when two answer the same question, one of them is wrong and nobody can tell which.

Records in the repository

As of 2026-08-30, notes/ is no longer in the tree. Three records remain here; where the old notes/ jobs went is listed below.

RecordAnswers
commit message What changed, and why. Long, because the reasoning behind a change has nowhere else to go once the diff is old. Lessons that used to live in notes/lessons/ belong here now.
docs/ How Emma works and why it is shaped that way. The only one addressed to somebody trying to use or modify the system rather than track the project.
CHANGELOG.md What is different for somebody upgrading, and nothing else.

Former notes/ records

WasJob now
notes/lessons/ Commit message on the change that carried the lesson.
notes/improvements.md The owner's vault outside this repository.
notes/STATUS.md The owner carries in-flight state; do not infer it from git log.

A changelog entry describing a refactor is describing something no user can observe. A documentation page narrating the project's week is doing STATUS.md's old job.

Rules for durable records

Comments carry the why, not the what

A comment restating the code is noise. A comment carrying the argument for a decision is the reason the file can be changed safely later. Read a module's existing doc before adding to it and match that register.

A test that cannot fail is a false receipt

Every behaviour gets a test, and tests that claim a guarantee must go red when the guarantee is removed. The way to know is to break the code, watch the test fail, and put it back. Report which mutations were run and what happened.

A source-grep test once passed while the thing it guarded was disabled entirely. Four tests in the terminal directory were found that cannot fail: one binds a value nothing reads, two discard their results, and one asserts against a label the module stopped emitting. That directory's test count is four higher than its coverage.

A green suite is not evidence

It has been wrong three times here. A language-server readiness check declared ready at 0.36 seconds against a real server. A frontmatter parser silently dropped 86 of 90 real files because its fixtures used LF endings. A strict wire decoder passed 712 tests and then decoded no real tool call, because the API adds a key the model did not know about.

Fixtures agree with their author. The rule that follows is to certify against the real thing, and paste what it actually said.

Say what you could not verify

Explicitly, in a section of its own, with what would settle it. Every page on this site ends with one, and they are collected on What is not verified. Terminal claims require this distinction because a cell buffer is not a console.

Do not fabricate

If a tool cannot compute something it says so rather than showing a plausible substitute. If output was cut it names the cap, the loss and the remedy, or says plainly that no argument raises it. The same rule covers suggestions: a warning that recommends a spelling is making a claim, and idna will return Ok for a wrong one, so the code refuses to guess rather than guessing helpfully.

Licences before code

A README is not a licence, and NOASSERTION on GitHub means open the actual file. This has caught five things in one week: a badge that read NOASSERTION over a real FSL-1.1-MIT licence, a crate that turned out GPL-3.0-or-later, a project silently relicensed to a source-available licence after an acquisition, a repository with no licence file at all, and one carrying a rider granting no rights to Anthropic specifically.

Why the record is this detailed

Emma is built mostly by agents, in sessions. Context carries inside a session and the rules carry across them, but the person holding the reasoning changes constantly. Anything kept only in someone's head is gone by the next session.

The alternative to writing down what was measured and what was assumed is re-deriving it. The four incidents above are what that costs. In each case the written record was the only possible correction, and where the record was silent, the mistake shipped.

How the records go wrong

Every failure below is real and recent. They are listed because the failure modes repeat, and because a record that has drifted is worse than a missing one: it will be believed.

FailureWhat happened
A backlog that stopped tracking the code Four defects were fixed and committed. Two days later all four still read Status: open, so the next reader would have re-planned finished work.
An item filed under the wrong heading Seven live items sat under ## Rejected, because each was appended to the end of the file and the end of the file was inside that section. Every item's own status line was correct. Only the heading it inherited was wrong.
An index claiming shipped features were plans Four rows of notes/README.md read "plan, not built" over delegation, the browser tools, /compact and the full-screen interface.
A constraints file describing a test that would be red CLAUDE.md said a test fails if a feature is ever named in the manifest. The test strips comments and fails only on a declaration, and the manifest names the feature in a comment.
A caveat that did not travel with its number An architecture map gave a file count and a line count in the same paragraph where it admitted reading almost none of those files. Both figures were quoted onward as fact, twice, and both were wrong.
A blocker recorded as the wrong problem An item was recorded as blocked on a corpus being too small. Counted from disk, the corpus was large. The blocker was that the feature it needed data about is barely used.

Two habits come out of that list. Record the count the blocking query returned rather than a summary of the corpus it ran against. And when quoting a figure, carry its caveat with it or check the figure first.

Writing a page here

DOCS.md in the repository root is the rule set: plain HTML that opens from file:// with no server and no build step, one shared stylesheet, source citations under claims, evidence chips on anything non-obvious, diagrams generated from the source rather than drawn, and a voice that describes the system rather than admiring it.

Who checks the checker

The records above are written by whoever did the work, which is the only way to keep the reasoning in them and is also their weakness: an author checking their own claim re-reads the argument they already made. On 2026-08-23 nine defects were found here in one day and every one came from an independent reviewer; none from the author.

emma verify is the command that fetches one: a fresh model, given a single ledger row and the tree, briefed to disprove it rather than confirm it, and required to end on a verdict that is allowed to say no.
