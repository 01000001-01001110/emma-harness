Hooks: three events, three failure rulings

Consent & permissions The two axes The ladder The egress question The five answers EXEMPT and the floor Permission rules Matching a host Hooks

A hook is an operator-authored program the runtime runs at one of three dispatch sites. A PreToolUse hook is the only thing in Emma that refuses a call and cannot be answered away at a prompt. It is also a program the operator wrote, running at the highest-privilege point of the turn, which is why this file is a subprocess supervisor rather than configuration.

crates/harness/src/hooks.rs — module doc

Everything checkable is checked at load

A hook that cannot be run safely stops the boot rather than failing at the moment it is needed. That is the same ruling every other refusal in the harness crate makes: an ambiguous configuration stops startup. 

pub(crate) fn contain(root: &Path, what: &str, command: &str) -> Result<PathBuf, String> {
    let dir = root
        .join("hooks")
        .canonicalize()
        .map_err(|_| format!("{what} is defined but hooks/ is missing"))?;
    let path = root
        .join(command)
        .canonicalize()
        .map_err(|_| format!("{what}: no such command `{command}`"))?;
    if !path.starts_with(&dir) {
        return Err(format!(
            "{what} resolves to {}, outside {}",
            path.display(),
            dir.display()
        ));
    }
    // Unix only, because there is no executable bit on Windows to consult — a
    // `.cmd` or `.exe` is runnable by extension.
    #[cfg(unix)]
    {
        use std::os::unix::fs::PermissionsExt;
        let meta = std::fs::metadata(&path).map_err(|e| format!("{what}: {e}"))?;
        if meta.permissions().mode() & 0o111 == 0 {
            return Err(format!("{what} is not executable"));
        }
    }
    Ok(path)
}
crates/harness/src/hooks.rs — contain, quoted entire

The containment check is why command is relative. An absolute path or a .. escape would let a config file run any executable on the box with Emma's permissions, and Emma's permissions include writing the user's source tree. Canonicalisation happens before the starts_with, so a symlink out of hooks/ is caught too. The executable-bit check is not the boundary; it catches the operator who forgot to chmod +x, which would otherwise surface much later as a spawn failure that reads like something else. what names the caller in the sentence, because "no such command" with no subject is a sentence an operator cannot act on. The same function is what the status line goes through, so anything config can point Emma at is contained here.

What resolve does with each declaration

resolve takes the root, the spine path, the declared map and the persona's optional enable list, and returns the hooks that survived. Its steps, in order:

  • Every name in the persona's enable list must exist in the declared map, or the boot fails naming it. A persona enabling a hook nobody declared is a policy that silently does not exist.
  • A declared hook the persona excludes is skipped before anything else is checked, so it costs nothing. "hooks": [] turns all of them off.
  • HookEvent::parse maps the event string. Claude Code implements a larger set including SessionStart, Stop and PreCompact. Emma implements three, and a config naming any of the rest is a startup error listing the three that work, never a silent skip, unless EMMA_CLAUDE_HOOKS=skip-unknown is set, which converts the refusal into a boot that names each hook it dropped. Still not a silent skip; that is the property, and it is the one thing the opt-in does not relax. It is an environment variable rather than a config key, so a repository cannot turn it on for the person cloning it.
  • contain resolves the command.
  • A UserPromptSubmit hook carrying a non-empty matcher fails the boot, because there is no tool name to match on that event. Claude Code ignores the field there; Emma names it, on the rule that a hook the operator believes is conditional and which never fires is worse than one that always does. A matcher that is present but empty or whitespace is treated as absent, since "matcher": "" is what a group written for a tool event looks like when it was copied for this one.
  • A matcher is compiled as ^(?:{m})$. Anchoring is what stops Read from silently guarding ReadFile, the near miss that looks like a working policy. A regex that does not compile fails the boot with the file and the hook named.
  • The executable is read and hashed with hash::short. The hash goes into every HookRun and into Harness::snapshot through ResolvedHook::identity, which reports name, event and hash and never the hook's text.
  • The timeout is def.timeout_ms or 5,000 ms, capped at 10,000 ms. Config asking for more is reduced silently rather than refused: the operator asked for a longer gate, not for a different program.

crates/harness/src/hooks.rs — HOOK_ENV_ALLOWLIST

Six names and no others. SYSTEMROOT and COMSPEC are Windows process-creation requirements rather than policy; the other four are what a small program needs to find its interpreter and behave. This process holds ANTHROPIC_API_KEY, and a hook gets what it needs to execute and nothing that would let it call a paid API as Emma. A hook that needs a value reads it from a file next to itself. certified Six entries at commit a3eba74: grep -n "HOOK_ENV_ALLOWLIST" -A2 crates/harness/src/hooks.rs prints the two lines above.

contained_command is the only place this crate configures a child process: an argv exec of an already-contained path, with no shell, no PATH lookup and no argument string for anything to be interpolated into. All three pipes are piped, kill_on_drop is set, and the environment is cleared and then repopulated from the allowlist. It is shared with the status line rather than copied, so there is no second spawn site that could omit the env_clear.

The three events

EventFiresCan doWhen it crashes, times out or writes garbage
PreToolUse before every matching tool call deny the call, with a reason; append context fail-closed: the call is stopped, so a broken policy check does not become no policy check
PostToolUse after the call, on success and on a tool error append text to the model-visible result; it can annotate, never rewrite fail-open: the tool ran and the side effect happened, so refusing now would make the log disagree with what the model saw
UserPromptSubmit once, on the words a person typed, before the goal opens block the prompt; add context in front of the model, the only event that can add rather than only refuse fail-open, with a notice: the prompt proceeds without the context and one sentence per silent hook reaches the terminal
crates/harness/src/hooks.rs — run, run_prompt, PromptVerdict::notices

The first two rulings are one condition at the end of run: 

// The two hook stages are asymmetric.
// A `PreToolUse` hook that denies — or that times out, crashes, or
// answers with garbage — stops the call: ambiguity resolves to deny,
// because a broken policy check must not degrade into no policy check. A
// `PostToolUse` failure changes nothing: the tool ran, the side effect
// happened, the result is already recorded, and pretending otherwise
// would make the log lie about what the model saw.
if denied && event == HookEvent::PreToolUse {
    verdict.denied =
        Some(reason.unwrap_or_else(|| "This call was blocked by policy.".into()));
    return verdict;
}
crates/harness/src/hooks.rs — run

denied is run.outcome != HookOutcome::Allow, so a failure and a refusal reach the same branch. A denial short-circuits: hooks after it in the loop do not run. Hooks run in hook-name order, which is the key in the hooks map, sorted, and not declaration order, which JSON does not preserve anyway. run also filters out UserPromptSubmit explicitly as well as by event, so a caller passing it by mistake dispatches nothing rather than handing a prompt hook a payload with a tool name in it and no prompt.

crates/harness/src/hooks.rs — run, ResolvedHook::matches

The third ruling

Resolving an enrichment failure to deny would mean a hook script with a syntax error locks the user out of their own agent: every prompt refused, by the program that was supposed to add the branch name to it. Losing the enrichment silently is what PromptVerdict::notices prevents; losing it visibly is a bad turn the user can see and fix. This is also Claude Code's documented behaviour on the event, so an existing configuration behaves the same under both runtimes.

Blocking is still available there, because a hook that says block is answering rather than failing. Both Claude Code spellings are honoured: a JSON decision, and exit code 2 with the reason on stderr. run_prompt converts an exit code of exactly 2 into HookOutcome::Deny and, when the hook printed no reason, lifts the first non-empty line of stderr into one. Every other non-zero exit stays a crash and takes the fail-open path.

crates/harness/src/hooks.rs — run_prompt

notices emits one sentence per failed run, in three shapes depending on whether stderr had a first line and whether an exit code was captured, and it emits any systemMessage whether or not the hook also failed. systemMessage is the hook talking to the person and is kept in its own field, away from context, because one of those two is paid for in tokens and read by a model.

permissionDecision: "ask" maps to deny, because Emma's approval gate is asked separately and a hook that wanted a human is not asking for the call to proceed unattended.

A compatibility feature that turns a working upstream hook into a wall is not a compatibility feature.

Unparseable stdout

On UserPromptSubmit, stdout that is not JSON is the context. That is the documented primary form, and requiring JSON there made a hook doing the ordinary thing, echo a line and exit 0, record "unparseable stdout" and discard the line. observed: found by running one, recorded in the comment at that branch; the transcript of that run is not kept. On the other two events unreadable stdout is a hook that meant something it failed to say, and PreToolUse denies on it.

crates/harness/src/hooks.rs — ResolvedHook::invoke, the from_str else-branch

Empty stdout with exit 0 is the normal answer for an observer and resolves to Allow. HookRun is initialised with outcome: HookOutcome::Failed, so every early return in invoke is a failure by construction and the default is the one that denies. A non-zero exit returns before stdout is looked at.

crates/harness/src/hooks.rs — ResolvedHook::invoke

Two verdict types come back to the caller. HookVerdict carries denied, the additive context list and the runs for the log; PromptVerdict carries blocked, context and runs. is_denied and is_blocked are one-line Option::is_some helpers over the first field of each and hold no argument. In PromptVerdict, blocked and context are independent: a hook that blocks contributes no context, since there is no turn to enrich, and a hook that enriches never blocks.

crates/harness/src/hooks.rs — the constants at the head of the file

HOOK_CONTEXT_CAP is Claude Code's own limit, kept to the character so a script sized against that documentation behaves the same here. It is not the pipe cap doing this job: HOOK_OUTPUT_CAP stops a program filling memory, this stops a program filling the prompt, which is a different resource with a different owner. The user pays for it by the token, on this turn and on every later turn that replays it. Claude Code spills the overflow to a file and passes the path; Emma truncates and says so in the text, because a path is only useful to a model that can read the file.

truncate_on_a_char_boundary is why the two character caps are safe. String::truncate panics on a byte index inside a character, and a hook's reason is arbitrary text from an arbitrary program: a 400-byte cut through a multi-byte character would take the process down at the exact moment a policy was being explained. It walks the index down to the last boundary at or below the cap.

crates/harness/src/hooks.rs — truncate_on_a_char_boundary, HOOK_CONTEXT_CAP

What a hook is told

A tool hook receives event, tool_name, tool_call_id, args, session_id, turn_id and the operator's own config_text. On PostToolUse it also receives result_content, truncated and error, the last being null on success. An audit hook that cannot tell a success from a failure is an audit log that cannot answer the question it exists for.

HookCall is built by the caller field by field rather than from a &ToolOutcome, because display is for the terminal and is not what the model saw. A hook shown more than the model is shown would be a side channel the operator did not know they were operating, and plumbing another internal field through needs a signature change a reviewer will see.

crates/harness/src/hooks.rs — HookCall, HookResult, ResolvedHook::payload

A prompt hook receives event and hook_event_name both, then prompt, session_id, transcript_path, cwd and config_text. Two names for the event because event is Emma's, consistent across all three sites, and hook_event_name is what a script copied out of somebody's .claude/hooks/ reads. permission_mode is not sent: Emma's approval gate is not Claude Code's mode enum, and a plausible-looking "default" would be a fact a hook could branch on and be wrong about. PromptCall is a separate type from HookCall rather than a variant, because the two payloads have no field in common beyond the session, and a tool hook that could read the prompt would be another side channel nobody configured.

Hooks may daemonize

Ruled by the owner on 2026-08-14, reversing the first draft of the plan that was written to stop it: a hook that starts something meant to outlive it is a supported use, not a leak. That removed the draft's central mechanism, a Windows job object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE plus a Unix process group and a kill(-pgid) drop-guard. The plan records it as dead so it is not rebuilt.

notes/plans/process-lifetime.md §1, §7

The defect was never that a grandchild lives. It was that exec read stdout to end-of-file and then waited, so a hook that started a background process and exited 0 in milliseconds was reported as timed out after 5000ms with its output discarded, not because anything was slow, but because the process it started inherited the write end of the pipe and EOF never came.

Reproduced as a rate: 20 of 20 invocations misreported before the fix, 0 of 20 after, with the daemon surviving 20 of 20 in both. observed: the before/after comparison ran once, on 2026-08-14, logged in notes/plans/process-lifetime.md §6. The "before" half needs the reverted code to reproduce, so nobody can run it again as it stands. The "after" half is on demand: tested crates/harness/tests/exec_lifetime.rs cargo test -p emma-harness --test exec_lifetime certify_the_misreport_rate_over_twenty_trials -- --ignored loops twenty times and asserts misreported == 0 and daemon_survived == 20. certified That the test exists with those two assertions, and that #[ignore] is why an ordinary run does not reach it: cargo test -p emma-harness --test exec_lifetime at commit a3eba74 reports 6 passed, 0 failed, 2 ignored in 14.21s on this Windows box. The twenty-trial certification is one of the two skipped. It was not executed for this page.

The order in exec

pub(crate) async fn exec(
    cmd: &mut tokio::process::Command,
    body: String,
) -> std::io::Result<(Option<i32>, Vec<u8>, Vec<u8>)> {
    let mut child = cmd.spawn()?;
    if let Some(mut stdin) = child.stdin.take() {
        // A hook that ignores stdin and exits gives us EPIPE. That is its
        // choice, not a failure.
        let _ = stdin.write_all(body.as_bytes()).await;
    }
    let (mut out, mut err) = (Vec::new(), Vec::new());
    let (mut so, mut se) = (child.stdout.take(), child.stderr.take());

    let status;
    {
        // Both pipes, concurrently with the wait. The buffers are borrowed
        // rather than owned by the futures precisely so that abandoning a read
        // keeps the bytes it already collected.
        let both = async {
            tokio::join!(
                async {
                    if let Some(r) = so.as_mut() {
                        let _ = drain(r, &mut out).await;
                    }
                },
                async {
                    if let Some(r) = se.as_mut() {
                        let _ = drain(r, &mut err).await;
                    }
                }
            );
        };
        tokio::pin!(both);
        let mut exited = None;
        tokio::select! {
            // Both pipes reached EOF (or the cap) first: the ordinary case with
            // no grandchild anywhere, and `wait` below returns immediately.
            _ = &mut both => {}
            s = child.wait() => exited = Some(s?),
        }
        status = match exited {
            Some(s) => {
                // The hook is done. Give whatever is still in the pipes a
                // moment to arrive, then stop: a write end we do not own may
                // stay open indefinitely and is not ours to wait for.
                let _ = tokio::time::timeout(Duration::from_millis(EXEC_DRAIN_GRACE_MS), &mut both)
                    .await;
                s
            }
            None => child.wait().await?,
        };
    }

    // Emma's read ends, closed. The write ends belong to whatever still holds
    // them and die with it; nothing is retained here.
    drop(so);
    drop(se);
    Ok((status.code(), out, err))
}
crates/harness/src/hooks.rs — exec, quoted entire

drain is hand-rolled instead of take(cap).read_to_end(buf) because the future is abandoned when the grace expires, and read_to_end is documented as not cancellation-safe: what it has read so far is not guaranteed to be in the buffer. Here the cancellation boundary is one read call, and every byte that returned from one is already appended. It stops at HOOK_OUTPUT_CAP, and the n.min(room) is what keeps the last chunk from overshooting. 

async fn drain<R>(r: &mut R, buf: &mut Vec<u8>) -> std::io::Result<()>
where
    R: tokio::io::AsyncRead + Unpin,
{
    let mut chunk = [0u8; 8 * 1024];
    while (buf.len() as u64) < HOOK_OUTPUT_CAP {
        let n = r.read(&mut chunk).await?;
        if n == 0 {
            return Ok(());
        }
        let room = HOOK_OUTPUT_CAP as usize - buf.len();
        buf.extend_from_slice(&chunk[..n.min(room)]);
    }
    Ok(())
}

A budget rather than an event

Once a write end may outlive the child there is no observable event meaning "the hook's own output is complete". End-of-file arrives when the last writer closes, which may be days later, and a pipe cannot say which writer a byte came from. What is knowable is that everything the hook itself wrote completed into the pipe buffer before exit could run, so a grace long enough to drain a local buffer captures all of it. A daemon's bytes that land inside the grace ride along, bounded by the 64 KiB cap and not separable without attribution the pipe does not offer.

crates/harness/src/hooks.rs — EXEC_DRAIN_GRACE_MS

Windows is what makes abandoning the pipe safe: there is no SIGPIPE. A write into a broken pipe returns ERROR_BROKEN_PIPE, an error code the writer may ignore, so a staged grandchild that keeps writing to the inherited stdout after Emma walks away is still alive seconds later. tokio also gives a child's stdio overlapped I/O on Windows, so an unfinished read is a cancelled future rather than a thread stuck in a blocking ReadFile. Historically mutation-tested crates/harness/tests/exec_lifetime.rs by six Windows fixtures, among them a_hook_that_exited_zero_is_not_reported_as_timed_out_because_a_grandchild_holds_the_pipe, a_daemonizing_hooks_child_is_still_running_after_emma_walks_away and a_timed_out_hooks_descendants_survive_by_ruling_not_by_accident. Each failure says the grandchild never recorded its pids and “the fixture did not stage the defect.” The failure is in fixture setup, before the asserted lifetime behaviour, so it neither confirms nor refutes that behaviour here.

The unix edge

On unix, closing the read end means a daemon that later writes to that stdout gets SIGPIPE and, by default, dies. Two things bound it: this is not new, since the timeout path already dropped the pipe, and a long-lived reader was never on offer; and the daemon idiom exists because inherited stdio is borrowed. A hook that starts a daemon should redirect its stdio to /dev/null (or NUL) first. The alternative, Emma keeping a reader alive for as long as somebody else's daemon lives, is an unbounded obligation and is refused.

The lifetime rule

Emma supervises the direct child it spawned, meaning its budget, its pipes and its exit code, and claims nothing about that child's descendants. On the timeout path kill_on_drop kills the hook and only the hook. Whatever the hook started is left, because Emma cannot tell a broken hook's orphans from the daemon the operator meant to start.

The cost is stated as a cost: a hung hook's descendants are unreclaimable, nothing short of reaping bounds that, and the only available mitigation is a clause in the transcript telling the operator to look. That is a report, not a bound.

StatusLine::run calls the same exec, so it inherits both the fix and the ruling, and a status script runs on a debounced trigger many times per session, so one that daemonizes accumulates a process per burst.
