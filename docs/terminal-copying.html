Getting text out of the frame

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Copying out

The full-screen frame took the terminal's own copy-paste away, and gave back three routes instead of one. Shift+drag is the terminal's selection, still there and still whole-row. /copy puts the last answer on the clipboard with an escape sequence. /export writes the conversation to a file and is the only one of the three that works when Emma is being piped. None of them is the plain drag that worked before 2026-08-12, and the page says why that is gone rather than pretending it was replaced.

The wheel cost the drag

On the alternate screen the mouse wheel does nothing at all without mouse capture. Not less useful: nothing. The frame turns capture on for that reason, and capture is all-or-nothing, so plain drag-selection goes with it.

crates/emma/src/term/frame.rs, Frame::start

if !inline {
    // Mouse capture, for the wheel: on the alternate screen the wheel
    // does nothing at all without it — not "less useful", nothing —
    // and the first instinct of anybody reading a long answer is the
    // wheel (`notes/audits/eval-tui-fullscreen-kimi.md` §1.5). The cost is
    // that plain drag-selection now needs Shift; the quick-help table
    // says so, because it is the one fact a user cannot guess. Only
    // on the full-screen path: inline, the terminal owns the wheel
    // and taking it would break scrollback that still works.
    if execute!(std::io::stdout(), EnableMouseCapture).is_ok() {
        MOUSE_ON.store(true, Ordering::SeqCst);
    }
}

Two facts close off the obvious fix. Crossterm's EnableMouseCapture is the widest tracking mode and has no narrower option, so "capture only the wheel" is not something the dependency offers. And on Windows the enable is a console-mode bit rather than escape bytes, which is why the leave path goes back through crossterm instead of writing the ?100x lows itself. certified Grep EnableMouseCapture across crates/emma/src: two hits, both in frame.rs, one enable and one disable.

crates/emma/src/term/frame.rs, the leave path

if MOUSE_ON.swap(false, Ordering::SeqCst) {
    // Through crossterm rather than a string on purpose: on Windows the
    // enable was a console-mode change, and only the matching command
    // undoes it. On unix this writes the `?100x` lows.
    let _ = execute!(std::io::stdout(), DisableMouseCapture);

Shift+drag, and the arm that refuses to bid for it

With capture on, the terminal still performs its own selection when the drag is Shift-modified. That is the one copy route on the alternate screen that involves no Emma code at all, so the input handler's job is to stay out of its way. Exactly one click is routed, a plain left press with no Shift; drags, releases and every other button fall through untouched.

crates/emma/src/term/input.rs, the reader thread

// The wheel, which mouse capture exists for: without capture,
// on the alternate screen, it does nothing at all. Beyond the
// wheel, exactly one click is routed: a plain left *press*,
// to the frame's single click target (the sidebar's collapse
// affordance — the route the owner actually tried when the
// toggle "did not work"). Drags, releases and every other
// button fall through untouched, and anything Shift-modified
// is refused even where a terminal forwards it: Shift-drag is
// the terminal's own selection — the one copy route left on
// the alternate screen — and this arm must never bid for it.
// A click mutates view state through the frame and never
// enters the line channel, same as the wheel.
Ok(Event::Mouse(mouse)) => match mouse.kind {
    MouseEventKind::ScrollUp => thread_frame.scroll_rows(true, WHEEL_ROWS),
    MouseEventKind::ScrollDown => thread_frame.scroll_rows(false, WHEEL_ROWS),
    MouseEventKind::Down(MouseButton::Left)
        if !mouse.modifiers.contains(KeyModifiers::SHIFT) =>
    {
        thread_frame.click(mouse.column, mouse.row);
    }
    _ => {}
},

Shift+drag appears in the QUICK HELP table for the reason the table's own doc comment gives: mouse capture taking plain drag away is the one fact a user cannot guess. certified keymap() in crates/emma/src/term/app.rs lists eleven rows and ("Shift+drag", "select text") is the last.

What Shift+drag gives back is a whole-row selection, which is not what a reader wants from a framed layout. Every line comes with the sidebar's columns, the borders and the gutter welded onto it. Collapsing the sidebar with Ctrl+B narrows the damage and does not remove it. unverified Nobody has recorded what a Shift+drag selection actually contains on a real Windows Terminal with the sidebar open. Settling it takes a person, a console and a paste into an editor; the byte-capture harness cannot see it, because the terminal's selection never passes through Emma.

/copy, and where INV-001 is enforced

/copy sidesteps the whole contest by not copying the screen. It reads the session log, finds the last assistant turn that said something rather than only calling tools, and sends that markdown source to the terminal with OSC 52: ESC ] 52 ; c ; <base64> BEL. The terminal does the clipboard write, which is why this works the same way locally and over SSH and needs no platform API.

It is an escape sequence, so it is refused wherever escape sequences are. INV-001 promises zero escape bytes on -p, on a pipe, under EMMA_NO_FRAME and with no console.

crates/emma/src/term.rs, Term::clipboard

/// platform clipboard API. Windows Terminal has supported it since 2020.
///
/// **Callers check [`Term::framed`] first so they can say something useful,
/// and this refuses anyway.** This emits escape bytes, and `INV-001`
/// promises none of those on `-p`, on a pipe, under `EMMA_NO_FRAME` or with
/// no console. The call-site guard stays because a clipboard write that
/// silently does nothing is the failure this whole area is about — the
/// caller has a message to give, and this function does not.
///
/// **But "callers must" was the whole of the enforcement, and a reviewer
/// found nothing tested it.** No test in the workspace named `Copy`, so
/// deleting the single `if !s.term.framed()` at the call site emitted OSC 52
/// on a pipe with the entire suite green. An invariant held up by a sentence
/// in a doc comment is held up by nothing; the refusal belongs at the one
/// place that can emit the bytes, and the message belongs where there is
/// somebody to read it.
///
/// Returns whether it wrote, so the guarantee is observable rather than
/// merely performed — the same correction `read_reporting` and
/// `SessionLog::transcript_failed` already made elsewhere in this tree.
///
/// **There is no acknowledgement.** The terminal honours the sequence or
/// ignores it, with no reply and no error, so nothing downstream can report
/// success as a fact. Callers say what was sent, never what arrived.
pub fn clipboard(&self, text: &str) -> bool {
    if !self.framed() {
        return false;
    }
    // Straight to stdout rather than through `write_out`, which routes prose
    // into the frame retained transcript. This is a control sequence, not
    // content: a buffer that held it would replay somebody clipboard write
    // on every redraw.
    //
    // Writing under the frame is safe because OSC 52 draws nothing - it
    // moves no cursor and paints no cell, so it cannot disturb a frame
    // mid-paint the way an unsolicited line would.
    use std::io::Write as _;
    let mut out = std::io::stdout();
    let seq = format!("\x1b]52;c;{}\x07", base64(text.as_bytes()));
    let _ = out.write_all(seq.as_bytes());
    let _ = out.flush();
    true
}

The refusal sits in the function that writes the bytes, and it did not always. Until 2026-08-23 the doc comment asked callers to check framed() first and the single call site did, which meant the invariant rested on one if and a sentence. An adversarial reviewer found that no test in the workspace named Copy: deleting that line emitted OSC 52 into a pipe with the whole suite green. tested an_unframed_terminal_refuses_to_write_the_clipboard in term.rs covers all four unframed constructors. Removing the guard turns it red, and the harness stdout then carries ]52;c;YW55dGhpbmcgYXQgYWxs, the forbidden sequence in a pipe, visible.

Both guards remain, and they do different jobs. The one at the call site has an operator to explain the refusal to. The one in clipboard has the bytes. What connects them is the return value: the report follows what was written rather than what was called, so it cannot say "sent" about bytes that never left.

crates/emma/src/session_command.rs, copy_last_answer

Emma never claims the clipboard received anything. OSC 52 has no acknowledgement in the protocol, so there is no reply to wait for and nothing downstream can report success as a fact. The note says how many characters were sent and that a terminal without OSC 52 will silently drop them. unverified Whether the sequence reaches the clipboard in the owner's Windows Terminal has not been observed. The PTY harness can prove the bytes go out and never that they arrived; settling it needs a person to press /copy and then Ctrl+V.

The base64 encoder is written out rather than pulled in as a dependency, and it is checked against the RFC 4648 vectors rather than against itself. A hand-written encoder is the thing to check against somebody else's numbers. tested the_encoder_matches_the_published_vectors and utf8_round_trips_through_the_encoder in crates/emma/src/term.rs.

/export, the route that survives a pipe

/export writes goals and assistant turns to a markdown file. With no argument it lands beside the session log, named after it, because the session id is the name somebody would reach for and the working directory is usually a repository the user is editing. It reads the same session log /copy does and writes a file rather than an escape sequence, so it is the one route that works on -p, on a pipe and with no console.

A session log with records that cannot be parsed produces an incomplete export, and the file says so in its first line.

crates/emma/src/session_command.rs, export_conversation

// **A damaged log is said out loud, in the file and on screen.** `read_reporting`
// returns the lines it could not parse, and an export that quietly omitted
// them would produce a transcript that reads as complete. That is the exact
// failure the session log's own loss counting exists to prevent, and it
// would be undone here by not passing it on.
if !lost.is_empty() {
    let note = format!(
        "> **{} record(s) of this session could not be read and are missing below** \
         (line {}). This export is incomplete.\n\n",
        lost.len(),
        lost.iter()
            .take(5)
            .map(|n| n.to_string())
            .collect::<Vec<_>>()
            .join(", ")
    );
    out.insert_str(0, &note);
}

export is ordered after exit in the builtin list. Both answer the prefix /ex, the menu highlights the first match, and muscle memory of /ex then Enter would otherwise have written a file where the user meant to end the session. A new command does not get to take an established prefix. tested export_takes_a_path_or_nothing, and the ordering is visible in BUILTINS.

What the frame does not give back

Terminal scrollback is gone on the alternate screen and the retained transcript buffer replaces it, reachable by keys and the wheel rather than by the terminal's own history. Re-reading the styled run after exit is gone outright: the session JSONL named in the exit line is the record. notes/design/tui-fullscreen.md §2 lists what the reversal cost, and /export is the half of the answer that landed.

In-app drag-selection with copy-on-release has not been built. The original design named it as the eventual target, so building it would not revive a rejected approach. Claude Code's own fullscreen renderer captures the mouse exactly as Emma does and rebuilt selection in-app for the same reason. unverified That reading of Claude Code's renderer comes from the parity investigation recorded on UI-006 and has not been re-checked against a current build.
