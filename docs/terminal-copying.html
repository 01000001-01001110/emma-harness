Getting text out of the frame

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Run control Copying out

The full-screen frame took the terminal's own copy-paste away and gave back three routes instead of one. Shift+drag is the terminal's selection, still there and still whole-row. /copy puts the last answer on the clipboard with an escape sequence. /export writes the conversation to a file and is the only one of the three that works when Emma is being piped. Since 2026-09-06 there is a fourth: a plain drag inside the chat pane is Emma's own selection, drawn by Emma and copied by Emma, which is not the same thing as the one mouse capture took away.

The wheel cost the drag

On the alternate screen the mouse wheel does nothing at all without mouse capture. Not less useful: nothing. The frame turns capture on for that reason, and capture is all-or-nothing, so plain drag-selection goes with it.

crates/emma/src/term/frame.rs, Frame::start

if !inline {
    // Mouse capture, for the wheel: on the alternate screen the wheel
    // does nothing at all without it — not "less useful", nothing —
    // and the first instinct of anybody reading a long answer is the
    // wheel (the full-screen evaluation). The cost is
    // that plain drag-selection now needs Shift; the quick-help table
    // says so, because it is the one fact a user cannot guess. Only
    // on the full-screen path: inline, the terminal owns the wheel
    // and taking it would break scrollback that still works.
    if execute!(std::io::stdout(), EnableMouseCapture).is_ok() {
        MOUSE_ON.store(true, Ordering::SeqCst);
    }
}

Two facts close off the obvious fix. Crossterm's EnableMouseCapture is the widest tracking mode and has no narrower option, so "capture only the wheel" is not something the dependency offers. And on Windows the enable is a console-mode bit rather than escape bytes, which is why the leave path goes back through crossterm instead of writing the ?100x lows itself. certified Grep EnableMouseCapture across crates/emma/src: two hits, both in frame.rs, one enable and one disable.

crates/emma/src/term/frame.rs, the leave path

if MOUSE_ON.swap(false, Ordering::SeqCst) {
    // Through crossterm rather than a string on purpose: on Windows the
    // enable was a console-mode change, and only the matching command
    // undoes it. On unix this writes the `?100x` lows.
    let _ = execute!(std::io::stdout(), DisableMouseCapture);

Shift+drag, and the arm that refuses to bid for it

With capture on, the terminal still performs its own selection when the drag is Shift-modified. That is the one copy route on the alternate screen that involves no Emma code at all, so the input handler's job is to stay out of its way. Every mouse arm in the reader thread carries the same guard: a Shift-modified event is refused, whatever a terminal chooses to forward.

That guard is the whole of the arrangement. A Shift-modified press is refused here even where a terminal forwards it, so the terminal's own selection is never bid for; an unmodified one is Emma's, and what it reaches is decided in order: an open page first, then the sidebar's affordance, then the scrollbar, then the chat pane. The comment above the arm still says “drags, releases and every other button fall through untouched”, which stopped being true when the in-pane selection landed: there are Drag and Up arms below it now. certified Read input.rs from that comment to the end of the Event::Mouse match: four arms, not three.

Shift+drag appears in the QUICK HELP table for the reason the table's own doc comment gives: mouse capture taking plain drag away is the one fact a user cannot guess. certified The table is bindings::CHAT now rather than app::keymap(), it holds twelve drawn bindings, and Trigger::Terminal("Shift+drag") with what: "select text" is the last of them. Trigger::Terminal is its own variant because a mouse gesture has no KeyCode to derive a label from, so that row's spelling is given rather than resolved.

What Shift+drag gives back is a whole-row selection, which is not what a reader wants from a framed layout. Every line comes with the sidebar's columns, the borders and the gutter welded onto it. Collapsing the sidebar with Ctrl+B narrows the damage and does not remove it. unverified Nobody has recorded what a Shift+drag selection actually contains on a real Windows Terminal with the sidebar open. Settling it takes a person, a console and a paste into an editor; the byte-capture harness cannot see it, because the terminal's selection never passes through Emma.

The in-pane selection, in content rows

A plain drag in the chat pane selects text, highlights it in reverse video, and puts it on the clipboard on release. It exists only while mouse capture is on, and that is not a rule this code writes: capture is what routes a drag to the program at all. Ctrl-S hands the mouse back, no mouse event arrives, and the terminal's own selection works as it does everywhere else. So the two selections cannot both be live, no mode flag decides between them, and the Shift+drag fallback above stays the fallback.

crates/emma/src/term/app.rs — the region header

The anchor and the head are content rows, not screen rows. cell_at adds the window's start to the row under the pointer, so a selection means the same text after the view has moved under a held button. Screen coordinates would have meant a drag that scrolls quietly reselects whatever slid into the row the pointer is on, which is the failure that makes edge auto-scroll useless. 

/// The pointer moved with the button down. Clamped into the pane rather
/// than dropped: a drag that runs off the edge is a normal drag, and
/// losing it there would leave a selection that stops mid-word.
///
/// A pointer *on* the edge row scrolls the view instead of stopping
/// there, which is what every editor does and what makes a selection
/// longer than the pane possible at all. See [`Self::selection_scroll`].
pub fn selection_extend(&mut self, col: u16, row: u16) {
    let Some((anchor, _)) = self.selection else {
        return;
    };
    let pane = self.chat_rect;
    if pane.width == 0 || pane.height == 0 {
        return;
    }
    // Scroll first, then read the head: the row the pointer is on now
    // holds different text than it did a moment ago, and the head belongs
    // to the text rather than to the cell.
    self.selection_scroll(pane, row);
    let x = col.clamp(pane.x, pane.right() - 1) - pane.x;
    let y = row.clamp(pane.y, pane.bottom() - 1) - pane.y;
    let start = self.transcript.window_start(pane.height);
    self.selection = Some((anchor, (start + usize::from(y), x)));
}
crates/emma/src/term/app.rs — selection_extend

The order in that function is the argument: scroll first, then read the head. The row the pointer is on holds different text after the scroll than before it, and the head belongs to the text rather than to the cell. Reading the head first would place it one screenful behind on every edge event. tested the_anchor_stays_on_its_row_while_the_drag_scrolls and a_drag_at_the_top_edge_reveals_rows_and_copies_them; the second is what goes red when the rebase in selection_text is pinned to zero. 

/// One step of drag auto-scroll, or nothing when the pointer is inside
/// the pane.
///
/// ⚠ A STEP PER EVENT, AND NO TIMER. A terminal mouse only reports on
/// movement, so holding still at the edge reports nothing and this
/// repeats only while the pointer keeps moving. That is the honest thing
/// a cell grid can do without a repaint loop running off a clock, which
/// is the same argument the copy notice's ⚠ makes about chrome that
/// changes with no event behind it.
///
/// The far step is the wheel's, not a new number: a pointer well past the
/// edge is asking for distance, and the reader already knows what three
/// rows feels like.
fn selection_scroll(&mut self, pane: Rect, row: u16) {
    let last = pane.bottom() - 1;
    let (up, past) = if row <= pane.y {
        (true, pane.y - row)
    } else if row >= last {
        (false, row - last)
    } else {
        return;
    };
    let step = if past > 1 { DRAG_FAR_ROWS } else { 1 };
    if up {
        self.transcript.scroll_up(step);
        // The bar's clamp, for the bar's reason: offset past `max_offset`
        // is travel the view cannot show, and a drag held at the top edge
        // would bank a row of it per event and then spend the way back
        // down undoing it.
        let top = transcript::max_offset(self.transcript.total_rows(), pane.height);
        if self.transcript.scroll_offset() > top {
            self.transcript.scroll_to(top);
        }
    } else {
        self.transcript.scroll_down(step);
    }
}
crates/emma/src/term/app.rs — selection_scroll, DRAG_FAR_ROWS

Three things in that function are worth stating rather than deducing. A pointer on the pane's first or last row scrolls one row per event, and a pointer more than one row past it takes DRAG_FAR_ROWS, which is the wheel's WHEEL_ROWS rather than a second three: an overshoot is asking for distance, and the reader already knows what the wheel's step feels like. The upward case is clamped to max_offset for the scrollbar's reason, because offset past it is travel the view cannot show, and a drag held at the top edge would otherwise bank a row of it per event and spend the way back down undoing it. And there is no timer: a terminal mouse reports only on movement, so holding still at the edge repeats nothing. That is what a cell grid can honestly do without a repaint loop running off a clock. tested a_pointer_well_past_the_pane_scrolls_by_the_wheels_step, the_top_edge_drag_stops_at_the_last_row_the_view_can_show, the_bottom_edge_drag_stops_at_the_tail, a_drag_inside_the_pane_scrolls_nothing and a_stationary_pointer_neither_moves_the_view_nor_drops_the_drag. Making selection_scroll a no-op turns five of them red.

The paint keeps what the selection may still need. record_cells stores the rows it drew together with the window's origin, chat_cells_start. While nothing is selected the snapshot is the pane and nothing more. While a drag is live it extends at whichever end the scroll revealed, because those rows are inside the selection and the pane no longer holds them; a window that has jumped clear of what is kept starts over, since nothing between the two was ever painted. selection_text then rebases a content row into the snapshot it has, subtracting chat_cells_start with a saturating subtraction so a row above the snapshot clamps rather than wraps. highlight paints only the rows the window is showing, so a selection running off either end shows the part that is on screen and no more.

The pane is the only surface that selects. The sidebar, the input box and the bar are chrome, and a selection over them would copy furniture. A press in the scrollbar's column never starts one, and no other screen can be selected over. tested a_press_in_the_bars_column_never_starts_a_selection, no_other_screen_can_be_selected_over, the_bar_and_the_text_drag_stay_distinct_under_auto_scroll.

/copy, and where INV-001 is enforced

/copy sidesteps the whole contest by not copying the screen. It reads the session log, finds the last assistant turn that said something rather than only calling tools, and sends that markdown source to the terminal with OSC 52: ESC ] 52 ; c ; <base64> BEL. The terminal does the clipboard write, which is why this works the same way locally and over SSH and needs no platform API.

It is an escape sequence, so it is refused wherever escape sequences are. INV-001 promises zero escape bytes on -p, on a pipe, under EMMA_NO_FRAME and with no console.

crates/emma/src/term.rs, Term::clipboard

/// platform clipboard API. Windows Terminal has supported it since 2020.
///
/// **Callers check [`Term::framed`] first so they can say something useful,
/// and this refuses anyway.** This emits escape bytes, and `INV-001`
/// promises none of those on `-p`, on a pipe, under `EMMA_NO_FRAME` or with
/// no console. The call-site guard stays because a clipboard write that
/// silently does nothing is the failure this whole area is about — the
/// caller has a message to give, and this function does not.
///
/// **But "callers must" was the whole of the enforcement, and a reviewer
/// found nothing tested it.** No test in the workspace named `Copy`, so
/// deleting the single `if !s.term.framed()` at the call site emitted OSC 52
/// on a pipe with the entire suite green. An invariant held up by a sentence
/// in a doc comment is held up by nothing; the refusal belongs at the one
/// place that can emit the bytes, and the message belongs where there is
/// somebody to read it.
///
/// Returns whether it wrote, so the guarantee is observable rather than
/// merely performed — the same correction `read_reporting` and
/// `SessionLog::transcript_failed` already made elsewhere in this tree.
///
/// **There is no acknowledgement.** The terminal honours the sequence or
/// ignores it, with no reply and no error, so nothing downstream can report
/// success as a fact. Callers say what was sent, never what arrived.
pub fn clipboard(&self, text: &str) -> bool {
    if !self.framed() {
        return false;
    }
    // Straight to stdout rather than through `write_out`, which routes prose
    // into the frame retained transcript. This is a control sequence, not
    // content: a buffer that held it would replay somebody clipboard write
    // on every redraw.
    //
    // Writing under the frame is safe because OSC 52 draws nothing - it
    // moves no cursor and paints no cell, so it cannot disturb a frame
    // mid-paint the way an unsolicited line would.
    use std::io::Write as _;
    let mut out = std::io::stdout();
    let seq = format!("\x1b]52;c;{}\x07", base64(text.as_bytes()));
    let _ = out.write_all(seq.as_bytes());
    let _ = out.flush();
    true
}

The refusal sits in the function that writes the bytes. Until 2026-08-23 only the call site checked framed(); the doc comment asked callers to do the same. No test named Copy guarded that path: deleting the call-site check emitted OSC 52 into a pipe with the whole suite green. tested an_unframed_terminal_refuses_to_write_the_clipboard in term.rs covers all four unframed constructors. Removing the guard turns it red, and the harness stdout then carries ]52;c;YW55dGhpbmcgYXQgYWxs, the forbidden sequence in a pipe, visible.

Both guards remain and do different jobs. The one at the call site has an operator to explain the refusal to. The one in clipboard has the bytes. The return value connects them: the report follows what was written, not what was called, so it cannot say "sent" about bytes that never left.

/export, the route that survives a pipe

/export writes goals and assistant turns to a markdown file. With no argument it lands beside the session log, named after it, because the session id is the name somebody would reach for and the working directory is usually a repository the user is editing. It reads the same session log /copy does and writes a file rather than an escape sequence, so it is the one route that works on -p, on a pipe and with no console.

A session log with records that cannot be parsed produces an incomplete export, and the file says so in its first line.

crates/emma/src/session_command.rs, export_conversation

// **A damaged log is said out loud, in the file and on screen.** `read_reporting`
// returns the lines it could not parse, and an export that quietly omitted
// them would produce a transcript that reads as complete. That is the exact
// failure the session log's own loss counting exists to prevent, and it
// would be undone here by not passing it on.
if !lost.is_empty() {
    let note = format!(
        "> **{} record(s) of this session could not be read and are missing below** \
         (line {}). This export is incomplete.\n\n",
        lost.len(),
        lost.iter()
            .take(5)
            .map(|n| n.to_string())
            .collect::<Vec<_>>()
            .join(", ")
    );
    out.insert_str(0, &note);
}

export is ordered after exit in the builtin list. Both answer the prefix /ex, the menu highlights the first match, and muscle memory of /ex then Enter would otherwise have written a file where the user meant to end the session. A new command does not get to take an established prefix. tested export_takes_a_path_or_nothing, and the ordering is visible in BUILTINS.

What the frame does not give back

Terminal scrollback is gone on the alternate screen and the retained transcript buffer replaces it, reachable by keys and the wheel rather than by the terminal's own history. Re-reading the styled run after exit is gone outright: the session JSONL named in the exit line is the record. The full-screen TUI design lists what the reversal cost, and /export is the half of the answer that landed.

In-app drag-selection with copy-on-release landed on 2026-09-06 and this paragraph used to say it had not been built. The original design named it as the eventual target, so it revived nothing that had been rejected. The section above is what it does; what stays gone is the terminal's own selection over the whole screen, which no amount of in-app work reaches while capture is on.
