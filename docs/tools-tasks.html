The task list: four tools over one file

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP

.emma/tasks/tasks.md is not a serialisation format that happens to be text. It is a document somebody has open in an editor while the agent works, and every constraint in the parser follows from that.

A line nobody changed is written back byte for byte. Nothing is reordered. Completing a task ticks a box where it sits. When a person's edit disappears they stop trusting the file, then stop reading it.

tools/tasks/src/lib.rs — module doc

The four tools

ToolArgumentsmeta
TaskCreate tasks: array, minItems: 1. Each item is a plain string, or an object with text and an optional status of pending / in_progress / completed write, not idempotent
TaskGet id: the handle, leading # optional read-only
TaskList status: open (default), all, pending, in_progress, completed read-only
TaskUpdate id required, plus status and/or text write, idempotent

TaskUpdate declaring idempotent: true where Edit declares false is the distinction working. Setting a status to what it already is leaves the same file and there is no anchor to consume, so a replay is safe. TaskCreate is not idempotent because two genuinely identical steps in a plan happen, and nothing here deduplicates by text.

An id that is not in the file is an argument error rather than an empty result. Returning nothing would teach the model that the task it just created has vanished, and its next move would be to create it again. A missing file, no tasks at all, and no tasks matching a filter are all Ok.

tools/tasks/src/{create,get,list,update}.rs

TaskCreate parses its whole list twice, once in validate_args and once in run. That is stated as a choice: validate_args is part of the trait's contract and callers may invoke it alone, so it cannot be the thing that produces the value, and run cannot assume it was called. The guarantee bought is that a plan with a bad fourth entry writes none of the first three.

The format

<!-- Emma maintains this file while it works. Edit it freely: reword a task,
     tick a box, add notes underneath one, reorder them, add headings of your
     own. Emma re-reads the file immediately before every write and keeps
     whatever it finds, including lines it did not write.

     `[ ]` not started   `[~]` in progress   `[x]` done
     Headings are yours; Emma reads the box, not the section.

     The `#abcd` at the end of a line is how Emma refers to that task. Reword
     the text as much as you like — keep the handle if you want the reference
     to survive. -->

- [ ] port the auth middleware `#a3f1`
- [~] write the migration `#7b02`
      needs the staging database back first
- [x] read the vendor's docs `#0c94`
tools/tasks/src/doc.rs — PREAMBLE

The path is fixed at .emma/tasks/tasks.md, because a configurable location would mean two agents in one project maintaining two lists neither knows about. Status lives in the checkbox glyph and nowhere else. The obvious alternative, ## In progress and ## Done sections, was rejected: making a heading authoritative means changing a status moves a line, which relocates the note a human wrote under it and reshuffles an order they chose. Rewriting one character in place does neither.

An unrecognised glyph parses as pending rather than as an error. Somebody typing [?] in an editor meant "a task", and refusing to see it would hide their work rather than surface it.

There is no Blocked status, and the reason is written into the enum: it is a relation, not a state. The moment it exists as a variant it asks "blocked by what?", and this format has nowhere to put the answer, so it degrades into a task sitting at [!] forever with the reason living in somebody's head. A blocked task is a pending task with a note under it, and notes are preserved verbatim.

The parser and round-trip

The document model is Vec<Line>, not Vec<Task>. Headings, blank lines, prose, a table, a task the writer would never have produced: all of it is held as the exact bytes it arrived as, and a line the parser did not recognise becomes Line::Raw, which has no rendering other than its original string. 

//! The safety here is structural rather than careful. Nothing in the parser has
//! to *decide* to preserve a line it does not understand; a line it did not
//! recognise as a checkbox becomes a `Line::Raw` holding the original string,
//! and `Raw` has no other rendering. A tolerant parser eventually is not
//! tolerant; one that never re-renders what it did not touch always is.

New text is the exception. When the words change there is no original spacing left to preserve, so the line comes back canonical: one space between bullet, box, text and handle. A line create synthesised takes the same branch, having never been anything else.

What counts as a task, and what counts as a note

split_checkbox accepts -, *, + or a number followed by . or ), then requires a space, then exactly one character between brackets. That last check is done on bytes, and the comment explains why it is safe: a UTF-8 continuation byte is 0x80..=0xBF and a lead byte is at least 0xC2, so neither can be ] at 0x5D. Byte 2 being ] therefore proves byte 1 is a single ASCII character.

split_id only recognises a handle at the very end of the line, which is what makes anything following it impossible to lose. It requires backticks, a #, and one to eight hex digits; anything else is part of the text.

A note is an indented, non-blank, non-task line following a task. Blank lines end the block, so a paragraph separated by whitespace reads as belonging to the document rather than to the task above it. Notes come back from TaskGet and are left out of TaskList, which lands in the model's context on every turn.

tools/tasks/src/doc.rs — split_checkbox, split_id, is_note_of, view

Handles, and the one hard limit

An id is an annotation, not a requirement. A checkbox line with no handle is a real task: its id is derived from a hash of its text, so it is addressable by TaskGet and TaskUpdate immediately, without a write. That is what lets TaskList stay genuinely read-only.

The handle is visible, at the end of the line, in backticks. An HTML comment parses more cleanly and is invisible in a rendered preview, which is the problem: what a person cannot see, they rewrite over without knowing it was there. 

/// **The space is 16 bits — 65,536 handles — and a file can exhaust it.** That
/// takes 65,536 tasks in one `tasks.md`, which is not a file anybody is
/// reading, but "nobody would" is not the same as "cannot" and this used to
/// claim the latter. Exhaustion panics, because the alternative is a duplicate
/// handle and `TaskGet` cannot see a duplicate: it would answer confidently
/// about the wrong task.
fn first_free_id(text: &str, taken: &[String]) -> String {
    const SPACE: usize = 1 << 16;
    // The distinct count is only paid for on the one branch where the space
    // could conceivably be full; `taken.len()` alone is the cheap gate.
    if taken.len() >= SPACE && taken.iter().collect::<BTreeSet<_>>().len() >= SPACE {
        panic!("all 65536 task handles in this file are in use; it cannot hold another task");
    }

The second panic in that function fires after 2^32 salts with a free handle known to exist. It says so rather than writing unreachable!, because nothing proves FNV-1a reaches every handle within that many salts and an unreachable! would be a claim about a hash function.

Salting rather than counting keeps the id opaque. A handle that read as #0001, #0002 would invite somebody to renumber them.

Nothing is truncated anywhere in this crate. No cap, no constant, no truncated flag ever set. The exhaustion above is the only hard numeric limit, and it is not a cut.

Two writers, no lock

You cannot lock a file a person is editing in VS Code. An advisory lock the editor does not take part in protects nothing, and a mandatory one turns their save into an error dialog. The strategy is to hold the file as briefly as possible and to notice when it moved. 

pub fn edit<T>(
    file: &Path,
    mut change: impl FnMut(&mut Doc) -> Result<T, ToolError>,
) -> Result<T, ToolError> {
    // Three, not one: two agents or an agent and a formatter can collide once
    // by chance. Three collisions in a row is a file being rewritten in a loop,
    // and retrying forever would hang the turn rather than report anything.
    for _ in 0..3 {
        let (mut doc, stamp) = load(file)?;
        let value = change(&mut doc)?;
        doc.stamp_ids();
        match replace_if_unchanged(file, stamp, &doc.render()) {
            Ok(()) => return Ok(value),
            Err(Collision) => continue,
        }
    }
    Err(ToolError::Failed(format!(
        "{RELATIVE_PATH} kept changing while it was being updated; \
         something else is writing it. Try again."
    )))
}
tools/tasks/src/store.rs — edit

The change closure is re-run against a freshly read document on a collision rather than forced on top of one, which is what makes a human's edit to a different task survive an agent's edit to this one. An error the closure returns, such as an unknown id, is returned as-is rather than retried.

The guard is a hash of the bytes, not the mtime. mtime has second granularity on some filesystems, which is an eternity next to this window, and a stamp that can silently fail to change is a stale-read guard that fails open. The hash is FNV-1a over the whole file and does not need to be cryptographic, because the other writer is a person saving in an editor.

The write goes to a sibling tasks.md.tmp and is renamed over the target, so a reader who opens the file mid-write sees the old version or the new one and never half of each. Beside the file rather than in the system temp directory, because a rename across filesystems is a copy and a copy is not atomic. On failure the temp file is removed, because a tasks.md.tmp left in somebody's repository is a bug report.

What the guard cannot catch

An editor holds the whole file in memory. If a person opened tasks.md at 10:00, Emma writes at 10:01, and the person hits Ctrl-S at 10:02, their editor writes its entire buffer and Emma's line is gone: no error, no conflict, because from the filesystem's point of view that is simply a newer complete file. Only the editor's own "file changed on disk" prompt prevents it, and that is the editor's to offer.

The guard's own window is not zero either. A write landing between the confirming read and the rename is lost. It is microseconds wide and not closed; the page says so.

read_only: true on TaskList is a fact

TaskList::run calls store::load and never store::edit, so nothing on that path can stamp a handle or create the file. Listing a project that has no tasks.md leaves it with no tasks.md. That is only possible because an unstamped task's id is derived from its text rather than assigned, so the tool can hand the model an id for a task the file has never been written to name.

The default filter is open rather than all. Completed tasks stay in the file forever, so by the end of a long run they outnumber the live ones several to one, and reprinting them every turn spends context re-establishing what is already settled. The file grows; the context does not. The counts in the result describe the whole file rather than the filtered slice, because a model that asked for pending still needs to know whether anything is in progress before concluding the work is stalled.

The three modules this page has not named

tools/tasks/src/get.rs is TaskGet: one task, with the prose a human wrote under it. An id that is not in the file is BadArguments rather than an empty result, because the call named something that is not there, which is a fact about the call and not about the world. It is the difference between there being no tasks, a perfectly good Ok from TaskList, and asking for #a3f1 when there is no #a3f1. An empty result for a bad id would teach the model that the task it just created has vanished, and its next move would be to create it again.

tools/tasks/src/get.rs — module doc, TaskGet

tools/tasks/src/update.rs is TaskUpdate, and it ticks a completed task's box where it sits. Not deleted, not moved to a ## Done section. Deleting throws away the note the person wrote underneath and is the one irreversible operation in the crate; the argument for it is that a file which only grows becomes noise, but the noise that matters is in the model's context and TaskList already defaults to open tasks. Moving to a section relocates the note and reshuffles an order somebody chose, every time a task completes, and it makes the file's structure carry data, so a person who reorganises the headings changes the record without meaning to. An unknown id is BadArguments, and so is an update that changes nothing, because a tool reporting success for a no-op is lying about what it did. certified: STATUSES in that file is pending, in_progress, completed, and KEYS is id, status, text.

tools/tasks/src/update.rs — module doc, TaskUpdate, STATUSES

tools/tasks/src/render.rs decides how a task reads back. TaskList is the call the loop makes most and its output lands in the context window again on every turn it is made, so line emits the checkbox, the handle and the text and nothing else: [~] #a3f1 port the auth middleware. Notes are left to TaskGet, since they are the part a person writes at length and paying for them every turn is how a task list becomes the reason a session runs out of room. counts puts the pending, in-progress and completed totals first, so a model that reads one line of the result already knows whether anything is outstanding.

tools/tasks/src/render.rs — line, counts, block

tools/tasks/src/args.rs is the argument reader, worded to match tools/fs and duplicated rather than shared because emma-tools-fs keeps its own args module private and this crate does not own that crate. The wording is copied rather than rewritten, because the model learns the shape of one argument error and then reads every other one, and a second dialect of the same message costs that for nothing. The file says where this ends. If a third tool crate appears, it belongs in tool-api. unverified Whether the three copies have stayed identical was not checked. Diffing tools/fs/src/args.rs, tools/tasks/src/args.rs and tools/lsp/src/args.rs side by side would settle it, and a divergence would be the first sign the shared-crate moment has arrived.

Two operations on the document that no tool reaches

Doc grew two public methods on 2026-09-06 and nothing calls either of them. move_task moves a task past its neighbour, and remove_completed drops every ticked task. They are here because the Harness page is the caller they were written for, and that package has not landed; a reader who greps for a TaskMove tool and finds nothing has found the truth rather than a hole. certified grep -rn "move_task\|remove_completed" --include=*.rs . matches only tools/tasks/src/doc.rs.

A move carries the block a task owns and nothing else, where "owns" is is_note_of, the rule view and insertion_point already use: the run of indented, non-blank, non-task lines directly underneath. Headings, blank separators and the preamble belong to nobody and stay at the offsets they are at. What makes the move its own inverse is that it swaps two blocks and leaves whatever sits between them in place: sliding the block up to the neighbour's first line instead would drag a blank separator with it and reshape the file over a few calls. tested: moving_a_task_down_and_back_up_reproduces_the_file compares bytes, a_moved_task_takes_its_notes_with_it pins the block, and moving_past_the_end_refuses_and_changes_nothing pins the refusal.

false from a move means nothing moved: either no task carries that id, or it is already the first or the last task in the document. There is no partial case between the two. A move also marks nothing dirty, because position is not part of a line's text, and stamping an id here would edit lines the caller did not name.

remove_completed is the one operation in the crate that removes a human's bytes, so it is scoped as tightly as it can be. A line goes only if it is a checkbox reading [x] or a note that checkbox owns. A ## Done heading, a blank line between tasks and any prose that is not indented under a completed task all stay where they are. It takes the notes with the task, so somebody who wrote a paragraph under a task they then completed loses it, which is why this is explicit and never something the tools do on their own initiative: TaskUpdate still cleans up by ticking a box. tested: removing_completed_tasks_leaves_everything_else_alone keeps the heading and the unowned prose.

block_of is the single definition of where a task ends, shared by both, so a move and a removal cannot disagree about it. Neither re-renders a line: every line involved is re-inserted, so a CRLF file comes back CRLF and a displaced note keeps its own bytes. tested: a_crlf_document_survives_a_move_and_a_removal is the fixture that says so, and it is the shape of the defect this repository has already paid for once in a frontmatter parser whose fixtures were all LF.

unverified Nobody has moved a task through a running Emma, because nothing in the interface can. Settling it needs the Harness page package and one press.
