The input dock

Three files meet at the bottom of the screen. view.rs draws the input box, the menu and the approval panel, and the full-screen frame borrows two of its renderers rather than growing its own. input.rs is the one place stdin is read, and holds the property in this subsystem that is not allowed to change. menu.rs decides what / shows and when it is allowed to show it.

The property that cannot regress

The queue must be empty before a question is asked. The reader is eager: it consumes whatever is typed, whenever it is typed, and holds it. Without a drain, a line typed while the agent was working is waiting when the next prompt appears and is handed over as the answer.

“That is not a stale-input annoyance — it is one question being answered by a keystroke aimed at another, and the place it matters most is the approval gate, where the line in question is a y.”

observed, on the first real run, and recorded in the module doc: an answered y outlived a turn that aborted on its token budget and was consumed as the next goal. The same path could as easily have approved a Bash command the user never saw, and left a log saying they approved it. The transcript of that run is not in the tree.

crates/emma/src/term/input.rs module doc

Raw mode strengthened this rather than weakening it. Under cooked mode there was a second buffer nothing in this process could reach: the line discipline held a partly-typed line, so a half-typed y followed by return after a question appeared would still answer it. In raw mode Emma holds that buffer itself.

crates/emma/src/term/input.rs · LineSource::drain

    pub fn drain(&mut self) -> usize {
        let mut dropped = 0;
        while self.rx.try_recv().is_ok() {
            dropped += 1;
        }
        if let Some(editing) = &self.editing {
            let mut ed = editing.lock().unwrap_or_else(|e| e.into_inner());
            if !ed.is_empty() {
                dropped += 1;
                ed.clear();
            }
        }
        // The menu is a third place a keystroke can sit: an open one has a
        // highlighted command, and Enter would turn it into a line. It closes
        // with the rest, and is not counted — nothing was typed into it that
        // the editor above did not already account for.
        if let Some(menu) = &self.menu {
            menu.lock().unwrap_or_else(|e| e.into_inner()).close();
        }
        if let Some(frame) = &self.frame {
            frame.set_input("", 0);
            frame.set_menu(None);
            frame.draw();
        }
        dropped
    }

Three hiding places, one call. The count is returned rather than swallowed “because silently eating a line a person typed is its own small betrayal”, and the caller says so. After a drain the input box is visibly empty, “which is the version of this property a user can check.”

tested, four ways. a_line_typed_before_the_question_cannot_answer_it is the original; a_half_typed_answer_is_drained_as_well_as_a_submitted_one is the ground raw mode gained, and its doc says it is written from the hole rather than from the implementation; draining_closes_the_command_menu_as_well checks the fixture really opened a menu first, “so this proves nothing” if it did not; and a_pasted_line_is_drained_like_a_typed_one covers the newest entrance. draining_an_empty_queue_drops_nothing_and_says_so guards the count, because “a false positive there tells a user their input was eaten when it was not.”

What never enters the channel

Four classes of keystroke are consumed reader-locally and never become a line: the pane keys, the tool chords, the four menu keys, and every mouse event. Each mutates view state through the frame and returns, so “a scroll cannot become a line, so it cannot answer a question”, and the drain guarantee is untouched by construction rather than by care.

The transcript's scroll position is likewise exempt from the drain, as a decision rather than an omission: “a scroll offset cannot answer a question, and yanking the reader's page because a prompt appeared would be hostile.”

The line editor

Fifteen match arms and a paste handler, and the scope is argued rather than left minimal by accident: “Everything here is a key that a user pressing it would be surprised not to have. Anything more — history, completion, word motion beyond Ctrl-W — is a text editor, and Emma already has one of those as a tool.”

Three of the arms are defensive rather than functional. A KeyEventKind::Release returns Ignore, because Windows reports both edges and acting on both types every character twice. Ctrl-C clears the buffer as well as interrupting, “a user who hits Ctrl-C and then types a goal must not find the interrupted line still in front of it.” And an unimplemented modifier arm catches every remaining Ctrl or Alt character:

Paste, and why it cannot submit

Without bracketed paste the terminal delivers a pasted block as the keystrokes it resembles, and the first \n in it is indistinguishable from Enter: half a code block is submitted as a goal and the other half is typed into whatever comes next. The red-team evaluation ranked that first on the list of things that would sink the redesign. ESC[?2004h from the frame makes the terminal wrap the block in markers, and crossterm hands it here as one Event::Paste. Nothing in Editor::paste can submit.

Line breaks become spaces, and a run of them collapses to one, because this editor is one line: “until [a multi-line editor] is [built], the choice is between flattening the paste and refusing it, and a flattened stack trace is still the stack trace the user meant to ask about.” Everything else that is not printable is dropped, tabs included, because a clipboard is untrusted bytes and “a tab in a cell is not eight columns, it is one cell containing a tab.”

What it lost is said out loud. The flattening is defensible and the silence was not: the next thing that happens after a paste is a model call, billed against text the clipboard did not hold. Editor::paste returns a PasteLoss counting joined line-break runs, flattened tabs and dropped control bytes, and the reader thread puts PasteLoss::note on screen through Frame::note_line when there is something to say. A run of breaks counts once, matching the single space that replaces it, so the number is one a reader can check against the clipboard.

This is half of DEF-028. The other half is keeping the breaks rather than reporting their loss, which needs the multi-line editor named as stage 0(a) of notes/design/tui-fullscreen.md and is not built.

tested: pasting_a_block_full_of_newlines_never_submits_it pastes fifty lines, asserts fifty joined breaks, asserts no newline survived, and then asserts it takes an actual Enter to send it. It no longer asserts Action::Edit, because paste returns the loss instead — a paste cannot submit, so the action was the one thing a caller could already work out. control_bytes_in_a_paste_never_reach_the_line pins the exact surviving string, safe[31mred text tabbed, which shows the [31m was only ever dangerous because of the escape in front of it.

a_paste_that_lost_something_says_what_and_a_clean_one_says_nothing carries the reporting, and the clean case is the load-bearing half of it: a note on every paste is noise, and noise is what gets ignored, which would leave the real notes unread. Four mutations go red on four different assertions — always silent, always speaking, breaks counted per character instead of per run, and control bytes dropped without being counted.

Which key acts on which pane

crates/emma/src/term/input.rs · pane_key, tool_key

pub fn pane_key(key: KeyEvent, editor_empty: bool, prompt_pending: bool) -> Option<PaneKey> {
    if key.kind == KeyEventKind::Release {
        return None;
    }
    let ctrl = key.modifiers.contains(KeyModifiers::CONTROL);
    match key.code {
        KeyCode::PageUp => Some(PaneKey::PageUp),
        KeyCode::PageDown => Some(PaneKey::PageDown),
        KeyCode::Up if ctrl => Some(PaneKey::RowUp),
        KeyCode::Down if ctrl => Some(PaneKey::RowDown),
        KeyCode::Home if editor_empty => Some(PaneKey::Top),
        KeyCode::End if editor_empty => Some(PaneKey::Tail),
        KeyCode::Char('b') if ctrl && !prompt_pending => Some(PaneKey::Sidebar),
        _ => None,
    }
}
crates/emma/src/term/input.rs — pane_key, PaneKey, WHEEL_ROWS

Three rules are encoded in those seven arms. Scrolling works while a goal runs and while a question is pending, because “reading the evidence above an approval prompt is exactly when scrolling matters most, and the prompt itself is fixed chrome that scrolling cannot move.” Home/End belong to the editor while there is a line to move within and to the transcript when there is not: “one rule, no mode: the keys act on the thing that can act.” And Ctrl-B dies under a prompt, so nothing aimed at a pane can read as part of an answer. tested, three tests, including one asserting Ctrl-Down still scrolls with prompt_pending true.

Defect: a comment credits a mechanism that is not there, and another names a feature that does not exist

Inside LineSource::raw, the reader loop opens with “A poll rather than a blocking read, so a frame that has been torn down does not leave a thread wedged inside the console driver holding a handle nobody can close.” The line under it is match event::read(), which blocks. The stated failure is not prevented by the mechanism the comment credits; whether it happens in practice is a separate question the comment does not answer.

Separately, inside the_pane_keys_route_to_the_transcript_and_nothing_else_does, a comment reads “Ctrl turns the arrows into row scrolling; plain arrows stay with history and the menu.” There is no history: the module doc says “there is no history and no completion”, and Editor::key has no Up/Down arm at all, so bare arrows fall to Action::Ignore. A reader would conclude Up recalls the previous goal. certified for both: read the two lines against the code immediately below them. The second is in a test comment rather than in pane_key's own doc, which is accurate.

Why the tool chords are Alt+<key>

The mockup showed bare s/c/f bindings. The design refused them outright: “a bare letter that acts while the input box exists is a footgun.” The softer rule, only when the editor is empty, dies on a fact the approval-gate keys never meet:

“the first character of every goal lands on an empty editor, so a bare s binding makes any goal beginning with s start a shell instead.”

crates/emma/src/term/input.rs — tool_key

An Alt chord types nothing, which puts it in Ctrl-B's class: safe whatever the editor holds, so the editor's content is not consulted. Ctrl is excluded from the match because AltGr arrives as Ctrl+Alt on Windows layouts and produces real characters. Which letters are bound is the catalogue's knowledge rather than this function's: tool_key returns the character and the frame looks it up.

tested: a_bare_letter_is_never_a_tool_shortcut walks seven characters and its doc says “If this test goes red, that refuted idea is back”, which is what makes it a guard rather than a check. alt_chords_launch_tools_and_die_under_a_prompt covers the four ways the chord must not fire: under a prompt, on a release edge, under AltGr, and with no Alt at all.

What / shows

menu.rs is pure: a filter string and a list of names in, an open or closed menu out. The reason for the split is stated: the menu's behaviour “is the part that can be wrong in a way nobody can see from a test binary — cargo hands the tests a pipe, so the viewport is never drawn while they run. What can be asserted is when it opens, what it filters to, what closes it and what an approval does to it.”

RuleWhy
Opens on a leading / and nothing else A second /, or any whitespace, means a path or a command with arguments rather than somebody reaching for a list.
No match closes it “A popup with nothing in it, sitting over the text somebody is trying to type, is a trap.”
Esc leaves the text alone Clearing what somebody typed is “the same class of theft as the drain eating a line, and the drain at least has a safety argument.”
A pending question outranks it Passed in as an argument rather than looked up, “so that the rule is a thing a test states rather than a thing a terminal has to be in front of.”
crates/emma/src/term/menu.rs module doc, sync

dismissed_at is a fifth rule that only exists because of the third: after Esc, the menu stays shut while what the user types still starts with the text they dismissed it at, since “reopening a popup somebody just dismissed, on their next keystroke, is worse than never having shown it.” sync also holds the selection on the same command while it survives the filter, “so narrowing does not move the selection out from under a hand that is already on Enter.” tested, both.

Nothing is invented. The vocabulary is Emma's own session_command::BUILTINS plus whatever the harness loaded, in the harness's order, and a harness command with no description gets NO_DESCRIPTION rather than a summary invented from prompt text: “a summary invented from prompt text is a description of a command that nobody wrote and nobody can correct.” tested: the_menu_and_the_parser_agree_on_the_vocabulary checks both directions, that every built-in has a row and that every row parses, “which is what stops the ninth command shipping undiscoverable.”

A name collision resolves to the built-in, and the project's row is marked rather than duplicated or dropped: “two identical rows would read as a bug, and dropping it silently would hide the collision entirely.” That is the one place the menu composes a sentence, and the file says why it is allowed to: what it composes is a fact about resolution, not a summary of a file nobody wrote a description for. tested: a_project_command_a_builtin_shadows_gets_one_marked_row_not_two.

What the dock draws

View::render lays out bottom-up: the body, the hint, and the status on the very last row. The comment records the reversal and the reason for it: the status used to be the first row, and the owner asked for what the terminal agents he uses do, “the chat bar at the bottom of the window with the status underneath it. The eye ends where the cursor is, and the two rows below the box are the two that never move.”

Nothing was added by the reorder, which is the part the comment insists on: “These are the same two rows of chrome the old order spent, reordered, so body gets exactly the height it got before and every case that fitted still fits.” A third fixed row would have cost the five-row viewport the ability to show a command and the keys to approve it. tested: the_reordering_cost_the_body_no_rows_at_the_smallest_viewport_emma_draws at heights 5, 8 and 10, and the_input_box_is_at_the_bottom_with_the_hint_and_then_the_status_beneath_it, which asserts the ordering by row index rather than by three contains calls, “because the property is the ordering: a test that only asked whether each piece appeared somewhere would pass the layout this replaced.”

The hint keeps a row of its own rather than sharing the status row, and the reason is the status row's law: “sharing that row with a fixed sentence would mean an advice string deciding whether a measurement fits.” Showing it only when it has something to say was the other candidate and is worse in the hand, because the row would come and go as the mode changed, moving the input box under the user's fingers.

Whatever is above it, a paragraph arriving or a command menu, takes what is left. That makes “the menu must not push the input off screen on a short viewport” a property of the layout rather than of a check somebody has to remember. tested: a_short_viewport_keeps_the_input_box_and_shortens_the_menu at seven rows and again at six.

Three smaller decisions live in the same function. The border is accent rather than grey, because “a widget that is the same weight as its own decoration reads as decoration.” An empty box shows menu::PLACEHOLDER, since a new user's first question is what this takes and the answer was previously nowhere except a note that had already scrolled away. And the mockup's [send: Enter] is drawn inside the right border only while it cannot collide with the typed line, because “a hint that overwrites the sentence it is hinting about is worse than none.” tested: the_send_hint_sits_inside_the_box_and_yields_to_a_long_line.

The approval panel drops its border before its evidence

A box costs two rows, and on a short window those two rows are the difference between showing the command and showing nothing but a title and a [y]. “A prompt the user cannot evaluate manufactures consent — that argument is older than this file — so the decoration goes first and the title becomes an ordinary line.” The keys and the answer share the last row and are laid out first: whatever else has to go, the way to answer the question does not. tested: the_shortest_viewport_drops_the_border_rather_than_the_evidence at five rows asserts the title, the command and the keys are all present and the border is not, and a_huge_preview_loses_lines_rather_than_the_answer_keys asserts the count of what was dropped points back at the transcript.

Both render_input and render_prompt are pub(crate) with the reason attached: “the approval panel must be the identical panel in both frames, because a consent interface with two renderings is two interfaces.” The full-screen dock calls them with a different rectangle and nothing else.

The cursor is returned rather than set, because Terminal::draw wants it after the frame is rendered. Both paths compute it in columns through cols_upto, because the editor counts characters and the cursor goes on a cell. tested: the_cursor_lands_on_the_right_column_after_wide_characters, whose doc names the failure the previous version had: “the character-counted version passed every test above because every string in them is one column per character.”

Defect: the input box does not scroll horizontally

render_input draws self.input as one span into the box's inner rectangle, and cursor_at clamps the column to area.width - 1. Past the inner width the text is clipped by the buffer and the caret stops moving, so neither the text nor the cursor tracks what is being typed. Editor::paste flattens a multi-line block onto one line, which makes a long line easy to reach without typing one. unverified as a felt symptom: no test drives an input longer than the box, and the send-hint test's fifty characters still fit in sixty columns. Typing past the box in a real run, or a test rendering a 200-character input at width 40, would settle it.

Two readers, one type

LineSource::stdin is the cooked reader: whole lines, edited by the terminal, a thread and a channel. It is unchanged from before the frame existed, because “it is what every fallback run uses and the fallback is the product.” Its editing, menu and frame fields are all None, so drain reaches only the channel, which is all there is.

LineSource::raw is the frame's, and its loop is the only place a crossterm::Event is inspected. The ordering in it is the routing table: pane keys, then tool chords, then menu keys, then the editor. Mouse events handle the wheel and exactly one click, a plain left press, and refuse anything Shift-modified even where a terminal forwards it, because “Shift-drag is the terminal's own selection — the one copy route left on the alternate screen — and this arm must never bid for it.” A resize is a redraw and nothing else, since ratatui re-measures on every draw.

WHEEL_ROWS is 3, “what terminals themselves scroll by”. A submit and a menu-accepted command both snap the view to the tail, “the answer to what was just sent is about to arrive there, and a reader parked fifty rows up would watch nothing happen.”

Coverage

All three files were read in full.

  • view.rs, 1,074 lines, 9 of 9 function items named. View::new, render, status_row, hint, render_input, render_menu, render_prompt, preview_lines, and the free cursor_at. Three types (Mode, Prompt, View) covered. Eleven of its twenty-three tests are cited.

  • menu.rs, 519 lines, 9 of 9. Entry::about and eight Menu methods. All four constants and three types covered. Seven of its fourteen tests are cited.

Not settled here. Two things. The drain is proven over a scripted queue and a hand-built editor; the reader thread that fills them cannot be started by a test, because it owns a real terminal. One of its arms is now driven anyway. The paste arm was lifted out as on_paste, taking a narrow Surface trait that Frame implements and a test satisfies with a recorder — so what the arm does is asserted rather than only what it decides. That distinction is the whole of ARCH-003: a reviewer deleted the line carrying the paste note to the screen and the entire workspace stayed green, because the decision had a test and the effect had nowhere to be observed. tested a_paste_puts_its_note_on_the_surface_and_a_clean_one_puts_nothing; deleting that line now turns it red. The other arms — keys, mouse, resize — are untouched, and the thread's one call to on_paste is itself still deletable with the suite green. The boundary moved rather than vanishing. unverified: type into a running Emma while a goal is in flight, then trigger an approval, and check the box is empty and the count is reported. And the whole of Editor's Windows double-fire guard rests on crossterm reporting KeyEventKind::Release, which the tests simulate by setting the field by hand.
