harness_state answers what ran. runctl is the other half: pause, resume, cancel, archive, delete, and starting a new run. It exists because the Harness page drew those controls against a scheduler Emma does not have; the controls stayed, because Emma already owns the things they name. The Harness page reaches all of it since 2026-09-06. This page describes the module; the pages page describes the keys.

Which keys reach it, and what they answer on Windows

Thirteen keys on the Harness page reach this module: start a run, archive one, delete one, pause, resume, cancel, add a task, sweep the finished ones, reorder the queue, write one of the three permission presets, and report what the permission file says today.

Archive, delete and sweep ask twice. Each of them destroys something you cannot get back by pressing the key again.

Three of the thirteen have no Windows implementation, and the page says so in three places rather than drawing a control that does nothing. Pause, resume and cancel send SIGSTOP, SIGCONT and SIGINT, and Windows has no equivalent of any of them.

Press one and you get the refusal's own sentence, naming the platform and the operation. The chip loses its accent while keeping its click rectangle, so a click reaches the same sentence a keystroke does, and the subtitle row carries the note whether or not you press anything.

The other ten work here: runctl gained real Windows arms for the process lookup, the detached spawn, archive, delete and the policy write when it landed. certified drawn from the real session store on Windows 11 at 161 columns, in the H2 port report. The refusal is the Refusal::Unsupported value's own Display, so the words on screen and the words in the module cannot drift.

policy_summary is the read side of write_policy and not its inverse. A permission file can hold a mixture no preset would produce, and answering “Safe” for it would be a summary that reads as a receipt for a write nobody made.

It names a preset only when the file matches one exactly, reports what is actually there otherwise, and counts rules carrying a specifier apart, because write_policy leaves those alone and a total that swallowed them would claim authorship of somebody else's decision. A file that does not parse is said to be unparseable and nothing is claimed about its contents. tested making the preset match accept every file turns both of its tests red.

A run is a process, and the process is named in the run's id

A session id is sess-<millis>-<pid>, so the pid that wrote a session log can be read back out of the log's own file name. That is the whole backend. Pause is SIGSTOP, resume is SIGCONT, and cancel is SIGINT, which the loop already handles and answers by writing its ending. There is no queue and no supervisor.

Cancel is SIGINT rather than SIGKILL because a run that is killed writes no ending, and its log then looks the same as a crashed one. You want to be able to tell “somebody stopped this” from “this fell over”, and that is most of what the record is for.

crates/emma/src/runctl.rs — module doc, Action, pid_of; crates/emma/src/session.rs — SessionLog::new_id

Pids are recycled, so every signal is verified first

A stored id can name a process that has nothing to do with Emma, and signalling it would be this program reaching into a stranger's. verify stands in front of every signal and refuses unless all four hold: the id parses and carries a pid above 1, so never init and never a nonsense zero; the pid is not this process, so the TUI cannot stop itself; the program running at that pid is named emma; and the run's recorded cwd is the repository the page is open on.

The last of those is policy rather than safety. A Harness page filtered to one repository must not reach into a run somewhere else on the machine, because you cannot see that run and cannot judge what stopping it costs.

Every refusal is a sentence the page can show, and there are seven of them: no pid in the id, the pid is this process, nothing is running there, something is running there and it is not Emma, the run belongs elsewhere, the run already finished, and the platform has no such control. You always get a sentence back, which is the point of enumerating them.

Nothing here calls kill directly. Control is a trait with one real implementation and one recording fake, so the verification logic is exercised mechanically and no test ever signals a real process. tested nine mutations were applied to the verification and each turned the suite red: the recycled pid, this process's own pid, a run in another repository, and a finished run are all pinned individually.

Windows, which is a target rather than a cfg hole

Three of the five things this module does have no Unix-shaped equivalent on Windows, and each answers rather than going quiet.

Asking what is running at a pid works. Os::name_of is OpenProcess plus QueryFullProcessImageNameW, so the recycled-pid guard is as real there as on Unix. The image name carries .exe and the file system is case-insensitive, which is why is_emma exists rather than a bare comparison. certified on this box: the test asks about this process's own pid and asserts the answer equals the leaf of current_exe, which on this machine is emma-….exe. Two pids that cannot be live both answer None, one of them chosen because Windows pids are multiples of four so 3 cannot race a real process into existence.

Signalling does not. There is no SIGSTOP, SIGCONT or SIGINT for an unrelated, detached process. GenerateConsoleCtrlEvent reaches only the caller's own console group, which a detached run is not, and TerminateProcess is not what Cancel means. So all three answer Refusal::Unsupported, which names the action and says why, and supported lets the page ask before it draws, so it can print a sentence instead of a control that refuses on every press. certified: the test calls the real Os for all three actions and asserts the refusal and its wording. Nothing is signalled, because the refusal returns before any syscall.

unverified: every Unix path. libc::kill, setsid, /proc/<pid>/comm and the ps -o comm= fallback are the fork's code, unchanged, and this box has no Unix to run them on. The macOS leg of the port's certification order settles them.

What a control writes down

Every carried-out action appends one record to the run's own session file, in the same one-JSON-per-line shape everything else in that file uses: 

{"kind":"harness_control","at_ms":1756512000000,"action":"pause","signal":"SIGSTOP","pid":4812}

It appends rather than rewrites, because a live process has that file open for append too and a rename underneath it would leave that process writing to an unlinked inode. The timestamp comes from the same clock every other record is stamped with, so the reader that folds the file sorts them together. The line ends with \n on every platform, never \r\n: the session log is LF-delimited JSON, and a CRLF here would put a stray carriage return inside the last field of every record this function writes.

Archiving, and the guard Windows needs and Unix does not

Archiving moves a session file into an archive subdirectory. A subdirectory rather than a marker record, because the run reader reads one directory level and no deeper, so moving a file there removes it from every feed without a line of reader code learning a new rule.

It is reversible on request. This is the control you reach for to tidy the list, and tidying must not be able to lose a transcript, so a file that is already archived comes back as an error naming that rather than as a silent success.

A live run is refused. Renaming the file out from under a process that holds it open for append does not stop that process writing: the handle follows the inode, so every record after the rename lands in a file with no name, the archived copy is missing exactly the tail still being written, and the transcript is split in two with one half unreachable.

On Unix, “verify would have refused to signal it” is taken as proof enough, because every way verify refuses is a run that cannot be signalled. That reasoning has a hole, since Elsewhere refuses a run that may be very much alive, and on Unix the hole is narrow because the page only offers archive on rows it listed and it lists rows whose cwd matched.

On Windows the same hole is wider and the consequence worse. Rust's File opens with FILE_SHARE_DELETE, so the rename succeeds over a live writer's handle with no error anywhere.

So Windows asks a different question: can we show nothing is running there? An ending was written, or the pid names nothing, or it names something that is not Emma. Everything else, including a run in another directory and an id with no pid in it, is unknown, and unknown does not archive. tested against a fake process table, both directions.

unverified as an observation. The guard defends against a rename succeeding over an open FILE_SHARE_DELETE handle while the writer keeps writing into the moved file, and that is read out of the standard library's documented open flags rather than watched. Two processes and a std::fs::rename under a live appender, twenty lines, on this box, would settle it.

session_file refuses any id containing a separator, a .. or a NUL rather than sanitising it, because there is no correct file for such a name to mean. The ids these functions receive come from file names this program enumerated itself, so in practice they are already plain; the check is there because two of the three callers are destructive, and “the input is always clean” is the assumption every path-traversal defect was written under.

Starting a run that outlives the window it was started from

A new run is a detached child. On Unix, setsid puts it in its own session so a SIGHUP aimed at Emma's process group does not take it too, and the three standard streams go to /dev/null so nothing it prints lands on top of the drawn page.

That is the one unsafe call in the module, because the standard library has no safe spelling for setsid. The other spawn site in the tree uses the safe process_group(0), which is enough there: a shell window only has to survive a signal aimed at Emma, while a detached run has to outlive the terminal.

On Windows the flags are DETACHED_PROCESS and CREATE_NEW_PROCESS_GROUP with null stdio. No console at all, which is right for a headless run, and it is the one way this differs from the user-tools launcher, whose whole purpose is a child that does own a console. certified that the child starts: the test spawns a real command with those flags and waits for the file it writes to appear, and it appears on the first poll. That test found a real defect in its own first draft, where the redirection was passed as one argument and Rust's quoting plus cmd /C's unwrapping between them lost it, so the child ran and wrote nothing.

unverified that the child outlives Emma on Windows. Removing the creation flags leaves the test green, because a child that inherits the console writes its marker too. What would settle it: start a long run from the Harness page on a real console, close Emma's window rather than pressing Ctrl-C, since the window close is what sends CTRL_CLOSE_EVENT to the console's process group, and check that the child's session file keeps growing. That needs the page's controls and an installed binary.

Deny All has to name every tool, one at a time

A new run can be started under a permissions preset, and Deny All writes out all 26 tool names rather than a wildcard. Emma refuses a * in the tool slot of a rule, so “deny everything” has to be spelled out, and a list that silently missed a tool would be a protection you believed you had.

The list is kept in step by a test rather than by memory: every_registered_tool_is_in_the_deny_all_list builds every tool constructor main.rs registers and fails naming any whose name is missing. That test is the reason the list can be trusted, and it earned its place immediately, because the list was wrong on arrival in both directions. The fork's list carried three tools this build does not register, which is harmless since denying a tool that does not exist denies nothing, and it was missing BashOutput and KillShell, which this build does register. A Deny All written from that list left the two background-execution tools callable on the next run. tested

Writing a policy merges into whatever the settings file already holds, for the same reason the permissions module's own writer does: the file belongs to more than one program, and losing somebody's hooks block to a settings write is a defect found weeks later. A file that is not JSON, or not an object, or whose permissions key is not an object, is not written to at all and the caller is told why. certified: the test parses what it wrote back through the real rule engine and asserts the decision is Deny for Bash, BashOutput and KillShell, rather than merely asserting the file is valid JSON.

What is still open

unverified Two reports disagree about Cancel on Windows. One says it should be CTRL_BREAK_EVENT; the other says that only reaches the caller's own console group, which a detached run is not, and recommends refusing. The refusal is what shipped. Trying GenerateConsoleCtrlEvent against a detached child on this box would settle it, and the reading that stopped it being implemented is that the call returns success and delivers nothing, which would be a control that reports it worked and did not.

unverified Whether verify's Elsewhere refusal should stop an archive on Unix too. The argument that it should is above; it was not changed, because no report sanctioned the behaviour change and it flips a fork test. The change is deleting two #[cfg(windows)] markers, and it needs a ruling rather than a measurement.

unverified Everything a person would see. No key on the Harness page reaches this module, so no refusal sentence has been drawn, no harness_control record has been written by a person pressing anything, and supported has never been asked before a control was drawn. The Harness package is what settles all three.
