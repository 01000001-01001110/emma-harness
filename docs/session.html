Running a goal

Sessions, context and compaction

One append-only JSONL file per session, written as the run happens. It is what --resume folds back into a message list, what compaction edits, and — since the interactive frame moved to the alternate screen — the only surviving record of a run once Emma exits.

certified proven against the real thing
tested a test that was shown to fail
unverified believed, not checked

Stage 2 of the full-screen TUI gave up terminal scrollback, and the line Emma prints on exit names this file as the record instead. There is no second copy of what the model said: the styled run goes with the alternate screen, and what is left is the JSONL.

CLAUDE.md, "Constraints that are load-bearing"; crates/emma/src/session.rs (module doc)

The file

~/.emma/sessions/<id>.jsonl, or $EMMA_SESSION_DIR when that is set, or --session-dir. The id is sess-<unix-millis, 13 digits>-<pid>: zero-padded so ids sort lexically by time, and stamped with the process id so two emma processes starting in the same millisecond cannot collide. Both consumers that scan the directory — locate for bare --resume, and the first-run check behind the welcome — sort by id rather than by mtime, because copying a file moves its mtime and does not move its id.

crates/emma/src/session.rs — SessionLog::new_id, default_dir, locate, first_run

One JSON object per line, appended and flushed as each event happens, from one std::fs::File behind a std::sync::Mutex in an otherwise async program. A record is a few hundred bytes and is written between a model call and a subprocess. Making the write async would add an await point in the gap between "append the record" and "do the thing it describes", which is where a cancellation would then be able to land.

crates/emma/src/session.rs — SessionLog::file, SessionLog::append
Why not SQLite

SQLite pays for itself against concurrent writers and against a crash-recovery fold that has to decide whether a side-effecting tool already ran. Emma has one process, one user, one writer, and no recovery requirement — a crashed run is re-run, because what it was doing is in the working tree where you can see it. What a database would add is a dependency, a schema, a migration story and a binary file you cannot grep.

Three changes would reverse that, and the module doc names them: a second writer (a daemon, a watch mode, two processes on one session id), exactly-once tool semantics across a crash, or queries across sessions. The last already costs something — locate is a directory scan — and is the one that will arrive first.

What a crash can do to it

Leave a torn final line, and nothing else. SessionLog::read parses line by line and drops anything that will not parse, so everything written before the kill still reads. tested — a_torn_final_line_costs_only_that_line writes {"kind":"goal",…}\n{"kind":"assis and asserts one record comes back.

crates/emma/src/session.rs — SessionLog::read and its tests

Write failures after open are swallowed: a full disk would otherwise kill a run halfway through editing your source tree. The price is that a session which stops being written stops silently. unverified — nothing in the tree exercises a write failure. Filling a volume, or opening the log on a read-only mount after creation, would settle whether anything is said at all.

crates/emma/src/session.rs — SessionLog::append

Every record

Every record carries two fields Emma adds itself: kind, and at_ms (unix milliseconds at the moment of the append). Nothing else is universal. Both readers match on kind with a catch-all arm, so an unknown kind is skipped rather than fatal, which is what lets a file written by an older build still fold.

Every one of these carries turn_id, which is turn-<n> counting from the start of the session rather than from the start of the goal. /clear does not reset it, because ids have to stay unique inside a file that is not cleared.

The pairing rule a parser needs

A failure gets two records: the prose one naming what went wrong (tool_failed, denied, tool_unknown, tool_fault) and then the tool_result that was actually sent. Two failure classes produce a tool_result with no preceding tool_call at all — a schema violation and the already-failed memo, both refused before dispatch. Anything joining calls to results by id will meet results with no call. restore_records hits the same thing and states the cost: those two classes are not restored into the memo, so a resumed model may re-issue one call that cannot run and be told so again.

Delegation records

A delegation writes into the same file through a second view of the same handle. Every kind it writes is prefixed sub., and every payload is stamped with sub_id, parent_turn_id and agent. The prefix is what keeps the two runs apart in both readers: they have catch-all arms, so sub.assistant and sub.model_call fall through. Written under the parent's names, a sub's assistant arriving between the parent's tool_call and its tool_result would close the parent's held turn without its results, fail the every-call-answered check, and drop that whole turn from every future resume of the session. tested — tests/delegate.rs folds a session containing a delegation and asserts the parent's message list is unchanged.

crates/emma/src/session.rs — SessionLog::subagent

That view also keeps its records in memory. Delegate reads them back — the tool calls, the results, the denials, the ending — and builds the footer the parent sees from them, so the parent's account of a delegation comes from the loop rather than from the subagent's prose. See Delegation.

Parsing one, from scratch

Read the file, drop lines that will not parse (the last one may be torn), then walk in order. Rebuilding the conversation needs five kinds: goal opens a goal and its opening is the first user message; assistant's raw_content is an assistant message; tool_result's block goes into a user message pairing with it; kick's text is a user message; cleared throws away everything before it. Then apply compacted as described below. Everything else is audit trail.

The rule that is not obvious: an assistant turn and the results answering it are placed together or not at all. The API rejects a tool_use with no matching tool_result, and equally a result answering nothing. A run killed between the model call and the last of its tools leaves exactly that in the file, and keeping the half that survived produces a message list the next request cannot send. tested — I replaced the answered check in place_turn with a constant and a_partly_answered_turn_is_dropped_whole and a_turn_whose_tool_calls_were_never_answered_is_dropped both went red; restored, 477 lib tests pass.

crates/emma/src/session.rs — place_turn, answered

The same rule swallows an older-format record: an assistant written before raw_content existed drops its whole turn, and the kick answering it goes too. There is no reconstruction available — rebuilding a turn from text is what invalidates a thinking-block signature, and the symptom would arrive later, as a resumed run dying on its first call with an error naming a signature nobody in the file mentions.

--resume

emma --resume [<id>] [<goal text>]. An argument starting sess- is read as an id; anything else is the goal. A named session is not filtered by working directory. Bare --resume means the last session run here: sessions from every project share one directory, so the newest file overall is routinely another project's, and resuming that into this tree is a conversation about the wrong repository with write tools attached. Candidates are walked newest id first and the walk stops at the first file with a goal record whose cwd canonicalises to this one.

crates/emma/src/cli.rs (--resume parsing); crates/emma/src/session.rs — locate, same_dir

A resumed run appends to the same file rather than opening a new one, so one goal's transcript stays in one place and a resume of a resume folds the whole thing rather than the last leg of it.

What comes back

The messages, and four things a message list cannot express: tokens, iterations and kicks spent on the goal being continued, and the failed-call memo. Without the counters, resume is a way to spend past a cap — a goal that ended on the token budget could be resumed indefinitely and the limit it hit would mean nothing. tested — tests/resume.rs has one test per counter (a_resumed_run_inherits_the_tokens_the_first_one_spent and its three siblings), all passing on commit 20ac400.

crates/emma/src/agent.rs — Resumed; crates/emma/src/session.rs — restore_records

Every counter resets at each goal record, so a file with three finished goals hands the fourth the spend of the goal it is continuing rather than the sum of all of them. The token sum is cost_tokens — cache-weighted, the same units the budget enforces — falling back to billable_total_tokens for records written before the weighting existed. That fallback is live: of 100 session files on this machine, 36 carry cost_tokens and the rest do not. certified — counted with grep -l cost_tokens *.jsonl in ~/.emma/sessions/, 2026-08-16.

A delegation's own sub.model_call records are invisible to that sum, so the parent-level delegation record's cost_tokens is added separately. It does not touch iterations: the parent made one model call for that turn, not fifteen.

What does not come back

No tool is replayed. Nothing in the resume path runs anything. A turn dropped for unmatched tool ids means those calls never happened as far as the restored conversation is concerned, and the gap goes to the model rather than being closed behind its back. Re-running them would re-run a Write or a Bash against a working tree that has moved on. tested — a_resumed_run_replays_no_tools.

crates/emma/src/session.rs, "Resume" region header

Nor does the split between finished and in-flight come back. The restored messages all go into query — the goal in progress — because the file does not record where the split was, and guessing wrong is a message list the API refuses. Two things follow. The chapters would have carried a cache breakpoint that stayed byte-stable for the rest of the session, and a restored prefix does not get one, which is a bill. And the whole restored block becomes one chapter however many goals went into it, so it compacts as a unit: a resume that comes back over max_context runs that one goal at that size.

Continuity

The last goal record's account of the harness — instructions_hash, tool_schema_hash, model — is compared against the run about to continue it, and each difference is printed as a sentence naming the field, the old value, the new one, and what it costs. It warns and does not refuse. Declining would leave you with a transcript and no way to use it; what is dangerous is not the change but the change being invisible. An empty recorded value produces no warning, because a warning derived from a field that did not exist yet trains people to ignore warnings. tested — resuming_into_a_changed_harness_names_what_changed.

crates/emma/src/session.rs — Continuity::differences

The warnings are emitted late in startup rather than beside the resume line, because Delegate is registered after the resume is resolved and a schema hash taken earlier would hash a tool surface no request will carry.

Compaction

When a request grows past --max-context (default 120,000), whole finished goals are replaced oldest-first with their goal text, their final answer, and a sentence saying the tool traffic is gone. It never touches the goal in flight. It is deterministic and makes no model call.

crates/emma/src/agent.rs — compact_if_needed, compact, summarise

The design note recommended a model call, and the code went the other way

notes/design-session-and-context.md §2 surveyed six shipped tools and recommended what all of them do: summarise with one model call — same model, tools absent, effort low — against a fixed template asking for objectives, what was verified, decisions and why, what failed, files touched, what is next. It also recommended trigger-high/compact-low hysteresis (cross ~120k, compact down to 30–40k), and that the compacted record carry the summary plus references to the retained turns rather than copies of them.

None of the three shipped. The note is still in the tree and still reads as current advice, so the three departures are worth having in one place:

  • No model call. Three arguments, in the order agent.rs makes them: it would spend the budget of whichever goal happens to be running; it can fail in the middle of one; and it produces a claim about the conversation where the mechanical version produces a record of it. The note conceded the same failure mode — "the summary is written by the same process that is being summarised, and it will sometimes be wrong" — and offered two mitigations it described as neither being a fix.
  • Half the cap, not a fixed floor. target = cap / 2 is 60,000 at the default rather than the note's 30–40k. Same effect on how often compaction fires, and no second constant to keep in step with the first.
  • The replacement is written into the record whole. The note argued for references, citing a bug in another tool where re-serialising surviving history made the log grow without bound. The code stores drop_messages and the exact replacement messages, so a resume replays the compaction instead of re-deriving it, and session.rs contains no summarising code that could disagree with the loop's. The growth the note warned about is bounded here by the replacement being two short messages per goal rather than a retained window of turns.
notes/design-session-and-context.md §2 and its 2026-08-16 header note; crates/emma/src/agent.rs — compact_if_needed doc

/compact takes the same path with a different count: every finished goal, or with all, every goal including the one that just ended. /compact <words> is refused rather than ignored, and the refusal says why — an instruction can only be honoured by a model. The workaround it offers works: ask for the summary as an ordinary goal first, because a goal's answer survives compaction.

crates/emma/src/session_command.rs — compact

The compaction that would not shrink anything

A compaction whose replacement is not smaller than what it replaces is abandoned. That case turns up in practice: the note is roughly three hundred characters, so two four-word goals compact upward. The first live run of /compact reported "already summarised" about two goals that were nothing of the sort — the arithmetic was right and the sentence was wrong. There are now two branches: one for a conversation that really is all summaries, and one that quotes the before and after and says the note is longer than what it would replace. tested — compaction_stops_when_there_is_nothing_left_to_win.

crates/emma/src/agent.rs — compact, the after >= before branch

What "approaching the limit" means

The trigger is measured, not estimated. compact_if_needed is handed the provider's own billable_input_tokens for the previous call — the whole request, so the system prompt and the tool schemas count as well as the conversation. That number is what is compared to max_context.

The estimate stands in for one case: the first check of a goal on a process that has not called the model yet, which in practice is a resume into a large session. It also decides how much to drop once a measured number has said that dropping is necessary, and it is what /model and the compaction receipt quote as "roughly N tokens". It never fires a budget.

crates/emma/src/agent.rs — estimate, compact_if_needed, estimated_context

The estimator

chars / 4 over the rendered JSON length of each message — quotes and escapes included, because the provider tokenises those too. Four is the same constant emma-llm's packer uses, and both places document it as under-counting what the provider bills. The under-count has a direction, and it lands differently on each consumer:

consumeran under-count meanswhich is
compaction trigger at goal open the cap looks further away than it is; compaction fires later, or not at all, on the first call tolerable — the next call reports a measured number and the check runs again before the request goes out
how many chapters to take every chapter looks smaller, so slightly more may be taken than strictly needed tolerable — the error is toward compacting more, not less
the cache-breakpoint gate in emma-llm a prefix that really does clear the model's floor is judged not to, and the marker is withheld a bill — the forgone 0.9× read discount on that span, with no symptom anywhere except the invoice
crates/emma/src/agent.rs — estimate; crates/llm/src/anthropic.rs — CHARS_PER_TOKEN, clears_minimum

The third row is where the margin widened. The gate used to be one constant, 512, which was right for claude-opus-5. The floor is per-model and not monotonic with release date, and the table now runs from 512 to 4,096: claude-haiku-4-5 and claude-opus-4-6 cache nothing under 4,096 tokens, and a model the table has never heard of is assumed to be at 4,096 too. At a 512 floor the gap between an under-counting estimate and the truth costs a marker on a prefix of a couple of kilobytes. At 4,096 it is a prefix of roughly sixteen kilobytes going unmarked, and one /model or one Haiku-typed delegation is enough to reach that floor. unverified — the direction of the error is stated in both source files and matches English-plus-JSON tokenising at closer to 3.5 characters per token, but nobody in this tree has measured Emma's own wire bytes against a token count. What would settle it: send a request of known rendered length with caching off and compare wire_len / 4 against the input_tokens the API reports, or push the same bytes through the token-counting endpoint.

What the gap does not touch

The token budget. --max-tokens is enforced on cost_tokens, computed from the provider's own usage numbers with the cache multipliers applied; no estimate is involved. It is tested after each call rather than before, so the call that crosses it is paid for in full: a 500,000 budget stopped a real run at 579,565. certified — that overshoot is not a recollection. It is the largest goal_finished.tokens in the 100 session files on this machine, read back today.

A folded goal, and what a later reader loses

A compacted goal becomes two messages: a user message that is the goal text verbatim, and an assistant message that is the final answer plus a fixed note. Empty fields get stated placeholders — [an earlier goal] and [this goal ended without a final message] — rather than blank strings. 

// one goal after compaction, taken from the left/right diff a
// fold with its compaction arm removed printed on this tree today
Message { role: User,      content: Text("read a.rs") }
Message { role: Assistant, content: Text(
  "the first file parses cookies.\n\nGOAL COMPLETE\n\n"
  "[Summarised to save context. The tool calls from this goal and their "
  "results — file contents, command output, diffs — are no longer in this "
  "conversation. Read anything you need again rather than recalling it.]") }
crates/emma/src/agent.rs — summarise, COMPACTED_NOTE

Gone: every tool call and every result — file contents, command output, diffs — and every intermediate assistant turn, with their thinking blocks. Kept for the life of the session: every goal's words and every goal's final answer. The note is there because a model that does not know a file has left its context answers from a memory of it, and a confident wrong answer costs more than a second read. tested — compaction_drops_the_oldest_tool_traffic_and_keeps_the_words asserts the file body is absent, the goal present, the answer present and the note present, in the bytes the fake provider actually received.

A summarised chapter is marked as such, and summarising it again returns it unchanged rather than wrapping it in a second note.

The fold replays the record

Fold does not re-derive a summary. On a compacted record it splices: drop drop_messages off the front of the folded history, insert the recorded messages in their place. That is what both halves of the record are for, and why there is no summarising code in session.rs — a second implementation would be a resumed conversation that differs from the one that was sent, in the cases neither is tested on. tested — I replaced the splice with a no-op and compaction_drops_the_oldest_tool_traffic_and_keeps_the_words failed on its last assertion, "the folded session is not the conversation that was held", with the left side still carrying the 200-line file body; restored, green.

crates/emma/src/session.rs — Fold::record, the "compacted" arm

The count indexes finished goals only, never the goal in flight, because compaction never touches the goal in flight.

/clear is the other thing that shortens a conversation, and it is not compaction. Its record makes the fold discard everything before it — both lists, and the in-goal flag with them. Without that arm /clear would fail quietly: the in-memory conversation empty, the next --resume folding the whole file, and the cleared conversation walking back in with its tool results attached. The bytes stay in the file for a human; the fold skips them.

Four things come out of that.

Half the corpus is empty files. 48 of 100 are 0 bytes. SessionLog::open creates the file at startup, so a run that never gets as far as a goal — start, look, /exit — leaves an empty one behind, and nothing prunes them. The readers cope (restore refuses a file with no goal record; locate and the first-run scan skip them); every count anyone quotes about the directory has to subtract them first.

Compaction has never fired here. Not once in 100 files and 174 model calls. The largest input any call carried is 95,524 tokens against a 120,000 default cap — close, and never over. certified — computed over every model_call record in the directory. So everything above about the compaction trigger rests on tests and on reading, with no production firing behind it. The mechanism is exercised by tests that set max_context to 400 and to 1.

The files are thin, but not as thin as the backlog says. notes/improvements.md item 6 records the corpus as "86 files, mostly 0 bytes, largest 4.7 KB". Today it is 100 files, largest 266 KB, with 52 carrying at least one goal. The size objection recorded there no longer holds.

Item 6 is still blocked, on something else. It needs a delegation-clustering number to decide whether moving deliver out of the SubagentClaim contract is worth it. There is one delegation record in the entire corpus. The blocker is not file size; it is that delegation has barely been used on this machine, and ordinary session growth does not fix that. certified — one record, in one file, out of 100.

What is not verified

  • The chars-per-token ratio. Both source files call chars / 4 an under-count; nobody has measured it against a real token count. unverified — settle it by comparing wire_len / 4 for a request of known content against the input_tokens the API reports for it with caching off.
  • Automatic compaction against a live provider. Zero compacted records exist in the real corpus, so every claim here about the trigger comes from tests with an artificially small cap. unverified — settle it by running a real session with --max-context set to something an ordinary conversation crosses, and reading the compacted record back.
  • The torn-line guarantee under a real kill -9. The test writes a truncated line by hand. Whether a Windows write of a few hundred bytes can be torn mid-line at all, and whether the tail after a real kill looks like the fixture, has not been observed. unverified — settle it by killing a run mid-tool-result and reading the last line of the file.
  • Resume across a genuine model change. Continuity::differences is tested on strings. Whether one model's signed thinking blocks are accepted by another is stated in agent.rs as not established in this tree, which is why the compact-and-retry recovery exists at all. unverified — settle it by resuming a session recorded on one model under another and reading what the provider says.
  • How this page looks in a browser. The two SVGs were hand-authored against the source and their geometry checked by arithmetic; the tag structure parses and the sidebar matches assets/NAV.html byte for byte. No renderer has drawn them — no browser was reachable from the session that wrote this. unverified — settle it by opening docs/session.html from file:// and checking that no label overflows its box and the two figures fit their columns.
  • Behaviour on a malformed compacted record. The fold deserialises messages with a fallback to empty while still dropping drop_messages off the front, so a record whose replacement cannot be read would turn compaction into deletion. Nothing writes such a record today. unverified — settle it by hand-writing a compacted record with a non-array messages field and folding the file.
