Running a goal

Sessions, context and compaction

One append-only JSONL file per session, written as the run happens. It is what --resume folds back into a message list, what compaction edits, and, since the interactive frame moved to the alternate screen, the only surviving record of a run once Emma exits.

The shape of it

Stage 2 of the full-screen TUI gave up terminal scrollback, and the line Emma prints on exit names this file as the record instead. There is no second copy of what the model said: the styled run goes with the alternate screen, and what is left is the JSONL.

CLAUDE.md, "Constraints that are load-bearing"; crates/emma/src/session.rs (module doc)

The format is one JSON object per line and the type that owns it is SessionLog. There is no database, and the module doc argues that rather than assuming it: one process, one user, one writer, and no crash-recovery requirement, because a crashed run is re-run and what it was doing is in the working tree where you can see it. Three changes would reverse the argument the same day, and one of them, queries across sessions, already costs a directory scan.

crates/emma/src/session.rs — module doc

Two readers walk those records, and they read different things out of the same file. The fold rebuilds the message list the last request carried. The restore rebuilds what the interrupted goal had already spent and which calls it had been refused. Neither replays a tool, and the absence is stated in the source rather than left to be noticed.

Four properties hold across the chapter. A record goes down before the thing it describes happens. A turn and the results that answer it are kept together or dropped together, because the API rejects either half alone. Compaction is deterministic and asks no model anything. And a session is one continuous conversation, so a finished goal stays in it whole until compaction or /clear takes it out.

What this chapter covers

All 28 functions in crates/emma/src/session.rs outside its test module, plus its one constant and its six types, and all twelve of its unit tests are named where the behaviour they cover is described. From agent.rs, the compaction path and the record-writing sites: compact_if_needed, compact, compact_now, summarise, estimate, estimated_context, conversation, clear, set_provider, log_result_block and log_hooks, with the Chapter, Compacted, Cleared and Resumed types. From cli.rs, main.rs, session_command.rs and delegate.rs, the parts that write or read a record. certified by counting fn items in session.rs outside mod tests and matching them against the per-page coverage lists.

What the chapter hands off. The loop that produces the records is The agent loop, and the budgets the restore inherits are on Budgets. The second view of the same file that a subagent writes through is described here and used on Delegation. The cache-breakpoint gate the estimator feeds is on Providers & caching.

What the chapter could not verify

unverified Nothing here was certified against a live provider call. The largest gap is that automatic compaction has never fired outside a test on the only machine whose corpus was available, so every claim about the trigger rests on tests with an artificially small cap. The mutations that prove the fold's turn-placement rule were run by an earlier pass over this chapter and not re-run by this one, which was not permitted to change source. Each page ends with its own list, and the four amber items worth settling first are the chars-per-token ratio, a real kill -9 mid-append, a resume across a genuine model change, and what the fold does with a malformed compacted record.
