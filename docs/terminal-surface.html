Which surface a run gets

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Copying out

One field on one struct decides whether Emma draws a full-screen application or writes a stream of lines: frame: Option<Arc<Frame>>. Everything else in this chapter hangs off which of the two it is. The decision itself is a pure function of five inputs that runs before anything is drawn, plus, on Windows, two console settings that are changed and then read back, because a call that reports success is not the same claim as a console that honoured it.

The one struct every write goes through

Term holds nine fields and forty-one methods, and the split that matters is between two of the fields. quiet decides which stream the running commentary goes to: under -p the assistant's prose still goes to stdout while notes, tool lines and warnings go to stderr, so a script can pipe the answer without filtering the commentary out of it. frame decides whether any of it is drawn into cells.

crates/emma/src/term.rs · struct Term, the two decisive fields

crates/emma/src/term.rs — struct Term

The other seven fields are state that has to survive across &self calls, which is why three of them are behind a Mutex: marker holds the completion-marker filter part-way through a streamed answer, pending holds the approval question while prompt_header and prompt_question fill it in from two separate calls, and spacing holds the blank-row state machine for the path that has no frame. subordinate marks a nested run's view; record is an optional log of what the meters and the prompt were told; enabled is false only for Term::silent.

Four constructors, and only one of them can draw. Term::interactive is the sole caller of Frame::install. Term::printing is -p, Term::silent writes nothing at all, and Term::recording is silent plus a Vec<String> of what was said. All three set frame: None in their initialisers. They do not decline to draw; they have nothing to draw with. tested: printing_never_draws_a_viewport and a_silent_terminal_never_draws_and_never_takes_a_terminal, which calls every write method in turn to prove none of them reaches for stdout on the disabled path.

Six ways to refuse

Whether to draw at all is separated from the drawing, and the reason is asymmetry of cost. Getting it wrong in one direction produces a plain terminal where a pretty one was possible. Getting it wrong in the other produces “a garbled terminal on somebody else’s machine, or a file full of escape sequences.”

crates/emma/src/term.rs · fallback_reason

/// Below this the viewport would be most of the screen, so it is not worth
/// drawing.
const MIN_ROWS: u16 = 8;
const MIN_COLS: u16 = 24;

/// Why the viewport is not being drawn, or `None` to draw it.
fn fallback_reason(
    stdout_tty: bool,
    stdin_tty: bool,
    term_var: Option<&str>,
    opted_out: bool,
    size: Option<(u16, u16)>,
) -> Option<&'static str> {
    if opted_out {
        return Some("EMMA_NO_FRAME is set");
    }
    // Both directions matter and for different reasons. Redirected output means
    // the escape sequences end up in somebody's file; redirected input means
    // there is nobody typing — and raw mode on a pipe is meaningless.
    if !stdout_tty {
        return Some("stdout is not a terminal");
    }
    if !stdin_tty {
        return Some("stdin is not a terminal");
    }
    // `dumb` is the one value that promises the opposite of what we need.
    if term_var == Some("dumb") {
        return Some("TERM=dumb");
    }
    match size {
        None => Some("the window size could not be read"),
        Some((cols, rows)) if rows < MIN_ROWS || cols < MIN_COLS => Some("the window is too small"),
        Some(_) => None,
    }
}
crates/emma/src/term.rs — fallback_reason, MIN_ROWS, MIN_COLS

The environment variable is the first arm, and the test that pins the ordering says why: “somebody setting this has a broken terminal in front of them and no interest in the other five checks agreeing.” No TERM at all is not a refusal, because that is the ordinary Windows case. An unknown platform answers None from terminal_size and lands on “the window size could not be read”, so the fallback is what a port to anything else gets by default. tested: five tests, one per refusal, plus a_real_terminal_of_a_reasonable_size_gets_the_viewport for the accepting case.

frame_wanted asks the same question of the real process and exists because the answer is needed before the frame is installed: the Windows code page is changed only for a run that will draw, and the glyph set is chosen from what the console says afterwards. Frame::install asks it again for itself, and the doc comment prices the duplication: “a check that lives in two places is cheaper than an installer that trusts its caller.”

The two Windows settings that are changed rather than asked

Detection alone was tried for the code page and was correct and useless. A normal PowerShell window reports code page 437, so the answer was always no and the box was always +---+. The module records the premise the old code got wrong: “a legacy code page is not a property of the terminal, it is a setting, and it is ours to set for the duration of the run.”

crates/emma/src/term.rs · adopt_utf8_output, windows

#[cfg(windows)]
fn adopt_utf8_output() -> bool {
    use std::sync::atomic::Ordering;

    use windows_sys::Win32::System::Console::{GetConsoleOutputCP, SetConsoleOutputCP};
    unsafe {
        let original = GetConsoleOutputCP();
        if original == CP_UTF8 {
            return true;
        }
        if original == 0 {
            // No console attached — a redirected handle, or a service. Nothing
            // to set and nothing to render.
            return false;
        }
        SetConsoleOutputCP(CP_UTF8);
        // Believe the console, not the call.
        if GetConsoleOutputCP() != CP_UTF8 {
            // Whatever it did with the request, it is not UTF-8 now, and we
            // may have moved it somewhere it did not start.
            SetConsoleOutputCP(original);
            return false;
        }
        ORIGINAL_CP.store(original, Ordering::SeqCst);
        true
    }
}
crates/emma/src/term.rs — adopt_utf8_output, CP_UTF8, ORIGINAL_CP

Three outcomes, and the middle one is the refusal that is easy to miss. A console that was already 65001 returns true without recording an original, so restore_console_cp leaves it alone on the way out: it was not Emma's to change. A GetConsoleOutputCP of zero means no console at all. And a set that did not stick is undone before returning false, because the console may have moved somewhere it did not start. ORIGINAL_CP uses 0 as its “not ours to restore” sentinel, which is safe because zero is not a code page.

enable_vt has the same shape and a second job. SetConsoleMode returning success is not the claim that the flag was honoured, and legacy conhost.exe fails the call outright. The read-back also decides which of crossterm's two code paths runs: with VT proved it writes escape sequences, and without it makes WinAPI calls in screen buffer coordinates. On Windows the buffer is usually far taller than the window, so a repaint aimed at row 40 of a nine-thousand-row buffer goes somewhere invisible. The comment names that as “the exact failure the first attempt at this file shipped.” Its sentinel is u32::MAX, because no real console mode has every bit set.

crates/emma/src/term.rs — enable_vt, ORIGINAL_MODE, restore_console_mode

terminal_size exists in three cfg variants and measures the visible window rather than the buffer, for the same reason. On Windows it is GetConsoleScreenBufferInfo and the arithmetic srWindow.Right - srWindow.Left + 1; on unix it is ioctl(TIOCGWINSZ); on anything else it returns None, with the comment “an unknown platform gets the fallback, which is the whole product.” Both live variants reject a zero or negative size rather than passing it on.

The glyph set is a consequence, not a choice

prefers_ascii(opted_out, utf8) is two booleans and one ||, and it is biased: UTF-8 has to be proved before the Unicode set is used, because “a transcript made of question marks reads as a broken program rather than as a stylistic choice.” EMMA_ASCII_FRAME is the opt-out and it outranks a console that was successfully moved to UTF-8. tested: a_code_page_change_that_did_not_take_still_gets_ascii asserts the decision at prefers_ascii rather than at the syscall, which is where a silently-failed SetConsoleOutputCP arrives.

What a redirected run actually produced

The claim this whole gate exists for is that nothing Emma writes to a non-terminal contains an escape byte. Two tests assert it on the renderer (the vocabulary covers those), and it is also checkable end to end against the built binary. Redirecting both streams of a real -p run: 

$ emma -p "say the single word: ok" > p.out 2> p.err

p.out  3 bytes, 0 escape bytes:  b'ok\n'
p.err 84 bytes, 0 escape bytes:  b'> say the single word: ok\n\n= goal complete\n
                                   1 calls | 1555 tokens (cache-weighted)\n'

certified 2026-08-16 at 62ab9c3 on Windows 11, and repeatable: run the command above and count \x1b in both files. Three separate claims fall out of those eighty-seven bytes. The answer went to stdout alone, which is what quiet is for. Neither stream carries an escape byte. And the glyphs are the ASCII set (> for the goal, = for the ending, | for the separator) because a run that will not draw asks the console rather than changing it, and this one was redirected.

The one residual escape route, and it is upstream

Term::delta passes the model's own characters through untouched on the fallback path. That is what keeps emma … | tee free of anything Emma invented, and it also means an escape sequence written by the model is not filtered there. Inside the frame it is: markdown::sanitise drops every control character before a cell is written. unverified that a model reply containing \x1b reaches a pipe intact. Reported from a reading of Term::delta and write_out; a run whose prompt asks the model to emit a literal escape byte, piped to a file, would settle it.

A nested run gets a different terminal

Term::subordinate shares the frame, the skin and the stdin path, and swallows exactly seven calls. Four are the status meters (set_budgets, goal_started, goal_ended, spent) and three are the assistant's prose (delta, text, end_of_text). The meters are the half that can go wrong. The doc names the defect it exists to fix: a nested agent driving them would re-point the context and token meters at the sub's caps for the rest of the process, stop the parent's clock while the parent is still running, and feed the live line a per-goal figure smaller than the parent's, so the meter would jump backwards mid-goal.

The four meter calls all go through one private funnel, Term::meter, “so a meter added later cannot forget the rule”. What a subordinate terminal must not swallow is the approval prompt: a subagent inherits the gate, and prompt_header, prompt_question, prompt_network_question and prompt_answered render exactly as they do for the parent. Term::recording exists so a test can see both halves of that rule rather than only one, because “a no-op nobody can observe is a rule nobody can test.”

The exit line

crates/emma/src/term.rs · impl Drop for Term

impl Drop for Term {
    /// The ordinary exit path. `restore_terminal` is idempotent and global, so
    /// this racing the panic hook or an explicit call costs nothing.
    fn drop(&mut self) {
        // Not on a subordinate view: it shares the parent's frame and goes out
        // of scope at the end of every delegation, which is the middle of the
        // parent's run. Restoring there would put the terminal back while the
        // session is still drawing into it.
        if self.frame.is_some() && !self.subordinate {
            let pointer = self.frame.as_ref().and_then(|f| f.session_pointer());
            restore_terminal();
            …
            if let Some(path) = pointer {
                println!("session: {path}");
            }
        }
    }
}
crates/emma/src/term.rs — impl Drop for Term (the omitted lines are a six-line comment quoted on the frame page)

The pointer is read before the restore and printed after it, so the line lands on the normal screen the alternate screen just gave back. Frame::session_pointer returns None on the inline path, because there the transcript is already in the shell's scrollback and needs no pointer.

The rest of the file, accounted for

GroupWhat it is
The write methods note, warn, banner, tool_started, tool_result, tool_failed, tool_blocked, tool_refused, kick, ending, welcome. Each asks Skin for lines and hands them to side. Only tool_started does more: it appends the diff for a tool that changes a file, and it is the only place a change reaches the transcript, because the prompt fires for a subset of calls and a Write covered by an allow rule would otherwise change a file with nothing on screen but its name.
The two exits side writes through render::for_stream to stdout or stderr depending on quiet, or to Frame::write_lines. write_out is the prose path and bypasses the spacing rule entirely, then tells it so with wrote_text(false).
The prompt trio prompt_header fills the evidence, prompt_question and prompt_network_question compose the keys, and both funnel into the private question. The network question offers [r] (this host) and [t] (every call this tool makes anywhere) as separate keys, because “a grant somebody arrived at by pressing the obvious key is a grant they did not read.”
Small readers framed, colour_level, recorded, line_source, set_status, set_status_source, goal_prompt, filtered. Uninteresting except colour_level, which exists so /theme can say plainly that a setting will not change anything under NO_COLOR.
summarise_args Which single argument identifies a tool call on one line, per tool rather than by rule. A Write banner showing its content would push the next twenty tool calls off the screen, so Write shows file_path. Long values are cut at 88 characters and newlines become spaces. tested with a 5,000-character content field.

One test that asserts on this file's own source

no_emitter_between_here_and_the_terminal_writes_a_blank_row_of_its_own reads term.rs, term/frame.rs and term/app.rs through include_str!, strips lines beginning //, and asserts that a needle assembled at runtime as format!("Line::{}()", "default") appears in none of them. Blank rows are boundaries, decided in spacing.rs alone.

Two things about it. The needle is assembled rather than written out “because this file is its own haystack”, which is the same technique the manifest test uses. And the doc names the exception rather than leaving it to be discovered: a block's internal layout may use blank rows, which is what welcome.rs does between its sections. tested, and the failure it prevents has no other witness: a second hand-rolled Line::default() beside a separate() passes every test that renders lines and produces two blank rows on a real screen.

Coverage

term.rs is 1,533 lines and was read in full for this page. Above the #[cfg(test)] boundary it declares 56 function items, counting the cfg-duplicated terminal_size (three), console_is_utf8 (two) and adopt_utf8_output (two) separately. Forty-one are Term methods, one is Drop::drop, and fourteen are free functions. Every one is named on this page: 56 of 56. Twelve of the fourteen tests are described or cited; the two that are not are the_banner_argument_is_the_one_a_human_would_look_at and a_long_command_is_cut_to_one_line, both covering summarise_args, which the table above summarises.

Not settled here. Whether the frame that Frame::install returns looks right on any console. A test binary is handed a pipe by cargo, which is exactly the condition under which fallback_reason says no, so install cannot run inside one at all. unverified: a run in Windows Terminal, conhost, iTerm2 and a Linux terminal at several window sizes, with screenshots, would settle it.
