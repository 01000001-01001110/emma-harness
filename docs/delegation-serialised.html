One at a time, and no recursion

Delegation The nested run One at a time Agent definitions resolve_tools The brief The footer Budgets & spend emma agents

Two of the three properties the module doc claims are about what cannot happen: two subagents cannot run at once, and a subagent cannot delegate. Neither is enforced by a check inside the loop. One is a one-permit semaphore held across the whole nested run; the other is the order in which two registries are built.

crates/emma/src/delegate.rs — module doc, Delegate::permit, Delegate::new 
//! **Three properties, each with the failure it prevents.**
//!
//! *One at a time.* A one-permit [`Semaphore`] held for the whole nested run.
//! Two subagents would mean two approval prompts racing for one stdin:
//! `decide` calls `prompt_header` and only then `ask`, so two concurrent
//! approvals interleave as A's header, B's header, A's question, B's question:
//! a screen showing B's evidence above A's question, with one `y` going to
//! whichever holds the mutex. That is the defect `LineSource::drain` exists to
//! prevent, arriving by another route, and `drain` makes it *worse*: the second
//! prompt discards the line typed in answer to the first. The closest prior art
//! (goose) resolved the same collision by refusing to run subagents at all
//! unless approval is switched off, which is the escape hatch Emma's design
//! rules out. The permit is redundant today (`run_goal` awaits its tool calls
//! one at a time), and it is what makes a future parallelisation of that loop
//! fail loudly rather than quietly.
//!
//! *No recursion, by construction.* Each agent type's registry is built here,
//! from tools resolved **before this tool exists**, so there is nothing to
//! forget at a call site and no depth counter to thread. An inner model asking
//! for `Delegate` gets the ordinary `no_such_tool` observation and routes around
//! it.
//!
//! *The footer is written from the log.* See [`footer`]. It is the answer to the
//! one failure delegation manufactures rather than merely risks.

The permit, and the screen it protects

Delegate holds a Semaphore with one permit. It is acquired after the budget arithmetic and the brief are settled, and the guard lives until invoke returns.

It buys nothing today

run_goal awaits its tool calls one at a time, so the parent cannot issue two delegations concurrently in the first place. The permit is there so a future parallelisation of that loop fails loudly: without it the symptom would be a misread approval prompt rather than a stack trace.

Recursion, prevented by construction

There is no depth counter and no call-site rule to forget. Each agent type's registry is built in Delegate::new, from the available slice main.rs assembles before Delegate itself is constructed. A tool that does not exist yet cannot be in a list, so no child registry can contain it.

crates/emma/src/main.rs — the construction order; crates/emma/src/delegate.rs — Delegate::new

The guard is a property of that ordering, which means a future edit that built child registries from the parent's would remove it silently. So there is an assertion whose message says exactly that: 

            debug_assert!(
                !tools.names().contains(&NAME),
                "the child registry contains {NAME}: recursion is prevented by this registry \
                 not containing it, so a future edit that builds it from the parent's has \
                 removed the only guard"
            );
crates/emma/src/delegate.rs — Delegate::new

debug_assert! is compiled out of a release build, so it is a developer's tripwire rather than a runtime guarantee. The runtime guarantee is the behavioural test, which asks for the worst case: an agent file that names Delegate in its own tools list. tested crates/emma/tests/delegate.rs an_agent_type_cannot_be_given_the_delegate_tool_even_by_name builds such a type and asserts Delegate is absent from tools_of.

    /// The tools one agent type may use. For the test that recursion is
    /// prevented by construction rather than by a check.
    pub fn tools_of(&self, agent: &str) -> Vec<&'static str> {
        self.types

            .map(|t| t.tools.names())
            .unwrap_or_default()
    }

tools_of answers Vec::default() for a name that is not a type, which is indistinguishable from a type with no tools. That conflation cannot arise in practice: Delegate::new refuses to register a type whose registry came back empty, so no offered type has zero tools.

What serialisation costs

There is no fan-out. Ten independent questions are ten delegations end to end, each paying the next one's startup, and the wall clock is their sum. The five-minute per-delegation deadline does not bound that sum: it bounds one delegation, and the parent's own wall clock is checked at the parent's next iteration boundary. A parent that issues four delegations back to back can therefore run twenty minutes past a five-minute cap, which is stated on Budgets & spend rather than discovered.
