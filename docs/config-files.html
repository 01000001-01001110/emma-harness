Every file Emma reads, and how each one fails

Configuration Discovery Every file The spine Reading .claude/ Skills & commands Agents Your own files Themes It did not apply

There is no single configuration file and no merged view of one. Three crates read from three scopes, and the reason a reader gets lost is that the project's configuration and the person's are different files, with different names, in different places, failing in different ways. This page is the map: every file, who reads it, what it decides, and what happens when it is wrong.

Seven kinds of file

A byte order mark is not malformed, and used to be

Until 2026-08-23 every JSON config here (.emma/config.json, .claude/settings.json, .claude/settings.local.json and the user's global ~/.claude/settings.json) refused the boot if it began with a UTF-8 BOM, with is malformed: expected value at line 1 column 1. That error names a correct file.

It matters on Windows specifically, because it is what the ordinary tools produce: PowerShell's >, Out-File and Set-Content -Encoding utf8 all write that mark. A settings file generated by a script could not start Emma.

The mark is stripped now, on every one of those readers. claude::open_frontmatter has stripped the same three bytes since 101 real skills were dropped by them; the JSON readers were written separately and never got it. One input shape, two answers, in one crate. tested five tests in crates/harness/tests/real_file_shapes.rs, each asserting the content behind the mark rather than that the boot merely survived, with a control that JSON which is genuinely malformed still refuses and still names the file. Removing the strip turns exactly those five red.

Rows one to four belong to the project and rows five to seven belong to the person, and nothing crosses. settings.rs's module doc gives the reason: the project's configuration is shared by everyone who clones the repository, so a personal default written there would be two files answering one question with no rule for disagreeing, and the answer that won would be the repository's, on somebody else's screen. There is no theme key in config.json and no personas key in ~/.emma/settings.json. Neither key appears in the other file.

The one exception to "the project's files never touch the person's" runs the other way and is narrow: ~/.claude/settings.json contributes deny rules to the project's permission set. That is a restriction crossing a boundary, never a grant. It is on the compatibility page, because the argument for it is the same argument as the discovery skip.

Four boot states, and they are closed

The crate's module doc states them, and the phrasing matters because it is the rule every refusal on the rest of this chapter is an instance of.

crates/harness/src/lib.rs · module doc

//! **The boot states, and they are not open here:** absent → refuse to start,
//! naming every path searched; present but empty → boot and answer nothing;
//! malformed → refuse to start, naming the file and the problem; and, in
//! `.emma/` only, persona files that nothing selects → refuse, because an empty
//! harness is a statement and an unselected one is an accident. That last rule
//! deliberately does not extend to `.claude/agents/`; `select_persona` says why.
//!
//! "Absent" is decided in `discover_in`, and a directory existing is not enough
//! to make it present: in the home directory a `.emma/` holding only credentials
//! is walked past rather than adopted, because `emma api` creates it and nobody
//! chose it. There it is the absent case, not the empty one.
//!
//! The reasoning, because the edges follow from it: an agent booted with the
//! wrong prompt does not crash. It acts fluently and confidently, attributed to
//! an `instructions_hash` nobody reviewed — and in Emma it acts by writing files
//! and running commands. So any ambiguity about *what the model was told*
//! resolves to not starting. The empty case is the one that is not ambiguous:
//! someone made the directory and put nothing in it, so Emma boots with no
//! standing instructions and needs no special case anywhere in the loop. That
//! the empty case needs no code is the proof the harness is separable from the
//! engine.
crates/harness/src/lib.rs — module doc

One function reads all of it

load_selecting is the whole of loading. It branches on the flavour once, at the top, to get five values out of the spine file, and then every later step is flavour-independent. Reading it is the fastest way to see what order things happen in and which failures are fatal.

crates/harness/src/lib.rs · Harness::load_selecting, the flavour branch

        let (spine, raw, hook_defs, status_block, permission_block) = match flavor {
            Flavor::Emma => {
                let raw = read_if_present(&spine_path)?;
                let spine: Spine = if raw.trim().is_empty() {
                    Spine::default()
                } else {
                    serde_json::from_str(&raw)
                        .with_context(|| format!("{} is malformed", spine_path.display()))?
                };
                let hooks = spine.hooks.clone();
                let status = spine.status_line.clone();
                let permissions = spine.permissions.clone();
                (spine, raw, hooks, status, permissions)
            }
            Flavor::Claude => {
                let (mut settings, raw) = claude::Settings::read(&root)?;
                // Taken before the hooks block is consumed, and separately from
                // it: a status line that cannot be resolved must not be able to
                // stop a hook from resolving, or the other way round. The
                // permissions block is taken on the same rule and for the same
                // reason — one unreadable key must not cost another.
                let status = settings.status_line.take();
                let permissions = std::mem::take(&mut settings.permissions);
                let hooks = settings.into_hook_defs(&root)?;
                (Spine::default(), raw, hooks, status, permissions)
            }
        };
crates/harness/src/lib.rs — Harness::load_selecting

The three keys are taken apart before any of them is resolved. Ordering it that way is the difference between one bad key costing its own feature and one bad key costing the other two.

The prompt is concatenation, and that is a property

The standing instructions are assembled from a fixed list of files, in a fixed order, with nothing trimmed, normalised or re-wrapped. With one file present the assembled prompt is that file's bytes. That is what makes a prompt hash comparable across a refactor and therefore worth logging.

crates/harness/src/lib.rs · assemble, the doc

/// Fixed order, shared first, absent files skipped, and **nothing trimmed or
/// re-wrapped** — so with one file present the assembled text is that file's
/// bytes. That is what makes a prompt hash comparable across a refactor.
///
/// `.emma/`: `_shared/rules.md`, `_shared/business.md`, `<persona>/rules.md`,
/// `<persona>/soul.md`. A persona file cannot remove a shared rule, because
/// assembly is plain concatenation — the shared text is still there for a
/// reviewer to see. Overriding `_shared` is a review on `_shared`. It is a
/// review discipline, not an enforcement mechanism.
///
/// `.claude/`: the project's `CLAUDE.md` (beside the directory, where Claude
/// Code puts it), then `.claude/CLAUDE.md`, then the selected agent's body.
/// Same rule, same order-is-fixed property.
///
/// Returns the tool allowlist alongside, because in the Claude flavour it is
/// carried in the same file as the prompt layer and reading that file twice
/// would be two chances to disagree.
crates/harness/src/lib.rs — assemble

Layers are joined with "\n\n", and an existing-but-empty file is skipped rather than contributing a blank separator, which is what keeps the single-file case byte-exact.

crates/harness/src/lib.rs · read_layer, read_if_present

/// A file that exists but is empty is skipped, so it cannot contribute a stray
/// blank-line separator to the assembled bytes.
fn read_layer(path: &Path) -> Result<Option<String>> {
    if !path.is_file() {
        return Ok(None);
    }
    let text =
        std::fs::read_to_string(path).with_context(|| format!("reading {}", path.display()))?;
    Ok((!text.is_empty()).then_some(text))
}
fn read_if_present(path: &Path) -> Result<String> {
    if !path.is_file() {
        return Ok(String::new());
    }
    std::fs::read_to_string(path).with_context(|| format!("reading {}", path.display()))
}
crates/harness/src/lib.rs — read_layer, read_if_present

Two things outside the prompt do get adjusted, and the module doc names both so that "nothing is trimmed" is not read wider than it is: a skill body is taken from after the frontmatter with leading whitespace stripped, and a command body is trimmed at both ends. Neither is always-on prompt text. A skill body arrives only when the model loads it, and a command body is text a person typed a /name to summon. Both are on the skills page.

What is hashed, and why it is truncated

Three digests appear in config check and in the startup log: instructions over the assembled prompt, config over the raw bytes of the spine file, and one per hook and per skill. All of them come from one six-line module.

crates/harness/src/hash.rs · the whole file, minus its uses

//! One digest function, used for every hash the harness reports.
//!
//! Kept here rather than pulled from a shared crate because it is six lines and
//! a shared crate would be a dependency edge bought for six lines. The
//! truncation to sixteen hex characters is not security — nothing here
//! authenticates — it is so a digest fits in a log line a human reads.
//!
//! `short` is what the rest of the crate calls, and the only caller of
//! `sha256_hex` in this workspace; the untruncated form is exposed beside it so
//! that wanting the whole digest never means reaching for a second sha2.

pub fn sha256_hex(input: &str) -> String {
    let mut h = Sha256::new();
    h.update(input.as_bytes());
    format!("{:x}", h.finalize())
}

/// The short form that appears in snapshots and logs.
pub fn short(input: &str) -> String {
    sha256_hex(input)[..16].to_string()
}
crates/harness/src/hash.rs

config_hash is taken over raw, the file's bytes, rather than over the parsed Spine. Reformatting the JSON changes it and re-ordering two keys changes it, which is the behaviour a reader wants from a line that answers "is this the same configuration file as yesterday". certified: an empty .emma/config.json containing {} reports config 44136fa355b3678a, which is sha256("{}")[..16]; this repository's own config.json reports edd1817c1861d002.

What the loop is given

Everything above ends in one struct, and the discipline the crate exists to enforce is what is not on it. The loop never reads a file, never learns which layer a sentence came from, and never branches on configuration.

crates/harness/src/lib.rs · Harness

/// What the loop consumes. Everything here is already decided.
#[derive(Debug)]
pub struct Harness {
    pub root: PathBuf,
    pub flavor: Flavor,
    /// `None` is the empty-harness boot, not an error.
    pub persona: Option<String>,
    /// The assembled system prompt, byte-exact. Empty when there is nothing to
    /// assemble.
    pub instructions: String,
    pub config_hash: String,
    skills: Vec<SkillDef>,
    commands: BTreeMap<String, String>,
    hooks: Vec<ResolvedHook>,
    tools: Option<Vec<String>>,
    agents: Vec<AgentDef>,
    agent_notes: Vec<String>,
    /// The configured status-line program, when one resolved.
    status_line: Option<StatusLine>,
    /// Why there is not one, when configuration asked for something Emma could
    /// not honour. A sentence rather than a boot failure — see `statusline.rs`.
    status_line_note: Option<String>,
    /// Project-scope permission rules, still as strings. See the region above
    /// for why they are not parsed here.
    permissions: Vec<PermissionEntry>,
}
crates/harness/src/lib.rs — Harness

Five fields are public and eight are private behind accessors, and the split tracks whether the loop needs the value or only a view of it. The accessors are one-liners with one exception each way: select_tools consumes a registry and is on the spine page, and expand_command does the whole of command expansion and is on the skills page. instructions_hash, is_empty, skills, skill, skill_names, tools, agent_types, agent_notes, command_names, status_line, status_line_note, permissions and permissions_file are getters and nothing more. run_hooks and on_user_prompt forward into hooks.rs and are Consent & permissions.

The snapshot, and the two things it refuses to carry

snapshot is what startup logs and what config check prints from. It carries identity and never content.

crates/harness/src/lib.rs · Harness::snapshot

    /// What startup logs and a `config check` prints: identity only. A snapshot
    /// carrying prompt text would be a second copy to drift.
    pub fn snapshot(&self) -> serde_json::Value {
        let hooks: Vec<_> = self.hooks.iter().map(ResolvedHook::identity).collect();
        let skills: Vec<_> = (self.skills.iter())
            .map(|s| serde_json::json!({ "name": s.name, "hash": s.hash }))
            .collect();
            // The rule text and the list it is in, never a resolved verdict: the
            // question a reader has is "what is written down", and a snapshot
            // that showed conclusions would be a second copy of the matcher to
            // drift away from the first.
            "permissions": self.permissions.iter().map(|p| {
                serde_json::json!({ "rule": p.rule, "kind": p.kind.word(),
                                    "source": p.source.display().to_string() })
            }).collect::<Vec<_>>(),
            // Identity of the program, never its text — the same rule a hook
            // follows, and for the same reason: a log that records a name
            // cannot answer "was this the program that ran".
            "status_line": self.status_line.as_ref().map(StatusLine::identity),
crates/harness/src/lib.rs — Harness::snapshot

A hook and a status line are recorded as a path plus a hash of the file's contents, so a log line can answer "was this the program that ran" rather than only "what was it called". A permission rule is recorded as the string and the list it was in, never as a verdict, because a verdict in the snapshot would be a second implementation of the matcher.
