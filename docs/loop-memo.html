The agent loop

The memo rule

The agent loop One turn Failure The memo Endings The kick Budgets Done Seams

A call that failed is not repeated identically until something else has succeeded. The rule is split across two functions and neither of them states it, which is why the architecture map calls this the only tricky control flow in the file.

crates/emma/src/agent.rs — Agent::run_goal, Agent::run_tool_call, memo_key

Why not "never again this turn"

The simpler rule, refusing a call that has ever failed, is affordable only when the whole tool surface is one read-only search. Emma's working rhythm is run the tests, see them fail, fix a file, run the tests again, and a memo keyed on the call alone would forbid the second run, which is the one that proves the fix. So the memo clears the moment any tool succeeds: an identical retry is refused only when literally nothing has changed since it failed, which is the case where retrying is a loop rather than a step.

The reading half

// crates/emma/src/agent.rs — Agent::run_tool_call
if failed_now.contains(&memo_key(call)) {
    return fail(
        "already_failed",
        format!(
            "this exact {} call already failed and nothing has changed since, so it \
             was not run again. Change the arguments or take a different route.",
            call.name
        ),
    );
}

The set arrives as &HashSet<String>, so this function cannot write to it. That is the whole of the reader: no clearing, no inserting, no notion of what "since" means. The sentence sent back names the tool and says what to do instead, because already_failed alone reads as a refusal rather than as a route change.

crates/emma/src/agent.rs — Agent::run_tool_call

Position matters twice. The check sits after argument validation, so a call whose arguments were malformed is a validation failure rather than a memo hit and can be corrected. It sits before the terminal banner, the tool_call record, the PreToolUse hooks and the approval gate, so a refused repeat costs no hook process and no prompt. certified by reading the function: the failed_now.contains line is between tool.validate_args and self.s.term.tool_started.

The writing half

// crates/emma/src/agent.rs — Agent::run_goal, the tool-dispatch loop
let mut results = Vec::new();
for call in turn.tool_calls() {
    tool_calls_since_kick += 1;
    // Set on the attempt rather than on success: a model whose only
    // tool call was denied at the gate is still mid-task, and the
    // stop that follows is a stall to be nudged, not a greeting.
    worked = true;
    let (block, succeeded, label) =
        self.run_tool_call(call, &turn_id, &failed_now).await;
    if succeeded {
        // Something changed, so an earlier failure is worth trying
        // again. This is what keeps edit-then-rerun-the-tests from
        // being blocked by the memo.
        failed_now.clear();
    } else if let Some(label) = label {
        failed_now.insert(memo_key(call));
        if !failed_ever.contains(&label) {
            failed_ever.push(label);
            trim_oldest(&mut failed_ever);
        }
    }
    results.push(block);
}
place(&mut query, &mut pending_turn, results);

clear() empties the whole set, not the key that just succeeded. That is the rule: one success anywhere means the world may have changed, so every remembered failure is worth trying again. The two collections are different in shape and lifetime. failed_now is a set of memo keys that is emptied on any success; failed_ever is a list of human-readable labels that is never emptied, deduplicated by contains, and trimmed to the last twenty. The kick quotes the second. See The kick.

crates/emma/src/agent.rs — Agent::run_goal

Calls inside one turn are dispatched in order and the set is updated between them, so a model that emits the same failing call twice in a single turn is refused the second time. A model that emits call A, has it fail, then call B which succeeds, then call A again in the same turn gets A run again, because B cleared the set. certified by reading the loop body: the clear and insert both happen inside for call in turn.tool_calls(), before the next iteration reads &failed_now.

What makes two calls the same call

// crates/emma/src/agent.rs
/// What makes two calls "the same call". Name plus arguments, canonically
/// rendered — so `Bash(ls)` and `Bash(ls)` collide and `Bash(ls a)` does not.
fn memo_key(call: &ToolCall) -> String {
    memo_key_of(&call.name, &call.input)
}

/// The same key from the two fields a session record has, which is not a
/// `ToolCall`. One definition rather than two: a resume that keyed the restored
/// memo differently from the loop would restore a set that never matches, and
/// the symptom would be a memo that silently does nothing.
pub(crate) fn memo_key_of(name: &str, input: &Value) -> String {
    format!("{name}\u{1}{input}")
}

The separator is U+0001, a byte no tool name contains, so a tool called Read with argument x cannot collide with one called Readx with no arguments. The arguments are rendered by serde_json's Display, which means whitespace in the model's original JSON is already gone by the time a key is built. tested the_memo_key_separates_different_arguments asserts that two identical calls agree and that ls and ls -a do not.

crates/emma/src/agent.rs — memo_key, memo_key_of
Object key order does not change the key

serde_json::Value's map is a BTreeMap unless the preserve_order feature is on, so {"a":1,"b":2} and {"b":2,"a":1} render identically and produce one memo key. That feature is not enabled anywhere in this workspace's feature graph. certified: cargo tree -p emma -e features -i serde_json prints the feature tree and no line of it names preserve_order or indexmap. Re-run it with | grep -ci 'preserve_order\|indexmap', which prints 0, at commit a3eba74.

The memo survives a resume

// crates/emma/src/agent.rs — Resumed
/// **Why the memo is here too.** `failed_now` is the loop's "this exact call
/// failed and nothing has changed since". Dropping it does not overspend
/// anything, but it hands the resumed model back the identical failing call as
/// its most obvious next move, which is the specific loop the memo exists to
/// break.
pub struct Resumed {
    pub messages: Vec<Message>,
    pub tokens: i64,
    pub iterations: u32,
    pub kicks: u32,
    /// Memo keys — see [`memo_key`] — for calls that had failed with nothing
    /// having succeeded since.
    pub failed_now: Vec<String>,
    /// Human-readable labels for everything that failed during the goal, which
    /// is what a kick quotes back.
    pub failed_ever: Vec<String>,
}

It travels as a Vec<String> and becomes a set on arrival: let mut failed_now: HashSet<String> = resumed.failed_now.into_iter().collect();. memo_key_of exists so the restoring code can build the same key from the two fields a session record has, which is not a ToolCall. A second definition would restore a set that never matches, and the symptom would be a memo that silently does nothing, which no test asserting "the tool ran" would catch.

What is not verified here

unverified Whether a real model reads already_failed as an instruction to change route. The block reaches the model with the right flag and the right sentence, which is what the tests assert. Whether that changes what a live model does next is a claim about the model, not about the loop, and nothing here measures it. What would settle it: a live session that drives a tool into a repeatable failure, with the session JSONL read back to see what the model tried after the refusal.

unverified Whether a restored memo ever matches in practice. The key function is shared, which removes the obvious way for it to fail, and there is no end-to-end test that interrupts a goal with a failed call outstanding, resumes it, and asserts the repeat is refused. What would settle it: such a test, or a live interrupt-and-resume with the refusal visible in the session file.
