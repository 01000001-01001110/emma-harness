Your own files: preferences, tools and the key

Configuration Discovery Every file The spine Reading .claude/ Skills & commands Agents Your own files Themes It did not apply

Two files under the home directory, never in the working tree, read by the binary and the provider crate rather than by the harness. One holds preferences and fails by going quiet; the other holds secrets and fails by refusing. A preference store that refused to start would be the tail wagging the dog. A credential write that replaced the document deleted a key belonging to another part of the program.

Why these are not in the project

crates/emma/src/settings.rs · module doc

//! `~/.emma/settings.json` — the small amount of state that belongs to the
//! person rather than to the project.
//!
//! It lives beside `credentials.json` under the home directory and **never** in
//! the working tree, for the same reason the key does: Emma runs inside
//! repositories, and anything it writes next to the code is something the next
//! `git add .` publishes. A model id is not a secret, but a file Emma creates
//! in someone's repository without being asked is a surprise either way.
//!
//! Deliberately *not* the harness. `.emma/config.json` is the project's
//! configuration, read by `emma-harness`, and putting a personal default in it
//! would mean two files answering "what is the model" with no rule for
//! disagreeing.
//!
//! **A model is not a model without a provider.** `claude-opus-5` means nothing
//! to anyone but Anthropic, so the stored unit is a provider plus a model *per
//! provider*: switching away and back must not cost you the model you had
//! chosen, because re-typing it is the entire annoyance of switching. The file
//! written before providers existed — a bare `{"model": …}` — is read as
//! Anthropic's, silently, because the only possible answer to a prompt asking
//! about it is yes.

A file that will not parse is read as an empty one

crates/emma/src/settings.rs · load

/// A missing or unreadable file is an empty `Settings`, not an error: this is a
/// preference store, and refusing to start because a preference could not be
/// read would be the tail wagging the dog.
///
/// Reading is also where the pre-provider file becomes a provider-scoped one.
/// It is done here rather than in a migration step so that every reader gets
/// the same answer whether or not anything has written since — there is no
/// window in which `emma` and `emma config check` disagree about the model.
pub fn load(home: &Path) -> Settings {
    let mut settings: Settings = std::fs::read_to_string(path(home))
        .ok()
        .and_then(|raw| serde_json::from_str(&raw).ok())
        .unwrap_or_default();
    if let Some(model) = settings.legacy_model.take() {
        // Anthropic is safe to assume: it is the only provider that has ever
        // existed here, so a model set before providers were a concept was set
        // for that one.
        settings
            .models
            .entry(DEFAULT_PROVIDER.to_string())
            .or_insert(model);
        settings
            .provider
            .get_or_insert_with(|| DEFAULT_PROVIDER.to_string());
    }
    settings
}

An unknown provider is an error

crates/emma/src/settings.rs · resolve_kind, the doc and the resolution

/// **An unknown provider is an error and never a fallback.** Falling back to
/// Anthropic would make a mis-set provider indistinguishable from a correct
/// one — same output, same bill, no message — and the mistake would only
/// surface as a model id that "does not exist". The error names what this build
/// supports.
///
/// `--model` on its own still means "this model, on the current provider",
/// which is what it means today; a cross-provider override for one run is
/// `--provider X --model Y`.
    let (model, model_source) = match flag_model {
        Some(model) => (model.to_string(), "--model"),
        // Keyed by the *resolved* provider's canonical name, so a settings file
        // written as `Anthropic` and a flag typed as `anthropic` find the same
        // entry.
        None => match settings.as_ref().and_then(|s| s.models.get(kind.name())) {
            Some(model) => (model.clone(), "settings.json"),
            None => (kind.default_model().to_string(), "built-in default"),
        },
    };

The tools block

Four optional strings. These are the sidebar keys a person presses, not anything the model can reach, and they are read by crate::usertools rather than by anything in the harness.

crates/emma/src/settings.rs · ToolSettings

/// What the user has said about their tools, all optional. Values are a bare
/// program name (looked up on PATH) or an absolute path — never a command
/// *line*: `usertools` spawns argv directly and refuses to word-split a
/// string, because splitting is the first half of running text through a
/// shell and a path with a space in it is not an argument boundary.
#[derive(Debug, Default, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct ToolSettings {
    /// The shell the Shell tool opens. Windows honours this directly; see
    /// `usertools` for why mac/linux v1 lets the terminal app pick instead.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub shell: Option<String>,
    /// The editor the Code and Settings tools open.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub editor: Option<String>,
    /// The file manager, when the OS default (`explorer`/`open`/`xdg-open`)
    /// is not the one wanted.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub file_browser: Option<String>,
    /// Where the Data Explorer points. Absolute path; defaults to `~/.emma`.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub data_dir: Option<String>,
}
crates/emma/src/settings.rs — ToolSettings

Every value is one program name or one absolute path, and never a command line. A bare name is looked up on PATH; an absolute path is checked for existence. Splitting a string on spaces is the first half of running text through a shell, and a path with a space in it is not an argument boundary. So a value carrying arguments is not split. It fails, and the failure names the rule rather than only the symptom.

crates/emma/src/usertools.rs · resolve_value

fn resolve_value(m: &dyn Machine, value: &str, origin: &str) -> Result<PathBuf, String> {
    let p = Path::new(value);
    if p.is_absolute() {
        if m.exists(p) {
            Ok(p.to_path_buf())
        } else {
            Err(format!("{origin} is set to {value}, which does not exist"))
        }
    } else if let Some(found) = m.find(value) {
        Ok(found)
    } else if value.chars().any(char::is_whitespace) {
        Err(format!(
            "{origin} is set to {value}, which is not on PATH (a configured value is one \
             program name or absolute path, never a command line)"
        ))
    } else {
        Err(format!("{origin} is set to {value}, which is not on PATH"))
    }
}
crates/emma/src/usertools.rs — resolve_value

The whitespace arm exists because the generic message, "which is not on PATH", sends somebody to check their PATH for a program that was never the problem. A value that does not resolve is an error naming it and is never quietly swapped for a probed default: a silent substitution looks identical to success right up until the wrong program opens.

crates/emma/src/usertools.rs — resolve_editor, probe_first, console_hostable, the module doc

$VISUAL and $EDITOR get the one concession, and it is a concession to the world rather than to the rule: those variables really do hold command lines, so a value there that does not resolve as a whole is skipped and the chain continues to the probe. Skipped, not split. Two smaller behaviours: a .cmd or .bat target is refused with a sentence saying to point the setting at the underlying .exe, because a script cannot own a console window; and settings.json is re-read on every call rather than cached, so the Settings tool's own writes appear on the next frame, while PATH lookups are cached for the life of the process.

The sampling block, where absence is two answers

sampling is keyed by provider for the reason models is: these are per-provider answers, and one global temperature would be wrong for whichever provider it was not chosen on. Each entry has three optional fields. 

"sampling": {
  "ollama": { "temperature": 0.15 },
  "anthropic": { "max_output_tokens": 16000, "stream": false }
}
crates/emma/src/settings.rs — SamplingSettings, Settings::sampling

The reason the fields are Option rather than defaulted at load is that an absent field does not mean the same thing in all three, and a page saying "absent means the default" would be wrong about one of them. An absent temperature means no key reaches the provider and the host decides: Emma does not know what number that is and does not guess one. An absent max_output_tokens means Emma sends 32,000, because the Messages API requires the cap and there is no absent case to be honest about. An absent stream means on. tested: an_absent_temperature_resolves_to_the_host_default_on_every_provider asserts the first across all four providers, and an_absent_output_cap_resolves_to_the_emma_default_because_it_is_always_sent the second.

/// `~/.emma/credentials.json`. A function rather than a constant because every
/// caller must pass the home it means — tests included, which is the only
/// reason they can run without touching the developer's real credentials.
pub fn credentials_path(home: &Path) -> PathBuf {
    home.join(".emma").join("credentials.json")
}
/// Which providers have a key stored in the file. Names only — `config check`
/// answers "did I store that key?" without being a way to read one back.
pub fn stored_providers(home: &Path) -> Vec<String> {
    read_keys(&credentials_path(home))
        .map(|keys| keys.into_keys().collect())
        .unwrap_or_default()
}

The scar: a write that deleted a key it never knew about

This file can hold more than one program's secrets. A search tool kept its key at the top level, beside the provider entries, until that tool left on 2026-09-05; the file it wrote is still on disks. A write that serialised a fresh document, the obvious implementation, deleted whichever keys the caller did not happen to know about, silently, and the symptom arrived hours later as a tool that had stopped being registered.

store now reads the file, replaces one provider's entry, and writes back everything else it found. A file that cannot be parsed is an error rather than something to overwrite, for the same reason: overwriting is how the other keys are lost. certified: a scratch credentials.json holding {"providers":{"anthropic":{"api_key":"sk-a"}},"other_key":"bk-1"}, after emma set-provider anthropic with a new key on stdin, reads {"other_key":"bk-1","providers":{"anthropic":{"api_key":"sk-newkey"}}}. Release binary, 2026-08-16. The field was the search tool's when this was observed; its name is not what the observation proves.

Reading an answer aloud

crates/emma/src/speech.rs is output only: no capture, no microphone, nothing leaving the machine, and off unless asked for. It landed from a branch that is macOS-only through say(1), and the owner runs Windows, so it either arrived with a real second implementation or as a setting that says the feature is unavailable here. It has the second implementation: Windows speaks through System.Speech.Synthesis.SpeechSynthesizer, driven by a fixed script handed to powershell.exe. certified: Backend is an enum with Say and Sapi, carried as a value rather than read from cfg! at each use, so every decision below it is exercised for both platforms by tests running on either one. Only backend is cfg-dependent and it is one expression.

crates/emma/src/speech.rs — module doc, Backend, backend, speak, plan_utterance

Nothing is spawned through a shell on either platform. The text of an answer is arbitrary model output, and it reaches the synthesiser on stdin rather than as an argument, so there is no argv element for it to be, no flag for a leading - to become, and no command line for it to be split out of. On Windows the voice name travels on stdin too. plan_utterance is the one place that decides what a child process is handed. A failure is a notice and never an abort: a missing binary, a voice this machine does not have, a non-zero exit. The answer is already on screen and this is decoration, so nothing in the file returns an error to the agent loop, and speak spawns and returns while a thread reaps.

Two decisions came across from the branch rather than being re-derived. A voice is stored by name, so a machine without it falls back to the system default and a synced settings file still starts. And an enhanced voice is a recommendation in the listing rather than a silent substitution, because preferring one would talk a user out of the voice they chose in their own accessibility settings. There is a cut on how much is read: the screen already has the whole answer, so the cap exists to stop a very long one becoming a monologue rather than to keep the spoken part short.

Neither synthesiser is looked for on PATH, which departs from usertools' PATHEXT-aware probe. That module resolves programs the user names, an editor or a shell, so it has to search the way the user's shell would. Both programs here are parts of their operating system at fixed locations, and a powershell.exe somebody dropped earlier on PATH is not what the owner asked for. Each is an absolute path checked with one exists.

What the Windows arm cannot reach is stated rather than papered over. System.Speech sees only the SAPI5 voices registered under HKLM\SOFTWARE\Microsoft\Speech\Voices\Tokens, and the more natural OneCore voices live under a different key and are invisible to it. Measured on the owner's box on 2026-08-26, GetInstalledVoices() returned two, Microsoft David Desktop and Microsoft Zira Desktop, while the OneCore key held three tokens, so a voice installed on that machine could not be offered. Reaching OneCore needs the WinRT synthesiser, which returns a stream the caller must play, and that is an audio pipeline this module does not have. A consequence follows: no Windows voice is ever enhanced in the sense the macOS listing means, so the recommendation half of the branch's decision has nothing to recommend here and says so instead of inventing a ranking. observed: one reading of one machine's voice registry on 2026-08-26, recorded in the module. Another Windows box could hold a different set, and nothing re-runs the check.

A second personal file: ~/.emma/keybindings.json

Nine actions can be moved onto a different chord: the four Alt tool chords (shell, code, reveal, search), the three page chords (settings, memory, harness), and the two toggles (sidebar, help). Those names are exactly the keys the file uses, and they are named for the surface rather than for the key, so a rebound chord still reads as what it opens.

Alt+q and Ctrl-C are not in the layer at all, and that is a hole rather than an omission. They are the way out of a running goal, and a keymap file that could take the exit away is a keymap file that can lock somebody in. REBINDABLE is the whole list rather than a filter applied somewhere else downstream, so there is one place to read to know what can move.

A file may hold several named presets, and two facts about timing that the Settings rows state separately. The file is read once, at startup: nothing watches it, so an edit in an editor applies to the next run, which is the same rule the LSP card follows and for the same reason. Selecting a preset is live: every preset was already parsed by that one read, so switching swaps a table this process is holding and binds immediately. Making a preset change wait for a restart would be a control that does nothing on a screen whose whole point is that its controls do something.

A duplicate chord is refused rather than resolved. Two actions on one chord has no correct answer, and whichever the loader picked would be arbitrary and silent. Both clashing entries fall back to their compiled defaults, and the keymap carries a note naming the chord and the actions that wanted it, which the Settings row prints. An unknown action name is kept as a note too rather than failing the file, which is lsp.enabled's rule. tested on the parse and the load, including the duplicate refusal and the note it leaves.

The help chord is ctrl+/ and a bare ? on an empty box is not the same thing. ? stays compiled in beside , for Settings: it is a convenience on an empty box rather than a chord, it cannot be typed by accident mid-sentence, and it is out of this layer for the reason Enter is. Both the Help page and emma --help print whichever chord is bound now, because the text names an action and the keymap resolves it at the moment it is drawn.
