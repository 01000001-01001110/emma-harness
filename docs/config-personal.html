Your own files: preferences, tools and the key

Configuration Discovery Every file The spine Reading .claude/ Skills & commands Agents Your own files Themes It did not apply

Two files under the home directory, never in the working tree, read by the binary and the provider crate rather than by the harness. One holds preferences and fails by going quiet; the other holds secrets and fails by refusing. A preference store that refused to start would be the tail wagging the dog. A credential write that replaced the document deleted a key belonging to another part of the program.

Why these are not in the project

crates/emma/src/settings.rs · module doc

//! `~/.emma/settings.json` — the small amount of state that belongs to the
//! person rather than to the project.
//!
//! It lives beside `credentials.json` under the home directory and **never** in
//! the working tree, for the same reason the key does: Emma runs inside
//! repositories, and anything it writes next to the code is something the next
//! `git add .` publishes. A model id is not a secret, but a file Emma creates
//! in someone's repository without being asked is a surprise either way.
//!
//! Deliberately *not* the harness. `.emma/config.json` is the project's
//! configuration, read by `emma-harness`, and putting a personal default in it
//! would mean two files answering "what is the model" with no rule for
//! disagreeing.
//!
//! **A model is not a model without a provider.** `claude-opus-5` means nothing
//! to anyone but Anthropic, so the stored unit is a provider plus a model *per
//! provider*: switching away and back must not cost you the model you had
//! chosen, because re-typing it is the entire annoyance of switching. The file
//! written before providers existed — a bare `{"model": …}` — is read as
//! Anthropic's, silently, because the only possible answer to a prompt asking
//! about it is yes.

Six keys, and a seventh is silence

keytypewhat it does
provider string Which provider this build should use. An unknown one is an error and never a fallback, because falling back to Anthropic would make a mis-set provider indistinguishable from a correct one.
models object provider → the model last chosen for it. Per provider so that switching away and back costs nothing.
validated object provider → {at, how}, where how is checked or forced. Nothing writes it yet; it is read and written back so a build that does validate does not have its record stripped by one that does not.
tools object The sidebar's user tools. Four optional keys, below.
theme string The theme file's name. Absent means the built-in. See Themes.
model string Legacy. The pre-provider spelling. Read as Anthropic's, never written back, so it survives being read and disappears on the first save.
crates/emma/src/settings.rs — Settings, Validation, How

Every field carries skip_serializing_if, so a save writes only what is set. A settings file that grew a tools key because this build knows the word would be a file that mutates on every save, and a file that mutates on every save is one nobody can diff. tested: tool_settings_round_trip_and_an_empty_block_is_never_written asserts the raw text does not contain tools after a save with nothing set, and a_theme_choice_round_trips_and_an_unthemed_file_never_grows_the_key does the same for theme.

A file that will not parse is read as an empty one

crates/emma/src/settings.rs · load

/// A missing or unreadable file is an empty `Settings`, not an error: this is a
/// preference store, and refusing to start because a preference could not be
/// read would be the tail wagging the dog.
///
/// Reading is also where the pre-provider file becomes a provider-scoped one.
/// It is done here rather than in a migration step so that every reader gets
/// the same answer whether or not anything has written since — there is no
/// window in which `emma` and `emma config check` disagree about the model.
pub fn load(home: &Path) -> Settings {
    let mut settings: Settings = std::fs::read_to_string(path(home))
        .ok()
        .and_then(|raw| serde_json::from_str(&raw).ok())
        .unwrap_or_default();
    if let Some(model) = settings.legacy_model.take() {
        // Anthropic is safe to assume: it is the only provider that has ever
        // existed here, so a model set before providers were a concept was set
        // for that one.
        settings
            .models
            .entry(DEFAULT_PROVIDER.to_string())
            .or_insert(model);
        settings
            .provider
            .get_or_insert_with(|| DEFAULT_PROVIDER.to_string());
    }
    settings
}
crates/emma/src/settings.rs — load, path, save

There is no deny_unknown_fields on this struct and no error path out of load. Two .ok() calls swallow both an unreadable file and unparseable JSON. The consequence for a reader is that a typo here is silence, not a message: {"provdier": "anthropic"} boots happily on the built-in default. tested: a_corrupt_settings_file_is_not_a_startup_failure writes { not json and asserts both sources come back as built-in default.

The check available is the pair of lines config check prints, which name the source of each answer rather than only the value:

api key        NOT FOUND — no API key for anthropic. Set ANTHROPIC_API_KEY, or run

The legacy migration is live rather than historical. The owner's real file holds one key, model, and the resolved model this repository reports is that migration firing at read time. tested: a_model_set_before_providers_existed_still_runs pins the owner's file byte for byte with the comment "If this test goes red, an upgrade silently moved somebody off the model they chose", and asserts that the first save drops the flat key rather than leaving a second answer behind.

An unknown provider is an error

crates/emma/src/settings.rs · resolve_kind, the doc and the resolution

/// **An unknown provider is an error and never a fallback.** Falling back to
/// Anthropic would make a mis-set provider indistinguishable from a correct
/// one — same output, same bill, no message — and the mistake would only
/// surface as a model id that "does not exist". The error names what this build
/// supports.
///
/// `--model` on its own still means "this model, on the current provider",
/// which is what it means today; a cross-provider override for one run is
/// `--provider X --model Y`.
    let (model, model_source) = match flag_model {
        Some(model) => (model.to_string(), "--model"),
        // Keyed by the *resolved* provider's canonical name, so a settings file
        // written as `Anthropic` and a flag typed as `anthropic` find the same
        // entry.
        None => match settings.as_ref().and_then(|s| s.models.get(kind.name())) {
            Some(model) => (model.clone(), "settings.json"),
            None => (kind.default_model().to_string(), "built-in default"),
        },
    };

The tools block

Four optional strings. These are the sidebar keys a person presses, not anything the model can reach, and they are read by crate::usertools rather than by anything in the harness.

crates/emma/src/settings.rs · ToolSettings

/// What the user has said about their tools, all optional. Values are a bare
/// program name (looked up on PATH) or an absolute path — never a command
/// *line*: `usertools` spawns argv directly and refuses to word-split a
/// string, because splitting is the first half of running text through a
/// shell and a path with a space in it is not an argument boundary.
#[derive(Debug, Default, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct ToolSettings {
    /// The shell the Shell tool opens. Windows honours this directly; see
    /// `usertools` for why mac/linux v1 lets the terminal app pick instead.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub shell: Option<String>,
    /// The editor the Code and Settings tools open.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub editor: Option<String>,
    /// The file manager, when the OS default (`explorer`/`open`/`xdg-open`)
    /// is not the one wanted.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub file_browser: Option<String>,
    /// Where the Data Explorer points. Absolute path; defaults to `~/.emma`.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub data_dir: Option<String>,
}
crates/emma/src/settings.rs — ToolSettings

Every value is one program name or one absolute path, and never a command line. A bare name is looked up on PATH; an absolute path is checked for existence. Splitting a string on spaces is the first half of running text through a shell, and a path with a space in it is not an argument boundary. So a value carrying arguments is not split. It fails, and the failure names the rule rather than only the symptom.

crates/emma/src/usertools.rs · resolve_value

fn resolve_value(m: &dyn Machine, value: &str, origin: &str) -> Result<PathBuf, String> {
    let p = Path::new(value);
    if p.is_absolute() {
        if m.exists(p) {
            Ok(p.to_path_buf())
        } else {
            Err(format!("{origin} is set to {value}, which does not exist"))
        }
    } else if let Some(found) = m.find(value) {
        Ok(found)
    } else if value.chars().any(char::is_whitespace) {
        Err(format!(
            "{origin} is set to {value}, which is not on PATH (a configured value is one \
             program name or absolute path, never a command line)"
        ))
    } else {
        Err(format!("{origin} is set to {value}, which is not on PATH"))
    }
}
crates/emma/src/usertools.rs — resolve_value

The whitespace arm exists because the generic message, "which is not on PATH", sends somebody to check their PATH for a program that was never the problem. A value that does not resolve is an error naming it and is never quietly swapped for a probed default: a silent substitution looks identical to success right up until the wrong program opens.

keywhat it points atabsent means
shell The shell the Shell tool opens. Windows honours it directly. Probe the machine. On mac and linux the terminal application is opened and lets the user's shell be picked, because Emma holds this terminal and has nowhere to put a child that wants one.
editor The editor the Code and Settings tools open. $VISUAL, then $EDITOR, then a probe of code, cursor, subl, zed, and nvim on Windows only, where a new console can hold it.
file_browser The file manager. The OS default: explorer, open, xdg-open.
data_dir Where the Data Explorer looks. Absolute path. It opened a file manager there until 2026-08-23; the Data Explorer is a page in the frame now and launches nothing. ~/.emma.
crates/emma/src/usertools.rs — resolve_editor, probe_first, console_hostable, the module doc

$VISUAL and $EDITOR get the one concession, and it is a concession to the world rather than to the rule: those variables really do hold command lines, so a value there that does not resolve as a whole is skipped and the chain continues to the probe. Skipped, not split. Two smaller behaviours: a .cmd or .bat target is refused with a sentence saying to point the setting at the underlying .exe, because a script cannot own a console window; and settings.json is re-read on every call rather than cached, so the Settings tool's own writes appear on the next frame, while PATH lookups are cached for the life of the process.

Never the project directory. Nothing in auth.rs resolves a path relative to the working directory. The home path is computed rather than searched upward, which is what makes it a property rather than an intention. tested: a_credentials_file_in_the_project_directory_is_ignored plants a real credentials.json in a scratch cwd and asserts the error names a path under the fake home.

crates/llm/src/auth.rs · credentials_path, stored_providers

/// `~/.emma/credentials.json`. A function rather than a constant because every
/// caller must pass the home it means — tests included, which is the only
/// reason they can run without touching the developer's real credentials.
pub fn credentials_path(home: &Path) -> PathBuf {
    home.join(".emma").join("credentials.json")
}
/// Which providers have a key stored in the file. Names only — `config check`
/// answers "did I store that key?" without being a way to read one back.
pub fn stored_providers(home: &Path) -> Vec<String> {
    read_keys(&credentials_path(home))
        .map(|keys| keys.into_keys().collect())
        .unwrap_or_default()
}
crates/llm/src/auth.rs — credentials_path, stored_providers
The scar: a write that deleted a key it never knew about

This file holds more than one program's secrets. The web tools keep brave_search_api_key at its top level, beside the provider entries. A write that serialised a fresh document, the obvious implementation, deleted whichever keys the caller did not happen to know about, silently, and the symptom arrived hours later as a tool that had stopped being registered.

store now reads the file, replaces one provider's entry, and writes back everything else it found. A file that cannot be parsed is an error rather than something to overwrite, for the same reason: overwriting is how the other keys are lost. certified: a scratch credentials.json holding {"providers":{"anthropic":{"api_key":"sk-a"}},"brave_search_api_key":"bk-1"}, after emma set-provider anthropic with a new key on stdin, reads {"brave_search_api_key":"bk-1","providers":{"anthropic":{"api_key":"sk-newkey"}}}. Release binary, 2026-08-16.

Both failure directions are visible from config check, which reports whether a key resolved and from which source, by name and never by value: 

$ emma config check | tail -4        # a key stored and a key exported
api key        found (ANTHROPIC_API_KEY)
               the environment overrides the key stored for anthropic

$ printf 'not json' > ~/.emma/credentials.json && emma config check | tail -3
api key        NOT FOUND — …\fakehome\.emma\credentials.json is not valid credentials JSON:
expected ident at line 1 column 2
certified: release binary, 2026-08-16. The first is this repository with ANTHROPIC_API_KEY exported; the hour that second line saves is a key stored, a key exported, and no way to tell which one the 401 came from.

What this page did not settle

  • The user-tool launch path. Everything about tools.shell, tools.editor, tools.file_browser and tools.data_dir comes from reading usertools.rs, whose decision layer is pure and testable. Only the first three are still launch settings: Settings and the Data Explorer became pages on 2026-08-23 and resolve no program at all. No program was launched from a running frame here, and the code --wait message was never seen on a screen. unverified. Settle it by setting tools.editor to a value with an argument in it, pressing c in the frame, and reading the sentence.
  • The Windows credential ACL. The claim in write_private's cfg(not(unix)) arm is that a file in the user's profile is already protected by the profile's default ACL. Nothing in this tree reads an ACL, and the source says the same. unverified. Settle it with icacls %USERPROFILE%\.emma\credentials.json on a machine with a second local account.
  • validated. Nothing writes it. The round-tripping is tested by a_validation_written_by_a_later_build_is_not_stripped_by_this_one, but no build exists that produces one, so what the two values would mean in practice is still hypothetical.
