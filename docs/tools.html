What a tool is

tool-api is one file. That is a decision with a stated cost rather than an accident of size: it holds the error taxonomy, the success type, the two structs the runtime reads, the trait, and a registry — and nothing else, so that adding a tool stays “a crate plus one registry line”. Twice in this project's history the gate grew knowledge of a particular tool's arguments (a hard-coded query check, and inferring retrieval from an empty chunks array), and both times that promise became false.

ToolMeta: three bits, and one that was deleted

The predecessor's struct had a needs_approval field that nothing ever read. It was not ported — a declaration pretending to be a mechanism is worse than no declaration, because reviewers stop asking the question the field appears to answer. What is left is three bits, and each one has a reader:

Field Means Read by
read_only Cannot change local state: no file written, no process spawned. Not “cannot reach the network” — WebFetch and WebSearch both declare true and both talk to the outside. the approval gate
reaches_network Sends bytes off this machine by construction. A separate axis because writing is a risk the model states in the call, while egress is how a prompt-injected page turns a read tool into an exfiltration channel — and passes every local-damage check on the way out. the approval gate, per host
idempotent Running it twice has the same effect as once. Edit declares false and means it. Registry::register, and nothing else

That last row is the interesting one. idempotent was for a while declared by every tool and consulted by nothing — the exact shape the needs_approval deletion rejects. It was not deleted, because the answer is a genuine per-tool fact; it was given a reader instead. Registry::register panics on the pair read_only: true, idempotent: false, because a call that changes no local state cannot have a different effect the second time: that is one fact and its negation, and read_only is the one the gate is about to trust.

There is no Default

ToolMeta does not derive Default, so adding a field breaks every construction site in the workspace and each tool has to state the new bit rather than inherit it. The predecessor added a defaulted field and thereby granted a safety property to every tool written afterwards, chosen by nobody and noticed by no review.

An error is a fact about the call

Three variants, a stable kind string the model routes on, and prose kept separate from it so rewording a message never changes the taxonomy.

kind()VariantMeans
tool_unavailable Unavailable The machinery is absent or unconfigured — no key, no binary, no permission. Phrased “I cannot do this”, never “this cannot be done”.
tool_failed Failed It ran and did not succeed.
bad_arguments BadArguments Wrong arguments, including the kind only discoverable at run time — validate_args cannot stat a path or know whether a string occurs once in a file.

Emptiness is a result. A read of an empty file succeeds and returns nothing. A glob matching zero paths succeeds with an empty list. A grep with no hits succeeds. Blurring that turns “I could not look” and “I looked and there was nothing” into one message, and the model cannot route around a failure it has been told is an answer.

That rule was written about the filesystem and did not survive contact with Bash. A non-zero exit had been documented as Failed, which makes grep -q answering “no” a tool failure — and the loop refuses to repeat a call that already failed with nothing changed since, so one legitimate miss would have blocked that command for the rest of the turn. The line is now whether the command ran: could-not-spawn, timed-out and killed are Failed; anything that started and finished is Ok. It was not resolved as “Bash is the documented exception”, because “except X” is how a rule starts becoming folklore.

Three tool sets need state that outlives one call, so each keeps it in the tool structs behind an Arc and hands the same instance to every member at construction. The invariant “these tools share one X” is therefore a wiring convention and not something the type system holds. Building the tools individually compiles and then silently misbehaves, and each failure is quiet in its own way:

Nothing catches a bypassed builder

Each crate's *_tools() function is the only supported way to build its set. Constructing a member directly is caught by nothing — not the compiler, not the registry's coherence check, not any test in the workspace.

tools/tasks escapes the whole problem: its four tools share no mutable state, because the file on disk is the state and is re-read on every call.

The order matters in two places. validate_args runs before the approval prompt, so a malformed call never spends a human's attention. The truncation rule

truncated alone is half an admission. “Output was truncated” is true and useless: it does not say whether the prose or an inventory was lost, does not say how much, and does not name the argument that would get the rest. A tool knows all three at the moment it cuts and nothing downstream can reconstruct them, so it says them in truncation and the runtime passes that on verbatim — to the model in the result, and to the human on the terminal line.

The rule: name the limit, name the loss, name the remedy — or say plainly that no argument raises it. The shape, from a real Glob call in this repository: 

[truncated: 1000 of 64097 matching paths shown — the 1000 most recently
modified — and 63097 dropped by a fixed 1000-result cap no argument raises.
A pattern matching 64097 paths is usually reaching into build output; narrow
`pattern` or set `path` to a subdirectory, which is the only thing that
returns the rest]
tools/fs/src/glob.rs — cuts

tested The number that must not appear in that sentence is max_results. the_result_cap_names_itself_the_loss_and_a_remedy_that_works asserts the invented knob is absent, because the defect this whole mechanism was built after was WebFetch advising the model to narrow a request when what had been dropped was an inventory it had no way to narrow. A remedy that cannot work is the failure being engineered against.

When several caps fire at once they stay several sentences, joined with ; also . Merging them is how a reader concludes the pattern was too broad when it was the traversal that gave up.

tested no_tool_here_cuts_without_naming_the_cap drives Glob, Grep, Read and Bash past their caps in one sandbox and demands of each: the flag set, a truncation reason over 40 characters containing a digit, and [truncated: present in content as well — because the model reads the content, not the struct. a_whole_answer_claims_nothing is the other half: an uncut result must carry neither, or the file would be satisfiable by marking everything truncated.

crates/emma/src/agent.rs — truncation_note

Path containment, in one implementation

tools/tasks and tools/lsp both depend on tools/fs so that path::resolve is the only answer to “is this path inside the root”. That matters more than code reuse usually does: a second implementation would not merely duplicate the check, it would eventually disagree with the first, and the disagreement would be silent in the direction that fails open. One tool would refuse a path another accepted, and nothing in either result would say the two had different ideas of the boundary.

The check is not “does the string contain ..”. A symlink inside the root pointing outward is an escape containing no .. at all, and a path that does not exist yet cannot be canonicalised at all — which Write needs, since it has to name a file it is about to create. So resolution is three moves: normalise lexically, canonicalise the longest part that actually exists, re-attach the part that does not. Searching for the canonicalisable prefix from the deepest cut downwards is what makes a symlinked parent visible.

tools/fs/src/path.rs — resolve, canonical_prefix

Two details that would fail open if they were got wrong. The root is canonicalised once per call, so on Windows the comparison is against the \\?\ verbatim spelling the OS uses — comparing a verbatim path to a non-verbatim one silently never matches. And containment uses Path::starts_with, which is component-wise: /work and /workspace do not match, where a string prefix test would have said they did.

What containment cannot catch

A hard link inside the root to a file outside it is not detectable this way: there is no “real” path to canonicalise towards, both names are equally the file, and canonicalize returns the inside one. Verified rather than assumed — on Windows mklink /H needs no privilege at all. The same is true of a bind mount. This is a boundary against paths, not against an operator who has already placed a link inside the tree.

Bash is a wider hole than either, and is documented as one rather than papered over. Its cwd argument is contained; the shell it starts is not.

tools/fs/src/path.rs — module doc

tested tools/fs/tests/containment.rs attempts each escape rather than assuming it fails: .. leading and buried mid-path, an absolute path elsewhere on the machine, a symlinked file and a symlinked directory read through, a file created through a symlinked directory, and Glob/Grep walking out through a link. It also carries the positive control — an absolute path inside the root still works — because the cheapest wrong way to pass every escape test is to reject all absolute paths.

tools/fs/src/read.rs — render

A clipped line gets #---- in place of a hash, because the model has seen its front and not its end and the label must never stand for text it was not shown. Edit refuses that marker by name.

A partial read is recorded as partial. A truncated read, or any read with offset > 1, leaves a sighting marked incomplete. That is what later refuses a whole-file Write while still permitting an anchored Edit.

Write

file_path and content, both required, and nothing else. There is no force and no create_only: the refusal below is the tool's reason to exist, and a flag that turns it off is a flag a model under pressure will find.

The destructive move that looks like progress is a whole-file write from an assumption. An agent asked to “add a function to utils.rs” can satisfy that by writing a file containing exactly that function; the tool returns Ok, the file exists, the function is in it, and everything that used to be there is gone with nothing in the transcript saying so. So a whole-file write requires a whole-file read, in this session, and there are three ways that read can fail to license it:

StateRefusal
Never {path} exists and has not been read in this session; Read it first so the overwrite is not blind
Partial {path} was only read in part; Read it in full before replacing it, or use Edit to change the part you saw
Stale {path} changed on disk after you read it; Read it again before overwriting so the change is not discarded

All three are BadArguments, because all three are entirely actionable. Creating a file that does not exist needs no prior read — there is nothing to lose. Nothing before the refusal touches the filesystem, not even create_dir_all, which is what makes a refusal actually a refusal.

tools/fs/src/write.rs — Write::run

Staleness is length and mtime, keyed by session so a resumed process cannot inherit an earlier session's claim to have looked at a file. Write declares idempotent: true: the same bytes twice leave the same file, and the mtime moves, which nothing here consults.

Edit, and its two ways of saying where

ArgumentTypeMeaning
file_path requiredstring
new_string requiredstringThe replacement. With lines, empty deletes.

An ambiguous anchor is a refusal, never a guess. Every way of choosing among three matches is wrong in a way that is hard to see afterwards: the first edits code the model was not looking at, the last is the same bug with different luck, all three is a refactor nobody asked for — and all three return Ok, with the damage surfacing later as a test failure in a file the transcript never mentions. So a match count other than one is BadArguments naming the count, which is what makes it actionable: zero matches and four matches are different problems and get different messages.

The two forms are mutually exclusive and a call supplying both or neither is refused rather than resolved by precedence — precedence means silently ignoring one of two things the model asked for. Why one tool and not two: a second tool would cost its whole description in every request forever, hand the model a choice it has no basis for making, and break the six-Claude-Code-names compatibility promise. Why not replace old_string: every model already knows how to drive it, while the addressed form can only be driven by a model that has seen a Read from this harness in this conversation.

tools/fs/src/edit.rs — module doc

Three checks stand between an address and the disk

  1. The endpoints still say what the model says they say. Catches a model aiming with a line number it worked out four turns ago. This is the only check the model's own quoted hash can make — the tracker knows what the world last looked like, and has no idea what the model thinks it looks like.
  2. Every line in the range is text this harness has shown. The model sends two hashes; this is the other ninety-eight, matched against the tracker's record. It closes the known failure of per-line hashing, which is that a range can drift in the middle while both its ends look untouched.
  3. No line in the range is longer than Read will show. Replacing a line whose end nobody has seen discards text nobody read.

Check 2 matches the run wherever it appears in the record rather than at the same line numbers. It is the difference between asking “did this text change” and “did this text move”, and only the first is this check's business. Comparing in place looks equivalent until something inserts a line above, at which point every number below shifts and a range nobody touched is refused — including the corrected retry that the relocation refusal explicitly tells the model to make. That contradiction was found by watching a real model take the advice and be refused for following it, not by review.

tools/fs/src/session.rs — ReadTracker::contains_run

Because the checks are per-line, lines accepts a Stale file where old_string still refuses one. That is a sharper rule rather than a weaker one: a literal anchor on a drifted file can match text that moved somewhere it does not belong, and nothing about the match would reveal it.

A successful addressed edit hands back the replacement lines with their new numbers and new hashes (up to ECHO_LIMIT = 20, beyond which it says to re-read for the labels), plus a sentence saying how far everything below moved. Every edit shifts the numbering underneath it, and a model working from pre-edit numbers aims its next one wrong.

The refusal that was rewritten after watching a model read it

The first draft of the moved-line refusal opened with “Edit.lines addressed 5#73b2, but line 5 now reads …” and closed by offering a re-read as a coequal option. Sonnet 4.5 replied “I see — I made an error. Let me re-read the file” and spent the whole Read the hint existed to save. Two faults, both in the prose: it did not say the file changed (which reads as you counted wrong, and the fix for counting wrong is to look again), and it offered the re-read as an equal option (a model choosing between “retry” and “read again” under uncertainty reads again, every time).

The reword worked as far as it can. What it did not do is stop the re-read — in both observed runs the model read the file again anyway before retrying. So the claim made here is the smaller one: the corrected address the refusal offers is one this tool accepts. No token saving is claimed from it.

tools/fs/src/edit.rs — moved

What the addressing actually costs, measured

The labels are a real cost paid on every Read to make some edits cheaper, and the measurement is closer than the idea's reputation suggests. Counted with Anthropic's count_tokens endpoint on 2026-08-11:

MeasuredResult
Addressed edit vs old_string, 14 real single-line edits from this repository 26% fewer output tokens — 842 against 1140, because the anchor stops having to be long enough to be unique
Labelling, over 2000 lines of this repository's Rust +3.6 tokens a line, +23% on every read. Irreducible: base36 at the same width is worse (3.97), dropping the # saves 0.5, three hex characters saves 0.7 at four times the collision exposure
Break-even, at list prices ≈14 edits per read uncached; ≈1.5 once the read is cached, which it normally is within a turn

So on tokens alone it is close to a wash, and the case does not rest on it. It rests on the call that no longer happens: an old_string edit against a drifted file was refused outright and cost a full re-read plus a re-emitted edit every time, and that is the common case on a machine where somebody has the file open in an editor.

The 61% figure is not this change's number

The widely-quoted −61% is the format author's own benchmark of their own scheme — 180 tasks × 3 runs over ~16 models — and −61% is Grok 4 Fast, the best case, not a median; the README does not say which of two baselines it is against. Better than a bare marketing line, still vendor-run and independently unverified. It does not describe Emma's implementation, which is a different scheme: the source project tags each file with one hash and addresses lines by bare number, and normalises trailing whitespace away before hashing, so a formatter stripping trailing spaces is invisible to its staleness check. Emma hashes per line, including trailing whitespace, and catches that.

notes/improvements.md item 2; tools/fs/src/read.rs and hashline.rs — module docs

The hash is FNV-1a: four hex characters rendered, 64 bits stored. Non-cryptographic — what is being defended against is accident, and an attacker who can rewrite the file being edited already has everything a collision would buy. The exposure is one comparison at 1 in 65,536, and the endpoints are checked twice over: at 16 bits by the model's claim and at 64 bits by the tracker's record.

tools/fs/src/hashline.rs — module doc

tested tools/fs/tests/addressed.rs carries the positive control (without it, the safe way to pass every refusal test is to refuse every addressed edit), a second edit made from the first edit's output with no Read between them, and a CRLF fixture — rebuilding from str::lines would convert every CRLF file to LF on the first one-line edit and add a newline to a file that never had one, both whole-file rewrites disguised as one-line changes.

Glob

pattern (required) matched against paths relative to the search root, and an optional path directory. Matching nothing succeeds with an empty list: “there are no .proto files here” is a fact about the repository and often the exact fact being checked. Results come back newest first with the path as tiebreak, so two calls over an unchanged tree return identical bytes — the output rides in the conversation and the conversation rides in the cached prefix.

The walk does not follow symlinks, and not for cycle safety. A directory symlink pointing outside the root would let a glob enumerate — and then a read reach — anything on the machine without a single .. in the pattern. Containment guards the arguments; refusing to follow links guards the traversal.

MAX_RESULTS is 1000 and no argument reaches it. The call that surfaced this returned 1000 of 64,097 paths in this repository, and 63,097 of them were build output under target/. A max_results knob would have turned a useless answer into a sixty-times larger useless answer and still not said the thing the model needed to know, which is that the pattern was too broad. The fix for this cap is the sentence it prints.

The two skips are not the same admission and only one is reported. The first live run of the naïve version reported 499 files not opened, every one an .rlib or .pdb under target/ — true, worthless, and how a warning stops being read. So the size cap sniffs a prefix for a NUL byte and valid UTF-8 before deciding which of the two it is looking at.

tools/fs/src/grep.rs — readable_text, looks_like_text
Known rough edge, flagged in the source

The glob filter matches against the path relative to the search base. When path names a single file, that relative path is empty, so passing path and glob together for one file matches nothing. Naming one file and then filtering the set of one is a redundant call, which is why it has not bitten — but it is a real asymmetry rather than a rule.

A shell, not an argv array. The argv alternative is genuinely safer — no quoting, no word splitting, no dependence on what sh happens to be — and unusable for what this tool is for, since almost every command a coding agent needs is a shell construct. The failure mode of argv exec is that the model emits sh -c "…" as the argv anyway: a shell with the safety story removed and nobody's caps applied. The injection argument also does not survive the threat model — there is no untrusted string being interpolated, the model composes the whole command, and a model that wants to delete something can do it through argv just as easily.

The child's environment is cleared and rebuilt from a 16-name allowlist rather than filtered, so an API key exported by whatever launched Emma cannot appear in it by default. EMMA_SHELL is absent from that list: it selects Emma's shell and has no business being visible to the commands that shell runs.

tools/fs/src/bash.rs — ENV_ALLOWLIST

Which shell, and why WSL is refused

The search used to be “the first bash on PATH”. On a stock Windows box that is C:\Windows\System32\bash.exe, the WSL launcher — and a real run showed pwd coming back /mnt/e/Projects/emma for a directory Emma had contained as C:\src\emma, with .wslconfig warnings mixed into the tool output. The two agreed only because WSL happened to translate the directory. Measured on the same box, when it cannot translate — a subst drive, a UNC path — WSL starts in the user's home directory instead, prints nothing, and exits 0. That is a command running outside the approved root, reported as success, and it is a hole rather than something the model can route around, because nothing in the result says it happened.

  1. EMMA_SHELL, if set to anything but whitespace. If what it names is not there the call is Unavailable and says where it looked. It never falls back — a tool that runs a different shell than the one you asked for is worse than one that stops.
  2. /bin/sh, on unix.
  3. A native POSIX bash then sh: the Git for Windows locations first, then PATH, skipping the WSL launcher wherever it appears.
  4. Nothing. PowerShell, WSL and cmd.exe are never chosen automatically. The model writes POSIX on the strength of being told it has a shell, and Windows PowerShell 5.1 has no && at all; auto-selecting it would turn every such command into a wrong answer shaped like the command's own output.

The model is told which shell it got in the result, not in the description. The description is hashed into tool_schema_hash, which is how anyone tells which tool surface produced a given answer, and a description naming the local shell would make that hash a property of the machine. So every result opens with shell: posix — /bin/sh. tested nothing_machine_specific_reaches_the_hashed_surface asserts the hashed surface contains none of /bin/sh, bash.exe, Program Files, System32, wsl, sh -c or EMMA_SHELL, and the positive half — that it does say where the answer is.

tools/fs/src/bash.rs — Shell::banner, resolve_with

Exit status is not failure

Could-not-spawn, timed-out and killed are Failed. Anything that started and finished is Ok, carrying exit status <n> under the shell banner.

This contract was stated three ways for a while, and the copy that was wrong is the one the model reads. The description went on calling a non-zero exit a failure long after the code stopped treating it as one, because changing it moves the registry's schema hash, which kept the edit looking too consequential to make in passing. That deferral cost more than the edit: it taught the model to avoid Bash for the commands it should use it for, and to append || true, which discards the status the tool now reports correctly. All three have agreed since 2026-08-10.

tools/fs/src/bash.rs — module doc

Two sharp edges, both known

The grandchild-holds-the-pipe race

Both streams are drained concurrently with the wait, and drained past the 64 KiB cap rather than stopping — a reader that stops fills the pipe buffer and the child blocks forever on a write nobody consumes, so the timeout becomes the only exit and every noisy command takes the full two minutes. After the wait, the drains are given 5 seconds and no more, because a background grandchild holding the pipe open outlives the kill and waiting on it would turn a timeout into a hang.

Losing that race discards whatever had already been drained and reports both streams as cut. That loses output, which is the lesser harm against a Bash call that never returns. The two cuts call for opposite moves and get different sentences: the cap means the body is a prefix of what was said, while a lost race means the whole output is missing and the body is assembled from nothing — telling the model “cut at 65536 bytes” there would name a limit that never fired and invite it to trust an empty body as short output.

unverified Only the cap is tested. The lost-race branch “needs a grandchild holding the pipe open, which no fixture can arrange reliably” — the truncation suite says so in its own comment. Settled by spawning something like (sleep 30 &) ; echo done under a short timeout on both platforms and checking which of the two sentences comes back.

The task list: TaskCreate TaskGet TaskList TaskUpdate

The file is the product and the tools are the accessor. .emma/tasks/tasks.md is not a serialisation format that happens to be text; it is a document somebody has open in an editor while the agent works. Every constraint in the parser follows from that: a line nobody changed is written back byte for byte, nothing is ever reordered, and completing a task ticks a box where it sits. The moment a person's edit disappears they stop trusting the file, then stop reading it, and a task list nobody reads is theatre with a write amplification problem.

tools/tasks/src/lib.rs — module doc
ToolArgumentsmeta
TaskCreate tasks — array, minItems: 1; each item a string, or an object with text and optional status of pending/in_progress/completed write, not idempotent
TaskGet id — the handle, leading # optional read-only
TaskList status — open (default), all, pending, in_progress, completed read-only
TaskUpdate id required, plus status and/or text write, idempotent

TaskUpdate declaring idempotent: true where Edit declares false is the distinction working: setting a status to what it already is leaves the same file, and there is no anchor to consume, so a replay is safe. TaskCreate is not idempotent because two genuinely identical steps in a plan are a thing that happens and nothing here deduplicates by text.

Nothing is truncated anywhere in this crate. No cap, no constant, no truncated flag ever set. The one hard numeric limit is not a cut but an exhaustion: handles are 16 bits, so a file can in principle hold 65,536 tasks and then panic with all 65536 task handles in this file are in use. Its doc corrects an earlier claim that the space could not be exhausted — “nobody would” is not the same as “cannot”.

tools/tasks/src/doc.rs — first_free_id

An id that is not in the file is BadArguments, never an empty result: returning nothing would teach the model that the task it just created has vanished, and its next move would be to create it again. A missing file, no tasks, and no tasks matching a filter are all Ok.

Two writers, no lock

You cannot lock a file a person is editing in VS Code. So every call reads, changes and writes inside one invoke, guarded by a hash of the whole file — not mtime, which has second granularity on some filesystems, and a stamp that can silently fail to change is a stale-read guard that fails open. The write goes to tasks.md.tmp beside the file, never in the system temp directory, because a rename across filesystems is a copy and a copy is not atomic. A collision retries three times, then Failed: three collisions in a row is a file being rewritten in a loop.

tools/tasks/src/store.rs — edit, write_atomically, hash
What the guard cannot catch, in its own words

An editor holds the whole file in memory. If a person opened tasks.md at 10:00, Emma writes at 10:01, and the person hits Ctrl-S at 10:02, their editor writes its entire buffer and Emma's line is gone — no error, no conflict. The guard's own window is not zero either: a write landing between the confirming read and the rename is lost. It is microseconds wide, and it is not closed, only made small and admitted.

tested tests/round_trip.rs holds hand-written fixtures — untidy bullets, trailing prose, notes, hand-ticked boxes, a CRLF file — and asserts each survives an update. tests/tools.rs asserts an exact file rather than a contains, because every rejected alternative design passes a contains check and fails an equality one.

TaskCreate and TaskUpdate declare read_only: false and are then named in the approval gate's EXEMPT list. The dodge belongs there rather than in a false declaration, and the gate's own comment says the list is owed a fix — an axis on ToolMeta for the scope of a write. See Consent.

The web: WebSearch WebFetch and five browser tools

Neither is registered unless it can work. web_tools() resolves Chrome and the Brave key first and returns only what is usable, plus a line per omission that main.rs prints. The predecessor shipped a web_search that registered with no key and failed on every call; a turn that touched it died, and the model had no way to learn the tool was decoration.

tools/web/src/lib.rs — web_tools

WebSearch

query (required) and count (default 10, capped 20 — Brave's own per-request ceiling, so asking for more would be silently clamped by the API and make the count in the result disagree with the request). read_only: true, reaches_network: true. The key travels in an X-Subscription-Token header, never in the query string, and never appears in an error message.

It returns places to look, not an answer, and the content says so above the results: the snippets are the search engine's summaries, and a model that answers from them is quoting a summary of a page it never opened. Zero results is Ok. Status handling is split by what the model can do about it — 401/403 is Unavailable (check the key), 422 is BadArguments (Brave refused the query), 429 is Failed and says the condition is temporary.

The five browser tools

A stateless fetch launches Chrome, reads, and throws it away. BrowserOpen keeps the browser and hands back a session id, which is a different capability: inside a session the model acts as the user, on a page that may hold their login.

BrowserOpen declares read_only: false for a reason: it leaves a live browser running with an unauthenticated CDP port on localhost, and while that exists any local process can puppet it. BrowserClose declares read_only: true, and that departs from the letter of the field, which says “no process spawned”. This ends one. The alternative is a prompt on cleanup, whose failure mode is that somebody answers n and a browser survives with a live remote-control port. This crate has already leaked a Chrome once; gating the thing that prevents it is how it happens again.

tools/web/src/browser/tools.rs — BrowserClose::meta

BrowserAct never returns page content — its result is a snapshot line and an instruction to call BrowserRead to see what changed, and a test asserts the content is under 400 characters. A negative answer is Ok rather than an error: Condition NOT met within {n} ms — the page never reached that state; this is the answer, not a failure to look. BrowserFill re-reads each field from the live page afterwards, so what it reports is what is actually there rather than what was sent.

Nothing here can submit a form, and that is two decisions rather than an omission. The upstream library's submit requires a second key in a config file resolved against the process's working directory — which, inside Emma, is the user's repository, and Bash can write it. A second key both parties can turn is one key. Separately, “the payload was shown” cannot be guaranteed from inside a tool: the prompt is rendered by the approval gate, and an allow rule or an a answer skips it. A tool cannot force its own gate. tested A recursive schema walk asserts no registered tool offers a submit argument, and BrowserFill passes file: None always — the library's file-attach is a different capability entirely, since it sends a file off this machine.

All four are read_only: true, reaches_network: false, idempotent: true, and prompt nobody. Three take the same position schema — file_path, line (1-based), symbol, and occurrence when the name appears more than once on the line. tools/lsp/src/tools.rs — position_schema; tools/lsp/src/doc.rs — locate

Rust only. rust-analyzer is the one server wired, and a non-Rust file is Unavailable with a refusal that names the alternative and its limits: use Grep for a text search, knowing that it is a text search: it cannot tell a definition from a mention, and it will match the same name in an unrelated crate. tools/lsp/src/server.rs — unsupported_language, nothing_found

Containment comes first, before the file is read and before a process is started: a path outside the root must not so much as cause a spawn. Results are contained on the way out too — a language server will happily answer about …\.cargo\registry\…, and hits outside the root are counted and named rather than shown. That outbound check canonicalises first, and the source is explicit that this “is not belt and braces — it is the check working at all”, because the root is \\?\E:\… on Windows while a URI round trip yields E:\…, and the mismatch would report every in-project hit as outside.

tools/lsp/src/render.rs — locations; tools/lsp/Cargo.toml

Readiness, and the 0.36-second lie

The obvious readiness mechanism is to count open work-done progress tokens and call the server ready when the count returns to zero. Traced against rust-analyzer 0.3.3008 on a two-file crate, that count reaches zero three times before the index exists. The first version of this crate declared ready at 0.36s, asked, and got [] — the confidently-wrong empty result the crate exists to prevent, produced by the machinery built to prevent it. It was caught by tests/real_server.rs and by nothing else: every fake passes, because a fake emits the tokens its author expected.

tools/lsp/src/client.rs — module doc

What replaced it: the authoritative experimental/serverStatus notification with quiescent: true, requested in initialize. The token-counting heuristic survives as a fallback with a 1.5-second settle window — roughly five times the largest observed gap between phases — and is switched off entirely once the authoritative signal has been seen once.

An unready request still runs and still returns Ok, with the readiness attached, because the loop will not repeat a call that already failed with nothing changed since — an error would forbid the one correct response. The distinction lands in the sentence a result carries when it is empty: 

ready:     No references found. The index was complete when this was
           asked, so this is an answer: there are none.

not ready: No references came back, and the index was not complete — so
           this is not an answer, it is a question that could not be
           answered yet. Do not conclude that none exist; ask again once
           indexing has finished.
