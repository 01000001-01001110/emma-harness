tools/fs/src/bash.rs — Bash::meta

Shell or argv

The argv alternative is genuinely safer: no quoting, no word splitting, no injection surface, no dependence on what sh happens to be. It is also unusable for what this tool is for, because almost every command a coding agent needs is a shell construct: cargo test 2>&1 | tail -40, grep -c . file || true, mkdir -p a && cd a.

The failure mode of argv exec is that the model emits sh -c "…" as the argv anyway, which is a shell with the safety story removed and nobody's caps applied. The injection argument also does not survive the threat model: there is no untrusted string being interpolated, the model composes the whole command, and a model that wants to delete something can do it through argv just as easily.

tools/fs/src/bash.rs — ENV_ALLOWLIST

Sixteen names, and the notable absence is EMMA_SHELL. It selects Emma's shell and has no business being visible to the commands that shell runs. The child also gets stdin from Stdio::null() and kill_on_drop(true), without which a timed-out command keeps running after Emma has given up on it and the next call sees a machine still busy with work nobody is waiting for.

The rebuild has a cost worth stating: a command that depends on an environment variable the user set will not see it, and nothing in the result says so. Sixteen names is the whole of what a POSIX command line can rely on here.

Which shell, and why WSL is refused

The search used to be "the first bash on PATH". On a stock Windows box that is C:\Windows\System32\bash.exe, the WSL launcher.

What that produced, measured

observed A real run showed pwd coming back /mnt/e/Projects/emma for a directory Emma had resolved and contained as C:\src\emma, with .wslconfig warnings mixed into the tool output. The two agreed only because WSL happened to translate the directory. Measured on the same box, when it cannot translate, on a subst drive or a UNC path, WSL starts in the user's home directory instead, prints nothing, and exits 0. That is a command running outside the approved root, reported as success, and it is a hole rather than something the model can route around, because nothing in the result says it happened. Seen by the author of bash.rs; no transcript was kept.

  1. EMMA_SHELL, if set to anything but whitespace: an absolute path, or one of sh, bash, pwsh, powershell. If what it names is not there the call is Unavailable and says where it looked. It never falls back. A tool that runs a different shell than the one you asked for is worse than one that stops, because the command still produces output and the output is wrong in a way that reads as the command's own answer.
  2. /bin/sh, on unix.
  3. A native POSIX bash then sh: the Git for Windows locations first, then PATH, skipping the WSL launcher wherever it appears.
  4. Nothing. PowerShell, WSL and cmd.exe are never chosen automatically. The model writes POSIX on the strength of being told it has a shell, and Windows PowerShell 5.1 has no && at all. Auto-selecting it would turn every such command into a wrong answer shaped like the command's own output.

Git for Windows is searched before PATH, and the WSL launcher is skipped rather than merely ranked below it, because on a box without Git the ranking alone still ends at WSL. Five directories are tried, built from ProgramFiles, ProgramW6432, ProgramFiles(x86), LOCALAPPDATA and ProgramFiles again for Git\usr\bin.

The WSL test additionally asserts the refusal explains itself, requiring the words "containment" or "namespace" in the message.

tools/fs/src/bash.rs — Shell::args

The model is told which shell it got, in the result

The description is hashed into tool_schema_hash, which is how anyone tells which tool surface produced a given answer. A description naming the local shell would make that hash a property of the machine. So every result opens with shell: posix — /bin/sh, on every call rather than once per session, because there is no session state here to hang "once" on and a compacted conversation would lose the one mention.

tested nothing_machine_specific_reaches_the_hashed_surface asserts the hashed surface contains none of /bin/sh, bash.exe, Program Files, System32, WSL, wsl, sh -c or EMMA_SHELL, and the positive half: that it does say the answer is on the first line of the result.

tools/fs/src/bash.rs — Shell::banner, mod shell_tests
Suspected defect: classify is not platform-gated

classify calls any shell whose parent directory's last component is system32, syswow64, sysnative or windowsapps the WSL launcher, on every platform. Unlike every other decision in that module it does not take the injected windows flag. On unix, a checkout containing a directory of any of those names yields a refusal that talks about WSL.

Its unit test asserts the behaviour unconditionally, so it can never go red. the_wsl_launcher_is_recognised_wherever_windows_keeps_it passes on Linux and on Windows alike, for the same reason the defect exists: classify gives the same answer on both. Flagged here rather than fixed. 

fn classify(path: &Path) -> ShellKind {
    let stem = path
        .file_stem()
        .map(|s| s.to_string_lossy().to_lowercase())
        .unwrap_or_default();
    if stem == "pwsh" || stem == "powershell" {
        return ShellKind::PowerShell;
    }
    if stem == "wsl" {
        return ShellKind::Wsl;
    }
    let parent = path
        .parent()
        .map(|p| p.to_string_lossy().to_lowercase())
        .unwrap_or_default();
    let in_system_dir = parent
        .rsplit(['\\', '/'])
        .next()
        .is_some_and(|leaf| WSL_DIRS.contains(&leaf));
    if in_system_dir {
        return ShellKind::Wsl;
    }
    ShellKind::Posix
}

The classification is by name rather than by probing, because this runs before anything is spawned and a decision that required executing the candidate to find out what it was would already have run it. The LSP crate diverges here and probes with --version, for a reason it states.

Exit status is not failure

        // A command that ran and exited non-zero is **not** a tool failure.
        //
        // The contract's rule — an error is a fact about the call, never about
        // what the world contains — was written about the filesystem, and it
        // did not survive first contact with exit-status-as-answer. `grep -q`
        // answering "no" exits 1. `test -f` answering "it is not there" exits
        // 1. `cargo test` answering "three of these fail" exits 101. Every one
        // of those is the world answering the question that was asked, and
        // reporting them as `Failed` tells the model its shell is broken and
        // invites it to route around a problem it does not have.

Could-not-spawn, timed-out and killed are Failed. Anything that started and finished is Ok, with exit status <n> stated first, above the output, because a model that skims sees the outcome before the output and a non-zero exit changes how the output should be read. A command killed by a signal reports exit status a signal, since ExitStatus::code is None there.

The copy that was wrong is the one the model reads

This contract was stated three ways for a while: in the module doc, in run, and in descriptions/bash.md. The description went on calling a non-zero exit a failure long after the code stopped treating it as one, because changing it moves the registry's schema hash, which kept the edit looking too consequential to make in passing. That deferral cost more than the edit: it taught the model to avoid Bash for the commands it should use it for, and to append || true, which discards the status the tool now reports correctly. All three have agreed since 2026-08-10.

The description moved once more the same day, for the same class of reason. It promised sh -c, which is false under PowerShell and false about && in particular.

Two streams, drained past the cap

/// consuming and discarding rather than returning. Stopping would leave the

/// Keeping the *head* rather than the tail is the deliberate half of that — the
/// first error is usually the real one, and the rest is cascade.

stderr is labelled rather than interleaved, under a --- stderr --- divider. Interleaving is what a terminal shows and it is not reconstructible here, because the two pipes arrive independently, so a merged view would invent an ordering that did not happen. Both streams empty renders as (no output) rather than an empty string, so a command that printed nothing and a call that lost its output do not read the same.

tools/fs/src/bash.rs — drain, render
The grandchild-holds-the-pipe race

After the wait, the drains are given 5 seconds and no more, because a background grandchild holding the pipe open outlives the kill and waiting on it would turn a timeout into a hang. Losing that race discards whatever had already been drained and reports both streams as cut. That loses output, which is the lesser harm against a Bash call that never returns.

The two cuts call for opposite moves and get different sentences. The cap means the body is a prefix of what was said. A lost race means the whole output is missing and the body is assembled from nothing, so the notice says Nothing here is the command's output and no argument changes that — re-run it redirecting output to a file, then Read or Grep the file. Telling the model "cut at 65536 bytes" there would name a limit that never fired and invite it to trust an empty body as short output.

unverified Only the cap is tested. The lost-race branch needs a grandchild holding the pipe open, which the truncation suite says in its own comment no fixture can arrange reliably. Settled by spawning something like (sleep 30 &) ; echo done under a short timeout on both platforms and checking which of the two sentences comes back.

tools/fs/src/bash.rs — Bash::run; tools/fs/tests/truncation.rs

The containment story, stated rather than implied

cwd is where the command starts, not a wall it is held behind. cd .. leaves. The cwd argument is contained and must resolve inside the root, which is a guard on the argument only. That is in the tool's description rather than papered over, because a boundary the operator believes in and that does not hold is worse than no boundary.

What actually protects anything here is the approval gate reading read_only: false and showing the command itself. See Consent & permissions.

What is not verified here

unverified The WSL measurement above, including the subst-drive and UNC-path behaviour, is one author's run on one Windows box with no transcript kept. Settled by repeating it with a subst drive and pasting the tool output.

unverified The claim that a rebuilt environment never surprises a real command is not made here, and nothing measures how often a command needs a seventeenth variable. Settled by logging, across a week of real sessions, every Bash failure whose message mentions an environment variable.

certified tools/fs/tests/edges.rs (38 tests) and tests/shell_override.rs (1) passed at commit a3eba74 on this box, and the edges suite takes 30 seconds because several of its cases spawn real shells.
