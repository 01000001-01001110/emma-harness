What it returns, and what it refuses to decide

// crates/emma/src/session.rs
/// The messages a session's last model call carried, in order.
///
/// Not "the conversation so far, tidied": every value here was written by the
/// loop at the moment it appended the same value to `query`, so what comes back
/// is the list itself rather than a reconstruction of it. That distinction is
/// the whole point — see the module doc on thinking-block signatures.
///
/// What it is *not*: the list a resumed run should send. That one has a new
/// user turn on the end and possibly a re-stated goal, and deciding its shape
/// is the `--resume` command's job, not this function's.
pub fn fold(path: &Path) -> Result<Vec<Message>> {
    Ok(fold_records(&SessionLog::read(path)?))
}

/// [`fold`] over records already read — the testable half, and the one a caller
/// that has the records for another reason should use.
pub fn fold_records(records: &[Value]) -> Vec<Message> {
    let mut fold = Fold::default();
    for record in records {
        fold.record(record);
    }
    fold.finish()
}

Every value in the output was written by the loop at the moment it appended the same value to query, so the fold is a replay rather than a reconstruction.

Here is why that matters. This model family signs its thinking blocks, and a block reassembled from its text is rejected on the next call. So the assistant record stores the provider's own content array, and the fold hands it back untouched.

The state a walk needs

// crates/emma/src/session.rs
/// The state a walk over the records needs.
///
/// Two lists because the loop keeps two: `history` is the conversation up to
/// the last finished goal — the part a request sends as `Request::history` —
/// and `query` is the goal in progress. A fold that merged them would return
/// the right conversation in the wrong shape and could not apply a compaction
/// record, which counts messages in the first list only.
///
/// **Nothing here collapses a finished goal.** It used to: the loop kept two
/// lines of prose per goal and the fold kept its own copy of that rule, which
/// was two implementations of one decision and a `--resume` that reconstructed
/// a different conversation the moment either moved. A finished goal now stays
/// in the conversation in full, and the *only* thing that shortens it is
/// compaction — which writes what it replaced the messages with into the
/// record, so this reads it rather than re-deriving it.
#[derive(Default)]
struct Fold {
    /// Records this fold refused to act on because they were damaged.
    damage: Vec<String>,
    history: Vec<Message>,
    query: Vec<Message>,
    in_goal: bool,
    /// The ending of the goal that has just finished, from `goal_finished`.
    /// Applied when the *next* goal opens — see [`Fold::close_goal`].
    finished: Option<String>,
    /// An assistant turn that has been read but not yet placed, because what
    /// follows it decides whether it can be placed at all.
    pending: Option<Vec<ContentBlock>>,
    /// Result blocks for `pending`, accumulating until something closes them.
    results: Vec<ToolResult>,
}

The removed collapse is documented here because it is the obvious alternative. A finished goal used to become two lines of prose the instant it finished, in the loop, and the fold carried its own copy of that rule so a resume would produce the same shape. Two implementations of one decision, and when either moved, --resume rebuilt a conversation that was never sent with nothing but a round-trip test to say so.

The two-line collapse survives only as what compaction makes, later, and only when the size forces it.

damage is the field a previous quote of this struct left out. A malformed compacted record still prints to stderr and refuses to act, which is the intended refusal; without the field, nothing downstream could tell it had happened, so a test guarding it asserted only that the fold did not panic. The sentences collect here so a resumed run can say the conversation it rebuilt is known not to match the one that was sent.

The arms, in the order you hit them

// crates/emma/src/session.rs — Fold::record
match r["kind"].as_str().unwrap_or_default() {
    "goal" => {
        self.close_turn();
        // A goal record while another goal is open means the previous
        // one ended — closed here rather than at `goal_finished`
        // because the loop does the same: after a `goal_finished` the
        // loop still holds the finished goal's `query` and would send
        // it again unchanged if nothing else happened, so closing early
        // would make the fold disagree with the last call of a one-goal
        // session.
        self.close_goal();
        self.in_goal = true;
        self.query = vec![Message::user(string(r, "opening"))];
    }
    "assistant" => {
        self.close_turn();
        // Absent only in logs written before `raw_content` was stored.
        // The turn is dropped rather than rebuilt from `text`: a
        // rebuilt thinking block is rejected, so an approximation here
        // would be a resumed run that dies on its first call with an
        // error naming a signature nobody in the file mentions.
        self.pending = r.get("raw_content").and_then(blocks_of);
    }

The timing of close_goal is the subtle one. A goal_finished record does not close the goal; the next goal record does. That matches the loop: after a goal ends the loop still holds that goal's query and would send it again unchanged if nothing else happened. A fold that closed early would disagree with the last call of a one-goal session, which is the commonest session there is.

self.query = vec![…] assigns rather than extends, so anything left in query that close_goal did not move is discarded. With in_goal false, close_goal returns early and that discard is real: records before the first goal in a file do not survive. 

// crates/emma/src/session.rs — Fold::record, continued
    "tool_result" => {
        // Anything that is not a `tool_result` block is not pushed, and
        // the turn it was meant to answer is therefore dropped by
        // `answered` rather than half-restored. A record this cannot
        // read is a gap, and a gap is the one thing the API will not
        // take: an unanswered `tool_use` is a 400.
        if let Some(ContentBlock::ToolResult(result)) =
            r.get("block").cloned().map(ContentBlock::from_value)
        {
            self.results.push(result);
        }
    }
    "kick" => {
        // A kick answers a turn that made no tool calls, so there is
        // nothing to pair. If the turn itself could not be placed the
        // kick goes with it — a user message with no assistant turn
        // before it would leave two user turns in a row.
        if let Some(content) = self.pending.take() {
            self.query.push(Message::assistant(content));
            self.query.push(Message::user(string(r, "text")));
        }
        self.results.clear();
    }

The kick arm pushes the held turn itself rather than calling close_turn, so it bypasses the answered check. It can afford to: a kick is only ever written for a turn that made no tool calls, so content has no tool_use to leave unanswered. The results.clear() afterwards is the guard on that assumption. If results had somehow accumulated, they are dropped rather than left to attach themselves to the next turn.

// crates/emma/src/session.rs — Fold::record, continued
    // Replayed rather than re-decided. The record carries both halves —
    // how many messages off the front were replaced, and exactly what
    // replaced them — so a fold cannot summarise differently from the
    // run that did it. Compaction only ever touches finished goals, so
    // the count is an index into `history` and never into `query`.
    "compacted" => {
        // **A damaged compaction record must not read as a no-op.**
        // `drop_messages` missing defaulted to 0 and `messages` missing
        // defaulted to empty, so a truncated or malformed record left
        // the conversation uncompacted — and the fold then rebuilt
        // something *different from what was sent*, which is the one
        // thing this fold exists to prevent. Silent, and visible only as
        // a resumed session that behaves unlike the one it continues.
        let drop = match r["drop_messages"].as_u64() {
            Some(d) => d as usize,
            None => {
                eprintln!(
                    "emma: a `compacted` record is missing `drop_messages`, so the conversation it describes cannot be rebuilt; this resumed conversation will not match the one that was sent."
                );
                return;
            }
        };
        let replacement: Vec<Message> = match serde_json::from_value(r["messages"].clone())
        {
            Ok(m) => m,
            Err(e) => {
                eprintln!(
                        "emma: a `compacted` record has unreadable replacement messages ({e}), so the conversation it describes cannot be rebuilt; this resumed conversation will not match the one that was sent."
                    );
                return;
            }
        };
        let drop = drop.min(self.history.len());
        self.history.splice(..drop, replacement);
    }
This arm used to turn a bad record into deletion

The warn box that stood here carried a certified chip on a different arm: two statements, an unwrap_or(0) on the count and an unwrap_or_default() on the messages, with no path that abandoned the splice. A messages field that would not deserialise yielded an empty vector and the splice still removed drop_messages messages off the front, so a malformed record deleted conversation rather than being ignored, which no other arm did. Both defaults are gone. A missing count and an unreadable replacement now each refuse the whole arm, say so on stderr, and leave the conversation alone. The refusal still names the consequence: the rebuilt conversation will not match the one that was sent. tested a_compaction_record_missing_its_fields_does_not_silently_rebuild_a_different_conversation in tests/resume.rs folds a file whose compacted record has no fields, though what it asserts is only that the restore neither fails nor panics; the stderr line and the untouched history are established by reading the two match arms above, and a hand-written damaged record has still not been folded while watching what prints. That last step would settle it.

crates/emma/src/session.rs — Fold::record, the "compacted" arm; crates/emma/tests/resume.rs

The drop.min(self.history.len()) clamp is the one thing that is defended: a count larger than the history cannot panic the splice. Since compaction only ever touches finished goals, the count is an index into history and never into query, and a compacted record arriving mid-goal splices the finished part while the goal in flight is untouched. 

// crates/emma/src/session.rs — Fold::record, continued
    // `/clear`. Everything before this point left the conversation
    // while the session was running, so a resume must not put it back.
    //
    // **Without this arm `/clear` is a lie**, and a quiet one: the
    // in-memory chapters would be empty, the next `--resume` would fold
    // the whole file, and the cleared conversation would walk back in
    // carrying its tool results. The bytes stay in the file for a human
    // to read; the fold skips them.
    //
    // Both lists go, and `in_goal` with them: `/clear` only ever happens
    // between goals, so anything still in `query` here is a goal that
    // finished and has not been moved across yet — which is exactly what
    // was cleared. `restore_records` needs no arm of its own, because it
    // already resets every counter at each `goal` record.
    "cleared" => {
        self.close_turn();
        self.history.clear();
        self.query.clear();
        self.in_goal = false;
        self.finished = None;
        self.pending = None;
        self.results.clear();
    }
    "goal_finished" => self.finished = Some(string(r, "ending")),
    _ => {}
}

close_turn() runs first inside the cleared arm and its effect is thrown away two lines later, which costs nothing and keeps the arm from being the one place a held turn can leak past a state reset. Six fields are reset by name rather than by assigning Self::default(), so a field added later has to be considered here rather than silently surviving a clear.

shed is the newest arm, landed 2026-09-06 with shedding. It does not add or drop a message: it walks every tool_use_id the record names and rewrites that block's content in the history, in the open query and in the pending results, to the replacement text the record carries. The record stores the replacement rather than the fold deriving it, which is the same rule the compacted arm follows and for the same reason: two derivations of one edit are two things a resume can disagree with. tested — a_single_long_goal_sheds_its_own_oldest_tool_results asserts the folded session equals the conversation that was held, and asserts separately that every recorded row names a block and carries the text that replaced it.

steer takes a line typed while the goal was running, closing the held turn and taking it up at the next one. The text stored is the composed string, attribution and all, for the reason the goal record stores opening rather than the user's words: a fold that recomposed it would replay a conversation the model never had, the moment the wording changed.

goal_finished stores the ending string and nothing else. It is spent by close_goal, once, when the next goal opens.

Placing a turn, or dropping it

// crates/emma/src/session.rs
fn finish(mut self) -> Vec<Message> {
    self.close_turn();
    let mut out = self.history;
    out.extend(self.query);
    out
}

/// Place the assistant turn and its results, or drop both. See
/// [`place_turn`], which is the rule and is shared with the loop.
fn close_turn(&mut self) {
    let Some(content) = self.pending.take() else {
        self.results.clear();
        return;
    };
    let results = std::mem::take(&mut self.results);
    place_turn(&mut self.query, content, results);
}

finish closes the last turn and concatenates. It does not call close_goal, so a session whose last goal never got a successor ends with that goal still in query, which is what the caller wants: the messages come back as one flat list either way, and resume puts all of them in query anyway because the split is not recorded in the file.

close_turn with no held turn clears the results. Results with no turn to answer are exactly as unsendable as a turn with no results. 

// crates/emma/src/session.rs
/// Place an assistant turn and the results that answer it, or place neither.
///
/// The rule the fold and the loop both turn on: **the API rejects an assistant
/// turn carrying a `tool_use` that no `tool_result` answers**, and equally a
/// result answering nothing. A run killed between the model call and the last
/// of its tools leaves exactly that — in the file, and in the loop's own
/// in-flight list. Half a turn is not worth a message list that cannot be sent,
/// so an unmatched turn is dropped whole.
///
/// One function rather than one per caller. The loop carries tool traffic
/// across goals now, so it needs this ruling in the same place the fold does,
/// and a second copy of it would be a resumed conversation that differs from
/// the one that was sent in precisely the cases neither is tested on.
///
/// Returns whether the turn was placed.
pub(crate) fn place_turn(
    out: &mut Vec<Message>,
    content: Vec<ContentBlock>,
    results: Vec<ToolResult>,
) -> bool {
    if !answered(&content, &results) {
        return false;
    }
    out.push(Message::assistant(content));
    // A turn that called nothing is answered by nothing, and appending an empty
    // user turn to say so is a 400 of its own.
    if !results.is_empty() {
        out.push(Message::tool_results(results));
    }
    true
}

/// Whether every `tool_use` in an assistant turn has exactly one result, and
/// every result a call. Both directions, because the API refuses both ways
/// round. A turn with no calls and no results satisfies it, which is what makes
/// a plain text turn placeable.
fn answered(content: &[ContentBlock], results: &[ToolResult]) -> bool {
    let mut calls: Vec<&str> = content
        .iter()
        .filter_map(ContentBlock::tool_use_id)
        .collect();
    let mut answers: Vec<&str> = results.iter().map(|r| r.tool_use_id.as_str()).collect();
    calls.sort_unstable();
    answers.sort_unstable();
    calls == answers
}

Sorted lists compared for equality, rather than a set comparison, so a duplicate result for one call fails the check as well: two answers to one call is one thing the API refuses in the other direction. Empty against empty is equal, which is what lets a plain text turn through.

Three of those tests fold a hand-built record list and assert the messages that come back. a_turn_whose_tool_calls_were_never_answered_is_dropped is the interrupt case, one call and no result, and expects the goal's opening message alone. a_partly_answered_turn_is_dropped_whole is two calls and one result, and expects the same. Closing a goal, and the note that stops a 400

// crates/emma/src/session.rs
/// Move a finished goal into the conversation, whole.
///
/// The one thing added is the note on a goal that stopped mid-turn. A run
/// killed on its token budget leaves a user turn last — the tool results
/// nothing answered — and the next goal's opening is also a user turn, so
/// without something between them the next request is two user turns in a
/// row, which is a 400. The note is that something, and it is information
/// rather than padding: without it the model reads an abandoned goal as a
/// completed one.
///
/// It is added when the *next* goal opens rather than when this one ends,
/// because that is when the loop adds it — and the two lists have to agree
/// at every point in the record stream, not merely at the end.
fn close_goal(&mut self) {
    if !self.in_goal {
        return;
    }
    let mut messages = std::mem::take(&mut self.query);
    if let Some(ending) = self.finished.take() {
        if messages.last().map(|m| m.role) == Some(Role::User) {
            messages.push(Message::assistant_text(crate::agent::ended_note(&ending)));
        }
    }
    self.history.extend(messages);
    self.in_goal = false;
}

Three conditions, all required: a goal was open, a goal_finished record supplied an ending, and the goal's last message is a user turn. The sentence itself comes from crate::agent::ended_note, the same function the loop calls, so the two cannot drift by a character. Two spellings of it would be a resumed conversation differing from the one that was sent by one message, which nothing notices until a cache miss or a rejection.

The three helpers

// crates/emma/src/session.rs
/// A stored `raw_content` array back into blocks.
///
/// `None` rather than an empty turn for anything that is not an array, because
/// an assistant record whose content cannot be read is a turn that must be
/// dropped whole — the same ruling `place_turn` makes about a half-answered one,
/// and for the same reason.
fn blocks_of(v: &Value) -> Option<Vec<ContentBlock>> {
    Some(
        v.as_array()?
            .iter()
            .cloned()
            .map(ContentBlock::from_value)
            .collect(),
    )
}

fn string(r: &Value, key: &str) -> String {
    r[key].as_str().unwrap_or_default().to_string()
}

blocks_of returns None for a non-array and Some(vec![]) for an empty array, and those are different outcomes: the first drops the turn, the second holds an assistant turn with no blocks. string turns a missing or non-string field into the empty string, which is why a goal record with no opening yields an empty first user message rather than an error. str_of, the third helper, belongs to restore and returns Option<String> instead, because there a missing id has to skip the record rather than match the empty one.

A second consumer, and the reason it is not a second fold

fold_prefixes walks the same records and hands back, for each assistant record, the conversation as that turn's request carried it. It is fold_records stopped early rather than a re-derivation, so a compacted record that had already been applied when a turn was sent is applied here too and one that came later is not. The training exporter is the caller, and its per-turn fidelity claim is therefore this fold's own answer rather than a second opinion about it. Its partial value is the same property from the other side: the fold reports what it refused, and an exporter that dropped the report would be claiming a fidelity the fold had already declined to give.

It clones the fold at each assistant record instead of re-walking the prefix, which is linear in the records and quadratic only in the messages copied — a few hundred small structs for a session file. unverified The cost on a large damaged file is unmeasured: an undamaged one is a single walk, and a damaged one costs extra folds to find where the damage starts. No damaged file of real size exists here to time it against. A fold_prefixes that reported the damage from the one walk would remove the question rather than answer it.
