crates/llm/src/content.rs

Typed content blocks, and the 712 tests that proved nothing

Providers & models The boundary Content blocks The turn back Model limits Caching The cache floor Retry Credentials

This module exists to delete one field. What replaced it decoded strictly, passed 712 tests with byte-identical output, and then decoded no real tool call at all, because the API puts a key on every tool_use block that nothing here had read about. The fix is two escape hatches pointing in opposite directions, and the split between them was decided by a live call rather than by taste.

The field it deletes

AssistantTurn used to carry raw_content: serde_json::Value, Anthropic's content array, echoed back on the next call without ever being read, and the loop built its own {"type":"tool_result",…} objects to answer it. Between them those two facts meant a second provider was a refactor of the loop rather than a second file beside anthropic.rs, because the loop knew the wire shape.

The blob was not laziness. This model family rejects a thinking block whose signature has been re-derived, so a turn rebuilt from text plus tool calls makes the next call fail, and the cheapest way to guarantee byte-fidelity is to never look inside. The shape that replaces it comes from goose (Block, Apache-2.0): opaque provider state becomes a narrow named field on an otherwise fully typed block. Its ThinkingContentBlock { thinking, signature } is ThinkingBlock here and its RedactedThinkingContentBlock { data } is RedactedThinkingBlock.

712 tests, clean clippy, identical bytes, dead agent

The first version of this module decoded strictly: deny_unknown_fields everywhere, and any block carrying a key the client did not model was demoted to Passthrough, kept whole and kept verbatim but no longer a typed thing the loop could act on. It passed everything. All 712 tests, clippy clean, and the rendered request bytes identical to the version it replaced.

Then it was called for real. Every tool_use block the Messages API returns carries a caller key, documented nowhere this client had read: 

{"caller":{"type":"direct"},"id":"toolu_01FJxk…","input":{…},"name":"Read","type":"tool_use"}

Under strict decoding that block was not a tool call. It was an unrecognised blob. The bytes round-tripped perfectly, the loop saw zero tool calls in a turn that contained one, took the success path, and a real goal ended on turn one reported as "answered, no tools were needed". certified: observed live on claude-sonnet-5, 2026-08-11, and the exact block is frozen as a fixture a reader can grep, in a_real_tool_use_block_is_a_tool_call_and_still_round_trips.

crates/llm/src/content.rs · a_real_tool_use_block_is_a_tool_call_and_still_round_trips

/// A `tool_use` block exactly as `claude-opus-5` sends one, `caller` and all.
///
/// **This is a regression test with a receipt.** The first version of this
/// module decoded strictly and demoted any block carrying an unmodelled
/// key. Every wire test passed, the whole suite was green, and the first
/// live goal ended on turn one reported as "answered — no tools were
/// needed": `caller` is on every real `tool_use`, so no real tool call ever
/// decoded as one. The bytes were perfect and the agent did not work.
///
/// So the two claims here are not the same claim, and both are load-bearing:
/// the block is still a **tool call** (the loop can act on it) and it still
/// round-trips **byte for byte** (the provider gets back what it sent).
#[test]
fn a_real_tool_use_block_is_a_tool_call_and_still_round_trips() {
    let v = json!({
        "caller": { "type": "direct" },
        "id": "toolu_01FJxkRrmirASsf79TJLvggU",
        "input": { "file_path": "absent.txt" },
        "name": "Read",
        "type": "tool_use"
    });
    let block = round_trips(v);
    let ContentBlock::ToolUse(call) = &block else {
        panic!("a real tool_use block did not decode as a tool call: {block:?}");
    };
    assert_eq!(call.name, "Read");
    assert_eq!(call.id, "toolu_01FJxkRrmirASsf79TJLvggU");
    assert_eq!(call.input, json!({ "file_path": "absent.txt" }));
    assert_eq!(call.extra["caller"], json!({ "type": "direct" }));
}
crates/llm/src/content.rs — tests

Nothing was malformed, nothing errored, no status code was wrong, and the harness reported success. A green suite is not evidence that a wire format still talks to the provider. The suite agreed with its author about what a tool_use block contains, and its author was out of date by one undocumented key. The detector was a live call.

Two escape hatches, pointing opposite ways

An unknown block type becomes ContentBlock::Passthrough, kept exactly as it arrived. There is nothing to interpret, so nothing is lost by not interpreting it. server_tool_use and web_search_tool_result are the next real instances arriving.

An unmodelled key on a known type keeps its variant, and the key goes into that block's extra map, echoed back untouched. That is the case the live call above failed on: the bytes were kept and "this is a tool call" was lost.

crates/llm/src/content.rs · ContentBlock::from_value

/// Parse one wire block, keeping everything it carried.
///
/// Two guarantees, and they fail in opposite directions if either is
/// removed. The `extra` field on each struct catches keys this client does
/// not model, so a `tool_use` that grew a `caller` is still a tool call —
/// take it away and the loop stops seeing real tool calls, which is what a
/// live run caught. The `.ok()` fallback catches a block this client cannot
/// build at all, so an unknown `type` still travels — take that away and
/// the turn is silently corrupted on replay.
pub fn from_value(v: Value) -> Self {
    let Some(kind) = v.get("type").and_then(Value::as_str) else {
        return Self::Passthrough(v);
    };
    // The tag is removed rather than tolerated, because tolerating it would
    // mean loosening `deny_unknown_fields` — the one thing holding the
    // guarantee above up.
    let mut rest = match v.as_object() {
        Some(obj) => obj.clone(),
        None => return Self::Passthrough(v),
    };
    rest.remove("type");
    let rest = Value::Object(rest);
    let typed = match kind {
        "text" => serde_json::from_value(rest).map(Self::Text).ok(),
        "thinking" => serde_json::from_value(rest).map(Self::Thinking).ok(),
        "redacted_thinking" => serde_json::from_value(rest)
            .map(Self::RedactedThinking)
            .ok(),
        "tool_use" => serde_json::from_value(rest).map(Self::ToolUse).ok(),
        "tool_result" => serde_json::from_value(rest).map(Self::ToolResult).ok(),
        _ => None,
    };
    typed.unwrap_or(Self::Passthrough(v))
}
crates/llm/src/content.rs — from_value

extra is written only by from_value, read only by to_value, and nothing branches on its contents. A key Emma needs to act on becomes a field promoted out of it rather than a lookup into it. That rule is what keeps the map from being raw_content at a smaller scale, and the module doc states it exhaustively: keys the provider put on a block whose type this client models, which this client does not read. Nothing else.

Why per-block Passthrough rather than goose's ProviderMetadata for the unknown-type case: that hangs a map off every block for any key a provider wants back, so every typed block has an untyped half and a reader cannot tell from the type which fields are real. A block here is either fully typed or fully opaque. The cost is that one unmodelled field demotes a whole block; the benefit is that ContentBlock::Text means what it says.

The five typed blocks

Each is a plain serde struct with a flattened extra map skipped when empty. Only two carry more than that.

crates/llm/src/content.rs — ThinkingBlock

signature is the narrow named field the whole module is built around. Emma never reads it, never composes one, never re-derives one. It is an Option rather than goose's bare String because a streamed block that carried no signature_delta has no signature, and sending "signature": "" is not the same request as sending no key at all. crates/llm/src/content.rs · ToolResult

/// The answer to one [`ToolCall`], including the answer "it failed".
///
/// **`is_error` is load-bearing and is not an error type.** A failed tool is an
/// observation the loop continues from — `agent.rs` says so at the top of the
/// file and five failure classes in tustle-agent were measured ending turns
/// silently before it did. So this is one struct with a flag rather than a
/// `Result`: a `Result` would make "the tool failed" unrepresentable as a
/// message, which is precisely what has to be representable.
///
/// The flag is skipped when false so a successful result renders the two keys
/// it always rendered, and no third.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize, Default)]
pub struct ToolResult {
    pub tool_use_id: String,
    pub content: String,
    #[serde(default, skip_serializing_if = "is_false")]
    pub is_error: bool,
    #[serde(flatten, default, skip_serializing_if = "serde_json::Map::is_empty")]
    pub extra: serde_json::Map<String, Value>,
}
crates/llm/src/content.rs — ToolResult, is_false

is_false is a two-character helper serde needs a path to; ToolResult::ok and ToolResult::failed are the two constructors and differ only in that flag. TextBlock, RedactedThinkingBlock and ToolCall add nothing beyond their fields and the same extra. Only ToolCall's doc explains why its map is not optional: the API puts caller on every tool_use it emits, so a ToolCall that could not hold an unmodelled key would never match a real one.

Rendering back out

crates/llm/src/content.rs · ContentBlock::to_value

/// The wire object. Byte-for-byte what the Messages API documents, and what
/// the previous `serde_json::Value` blocks rendered.
pub fn to_value(&self) -> Value {
    match self {
        Self::Text(b) => with_extra(json!({ "type": "text", "text": b.text }), &b.extra),
        Self::Thinking(b) => {
            let mut v = json!({ "type": "thinking", "thinking": b.thinking });
            if let Some(sig) = &b.signature {
                v["signature"] = json!(sig);
            }
            with_extra(v, &b.extra)
        }
        Self::RedactedThinking(b) => with_extra(
            json!({ "type": "redacted_thinking", "data": b.data }),
            &b.extra,
        ),
        Self::ToolUse(c) => with_extra(
            json!({ "type": "tool_use", "id": c.id, "name": c.name, "input": c.input }),
            &c.extra,
        ),
        Self::ToolResult(r) => {
            let mut v = json!({
                "type": "tool_result",
                "tool_use_id": r.tool_use_id,
                "content": r.content,
            });
            if r.is_error {
                v["is_error"] = json!(true);
            }
            with_extra(v, &r.extra)
        }
        Self::Passthrough(v) => v.clone(),
    }
}
crates/llm/src/content.rs — to_value

Two conditional keys, and both matter to the bytes: a signature that is None renders no key at all, and is_error appears only when true. Both are pinned in the golden request body, which contains {"thinking":"unsigned","type":"thinking"} with no signature and one tool_result with "is_error":true beside one without the key. certified: read the literal in the_whole_request_body_is_pinned_byte_for_byte.

crates/llm/src/content.rs · with_extra

/// Put the unmodelled keys back on a rendered block.
///
/// Insertion rather than a raw copy so a provider key can never overwrite one
/// this client models: `extra` is only ever populated from keys the struct did
/// not claim, and this asserts that invariant instead of trusting it.
fn with_extra(mut v: Value, extra: &serde_json::Map<String, Value>) -> Value {
    if let Some(obj) = v.as_object_mut() {
        for (k, val) in extra {
            debug_assert!(
                !obj.contains_key(k),
                "`extra` carried {k}, which the typed block also renders"
            );
            obj.insert(k.clone(), val.clone());
        }
    }
    v
}
crates/llm/src/content.rs — with_extra

The assertion is a debug_assert!, so it fires in a test or a debug build and is compiled out of a release binary. In release, a colliding key would overwrite the typed field silently. Whether that can happen at all depends on serde(flatten) never handing back a key the struct claimed, which is serde's documented behaviour and is not checked here. unverified Settling it means a test that constructs a ToolCall with "name" forced into extra and asserts the panic, which no test currently does.

Locating the state a model change would break

crates/llm/src/content.rs · ContentBlock::is_model_bound

/// `Passthrough` counts, and that is the conservative direction on purpose:
/// this client does not know what is in a block it could not model, so it
/// must not claim the block is portable.
///
/// A plain text block is not model-bound, which is why the existing
/// compaction path is already a working escape hatch: a summarised chapter
/// is [`Content::Text`] and carries no signatures at all.
pub fn is_model_bound(&self) -> bool {
    match self {
        Self::Thinking(t) => t.signature.is_some(),
        Self::RedactedThinking(_) | Self::Passthrough(_) => true,
        Self::Text(_) | Self::ToolUse(_) | Self::ToolResult(_) => false,
    }
}
crates/llm/src/content.rs — is_model_bound

Nothing calls it yet. It exists so a question stays answerable: whether a thinking signature minted by one model is accepted when the conversation continues on another is untested here, and an in-session /model command is the first thing that would need to know. unverified Nothing records which model produced a signed block, so the granularity that does exist is per goal, from the session log's goal record. Settling it means one conversation continued across two models, watching whether the second accepts the first's signature. Under the blob this replaced, finding those blocks meant re-parsing Anthropic's format at the call site.

tool_use_id is its neighbour and answers a narrower question: the id a block is, for a ToolUse, and None for everything else. The doc comment says "is, or answers", but the match returns None for ToolResult, so a caller wanting the pairing from the answering side reads ToolResult::tool_use_id directly. The comment and the match arms disagree, and the match arms are what runs.

A message's content is two shapes, not one

crates/llm/src/content.rs · enum Content

/// Two variants because the API takes two forms and Emma sends both: a user's
/// typed words go as a plain string, and anything with tool traffic in it goes
/// as blocks. Collapsing them to `Blocks` alone would be tidier and would
/// change the bytes of every ordinary user turn, which is a cache prefix nobody
/// asked to invalidate.
#[derive(Debug, Clone, PartialEq)]
pub enum Content {
    Text(String),
    Blocks(Vec<ContentBlock>),
}
crates/llm/src/content.rs — Content

Content::blocks() returns an empty slice for the text variant rather than an Option, which is what lets a caller ask "is anything in here model-bound" without matching first. wire_len() is the rendered byte count and feeds the cache size gate, so it counts the quotes and the escapes rather than the length of the text inside. wire_len_counts_the_rendered_bytes_not_the_text pins Content::Text("hi") at 4 bytes, which is the string plus its two quotes. tested

Four impls do the serde work. ContentBlock's Serialize and Deserialize delegate to to_value and from_value, which is what puts the two escape hatches on every path in and out, including session files. Content's Serialize renders whichever variant it holds; its Deserialize maps a JSON string to Text, an array to Blocks, and rejects anything else with a message naming what it got. Display renders the JSON, which is what Value's own Display gave before this was a type, and half a dozen assertions elsewhere ask "did the model see this string anywhere in the message".

Coverage

All 16 functions in content.rs are named on this page: with_extra, is_false, ContentBlock::text, to_value, from_value, is_model_bound, tool_use_id, ToolResult::ok, ToolResult::failed, Content::blocks, Content::wire_len, Display::fmt, and the four Serialize and Deserialize impls. ContentBlock::text is the one-line constructor for a text block with an empty extra, and has nothing else in it.

Eight tests guard the module and every one of them is a round-trip in some shape. The interesting ones are where the typed model is wrong about a block: an unknown type, and a known type with an extra field. Those are what a silently-lossy design passes and this one has to fail. All eight ran green here on 2026-08-16, as part of the 72 tests cargo test -p emma-llm reports. certified
