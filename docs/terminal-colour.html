Colour, named by role

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Run control Copying out

Nothing in term/ names a colour at the point of use. Text is given a role, and the role is resolved at one function. That single substitution point is what makes the sixteen-colour fallback one match rather than a change at every call site, and it is also where NO_COLOR stops being a preference and becomes unreachable-by-construction.

Three rules above the roles

Each of the three is in the module doc, and each is there because the alternative breaks on a machine nobody here can see.

  • Ordinary text is never given a colour. Emma cannot ask the terminal what its background is. Gruvbox's foreground is #ebdbb2, a cream that is invisible on white, so body text is Color::Reset, whatever the user already chose.
  • Colour is never the only signal. Every event that gets a colour also gets its own glyph and its own weight. A terminal rendering #b8bb26 as a muddy olive still shows ✓ where a success was, and the same redundancy covers the readers who cannot distinguish the red from the green.
  • Nothing paints a lone background. The two places a background exists set foreground and background together, which is what makes them legible against an unknown ground. Both degrade to reversed video at Level::None.
crates/emma/src/term/palette.rs module doc

The first and third are enforced twice, and the module says why: “once by the loader, which refuses the keys by name, and once here in Palette::color, which returns before the theme is read. The loader can only refuse data it has thought of; this function cannot be given data at all.”

How much colour, from six inputs

crates/emma/src/term/palette.rs · Level::of

    pub fn of(
        color: bool,
        no_color: bool,
        override_var: Option<&str>,
        colorterm: Option<&str>,
        term: Option<&str>,
        windows_terminal: bool,
    ) -> Self {
        if let Some(v) = override_var {
            match v.trim().to_ascii_lowercase().as_str() {
                "none" | "0" | "off" => return Self::None,
                "16" | "ansi" => return Self::Ansi16,
                "256" => return Self::Ansi256,
                "truecolor" | "24bit" | "full" => return Self::Truecolor,
                // An unreadable value is not permission to guess loudly.
                _ => return Self::Ansi16,
            }
        }
        if no_color || !color {
            return Self::None;
        }
        if matches!(colorterm, Some(v) if v.contains("truecolor") || v.contains("24bit")) {
            return Self::Truecolor;
        }
        if windows_terminal {
            return Self::Truecolor;
        }
        match term {
            Some(t) if t.contains("256color") => Self::Ansi256,
            Some("dumb") => Self::None,
            None => Self::Ansi16,
            Some(_) => Self::Ansi16,
        }
    }

The Windows console that says yes and means no

Before the ladder runs, detect asks a Windows-only question: if output looks colour-capable, but there is no WT_SESSION, no EMMA_COLORS, and enable_vt() returns false, the answer is Level::None regardless of what the environment claims.

That console exists. It is a terminal, it is not redirected, and it does not process escape sequences, so every SGR byte Emma wrote landed on the screen as literal text. The ladder could not catch it, because every input the ladder reads was truthfully saying "this is a terminal". The only signal that distinguishes the case is whether virtual-terminal processing could actually be turned on, which is a syscall rather than a variable.

EMMA_COLORS still wins when set, in this direction as much as the other. unverified against a real VT-less console: this is reasoned from enable_vt's contract and exercised with the syscall stubbed, not observed on a console that genuinely refuses VT. What would settle it: a run under a Windows console host with virtual-terminal processing disabled, checking stdout for escape bytes.

The environment is an argument rather than a global, which is what makes the whole ladder testable. Level::detect is the one place that reads the real process, and on Windows it does the one thing above before the ladder runs.

The order is “so the honest signals beat the hopeful ones”: an explicit override first, since the person setting EMMA_COLORS is looking at a terminal Emma guessed wrong about; then NO_COLOR and “this is not a terminal at all”; then the environment's own claims. WT_SESSION is the Windows Terminal case, which does 24-bit and sets neither a useful COLORTERM nor a useful TERM.

An unreadable override resolves to Ansi16 rather than to truecolor, and the comment carries the reasoning in seven words: “an unreadable value is not permission to guess loudly.” tested crates/emma/src/term/palette.rs: four tests over Level::of, including the_override_beats_every_other_signal, which sets EMMA_COLORS=256 against NO_COLOR and TERM=dumb together and still gets Ansi256.

A theme is not one of the six inputs. That is what stops /theme from promoting a sixteen-colour console, and Palette::with_theme has no way to detect anything, so the property holds by signature. tested crates/emma/src/term/palette.rs: a_theme_chooses_colours_and_never_how_many_of_them_there_are.

crates/emma/src/term/palette.rs — enum Role; crates/emma/src/term/theme.rs — BUILTIN

The values moved into theme.rs when themes landed. The arguments for them stayed here, and the region comment says why: they are arguments about what a role means, “and the person most likely to reverse one by accident is somebody editing a theme file who never opens the loader.” Four of them travel with the role.

The last six arrived on 2026-09-06, when the Code page started colouring source from the language server. They sit in the same family as the eight above rather than importing another editor’s palette, so a file on that page looks like the rest of Emma.

Two of the choices carry an argument. A comment is dimmer than Dim, because Dim is chrome you glance at and a comment is text you are choosing not to read. And the keyword is the accent’s hue desaturated, so a screen of let and fn does not compete with Emma’s own chrome for attention. Function is blue, the one family nothing else uses, so a call reads as its own thing beside the type it is called on.

  • Dim is a neutral grey rather than Gruvbox's warm #928374, because a warm grey beside a pink accent reads as a third, muddier colour rather than as an absence of one.
  • Accent at sixteen colours is not LightRed, even though the hue is nearer. Role::Err owns red at that level, and the accent is what a user's own message is drawn in, so a goal line that read as an error would be worse than one that reads as violet.
  • Warn is yellow at every level even though the 24-bit yellow is nearer to some oranges: a warning that changes hue between terminals is a warning somebody has to re-learn.
  • Text has no value reachable here at all. The rest of this page is about that short-circuit.

The one substitution point

crates/emma/src/term/palette.rs · Palette::color

    pub fn color(&self, role: Role) -> Color {
        if self.level == Level::None || role == Role::Text {
            return Color::Reset;
        }
        match self.level {
            Level::Truecolor => {
                let (r, g, b) = self.theme.rgb(role);
                Color::Rgb(r, g, b)
            }
            Level::Ansi256 => Color::Indexed(self.theme.indexed(role)),
            _ => self.theme.ansi16(role),
        }
    }

The two backgrounds

crates/emma/src/term/palette.rs · Palette::chip, Palette::band

    pub fn chip(&self, role: Role) -> Style {
        if self.level == Level::None {
            // No colour to invert, so the emphasis has to come from somewhere:
            // reversed video is the one attribute every terminal has.
            return Style::default().add_modifier(Modifier::REVERSED | Modifier::BOLD);
        }
        Style::default()
            .fg(self.color(Role::Ground))
            .bg(self.color(role))
            .add_modifier(Modifier::BOLD)
    }
crates/emma/src/term/palette.rs — chip, band, BAND_ANSI16_BG

chip is the approval prompt's answer keys, and its background is the caller's argument: the prompt draws its answer key on Role::Accent and its refusal on Role::Warn, so a stored pair with a fixed background could not say both. band is the sidebar's selected-session row, and that one is a stored pair, because the colour has no role behind it: accent text on a barely-raised near-black, rgb(25,27,30), measured off the approved TUI mockup on 2026-08-13.

The band lived in sidebar.rs behind a note saying it was there only because this file was not that workstream's to grow. It moved here, and the reason is the whole premise of the module: “a second private colour table outside the one substitution point is exactly the drift a theme cannot be applied to.”

Its two non-hex fidelities differ from each other, and the asymmetry is the same one themes use. The 256 index is derived from the pair's own hex, because that is mechanical: nearest_index puts rgb(25,27,30) on 234, the greyscale ramp's #1c1c1c. The sixteen-colour background is not derived, because nearest distance on a near-black picks black, which is the terminal's own background on the machines this band exists for, “and a band the same colour as the ground is not a band.” BAND_ANSI16_BG is DarkGray, chosen by intent.

tested crates/emma/src/term/palette.rs: the_selection_band_is_the_measured_pair_at_every_fidelity pins all four, and closes with a property rather than a literal, that the band is never equal to chip(Role::Accent) at any fidelity. That is the regression the owner reported by eye as “not formatted like the image”, when an earlier draft reused the chip's dark-on-pink and the sidebar row read as a second approval prompt. nothing_paints_a_background_except_the_named_pairs holds the other end: every role is a lone foreground, and both pairs set both halves and are never equal to each other.

crates/emma/src/term/palette.rs — nearest_index

Squared RGB distance over the 6×6×6 cube (indices 16 to 231, levels 0/95/135/175/215/255) and the 24-step greyscale ramp (232 to 255, value 8 + 10i). The first sixteen entries are excluded, because they are whatever the user's terminal theme says they are, so “nearest” is a claim about a colour this process cannot see.

Only pairs come through this function, and only for their 256-colour half.

A role's index is declared by the theme, and the reason was measured: the derivation reproduces five of the seven shipped indices exactly and disagrees with two by a shade of the same hue. Err derives to 203 where the customary Gruvbox terminal mapping is 167, and Dim to 246 where it is 245, one greyscale step. Both divergences are pinned by the_256_derivation_reproduces_the_measured_table rather than smoothed over, “because the reason the built-in theme declares those two indices is that this function would otherwise quietly change what Emma looks like.” tested crates/emma/src/term/palette.rs

A consequence the file states rather than hides

Where a pair's half names a role whose index the theme declared against the derivation, the band will use the derived one, because Palette::band calls nearest_index on the pair's hex rather than reading the role's declared index. For the built-in theme the two agree: accent derives to the 204 it declares, which is what the test pins. A theme declaring an ansi256 for accent and naming accent as its selection foreground would see the declared index in ordinary text and the derived one in the band. unverified as a visible symptom; it follows from reading band beside Theme::indexed. A theme file declaring a distant ansi256 for accent, rendered at Level::Ansi256, would settle it.

Why the whole thing is Copy

Palette is two fields, a Level and a Theme, and it is Copy. Fifty-five call sites construct one and pass it by value: 36 outside term/palette.rs itself, which holds the other 19. certified: rg -n "Palette::new" crates/emma/src | wc -l returns 55 on 2026-09-01. The page said "roughly thirty" until then, which was a hedge rather than a count.

The Skin that holds one is stored in widgets across the module. A Theme holding a String would end that and cascade through every signature in term/, which is why themes are resolved to fixed-size data at load. tested crates/emma/src/term/palette.rs: a_palette_is_still_copy asserts it of Palette, Theme and Level through a fn assert_copy<T: Copy>().

The four small helpers on top of color are style (a foreground, and for one role a modifier as well), dim (the Dim role plus Modifier::DIM, so a colourless terminal still separates a note from a line somebody has to read), bold, and the two pair functions above. Palette::new(level) and Palette::with_theme(level, BUILTIN) are the same thing, which keeps all 55 Palette::new call sites interchangeable with with_theme.

style adds Modifier::DIM for Role::Comment and for no other role, which is dim’s reason rather than a flourish. At Level::None every colour is Color::Reset, so a comment and the code it explains would be the same white text, which is the exact complaint the palette was extended to answer. A modifier is the only separation a terminal with no colour can still draw. Dimming the code as well would be worse than nothing, so nothing else is dimmed, and the modifier stays on at every fidelity: a comment is quieter than the rest whatever the terminal can do. tested crates/emma/src/term/palette.rs: a_comment_is_dim_even_on_a_terminal_with_no_colour asserts the comment carries DIM at Level::None, that Role::Keyword does not, and that the modifier survives at truecolor.

The whole built-in palette, pinned

the_built_in_theme_renders_exactly_what_shipped is a full table of the original eight roles at four fidelities, thirty-two assertions, and its doc says why it is written as literals rather than as properties: “the failure it guards against is a single value drifting during the move, which no property test can see, since every property here (degradation, accent ≠ error, no lone background) would still hold of a subtly different palette. Somebody who changes a colour on purpose edits this table and says so; nobody changes one by accident.” tested crates/emma/src/term/palette.rs

unverified The six source-code hexes are not pinned to their values anywhere. That table stops at Ground. The other assertion, the_builtin_theme_is_what_emma_renders_today in theme.rs, walks all fourteen roles comparing the live Palette against BUILTIN, which is close to a tautology now that palette.rs reads BUILTIN: it pins the shape (Rgb at 24 bits, Indexed at 256, a named colour at 16) and not the colour. Its literal receipts cover seven of the original eight and none of the six. So a typo in #7c7974 would go green. What would settle it: six more rows in the palette.rs table, or six literal assert_eq!(BUILTIN.rgb(Role::Comment), (124, 121, 116)) lines beside the seven already in theme.rs. Recorded as a hazard.

The accent can be overridden, by role or by cube index

appearance.accent in settings.json holds one of two shapes. A role name — theme, ok, info, warn, err — makes the accent borrow that role's swatch from whatever theme is in force. cube:N for N in 16–231 pins a literal xterm cube index. Anything else parses as nothing, and an unset preference is theme, which is why theme is index 0 of ACCENTS.

A borrowed accent is a name and a role, never a colour. The swatch still comes out of the theme, so the override survives a theme switch, degrades through Level as every other colour does, and cannot introduce a hex no theme approved.

The cube form gives that up on request: it is a literal index, so cube_renderable is false below Level::Ansi256 and the picker does not offer the cube at all on a 16-colour terminal, where the theme's own accent is what is drawn. tested — parse_accent_reads_role_names_and_cube_indices (which pins cube:0 and cube:999 as refusals, not clamps) and a_cube_accent_is_an_index_on_a_256_colour_terminal. Replacing the borrow with a fresh hex fails with the override must be the theme's Ok swatch, not a new hex.

The choice is ambient rather than a field on the Skin, and the reason is the section below this one: a Skin is Copy and the viewport holds copies, so a picker that changes the accent later must not have to find them all.

main.rs reads the stored value and calls activate_accent_choice before the first palette is built, so a saved choice applies from the first frame, and only a live palette (Palette::live) consults the override. A pinned Palette::new or with_theme ignores it, which is the seam that keeps the colour tests independent of whatever a settings file happens to say.
