The claude engine: a goal handed to another program

Providers & models The boundary Content blocks The turn back Model limits Caching The cache floor Retry Credentials The claude engine The claude engine

Selecting claude does not put a client behind Emma's loop. It replaces the loop. main.rs branches once, on the resolved provider's name, and hands the whole goal to a claude -p child whose events are streamed back and turned into the same Outcome every other goal produces. The two engines agree on exactly one thing: a goal in, an outcome out.

A provider name that refuses every request

There is a ProviderKind for claude even though nothing behind it ever sends a request, because provider selection is one mechanism and has to stay one: the flag, the settings file, the Settings screen's cycler, the keys row and the per-provider model entry all read the same registry, and a second selection surface beside it would be two places to set this and two places for a bug to hide.

The price is an object that cannot pretend. Every request through it fails, loudly, naming the branch in main.rs that should have caught the dispatch before anything got there. That is an assertion wearing a trait rather than a half-working client, and it is deliberate: a send that answered prose would make a mis-wired dispatch look like a working one. tested the refusal is the thing that gets a test, because a send that ever succeeded would mean Emma's loop had quietly become what drives this engine.

It is keyless, like Ollama and for a related reason: the CLI carries its own authentication, so Emma has no credential to store and does not want one. A second copy of a key under ~/.emma would be a second thing to rotate and a second thing to leak. That is what makes the keys row read n/a.

The escalation rule

Emma hands the child the posture the user handed Emma, and never more. The same bit that puts Emma's own gate into skip-everything is the only thing that may unlock the child's bypass; without it the child is given --permission-mode default positively rather than by omission, so a change in the CLI's own default cannot silently widen what a goal may do. tested without the bypass bit, Emma never passes the dangerous flag; shown red under mutation.

Under this engine Emma's approval gate does not apply at all. The permission system in force is the child's own, and a denial from it ends the goal stalled rather than being retried. A page describing Emma's gate is describing something that is not running for a claude goal. tested a denial ends the goal stalled; shown red under mutation.

Windows: the handle, the shim and the newline

The fork shipped a Windows liveness check that answered “exited” without asking. That is a kill reporting success over a running command, which is a defect class this repository has already paid for once, and it arrived as new code rather than as a reverted hunk, so no diff of the old file would have flagged it. The child now holds a real process handle taken at spawn, which also reserves the process id and closes the recycled-id hazard; liveness is a zero-length wait on that handle and the stop is a terminate. tested a test spawns a real child, stops it, reaps it and asks again; making the check answer “exited” unconditionally turns it red.

Resolution honours PATHEXT, so a native executable beats a .cmd shim, and a shim runs through the command interpreter with a hand-built, caret-escaped command line. Two things were measured on the way to that. The interpreter expands environment variables inside a quoted argument, so a goal mentioning one would splice the user's own paths into the prompt; the quotes are escaped for that reason. And it truncates its command line at the first newline and exits zero, which is silent loss, so a multi-line goal through a shim is refused in words rather than cut. certified both measured on Windows 11, with the argument round-trip pasted in the port report.

unverified The shim half has met a shim the port wrote and never a real npm one, which re-execs a runtime and may not carry the exit code and output through that extra hop. Settled by a global npm install on a Windows box with no native binary, then the same certification again.

Typing during a claude goal

A claude -p child runs with its input closed, so there is no turn boundary inside it that a mid-goal steer could land on. Steering still takes what is typed, and the between-goals drain turns it into the next goal, so nothing typed is lost. The queued row has to say that rather than promise a turn that will not come, which is what the steerable flag exists for: under this engine it is false, and the transcript says “queued for after this goal”. tested the two wordings are chosen by that one flag.

What has not been checked

unverified The stream shape is believed, not measured. The fixture the decoder is tested against is synthetic, written from the documented event shapes, so a shape transcribed wrongly is a shape every test here agrees with. Settled by one real run with the streaming output format, diffing event keys against the fixture. This is the same shape as the strict decoder that passed every test and then decoded no real tool call, which is why it is named here rather than left implied.

unverified Nothing in the engine has run on macOS. The unix liveness check reads a zombie as alive, which is mitigated by racing the stop against the child's own wait, and that race is untested. Settled by the filtered suite on the Mac.

unverified Nothing has been drawn on a real console: every terminal seam here goes through a recording double. Two terminal defects have shipped from this repository past a green suite for exactly that reason.
