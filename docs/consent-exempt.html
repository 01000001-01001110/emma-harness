The list

/// Writers that do not prompt, and the whole argument for each one.

crates/emma/src/approval.rs — EXEMPT

certified Two entries and no more, at commit a3eba74: grep -n "const EXEMPT" crates/emma/src/approval.rs returns one line and it is the one above.

The two task tools rewrite .emma/tasks/tasks.md. They declare read_only: false and were not declared read_only: true to dodge the gate. A tool that misreports itself leaves the gate protecting nothing in general rather than only for that tool, which is why the hole is a list of names in one place rather than a lie in a tool crate.

The write is confined to the tool's own bookkeeping file, and it is the write a model performs several times per goal. The argument on the list quotes the module's own rule back at itself: a prompt the user cannot evaluate is worse than no prompt, and "TaskUpdate wants to tick a checkbox, allow?" fifteen times in one goal is the prompt that teaches somebody to hold down y, including through the Bash call that follows it.

crates/emma/src/approval.rs — EXEMPT, doc comment
A bypass keyed by name, not by property

EXEMPT is a const &[&str] compared against tool.name() with contains. Nothing about a listed tool is checked: not its ToolMeta, not what it writes, not where. A name added to that array stops prompting, whatever the tool behind it does.

The test is written about what is not on the list. It asserts Bash, Write and Edit are absent and that all three are still gated under Gate::Unattended, which is what would catch a later edit adding a tool that writes the user's source tree. It also loops over EXEMPT itself and asserts each entry is allowed, so shrinking the list to nothing would fail too. tested

The two things that bound it

A PreToolUse hook denial is resolved in the loop before approvals are consulted, so an operator can block these by name. And an ask rule reaches them, because the ask check sits above the exemption in decide. Every call, exempt or not, is written to the session log by the loop. tested an_ask_rule_reaches_even_a_read_only_tool_and_an_exempt_one puts Read and EXEMPT[0] in the ask list with an empty answer queue and asserts both are denied, which they can only be if the prompt was reached.

The opposite shape does not exist

EXEMPT is an always-allow hole. A small, hardcoded, non-overridable deny list that no rule, no flag and no remembered grant can relax is notes/improvements.md item 14, and it is open. rm -rf / in a Bash call is a prompt like any other, and answering y runs it.

Three projects that built the floor

Zed's tool_permissions has three regex tiers plus built-in protections its documentation illustrates with rm -rf /, which no rule can override. avala-ai/agent-code blocks .git/ and node_modules/ unconditionally. And c4pt0r/pie has it written in Rust already, in crates/agent/src/harness/permission.rs, a 491-line module including its tests: an unconditional-deny corpus where each entry carries a label naming what it protects and that label is carried into the denial reason; token-aware predicates for rm that survive flag permutations and one layer of quote stripping; clause splitting on ;, &&, || and |; and roughly forty dangerous-command cases beside a false-positive suite.

The counter-argument, recorded because it may win

An unconditional refusal that fires on a legitimate command is an outage, not a safety property. That is the "rule that fires on correct configuration" shape this codebase rejects elsewhere by name. If the floor is built, the list has to be short and every entry has to name what it protects.

That becomes a condition on copying: take pie's predicates and its corpus, not its regexes. Pie's are substring matches that accept false positives. \bsudo\b fires on echo "sudo", and reboot fires inside any quoted string containing the word. Pie's own module doc states the trade as "the permission layer must close, not minimize", which is the failure the counter-argument predicts.

One further idea from pie transfers even though its mechanism does not: it treats writes to the harness's own configuration as their own permission category. Emma has the same hazard in file form. A Write to .claude/hooks/, settings.local.json, agents/ or skills/ is a persistent behaviour change that classifies today as an ordinary file write, and it is the one edit that can disable the check that would have caught it.
