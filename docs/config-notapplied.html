1 · A different directory was loaded than the one you edited

Three causes, and all three look identical from inside the editor: .emma/ beat a .claude/ sitting beside it, a nearer ancestor had a harness you had forgotten about, or EMMA_ROOT is exported in that shell. Read the first three lines of the report: cwd, harness, flavor. If harness is not the directory you edited, nothing below matters.

A fourth cause is narrower and worth knowing because it has no message at all: the home directory's .emma/ is only a harness when it holds a config.json or a personas/. A ~/.emma/ holding a stored key and a settings file is walked past, and the run gets the absent-harness refusal rather than a silent boot. Discovery has the whole walk.

2 · The key is real, but it belongs in a different file

if you wrote…in…it belongs in…
theme, provider, model, tools .emma/config.json ~/.emma/settings.json, and the spine would have refused to start over it, so if Emma booted, that is not what happened
permissions.allow ~/.claude/settings.json the project's spine or settings.local.json. User scope contributes deny only, silently
a hook for SessionStart, Stop, PreCompact either spine nowhere: Emma has three events. By default this is a startup error rather than a skip — so if Emma booted with no EMMA_CLAUDE_HOOKS set, this is not it. With EMMA_CLAUDE_HOOKS=skip-unknown it boots and names each dropped hook, so the inference needs the variable checked first
a skill or agent in a subdirectory agents/<sub>/x.md top level. agents/ and commands/ read *.md at the top only; skills/ wants <name>/SKILL.md exactly
a hook or status-line command outside hooks/ either spine <harness>/hooks/. An absolute path or a shell string is a startup error for a hook and a note for a status line

Two of those rows say "if Emma booted, this is not it", and that is the most useful property the chapter has. Emma's own format refuses rather than ignores, so a misplaced key in .emma/config.json cannot be the explanation for a run that started.

3 · The key was swallowed rather than refused

Three files ignore keys they do not know, and in all three a misspelling is silence:

file or blockunknown keywhy
.claude/settings.json, outer level ignored Somebody else's format, carrying keys Emma has no opinion about. Denying them would refuse the boot in essentially every real Claude Code repository
permissions, in either spine ignored defaultMode and additionalDirectories are real keys in real files. This is the one permissive block inside Emma's own strict file
statusLine, in either spine ignored refreshInterval and friends are display preferences
.claude/skills/*/SKILL.md frontmatter ignored Real skills carry model-role, version and allowed-tools; under the strict struct every one of them took the boot down
agents/*.md frontmatter ignored Measured against 90 real agent files, category and version appear throughout
~/.emma/settings.json, entirely ignored, and a parse failure is too A preference store that refused to start would be the tail wagging the dog

So: if you edited a permissive file, compare your key against the tables on the compatibility page and your own files by eye. There is no spelling check available, and that is the price of one format belonging to another program and the other being a preference store that must not refuse to start. .emma/config.json's outer level is the opposite and would have named your key and the whole valid vocabulary.

The lower-level version of the same thing is a value swallowed by shape rather than by name. tools: [] in an agent file means inherit, not nothing. A theme role spelled wrongly is a notice and costs that role only. A skill under .claude/ whose frontmatter will not parse is skipped with a line on stderr that scrolls past on a busy start, and config check is where the surviving list is.

4 · It applied, and it does not take effect until the next start

Everything the harness reads is resolved once at startup into a value the loop consumes; nothing re-reads a configuration file mid-run. /theme is the one that surprises people, and the command says so itself: a theme is read once, so selecting one is writing it down, and there is no --save to forget.

The exception runs the other way. ~/.emma/settings.json is re-read on every usertools call rather than cached, so an editor changed through the Settings tool is live on the next frame. In the same module, PATH lookups are cached for the life of the process, so a program installed mid-session appears after a restart.

5 · It loaded, and was rejected at use

A rule Emma cannot evaluate is the clearest case: it is in the file, it is listed by config check, and it approves nothing. That is a note rather than a refusal, because a file written correctly for a program with a larger vocabulary is not a broken file.

The example this section used to give is no longer one. Bash(ls:*) was the illustration, and it now evaluates — along with Read(./src/**) and Bash(git log:*). Run against a scratch harness carrying all three plus two denies, the current binary loads five rules and has nothing to announce: 

permissions    5 rule(s)
               deny  WebFetch(domain:evil.test)   …\.claude\settings.json
               deny  Bash(rm *)   …\.claude\settings.json
               allow Bash(ls:*)   …\.claude\settings.json
               allow Read(./src/**)   …\.claude\settings.json
               allow Bash(git log:*)   …\.claude\settings.json
               a remembered grant is written to …\.claude\settings.local.json
certified: release binary rebuilt at ce0dd69, scratch .claude/ harness, 2026-08-22. Paths elided for width; nothing else altered. The previous certification on this block showed a warning line the current binary cannot produce — it was honest of its own build and went on looking green for weeks after the behaviour moved, which is the failure mode a dated certification has, and the reason a reader who tries to reproduce one is doing the site a favour.

So the category still exists and its example had to be replaced. Bash(git log) with no wildcard and no separator is still a command prefix; a specifier this build genuinely cannot parse into any of the four shapes still loads, still gets named, and still approves nothing. What changed is how rarely that happens: the same measurement that found 62 of 64 real rules inert is why this example stopped working.

Four things share that shape: loaded, named, and doing nothing. A configured editor that is not on PATH; an agent with no description; a project command a built-in shadows; and the permission rule above. config check prints all four.

The fifth one does not print, and it is worth knowing about

A statusLine Emma refused produces a sentence, and config check never asks for it. The report comes back complete and ordinary with no mention of the status line at all. certified: a scratch harness whose settings.json asks for an inline jq pipeline prints a nineteen-line report in which grep -ci status finds nothing. The files page has the call graph. The note does reach an interactive run through Term::warn; unverified that it is legible there.

Two failures that are not configuration at all

Approval. If Emma keeps asking about something you granted, the rule may be right and simply not matching. That is Consent & permissions, not this chapter. And the gate is a consent interface rather than a sandbox: it enforces nothing a tool does not honestly declare, and Bash can do anything.

An unknown /word. It is not an error and not a missing command. Anything that is not a known command file passes through to the model as ordinary text, which is indistinguishable from a command that "did nothing" if you were expecting an expansion.

What this page did not settle

  • The shadowed-command note. The table above lists the four loaded-but-inert cases config check prints. Three were seen; a project command shadowed by a built-in was not. unverified. Settle it with a commands/exit.md in a scratch harness.
  • Everything downstream of loading. This chapter ends where a value reaches the loop. Whether a permission rule then fires, whether a hook then blocks, and whether a delegated agent then runs are three other chapters, and nothing on this page called a model. unverified here by construction.
