emma verify, and why the author cannot write these receipts

Records & house rules emma verify

Every required row of the parity ledger wants an independent review, and the implementer writing their own is the self-certification the whole scheme exists to refuse. This command fetches somebody else: a fresh model, given one row and the tree, briefed to disprove it.

crates/emma/src/verify.rs, and run_verification in crates/emma/src/main.rs

Why a command rather than a person

On 2026-08-23 nine defects were found in this codebase in one day. Every one came from an independent reviewer and none from the author: a host grant that silently covered wherever a page redirected to, a resume that reported correct answers as failures, three assertions that could not fail, and a configuration key that did nothing with no way to discover it. That is not a comment on the author’s care. It is what it costs to check your own work: you re-read the argument you already made.

So the reviewer has to be someone else, and there are roughly a hundred rows to get through. A command is the only shape that scales.

The brief is the product

A reviewer told to check a row agrees with it. The brief instead says to assume the implementer believes the row is finished and to find evidence that it is not, and then asks the questions that have actually found things here. First among them: take each test the row names, and say what one line changed in the production code would leave it green. Three false receipts were found by that question in a single day. It also asks for file:line on every claim, and says an answer without any is unusable. tested crates/emma/tests/verify.rs the_brief_asks_a_reviewer_to_disprove_rather_than_confirm asserts on the text, because here the text is the mechanism.

What a verdict is allowed to mean

Three answers, and only one of them closes a row.

VerdictMeansCloses the row
UPHELDthe claim holds and the evidence named really defends ityes
OVERSTATEDthe claim is true and the evidence named does not defend itno
REFUTEDthe claim itself is wrongno

OVERSTATED leaves a row open even when the behaviour it describes may be correct. It stays open anyway: a row whose evidence does not defend it is a false receipt, and a gate that accepted those would be measuring paperwork rather than the tree.

The verdict is the last one in the report, not the first. A model that reasons out loud names several on its way to one, and reading the first turns a thought into a conclusion in the closing direction. tested crates/emma/tests/verify.rs the_last_verdict_wins_and_a_missing_one_is_not_a_pass, which also pins the third case: a reviewer that ends with no verdict line at all is recorded as exactly that, rather than smoothed into a failure. Saying the row is wrong and not answering are different things to whoever reads the receipt next.

The fingerprint is certified, not believed

A receipt is dated by a hash of the production tree, and this command needed its own implementation of one. That function’s history is a list of subtle wrong answers: it once hashed HEAD’s sha, so writing a receipt invalidated every receipt; then HEAD-plus-diff, so a receipt went stale at the moment it was committed; and it once missed a staged file entirely, fingerprinting a tree with an extra production module in it identically to a clean one.

A second implementation reasoned about rather than compared would be the next entry on that list. certified the_rust_fingerprint_agrees_with_the_python_authority runs the real script against this repository and compares the two values. They agree. If they ever stop, the Python one is the authority and the Rust one is what changes; the failure message says so. The skip is real and reported: the script is a user-level skill, so a checkout elsewhere has nothing to compare against, and saying so beats passing in silence.

Each reviewed row spends money

Each row is a full agent run with tools, so a default that swept the ledger would turn a curious first command into a bill nobody chose. --limit defaults to five, --dry-run lists what would be reviewed and reaches no model, and the run says how many rows it is leaving behind rather than quietly stopping at the cap.

unverified How good these reviews are. One live run against claude-opus-5 read the module, the tests, the mutation spec and the receipt before answering, which is the behaviour the brief asks for. One run is not a measurement, and nothing yet compares a model’s verdict against a review a human already trusted. What would settle it: select the ledger row IDs whose defects were first found by hand, preserve those human verdicts as the answer key, then run emma verify --rows ID1,ID2 --limit 2 with the intended reviewer model. Score each final verdict against the answer key and retain every receipt. Repeat on a second reviewer before claiming a rate. Each selected row is a billed model run, so this was not run here.

unverified Reviews are sequential. Running several at once is the obvious next thing and is not done: the terminal is one terminal, and interleaved transcripts would make a review nobody can follow, which is a receipt nobody believes. What would settle it: define one transcript sink per row, dispatch two fixed dry fixtures concurrently, assert each sink contains only its own row ID and complete report, then compare wall time with the sequential run. Do not enable billed concurrency until that no-interleaving test passes.
