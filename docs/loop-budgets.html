The agent loop

Budgets, and three token numbers

The agent loop One turn Failure The memo Endings The kick Budgets Done Seams

Five bounds, three token numbers that are not each other, and one meter that a delegated run can reach. The bounds are separate because they fail differently: a model calling one cheap tool forever is caught by iterations and not by tokens, and a model reading enormous files is caught by tokens and not by iterations.

crates/emma/src/agent.rs — Budgets, Spend, cost_tokens

The five

BoundDefaultShapeWhat it bounds
max_iterations 60 ceiling, tested before the call Model calls in one goal. A run never makes more than this many.
max_tokens 500,000 tripwire, tested after the call What one goal may spend, weighted by price.
wall_clock 30 min tripwire, tested at the top of an iteration When the loop will decline to start another iteration.
max_kicks 3 ceiling Nudges after the model stops without claiming completion.
max_context 120,000 threshold, triggers compaction How large one request's input may get. The only bound here that is about the session rather than the goal. 
// crates/emma/src/agent.rs
impl Default for Budgets {
    fn default() -> Self {
        Self {
            max_iterations: 60,
            max_tokens: 500_000,
            wall_clock: Duration::from_secs(30 * 60),
            max_kicks: 3,
            max_context: 120_000,
        }
    }
}

crates/emma/src/agent.rs — Budgets

Ceiling, tripwire, threshold

The three shapes are not interchangeable and the code says which is which at each site. max_iterations is tested at the top of the loop before anything is sent, so it is a ceiling: a run never makes more calls than that. max_tokens is tested after a call returns, so the call that crosses the line is paid for in full. wall_clock is tested at the top of an iteration and bounds when the loop will decline to start another one, not how long a goal can take. max_context is neither: passing it triggers compaction rather than an ending.

The token budget is a tripwire, not a ceiling

spend.get() > max_tokens is tested after the call returns, so the overshoot is bounded only by how large one request can be. A 500,000 budget stopped a real run at 579,565. certified. The session file is ~/.emma/sessions/sess-1786385316950-34808.jsonl; grep -o '"tokens":[0-9]*' over it prints "tokens":519662 and "tokens":579565, and the file holds two goal_finished records. Run at commit a3eba74 on the owner's machine. The same figure is quoted in Budgets::max_tokens's doc and in a test comment; those are attributions to this run rather than independent evidence.

The mechanism is covered. tested the_token_budget_stops_the_loop_and_the_run_is_charged_for_what_it_spent sets a budget of 15, scripts two calls costing 10 each, and asserts the outcome is Ending::Tokens with 20 spent, an overshoot of one call, and that the session log records the 20 rather than recording an aborted run as free.

Making it a true ceiling would mean gating on an estimate of the request before sending it, and the only estimator available under-counts. A gate built on it refuses calls that would have fit and still overshoots on the ones it lets through, while sounding exact. So the wording admits what the check does, and there is a test asserting the message says "after". Promoting this to a measured pre-call headroom check is item 0 of notes/plans/loops-stage-1.md and item 20 of notes/improvements.md. It matters most for unattended runs, where the person who set the budget is no longer watching the meter.

Three token numbers, three jobs

Every model call produces three different token figures, and assuming any two are the same is how this project got a budget that fired on the length of the conversation instead of on the bill.

NumberArithmeticJob
cost_tokens(usage) input + 1.25×cache_write + 0.1×cache_read + output The only number max_tokens is tested against. Weighted, because a cache read is billed at a tenth of what it weighs.
billable_total_tokens() the provider's own unweighted total Logged raw beside the four provider fields. Answers "how much context did this call carry", which is a different question.
billable_input_tokens() the provider's reported input for the call Stored as last_input and tested against max_context to decide compaction. Measured, so it includes the system prompt and the tool schemas. 
// crates/emma/src/agent.rs
/// Tokens weighted by what they cost, which is what a budget should count.
///
/// The multipliers are the provider's: a cache read is billed at 0.1× and a
/// cache write at 1.25×, and `Usage::billable_total_tokens` deliberately counts
/// neither — it answers "how much context did this call carry", which is a
/// different question and the right one for the field it is on. Emma asks both:
/// the size question decides compaction, and this one decides the budget. See
/// [`Budgets::max_tokens`] for what went wrong when one number answered both.
///
/// Integer arithmetic, so a cache read under ten tokens weighs nothing. At the
/// scale a budget is set in, that is not a rounding error worth a float.
fn cost_tokens(u: &emma_llm::Usage) -> i64 {
    u.input_tokens
        + (u.cache_creation_input_tokens * 5) / 4
        + u.cache_read_input_tokens / 10
        + u.output_tokens
}

The weighting had to arrive when the session started carrying its whole conversation. At a 100,000 token context every call charges roughly 100,000 against an unweighted cap, so a 500,000 default fires five calls into a barely-started goal while the actual bill for those five calls is a few cents. A cap that fires on how long the conversation is rather than on spend is not what somebody typing --max-tokens is asking for. The provider's own numbers are still logged raw; only the arithmetic that enforces the cap is weighted.

crates/emma/src/agent.rs — Budgets::max_tokens, cost_tokens

Both cost_tokens and billable_total_tokens() go into the model_call record, next to the four raw provider fields and the running goal total. So a session file can be read back to answer either question without re-deriving the weighting from the code that was in force at the time.

A fourth number that enforces nothing

// crates/emma/src/agent.rs
/// Roughly how many tokens a message list is worth.
///
/// `chars / 4`, the same conservative ratio `emma-llm`'s packer uses to decide
/// whether a prefix is worth a cache breakpoint, and documented there as
/// under-counting what the provider bills. It is used here for two things that
/// tolerate it — deciding *how much* to drop once a measured number has already
/// said dropping is necessary, and standing in for that measurement on the one
/// call of a process that has none. It is never what fires a budget.
fn estimate(messages: &[Message]) -> i64 {
    let chars: usize = messages.iter().map(|m| m.content.wire_len()).sum();
    (chars / 4) as i64
}

Three callers: Agent::estimated_context, which is what /compact and the arrival warning quote; compact_if_needed, when no measured number exists yet; and compact, to size chapters against each other and to report a before and after. It never decides that a budget was exceeded.

The meter, and why it is not a local

// crates/emma/src/agent.rs
/// The token meter one goal is charged against, shared with anything it
/// delegates to.
///
/// **Why it is not a local.** `run_goal` kept `let mut tokens` and tested it
/// after every call, which is exactly right for a loop that is the only thing
/// spending. A delegation is a second loop spending the same budget, and it
/// cannot reach a local — so the owner's ruling that a subagent spends the
/// parent's budget is either this type or an `if call.name == "Delegate"` in
/// `run_tool_call` adding the tool's self-reported cost. The second is the loop
/// branching on a tool's identity, which the module doc forbids and which this
/// project has already paid to remove twice.
///
/// **The parent link, and why `set` does not follow it.** A nested run gets a
/// meter of its own whose every `add` also lands on its parent's, so the sub's
/// spend charges the parent as it happens and the parent's `tokens > max_tokens`
/// test sees it on its very next iteration. `set` is the per-goal reset and
/// stays local: a nested `run_goal` opening its own goal would otherwise zero
/// the meter of the goal that is paying for it.
#[derive(Debug, Default)]
pub struct Spend {
    counted: std::sync::atomic::AtomicI64,
    parent: Option<Arc<Spend>>,
}

impl Spend {
    pub fn new() -> Arc<Self> {
        Arc::new(Self::default())
    }

    /// A meter of its own that also charges `parent`.
    pub fn child(parent: &Arc<Self>) -> Arc<Self> {
        Arc::new(Self {
            counted: std::sync::atomic::AtomicI64::new(0),
            parent: Some(parent.clone()),
        })
    }

    /// Charge, and answer what this meter now reads.
    pub fn add(&self, tokens: i64) -> i64 {
        if let Some(parent) = &self.parent {
            parent.add(tokens);
        }
        self.counted.fetch_add(tokens, Ordering::SeqCst) + tokens
    }

    pub fn get(&self) -> i64 {
        self.counted.load(Ordering::SeqCst)
    }

    /// The per-goal reset. Local by design — see the type's doc.
    pub fn set(&self, tokens: i64) {
        self.counted.store(tokens, Ordering::SeqCst);
    }
}

add charges the parent first and recurses, so a chain of nested runs charges every ancestor. It returns this meter's own new reading rather than the parent's, which is what the model_call record shows as goal_total_so_far. set writes only this meter, so a nested goal cannot zero the goal paying for it. get is what the budget test reads, rather than the value add returned, because a tool call earlier in the same turn may have been a delegation and what bounds this goal is everything charged to it.

The warning before the first call

// crates/emma/src/agent.rs
fn warn_if_the_budget_is_nearly_spent_on_arrival(&self) {
    let carried = estimate(&self.conversation());
    if carried <= 0 || carried * 4 < self.s.budgets.max_tokens {
        return;
    }
    self.s.term.warn(&format!(
        "this goal opens with roughly {carried} tokens of conversation behind it, so the \
         {} token budget is about {} model calls at that size. Raise it with --max-tokens, \
         lower --max-context, or start a new session.",
        self.s.budgets.max_tokens,
        (self.s.budgets.max_tokens / carried.max(1)).max(1)
    ));
}

The trigger is carried * 4 >= max_tokens, so it fires when the budget is worth about four calls at the size the conversation already is. At the defaults that is roughly 125,000 estimated tokens of conversation. The number in the sentence is an estimate and is described as "roughly", and it is not what any budget is tested against.

crates/emma/src/agent.rs — Agent::warn_if_the_budget_is_nearly_spent_on_arrival

max_context is what keeps max_tokens reachable in a long session: input per call is bounded by compaction, so the number of calls a goal gets is bounded below by roughly max_tokens / max_context, four at the defaults, and in practice far more, because most calls sit nowhere near the cap. Raising the context cap without raising the token budget buys context by spending calls.

crates/emma/src/agent.rs — Budgets::max_context

The context cap, and the functions it drives

Compaction belongs to Sessions & context, which is where the summary format and the fold that replays it are described. Its code lives in agent.rs, so what follows is what the loop does with it and where each function fits. 

// crates/emma/src/agent.rs
fn compact_if_needed(&mut self, measured: Option<i64>, why: &str) {
    let cap = self.s.budgets.max_context;
    if cap <= 0 {
        return;
    }
    let size = measured.unwrap_or_else(|| estimate(&self.conversation()));
    if size <= cap {
        return;
    }
    // Half the cap rather than all of it: the goal now running needs room
    // to work in, and compacting to exactly the limit would mean compacting
    // again on the next call.
    let target = (cap / 2).max(1);
    // Measured once per chapter rather than once per step. Re-summing the
    // whole conversation on every iteration of the loop below is quadratic
    // in a list whose elements are file contents.
    let sizes: Vec<i64> = self
        .chapters
        .iter()
        .map(|c| estimate(&c.messages))
        .collect();
    let mut remaining: i64 = sizes.iter().sum();
    let mut take = 0;
    while take < sizes.len() && remaining > target {
        remaining -= sizes[take];
        take += 1;
    }
    // **The returned reason used to be dropped here.** `/compact` explains
    // itself and the threshold path did not, so a conversation over its cap
    // with nothing left to summarise — one enormous goal, or a history
    // already reduced to summaries — grew on every single call in silence
    // until the token budget or a provider 400 ended it. The user's first
    // sign was the run stopping.
    if let Compacted::Nothing(reason) = self.compact(take, size, why) {
        if !self.said_compaction_stuck {
            self.said_compaction_stuck = true;
            self.s.term.warn(&format!(
                "this conversation is over the context limit and compaction cannot \
                 shrink it: {reason}. Every request from here is larger than the cap, \
                 and the run will end on a budget or a provider error rather than on \
                 the goal. `/clear` starts a fresh conversation; a smaller goal would \
                 also fit."
            ));
        }
    }
}

cap <= 0 disables compaction entirely, which is the escape hatch for a run that wants none. The trigger is measured whenever a measurement exists: last_input, the provider's own input count for the previous call. The estimate stands in for exactly one case, the first check of a goal on a process that has not called the model yet, which is a resume into a large session. The tail used to drop the Compacted result, so a conversation the cap could not shrink grew in silence until a budget or a provider error ended the run; it now warns once per session when compaction answers Nothing, naming the reason and /clear. The argument, and the test, are on Compaction.

crates/emma/src/agent.rs — Agent::compact_if_needed

It is called from two places in run_goal: once before the first request of a goal, with None, so a goal never opens already over the cap; and once per iteration between the budget tests and the request, with last_input, so the request that goes out is the compacted one.

crates/emma/src/agent.rs — Agent::run_goal

The rest of the compaction code covers as follows, each in one line. Agent::compact is the single implementation: it replaces the oldest n chapters with their summaries, refuses when the replacement would not be smaller, writes the compacted record the fold replays, and narrates itself on the terminal unless the caller was /compact. Agent::compact_now is the user-facing door, counting every finished goal or every one but the last, and returning a Compacted::Nothing with a reason when there is nothing to do. summarise turns one chapter into two messages, the goal and the answer, with COMPACTED_NOTE appended. COMPACTED_NOTE is the sentence telling the model that the tool results are gone and to read anything it needs again. Agent::clear drops the conversation without ending the session, returning a counted Cleared and writing a cleared record the fold honours, and it drops an unspent Resumed as well while keeping turn_seq, because turn ids must stay unique inside a session file that is not being cleared.

crates/emma/src/agent.rs — Agent::compact, Agent::compact_now, summarise, COMPACTED_NOTE, Agent::clear, Compacted, Cleared
A compaction that would grow the conversation is refused

compact compares the estimated size of the replacement against what it replaces and returns Compacted::Nothing when the replacement is not smaller. The two reasons it can give are different sentences, because the first live run of /compact said "already summarised" about two goals that plainly were not: those goals were four words long and COMPACTED_NOTE is around three hundred characters, so the replacement was larger than what it replaced. The sentence was true of the arithmetic and false about the conversation. observed by whoever ran that first /compact; the transcript is not in this tree, and what survives is the comment written from it and the two-branch code it produced.

What is not verified here

certified The wall clock is a tripwire and is not worded like one. By reading the function: started.elapsed() > wall_clock is tested only at the top of an iteration, and neither tool.invoke nor call_model is wrapped in a deadline, since call_model's select! races the stream against the interrupt only. So wall_clock bounds when the loop will decline to start another iteration, and Ending::Deadline's "hit the 1800s time limit" reads as a ceiling in the way Ending::Tokens was reworded to stop doing. A long tool call is bounded by that tool's own timeout; Bash has one, and a tool that has none is bounded by nothing in this file. Flagged, not fixed.

crates/emma/src/agent.rs — Agent::run_goal, Agent::call_model; tools/fs/src/bash.rs

unverified The cache multipliers. 1.25× on a write and 0.1× on a read are the provider's published prices as recorded in the comment, and nothing in this tree checks them against a current price list or an invoice. If they change, the budget silently counts the wrong thing. What would settle it: compare a month of model_call records against the billed amount for the same period.
