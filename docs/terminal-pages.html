Pages inside the frame

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Run control Copying out

Five chords each replace the middle of the frame with a page and nothing else: Alt+, Settings, Alt+m Memory, Alt+h the Harness dashboard, Alt+c Code, and Ctrl+/ Help. The sidebar, the dock and the status row stay exactly where they were, and Esc puts the conversation back with its scroll position intact. A sixth chord, Alt+d, used to do the same for a Data Explorer page. That page was removed 2026-08-27, so the sidebar shows the row as n/a and pressing the chord prints a line saying there is nothing to open. What the pages draw is only what Emma actually has, and each one names in words the panel it is not drawing.

A page is a field on App, not a second application

This section described a design that has been reversed, and saying so is the point of keeping it. The main region’s occupant used to be one value, a Pane enum whose Page variant named Settings, Data Explorer and Memory. Neither enum exists now. What replaced them is one field per page: 

settings_open: bool,
memory: Option<super::memory::MemoryView>,
harness: Option<super::harness::HarnessView>,
help: Option<super::help::HelpView>,
code: Option<super::code::CodeView>,
crates/emma/src/term/app.rs — App's page fields, App::toggle_settings, App::toggle_memory, App::toggle_harness, App::toggle_help, App::toggle_code

Five pages, and Data Explorer is not among them. This paragraph said three until 2026-09-06, when Help and Code landed; the shape it describes did not have to change to take them, which is the argument for the shape. Settings is a bool because its interaction state lives in a SettingsView that is always present. Memory, Harness, Help and Code are Options because each is rebuilt when it opens, so the absence of the value and the absence of the page are the same fact. Each toggle_ clears the other four: one occupant of the main region at a time, which is a rule every page obeys rather than a rule any one page enforces.

What survives the reversal is the part that mattered. App::render lays the frame out first, border, sidebar, dock, hint and status, and only then decides what fills the space between them. A page is not a separate window or a second App, and nothing about the surrounding frame is reachable from a page’s drawing code, which is why a page cannot move the status row by accident.

What the reversal cost is the compile error. The old enum meant a fourth page was a build failure at every site that decided what to draw, rather than a silent fall-through to the transcript. Three independent fields do not give that, and adding a fourth page now means finding the sites by reading. I have not decided whether that trade was worth it. tested: a_page_swaps_the_middle_and_keeps_the_frame_and_the_transcript in crates/emma/src/term/guarantees.rs renders both occupants at the same size and asserts the frame and the transcript survive a page swap. That test still holds and is what the section above rests on.

Two pages were once the same page twice

This is history, and the code it describes is gone. Data Explorer and Memory both read the session store and both drew a captured report with a footer, so they shared one text_page shape taking a title, a subtitle and per-page footer lines. The footer was per page because what each one refused to draw was the part a reader most needed told. The text was one Vec<String> on App rather than one per page, since only one page showed at a time and a second buffer is a second thing to forget to clear.

Data Explorer was removed on 2026-08-27, which took away half the reason for a shared shape, and the pages that remain no longer share one. text_page and show_explorer are not in the tree. Memory has its own MemoryView, Harness its own HarnessView, and each is built by its own module.

crates/emma/src/term/memory.rs — MemoryView; crates/emma/src/term/harness.rs — HarnessView

The snapshot is taken when the page opens, never on paint. Reading the store is a directory walk and real file I/O; the frame repaints on every keystroke, every stream chunk and every resize, so a page that rescanned each time would put that walk on the render path. A table that changed under the reader between two repaints would be worse than one that is plainly as of when it was opened, and the subtitle says “as of opening this page” for that reason.

The page and the command cannot disagree, because there is one implementation. The text comes from a commands::* writer (commands::sessions, kept alive by the emma sessions CLI command now that the Data Explorer page it fed is gone, and commands::memory, both writer-shaped like commands::agents), captured into a string by capture_sessions / capture_memory. The frame paints what the memory command would have printed.

crates/emma/src/commands.rs — sessions, memory, capture_sessions, capture_memory

Headings are styled from shape rather than from a parallel list: an unindented non-empty line is a heading, everything else is data. A list of which lines to embolden, kept beside a writer that emits them, is two things that drift.

What each page will not draw, and says so

Every one of these came from a mockup that had more on it than Emma has behind it. The rule applied throughout: an empty panel invites the reader to assume the number lives somewhere else, so the page says it in words.

PageDrawsRefuses, and says why
Settings The values this run actually resolved, each with where it came from. Seven of the mockup’s panels have nothing behind them yet, and are named. A switch that changes nothing is worse on a settings page than anywhere else, because that is where a user goes expecting their change to take.
Data Explorer (removed 2026-08-27) Drew a real count of real files in the session store: sessions, records, kinds, and any records that could not be read. The query box, typed columns, elapsed time and chart. A query surface over a store with no query engine would have been the most convincing thing on the page and the least real.
Memory What was asked in this project, how many sessions, how many compactions and clears. Similarity scores, an embedding model name, retrieval latency, index coverage. Emma has no embedding index and no retrieval; she keeps a record of what was asked and what happened, which is a real thing to show and a different one.
Harness The mock's full chrome: an action bar, six cards, an event log and a trace band. RUNTIME STATUS is live today, since the binary, the version and the workspace are things Emma knows. The rest of the numbers. ACTIVE RUNS, WORKER POOL, TASK QUEUE, TOOL GATES and RESOURCES render from a HarnessView that is empty until a backend exists, so the cards keep their shape and show honest zeros and one-line dim empty states. Drawing the mock's sample runs as though they were real would be the status bar's own rule broken at page size.
Help help::SECTIONS, scrolled. The chords it prints are the chords bound now, resolved through the keymap rather than typed into the text. Nothing, because there is nothing here that is not Emma's own surface. The page has no second copy of the text to be wrong: emma --help is built from the same constant at call time, so a rebound chord shows up in both and the two cannot drift.
Code An EXPLORER tree of the tracked files, the selected file's contents, and that file's commit history with the patch each commit introduced. Read-only. Editing. There is no cursor and no write path in this stage, and the footer says read-only rather than leaving the reader to find out by pressing a key. F7 and the header's [Editor] button hand the file to the external editor, which is where editing happens.

tested crates/emma/src/term/guarantees.rs each_pages_disclosure_belongs_to_that_page_alone asserts the Memory page carries NO_INDEX on painted cells, and memory_draws_one_input_box_and_says_what_it_cannot_do asserts the search key's honesty notice. The test names on this page when it was written (the_memory_page_says_it_has_no_index_rather_than_inventing_one, the_explorer_page_draws_its_snapshot_and_names_what_it_omits) no longer exist. The Data Explorer page was removed 2026-08-27.

One thing the Harness row does not yet say out loud: the action bar's nine keys are inert. ACTIONS is the mock's pairs in the mock's order — a Run, p Pause, r Resume, x Cancel and five more — and nothing routes any of them. The module that would answer them exists: runctl landed on 2026-09-06 with the verification, the signalling and the detached spawn behind it, and no key on this page reaches it. That is a drawn control that does nothing, which is the defect class this page's own Memory story is about, so it is named here rather than left to be discovered. certified: grep the tree for runctl and the only hit outside the module is its pub mod line in lib.rs.

tested for the Harness row above, since 2026-09-05. each_pages_disclosure_belongs_to_that_page_alone now opens Settings, Memory and Harness: its third arm points the Harness page at an empty session directory and asserts EMPTY_RUNS is on its painted cells and on neither of the other two. That arm needed a seam (App::set_harness_dir) before it could be honest, because the page reads a private field that otherwise resolves to the real ~/.emma/sessions — an assertion about the developer's machine rather than about the page. Removing the empty-state render from harness.rs turns the arm red, which is what I checked before moving this chip.

The removed Data Explorer counted through SessionLog::read_reporting rather than read, so a session with unreadable records was reported as damaged rather than counted as clean. The emma sessions command, which shares the same writer, still counts this way: an explorer that tallied only what parsed would describe a damaged library as a tidy one.

Help, which is the same text --help prints

Ctrl+/ opens the Help page, and ? at an empty prompt does the same. It is checked first in the page reader, before every other page's key, so it opens over whatever else is up. The page holds no text of its own: HelpView is a scroll offset and two numbers the last paint discovered, and the rows are built from help::SECTIONS at paint time because they depend on the width. A stored copy would be the second source of truth the module exists to avoid.

The interesting half is one file over. cli.rs no longer holds the session help text at all. emma --help is built at call time from the same SECTIONS the page draws, so a rebound chord shows up in --help and the page cannot drift from the terminal output. A chord in the text is an Entry keyed by Key::Bound(Action) rather than a literal, which is what makes that true: the keymap resolves it when it is drawn. tested — the key seam and both renderings are covered, and a_rebound_chord_reaches_both_renderings installs a keymap and asserts the new spelling appears in the page and in the plain text.

crates/emma/src/term/help.rs — SECTIONS, HelpView, handle_key, plain; crates/emma/src/cli.rs; crates/emma/src/term/input.rs — run_page_key

Code, and the chord that stopped launching an editor

Alt+c opened the configured editor on the project until 2026-09-06. It now opens a page, on the owner's ruling, and the editor is F7 or the header's [Editor] button inside that page. Nothing about the editor launch was thrown away: the same usertools::launch call runs, so the tools.editor setting, the $VISUAL and $EDITOR fallbacks and the PATH probe all stay live and reachable. One row in the sidebar, two doors.

Three regions: an EXPLORER tree on the left, and on the right a header over either the open file's contents or its commit history with the patch the selected commit introduced. F3 and the clickable FILE · HISTORY tabs move between the two. Tab moves between panes, Enter opens, and the footer says read-only in as many words.

Two numbers bound what the page will take on. MAX_FILE is 1 MiB, past which a file is not read into the viewer, and MAX_PATHS is 20,000 entries in the tree. Raw file bytes are sanitised before they reach a cell, because a TAB in a cell is the column-budget class this repository has already fixed once elsewhere.

The page is read-only and the write path is not, which matters for whoever adds one: code_git::joined puts a file back with the line ending the file itself had, CRLF or LF, and the trailing-newline shape it had when it was opened. A save that normalises to LF on a Windows checkout rewrites every line of the file and calls it an edit. tested — making detect_line_ending always answer LF, and making joined always append a trailing newline, each turn the round-trip tests red.

crates/emma/src/term/code.rs — CodeView, takes_key, handle_key, click, CodeAction::LaunchEditor, EDITOR_LABEL; crates/emma/src/term/code_git.rs — MAX_FILE, MAX_PATHS, paths, read_file, detect_line_ending, joined, history, diff_at; crates/emma/src/term/frame.rs — Frame::launch_tool

certified against this repository on 2026-09-06, Windows: the real code_git answered paths with 355 entries in 16.2 ms and read a file in 0.68 ms; the tree nested correctly, Windows separators came back as /, and no escape byte reached a cell over a real patch. The same run measured git log --follow and git show at 32 ms and 20 ms on a 289-commit repository, and the report's wider range is 17 to 475 ms.

One module beside it is a declared stub and not a defect: crates/emma/src/term/code_lsp.rs is the bridge between this page's editor and the language servers the model's tools already run. It is blocked on client methods that do not exist yet, and its own doc says not to stub a second language table in this crate to unblock it. It is named here so that a reader who finds an empty module knows it is waiting rather than forgotten.

That measurement is the reason the page has sinks rather than return values. History and diff run on a worker and hand their answers back through two setters, because a keystroke handler that waits on a process is an event loop that has stopped. Anybody simplifying it back to a synchronous call needs the 475 in front of them.

Getting in, and getting back out

Four of the five chords are the tools’ own, intercepted in Frame::launch_tool before they reach usertools::launch: Alt+,, Alt+m, Alt+h and, since 2026-09-06, Alt+c. Alt+d falls through to usertools::launch, which refuses it, because no page has taken that key since the Data Explorer was removed. Ctrl+/ is not a tool chord at all and is answered by the page reader directly. Where a page does open, the frame already knows the session path because the status row shows it, and the page is handed a finished snapshot.

Tool::Code stays out of in_app() even though Alt+c now opens a page, and that is not an oversight. The predicate governs whether plan_code's settings chain and PATH probe stay reachable, and they have to, because F7 inside the page still calls them.

crates/emma/src/term/frame.rs — Frame::launch_tool, Frame::leave_page

Esc is routed after the menu, not before. With the command menu open, Esc dismisses the menu and keeps the typed line, which is what it has always done; only when no menu is up does it reach leave_page. That function answers whether it did anything, so a caller can tell “handled” from “pass it on”. An Esc swallowed while no page was showing would quietly take the key away from whatever else wanted it.

crates/emma/src/term/input.rs — the reader loop, below menu_key

The transcript is not discarded while a page is up. It is not painted, so returning costs nothing and loses no scroll position.

Why these three stopped launching programs

Settings opened ~/.emma/settings.json in the configured editor and the Data Explorer opened the file manager on ~/.emma. Both were correct as built. The original comment argued that “the tool’s promise is edit your settings, not open your chosen editor”, and that was not what was wanted. The owner reported Alt+, opening VS Code three times before it was ruled on. That is a reversal, not a bug found.

Memory is the one that was a defect. It had declared in_app since the tools were written and nothing routed it: pressing the chord reached usertools::launch, which refused it with the words “the frame owns the m key”, a key the frame had never claimed. The sidebar advertised a chord that only produced a warning. That is why Tool::in_app and Tool::routed are now two predicates: one says a tool runs inside Emma, the other says the frame actually takes its key, and the gap between them is where this hid. The user tools page has the catalogue.

Looking at them

An ignored test prints the Settings screen, for the question the assertions cannot answer. Does this read well: 

cargo test -p emma --lib term::app::tests::dump_the_settings_screen -- --ignored --nocapture

It asserts nothing, and what it shows is the cell buffer rather than a console: no colour, no proof that the chord arrived, no tearing. Everything it draws is already covered by the tests above it. tested: Memory and Harness have the same dumps now — dump_the_memory_screen and dump_the_harness_screen, ignored, in the same module. Both are driven off the tempdir rigs the page tests already use, so each prints a screen with data in it rather than an empty one, and neither reads a store belonging to anybody. They assert nothing either; looking is the whole job.

What has not been checked

unverified Nobody has pressed these chords on a real terminal and reported back. Every assertion above is against ratatui’s TestBackend, which is a cell buffer and not a console: it cannot tell you that Windows Terminal delivered Alt+, as the frame expects, or that the page painted without tearing. Frame cannot be constructed in a test binary at all, so the chord path from key press to painted page is genuinely uncovered. What would settle it: open a framed session, press each of the five chords and Esc, and say what appeared. Help and Code, which landed on 2026-09-06, have never been drawn on a console at all: what exists for each is a Buffer, and a cell buffer is not a console. This repository has shipped a fully-tested scrollback defect twice out of exactly that gap.

unverified Behaviour at very narrow widths is untested for every page named in the lede. Settings at 80×24 is covered by a_page_that_runs_out_of_room_says_how_much_is_missing in term/guarantees.rs; Memory compresses rather than clips. At 40 columns specifically, nobody has rendered each remaining page and decided whether clipping or wrapping is wanted. What would settle it: render each page at 40 columns on a TestBackend and inspect the painted cells.

unverified Ctrl+/ may not arrive as Ctrl+/. Some terminals report that chord as 0x1F, as Ctrl+_ or as Ctrl+7, and the reader folds all three into one action. The folding is copied from the fork and believed rather than measured: no terminal on either machine reports it the other way, so the arm is exercised only by a unit test that feeds the event its author assumed. What would settle it: a keystroke dump on macOS Terminal.app, iTerm2 and Windows Terminal, recording which of the three each actually sends. ? at an empty prompt opens the same page and does not depend on any of this.

unverified The Code viewer's column arithmetic on wide characters. Rows go through fit, which is column-aware, so a CJK line should not overrun its pane, and there is no cursor in this stage so the char-versus-column desynchronisation the fork hit cannot bite here. It becomes live the moment a cursor is added. What would settle it: open a file with a CJK line in the page on a real terminal.

unverified Whether git ls-files at 16 to 46 ms is acceptable synchronously when the Code page opens. It runs once, on the same footing as the Harness page's read. On a monorepo it will be worse, and MAX_PATHS bounds the vector rather than the git call. What would settle it: time git ls-files on a repository with more than 100,000 tracked files; past roughly 150 ms the page open needs the same worker treatment the history already has.

unverified The keymap is one process-wide cell, and three test modules install into it on different threads of one cargo test process with nothing serialising them. A green run is not proof they cannot interleave; it has not flaked in about ten runs here. What would settle it: a shared test lock in keymap.rs that all three take.
