Pages inside the frame

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Copying out

Alt+,, Alt+d and Alt+m each replace the middle of the frame with a page and nothing else. The sidebar, the dock and the status row stay exactly where they were, and Esc puts the conversation back with its scroll position intact. All three used to launch a program on the machine, or claim they would. What they draw is only what Emma actually has, and each one names in words the panel it is not drawing.

One field, not a second application

The main region’s occupant is a single value on App: 

pub enum Page { Settings, DataExplorer, Memory }

pub enum Pane {
    #[default]
    Chat,
    Page(Page),
}
crates/emma/src/term/app.rs — enum Pane, App::render

App::render lays the frame out first — border, sidebar, dock, hint, status — and only then matches on self.pane to decide what fills the space between them. So a page is not a window, not a mode and not a second App. Nothing about the surrounding frame is reachable from a page’s drawing code, which is why a page cannot accidentally move the status row.

Chat is a named variant rather than the absence of a page. A fourth page added tomorrow is a compile error at every site that decides what to draw, instead of falling silently through to the transcript. tested crates/emma/src/term/guarantees.rs crates/emma/src/term/guarantees.rs a_page_swaps_the_middle_and_keeps_the_frame_and_the_transcript renders both occupants at the same size and asserts the frame and transcript survive a page swap (the old name was the_pane_seam_paints_the_chat_view_and_leaves_the_frame_alone).

Two of the three are the same page twice

The Data Explorer and Memory both read the session store and both draw a captured report with a footer. text_page is that shape, taking a title, a subtitle and the footer lines; the footer is per page because what each one refuses to draw is the part a reader most needs told. The text itself is one Vec<String> on App, not one per page — only one page shows at a time, and a second buffer would be a second thing to forget to clear.

crates/emma/src/term/app.rs — App::text_page, App::show_explorer, App::show_memory

The snapshot is taken when the page opens, never on paint. Reading the store is a directory walk and real file I/O; the frame repaints on every keystroke, every stream chunk and every resize, so a page that rescanned each time would put that walk on the render path. A table that changed under the reader between two repaints would be worse than one that is plainly as of when it was opened, and the subtitle says “as of opening this page” for that reason.

The page and the command cannot disagree, because there is one implementation. The text comes from a commands::* writer — commands::sessions and commands::memory, both writer-shaped like commands::agents — captured into a string by capture_sessions / capture_memory. The frame paints what a command would have printed.

crates/emma/src/commands.rs — sessions, memory, capture_sessions, capture_memory

Headings are styled from shape rather than from a parallel list: an unindented non-empty line is a heading, everything else is data. A list of which lines to embolden, kept beside a writer that emits them, is two things that drift.

What each page will not draw, and says so

Every one of these came from a mockup that had more on it than Emma has behind it. The rule applied throughout: an empty panel invites the reader to assume the number lives somewhere else, so the page says it in words.

PageDrawsRefuses, and says why
Settings The values this run actually resolved, each with where it came from. Seven of the mockup’s panels have nothing behind them yet, and are named. A switch that changes nothing is worse on a settings page than anywhere else, because that is where a user goes expecting their change to take.
Data Explorer A real count of real files in the session store: sessions, records, kinds, and any records that could not be read. The query box, typed columns, elapsed time and chart. A query surface over a store with no query engine would be the most convincing thing on the page and the least real.
Memory What was asked in this project, how many sessions, how many compactions and clears. Similarity scores, an embedding model name, retrieval latency, index coverage. Emma has no embedding index and no retrieval; she keeps a record of what was asked and what happened, which is a real thing to show and a different one.

tested crates/emma/src/term/guarantees.rs crates/emma/src/term/guarantees.rs each_pages_disclosure_belongs_to_that_page_alone asserts the Memory page carries NO_INDEX on painted cells, and memory_draws_one_input_box_and_says_what_it_cannot_do asserts the search key's honesty notice. The test names on this page when it was written (the_memory_page_says_it_has_no_index_rather_than_inventing_one, the_explorer_page_draws_its_snapshot_and_names_what_it_omits) no longer exist — the Data Explorer page was removed 2026-08-27.

The Data Explorer counts through SessionLog::read_reporting rather than read, so a session with unreadable records is reported as damaged rather than counted as clean. An explorer that tallied only what parsed would describe a damaged library as a tidy one.

Getting in, and getting back out

The chords are the tools’ own, unchanged: the sidebar advertises Alt+,, Alt+d and Alt+m, and Frame::launch_tool intercepts those three before they reach usertools::launch. The scan happens there — the frame already knows the session path because the status row shows it — and the page is handed a finished snapshot.

crates/emma/src/term/frame.rs — Frame::launch_tool, Frame::leave_page

Esc is routed after the menu, not before. With the command menu open, Esc dismisses the menu and keeps the typed line, which is what it has always done; only when no menu is up does it reach leave_page. That function answers whether it did anything, so a caller can tell “handled” from “pass it on” — an Esc swallowed while no page was showing would quietly take the key away from whatever else wanted it.

crates/emma/src/term/input.rs — the reader loop, below menu_key

The transcript is not discarded while a page is up. It is simply not painted, so returning costs nothing and loses no scroll position.

Why these three stopped launching programs

Settings opened ~/.emma/settings.json in the configured editor and the Data Explorer opened the file manager on ~/.emma. Both were correct as built — the original comment argued that “the tool’s promise is edit your settings, not open your chosen editor” — and simply were not what was wanted. The owner reported Alt+, opening VS Code three times before it was ruled on. That is a reversal, not a bug found.

Memory is the one that was a defect. It had declared in_app since the tools were written and nothing routed it: pressing the chord reached usertools::launch, which refused it with the words “the frame owns the m key” — a key the frame had never claimed. The sidebar advertised a chord that only produced a warning. That is why Tool::in_app and Tool::routed are now two predicates: one says a tool runs inside Emma, the other says the frame actually takes its key, and the gap between them is where this hid. The user tools page has the catalogue.

Looking at them

An ignored test prints all three, for the question the assertions cannot answer. Does this read well: 

cargo test -p emma --lib term::app::tests::show_the_pages -- --ignored --nocapture

It asserts nothing, and what it shows is the cell buffer rather than a console: no colour, no proof that the chord arrived, no tearing. Everything it draws is already covered by the three tests above it.

What has not been checked

unverified Nobody has pressed these chords on a real terminal and reported back. Every assertion above is against ratatui’s TestBackend, which is a cell buffer and not a console: it cannot tell you that Windows Terminal delivered Alt+, as the frame expects, or that the page painted without tearing. Frame cannot be constructed in a test binary at all, so the chord path from key press to painted page is genuinely uncovered. What would settle it: open a framed session, press each of the three chords and Esc, and say what appeared.

unverified Behaviour at very narrow widths is untested for all three pages named in the lede. Settings at 80×24 is covered by a_page_that_runs_out_of_room_says_how_much_is_missing in term/guarantees.rs; Memory compresses rather than clips. At 40 columns specifically, nobody has rendered each remaining page and decided whether clipping or wrapping is wanted. What would settle it: render Settings and Memory at 40 columns on a TestBackend and inspect the painted cells.
