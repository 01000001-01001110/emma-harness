Pages inside the frame

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Run control Copying out

Five chords each replace the middle of the frame with a page and nothing else: Alt+, Settings, Alt+m Memory, Alt+h the Harness dashboard, Alt+c Code, and Ctrl+/ Help. The sidebar, the dock and the status row stay exactly where they were, and Esc puts the conversation back with its scroll position intact. A sixth chord, Alt+d, used to do the same for a Data Explorer page. That page was removed 2026-08-27, so the sidebar shows the row as n/a and pressing the chord prints a line saying there is nothing to open. What the pages draw is only what Emma actually has, and each one names in words the panel it is not drawing.

A page is a field on App, not a second application

This section described a design that has been reversed, and saying so is the point of keeping it. The main region’s occupant used to be one value, a Pane enum whose Page variant named Settings, Data Explorer and Memory. Neither enum exists now. What replaced them is one field per page: 

settings_open: bool,
memory: Option<super::memory::MemoryView>,
harness: Option<super::harness::HarnessView>,
help: Option<super::help::HelpView>,
code: Option<super::code::CodeView>,
crates/emma/src/term/app.rs — App's page fields, App::toggle_settings, App::toggle_memory, App::toggle_harness, App::toggle_help, App::toggle_code

Five pages, and Data Explorer is not among them. This paragraph said three until 2026-09-06, when Help and Code landed; the shape it describes did not have to change to take them, which is the argument for the shape. Settings is a bool because its interaction state lives in a SettingsView that is always present. Memory, Harness, Help and Code are Options because each is rebuilt when it opens, so the absence of the value and the absence of the page are the same fact. Each toggle_ clears the other four: one occupant of the main region at a time, which is a rule every page obeys rather than a rule any one page enforces.

What survives the reversal is the part that mattered. App::render lays the frame out first, border, sidebar, dock, hint and status, and only then decides what fills the space between them. A page is not a separate window or a second App, and nothing about the surrounding frame is reachable from a page’s drawing code, which is why a page cannot move the status row by accident.

What the reversal cost is the compile error. The old enum meant a fourth page was a build failure at every site that decided what to draw, rather than a silent fall-through to the transcript. Three independent fields do not give that, and adding a fourth page now means finding the sites by reading. I have not decided whether that trade was worth it. tested: a_page_swaps_the_middle_and_keeps_the_frame_and_the_transcript in crates/emma/src/term/guarantees.rs renders both occupants at the same size and asserts the frame and the transcript survive a page swap. That test still holds and is what the section above rests on.

Two pages were once the same page twice

This is history, and the code it describes is gone. Data Explorer and Memory both read the session store and both drew a captured report with a footer, so they shared one text_page shape taking a title, a subtitle and per-page footer lines. The footer was per page because what each one refused to draw was the part a reader most needed told. The text was one Vec<String> on App rather than one per page, since only one page showed at a time and a second buffer is a second thing to forget to clear.

Data Explorer was removed on 2026-08-27, which took away half the reason for a shared shape, and the pages that remain no longer share one. text_page and show_explorer are not in the tree. Memory has its own MemoryView, Harness its own HarnessView, and each is built by its own module.

crates/emma/src/term/memory.rs — MemoryView; crates/emma/src/term/harness.rs — HarnessView

The snapshot is taken when the page opens, never on paint. Reading the store is a directory walk and real file I/O; the frame repaints on every keystroke, every stream chunk and every resize, so a page that rescanned each time would put that walk on the render path. A table that changed under the reader between two repaints would be worse than one that is plainly as of when it was opened, and the subtitle says “as of opening this page” for that reason.

The page and the command cannot disagree, because there is one implementation. The text comes from a commands::* writer (commands::sessions, kept alive by the emma sessions CLI command now that the Data Explorer page it fed is gone, and commands::memory, both writer-shaped like commands::agents), captured into a string by capture_sessions / capture_memory. The frame paints what the memory command would have printed.

crates/emma/src/commands.rs — sessions, memory, capture_sessions, capture_memory

Headings are styled from shape rather than from a parallel list: an unindented non-empty line is a heading, everything else is data. A list of which lines to embolden, kept beside a writer that emits them, is two things that drift.

Help, which is the same text --help prints

Ctrl+/ opens the Help page, and ? at an empty prompt does the same. It is checked first in the page reader, before every other page's key, so it opens over whatever else is up. The page holds no text of its own: HelpView is a scroll offset and two numbers the last paint discovered, and the rows are built from help::SECTIONS at paint time because they depend on the width. A stored copy would be the second source of truth the module exists to avoid.

The interesting half is one file over. cli.rs no longer holds the session help text at all. emma --help is built at call time from the same SECTIONS the page draws, so a rebound chord shows up in --help and the page cannot drift from the terminal output. A chord in the text is an Entry keyed by Key::Bound(Action) rather than a literal, which is what makes that true: the keymap resolves it when it is drawn. tested — the key seam and both renderings are covered, and a_rebound_chord_reaches_both_renderings installs a keymap and asserts the new spelling appears in the page and in the plain text.

Code, and the chord that stopped launching an editor

Alt+c opened the configured editor on the project until 2026-09-06. It now opens a page, on the owner's ruling, and the editor is F7 or the header's [Editor] button inside that page. Nothing about the editor launch was thrown away: the same usertools::launch call runs, so the tools.editor setting, the $VISUAL and $EDITOR fallbacks and the PATH probe all stay live and reachable. One row in the sidebar, two doors.

Three regions: an EXPLORER tree on the left, and on the right a header over either the open file's contents or its commit history with the patch the selected commit introduced. F3 and the clickable FILE · HISTORY tabs move between the two. Tab moves between panes and Enter opens.

The keys, in full, because most of them appear nowhere else on this site. Tab moves between the tree, the body and the ask box at the foot of the page; Enter opens a file from the tree and starts editing in the body; F2 or Ctrl+s saves; F3 switches between the file and its history; F4 copies; F5 asks the language server what is under the cursor and F6 asks where it is defined; F7 hands the repository to the configured editor; F8 asks where the symbol under the cursor is used and F10 asks what the open file contains, both of which draw the places panel below; Ctrl+space and F9 both ask for a completion list; Alt+c closes the page, which its own footer says in every mode. A definition in another file opens that file at the line.

The six function keys that ask a server are function keys for one reason: inside the document every letter is text, so a mnemonic could not reach them. F8 and F10 are the pair rather than the two after F6, because F7 already opens the outside editor and F9 already asks for a completion, and moving either would change a key somebody has learned. Completion has two spellings because one of them does not survive every terminal: Ctrl+space is the chord every editor uses and some terminals swallow it, and F9 is the one that always arrives. Both are on the help row, so nobody has to discover the second after the first appeared to do nothing.

That second spelling was advertised for a fortnight and did nothing. takes_key refused every Ctrl chord but the save, so the completion arm below it was unreachable, while the help row, the module header and a commit message all named the key. The fix needed both halves: relaxing the predicate alone would have let the chord fall into handle_key's blanket Ctrl arm and saved the file when somebody asked for a completion. tested: ctrl_space_asks_for_a_completion_and_does_not_save asserts both halves in one test. tested — f8_asks_where_a_symbol_is_used_and_f10_what_the_file_contains asserts both from the tree and from inside the document, and the_list_keys_refuse_in_words_when_there_is_no_file_to_ask_about asserts the refusal reaches the status row rather than being silent.

The page edits and saves since 2026-09-06. Enter on the body starts editing and the header says EDIT; Ctrl+s and F2 both save, and the header names both because some terminals eat Ctrl+s for flow control; F4 copies the selection or the whole file; a paste lands in the editor; the mouse selects text in the document and a release copies it; Esc leaves the editor and a second Esc leaves the page, guarded once by an unsaved warning.

A file whose bytes this page cannot reproduce is read-only, and the header says why. Three causes: the read was sanitised (a TAB or a control byte in the source), the file has mixed line terminators, or it was rewritten underneath the read. The argument is the column-budget rule read backwards, and it is worth stating because the next person to “fix” the read-only header by removing the lock will detab somebody's source. certified against real files through the real writer: a CRLF file saved byte-identical, a line inserted mid-file carrying CRLF, no invented trailing newline, and this repository's own docs/architecture.html round-tripped whole.

Two numbers bound what the page will take on. MAX_FILE is 1 MiB, past which a file is not read into the viewer, and MAX_PATHS is 20,000 entries in the tree. Raw file bytes are sanitised before they reach a cell, because a TAB in a cell is the column-budget class this repository has already fixed once elsewhere.

The write path was built before the page had one, which is why the page could take it unchanged: code_git::joined puts a file back with the line ending the file itself had, CRLF or LF, and the trailing-newline shape it had when it was opened. A save that normalises to LF on a Windows checkout rewrites every line of the file and calls it an edit. tested — making detect_line_ending always answer LF, and making joined always append a trailing newline, each turn the round-trip tests red.

crates/emma/src/term/code_lsp.rs was a declared stub until 2026-09-06 and this paragraph said so. It is the bridge between this page and the language servers the model's tools already run, and it is 2,195 lines that main.rs spawns, of which 1,107 come before the #[cfg(test)] on line 1,108. certified by wc -l crates/emma/src/term/code_lsp.rs and grep -n '#\[cfg(test)\]' on it, 2026-09-06. Nothing on the input path waits for a server: the handle only ever offers a request to a bounded channel, so a busy or dead server means the page lacks decorations rather than pausing. It calls the language table in tools/lsp rather than carrying a second one, which was the thing its stub doc warned against. tested a mutation proving the call into that table is real, among thirty-three in the package's report.

One consequence is worth stating because nothing else on this site does. The page and the model's tools share one server per language, which is deliberate: a second copy of a language server is about a gigabyte of memory, and what you type keeps the server's view current for the model's next call. It also means an unsaved buffer is what the server knows about, so the model can ask a question and get an answer about text that is not on disk. That is usually what you want and is never said out loud anywhere else. certified diagnostics were produced for a buffer deliberately not written to disk, and the file read back byte-identical afterwards.

That measurement is the reason the page has sinks rather than return values. History and diff run on a worker and hand their answers back through two setters, because a keystroke handler that waits on a process is an event loop that has stopped. Anybody simplifying it back to a synchronous call needs the 475 in front of them.

The completion list, and when it opens by itself

Two things open it, and they are different questions. A trigger character is the server’s own claim that something follows it, so it opens a list at once with nothing typed: after a dot the useful answer is the whole set of members. An identifier character opens one only once the word reaches MIN_WORD, which is 3, counted after the character just typed, so the list appears on the third letter. That is later than a graphical editor puts it, and the reason is that here the popup covers the code being written rather than floating over its own layer.

The triggers come from the handshake reply, never from this client. rust-analyzer names . and :; another language’s server names something else, and a hard-coded guess is wrong everywhere the guess does not hold. A server that names none gets no guesses: typing a dot then asks for nothing, and F9 is what remains. tested: a_trigger_character_asks_at_once, an_identifier_asks_only_once_it_is_long_enough_to_narrow (which asserts one and two letters do not ask), and with_no_triggers_named_a_dot_asks_for_nothing.

The popup owns a short list of keys and lets the editor keep every other. Esc closes it, Up and Down move the selection, and Tab and Enter both accept: Tab because it is the habit from every editor, Enter because it is what somebody who has never used one tries. Everything else falls through, which is the rule that keeps this from being the feature people turn off: a popup that swallowed Backspace would strand somebody mid-word. Typing a character both inserts it and narrows the list, and a list nothing matches closes. tested: the_popup_takes_its_own_keys_and_lets_the_editor_keep_the_rest and typing_past_every_match_closes_the_popup.

Narrowing is local. Typing into an open list filters what is already there rather than asking again, because a request per keystroke is what makes an editor feel slow. The exception is a list the server marked isIncomplete: that means it truncated its own answer and expects to be asked once more, so the next character re-queries. tested: typing_into_an_open_list_narrows_it_unless_the_server_wants_re_asking covers both halves in one test.

Asking for a completion needs the document to be being edited, which no other question on this page needs. Every other one answers into a note or a panel; this one answers into a popup whose only exit key belongs to the editor layer. Opened from the tree or over a read-only document it covered the code with nothing to dismiss it, and Esc closed the page out from under it. So outside the editor both keys refuse in words: “press Enter to edit before asking what can be typed”. tested: a_completion_asked_for_outside_the_editor_refuses_in_words asserts the refusal, that no popup opened, and that the same key asks once Enter has started an edit.

An empty answer is a sentence, not an empty box. No items means “nothing to complete here” on the status row and no popup at all. An answer about a line the cursor has since left is dropped rather than applied, for the same reason: it would offer members of whatever was under the cursor a moment ago.

Emma declares snippetSupport: false in the handshake, because a client that cannot expand a placeholder and claims it can inserts push(${1:value}) into somebody's source. A server that sends a snippet anyway is not refused: the candidate is offered as its filter text, so accepting it types push.

Accepting uses the server's replace range only while the cursor is still where it was asked. A completion is computed at one position and the list narrows locally as somebody keeps typing, so by the time Enter lands the cursor has usually moved past where the server was looking. rust-analyzer answers a dot completion with an empty replace range at the request position — certified against 1.94.1 — so applying it after three more letters inserted the candidate and left those three behind: c.pus accepted as push became c.pushpus. Once the cursor has moved, the word before it is used instead, the same fallback a server naming no range at all already gets. tested: a_server_range_is_dropped_once_the_cursor_has_moved_past_it reproduces exactly that rust-analyzer answer and asserts the three typed letters are replaced, not doubled.

Signature help shares the status row rather than opening a second popup. The active signature is flattened to one line with the current argument in square brackets. Brackets rather than a colour, so the marker survives the ASCII skin and a terminal with no colour at all. When the parameter cannot be found inside the signature label, the bare label is drawn: a marker on the wrong argument is worse than none.

The places panel

F8 asks where the symbol under the cursor is used and F10 asks what the open file contains, and both answers land in one panel. They share a type because they share a purpose and a key: both draw as a row you can open, and two nearly identical lists would be two places to fix the next time the opening rule changes.

It draws on the right half of the document when the pane is at least 60 columns wide, and across the whole width below that, because half of a narrow pane is a column of ellipses. The list is a set of destinations rather than an annotation on a line, so unlike the hover and the completion popup it has no line it must stay beside, and keeping the left half clear means the code stays readable while somebody arrows through answers about it. PLACES_MAX_ROWS is 12, and the height of the pane can lower that further.

The header names what was asked and how many came back, which is the whole reason it carries a count: twelve rows out of forty is a different fact from twelve rows. The chosen row is drawn as a styled cell rather than as a colour, the rule every list on this page follows.

The panel takes every key while it is up, the hover popup’s rule rather than the completion popup’s, and for one more reason than the hover has: it is a destination, so Enter belongs to it rather than to the buffer underneath. Arrows move, Enter opens the chosen row, and anything else closes it, which makes leaving the cheapest thing on the page. A row naming the file already open is a cursor move rather than a read. tested — the_places_panel_moves_opens_and_closes asserts the buffer is unchanged by the keys the panel ate, and the_places_panel_is_painted_with_its_count_and_a_marked_row reads the painted cells.

A reference outside the repository root is dropped rather than listed, which is the containment rule the definition jump already follows: offering a row that opens a file the page cannot save is offering a dead end. The comparison uses relative_to rather than strip_prefix, because on Windows the root canonicalises to \\?\E:\… while the server’s URI comes back as E:\…, and the raw comparison drops every hit in the repository instead. The definition jump paid for that one first. Unlike the model-facing tool, which reports outside hits as a count, the page says nothing about what it dropped.

An empty answer is a sentence again: “no results for …” on the status row, and no panel. tested: no_results_is_a_sentence_rather_than_an_empty_panel.

Colour comes from the type-checker, not from a grammar

Code on this page is coloured from textDocument/semanticTokens/full. That is how a // inside a string stays a string: the answer comes from the server that type-checked the file, so nothing here has an opinion about syntax. The alternative was a grammar, which is a dependency per language and a second opinion about the thing this crate exists to ask somebody else.

The legend is read from the handshake, and without it nothing is coloured. The wire sends token numbers, and type 3 is whatever this server put third in its own list; a client with a hard-coded legend colours Rust correctly and Python wrongly, silently. So an empty legend draws plain text rather than colouring by a guessed order, and the request is not even sent. A file with no server behind it is plain text for the same reason. Every character resolves to Role::Text when no token covers it, which is also the answer for ordinary identifiers.

Colour is asked for when the file opens, not on a key: a reader who has to press something to tell a comment from code is a reader looking at white text until they learn the key exists. After that it is re-asked on the same beat the buffer is sent to the server, which the 300 ms typing debounce already governs, so a burst of typing is one request rather than one per keystroke.

The painter finds a line's tokens with two binary searches rather than a filter, and that is a measurement rather than a preference: parse_tokens returns them in wire order, which is line order, so a line's tokens are a contiguous run. Before that the painter asked every token in the file about every cell it drew, which for code.rs is 28,330 tokens against roughly five thousand cells, on every repaint, which is every keystroke. A line with nothing on it and every line when there is no server both give an empty slice, which is what makes the plain-text fallback one branch instead of two.

Six colour roles come out of it: comment, keyword, string, number, type and function. The protocol offers twenty-odd token types and the rest map onto Other, which draws as text: a distinction nobody can see costs and pays nothing. Tokens whose line the buffer no longer has are dropped, because colouring by a stale position is how highlighting ends up half a line out, and tokens belonging to another file are never painted over this one. tested: a_comment_and_the_code_beside_it_are_not_the_same_colour asserts the painted cells differ, which is the only claim that matters, and tokens_for_another_file_are_not_painted_over_this_one covers an answer that arrives about a different file.

Getting in, and getting back out

Four of the five chords are the tools’ own, intercepted in Frame::launch_tool before they reach usertools::launch: Alt+,, Alt+m, Alt+h and, since 2026-09-06, Alt+c. Alt+d falls through to usertools::launch, which refuses it, because no page has taken that key since the Data Explorer was removed. Ctrl+/ is not a tool chord at all and is answered by the page reader directly. Where a page does open, the frame already knows the session path because the status row shows it, and the page is handed a finished snapshot.

Tool::Code stays out of in_app() even though Alt+c now opens a page, and that is not an oversight. The predicate governs whether plan_code's settings chain and PATH probe stay reachable, and they have to, because F7 inside the page still calls them.

crates/emma/src/term/frame.rs — Frame::launch_tool, Frame::leave_page

Esc is routed after the menu, not before. With the command menu open, Esc dismisses the menu and keeps the typed line, which is what it has always done; only when no menu is up does it reach leave_page. That function answers whether it did anything, so a caller can tell “handled” from “pass it on”. An Esc swallowed while no page was showing would quietly take the key away from whatever else wanted it.

crates/emma/src/term/input.rs — the reader loop, below menu_key

The transcript is not discarded while a page is up. It is not painted, so returning costs nothing and loses no scroll position.

Why these three stopped launching programs

Settings opened ~/.emma/settings.json in the configured editor and the Data Explorer opened the file manager on ~/.emma. Both were correct as built. The original comment argued that “the tool’s promise is edit your settings, not open your chosen editor”, and that was not what was wanted. The owner reported Alt+, opening VS Code three times before it was ruled on. That is a reversal, not a bug found.

Memory is the one that was a defect. It had declared in_app since the tools were written and nothing routed it: pressing the chord reached usertools::launch, which refused it with the words “the frame owns the m key”, a key the frame had never claimed. The sidebar advertised a chord that only produced a warning. That is why Tool::in_app and Tool::routed are now two predicates: one says a tool runs inside Emma, the other says the frame actually takes its key, and the gap between them is where this hid. The user tools page has the catalogue.

Looking at them

An ignored test prints the Settings screen, for the question the assertions cannot answer. Does this read well: 

cargo test -p emma --lib term::app::tests::dump_the_settings_screen -- --ignored --nocapture

It asserts nothing, and what it shows is the cell buffer rather than a console: no colour, no proof that the chord arrived, no tearing. Everything it draws is already covered by the tests above it. tested: Memory and Harness have the same dumps now — dump_the_memory_screen and dump_the_harness_screen, ignored, in the same module. Both are driven off the tempdir rigs the page tests already use, so each prints a screen with data in it rather than an empty one, and neither reads a store belonging to anybody. They assert nothing either; looking is the whole job.

What has not been checked

unverified Nobody has pressed these chords on a real terminal and reported back. Every assertion above is against ratatui’s TestBackend, which is a cell buffer and not a console: it cannot tell you that Windows Terminal delivered Alt+, as the frame expects, or that the page painted without tearing. Frame cannot be constructed in a test binary at all, so the chord path from key press to painted page is genuinely uncovered. What would settle it: open a framed session, press each of the five chords and Esc, and say what appeared. Help and Code, which landed on 2026-09-06, have never been drawn on a console at all: what exists for each is a Buffer, and a cell buffer is not a console. This repository has shipped a fully-tested scrollback defect twice out of exactly that gap.

unverified Behaviour at very narrow widths is untested for every page named in the lede. Settings at 80×24 is covered by a_page_that_runs_out_of_room_says_how_much_is_missing in term/guarantees.rs; Memory compresses rather than clips. At 40 columns specifically, nobody has rendered each remaining page and decided whether clipping or wrapping is wanted. What would settle it: render each page at 40 columns on a TestBackend and inspect the painted cells.

unverified Ctrl+/ may not arrive as Ctrl+/. Some terminals report that chord as 0x1F, as Ctrl+_ or as Ctrl+7, and the reader folds all three into one action. The folding is copied from the fork and believed rather than measured: no terminal on either machine reports it the other way, so the arm is exercised only by a unit test that feeds the event its author assumed. What would settle it: a keystroke dump on macOS Terminal.app, iTerm2 and Windows Terminal, recording which of the three each actually sends. ? at an empty prompt opens the same page and does not depend on any of this.

unverified The Code viewer's column arithmetic on wide characters. Rows go through fit, which is column-aware, so a CJK line should not overrun its pane, and there is no cursor in this stage so the char-versus-column desynchronisation the fork hit cannot bite here. It becomes live the moment a cursor is added. What would settle it: open a file with a CJK line in the page on a real terminal.

unverified Whether git ls-files at 16 to 46 ms is acceptable synchronously when the Code page opens. It runs once, on the same footing as the Harness page's read. On a monorepo it will be worse, and MAX_PATHS bounds the vector rather than the git call. What would settle it: time git ls-files on a repository with more than 100,000 tracked files; past roughly 150 ms the page open needs the same worker treatment the history already has.

unverified The keymap is one process-wide cell, and three test modules install into it on different threads of one cargo test process with nothing serialising them. A green run is not proof they cannot interleave; it has not flaked in about ten runs here. What would settle it: a shared test lock in keymap.rs that all three take.
