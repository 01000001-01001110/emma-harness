Eighteen kinds, written from five files, plus the same kinds again under a sub. prefix when a delegation is running. This page is meant to be enough on its own: what writes each one, every field on it, who reads it back, and the two pairing rules a parser gets wrong if nobody says them.

The two fields every record has

kind and at_ms, both inserted by SessionLog::append rather than by the call site. at_ms is unix milliseconds at the moment of the append, which for a tool_result is after the tool ran and for a tool_call is before it started. Nothing else appears on every record. turn_id comes close and is missing from the eight session-level kinds below.

crates/emma/src/session.rs — SessionLog::append

Both readers, Fold::record and restore_records, match on kind with a _ => {} arm. An unknown kind is skipped rather than fatal, which is what lets a file written by an older build still fold, and what makes the sub. prefix work without either reader mentioning delegation.

Read the goal append in the source: two fields are written for readers who are not the fold, and the comments say which. 

// crates/emma/src/agent.rs — Agent::run_goal
self.s.log.append(
    "goal",
    json!({
        "session_id": self.s.session_id,
        "text": goal.text,
        "opening": opening,
        // The one field written for a reader rather than for the fold.
        // Bare `--resume` means "the session I was last running *here*",
        // and a file that does not say where it ran cannot answer that —
        // so the working directory is recorded once per goal, which is
        // also the only place the answer could change within a session.
        "cwd": self.s.cwd.display().to_string(),
        "instructions_hash": emma_harness::hash::short(self.s.instructions),
        "tool_schema_hash": self.s.tools.schema_hash(),
        "model": self.s.provider.model_id(),
        "done_check": self.s.done.name(),
    }),
);

opening is the composed user turn and not the words you typed; text is the words you typed. The fold rebuilds the first message of a goal from opening, so a hook that injected context in front of the prompt is inside the replayed conversation and a resume sends what the model originally saw. done_check is the name of the completion rule rather than the rule, and the comment above the call explains why the composed string is stored instead of being re-derived: a fold that rebuilt it would need a name-to-implementation table kept in step with goal.rs forever.

Turn-level records

Each of these carries turn_id, which is turn-<n> counting from the start of the session rather than the start of the goal. /clear does not reset it, because the ids have to stay unique inside a file that is not cleared.

Two pairing rules a parser needs

A failure writes two records, and sometimes only one

Every failure gets the prose record naming what went wrong (tool_unknown, denied, tool_failed, tool_fault, tool_cancelled or tool_panicked) and then the tool_result that was actually sent, under the same kind a success uses. The fold rebuilds the user turn from those blocks, and a fold that skipped failures would reconstruct a turn answering only the calls that worked, which the API rejects.

Two failure classes produce a tool_result with no preceding tool_call: a schema violation and the already-failed memo. Both are refused inside run_tool_call before the tool_call record is written, so anything joining calls to results by id will meet results with no call. certified in the corpus, not only in the source: at 2026-08-16 20:28 EDT two tool_result records in ~/.emma/sessions/ have no earlier tool_call with their id, in sess-1786386360054-46700.jsonl and sess-1786387904169-52756.jsonl, and both carry "kind":"already_failed" inside the block. The script is on The corpus. The schema-violation class has not appeared in this corpus at all.

crates/emma/src/agent.rs — Agent::run_tool_call, the fail closure; crates/emma/src/session.rs — restore_records

The order inside run_tool_call is what produces that gap. The unknown-tool check, validate_args and the memo check all come before the tool_call append; the hooks and the approval gate come after it. So a denied record always has a tool_call above it with the same id, and an already_failed result never does. restore_records states the cost of that in its own comment: those two classes are not restored into the memo, so a resumed model may re-issue one call that cannot run and be told so again.

A turn and its results are placed together or not at all

The second rule, and the one that decides what a parser may keep. The API rejects an assistant turn carrying a tool_use that no tool_result answers, and equally a result answering nothing. A run killed between the model call and the last of its tools leaves exactly that in the file. Keeping the half that survived produces a message list the next request cannot send, so the fold drops both. The fold has the code and the mutation that proves the check is live.

Records a delegation wrote

// crates/emma/src/session.rs
/// A second view of this same file for one delegation, and the buffer its
/// records also land in.
///
/// **Why the `kind`s are namespaced.** [`fold_records`] and
/// [`restore_records`] match on `kind` and both have a `_ => {}` arm, so
/// `sub.assistant` and `sub.model_call` are ignored for free — which is the
/// whole mechanism. Written under the parent's own names the damage would
/// not be subtle: a sub `assistant` record arriving between the parent's
/// `tool_call` and its `tool_result` calls `close_turn`, which places the
/// parent's held turn *without* its results, `answered()` fails, and the
/// parent's whole turn is silently dropped from every resume of that
/// session. `tests/delegate.rs` folds a session containing a delegation and
/// asserts the parent's message list is unchanged, because without that test
/// this is a convention rather than a property.
///
/// The three stamped fields are what make the file greppable back apart:
/// which delegation wrote a record, which of the parent's turns asked for
/// it, and which agent type ran.
pub fn subagent(&self, sub_id: &str, parent_turn_id: &str, agent: &str) -> (Self, Records) {
    let tap: Records = Arc::new(Mutex::new(Vec::new()));
    (
        Self {
            id: self.id.clone(),
            path: self.path.clone(),
            file: self.file.clone(),
            prefix: Some("sub"),
            stamp: vec![
                ("sub_id".into(), json!(sub_id)),
                ("parent_turn_id".into(), json!(parent_turn_id)),
                ("agent".into(), json!(agent)),
            ],
            tap: Some(tap.clone()),
        },
        tap,
    )
}

Same Arc<Mutex<Option<File>>>, so both runs write to one file through one lock and the records interleave in real time rather than being buffered and appended at the end. What separates them is the prefix on the kind and the three stamped fields on every payload. A delegated run therefore writes sub.goal, sub.model_call, sub.assistant, sub.tool_call, sub.tool_result, sub.goal_finished and so on for every kind its loop reaches, since it is the same Agent::run_goal doing the writing. certified: all six of those appear in ~/.emma/sessions/ today, alongside exactly one delegation record. Counts on The corpus.

Parsing a session from scratch

Read the file, drop lines that will not parse, then walk in order. Five kinds rebuild the conversation and everything else is audit trail.

  1. goal opens a goal. Its opening is the first user message. If a goal was already open, close it first.
  2. assistant holds a turn. Its raw_content array is the assistant message, blocks and all. A record without that field cannot be used and costs its whole turn.
  3. tool_result accumulates. Its block is a content block that goes into a user message pairing with the held turn.
  4. kick closes a turn that made no tool calls. Its text is a user message, and it is dropped if the turn before it could not be placed.
  5. cleared throws away everything before it, both the finished goals and the one in flight.

Then compacted, which is a splice rather than a message: drop drop_messages off the front of the finished-goal list and insert the recorded messages in their place. The count indexes finished goals only. All of this is the fold, in code, with the arms in the order the reader hits them.

Records under sub. are skipped by that walk. Records with no arm are skipped too, which today means model_call, tool_call, tool_unknown, denied, tool_failed, tool_fault, hook, model_changed, prompt_blocked and delegation. Three of those are read by restore for numbers rather than messages.

Four more records, written for a reader that draws a picture

crates/emma/src/runfacts.rs defines the records a run graph can be drawn from. Its name is the argument: the fork called this telemetry, a word meaning measurements sent somewhere, and this sends nothing anywhere. Every record goes to the local session JSONL, with no network, no prompt text and no hostname. A user reading telemetry.rs in a coding agent would reasonably assume they were being reported on, and being wrong about that in the reassuring direction is the worse error. tested: a test in the file strips comment lines from its own source and asserts the remainder contains none of reqwest, TcpStream, UdpSocket, Command::new, std::env or hostname, so the name and the code cannot drift apart quietly.

crates/emma/src/runfacts.rs — module doc

The rule the file keeps is that a screen must never claim what the store cannot back, so a field that would have to be estimated is absent rather than guessed. What that has already refused: no retries, because nothing retries a delegation; no host, because nothing in the workspace asks the operating system its name and adding a crate to invent one would be inventing the field; no threads, because a nested run is a future on the same runtime; and no ETA, because there is no completion-rate model here and a number derived from one would be an estimate wearing a measurement's clothes.

Addressing reuses ids this file already carries rather than correlating anything new. The root node is the session's own goal, addressed by the session id, and it is implicit: nothing spawns it, so nothing writes a node_spawn for it and its records are the un-prefixed ones. A nested node is one delegation, addressed by the sub_id that SessionLog::subagent stamps onto every record that run writes, built as sub-<parent turn id>-<n>. Delegation cannot nest today, because the child registry is built without the Delegate tool at all, so every parent_node_id written is the root. The field is written anyway rather than implied, so the day nesting becomes possible the reader needs no change. unverified Whether anything reads these records was not checked here. The two terminal views that would draw them, term/inspect.rs and term/rungraph.rs, render from their own view types and say the harness behind them does not exist yet. Grepping for the record kinds outside this module would settle it. Part of the same amber is settled in the affirmative now: the acting half exists as runctl, which reads a run's id for its pid and appends to that run's file. What is not settled is whether anything draws any of it, and that stays open until the Harness page's keys are wired.

Reading the file back into runs

crates/emma/src/harness_state/mod.rs is the read-only derivation over the records described on this page. It adds no record and decides nothing: nothing in it starts a run, ends one, or asks the model anything, and every number comes off the same session JSONL that emma agents counts and --resume folds. That is still true of this module, and the sentence that used to follow it is not. It said the harness the fork's mocks draw does not exist here. runctl landed on 2026-09-06 and is exactly the acting half: pause, resume, cancel, archive, delete and starting a run, over the pid a session id already carries. What is still absent is the scheduler, and that distinction is the whole of the module's argument: there is no worker pool, no task queue and no DAG, so runs returns goals in a session and the delegations inside them, and a card the log cannot feed stays empty. No key reaches runctl yet either, so nothing has written a harness_control record outside a test. Nearly every field is an Option carrying the reason it is optional. certified: grep -c "Option<" crates/emma/src/harness_state/mod.rs is non-zero across the struct definitions, and the module contains no provider call.

crates/emma/src/harness_state/mod.rs — module doc, runs, RunStatus

One inference lives there and it is named. A session file records that a goal started and, later, that it finished. It never records that the process is alive. So running is read off the clock: an unfinished goal whose file has been written to within STALE_AFTER_MS is RunStatus::Running, and one quiet longer than that is RunStatus::Stalled. Not failed, because nothing said it failed, and not running, because nothing has said anything.

Its damage account is better than the fork's because the reader underneath it is. SessionLog::read_reporting returns line numbers rather than a count, so a page can say which lines to look at, and it exempts a torn tail keyed on the trailing byte rather than on the line's position, which is what a crash mid-write leaves and is not damage. The fork's counter had no such notion, so every live session being written to at the moment of the read would have reported one damaged line. The cost is stated in the module rather than hidden: read_reporting also prints to stderr, which under the full-screen frame is not somewhere a person is looking, and a page polling a damaged file calls it again on every poll. Nothing in harness_state can fix that, because the print is in session.rs. unverified Whether the repeated stderr print is visible in practice depends on a caller that polls, and no such caller was found while writing this. Running a page against a session file with a corrupt line and watching stderr would settle it.

What this page covers

All seventeen record kinds Emma writes, their fields and their writers, plus SessionLog::subagent and the Records tap from session.rs. The field lists were read off the json! macro at each call site rather than from the corpus, so a field a run has never produced is still listed. certified that the list is complete for this commit: grep -rn "\.append(" --include=*.rs crates/, with session.rs's own definition excluded, returns 20 call sites. Sixteen are in agent.rs, one in delegate.rs, two in main.rs, and one in crates/emma/tests/resume.rs. Seven of the sixteen in agent.rs write turn-level tool records from run_tool_call and log_result_block.
