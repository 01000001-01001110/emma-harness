Compaction, and the model call it now makes

Sessions & context The file Records The fold Resume Continuity Compaction The corpus

Whole finished goals, replaced oldest-first with a summary a model writes, falling back to their goal text, their final answer and a fixed sentence when the model cannot be asked or does not help. This page used to be called “Compaction without a model call” and its subject was a reversal: the design note recommended asking a model and was overruled. On 2026-09-06 the reversal was reversed, so the subject is now what it cost to overrule the note, what changed, and the four guardrails that answer each objection it raised.

What it operates on

// crates/emma/src/agent.rs
struct Chapter {
    goal: String,
    answer: String,
    messages: Vec<Message>,
    /// Already a summary. Summarising it again would produce the same two
    /// messages and a second log record saying nothing happened.
    summarised: bool,
}

A chapter is one whole goal. Compaction works in chapters because cutting anywhere else risks separating a tool_use from the result that answers it, and a boundary that is "wherever the arithmetic landed" is one somebody has to re-derive every time they read the code. goal and answer live beside the messages because they are what a summary is made of, and deriving them back out of the message list afterwards would be guesswork.

pub fn conversation(&self) -> Vec<Message> {

        .flat_map(|c| c.messages.iter().cloned())

estimated_context is that flattening measured by estimate, and it is what /model and the compaction receipt quote as "roughly N tokens". It enforces nothing.

The trigger is measured

// crates/emma/src/agent.rs
fn compact_if_needed(&mut self, measured: Option<i64>, why: &str) {
    let cap = self.s.budgets.max_context;
    if cap <= 0 {
        return;
    }
    let size = measured.unwrap_or_else(|| estimate(&self.conversation()));
    if size <= cap {
        return;
    }
    // Half the cap rather than all of it: the goal now running needs room
    // to work in, and compacting to exactly the limit would mean compacting
    // again on the next call.
    let target = (cap / 2).max(1);
    // Measured once per chapter rather than once per step. Re-summing the
    // whole conversation on every iteration of the loop below is quadratic
    // in a list whose elements are file contents.
    let sizes: Vec<i64> = self
        .chapters
        .iter()
        .map(|c| estimate(&c.messages))
        .collect();
    let mut remaining: i64 = sizes.iter().sum();
    let mut take = 0;
    while take < sizes.len() && remaining > target {
        remaining -= sizes[take];
        take += 1;
    }
    // **The returned reason used to be dropped here.** `/compact` explains
    // itself and the threshold path did not, so a conversation over its cap
    // with nothing left to summarise — one enormous goal, or a history
    // already reduced to summaries — grew on every single call in silence
    // until the token budget or a provider 400 ended it. The user's first
    // sign was the run stopping.
    if let Compacted::Nothing(reason) = self.compact(take, size, why) {
        if !self.said_compaction_stuck {
            self.said_compaction_stuck = true;
            self.s.term.warn(&format!(
                "this conversation is over the context limit and compaction cannot \
                 shrink it: {reason}. Every request from here is larger than the cap, \
                 and the run will end on a budget or a provider error rather than on \
                 the goal. `/clear` starts a fresh conversation; a smaller goal would \
                 also fit."
            ));
        }
    }
}

cap <= 0 disables compaction entirely, which is how --max-context 0 turns it off. measured is the provider's own billable_input_tokens for the previous call, which covers the whole request: the system prompt and the tool schemas as well as the conversation. The estimate stands in for one case, the first check of a goal on a process that has not called the model yet, and in practice that is a resume into a large session.

crates/emma/src/agent.rs — compact_if_needed, and its two call sites in run_goal

Two call sites. One before the first request of a goal, with None and the reason "a new goal opened over the context limit"; one inside the loop, after the budget guards and before the request is built, with self.last_input and the reason "the request passed the context limit". The second is why the request that goes out is the compacted one rather than the next one after it.

The counting loop is greedy over whole chapters and stops as soon as the remainder fits, so it never takes the newest goal unless it has to take everything. It measures each chapter once. Re-summing the conversation inside the loop would be quadratic in a list whose elements are file contents. That cost stays invisible until a session gets large enough to need compaction in the first place.

The tail of the function used to be a bare self.compact(take, size, why);, dropping the returned Compacted on the floor. That mattered in exactly one case: a conversation over its cap with nothing left to summarise (one enormous goal, or a history already reduced to summaries) where compact answers Compacted::Nothing with a reason and the threshold path said none of it. Such a session grew on every call in silence until the token budget or a provider 400 ended it, and the user's first sign was the run stopping. The reason is now caught and said once per session, on the said_compaction_stuck flag, with /clear named as the way out; once rather than per call, because the condition holds on every subsequent request and a warning per request is a run burying itself in its own complaint. tested automatic_compaction_that_cannot_help_says_so_once in crates/emma/tests/commands.rs.

Replacing them

// crates/emma/src/agent.rs
fn compact(&mut self, take: usize, size: i64, why: &str) -> Compacted {
    let take = take.min(self.chapters.len());
    if take == 0 {
        return Compacted::Nothing("there is nothing behind the current goal".into());
    }
    let before: i64 = self.chapters[..take]
        .iter()
        .map(|c| estimate(&c.messages))
        .sum();
    let replacement: Vec<Message> = self.chapters[..take].iter().flat_map(summarise).collect();
    let after = estimate(&replacement);

One implementation with two doors. The threshold path counts until the remainder fits half the cap; /compact counts every finished goal, or every one but the last. Everything after the count is here once, because two compaction implementations would be two things a resume could disagree with, and the fold has no summarising code of its own to be the second. 

// crates/emma/src/agent.rs
/// What a compacted goal leaves behind: the goal, the answer, and a sentence
/// saying what is no longer there.
///
/// Exactly the collapse `run_goal` used to apply to every goal the moment it
/// finished — see [`Agent::chapters`]. The note is the part that is new, and it
/// is the difference between a model that reads a file again and one that
/// answers from a recollection of it.
fn summarise(c: &Chapter) -> Vec<Message> {
    if c.summarised {
        return c.messages.clone();
    }
    let goal = if c.goal.trim().is_empty() {
        "[an earlier goal]"
    } else {
        c.goal.trim()
    };
    let answer = if c.answer.trim().is_empty() {
        "[this goal ended without a final message]"
    } else {
        c.answer.trim()
    };
    vec![
        Message::user(goal),
        Message::assistant_text(format!("{answer}\n\n{COMPACTED_NOTE}")),
    ]
}

/// Said to the model, in the place the traffic used to be.
const COMPACTED_NOTE: &str = "[Summarised to save context. The tool calls from this goal and \
     their results — file contents, command output, diffs — are no longer in this conversation. \
     Read anything you need again rather than recalling it.]";

A compacted goal is exactly two messages: a user message that is the goal text, and an assistant message that is the final answer plus the note. Empty fields get stated placeholders rather than blank strings, so a goal that ended without a final message says so instead of producing an assistant message that opens with a newline. An already-summarised chapter comes back unchanged. A second pass must not wrap it in a second note.

What a folded goal loses: every tool call and every result, which means file contents, command output and diffs, and every intermediate assistant turn with its thinking blocks. What survives for the life of the session is every goal's words and every goal's final answer. The note exists because a model that does not know a file has left its context answers from a memory of it, and a confident wrong answer costs more than a second read. tested compaction_drops_the_oldest_tool_traffic_and_keeps_the_words in crates/emma/tests/conversation.rs asserts the file body absent, the goal present, the answer present and the note present, in the bytes the fake provider actually received.

The compaction that would not shrink anything

// crates/emma/src/agent.rs — Agent::compact
// A conversation summarising would not shrink has nothing to give.
// Stopping here rather than rewriting it into itself is what keeps a
// session under a cap it cannot reach from logging a record and
// reporting a saving on every single call.
//
// **Two different situations reach this line and a user needs to be
// told which.** Automatic compaction is no longer silent either way —
// DEF-009 gave the threshold path a one-shot warning naming `/clear`,
// because a session pinned against a cap it cannot compact below was
// otherwise a loop that just kept costing money. `/compact` was always
// loud, and the first live run of it said "already summarised" about two
// goals that plainly were not — because those goals were four words
// long and `COMPACTED_NOTE` is three hundred characters, so the
// replacement was *larger* than what it replaced. The sentence was true
// of the arithmetic and false about the conversation, which is the class
// of untruth this repository has already paid for twice.
if after >= before {
    let all_summaries = self.chapters[..take].iter().all(|c| c.summarised);
    return Compacted::Nothing(if all_summaries {
        "the conversation is already summarised — there is nothing left to take out".into()
    } else {
        format!(
            "summarising those {take} goal(s) would not make the conversation smaller. \
             Compaction replaces a goal with its text, its answer and a note saying the \
             tool results are gone, and here that note is longer than what it would \
             replace — roughly {before} tokens becoming {after}."
        )
    });
}

The note is roughly three hundred characters, so two four-word goals compact upward and the guard fires. That is not a corner case invented for a test; it is what the first live /compact did, and the bug it produced was a sentence rather than a crash. The arithmetic was right and the explanation was wrong, so a user was told their conversation was already summarised when it was nothing of the sort. There are now two branches, and the second quotes the before and after so the claim can be checked against the numbers. tested compaction_stops_when_there_is_nothing_left_to_win.

The replaced chapters become one chapter with empty goal and answer and summarised: true. The design note recommended a model call, and was overruled

The session-and-context design note surveyed six shipped tools and recommended what all of them do: summarise with one model call, same model, tools absent, effort low, against a fixed template asking for objectives, what was verified, decisions and why, what failed, files touched, what is next. It also recommended trigger-high/compact-low hysteresis, crossing around 120k and compacting down to 30–40k, and that the compacted record carry the summary plus references to the retained turns rather than copies of them.

None of the three shipped. The note is still in the tree and still reads as current advice, so the three departures belong in one place, or the recommendation comes back.

  • No model call — until 2026-09-06. Three arguments were made against it: it would spend the budget of whichever goal happens to be running; it can fail in the middle of one; and it produces a claim about the conversation where the mechanical version produces a record of it. The note also warned that a model-written summary can be wrong, and offered two mitigations while describing neither as a fix. Every one of those objections is still true. What changed is that the deterministic collapse was measured and found to be worse than a wrong summary, and each objection was answered with a guardrail rather than argued away. The next section is the whole of it.
  • Half the cap, not a fixed floor. target = (cap / 2).max(1) is 60,000 at the default rather than the note's 30–40k. Same effect on how often compaction fires, and no second constant to keep in step with the first.
  • The replacement is written into the record whole. The note argued for references, citing a bug in another tool where re-serialising surviving history made the log grow without bound. The code stores drop_messages and the exact replacement messages, so a resume replays the compaction instead of re-deriving it, and session.rs contains no summarising code that could disagree with the loop's. The growth the note warned about is bounded here by the replacement being two short messages per goal rather than a retained window of turns.

What it cost to overrule the note, and what changed

The deterministic collapse replaces a finished goal with its goal text, its answer, and a sentence saying the tool traffic is gone. That is a faithful record of what happened and it is not a usable handover: the reasoning, the constraints the user stated, and the state of the work all lived in the tool traffic. The measurement that moved this was 129,254 tokens of conversation collapsing to something a model could not pick the work up from.

So model_summary asks. One call, no tools, no history, Caching::Off, against a prompt asking for the decisions and why, the current state, what remains, the file paths by full path, and any constraint or correction the user stated in their own terms; and asking it to drop tool-result bodies, dead ends and commentary about the summary itself. It asks for prose rather than JSON, because what the answer becomes is a message in a conversation and a structure would add a parse that can fail and buy nothing.

Four guardrails, one per objection.

  • A budget floor. The tokens are the running goal's, metered on the same Spend as every other call, so a compaction that pushed the goal over max_tokens would have ended the goal in order to shorten its conversation. SUMMARY_BUDGET_FLOOR is 50,000 weighted tokens, sized above the answer budget plus the input, so the call cannot be started when it could not be afforded. Under the floor, the deterministic collapse runs and the reason is written down.
  • A timeout. SUMMARY_TIMEOUT is 120 seconds. Compaction sits on the path of a request that has already passed the cap, so somebody is waiting on it, and a compaction nobody can interrupt for an hour is worse than a deterministic summary now.
  • An input cap. SUMMARY_INPUT_CHARS is 120,000, roughly 30,000 tokens at the packer's ratio. The conversation being folded is by construction the largest thing in the session, which is why it is being folded, so sending all of it would reproduce the oversized request compaction is being run to prevent.
  • A size check that has the last word. compact still refuses a replacement that does not shrink the conversation, and that guard is not a formality. A model that returns a long answer to a short stretch of goals is answered with the collapse.

ModelSummary carries the text or the reason there is none, and the tokens either way. A call that failed after the provider answered was still billed, and a record showing zero would understate what compaction spent. The failure modes are all one shape: no text, a fallback sentence, and the deterministic collapse.

The note under a summary is a different sentence from the note under a collapse, and the reason is worth keeping. COMPACTED_NOTE opens by promising the text above it is preserved word for word, which is the whole reason the collapse can be trusted and is exactly what a summary is not. SUMMARISED_NOTE says the text was written by a model rather than quoted, tells the model to treat it as a recap rather than a quotation, and tells it not to attribute the words to the user. Saying the first sentence over a summary would be a sentence that is true of the mechanism it was written for and false about the text it is attached to.

The replacement is a user message and an assistant text message and nothing else: no thinking block, so no signature, so nothing bound to the model that produced it. That is the property the recovery path relies on when it compacts to escape a provider that has rejected signed content, and it is why a summary survives a /model switch for the same reason the answer text already did.

The same run found two things the design did not predict, and both are amber. unverified The prompt says “no headings” and the model added a Files involved: heading with a bullet list under it anyway. Harmless, since this is prose in a conversation and not a parsed structure, but the instruction is not obeyed, so no future code may assume the answer's shape. One model, one prompt, one transcript: the same call against the three other local models would say whether it is a habit of this model or of the prompt. unverified The answer's last clause was garbled — “remains updated to be corrected” is not English and inverts what the transcript said. That is the objection the design answered rather than removed. A summary is a claim, a bad one is recorded verbatim, and it is replayed on every resume for the life of the session. It is the reason SUMMARISED_NOTE tells the model not to treat the text as a quotation. What would settle how often it happens: read a corpus of real summaries against the transcripts they replaced.

Shedding, for the goal that is too big on its own

Compaction takes whole finished goals, so a single long goal has nothing for it to take: the running goal is the whole conversation, and a request over the cap goes out over the cap. shed_the_running_goal is the answer. It rewrites the running goal's message list in place, replacing the bodies of old tool results with a note. The user turns, the assistant text, the thinking blocks and the tool calls with their arguments all stay; only the results go, which is what makes the note actionable: it names the tool and says re-run rather than recall.

KEEP_RECENT_TURNS is 1, so the most recent tool-calling turn is never shed. Its results are the answer to a call the model has just made and not yet acted on, and taking those would delete the step in progress rather than save context. A result already shorter than the note saying it is gone is left alone, because replacing it would make the request larger; the compactor learned that same lesson on a four-word goal. SHED_MARK is the note's opening and doubles as the test for “this one has already gone”, a prefix rather than a stored flag, because the block crosses the wire and comes back through a fold and a flag would have to be kept in step with the text.

There is no flag for it, and it is on whenever the cap is. The alternatives are worse in ways the module names. prune removes traffic a later call superseded, so twenty-five reads of twenty-five different files are twenty-five live results and it has nothing to take; it also runs on every call whether or not the request is near the cap, paying the prompt-cache invalidation unconditionally. Shedding runs only when a measured request has already passed the cap, so the cache cost is paid exactly when the alternative is a request the provider will refuse. An amnesiac conversation beats a refused one.

/compact <words> is refused rather than ignored, and the refusal names a workflow that does work. 

// crates/emma/src/session_command.rs — compact
// Said rather than ignored. `Agent::compact`'s doc rules that
// compaction is not model-summarised — a call there spends the running
// goal's budget, can fail mid-goal, and produces a *claim* about the

);

The workaround it offers is real rather than a deflection: a goal's answer is one of the two things compaction keeps, so asking for the summary as an ordinary goal puts it somewhere compaction cannot take it. tested compact_with_an_instruction_says_it_cannot_follow_one and compact_tells_all_from_an_instruction_it_cannot_honour.

The other thing that shortens a conversation

// crates/emma/src/agent.rs
/// Drop the conversation without ending the session.
///
/// A `cleared` record goes in the log, and `session::Fold` honours it — the
/// bytes stay in the file for a human to read and the fold skips them.
/// Without that arm `--resume` would fold the whole file and un-clear the
/// session, which would make this command a lie.
///
/// `turn_seq` is deliberately **kept**: turn ids have to stay unique inside
/// one session file, and the file is not cleared.
pub fn clear(&mut self) -> Cleared {
    let cleared = Cleared {
        goals: self.chapters.iter().filter(|c| !c.summarised).count(),
        messages: self.chapters.iter().map(|c| c.messages.len()).sum(),
    };
    self.chapters.clear();
    self.last_ending = None;
    self.last_input = None;
    // A resume that has not been spent yet is still a conversation waiting
    // to be injected into the next goal's query. Leaving it would mean
    // `/clear` on a `--resume`d session cleared everything except the thing
    // the user was most obviously trying to get rid of.
    self.resumed = None;
    self.s.log.append(
        "cleared",
        json!({ "goals": cleared.goals, "messages": cleared.messages }),
    );
    cleared
}

/clear is not compaction and shares none of its code. It drops everything, writes its counts into the record, and clears last_input so the next goal's compaction check has no stale measurement to compare against. A summarised chapter is not counted as a goal in the receipt, which keeps the number honest about what the user is losing.

The receipt in session_command.rs then says what survived: the session's tool and host grants, the transcript path, the model and the session id. Grants are consent about the process rather than about the conversation, and clearing them would make nothing safer, since the human is still at the keyboard and would be asked the same questions again. What silence would cost is the ability to notice, so the receipt names them.

The third thing, which rewrites rather than shortens

crates/emma/src/prune.rs is a transform over the outbound history that neither compaction nor /clear touches. Every tool result Emma has received is re-sent on every later call, so a result's cost is its size multiplied by the number of calls still to come, and an earlier Read of a file a later Read has replaced is paid for again on every remaining turn while saying nothing the newer copy does not. Three transforms act on that: supersede_reads stubs an older read covered by a newer one, fold_edits rewrites a superseded edit's input, and collapse_failures replaces a repeated rejection with a sentence. certified: the three functions are declared in the file and prune is its only public entry point.

crates/emma/src/prune.rs — prune, supersede_reads, fold_edits, collapse_failures, Report

It ships off, and the reason is a measurement that contradicted the claim it was ported on. The fork this came from says 81.8% of byte-turns across 25 recorded runs were carried by superseded Read results. Those recordings were not in the archive, so the harness at the foot of the file re-derived the figure against a different corpus, the operator's own 156 session files, on 2026-08-26: superseded reads carry 2.4% of byte-turns there, 245,728 tool_result bytes of 10,104,760 over the 36 sessions that used a tool at all, and all three transforms together reach 2.5%. The best single session was 5.1% and most were 0.0%. Neither number refutes the other. The payoff depends on what the session did: a run that reads one file eleven times to make four edits is the shape that pays, and a run that greps, builds and reads each file once is this corpus. observed: one run of the in-file measurement harness over a home directory nobody kept. Re-run it against any corpus and it prints that corpus's own number.

The same run found a bug in the port, which is the argument for measuring at all. On the first pass all three transforms together removed fewer bytes than supersede_reads alone, 245,356 against 245,694, because a short rejection like "denied" is smaller than the sentence explaining it was dropped, so the rewrite grew the request and lost the original text at once. No fixture in the file could have caught it: every one used a short result. claim_stub is the fix and the same run now reports 2.5% against 2.4%.

Two invariants hold the whole file. It rewrites and never deletes, because a tool_result whose tool_use_id has no matching tool_use is rejected by Anthropic, so dropping one side of a pair is not an option even when only one side holds the bytes. Every function mutates the contents of a block that is already there, and the transform takes &mut [Message] rather than a Vec so the type carries the length invariant. And nothing here touches the session log: Agent::conversation stays faithful to what was recorded, because the fold of the log has to equal it, and only the outbound request is rewritten. Despite the module's name there is no std::fs in the file. certified: grep -n "std::fs" crates/emma/src/prune.rs matches twice, once in the module doc's own sentence and once inside the #[ignore]d measurement test that walks a session corpus. Nothing on the transform path touches a file, and prune's signature takes &mut [Message].

One deviation from the fork is a correctness fix rather than a port artefact. The fork modelled a Read with no limit as reaching infinity, so an unbounded re-read from line 1 covered any earlier read of the same file. A live Read shows at most MAX_LINES whatever the arguments say, so an unbounded read of a 5,000-line file stops at 2,000, and stubbing an earlier offset: 3000 read against it would delete the only copy of those lines while claiming a newer one exists. Window is bounded at both ends, with the cap read from tools/fs itself so the two cannot drift.

nothing in the loop calls it

prune has no caller outside its own tests. The settings screen writes prune_history into settings.json and app.rs reads it back into a row, but no request path passes a message list through this module. certified: grep -rn "prune" crates/emma/src/agent.rs prints nothing, and the only matches for prune_history outside settings.rs are in term/app.rs and term/settings.rs. So the measurement above describes what the transform would save, not what any run has saved.

The estimator, and where its error lands

// crates/emma/src/agent.rs
/// Roughly how many tokens a message list is worth.
///
/// `chars / 4`, the same conservative ratio `emma-llm`'s packer uses to decide
/// whether a prefix is worth a cache breakpoint, and documented there as
/// under-counting what the provider bills. It is used here for two things that
/// tolerate it — deciding *how much* to drop once a measured number has already
/// said dropping is necessary, and standing in for that measurement on the one
/// call of a process that has none. It is never what fires a budget.
fn estimate(messages: &[Message]) -> i64 {
    let chars: usize = messages.iter().map(|m| m.content.wire_len()).sum();
    (chars / 4) as i64
}

wire_len is the rendered JSON length, quotes and escapes included, because the provider tokenises those too. The under-count has a direction, and it lands differently on each consumer.

The third row is where the margin widened. The gate used to be one constant, 512, which was right for claude-opus-5. The floor is per-model and not monotonic with release date, and the table now runs from 512 to 4,096: claude-haiku-4-5 and claude-opus-4-6 cache nothing under 4,096 tokens, and a model the table has never heard of is assumed to be at 4,096 too. At a 512 floor the gap between an under-counting estimate and the truth costs a marker on a prefix of a couple of kilobytes. At 4,096 it is a prefix of roughly sixteen kilobytes going unmarked, and one /model or one Haiku-typed delegation is enough to reach that floor. unverified: the direction of the error is stated in both source files and matches English-plus-JSON tokenising at closer to 3.5 characters per token, but nobody in this tree has measured Emma's own wire bytes against a token count. Settle it by sending a request of known rendered length with caching off and comparing wire_len / 4 against the input_tokens the API reports, or by pushing the same bytes through the token-counting endpoint.

What the estimate does not touch
