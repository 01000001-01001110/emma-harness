The cache floor, and why there are two tables

Providers & models The boundary Content blocks The turn back Model limits Caching The cache floor Retry Credentials

Below a model's minimum cacheable prefix, a cache_control marker is accepted and silently does nothing. Not rejected, not warned about. HTTP 200, a normal response body, and cache_creation_input_tokens: 0. The marked span is billed at the uncached rate, and there is no symptom anywhere except the invoice.

A feature that is accepted and inert

Every reflex in this codebase for catching a wrong request is tuned for a 400. models.rs exists because too high a max_tokens is a 400; retry.rs classifies by status; the wire tests assert the bytes that avoid a 400. None of that machinery can see this one, because there is nothing to see: the same status, the same body shape, and a field that is 0 instead of a number. A single MIN_CACHEABLE_TOKENS = 512 had been wrong for every non-Opus-5 model since it was written, and no test, no log line and no status row had a way to say so.

observed, not argued

A 3,001-token prefix on claude-haiku-4-5 with the marker present returned 200 OK and cache_creation_input_tokens: 0, twice. Each floor was then bracketed by a pair of prefill calls about 30 tokens either side of the documented value, sized with count_tokens so that "3,000 tokens" meant real tokens rather than characters over four: 

claude-haiku-4-5: 4069 tokens, marker present -> cache_creation = 0
claude-haiku-4-5: 4129 tokens, marker present -> cache_creation = 4122

Haiku 4.5's gate opens between 4,069 and 4,129 real tokens; Opus 5's between 483 and 543. Both are consistent with the documented 4,096 and 512. Under a cent for both models. observed: bisected live against the API on 2026-08-14 by the agent that wrote the fix; no raw request or response body was kept, only the printed pass and fail lines above. That is why this is amber and not green. The record is the status line and the two-line table, which is the whole of it.

notes/lessons/a-provider-feature-can-be-accepted-and-inert.md; commit bb78857

The generalisable part: when a provider feature is advisory rather than mandatory, failure is silent, and the only detector is the usage counter it was supposed to move. A test asserting that the marker was sent passes forever. A test asserting that the marker moved the counter runs only against the real API.

The floors, and which of them anybody has seen

crates/llm/src/anthropic.rs · MIN_CACHEABLE

/// Smallest prefix each model will cache at all, longest-prefix keyed so a
/// dated snapshot (`claude-haiku-4-5-20251001`) resolves to the same row as its
/// alias. Below its model's floor a `cache_control` marker is **accepted and
/// silently does nothing** — no error, no entry, and the marked span still
/// billed at the uncached rate. That is why every breakpoint below is gated,
/// and why the gate cannot be one number: the floor is not monotonic with
/// release date, and the newest models have the *lowest* floors. A single
/// `512` was right for `claude-opus-5` and eight times too low for
/// `claude-haiku-4-5`, which a user reaches with one `/model` or one
/// Haiku-typed delegation.
///
/// Transcribed 2026-08-11 from Anthropic's published prompt-caching docs.
/// **A snapshot of facts that change without asking us** — floors have moved
/// with every model generation, so re-check this table when adding a model
/// rather than pattern-matching from the rows above it.
const MIN_CACHEABLE: &[(&str, usize)] = &[
    ("claude-opus-5", 512),
    ("claude-fable-5", 512),
    ("claude-mythos-5", 512),
    ("claude-opus-4-8", 1_024),
    ("claude-sonnet-5", 1_024),
    ("claude-sonnet-4-6", 1_024),
    ("claude-sonnet-4-5", 1_024),
    ("claude-opus-4-7", 2_048),
    ("claude-opus-4-6", 4_096),
    ("claude-haiku-4-5", 4_096),
];

The floors are not monotonic with release date: the newest models have the lowest floors and an older, smaller model the highest. That is what makes a single constant wrong rather than merely stale, and no_cache_floor_row_shadows_another asserts it directly with min_cacheable_tokens("claude-opus-5") < min_cacheable_tokens("claude-haiku-4-5") alongside the no-shadowing property. tested

two rows out of ten

Only 2 of the 10 rows have been measured. The other eight are transcription from Anthropic's published prompt-caching documentation dated 2026-08-11, and nobody has pointed a request at any of those models to check. unverified The measurement that settles one is cheap and already written down: send a prefix 30 tokens under the claimed floor and one 30 tokens over, with count_tokens for the sizing and max_tokens: 1 so no output is generated, then read cache_creation_input_tokens. Under a cent per model. Because the floors move with model generations, measure a new row rather than copying the row above it.

The table is also shorter than the documentation it came from. notes/research/caching-mechanics.md's floor table names four ids the shipped rows dropped: Opus 4.1 at 1,024, Mythos Preview and Haiku 3.5 at 2,048, and Opus 4.5 at 4,096. A user who names one of those today falls to MIN_CACHEABLE_UNKNOWN and is gated at 4,096, so three of the four cache less than they could. unverified Whether the omission was a decision or an oversight is not recorded anywhere. Those ids have no rows in models::TABLE either, so adding them means two measured values per model rather than one.

The lookup, and the fallback that guesses high

crates/llm/src/anthropic.rs · MIN_CACHEABLE_UNKNOWN, min_cacheable_tokens

/// What we assume for a model this table has never heard of: **the highest
/// floor anyone ships**, which is the opposite direction from
/// [`models::UNKNOWN`]'s conservative *low* ceiling, and deliberately so.
///
/// - *Guess too low* and we reproduce the defect this table exists to fix:
///   markers on prefixes under the real floor, the marked span billed
///   uncached, no symptom anywhere except the invoice, unbounded in time.
/// - *Guess too high* (chosen) and an unknown model whose real floor is lower
///   goes unmarked while its estimated prefix sits under 4,096 tokens
///   (~16 KB rendered). The cost is the forgone 0.9× read discount on that
///   span — cents per call — and it ends by itself, because history grows past
///   the threshold within a few turns.
///
/// Silent-and-forever versus visible-and-self-healing is the whole argument.
const MIN_CACHEABLE_UNKNOWN: usize = 4_096;

/// The smallest prefix `model` will cache, or [`MIN_CACHEABLE_UNKNOWN`] if this
/// table has never heard of it.
fn min_cacheable_tokens(model: &str) -> usize {
    MIN_CACHEABLE
        .iter()
        .filter(|(id, _)| model.starts_with(id))
        // Longest match wins, so a shorter row added later cannot swallow a
        // model whose id it happens to prefix.
        .max_by_key(|(id, _)| id.len())
        .map(|(_, floor)| *floor)
        .unwrap_or(MIN_CACHEABLE_UNKNOWN)
}
crates/llm/src/anthropic.rs — MIN_CACHEABLE_UNKNOWN, min_cacheable_tokens

an_unknown_model_is_gated_at_the_highest_known_floor pins both halves. It asserts the fallback equals the maximum floor in the table rather than the literal 4,096, so adding a higher row cannot leave the constant behind; then it asserts an unknown model gets no markers on a roughly 700-token prefix, and gets them back once the prefix clears 4,096. That is a gate, not a refusal. tested

Four more tests hold the gate. a_prefix_over_one_models_floor_and_under_anothers_is_marked_only_for_the_first sends the identical request to Haiku and to Opus 5 and asserts zero markers against two. a_high_floor_model_still_gets_every_breakpoint_once_it_clears_it sends a much larger request to Haiku and asserts all three land where the Opus placement tests put them, so the gate moved and the placement did not. a_dated_snapshot_resolves_to_its_alias_on_the_wire asserts claude-opus-5-20260101 resolves to 512 rather than falling through to the unknown fallback. tested

Why there are two tables and not one

models::TABLE and anthropic::MIN_CACHEABLE name the same ten models, and a model release adds a row to each. Merging them is the obvious tidy-up. Three things break if they are merged:

  • Limits is the struct GET /v1/models parses into. A discovery stage swaps the lookup for that call and leaves the clamping alone; a merged struct could not be swapped, because the endpoint cannot fill it.
  • That endpoint reports no cache minimum. The floor cannot follow the other values into discovery, so it would remain hand-maintained inside a struct that had otherwise stopped being.
  • The two fallbacks argue in opposite directions. models::UNKNOWN guesses low because too high a ceiling is a 400; MIN_CACHEABLE_UNKNOWN guesses high because too low a floor silently overpays. One shared UNKNOWN would carry a doc comment arguing both ways at once.

What the split costs, and the guard that pays for it

A model release means a row in both tables, and for a while nothing in the compiler noticed when only one was added. Each table had an internal-consistency test and neither could see the other, so adding a model to one and forgetting the other compiled, passed, and went wrong quietly. The architecture map found that gap the same day the second table shipped, in the same work that argued for the split.

Missing from What happens Who notices
MIN_CACHEABLE Gated at 4,096; caches less than it could have. Visible on an invoice, self-heals as history grows.
models::TABLE Clamped to the 8,192 ceiling; a legitimate long answer is silently truncated. Nobody. This is the one that costs a user something they cannot see.

One thing the project's own notes disagree about

Whether an ignored marker costs anything directly. notes/plans/caching-defects.md describes it as "+25% on the marked span, forever". notes/research/caching-mechanics.md says a below-minimum prefix is "cost-neutral (marker ignored), not negative", adding that what it really costs is the false belief that caching is on. unverified The reconciliation that fits both is that the marker is ignored, so no write premium is charged, and the loss is the read discount that never arrives on a span the user believed was cached. Which of the two is literally true is settled by one usage row from a below-floor call: if cache_creation_input_tokens is 0 and the span appears in input_tokens at base rate, the research doc is right.

The pages on this site do not pick a side, because picking one would put a number in front of a reader that nobody has seen. The observed bisection above is consistent with both readings: it recorded cache_creation = 0, and did not record what input_tokens did.
