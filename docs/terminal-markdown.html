crates/emma/src/term/markdown.rs

Markdown, one line at a time

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Run control Copying out

The model writes markdown. This is as much of it as a terminal transcript can carry without inventing structure, and the boundary that makes it possible is the newline: every block this file recognises is decided by the start of a line, so one complete line is all the context any of them needs, and the only state crossing lines is whether a fence is open.

Why not pulldown-cmark

The obvious answer, and the wrong shape for this job twice over. It is an event parser over a whole document, “it wants the text before it can tell you what the text was”, and prose here arrives in fragments, a few characters at a time, with the screen updating as it goes. And it parses the whole of CommonMark, including link reference definitions, HTML blocks and setext headings, none of which a terminal can render as anything other than the characters they were written with.

Buffering a paragraph until it is complete was rejected on feel rather than on architecture: “Emma streams because forty seconds of blank terminal is indistinguishable from a hang; a renderer that waits for a blank line before it prints anything reintroduces exactly that pause, at the end of every paragraph, in the one place the user is actually reading.”

The costs are documented up front. Setext headings (Title under =====) cannot be recognised, because by the time the underline arrives the title has already been printed; they show up as a paragraph and a rule. Tables are not aligned, because column widths need the whole table; their rows print as written.

The one entry point

crates/emma/src/term/markdown.rs · Markdown::line

    pub fn line(&mut self, raw: &str, width: u16, skin: &Skin) -> Vec<Line<'static>> {
        let width = usize::from(width.max(1));
        let raw = sanitise(raw);

        if let Some((ch, len)) = self.fence {
            if closing_fence(&raw, ch, len) {
                self.fence = None;
                return vec![rule(skin, width, "")];
            }
            return code_rows(&raw, width, skin);
        }
        if let Some((ch, len, info)) = opening_fence(&raw) {
            self.fence = Some((ch, len));
            return vec![rule(skin, width, &info)];
        }
        if raw.trim().is_empty() {
            return vec![Line::default()];
        }
        if thematic_break(&raw) {
            return vec![rule(skin, width, "")];
        }
        if let Some((level, text)) = heading(&raw) {
            …
        }
        if let Some((indent, marker, rest)) = list_item(&raw) {
            …
        }
        if let Some(rest) = quote(&raw) {
            …
        }
        let spans = inline(&raw, skin, skin.palette.style(Role::Text));
        flow(Vec::new(), spans, width, 0)
    }

The fence check is first; inside a fence, nothing else is recognised. The last arm is prose. Shapes that are nearly something else render as paragraphs, because a paragraph is always renderable.

RecogniserWhat it accepts, and what it refuses
heading One to six hashes followed by a space. The space is required, so #hashtag and #1 are prose, which is what a model writing about an issue number meant. Closing hashes are dropped, as CommonMark says.
list_item -, *, +, or up to nine digits then . or ), each followed by a space. Indent above 12 is refused outright: “a deeply indented line is somebody's code block and is left alone.”
quote A leading >, and one optional space after it.
thematic_break Three or more of -, * or _ and nothing else on the line.
opening_fence Three or more backticks or tildes. A backtick fence whose info string contains a backtick is refused, “that rule is what stops `a` and `b` in a sentence from opening a code block.”
closing_fence The same character, at least as many, and nothing else on the line, which is what lets a backtick block contain a ~~~ line.

tested: a_fence_closes_only_on_the_mark_that_opened_it, inline_backticks_never_open_a_code_block, and the heading test which asserts #3 failed stays prose.

The three guarantees

Every line this file produces is written into scrollback or into a retained buffer and is final. Three rules follow, and each one is a test.

1. Nothing is reflowed that changes meaning

Prose is wrapped at word boundaries, which is better than the terminal's own wrap. A line inside a fenced code block is never wrapped at a word: it is continued at the exact column the window ends, which is what the terminal itself would have done, and joining the rows back together reproduces the source byte for byte.

crates/emma/src/term/markdown.rs · code_rows

/// A line inside a fenced block, split only where the window ends.
///
/// **Never at a space.** Wrapping code at a word boundary changes what it says;
/// the terminal would have broken it at the last column anyway, and breaking it
/// here as well means the row count `frame.rs` reserves is right.
fn code_rows(text: &str, width: usize, skin: &Skin) -> Vec<Line<'static>> {
    let style = skin.palette.style(Role::Info);
    if text.is_empty() {
        return vec![Line::from(Span::styled(String::new(), style))];
    }
    let mut rows = Vec::new();
    let mut rest = text.to_string();
    while !rest.is_empty() {
        let (head, tail) = split_at_cols(&rest, width);
        if head.is_empty() {
            // A single glyph wider than the whole window. Emit it rather than
            // spinning: a lost character is worse than a row that is one column
            // over on a terminal two columns wide.
            rows.push(Line::from(Span::styled(rest, style)));
            break;
        }
        rows.push(Line::from(Span::styled(head, style)));
        rest = tail;
    }
    rows
}

tested: a_fenced_code_block_is_never_reflowed_and_never_loses_a_character is written as “the rows concatenate back to the source” because word-wrapped code would stay under the width and still be wrong. It then renders the same text outside a fence and asserts that one does break at a space, so the first assertion tests a real distinction.

2. Nothing is inserted into what a reader copies

No gutter down the side of a code block, no │ in front of a quote, no added indent. The markers this file removes, the hashes of a heading, the ** of a bold run, the backticks around a code span, are removed because that is what rendering them means, and nothing takes their place. The quote's > is kept rather than swapped for │, because the swap “would put a character into the copy that the model never wrote.” It is kept as "> " with the source's own space, so the marker column costs the copy nothing and the text lines up under itself when it wraps.

The fence itself is not printed, on the ground that ``` on a screen is three characters of syntax; a dim rule takes its place with the language written into it. It is the block's own row either way, so nothing a reader copies out of the code gains a character.

3. Every row fits the width it was given

insert_before is told in advance how many rows to make room for, and that count is ceil(width / columns). A row wider than the window takes a row more than was reserved and its tail lands on the viewport. So the wrap is what keeps the arithmetic in frame.rs true. tested: no_row_is_ever_wider_than_the_window renders a five-line document, including an unbreakable word, at widths 8, 12, 20, 40 and 80 and checks every row.

Defect: two paths can still emit an over-wide row

rule builds a fence's replacement as {head} {lang} {tail} where tail_room = width.min(72).saturating_sub(cols(&head) + cols(&lang) + 2). The subtraction saturates, but the pieces in front of it do not: at width 8, ```typescript gives a two-column head, a ten-column language and two spaces, so the row is fourteen columns wide with a tail_room of zero. The guarding test's document uses ```rust, which is exactly eight columns at width 8 and fits.

flow has the mirror case. hang is clamped to width - 1, but the lead spans are pushed into cur before any wrap can occur, so a list item whose indent plus bullet plus space exceeds the width starts over budget. The refusal at indent > 12 bounds it, but 12 plus a bullet plus a space is 14, and the fallback gate allows a 24-column window. unverified for both: reasoned from the arithmetic, not reproduced. A two-case test at width 8, one rendering ```typescript and one rendering twelve spaces then - x, would settle it.

Two inline constructs, and the one that is absent

inline resolves code spans and bold runs and nothing else. The choice of which two is the judgement: “one is a colour, the other is a weight, and both exist at every fidelity down to a monochrome console.”

Italic is absent, and the region comment gives three reasons: Modifier::ITALIC is not written by render::codes, several terminals render it as reverse video, and a * in running prose is more often a footnote or a glob than an emphasis. Leaving the asterisks alone shows the reader exactly what the model wrote.

Emphasis is applied on top of the surrounding block's style, so a bold word in a heading stays the heading's colour and a code span in a quote is still dim behind its own colour. code_style is the mechanism: it takes Role::Info's colour and copies the base's add_modifier over it. tested: bold_and_inline_code_are_styled_and_their_markers_go checks the code span is coloured across every word of it, because “wrapping splits spans, and a style that survived only the first word would look right at this width and wrong at a narrower one.”

The wrapper, and the hanging indent

flow(lead, body, width, hang) is the prose path. lead is drawn once on the first row (a bullet, a >) and counts toward that row's width; hang is how far the rows after it are indented, “so a wrapped list item lines up under its own text” and reads as one item rather than as two.

Two mechanisms inside it. tokens splits the styled spans into runs of whitespace and runs of not-whitespace, carrying each span's style, so a wrap can happen between words without losing where a style boundary was. And pending holds the space before a word rather than after it, so a line break eats the space rather than leaving a trailing one on the row above. A word longer than the window has nowhere to go but across rows, and “a character boundary is the only honest place to put the break.” tested: prose_is_wrapped_at_words_to_the_width_it_was_given asserts both the widths and that the joined words are the original sentence.

What may reach a cell

crates/emma/src/term/markdown.rs · sanitise

/// What may reach a cell.
///
/// A model can put anything in its prose, including the escape byte that would
/// otherwise be written straight into the terminal — where it is a control
/// sequence rather than text, and where ratatui counts it as a column the
/// terminal does not. That is the same class of defect the status line already
/// refuses (`view.rs`), applied to the one other thing on screen that comes from
/// outside. Tabs become spaces because a tab in a cell has no width anybody
/// agrees on; everything else that is not printable is dropped.
fn sanitise(raw: &str) -> String {
    let mut out = String::with_capacity(raw.len());
    for ch in raw.chars() {
        match ch {
            '\t' => out.push_str("    "),
            '\r' | '\n' => {}
            c if c.is_control() => {}
            c => out.push(c),
        }
    }
    out
}

tested: an_escape_byte_in_the_models_prose_never_reaches_a_cell feeds hello \x1b[31mred\x1b[0m \x07 and\ttabs and asserts no control character survives and that the words did, so the test checks translation, not refusal to draw.

Two smaller defects, both about a promise slightly overstated

heading ends with .trim_end_matches('#').trim_end(), which drops a trailing hash that is part of the text: # C# renders as C. CommonMark's rule requires the closing sequence to be preceded by a space, and this implementation does not check for one.

sanitise expands a tab to four spaces, and it runs on every line including the ones inside a fence. So the guarantee that a fenced block's rows concatenate back to the source does not hold for tab-indented code: the rows concatenate back to a spaces-for-tabs version of it. Both facts follow from reading the two functions; neither is a crash and neither has a test. unverified: rendering # C# and a tab-indented fenced block and comparing against the source would settle both.

One malformed answer must not style the next one

Markdown::reset is one line and exists for one failure: a model that opens a fence and never closes it would otherwise leave the next answer rendered as code, “one malformed reply poisoning every reply after it, which is a worse failure than the malformed one.” Frame::flush_prose calls it at the end of every inline turn, and the full-screen path re-runs a fresh Markdown per entry, so neither can carry a fence across an answer. tested: an_unclosed_fence_does_not_leak_into_the_next_answer.

What is not understood is printed

Tables, images, links, HTML spans, footnotes and *italics* all reach the screen as the text they were written as. Content is never swallowed: the worst case is plain. tested: what_is_not_understood_is_printed_rather_than_swallowed asserts six needles including | a | b |, [a link](https://example.com) and <div>html</div> survive intact.

Coverage

markdown.rs is 891 lines (wc -l, 2026-09-06; 886 when this page was written) and was read in full for this page. It declares 20 function items above the test boundary: four Markdown methods (new, reset, in_code, line), six recognisers, four inline helpers (inline, flush, code_style, and the local cols), four fitting functions (flow, tokens, split_at_cols, code_rows), rule and sanitise. All 20 are named here: 20 of 20. Ten of its sixteen tests are cited; the six that are not are the degradation checks (ASCII, sixteen-colour, no-colour) and three shape tests for quotes, blank lines and lists.

Not settled here. Whether the rendered result reads as markdown. Every test compares strings and widths; nobody has looked at a heading, a bullet list and a fenced block side by side on a console and judged the result. unverified: one real answer containing all four block kinds, photographed.
