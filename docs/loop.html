Running a goal

The agent loop

Send a request, receive a turn, run whatever tools it asked for, put the results back in the conversation, send again. Everything else in this chapter is a rule about when that stops, plus one rule, the memo, about when a tool call is refused before it is ever run.

The shape of it

The loop is Agent::run_goal, one function of about 370 lines. I kept every decision about what ends a goal visible in one place rather than spread across helpers that each look harmless. Everything a tool call does is Agent::run_tool_call. Read those two together, because the memo rule is split between them and reads as nonsense in either alone.

crates/emma/src/agent.rs — Agent::run_goal, Agent::run_tool_call

goal.rs is the other half: the text a run is held to, the trait that answers "is this met?", and the filter that keeps the completion marker off the screen without keeping it from the loop. Between them the two files are, for me, what separates this from a chat client.

crates/emma/src/goal.rs

Four properties hold across the whole chapter, and each is here because I paid for it somewhere else first. A session is one conversation and a goal is a turn in it. A tool failure is a tool_result, never an abort. A call that failed is not repeated identically until something else has succeeded. An assistant turn is echoed back exactly as it came. The fifth, that budgets are enforced and aborting costs what it spent, is the one that decides when any of it stops.

The pages

  1. One turn, end to end Three guards, a request built from four parts, the model call and the two things racing it, and where a received turn is held until something knows where it goes.
  2. Failure as an observation Seven ways a tool call can go wrong, one closure they all reach, and what the model is handed instead of an abort.
  3. The memo rule Why an identical failing call is refused, why the refusal lifts the moment anything succeeds, and why neither half of the rule is written where you would look for it.
  4. How a goal ends Nine endings, four of them decided by a ladder whose order is the whole rule, and the three variables that carry its state.
  5. The kick What the model is told when it stops without claiming completion, why the list of what has already failed is included, and the two bounds that stop it firing forever.
  6. Budgets, and three token numbers Five bounds with three different shapes, the weighted number a budget is tested against, the estimate that enforces nothing, and the meter a delegated run can reach.
  7. The goal, and how done is decided All of goal.rs: what a goal is, the trait, the marker the model prints, the streaming filter that hides it, and the weakness that the acting model grades its own homework.
  8. Seams How a test replaces the network without replacing anything else, how Ctrl-C reaches a call in flight, and what happens when the user changes model mid-conversation.

What this chapter covers

Every function in both files is covered on one of the eight pages, public and private: 49 of 49 in agent.rs outside its test module, and 19 of 19 in goal.rs. All five of agent.rs's own unit tests and all eleven of goal.rs's are named where the behaviour they cover is described. Each page ends with a list of what it covered and a section saying what it could not verify. certified by counting fn items in each file outside mod tests and matching them against the per-page coverage lists.

Two things this chapter hands off rather than covering. Compaction's code lives in agent.rs and its behaviour is described on Sessions & context; the loop's side of it is on Budgets. The approval gate is passed through on Failure and described on Consent & permissions.

What the chapter could not verify

unverified Nothing in this chapter was certified against a live provider call. The suite passes at this checkout: cargo test -p emma --test loop printed test result: ok. 35 passed; 0 failed and cargo test -p emma --lib printed test result: ok. 1065 passed; 0 failed; 14 ignored on 2026-09-02. No mutations were run, because this pass was not permitted to change source, so every tested chip in the chapter means "a test covers this and its author recorded it as mutation-checked" rather than "I watched it go red". tests/loop.rs's header is where that record lives. What would settle it: for each guarantee, delete it in agent.rs, run the named test, confirm the failure, restore. That requires a source edit this round cannot make.
