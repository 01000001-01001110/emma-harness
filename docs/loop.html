Running a goal

The agent loop

Send a request, receive a turn, run whatever tools it asked for, put the results back in the conversation, send again. Everything else on this page is a rule about when that stops, plus one rule, the memo, about when a tool call is refused before it is ever run.

crates/emma/src/agent.rs · crates/emma/src/goal.rs
certified proven, and a reader can repeat it: a file, a command, a grep
observed seen once, live, not repeatable on demand
tested a test covers it
unverified believed, not checked

The loop lives in Agent::run_goal. It is one function of about 370 lines: every decision about what ends a goal is visible in one place rather than distributed across helpers that each look harmless. The two functions worth reading together are run_goal and run_tool_call. The memo rule below is split between them and reads as nonsense in either alone.

crates/emma/src/agent.rs — Agent::run_goal, Agent::run_tool_call

One turn, end to end

A turn begins with a Request assembled from four things: the harness instructions with goal::standing_contract(done) appended, the tool definitions, history (the whole session conversation, every finished goal in order), and query, the goal in flight. The standing contract is appended to the system prompt rather than prepended to the user's message, and that placement is a reversal: it used to wrap every goal, and typing Hello produced a model that ran pwd && ls -la before saying hello. A preamble applied to every input is an instruction the user did not write and cannot see.

crates/emma/src/goal.rs — Goal::opening, standing_contract

The assistant turn is echoed back exactly as it arrived. What goes into query is AssistantTurn::content, the provider's own blocks, thinking blocks and signatures included. Nothing rebuilds a turn from its text plus its tool calls, because a re-derived signature is rejected on the next call, which puts the symptom one step away from the change that caused it. tested the_assistant_turn_is_echoed_back_exactly_as_it_arrived asserts the intact tool_use block is present in the message that was actually sent back, not merely somewhere in the transcript.

crates/emma/src/agent.rs · crates/emma/tests/loop.rs

Holding the turn is what makes the placement rule single. pending_turn carries the received turn until the loop knows where it goes: beside its tool results, beside a kick, or on the end of the conversation once the loop breaks. A turn whose tools were never run cannot go anywhere. This is the Ending::Tokens case, where the budget fires between receiving the turn and dispatching it, and session::place_turn drops it rather than leaving an unanswered tool_use in the history. Four branches each deciding that separately is the version of this that produced a 400.

crates/emma/src/agent.rs — place; crates/emma/src/session.rs — place_turn

Failure as an observation

A tool failure is a tool_result with is_error set, and the loop continues. This is the property the crate is arranged around, and it is here because it was paid for elsewhere: in the predecessor project, five of eight failure classes ended turns silently, the user saw "Something went wrong on my side", and the model never learned anything had failed.

crates/emma/src/agent.rs — module doc

The reason the guarantee is checkable rather than merely asserted is that every failure path converges on one closure. fail() is defined at the top of run_tool_call and is the only way out of that function that is not a success: it builds the block, logs it under the same record kind a successful result gets, and returns the label the kick will quote. Seven distinct things can reach it.

Even the outer error is not an abort. A tool's invoke returns Result<Result<Outcome, ToolError>>: the inner error is an ordinary failed call, and the outer one is the tool saying the session cannot continue. That second one also becomes a tool_result the model can read. The loop's own budgets stay the only things that end a goal.

crates/emma/src/agent.rs — run_tool_call

Exit status is not a failure signal anywhere in this file. ToolError is the only one. A non-zero Bash exit comes back as Ok with exit status <n> in the content, so grep -q answering "no" is not a broken shell: it does not enter the memo and is not painted as an error on the terminal. Nothing in the loop branches on a tool's identity, on ToolError::kind, or on exit status, which is what let the Bash contract change land here without an edit, and it is also what makes Delegate an ordinary tool.

crates/emma/src/agent.rs — module doc; tools/fs/src/bash.rs
What each half carries

is_error is what the API and the model's own training key on. The JSON body, { kind, tool, detail }, says which failure it was and what to do instead. A failure rendered without the flag reads to the model as a successful call that returned odd text. tested a_failure_block_is_flagged_and_typed asserts the flag on the wire and asserts that a success carries no is_error key at all.

crates/emma/src/agent.rs — failure_result and its unit test

The memo rule, whole

A call that failed is not repeated identically until something else has succeeded. Not "never again this turn": that is affordable only when the whole tool surface is one read-only search. Emma's working rhythm is run the tests, see them fail, fix a file, run the tests again, and a memo keyed on the call alone would forbid the second run, which is the one that proves the fix.

The rule is split across two functions and neither half states it. run_tool_call only reads: if this call's memo_key is in the set it was handed, refuse it with already_failed and never reach the tool. run_goal only writes: clear the entire set the moment any tool succeeds, insert into it when one fails. The rule emerges from the pair: "this exact call failed and nothing has changed since", not "this call failed once".

Both halves are covered, and the second test is the one that matters, because a stricter memo passes the first. tested a_failed_call_is_not_repeated_with_the_same_arguments scripts the identical call twice and asserts the tool was reached once; a_failed_call_may_be_repeated_once_something_else_has_succeeded scripts fail–succeed–fail and asserts the tool was reached twice.

crates/emma/tests/loop.rs

Two details that are easy to get wrong. The memo is checked after argument validation and before the hooks and the gate, so a refused call costs nothing at all: no hook process, no prompt. And the memo survives --resume: dropping it would not overspend anything, but it would hand the resumed model back the identical failing call as its most obvious next move, which is exactly the loop the memo exists to break.

crates/emma/src/agent.rs — run_tool_call, Resumed::failed_now

How a goal ends

When a turn contains no tool calls, the model has stopped, and four rules decide what that means. They are order-dependent and the order is the whole rule. Each one is written to be true only given that the ones above it already answered no.

Verdict first, so a model that claims completion on its first breath is Done and not something else. Put the answered rule above it and every one-shot goal, the ones where nothing needed changing, collapses into an ending nothing downstream treats as success. tested a_first_turn_that_claims_completion_is_still_done.

Stall second, so a model that has already been nudged is judged by the rule written about being nudged. The stall condition is no tool call since the last kick, and a kick has been sent in this run. Note kicked rather than kicks > 0: the kick count comes back across a resume, but a resumed run's last nudge was answered by a human typing a new goal, so reading the budget here would end every resumed run on its first stop and report it as a stall. tested a_model_that_abandons_started_work_twice_is_believed asserts kicks == 1, proving the stall rule fired rather than the count running out.

Answered third, which leaves it meaning exactly what it says: no tool has been called in this goal, and nothing has been asked of the model that it has not already answered. This ending exists because the owner typed hello and was told his exchange had stalled. It is not a failure. Ending::Answered's message is not phrased as a stop, because nothing went wrong and the answer is already on the screen above the line. The distinguishing signal is tool use, not wording: worked is per goal, not per turn, so one tool call anywhere earlier makes every later stop a stall again, however conversational the sentence it stopped on. tested, and the narrowness has its own test, one_tool_call_earlier_in_the_goal_is_enough_to_make_a_stop_a_stall, because the obvious simplification ("did this turn use a tool") passes every other test in the file while quietly deleting the stall rule.

Kick budget last. Reaching it means the goal was genuinely being worked and the nudges ran out; Ending::KicksExhausted says so and adds the sentence that matters after an unfinished run: what was changed is on disk; nothing was rolled back.

crates/emma/src/agent.rs — run_goal, Ending; crates/emma/tests/loop.rs

worked is set on the tool-call attempt, before the gate runs. A model whose only call was denied at the approval prompt is still mid-task, and the stop that follows is a stall to be nudged rather than a greeting.

crates/emma/src/agent.rs — run_goal

Every ending names the limit that fired

The remaining endings are the budgets, the user, and the provider: Iterations, Tokens, Deadline, Interrupted, Provider(String). None is silent. Ending::message renders each with its number in it, because "I stopped" without a reason is indistinguishable from a crash. tested every_ending_says_which_limit_fired asserts that the four budget messages each contain a digit, a weak assertion that catches the real regression, which is a tidy-up replacing the number with prose.

crates/emma/src/agent.rs — Ending::message

A goal joins the conversation whatever the ending. A run that hit its token budget still happened, and the next goal in the session must not be told a story in which it did not. If the abandoned goal's last message was a user turn, trailing tool results or an unanswered kick, the next goal's opening would make two user turns adjoin, which is a 400 rather than a conversation, so close_previous_goal inserts a note: [The previous goal stopped before it was finished: <ending>.]. The same sentence is composed by the session fold from the recorded ending, so a resumed conversation is not one message different from the one that was sent.

crates/emma/src/agent.rs — close_previous_goal, ended_note; crates/emma/src/session.rs

The kick

The kick is what makes this a loop rather than a chat client. When the model stops and the check says the goal is not met, the loop pushes a user message and goes round again. It carries three things: why it is not recorded as done, the goal restated verbatim, and up to five of the calls that have already failed in this goal. 

// goal::kick, composed
The goal is not recorded as done: {why}. Nothing has been lost — you
still have every tool, and the goal is unchanged:

{goal text}

Continue working on it.

These calls failed earlier in this goal — change the approach rather
than the spelling:
- Bash(cargo build --release)
crates/emma/src/goal.rs — kick

The failure list is the part that is easy to leave out and expensive to leave out: without it, the plain reading of "continue" is "try again", and the first thing a model retries is the thing that just failed. The labels come from label_of, the same rendering the memo key is built from, and the goal remembers up to 20 distinct ones, oldest dropped first, of which a kick quotes the last five.

crates/emma/src/agent.rs — label_of, trim_oldest, FAILED_EVER_MAX

Two independent bounds stop it firing forever, and the goal ends the moment either is reached: max_kicks (default 3), a hard count for the whole goal; and the stall rule, which needs no cooperation from the model at all. Both sit under the iteration, token and wall-clock budgets, so the worst case is bounded by arithmetic rather than by good behaviour. The cost is that a goal genuinely needing a fourth nudge stops one step early. It says which limit stopped it, so the user can raise it. tested the_kick_is_bounded_by_its_budget sets max_kicks = 2 and asserts the seventh scripted turn was never requested, so the bound is real rather than merely reported.

crates/emma/src/goal.rs — module doc; crates/emma/tests/loop.rs

Budgets, and three different token numbers

Five bounds, and they exist separately because they fail differently: a model calling one cheap tool forever is caught by iterations and not by tokens; a model reading enormous files is caught by tokens and not by iterations.

Bound Default Shape What it bounds
max_iterations 60 ceiling, tested before the call Model calls in one goal. A run never makes more than this many.
max_tokens 500,000 tripwire, tested after the call What one goal may spend, weighted by price.
wall_clock 30 min tripwire, tested at the top of an iteration When the loop will decline to start another iteration.
max_kicks 3 ceiling Nudges after the model stops without claiming completion.
max_context 120,000 threshold, triggers compaction How large one request's input may get. The only bound here that is about the session rather than the goal.
crates/emma/src/agent.rs — Budgets, Budgets::default

Three token numbers, three jobs

Every model call produces three different token figures, and assuming any two are the same is how this project got a budget that fired on the length of the conversation instead of on the bill.

Number Arithmetic Job
cost_tokens(usage) input + 1.25×cache_write + 0.1×cache_read + output The only number max_tokens is tested against. Weighted because a cache read is billed at a tenth of what it weighs.
billable_total_tokens() the provider's own unweighted total Logged raw beside the four provider fields. Answers "how much context did this call carry", which is a different question.
billable_input_tokens() the provider's reported input for the call Stored as last_input and tested against max_context to decide compaction. Measured, so it includes the system prompt and the tool schemas.
crates/emma/src/agent.rs — cost_tokens, run_goal's model_call record, compact_if_needed

A fourth number exists and enforces nothing: estimate(), chars / 4, the same conservative ratio the packer in emma-llm uses and documented there as under-counting what the provider bills. It decides how much to drop once a measured number has already said dropping is necessary, and it stands in for the measurement on the one call of a process that has none: a resume into a large session. It never fires a budget.

crates/emma/src/agent.rs — estimate
The token budget is a tripwire, not a ceiling

spend.get() > max_tokens is tested after the call returns, so the call that crosses the line is paid for in full and the overshoot is bounded only by how large one request can be. A 500,000 budget stopped a real run at 579,565. certified. The session file is ~/.emma/sessions/sess-1786385316950-34808.jsonl, and its goal_finished record reads "tokens":579565. Grep it and see. The figure is also quoted in Budgets::max_tokens's doc and in the test comment that prompted the rewording; both are attributions to this run rather than independent evidence.

The mechanism itself is not in doubt. tested the_token_budget_stops_the_loop_and_the_run_is_charged_for_what_it_spent sets a budget of 15, scripts two calls costing 10 each, and asserts the outcome is Ending::Tokens with 20 spent, an overshoot of one call, and that the session log records the 20 rather than recording an aborted run as free.

Making it a true ceiling would mean gating on an estimate of the request before sending it, and the only estimator available is the one that under-counts. A gate built on it is wrong in both directions while sounding exact, so the wording says plainly what the check does: Ending::Tokens says the check runs after each call, and there is a test asserting the message admits it. Promoting this to a measured pre-call headroom check is item 0 of notes/plan-loops-stage-1.md and item 20 of notes/improvements.md; it matters most for the unattended runs that plan is about, because the person who set the budget is no longer watching the meter.

crates/emma/src/agent.rs — Budgets::max_tokens, Ending::Tokens, the_token_budget_is_described_as_the_tripwire_it_is

Usage is recorded before the budget is tested, so a run that dies on the cap is recorded having spent what it spent. In the predecessor project the counter only reached the log on a completed turn, which made aborting the cheapest way to spend money. The meter is Spend, an Arc rather than a local, because a delegation is a second loop spending the same budget and cannot reach a local. A nested run gets its own meter whose every add also lands on the parent's, so a subagent's spend charges the parent as it happens. set, the per-goal reset, does not follow the parent link, or a nested goal would zero the meter of the goal paying for it.

crates/emma/src/agent.rs — Spend

max_context is also what keeps max_tokens reachable in a long session: input per call is bounded by compaction, so the number of calls a goal gets is bounded below by roughly max_tokens / max_context, four at the defaults, and in practice far more, because most calls sit nowhere near the cap. Raising the context cap without raising the token budget buys context by spending calls. When a goal opens with enough conversation behind it that the budget is worth about four calls, the loop says so before the first request rather than stopping later with a number the user cannot connect to anything.

crates/emma/src/agent.rs — Budgets::max_context, warn_if_the_budget_is_nearly_spent_on_arrival

DoneCheck, MarkerClaim, and the model grading itself

DoneCheck is the authority the loop consults when the model stops. It is a trait with three methods: name() for the log, contract() for what the model is told about how completion will be judged, and an async verdict() returning Done::Yes or Done::No(why). The loop knows nothing else: it asks for a verdict and composes a kick from whatever reason comes back. The trait is async because every alternative authority reads a file or runs a process.

crates/emma/src/goal.rs — DoneCheck

The shipped implementation is MarkerClaim: the model must end its final message with the line GOAL COMPLETE. Stopping without it is treated as stopping mid-work. The check is tolerant about decoration (**GOAL COMPLETE** means the same thing and spending a kick on formatting would be silly) and intolerant about position: the marker must own its line, so "I will print GOAL COMPLETE when the tests pass" is not a claim. tested a_marker_on_its_own_line_is_a_claim_and_a_mention_is_not.

crates/emma/src/goal.rs — MarkerClaim, claims_done

The marker never reaches the screen. MarkerFilter is a streaming state machine that holds only a line which could still become the marker and releases it the instant a character rules that out: in prose, a one- or two-character pause on a line beginning with g. It is applied on the way to the terminal only; verdict still reads the model's real text, and Outcome::text keeps it verbatim, marker and all. tested, including a marker cut across four streamed fragments, and the inverse case where a sentence about the marker must not be censored.

crates/emma/src/goal.rs — MarkerFilter
The largest known weakness: the acting model grades its own homework

MarkerClaim asks the model that just did the work whether the work is done, and accepts a line of its own prose as the answer. Nothing in the loop verifies the claim. The accurate statement of the guarantee is "the loop will not stop before the model says it is finished", not "the loop stops when the work is finished". goal.rs's module doc says this in its own words rather than leaving it to be discovered.

crates/emma/src/goal.rs — module doc

Three other authorities were considered and each fails in a specific way. Stopping when the model stops costs nothing and catches nothing. A model that runs one command, reads the first error and writes "this looks like a session-API mismatch" has stopped, and the goal is untouched; that is the behaviour Emma exists to not have. A check command exiting zero touches reality and passes vacuously: cargo test on a target with no tests, a test -f against a path that was already there, a suite whose failing case was deleted rather than fixed. No open tasks remain is the most legible, because a user can watch the file in an editor, and legible is not honest: a model that learns closing tasks ends the loop will close them, and a model that never opened one has an empty list from turn zero, which reads as done before it has started.

The intended upgrade path is not to replace one signal with another but to make bookkeeping insufficient: use the task count to decide when to stop asking, and gate the verdict behind something the model does not author. That is a second impl and a different value in Setup, not surgery on the loop, which is the entire reason DoneCheck is a trait. notes/plan-loops-stage-1.md designs a third implementation along those lines: a cheap second model call as an independent judge, whose "no" costs one kick and is bounded by max_kicks exactly like any other not-done. It is not built.

crates/emma/src/goal.rs — module doc; notes/plan-loops-stage-1.md

goal.rs's module doc says DoneCheck "has one implementation today". There are two: MarkerClaim, and SubagentClaim in delegate.rs, which is MarkerClaim's contract plus the paragraph telling a subagent that its final message is the only thing reaching its caller. The seam was used, and the doc predates the use. certified. Grepped for impl DoneCheck across crates/ at commit 20ac400: three hits, of which one is a test double inside goal.rs's own tests. What the research says about grading by model

notes/research-loops-goals-and-cost.md collected the numbers behind "LLM-as-judge is brittle", and they are worth having before anyone builds the judge check, because the failure is not that a judge is a coin flip. It is that the reassuring number is the wrong number.

  • Chance-corrected agreement with human raters (Cohen's κ) ranged 0.376–0.511 across 21 judge models, with the best two at 0.511 and 0.489.
  • Raw exact-match agreement overstates the judge by 33.8–41.3 percentage points, because much of the apparent agreement is what two graders would hit by chance on a task with few possible verdicts. The widely repeated "greater than 80% agreement, matching human-human agreement of 81%" is the uncorrected figure.
  • Position bias ranged 0.002 to 0.192 between judges, and two production models showed test-retest reliability above 0.95 while showing position bias above 0.10, the "consistency-bias paradox". A loop cannot detect this by asking the judge twice.
  • Position-flip rates rose from a median of 0.09 on easy tasks to 0.17 on hard ones: the bias is worst exactly where the judgment matters.
  • Separately, METR's evaluations of o3 and Claude 3.7 Sonnet found reward hacking in 30%+ of evaluation runs: monkey-patching graders, manipulating scorers. That is the failure a verifier invites rather than prevents.

unverified. These are figures quoted from that note, not measurements taken here, and the note itself flags that the METR 30% figure came from a secondary aggregation it could not re-confirm against METR's raw report. What would settle them: reading arXiv:2606.19544 and METR's own evaluation pages directly. Nothing in Emma's shipped loop depends on them; they bound how much to trust the judge check when it is built.

The scripted-provider seam

Everything with a decision in it lives in the library, not in main.rs. Agent::run_goal takes a Setup whose provider is an Arc<dyn Provider>, whose done is a &dyn DoneCheck, and whose term can be Term::silent(). So a test constructs the real Agent, the real Registry, the real Harness and the real approval gate, and swaps out exactly one thing: the network.

crates/emma/src/agent.rs — Setup; crates/emma/tests/support/mod.rs

The fake provider answers from a script of turns: text, tool calls, a token cost, or a BadRequest rejection, and it records every request it was sent. That last half is what makes the tests assertions about behaviour rather than about return values: a test can check what the model was told, which is where most of this file's guarantees actually live. the transcript contains "already_failed", the kick restated the goal, the model was told the denial cannot be approved away: none of those is observable from an Outcome.

crates/emma/tests/support/mod.rs — Fake, Say

What it buys, concretely: 22 tests covering the failure-is-an- observation property, both halves of the memo, both budget shapes, every ending on the ladder, the approval ordering, and the byte-for-byte round trip through the session file, all running without a network, an API key, or a terminal. certified. cargo test -p emma --test loop at commit 20ac400 printed test result: ok. 22 passed; 0 failed in 0.04s.

crates/emma/tests/loop.rs

The limit of the seam is worth stating in the same breath. A scripted provider agrees with its author about what the wire looks like, and this project has already shipped a strict decoder that passed every test and then decoded no real tool call, because the live API adds a key the model did not know about. Tests built on the fake prove the loop's decisions; they prove nothing about the wire.

What is not verified

Everything below is a gap in this page's evidence, not a rhetorical flourish.

The suite passes; I did not re-run the mutations

unverified tests/loop.rs's header states that every test in it was validated by mutation: the guarantee removed from agent.rs, the test confirmed to fail, the guarantee restored. I ran the suite (22 passed at 20ac400) but ran no mutations, because this task was not permitted to change source. Every tested chip on this page therefore means "a test covers this and its author reports it was mutation-checked", not "I watched it go red". What would settle it: for each guarantee, delete it, run the named test, confirm the failure, restore.

Nothing here was run against a live model

unverified No claim on this page was certified against a real provider call. The behaviours most exposed to that gap are the ones about what the model does with what the loop sends it: whether a real model reliably ends with the marker, whether a kick carrying five failed labels changes its approach rather than its spelling, and whether the already_failed observation reads to a real model as an instruction to change route. What would settle it: a live session with --max-kicks forced low, and the session JSONL read back.

The wall clock is a tripwire and is not worded like one

certified by reading the function: started.elapsed() > wall_clock is tested only at the top of an iteration, and neither tool.invoke nor call_model is wrapped in a deadline: call_model's select! races the stream against the interrupt only. So wall_clock bounds when the loop will decline to start another iteration, not how long a goal can take, and Ending::Deadline's "hit the 1800s time limit" reads as a ceiling in exactly the way Ending::Tokens was reworded to stop doing. A long tool call is bounded by that tool's own timeout: Bash has one, and a tool that has none is bounded by nothing in this file. This is flagged, not fixed; see the defects note below.

crates/emma/src/agent.rs — run_goal, call_model; tools/fs/src/bash.rs

Ctrl-C during a tool call

unverified The interrupt is checked at the top of each iteration and raced against the model call. It is not passed to ToolCtx, so a Ctrl-C pressed during a long Bash run appears to be observed only when that call returns. I read this from the source and did not reproduce it. What would settle it: run a goal whose tool sleeps for 60 seconds, press Ctrl-C at 5, and time how long the process takes to report interrupted.

crates/emma/src/agent.rs — Interrupt, run_tool_call; crates/tool-api/src/lib.rs — ToolCtx

The fold's reliance on a convention

certified by reading both files: the session fold has no arm for denied, tool_failed, tool_fault or tool_unknown, and it does not need one, because each of those paths also writes a tool_result record. That is correct today. Every one of them goes through the same fail() closure, which calls log_result_block, but it is a convention held by one closure rather than a property the type system enforces. A new failure path added anywhere in run_tool_call that returns without going through fail() would produce a session file that folds back into a conversation the API rejects, and nothing would say so until a resume.
