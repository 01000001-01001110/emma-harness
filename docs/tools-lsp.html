Code intelligence: asking a language server

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP screenshot

Grep finds a name. It cannot tell a call from a comment, does not know that Config here is the type declared over there, and cannot answer what breaks if a signature changes. These five tools ask a language server's own understanding instead, and the whole crate is arranged around one rule: an empty answer is only an answer when the index was complete.

The five tools

ToolArguments

All five declare the same const READ_ONLY: ToolMeta: read_only: true, reaches_network: false, idempotent: true. None of them prompts. 

fn position_schema(extra: Option<(&str, Value)>) -> Value {
    let mut properties = json!({
        "file_path": { "type": "string", "description": "A Rust file inside the working directory." },
        "line": { "type": "integer", "minimum": 1, "description": "1-based line number the symbol appears on." },
        "symbol": { "type": "string", "description": "The symbol's name as it is written on that line. Emma finds the column; it refuses rather than guessing if the name appears more than once." },
        "occurrence": { "type": "integer", "minimum": 1, "description": "Which occurrence on the line, 1-based. Only needed when the name appears more than once." }
    });

A name rather than a column, because asking a model for a column offset gets a plausible number and a plausible number is a wrong answer about the symbol next door. The shape also means Grep output feeds straight in, which is the workflow: grep to find candidate lines, then ask the compiler which of them is real.

tools/lsp/src/tools.rs — position_schema, READ_ONLY

What every call does before asking

prepare is five steps in a fixed order: contain the path, refuse anything that is not .rs, read the file, get a client for the root, and push the current bytes to the server. Containment comes first, before the file is read and before a process is started, because a path outside the root must not so much as cause a spawn.

The push is not optional. An agent's rhythm is Edit then ask, and a server answering from the version it opened before the edit returns positions into a file that no longer exists. sync_document compares a hash of what the server was last told and sends didChange when the bytes have moved.

Quoting the line is what turns a retry into a correction, and the ambiguity case is a refusal rather than a guess for a reason its doc gives: in foo(foo) the two are a call and an argument, and answering about the wrong one produces a confident, wrong, unfalsifiable result.

The column sent on the wire is a UTF-16 offset, because that is what LSP counts in. byte_offset is the inverse and exists for the same reason.

A launcher is the program that has to be on PATH before an entry point can run at all, which is a different absence from the server being missing. Direct executes the entry point; Node, Dotnet and PowerShell put node, dotnet or pwsh in front of it. On this Windows box the PowerShell entry point is present inside ms-vscode.powershell-2025.4.0 and there is no pwsh, because Windows PowerShell 5.1 is a different program, so the refusal names the launcher and how to install it for the host it is running on rather than telling a Windows user to brew install node.

There are now three refusals rather than one, because the reader should learn the rule rather than the verdict. unsupported_language lists the extensions that are served, computed from the table so it cannot drift from it. disabled_language is the paragraph above. yaml_not_ansible is the case an extension cannot decide: .yml is handed to a playbook server only when the tree says Ansible, meaning an ansible.cfg at the working directory or one of a fixed list of path segments, because answering about a compose file or a CI workflow with a playbook server would produce a result that reads exactly like a real one.

And when no server can be found at all, the refusal declines to substitute in the same terms: Emma will not answer these questions with text search instead: a reference list produced by grep is a different answer to a different question, and nothing in the result would say so. It also names what it looked for, where, and any candidate it found and rejected.

Which binary, and the probe that Bash does not do

  1. EMMA_LSP_SERVER, if set to anything but whitespace. If what it names is not there, or is there and does not identify itself, the call is Unavailable and says which. It never falls back.
  2. rust-analyzer on PATH.
  3. The server inside the VS Code extension: ~/.vscode/extensions/rust-lang.rust-analyzer-*/server/, and the .vscode-server spelling used by remote and WSL installs. Highest version wins.
  4. Nothing, with a refusal naming both opt-ins.

Every candidate is probed with --version before it is chosen, and that is where this diverges from Bash, which classifies by filename precisely so it never executes a candidate to find out what it is. A shell's selection argument is -c, so probing a shell means running something; --version runs nothing. 

//! ```text
//! $ rust-analyzer --version
//! error: Unknown binary 'rust-analyzer.exe' in official toolchain '…'
//! ```
//!
//! `~/.cargo/bin/rust-analyzer` exists as a rustup proxy whether or not the
//! component behind it is installed. It is first on `PATH`, it is a real file,
//! and it exits **0** while printing that to stderr — so a chosen-by-existence
//! search picks a binary that will never speak LSP, and the failure surfaces
//! much later as a handshake that times out. Measured on this machine on
//! 2026-08-11, which is why the search costs one process spawn.

The probe requires stdout to start with rust-analyzer, because the rustup proxy prints its complaint to stderr and exits 0, so neither the exit status nor the presence of output settles it. The probe has a 10-second ceiling: a version flag is a spawn and an immediate print, and anything slower is a binary doing something a version flag should not do. The resolved version is carried rather than discarded, so it can go on the first line of every result and a wrong answer is attributable to a particular build.

Readiness, and the 0.36-second lie

rust-analyzer answers references the moment it starts and returns [] for the first ten to sixty seconds. "No references" and "not indexed yet" are the same shape, and a model told the first will delete the function.

The obvious mechanism is to count open work-done progress tokens and call the server ready when the count returns to zero. Traced against rust-analyzer 0.3.3008 on a two-file crate, that count reaches zero three times before the index exists: 

0.01  Fetching begin        0.68  Fetching end / Fetching begin
0.34  Fetching end          0.68  cachePriming begin, end     ← zero again
0.36  …end        ← zero    1.01  Building CrateGraph begin, end ← zero
0.36  Roots Scanned begin   1.01  cachePriming begin
0.54  Roots Scanned end     1.83  cachePriming end
                            1.84  serverStatus quiescent: true

The phases are sequential handoffs with gaps of milliseconds between them, and the counter is momentarily zero inside each gap. The first version of this crate declared Ready at 0.36s, asked, and got []. That is the confidently-wrong empty result the crate exists to prevent, produced by the machinery built to prevent it. It was caught by tests/real_server.rs and by nothing else: every fake passes, because a fake emits the tokens its author expected.

tools/lsp/src/client.rs — module doc

What replaced the heuristic is experimental/serverStatus with quiescent: true, requested by declaring experimental.serverStatusNotification in initialize. It also carries health, which is how a broken project model, meaning a cargo metadata that failed or a Cargo.toml that does not parse, becomes something the model is told about rather than something it infers from thin answers. Health is printed above readiness in the header, because a server that has finished and cannot load the project is Ready and answers nothing, which is the one case readiness alone gets backwards.

The token-counting heuristic survives as a fallback with a settle window, SETTLE = 1.5 seconds, roughly five times the largest gap in the trace above. It is switched off entirely once the authoritative signal has been seen once, because a heuristic running alongside an authoritative signal can only contradict it.

tools/lsp/src/client.rs — SETTLE, Readiness

An unready request still runs

It returns Ok with the readiness attached, because the loop will not repeat a call that already failed with nothing changed since, and "wait a moment and ask again" is exactly what should happen next. An error would forbid the one correct response. The distinction lands in the sentence a result carries when it is empty: 

ready:     No references found. The index was complete when this was
           asked, so this is an answer: there are none.

not ready: No references came back, and the index was not complete — so
           this is not an answer, it is a question that could not be
           answered yet. Do not conclude that none exist; ask again once
           indexing has finished.
tools/lsp/src/render.rs — no_results_line

Readiness::caveat returns None for Ready, because a caveat on every correct answer is noise that teaches the model to skip caveats.

tested tests/readiness.rs covers both directions and the settle window itself, asserting the gaps-then-settles case takes at least 1.4 seconds, so a future edit that skips the window fails rather than merely getting lucky.

Containment applies to what comes back

A language server answers about ~/.cargo/registry and the standard library as a matter of course. Emma has decided it does not read outside the root, and that decision has to hold for a path arriving over a pipe exactly as it does for one the model typed. 

            // Canonicalised before the comparison, and this is not belt and
            // braces — it is the check working at all. `root` comes from
            // `path::root`, which canonicalises, and on Windows that is the
            // `\\?\E:\…` verbatim form; a URI round trip produces the ordinary
            // `E:\…` spelling. Comparing the two silently never matches, so
            // every hit in the project reads as a hit outside it and the tool
            // reports "no references, and 14 in dependencies". Caught by
            // `tests/tools.rs`, which is the only reason it is not still here.

Hits outside the root are counted and named rather than dropped: {n} further {what} are outside the working directory — in dependencies or the standard library — and are not shown. A list that silently omits six hits in the standard library reads as a complete list with six fewer entries. A non-file URI, an item inside a dependency Emma has only metadata for, is dropped without a count, and the source says why: those are indistinguishable from the out-of-root hits already counted.

Three answer shapes, because the choice is the server's

parse_locations handles a single Location, an array of them, and an array of LocationLink, preferring targetSelectionRange over targetRange because it is the identifier rather than the whole item. Handling one shape and returning nothing for the others would look exactly like "there is no definition". hover_text does the same for the three legal contents shapes, and symbols for both the hierarchical tree and the flat SymbolInformation list, the second of which is handled because a server ignoring Emma's declared capability would otherwise render as an empty file.

tools/lsp/src/render.rs — parse_locations, hover_text, symbols

Every location carries its source line

src/config.rs:412:9 makes the model open the file. src/config.rs:412 let c = Config::new(); is usually the whole answer. That is what the location cap exists for: reading each hit file costs, so files are read once each rather than once per hit, and results are grouped by file and sorted, because the server's order is its own and is not stable across runs. A line the file no longer has is reported as (this line is no longer in the file) rather than shown blank, because a blank line reads as an empty source line.

This crate used the weaker truncation form, and it was the last one that did

Why it was fixed rather than left flagged. The model was never the reader being failed. It read a specific sentence either way, and then got the runtime's generic fallback appended to it as well, which is its own small confusion. The reader left with nothing was the human watching the terminal, who saw a line naming no cap. A cut that is legible to one reader and opaque to the other is exactly what the truncation invariant is for, and it sat here for weeks with a warning box on it because the class-wide test that guards the invariant covers the fs tools only. A flag is not a fix, and a page that says "flagged, not fixed" is a defect with a receipt attached. tested the truncation_honesty module in render.rs.

What makes read_only and reaches_network true

pub const INIT_OPTIONS: &str = r#"{
  "check": { "enable": false },
  "checkOnSave": false,
  "cargo": { "buildScripts": { "enable": false }, "extraArgs": ["--offline"] },
  "procMacro": { "enable": false }
}"#;

Checking, build scripts and proc macros are the three ways rust-analyzer writes to a project or runs its code. --offline is what makes reaches_network: false true, because cargo metadata on a project with unfetched dependencies otherwise reaches crates.io, which is real egress from a tool the gate lets through silently.

The stated cost: items generated by derive and by attribute macros are not in the index, so references into macro-generated code will be missed. That is a hole in the direction this crate is most dangerous, a confidently short answer, which is why it is in the tool descriptions and not only in the source.

What was cut

Diagnostics was cut, and on 2026-09-06 it shipped. The argument for cutting it is still true and is why the tool is shaped the way it is. Diagnostics are pushed rather than requested, so “get the diagnostics for this file” means waiting an unknowable time for a notification that may never come: the readiness problem again, without the progress notifications that make readiness solvable. What changed is that the wait was given a third outcome instead of two. The result is an Option: a set of diagnostics, or an explicit empty publication which is a real clean answer, or the sentence The language server published no diagnostics for … within 20.0s. That is not a clean result: it means the server did not answer, not that the file has no problems. The ceiling moves with EMMA_LSP_DIAGNOSTICS_MS.

The other half of the cut argument stands and is now stated in the tool's own description. check.enable is false, which is what makes read_only: true a fact rather than a hope, so for Rust this tool reports syntax errors only. A file whose only fault was a call to a function that does not exist came back as an explicit empty publication, twice, on separate runs: a real “clean” answer to a file that does not compile. Bash running cargo check is still the tool for type errors. Where Diagnostics earns its place unambiguously is bash, terraform, bicep and ansible, none of which have a cargo check and none of which are installed here. certified on this box, 2026-09-06: cargo test -p emma-tools-lsp --test real_server a_real_server_publishes -- --nocapture against rust-analyzer 1.94.1 returned seven rust-analyzer:syntax-error diagnostics with 1-based positions on a broken file, and the explicit-empty answer on the two clean ones, each call in 0.00 s after a 3.99 s readiness wait.

The bug this tool shipped with is worth more than the tool. The publication map was keyed on the URI Emma writes, and rust-analyzer lowercases the Windows drive letter in everything it sends back, so the lookup could never succeed: the diagnostics arrived, were stored under one spelling, were read under another, and the tool returned the honest-looking timeout sentence every time, after the full 20 seconds. That is the worst available shape, because it reads as careful behaviour. doc.rs's module doc had said since the crate was written that the comparison in that direction cannot be a string comparison, and this map was the one place that had not read it. client::published_key now parses with doc::from_uri and case-folds on Windows only, since there a path is case-insensitive and on Unix it is not. No fake could have caught it, because a fake echoes back the URI it was handed and both spellings are one string inside the suite; the fix ships with a fake that respells URIs the way a real server does. certified: the trace and both outputs are in the port report, and the test fails without the fix.

tools/lsp/src/lib.rs — module doc

There are two writers to these servers, not one

This page described one writer until 2026-09-06 and there are two. The Code page holds the same Pool the five tools hold, deliberately: a second copy of a language server is about a gigabyte of memory, and the editor's own change notifications keep the server's view current for the model's next call. One server per language serves both the person editing and the model asking.

The consequence is the part worth reading. The page sends the buffer, not the file, so while somebody is editing, the document the server holds is the unsaved text. A tool call that asks about the same file gets an answer about what is on screen rather than what is on disk. That is almost always what a person wants and it is not what a reader of this page would have assumed, which is why it is written down rather than left to be discovered. The page sends nothing when the buffer is unchanged, so a cursor key costs a hash and no traffic. certified diagnostics were produced for a buffer deliberately not written to disk, and the file read back byte-identical afterwards.

Nothing on the input path waits for a server. The page offers a request to a bounded channel and never blocks: a busy or dead server means the page lacks decorations, never that a keystroke pauses. The model's tools keep their own timeouts, which this page describes above.

crates/emma/src/term/code_lsp.rs; crates/emma/src/main.rs — the spawn, with the pool the tools hold

One server per root, and what happens when it dies

Started lazily, one per canonical root. The pool uses a tokio::sync::Mutex held across the spawn await on purpose, because two tools asking at once during the first call of a session is the normal case and the alternative to serialising them is two rust-analyzers indexing the same workspace.

A crash is noticed, the corpse dropped, and a fresh server started, up to MAX_CRASHES = 3. Without a ceiling, a server that panics on this particular workspace becomes an invisible respawn on every call, each costing a spawn and an index, and the model sees a slow tool rather than a broken one. At the ceiling the pool refuses with the last death message, which contains the server's own stderr tail, 4 KiB from the end because a panic message is the last thing printed. The request in flight when it dies is not retried here, because an automatic retry would hide a crash loop behind a tool that merely feels slow, and would re-run a request whose crash it may have caused.

Nothing reaps an idle server. A rust-analyzer holding a workspace index is hundreds of megabytes, and it stays until the pool is dropped. An idle timer was considered and refused for this pass: it is a background task with its own lifecycle, and a background task that outlives its owner is the bug this module is organised around not having.

Cleanup lives in Drop, and processId is sent in initialize so the server exits if Emma is killed without unwinding, which is the one piece of cleanup that survives kill -9.

The wire, and the argument reader beside it

tools/lsp/src/proto.rs is the whole of LSP's transport in about fifty lines: JSON-RPC 2.0 messages inside Content-Length frames over stdio. A client crate was considered and refused for the reason a dependency usually gets refused here. It would bring a generated model of every LSP type, of which this crate uses six, and the parts that are actually hard, readiness and lifecycle and containment, are not the parts a client crate solves.

tools/lsp/src/proto.rs — module doc, read_message, write_message, Frame

Three details in the framing have each cost somebody a day. Header names are matched case-insensitively, because the spec says Content-Length and servers have shipped content-length, and the failure when the match is exact is a hang rather than an error, since a frame whose length was not parsed is a frame nobody consumes. The body is read with read_exact into a byte buffer, because Content-Length counts bytes: reading it as a string and counting chars desynchronises the stream permanently on the first non-ASCII doc comment, and everything after that frame is garbage. And a short read at the header is end-of-stream rather than an error, because the server exiting is an ordinary event that has to be told apart from a corrupt frame. One means it died and the other means it is confused, and they reach the model as different sentences. certified: Frame is an enum distinguishing the two, and MAX_MESSAGE_BYTES is 64 * 1024 * 1024, so a server answering Content-Length: 4294967296 is refused rather than allocated for.

tools/lsp/src/proto.rs — MAX_MESSAGE_BYTES, Frame

tools/lsp/src/args.rs is a near-copy of tools/fs/src/args.rs, and a copy rather than a shared crate on the same call tools/tasks made: args is private in both, the whole of it is thirty lines of match, and the property that matters is that the messages are the same shape rather than that the code is. Making it public to save this file would export a module whose only job is producing one crate's error prose. Two conventions carry across because the model depends on them. An explicit JSON null is treated as absent, and everything in the file is pure, so it can run in validate_args before any process is started. Unknown keys are refused rather than ignored, because a silently dropped occurrence looks to the model exactly like a parameter that had no effect, and it concludes the behaviour is impossible rather than that it misspelled the key. certified: deny_unknown collects the keys not in the known list, sorts them, and returns ToolError::BadArguments when the list is non-empty.
