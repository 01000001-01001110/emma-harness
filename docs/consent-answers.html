The five answers, and which two write to disk

Consent & permissions The two axes The ladder The egress question The five answers EXEMPT and the floor Permission rules Matching a host Hooks

A prompt offers between three and five keys. Two of them write a line into a JSON file that outlives the process, and those two are only accepted when the prompt showed them.

crates/emma/src/approval.rs — Answer, Approvals::ask, Offers

The keys

KeyVariantGrantsLives forWrites a file
y, yes Answer::Yes this one call. On the network question, this host the call, or the process no
n, no, or an empty line Answer::No nothing ​ no
a, always Answer::AlwaysThisTool this tool. On the network question it means what y means and no more the process no
r, remember Answer::RememberNarrow the narrow rule: the host on the network question, the tool on the local one until the line is deleted settings.local.json
t, trust Answer::RememberWide the tool-wide rule: every call, any host. Network question only until the line is deleted settings.local.json
crates/emma/src/approval.rs — Answer, Approvals::ask

The two remember answers are separate variants rather than one variant with a width flag, so which rule a keystroke granted is answered by the type and not by an argument that can be passed wrong. Their content is not carried on the variant either: the rule is composed by the gate, from the tool and the host it is holding, and shown to the user in the question. An Answer carrying its own rule string would be a second place for the granted rule to be decided, one of them out of sight of the prompt that displayed it.

The answer loop

ask has two shapes. Under Asker::Scripted it pops the front of a queue and returns None when the queue is empty, which is how every unit test in the file makes "allowed" mean "something other than an answer allowed it". Under Asker::Terminal it drains, then loops until it reads a key it recognises. 

let (narrow, wide) = (Offers::text(&offers.narrow), Offers::text(&offers.wide));
loop {
    // The rule text goes on screen *before* the key that writes
    // it is pressed, and it is the same string `keep` writes —
    // one `Rule`, formatted once. Nobody is to discover later
    // that they granted something other than what they read.
    match question {
        Question::Tool => term.prompt_question(name, narrow.as_deref()),
        Question::Network(host) => {
            term.prompt_network_question(host, narrow.as_deref(), wide.as_deref())
        }
    }
    let line = lines.next().await;
    // Before anything else is printed, and on both arms. The
    // terminal echoed the user's return itself; nothing in this
    // process can see that happen, so the input box has to be
    // told, or every repaint after this one erases a row too
    // high and walks up the screen. See `Term::prompt_answered`.
    term.prompt_answered(line.as_deref());
    let line = line?;
    match line.trim().to_ascii_lowercase().as_str() {
        "y" | "yes" => return Some(Answer::Yes),
        // Empty is *not* yes. A user who hits return to get
        // their prompt back has not read anything.
        "" | "n" | "no" => return Some(Answer::No),
        "a" | "always" => return Some(Answer::AlwaysThisTool),
        // Guarded on the offer rather than on the question, so a
        // key that was not shown is a key that does not work. A
        // prompt with an undocumented answer that writes to disk
        // is the same trap as a prompt nobody can evaluate.
        "r" | "remember" if narrow.is_some() => {
            return Some(Answer::RememberNarrow)
        }
        "t" | "trust" if wide.is_some() => return Some(Answer::RememberWide),
        other => {
            let mut keys = String::from("y / n / a");
            if narrow.is_some() {
                keys.push_str(" / r");
            }
            if wide.is_some() {
                keys.push_str(" / t");
            }
            term.note(&format!("`{other}` is not one of {keys}"));
        }
    }
}
crates/emma/src/approval.rs — Approvals::ask, terminal arm

Four properties come out of that block. Input is trimmed and lowercased, so Y and  yes  work. An empty line is n. An unrecognised line prints the keys that were actually offered and asks again rather than resolving to anything. And end of input, which is line? returning None, leaves the caller with the "no approval was given" denial.

Two of those four had never been executed by a test

Until 2026-08-23 nothing in this repository could reach the block above. Changing the empty-line arm to Answer::Yes, so that pressing Return at any prompt approves the call, left all 85 tests in approval and permissions green. So did accepting r and t on a prompt that offered neither.

Not a forgotten test. ask drains before it prints the question (below), and the only test constructor, LineSource::scripted, pre-fills the channel and drops the sender; every scripted line is therefore type-ahead by construction, the drain eats it, and next() finds a closed channel. Every one of the forty-five gate tests therefore exercises the policy above this block and none of them the parser inside it. LineSource::answering keeps the sender, so a test can drain first and send after.

tested An empty line is n: return_on_its_own_refuses_the_call. Mutating the arm to Answer::Yes turns it red. tested A key that was not offered does not resolve: a_key_the_prompt_did_not_offer_does_not_answer_it types r then t at a Write prompt. Dropping ask's if narrow.is_some() guard turns it red. unverified Trimming and lowercasing, and the None arm, are still read from source only.

Lines typed before the question are dropped

Both ask and read_line call LineSource::drain first and announce what it took. Anything typed before the question existed cannot be an answer to it, and the line most likely to be waiting is a y aimed at the previous question.

read_line is the goal prompt reading through the same queue, for a reason stated in its doc: two readers on one stdin race, and the loser buffers the answer to a question the winner asked. It used to drain silently. A /exit typed while a goal was still finishing vanished with nothing on screen, which was reported as the command not working. tested a_line_dropped_at_the_goal_prompt_is_reported_rather_than_vanishing scripts two lines, asserts the notice says "ignoring 2 line" and "while a goal runs", then builds a second gate with an empty source and asserts the terminal recorded nothing at all. That second half is what stops a false "your input was eaten".

What is offered, and when nothing is

Offers holds two Option<Rule>s. Both slots are empty in three situations, and in each of them r and t are neither shown nor accepted:

  • there is no file to write to, meaning Approvals::file is None, which is an unattended run or a harness whose directory could not be resolved;
  • an ask rule forced this prompt, so the allow the keystroke would write is outranked by that same rule;
  • on the local question, wide is always None, because the narrow rule and the tool-wide rule are the same grant there.

One field decides both whether the key is offered and whether it would persist, so those two cannot disagree. An option on screen that silently does not persist is worse than no option. tested the_prompt_names_the_rule_it_would_write asserts the rendered strings: Rule::domain("WebFetch", "apnews.com") is WebFetch(domain:apnews.com), and Rule::every_call("WebSearch") is WebSearch.

Writing it down, and failing to

async fn keep(&self, rule: Rule, term: &Term) {
    match &self.file {
        Some(file) => match crate::permissions::remember(file, &rule) {
            // The rule and the file, both, every time. A grant whose text is
            // on screen and whose location is not is a grant the user cannot
            // go and revoke.
            Ok(wrote) => term.note(&format!(
                "{} `{rule}` in {} — Emma will not ask about this again",
                if wrote { "saved" } else { "already had" },
                file.display()
            )),
            Err(e) => term.warn(&format!(
                "`{rule}` was allowed for this session but NOT saved: {e:#}"
            )),
        },
        // Not reachable from the terminal, which offers the key only when
        // there is a file. A scripted run can get here, and saying so is
        // better than pretending something was written.
        None => term.warn(&format!(
            "`{rule}` was not saved: this run has nowhere to write permission rules"
        )),
    }
    // **Adopted on every path, including both failures.** The user answered
    // the question; the file is how the answer survives the process, not how
    // it takes effect. A `keep` that returned early on a write error would
    // re-ask for the rest of the run — punishing them a second time for a
    // problem with a file.
    self.rules.lock().await.adopt(rule);
}

What the prompt shows

A prompt the reader cannot evaluate manufactures consent and leaves a record saying they agreed. preview has one arm per tool that can change something, and the fallback is pretty-printed JSON, which is visibly worse and is the pressure on whoever adds the next writing tool.

ArmShows
Bash $ <command>, and a second line in <cwd> when the call carried one
Write the path, then <n> bytes, <n> lines, then the diff against the file on disk when one can be computed
Edit the path, (every occurrence) when replace_all is set, then the diff of the two argument strings
Delegate the agent type, the count of facts handed down when non-zero, the first BRIEF_LINES lines of the brief with an ellipsis if it was cut, and the deliver clause when present
anything else serde_json::to_string_pretty(args), falling back to args.to_string()
crates/emma/src/approval.rs — preview, BRIEF_LINES (12)

BRIEF_LINES is 12. The brief is prose a model wrote and can be arbitrarily long; the question at the prompt is whether the delegation should run at all, and the first lines answer it. The delegate arm is keyed on crate::delegate::NAME rather than a string literal, so renaming the tool cannot silently drop its arm back to the JSON fallback.

crates/emma/src/approval.rs — preview, BRIEF_LINES

The Write arm used to print a path and a byte count and withhold the change. Its own module doc names that as the arm failing the file's rule. It now carries the diff, and every case that cannot be diffed becomes a sentence saying so rather than a rendering that looks like a diff and is not. The renderer is crate::term::diff; see the terminal. tested a_write_over_an_existing_file_shows_what_it_destroys writes a real file, previews a Write over it, and asserts the output contains - DELETE ME, + BRAND NEW, +1 -1 lines, and never the phrase "a new file".

Naming the grants back

session_grants returns the tools and the hosts a run has accumulated, each sorted. It is there for /clear, which keeps both sets and has to be able to name them: a receipt saying "grants were kept" without saying which is the silence the command is written against. The sort is because a HashSet has no order and a receipt that reshuffles itself between two readings is one nobody trusts.

The rest of the type

Four items on Approvals need no paragraph of their own. new builds a gate with empty sets and no rules; with_rules is a separate builder step rather than two more parameters, so that every existing caller still means "ask about everything"; unattended is new(Gate::Unattended, Scripted(empty)); and gate returns the mode. Offers::text renders an optional rule to an optional string. Verdict has two variants, and the Deny one carries the sentence the model is told, because a denial the model cannot read is a tool that mysteriously does nothing.

What is not settled here

unverified Every claim on this page about what reaches the screen is read from source or from unit tests against a recording Term. A fully-tested drawing defect has shipped from this repository twice, so a cell buffer agreeing is not a console agreeing. What would settle it: a live run that answers r at a network prompt, with the note, the rewritten settings.local.json and the "ignoring N line(s)" notice all read off the console.

tested A local prompt refuses a t: this is the test this paragraph used to ask for, and it now exists as a_key_the_prompt_did_not_offer_does_not_answer_it. unverified It asserts the verdict the fall-through produces, not the "not one of y / n / a / r" notice itself, so the wording a user actually reads is still unchecked. What would settle it: the same test, asserting against the recording Term's notes. That is a cell buffer, so it settles the wording and not the console.
