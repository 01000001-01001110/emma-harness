Path containment, in one implementation

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP

tools/fs/src/path.rs is 478 lines and 12 functions, and it is the only answer in the workspace to "is this path inside the root". crates/emma, tools/lsp and tools/tasks all depend on tools/fs to reach it.

That matters more than code reuse usually does. A second implementation would not only duplicate the check; it would eventually disagree with the first, and the disagreement would be silent in the direction that fails open. One tool would refuse a path another accepted, and nothing in either result would say the two had different ideas of the boundary.

The root, canonicalised once per call

/// The canonical root. Canonicalised once per call so that comparisons below
/// are against the same spelling the OS uses — on Windows that means the
/// `\\?\` verbatim form, and comparing a verbatim path to a non-verbatim one
/// silently never matches, which would fail *open* if the check were inverted.
pub fn root(ctx: &ToolCtx) -> Result<PathBuf, ToolError> {
    ctx.cwd.canonicalize().map_err(|e| {
        ToolError::Unavailable(format!(
            "working directory {} cannot be resolved: {e}",
            ctx.cwd.display()
        ))
    })
}
tools/fs/src/path.rs — root

A working directory that cannot be canonicalised is Unavailable rather than BadArguments, because the model did not choose it and cannot fix it by passing something else. The same verbatim-spelling problem reappears in tools/lsp, where it is the reason results are canonicalised on the way out as well; see the LSP page.

Three moves, because a file that does not exist yet still has to be contained

The check is not "does the string contain ..". A symlink inside the root pointing outward is an escape containing no .. at all, and a path that does not exist yet cannot be canonicalised at all, which Write needs since it has to name a file it is about to create. 

/// `starts_with` is `Path`'s, so the comparison is component-wise. A sibling
/// directory whose name merely begins with the root's — `/work` and
/// `/workspace` — does not match, which a string prefix test would have got
/// wrong in the direction that fails open.
pub fn resolve(root: &Path, raw: &str) -> Result<PathBuf, ToolError> {
    if raw.trim().is_empty() {
        return Err(ToolError::BadArguments("path is empty".into()));
    }

    let asked = Path::new(raw);
    let joined = if asked.is_absolute() {
        asked.to_path_buf()
    } else {
        root.join(asked)
    };

    let lexical = lexical_normalize(&joined);
    let (mut out, tail) = canonical_prefix(&lexical);
    for component in tail {
        out.push(component);
    }

    if !out.starts_with(root) {
        return Err(ToolError::BadArguments(format!(
            "{raw} resolves to {}, which is outside the working directory {}",
            out.display(),
            root.display()
        )));
    }
    Ok(out)
}
tools/fs/src/path.rs — resolve

An absolute path is taken as given rather than rejected, then contained like everything else. Absolute-inside-the-root is a call the model makes constantly, and the containment assertion is what tells the two apart. The refusal names the resolved path as well as the raw one, so a model that passed ../../etc/passwd sees where that landed.

The two halves

lexical_normalize drops . and resolves .. textually, and popping past the filesystem root is a no-op, matching POSIX /... It is the containment assertion and not this function that rejects the attempt, which keeps the normaliser from having an opinion about policy. 

/// Searching from the deepest cut downwards is what makes a symlinked parent
/// visible: `escape/planted.txt` cannot be canonicalised, but `escape` can, and
/// it canonicalises to wherever the link points — so the containment check sees
/// the outside path rather than the inside spelling.
///
/// When nothing at all canonicalises the input is returned unchanged with an
/// empty tail. That is not a bypass: an uncanonicalisable path is one whose
/// every ancestor is missing, so there is no link to have been followed, and it
/// still faces the same containment assertion in [`resolve`].
fn canonical_prefix(p: &Path) -> (PathBuf, Vec<OsString>) {
    let comps: Vec<Component> = p.components().collect();
    for cut in (1..=comps.len()).rev() {
        let candidate: PathBuf = comps[..cut].iter().collect();
        if let Ok(canon) = candidate.canonicalize() {
            let tail = comps[cut..]
                .iter()
                .map(|c| c.as_os_str().to_os_string())
                .collect();
            return (canon, tail);
        }
    }
    (p.to_path_buf(), Vec::new())
}
tools/fs/src/path.rs — canonical_prefix

Because the input is already lexically normal, the tail can never contain .., so re-attaching it cannot walk anywhere the prefix did not permit. That ordering is the whole reason the two functions are separate.

A colon is a fourth move, and it refuses

On NTFS foo:bar does not name a file called foo:bar. It names an alternate data stream of foo. That mattered here because the atomic write builds foo:bar.emma-tmp.<pid>.<seq>, and writing to that materialises the base file foo as a zero-byte entry before failing; the rename then fails with os error 87, and the cleanup removes only the stream. A reviewer certified the outcome: Write returned an error and dir /r showed brandnew left behind, a file the error never mentioned. certified by that probe, and pinned since by a_refused_stream_write_leaves_the_directory_empty, which asserts on the directory listing before it asserts on the message.

Two promises in the write path were false for that one input: nothing before the refusal may change the filesystem, and a stray .emma-tmp in somebody’s repository counts as a bug report. So this is refused rather than attempted. 

// **A colon inside a name is an NTFS alternate data stream, and it made a
// refused write create a file.** `foo:bar` names a stream of `foo`. The
// atomic write builds `foo:bar.emma-tmp.<pid>.<seq>`, and `fs::write` on
// that **materialises the base file `foo`** as a zero-byte entry before
// failing; the rename then fails with os error 87, and the cleanup removes
// only the stream. A reviewer certified it: `Write` returned an error and
// `dir /r` showed `brandnew` left behind — a file named something the error
// never mentioned.
//
// `write.rs` promises *"nothing before the refusal changes the filesystem,
// which is what makes a refusal actually a refusal"*, and `write_atomically`
// promises a failed temp is removed *"because a stray `.emma-tmp` in
// somebody's repository is a bug report"*. Both were false for this input.
//
// Refused here rather than warned about, which is the opposite of the
// reserved-name decision one file over — and the difference is what
// succeeds. A `NUL` file is real, round-trips, and is merely awkward for
// other tools, so refusing it would be Emma deciding what a user may call a
// file. A stream write does not work *at all*; there is nothing to preserve
// and a real side effect to prevent.
//
// Windows only, and on **every** normal component rather than the last.
//
// It was the last one only until a reviewer pointed at `sub:s/file.txt`,
// which is a stream of the directory `sub` with a path hung off it. That is
// the same construction the paragraph above is about, one component to the
// left, and it went through this check without a word. A directory cannot
// live under a stream, so the write fails either way; what the refusal
// buys is that it fails *before* anything is created, which is the promise
// `write.rs` makes and the reason this check exists at all.
//
// `Component::Normal` is the right filter and not merely a convenient one:
// a drive letter's colon arrives as `Component::Prefix`, so `C:\a\b` yields
// Prefix, RootDir, Normal, Normal and the legitimate colon is never
// examined. Widening from the last component to all of them therefore adds
// no false refusals on absolute paths.
#[cfg(windows)]
for component in lexical_normalize(&joined).components() {
    let Component::Normal(name) = component else {
        continue;
    };
    if name.to_string_lossy().contains(':') {
        return Err(ToolError::BadArguments(format!(
            "{raw} names an alternate data stream (the `:` in `{}`). Emma cannot write one \
             — the attempt creates the base file and then fails — so it is refused before \
             anything is touched",
            name.to_string_lossy()
        )));
    }
}
tools/fs/src/path.rs — resolve

It is a refusal here and a warning one file over. The difference is what succeeds. A file named NUL under Emma’s verbatim root is real, round-trips, and is merely awkward for other Windows tooling, so refusing it would be Emma deciding what a user may call a file. A stream write does not work at all. There is nothing to preserve and a real side effect to prevent.

The check reads every normal component and not only the last. It read only the last until 2026-08-23, when a reviewer pointed at sub:s/file.txt: the same construction one component to the left, going through without a word. Component::Normal is what makes widening safe rather than merely convenient, because a drive letter’s colon arrives as Component::Prefix: C:\a\b yields Prefix, RootDir, Normal, Normal, and the legitimate colon is never examined. tested tools/fs/tests/containment.rs a_stream_named_in_a_directory_component_is_refused_too goes red when the loop is narrowed back to next_back(), while an_ordinary_nested_path_is_not_caught_by_the_stream_refusal stays green. That shows the widening refuses the right thing and not simply more things.

It is #[cfg(windows)] because on unix a colon is an ordinary character in a file name and refusing it would break real paths. The hazard the check cannot rule out — a non-NTFS Windows filesystem that treats : as ordinary would be refused a name that would have worked — is listed under named hazards rather than described here.

How a path reads back

pub fn display(root: &Path, path: &Path) -> String {
    path.strip_prefix(root)
        .unwrap_or(path)
        .to_string_lossy()
        .replace('\\', "/")
}

Relative to the root when it is inside it, because absolute paths in tool output are noise the model then copies. Backslashes become forward slashes so a path reads the same whichever machine produced it, and so a path the model copies into a Glob pattern is already in the spelling the matcher expects.

What containment cannot catch

Hard links, bind mounts, and the shell

A hard link inside the root to a file outside it is not detectable this way. There is no "real" path to canonicalise towards, both names are equally the file, and canonicalize returns the inside one. The module doc marks this as verified rather than assumed, and notes that on Windows mklink /H needs no privilege at all. A bind mount is the same shape. This is a boundary against paths, not against an operator who has already placed a link inside the tree.

Bash is wider than either and is documented as a hole rather than papered over. Its cwd argument is contained; the shell it starts is not, and cd .. leaves.

The gap between the check and the write

resolve proves a string lands inside the root. The write happens later. In between, a directory component of that path can be replaced by a link pointing somewhere else, and the write follows it out. An external reviewer filed this as DEF-016, and it is real.

The check is now re-run as the last thing before every write: path::still_contained, from Write and both Edit paths. It re-resolves from the original argument rather than re-checking the resolved path against itself, because the second is a tautology and is the shape this check decays into once the reason stops being written down.

This narrows the window. It does not close it

The gap goes from “however long the tool spends thinking” to “a canonicalise and a syscall”. A gap of microseconds is still a gap, and the function's own doc says so in those words. Closing it means handle-based I/O: openat against a directory descriptor on unix, a relative open against a parent handle on Windows, so that the path checked and the path written are the same object rather than the same string. That is a rewrite of four call sites on two platforms with unsafe on both, and it is not done.

tested tools/fs/tests/containment.rs Two cases, because one does not cover the other and mutation proved it. A directory swapped for a link pointing out is refused by resolve itself, so disabling the drift comparison left that test green. The second case is a link to a different directory inside the root, where containment still holds and the path now names a different file. That case exercises the comparison, and it goes red when the comparison is disabled. a_directory_swapped_for_a_link_out_is_caught_by_the_recheck and a_path_that_resolves_somewhere_else_inside_the_root_is_refused_too. Both tests set up the swap instead of racing it: a race that can be won on demand is not the race being guarded against.

Whether the recheck runs at all is unproven: deleting still_contained(…) from write.rs leaves the whole workspace green. It is listed under named hazards rather than described here.

Whether closing it is worth paying for is a product question, and it is open

Winning this race needs somebody who can write into the working directory while Emma is running. Two records already put that person out of scope: the module doc above says containment is “a boundary against paths, not against an operator who has already placed a link inside the tree”, and CLAUDE.md is blunter: “the approval gate is a consent interface, not a sandbox… and Bash can do anything.” Someone able to swap a directory under Emma mid-call has a far shorter route to the same result.

Under that reading, containment is a leash on a wandering model, it already does that job, and DEF-016 is asking it to be a sandbox the product has decided it is not. The counter-argument is that “Bash can do it anyway” is the reasoning that ends with every guard removed, so the decision is the owner's. It was recorded as SEC-001 in a rulings file that left the tree on 2026-08-30, and it is still unanswered: a product question about whether containment should become a sandbox, not a security incident.

Containment guards arguments; not following links guards the walk

A directory symlink pointing outside the root would let a glob enumerate, and then a read reach, anything on the machine without a single .. in the pattern. So the shared walk passes follow_links(false), and the two guards are separate because they cover different attacks.

What is not verified here

The backslash-in-a-unix-filename defect is listed under named hazards with its chip and its settling experiment.

certified Settled on 2026-08-23, by exactly the experiment this paragraph used to ask for, and then taken apart by a reviewer the same evening. The first row emma verify ever judged, returned OVERSTATED. The test used a fixed filename in the shared temp directory that a neighbouring test also writes and deletes, so a parallel run could turn it into a silent skip; its crafted failure message sat in the branch a closed hole would not take; and it had no positive control, so a resolve returning its argument unchecked would have passed it and still backed this chip. All three are fixed, and the control is what makes the test mutable at all (a mutation receipt in the owner’s records). An independent reviewer ran it live on Windows; a_hard_link_inside_the_root_reads_a_file_outside_it in tools/fs/tests/containment.rs now runs it in the suite: a hard link created inside a sandbox root pointing at a file outside it, and Read returns outside-secret.

The test asserts the limitation and not a fix, because there is no fix at this layer. Both names are equally the file, there is no real path to canonicalise towards, and canonicalize returns the inside one. What it buys is that the hole cannot quietly change: if a future resolver ever does catch this, the test goes red and somebody has to come and rewrite this page rather than leaving it saying the opposite. Its failure message says so. The skip is real and reported. A filesystem that refuses a hard link leaves nothing to certify, and this box refused nothing.
