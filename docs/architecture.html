Architecture

Eight crates

Four library crates and four tool crates, with one shared vocabulary at the bottom and no path from a tool back up into the loop that runs it.

The dependency graph

crates/{tool-api,harness,llm,emma}/Cargo.toml, tools/{fs,tasks,web,lsp}/Cargo.toml

The four facts in that picture

No tool crate depends on the harness

A tool receives a context and returns an outcome. It has no type through which it could reach the loop, the approval gate, or the session log, so a tool cannot start a goal, grant itself permission, or write a record the loop did not write. tested by the graph itself: adding such a call would not compile.

tools/tasks and tools/lsp depend on tools/fs

Both need to decide whether a path is inside the working directory, and path containment has one implementation rather than three. Containment written twice is containment that disagrees with itself on the third unusual input: a symlink, a UNC path, a trailing dot. That disagreement surfaces as one tool refusing what another allowed.

tools/web depends on llm, and not for the model

It reads ApiKey and the credentials path. Web search needs a key, and credential resolution lives in llm because that is where the provider that owns the account lives. This edge is the one people misread as the browser calling a model. It does not.

tools/web/Cargo.toml, crates/llm/src/auth.rs

llm's dependency on tool-api is dev-only

The provider layer does not need the tool vocabulary to build a request. Tool schemas arrive as already-rendered JSON. It needs the vocabulary only to test the seam where the two meet, so the dependency sits under [dev-dependencies] and the seam test is inline in anthropic.rs rather than in a tests/ directory.

Why tool-api is small

Every crate above it depends on it, so anything added there is added to everything, and every tool has to answer it. That cost is why ToolMeta carries less than it could.

needs_approval was removed after it turned out nothing read it: the approval gate derives what it needs from the two axes a tool already declares, and a third field that only looked like it mattered is a field fifteen tools maintain for no reader.

The gap this leaves: ToolCtx has no session slot

There is nowhere in the context for per-session state, so read-tracking and anything else a tool needs to remember across calls has no home. Constructing tools individually compiles and then silently misbehaves.

Three crates document this separately: tools/fs, tools/lsp and tools/web each warn about it in their own words, which is what a missing shared abstraction looks like from below. Backlog item 17. unverified. The failure is described in three comments; no test reproduces it. What would settle it: construct two tools separately, exercise the shared state, and assert the divergence.

The library and the binary

Everything that makes a decision lives in the library. main.rs parses arguments and starts things. The reason is testability: a scripted Provider can drive an entire goal (tool calls, approvals, compaction, endings) with no network and no API key, which is how most of the loop's behaviour is covered at all.

The split is not clean

main.rs opens by saying it is "wiring, and nothing else". run() is 634 lines of policy sitting above the point a scripted provider attaches, so the code that decides what happens before the loop starts is the part the seam cannot reach. unverified. Found by reading, in notes/map-architecture.md; no measurement of what that code does that is untested. Backlog item 19.

What each crate is

CrateHolds
tool-api The Tool trait, ToolMeta, ToolCtx, ToolOutcome. The vocabulary every other crate agrees on.
llm The provider boundary, the Anthropic client, typed content blocks, per-model limits and cache floors, retry, credentials. See Providers.
harness Configuration discovery across .emma/ and .claude/, agent definitions, skills, commands, hooks, the status line. See Configuration.
emma The loop, goals, sessions, the approval gate, permissions, delegation, the terminal, and main.rs.
tools/fs Read, Write, Edit, Glob, Grep, Bash, and path containment.
tools/tasks The task list a goal-holding loop writes down what is left in.
tools/web WebSearch, WebFetch rendering in real Chrome, and five tools driving a live page.
tools/lsp FindReferences, GoToDefinition, Hover, DocumentSymbols.

What is not verified on this page

  • The dependency edges were read from the manifests on 2026-08-16 and are accurate for commit 20ac400. A manifest change moves them and nothing here notices. unverified. What would settle it continuously: a test that reads the manifests and asserts the edge set.
  • "No tool crate depends on the harness" rests on the manifests, not on a test that would fail if someone added the dependency. It would fail at compile time for a cyclic edge, but a non-cyclic one would simply appear. unverified
  • The ToolCtx hazard and the main.rs policy count both come from notes/map-architecture.md, whose citations were sampled and confirmed on 2026-08-16 but not exhaustively re-read here. unverified
