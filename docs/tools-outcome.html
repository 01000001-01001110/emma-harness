ToolOutcome: one type, two audiences

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP

A successful call produces four fields. Two of them are the same answer written for two different readers, and the other two are the admission that the answer is not whole. 

/// What a successful call produced.
///
/// `content` is what the model sees. `display` is what a human watching the
/// terminal sees, when a full dump would be noise — the diff rather than the
/// whole file, the first lines of output rather than ten thousand. When it is
/// `None` the terminal shows nothing beyond the fact that the tool ran.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ToolOutcome {
    pub content: String,
    pub display: Option<String>,
    pub truncated: bool,
    pub truncation: Option<String>,
}

Why the answer is written twice

A full dump is often noise on a terminal and never noise to a model. The model is going to reason about the bytes; the human is going to glance at the line while it scrolls past. Collapsing the two means choosing which of them to serve badly, and the choice that tends to get made is the one that keeps the terminal readable, which is the one that starves the model.

Read of an empty file returns a genuinely empty content, not a sentence saying the file is empty, because anything written there would be indistinguishable from file content the next time the model quotes it back. Four constructors, and the one pairing they forbid

impl ToolOutcome {
    pub fn new(content: impl Into<String>) -> Self { /* … */ }

    pub fn with_display(mut self, display: impl Into<String>) -> Self { /* … */ }

    /// Cut, with no stated reason. See [`ToolOutcome::truncated_because`].
    pub fn truncated(mut self) -> Self {
        self.truncated = true;
        self
    }

    /// Cut, and here is what was lost and how to get it.
    ///
    /// The two fields cannot disagree: there is no way to supply a reason
    /// without also setting the flag, and `truncation.is_some()` therefore
    /// always implies `truncated`.
    pub fn truncated_because(mut self, reason: impl Into<String>) -> Self {
        self.truncated = true;
        self.truncation = Some(reason.into());
        self
    }
}
crates/tool-api/src/lib.rs — impl ToolOutcome

There is no constructor that sets truncation without truncated. If those two could disagree, a result could carry a full explanation of its own truncation and still be presented as whole, which is the failure the flag exists to prevent.

tested a_reason_for_truncation_implies_truncation asserts all three states: a reason implies the flag, the bare flag leaves truncation at None, and a plain outcome claims nothing. Making the fields public and settable independently would not break it, which is worth knowing: the test guards the constructors, not the struct.

The weaker form, and who still uses it

truncated() without a reason is described in its own doc as never the preferred choice for a new tool. It survives because several tools explain their cut inside content instead, and the model reads the content. What it costs is the terminal line and the runtime's own note, which then have nothing specific to say.
