Doing work

ToolCtx, and the state it has no room for

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP screenshot

ToolCtx carries four fields. Session state is not one of them, and three separate crates have each worked around that absence in their own words. This is the sharpest edge in the tool layer: an invariant the type system does not hold, guarded by three comments and nothing else. 

/// What a tool is told about the call it is serving.
///
/// Note what is missing: there is nowhere here for **session state**. The
/// read-tracking that makes `Write`'s refusal-to-clobber meaningful therefore
/// lives in the tool structs instead, which means "these tools share one
/// tracker" is a wiring convention rather than something the type system holds
/// — a `Write` built with the wrong tracker refuses nothing, and it compiles.
/// Known, and cheaper to fix at six tools than at sixteen.
pub struct ToolCtx {
    /// Every relative path resolves against this, and nothing may escape it.
    pub cwd: std::path::PathBuf,
    pub session_id: String,
    pub turn_id: String,
    pub background: background::Registry,
}
crates/tool-api/src/lib.rs — ToolCtx

cwd is the containment root, canonicalised once per call by path::root. session_id keys the read tracker, so a resumed process cannot inherit an earlier session's claim to have looked at a file. turn_id is carried for logging and is read by nothing in the four tool crates. background holds in-flight shell work; it is not the read tracker the page is about.

Three sets of tools, three shared objects

Because there is nowhere in ToolCtx to put it, state that has to outlive one call lives in the tool structs behind an Arc, handed to every member at construction. Each crate exposes one builder that does the handing. 

/// The whole surface, wired to one read tracker.
///
/// Returns the tracker as well so a caller that wants to inspect or reset it —
/// a test, or a harness starting a new session — can, without any tool having
/// to expose it.
pub fn fs_tools() -> (Vec<Arc<dyn Tool>>, Arc<ReadTracker>) {
    let tracker = Arc::new(ReadTracker::new());
    let tools: Vec<Arc<dyn Tool>> = vec![
        Arc::new(Read::new(tracker.clone())),
        Arc::new(Write::new(tracker.clone())),
        Arc::new(Edit::new(tracker.clone())),
        Arc::new(Glob::new()),
        Arc::new(Grep::new()),
        Arc::new(Bash::new()),
    ];
    (tools, tracker)
}

What a wrong wiring does, per crate

SharedBuilderThe failure, if a member is built alone
ReadTracker
Read, Write, Edit		 fs_tools() A Write holding a tracker its Read does not share never refuses anything, and the read-before-write rule quietly stops existing. A fresh tracker is the mirror image: it refuses every overwrite.
Pool
the four LSP tools		 lsp_tools() Four tools with four pools is four rust-analyzers indexing one workspace, each holding hundreds of megabytes of index.
BrowserPool
the five browser tools		 browser_tools() Five independent registries, four of which cannot see the session the fifth opened. BrowserClose would then be unable to close what BrowserOpen started, which is how a Chrome outlives the process with a live CDP port.
nothing task_tools() No failure. The four task tools share no mutable state; the markdown file is the state and is re-read inside every invoke.
tools/fs/src/session.rs; tools/lsp/src/lib.rs; tools/web/src/browser/mod.rs; tools/tasks/src/lib.rs

Every one of those compiles. Nothing in the workspace catches a caller that constructs a member directly: not the compiler, not the registry's coherence check, not any test.

The same warning, three times, in three sets of words

Each crate wrote the hazard down where it lives, and none of them wrote it in tool-api, where the missing field is.

FileHow it puts it
tools/fs/src/session.rs "A caller that builds Write with a fresh tracker gets a Write that refuses every overwrite, and a caller that builds it with a tracker Read does not share gets a Write that never refuses. Nothing in the type system stops either."
tools/lsp/src/lib.rs "Five tools built with five pools is five language servers indexing the same workspace, and it compiles. The same known defect tools/fs records about its read tracker, recorded here for the same reason: cheaper to notice at five tools than at fourteen."
tools/web/src/browser/mod.rs "Five tools built with five pools is five independent registries, four of which cannot see the session the fifth opened — and it compiles."
crates/tool-api/src/lib.rs The fourth copy, on ToolCtx itself: "Known, and cheaper to fix at six tools than at sixteen." Written when there were six.

The same fact appears in four module comments. That is the argument for the fix belonging in tool-api. It is a real trade rather than a free win, because tool-api is kept to one file, and a session-state slot on ToolCtx would have to answer what its lifetime is and who clears it. The current state is that the contract is enforced by four comments.

the owner’s records, outside this repository
Nothing catches a bypassed builder

Each crate's builder is the only supported way to construct its set. The tests below check that the builder still shares, which is a different question from whether a caller used it. Emma's own main.rs is the only production caller, so today the invariant holds by there being one call site.

What the tests do cover

        // Five tools holding a clone, plus the one returned: six. This is the
        // only thing that catches "five tools, five pools", which compiles fine
        // and would mean BrowserClose could not find BrowserOpen's session.
        assert_eq!(Arc::strong_count(&pool), 6);
tools/web/src/browser/mod.rs — the_surface_is_five_tools_sharing_one_pool

tested tools/lsp makes the same assertion with 8 in the_surface_is_the_seven_tools_and_they_share_one_pool: seven tools holding a clone of the pool, plus the one the builder returns. A strong_count assertion goes red the moment a builder stops sharing, and stays green for a caller that bypassed the builder entirely. tools/fs has no equivalent count; its sharing is checked indirectly, by the_result_labels_its_new_lines_so_the_next_edit_needs_no_read in tests/addressed.rs, which makes a second edit from the first edit's output with no Read between them. That only works if Edit and Read hold the same tracker.

What is not verified here

certified No production code outside the four builders constructs a member directly. grep -rn 'Read::new(\|Write::new(\|Edit::new(\|BrowserOpen::new(\|FindReferences::new(' crates/ tools/ --include=*.rs at commit a3eba74 returns sixteen lines: the builders themselves and thirteen inside test modules and integration tests. So the invariant currently holds by there being one way in, not by anything enforcing it.

certified turn_id is read by no tool. grep -rn turn_id tools/ --include=*.rs returns nine lines, every one of them a struct literal building a ToolCtx: seven in tests, one in tools/tasks/src/lib.rs's open_count, which passes String::new(). Nothing reads the field back.

Nothing catches a caller that bypasses the builders. A member built alone compiles, passes every test, and silently stops sharing; it is listed under named hazards rather than described here.
