The agent loop

Failure as an observation

The agent loop One turn Failure The memo Endings The kick Budgets Done Seams

Nothing a tool does ends a goal. Ten different things can go wrong inside run_tool_call, including a panicking tool and a Ctrl-C mid-tool, and all ten come back as a tool_result with is_error set, which the model reads and works from. The loop's own budgets stay the only things that stop a run.

In the predecessor project five of eight failure classes ended turns silently, the user saw "Something went wrong on my side", and the model never learned anything had failed.

crates/emma/src/agent.rs — module doc

One closure, ten callers

Every failure path converges on one closure. fail() is defined at the top of run_tool_call and is the only non-success exit from the function. 

// crates/emma/src/agent.rs
/// Everything that happens to one `tool_use` block.
///
/// Returns the result block, whether the tool actually ran and succeeded,
/// and a label for the kick when it did not.
async fn run_tool_call(
    &self,
    call: &ToolCall,
    turn_id: &str,
    failed_now: &HashSet<String>,
) -> (ToolResult, bool, Option<String>) {
    let label = label_of(&call.name, &call.input);
    let fail = |kind: &str, detail: String| {
        let block = failure_result(&call.id, &call.name, kind, &detail);
        // A failure block is a block that was sent, so it is recorded under
        // the same kind as a successful one — the fold rebuilds the user
        // turn from these and would otherwise reconstruct a turn that
        // answers only the calls that worked, which the API rejects. The
        // record immediately above this one (`tool_failed`, `denied`,
        // `tool_unknown`, …) is the prose a human reads; this is the wire.
        self.log_result_block(turn_id, call, &block, None, None);
        (block, false, Some(label.clone()))
    };

The three-part return is what the caller needs and no more: the block to send, whether a tool ran and succeeded, and the label a kick will quote. The middle value is what clears or writes the memo; the third is None on success so the caller cannot record a label for a call that worked.

The order of the checks, and what each one costs

The ten are not interchangeable. Each sits where it does because of what the checks above it have already ruled out, and because of what it would cost to run later.

Three failures leave no tool_call record

no_such_tool, an argument-validation failure and already_failed all return before the tool_call record is written, so the session file carries a tool_result for them with no matching tool_call above it. Only the first of the three logs anything of its own, as tool_unknown. That is enough for the fold, which rebuilds the user turn from tool_result records, but a human grepping for a call that never appeared will find only its result. certified by reading the function: the three return fail(...) statements above precede the self.s.log.append("tool_call", ...) line.

Policy before consent, consent before invocation

// crates/emma/src/agent.rs — Agent::run_tool_call
// Policy before convenience. A `PreToolUse` denial is not something the
// person at the keyboard gets a vote on, so it is resolved before they
// are asked — a gate a human can wave through is advice.
let hook_call = HookCall {
    tool_name: &call.name,
    tool_call_id: &call.id,
    args: &call.input,
    session_id: &self.s.session_id,
    turn_id,
    result: None,
};
let pre = self
    .s
    .harness
    .run_hooks(HookEvent::PreToolUse, &hook_call)
    .await;
self.log_hooks(turn_id, &pre.runs);
if let Some(reason) = pre.denied {
    // Its own treatment on screen, and not a warning: no answer at the
    // prompt could have allowed this, and a user who reads it as "I
    // could have said yes" goes looking for a prompt that never comes.
    self.s.term.tool_blocked(&call.name, &reason);
    self.s.log.append(
        "denied",
        json!({ "turn_id": turn_id, "id": call.id, "by": "hook", "reason": reason }),
    );
    return fail(
        "blocked_by_policy",
        format!("{reason} This is configured policy and cannot be approved away."),
    );
}

match self
    .s
    .approvals
    .request(tool.as_ref(), &call.input, self.s.term)
    .await
{
    Verdict::Allow => {}
    Verdict::Deny(reason) => {
        // Said on screen as well as in the log. A call that vanishes
        // between "wants to run" and the next thing is a tool that
        // mysteriously did nothing.
        self.s.term.tool_refused(&call.name);
        self.s.log.append(
            "denied",
            json!({ "turn_id": turn_id, "id": call.id, "by": "user", "reason": reason }),
        );
        return fail("not_approved", reason);
    }
}

Both denials write a denied record and differ by the by field, "hook" or "user". The sentence sent to the model differs too: a policy denial appends "This is configured policy and cannot be approved away", so a model that would otherwise ask the user to approve it is told not to bother. tested crates/emma/tests/loop.rs a_hook_denial_overrides_every_approval and a_hook_denial_outranks_a_network_grant in tests/loop.rs assert the ordering; the consent side of it is on Consent & permissions.

Four ways the call itself goes wrong, two of them newer than this page's first draft

This section used to be titled "Two errors", and the match below had exactly two error arms. Two failure classes existed that neither arm caught, and both ended more than the call. A panicking tool unwound straight through the loop, past the session log and the budget accounting, and took the run with it. That was the one failure class that did not reach the model as an observation, on a tool surface where several crates parse input the model wrote. And a Ctrl-C during a tool did nothing until the tool finished on its own: invoke was awaited outright, the flag was read only at iteration boundaries and around the model call, so a wrong Bash ran to its own timeout (120 seconds by default) with the keyboard already asking it to stop, and in the framed UI raw mode means the child never sees a console signal either. Both are now ordinary failed calls: the future is wrapped in catch_unwind and raced against the interrupt, and the model reads tool_panicked or cancelled and continues. tested crates/emma/tests/loop.rs a_tool_that_panics_is_an_observation_and_the_goal_continues and an_interrupt_reaches_a_tool_that_is_already_running, both in tests/loop.rs.

The guard was one function too late, and the test that should have caught it panicked in the wrong place

Until 2026-08-23 the catch_unwind wrapped Tool::invoke and nothing else. The argument quoted above is that “several of its crates parse input from the model, and an index or an unwrap in any of them ended everything”, and the first function on the call path to see that input is Tool::validate_args, which sat outside the guard. So did network_target and meta, both of which the approval gate calls on the tool’s own code before anything runs. There are nineteen-odd real validate_args implementations across tools/fs, tools/lsp, tools/tasks and tools/web, each parsing a JSON blob the model wrote.

The positive control could not have caught it. TestTool::panicking panics inside invoke, the half the guard already covered. An independent reviewer staged a panic in a test tool’s validate_args and the session died exactly the way this page said it no longer could.

Both are wrapped now, and a panic in either is an ordinary failed call. A tool that panics when asked where it would connect is denied rather than run: nothing about a call can be approved on the word of a tool that cannot answer the question. tested crates/emma/tests/loop.rs a_tool_that_panics_before_it_runs_is_an_observation_too uses a fixture that panics before invoke, and asserts the goal completes, the model is told, and that invoke was never reached. That last assertion is what stops the test drifting back to measuring the arm that was already guarded, which is how the old control ended up where it was.

crates/emma/src/agent.rs — Agent::run_tool_call; crates/emma/tests/loop.rs 
// crates/emma/src/agent.rs — Agent::run_tool_call
let ctx = ToolCtx {
    cwd: self.s.cwd.clone(),
    session_id: self.s.session_id.clone(),
    turn_id: turn_id.to_string(),
};
// **A panicking tool is a failed tool, not a failed session.** This
// file's own first rule is that every failure class reaches the model as
// a `tool_result` and the turn continues — a missing tool, bad
// arguments, a `ToolError`, a hook denial, a refused approval. A panic
// was the one class that did not: it unwound straight through the loop,
// past the session log, past the budget accounting, and took the run
// with it. The tool surface here is large, several of its crates parse
// input from the model, and an index or an `unwrap` in any of them
// ended everything.
//
// `AssertUnwindSafe` is honest rather than a shrug: what crosses the
// boundary is `&ctx` and an owned `Value`, and the loop's own state is
// not touched by the tool. A tool that panics mid-write may of course
// leave its own mess on disk, which is the tool's business and is
// exactly what the message hands back to the model.
// **Ctrl-C reaches a running tool, not just the gap between two.**
// `invoke` used to be awaited outright, and the interrupt flag was read
// only at iteration boundaries and around the model call — so a wrong
// `Bash` ran to its own timeout, 120 seconds by default and up to 600,
// with the keyboard already asking it to stop. In the framed UI raw mode
// means the child never sees a console signal either, so nothing else
// was going to end it.
//
// Dropping the `invoke` future is what cancels the work. That is only
// safe because the one tool that owns a child process spawns it with
// `kill_on_drop(true)` (`tools/fs/src/bash.rs`), so the process dies
// with the future rather than outliving it. A tool that acquires
// something needing an explicit release must say so the same way.
//
// The cancellation is reported as an ordinary failed call: the loop's
// first rule is that every failure class is an observation, and a
// cancelled tool is a failure the model should see rather than a hole
// in the transcript.
let invoked = futures_util::FutureExt::catch_unwind(std::panic::AssertUnwindSafe(
    tool.invoke(&ctx, call.input.clone()),
));
let called = tokio::select! {
    biased;
    () = self.s.interrupt.wait() => {
        self.s.log.append(
            "tool_cancelled",
            json!({ "turn_id": turn_id, "id": call.id, "tool": call.name }),
        );
        let detail = format!(
            "{} was cancelled part-way through by the user. Anything it had already \
             done stands; anything it had not is undone.",
            call.name
        );
        self.s.term.tool_failed(&call.name, &detail);
        self.run_post_hooks(turn_id, call, &detail, false, Some("cancelled"))
            .await;
        return fail("cancelled", detail);
    }
    r = invoked => r,
};
let called = match called {
    Ok(v) => v,
    Err(panic) => {
        let what = panic
            .downcast_ref::<&str>()
            .map(|s| (*s).to_string())
            .or_else(|| panic.downcast_ref::<String>().cloned())
            .unwrap_or_else(|| "a panic with no message".into());
        self.s.log.append(
            "tool_panicked",
            json!({ "turn_id": turn_id, "id": call.id, "tool": call.name,
                    "detail": what }),
        );
        self.s.term.tool_failed(&call.name, &what);
        self.run_post_hooks(turn_id, call, &what, false, Some("tool_panicked"))
            .await;
        return fail(
            "tool_panicked",
            format!(
                "{} panicked and did not finish: {what}. This is a defect in the tool, \
                 not something your arguments can fix — do not retry the same call. \
                 Anything it had already written may be half-done.",
                call.name
            ),
        );
    }
};
let outcome = match called {
    Ok(Ok(outcome)) => outcome,
    Ok(Err(e)) => {
        // The line this whole design exists for. A typed failure is an
        // observation the model acts on; the goal continues.
        self.s.log.append(
            "tool_failed",
            json!({ "turn_id": turn_id, "id": call.id, "tool": call.name,
                    "kind": e.kind(), "detail": e.detail() }),
        );
        self.s.term.tool_failed(&call.name, e.detail());
        self.run_post_hooks(turn_id, call, e.detail(), false, Some(e.kind()))
            .await;
        return fail(e.kind(), e.detail().to_string());
    }
    // The outer `Result` is the tool claiming the session cannot
    // continue. Even that is not allowed to abort silently: it becomes
    // a result the model can read, and the loop's own budgets remain
    // the only thing that ends a goal.
    Err(fault) => {
        self.s.log.append(
            "tool_fault",
            json!({ "turn_id": turn_id, "id": call.id, "tool": call.name,
                    "detail": fault.to_string() }),
        );
        self.s.term.tool_failed(&call.name, &fault.to_string());
        return fail("tool_fault", fault.to_string());
    }
};

Reading it inside out: invoke returns Result<Result<Outcome, ToolError>>. The inner error is an ordinary failed call and keeps its own kind, which is passed straight through to fail rather than being flattened to a single "tool failed" string. The outer error is the tool saying the session cannot continue, and it becomes a result too. catch_unwind wraps another Result around both, whose Err is a panic payload, and the select! can preempt the whole stack when the interrupt trips. It uses biased, so a pending Ctrl-C wins the race against a completed tool. Four error shapes, one closure; none returns early from run_goal. The cancellation is safe to do by dropping the future only because the one tool that owns a child process spawns it with kill_on_drop(true), which the comment above names as an obligation on any future tool holding something that needs an explicit release.

Post-hooks fire on a ToolError and not on a fault

The Ok(Err(e)) arm calls run_post_hooks(..., Some(e.kind())) before failing. The Err(fault) arm does not call it at all. So a PostToolUse hook watching a tool sees its typed failures and not its faults, even though the tool ran in both cases. certified by reading the two arms above: there is one run_post_hooks call in the first and none in the second. Whether that asymmetry is intended is not stated anywhere in agent.rs; it is flagged here rather than changed.

What a failure looks like on the wire

// crates/emma/src/agent.rs
/// A tool that failed, as the observation the model reads and the loop keeps
/// going from.
///
/// `is_error` as well as the kind in the body: the flag is what the API and the
/// model's own training key on, and the body is what says which failure it was
/// and what to do instead. Both halves are load-bearing and neither substitutes
/// for the other.
fn failure_result(id: &str, tool: &str, kind: &str, detail: &str) -> ToolResult {
    ToolResult::failed(
        id,
        json!({ "kind": kind, "tool": tool, "detail": detail }).to_string(),
    )
}

is_error is the flag the API and the model's training key on; the JSON body says which failure it was and what to do instead. A failure rendered without the flag reads to the model as a successful call that returned odd text. tested crates/emma/src/agent.rs a_failure_block_is_flagged_and_typed, a unit test in agent.rs itself, asserts the flag survives to ContentBlock::ToolResult(b).to_value() and, in the same test, that a success carries no is_error key at all. Run it with cargo test -p emma --lib a_failure_block.

// crates/emma/src/agent.rs
fn log_result_block(
    &self,
    turn_id: &str,
    call: &ToolCall,
    block: &ToolResult,
    truncated: Option<bool>,
    exit_code: Option<i64>,
) {
    self.s.log.append(
        "tool_result",
        json!({ "turn_id": turn_id, "id": call.id, "tool": call.name,
                // Written as the content block it becomes, `type` tag and
                // all, because that is the shape the fold reads back and the
                // shape `restore_records` tests `is_error` on.
                "block": ContentBlock::ToolResult(block.clone()),
                "truncated": truncated,
                // Beside the block rather than inside it: the block is the
                // wire shape and the API has no field for this. The
                // delegation footer reads it here instead of parsing the
                // prose, which it could never do correctly.
                "exit_code": exit_code }),
    );
}

The record carries the block rather than the rendered content string, because the string alone cannot be turned back into a message: the block also carries the tool_use_id that pairs it with its call, and is_error when it failed. The content is still greppable, one JSON string deeper than before. truncated is None on every failure path, because a failure has no output to have cut.

Truncation notes, verbatim rather than summarised

// crates/emma/src/agent.rs
fn truncation_note(reason: Option<&str>) -> String {
    match reason {
        Some(reason) => format!("\n[truncated: {reason}]"),
        None => "\n[truncated: this is not the whole output, and this tool did not say which \
                 limit cut it. Narrow the request if you need the rest.]"
            .to_string(),
    }
}

A tool that knows which cap bound says so itself, with the amount and the argument that raises it, and that sentence is repeated rather than reworded. The numbers are the entire content: a page whose link list was cut and a page whose prose was cut both read as "truncated", and only one of them is fixed by asking for fewer characters. The fallback admits that nobody named a limit rather than sending the model to guess at one. tested crates/emma/src/agent.rs a_stated_reason_reaches_the_model_verbatim asserts the reason string survives unmodified and that the generic line contains "did not say which limit".

Exit status is not a failure signal

ToolError is the only failure signal in this file. A non-zero Bash exit comes back as Ok with exit status <n> in the content, so grep -q answering "no" is not a broken shell: it does not enter the memo and is not painted as an error on the terminal. Nothing in the loop branches on a tool's identity, on ToolError::kind, or on exit status, which is why the Bash contract change landed without an edit here and why Delegate is an ordinary tool. certified: grep -n 'call.name ==\|name() ==' crates/emma/src/agent.rs returns exactly one line, and it is inside Spend's doc comment, naming the if call.name == "Delegate" that was rejected. No executable line in the file branches on a tool's name.

The label a failure is remembered by

// crates/emma/src/agent.rs
/// The label a kick quotes, from the same two fields — see [`memo_key_of`] for
/// why this is shared rather than re-derived.
pub(crate) fn label_of(name: &str, input: &Value) -> String {
    format!("{}({})", name, compact(input))
}

// … elided: `open_query`, `failure_result` and `truncation_note` sit between
// these two functions in the file; the latter two are quoted in their own
// sections above.

/// Arguments, short enough to sit inside a kick.
fn compact(args: &Value) -> String {
    let s = args
        .as_object()
        .and_then(|o| {
            o.get("command")
                .or_else(|| o.get("file_path"))
                .or_else(|| o.get("pattern"))
        })
        .and_then(Value::as_str)
        .map(str::to_string)
        .unwrap_or_else(|| args.to_string());
    let s = s.replace('\n', " ");
    if s.chars().count() > 60 {
        format!("{}…", s.chars().take(60).collect::<String>())
    } else {
        s
    }
}

Three argument names are privileged, in this order: command, file_path, pattern. A call with none of them falls back to the whole JSON object. Newlines collapse to spaces so a label stays one line, and the cut is at 60 characters rather than bytes, so a multi-byte argument is not sliced in half. The label is computed once, at the top of run_tool_call, and is what the kick quotes back.

The two hook helpers

// crates/emma/src/agent.rs
async fn run_post_hooks(
    &self,
    turn_id: &str,
    call: &ToolCall,
    content: &str,
    truncated: bool,
    error: Option<&str>,
) -> Vec<String> {
    let hook_call = HookCall {
        tool_name: &call.name,
        tool_call_id: &call.id,
        args: &call.input,
        session_id: &self.s.session_id,
        turn_id,
        result: Some(HookResult {
            content,
            truncated,
            error,
        }),
    };
    let verdict = self
        .s
        .harness
        .run_hooks(HookEvent::PostToolUse, &hook_call)
        .await;
    self.log_hooks(turn_id, &verdict.runs);
    verdict.context
}

fn log_hooks(&self, turn_id: &str, runs: &[emma_harness::HookRun]) {
    for run in runs {
        self.s
            .log
            .append("hook", json!({ "turn_id": turn_id, "run": run }));
    }
}

run_post_hooks returns only verdict.context. A PostToolUse denial has nothing left to deny, since the tool has already run, so the field is not read. log_hooks writes one hook record per run and is called from both hook sites, which is why a hook that produced no output still appears in the session file.

What is not verified here

certified No shipped tool returns the outer Err. The tool_fault path is reachable by type, and every production invoke in tools/ wraps its inner result in Ok(...). rg -n "async fn invoke" tools/ -A 5 | rg "return Err|^\s+Err\(" printed nothing on 2026-09-02 (NO_OUTER_ERR_IN_INVOKE). Failures are always Ok(Err(ToolError)) and become tool_failed, not tool_fault.

crates/emma/src/agent.rs — Agent::run_tool_call; tools/

certified The session fold's reliance on a convention. Reading both files: the fold has no arm for denied, tool_failed, tool_fault, tool_unknown, tool_cancelled or tool_panicked, and needs none, because each of those paths also writes a tool_result record. That is correct today because all of them go through fail(), which calls log_result_block. It is a convention held by one closure rather than a property the type system enforces. A new failure path that returned without going through fail() would produce a session file that folds into a conversation the API rejects, and nothing would say so until a resume.
