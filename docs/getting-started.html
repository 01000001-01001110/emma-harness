Getting started

Build it, give it a key, point it at a directory, state a goal.

certified proven, and a reader can repeat it: a file, a command, a count
observed seen once, live, not repeatable on demand
tested covered by a test shown to fail when the guarantee is removed
unverified believed, not checked

Build

cargo build --release

There is no installer and no published crate. Take the binary from target/release/ and put it on your path, or run it in place. Rust 1.97 or newer builds it; the Mac has built it on 1.97.1. unverified: no minimum version is pinned anywhere, and nobody has tried an older toolchain. What would settle it: build against a few older versions and record the first that fails.

Give it a key

# prompts, and does not echo what you type
emma set-provider anthropic

# the same thing, for the provider already selected
emma api

# for scripts; `-` reads the key from stdin
emma set-provider anthropic --key -

Keys are stored per provider under ~/.emma/, so switching providers does not lose the key for the one you left. The file is merged rather than replaced when a key is written, and Emma refuses to overwrite a credentials file it cannot parse. That behaviour exists because an earlier version replaced the whole document and silently deleted an unrelated key that lived in it.

Point it at a directory

Emma has no prompt compiled into it. It walks up from where you are standing, the way git looks for .git, and loads whatever configuration it finds. If the directory already has a .claude/ from Claude Code, Emma reads it as it stands and you can skip this step entirely. 

# write a minimal working .emma/ here, then stop
emma init

# load what is there and report, without calling a model
emma config check

config check is the command to reach for whenever something you configured did not take effect. It prints what was found, what was skipped, and why: an agent file with no description, frontmatter that will not parse, a settings key Emma does not model. It makes no model call and costs nothing. certified: run it in this repository and it reports 21 tools and a tool-schema hash.

State a goal

# interactive: the full-screen interface, goal typed at the prompt
emma

# the goal on the command line
emma goal "make the tests pass"

# one goal, no prompts, then exit. Anything needing approval is denied
# and the model is told why
emma -p "summarise what changed since the last tag"

A goal is held rather than answered. Emma keeps working until the goal is met, the budget runs out, or a rule stops it. What "met" means, and the four ways a goal can end, are on the loop page.

What it will ask you

Anything that can change your machine or reach the network stops for approval the first time. You can approve once, or for the session, and a remembered answer is written to settings.local.json in the project. Network approvals are per host.

The gate is a consent interface rather than a sandbox. It enforces nothing a tool does not declare about itself, and Bash can do anything. Consent covers where that ends, including the parts that will surprise you.

Bound the run

Every goal is bounded four ways, and each has a flag. The defaults are the values below.

FlagDefaultBounds
--max-iterations60model calls per goal
--max-tokens500,000billable tokens per goal
--timeout1,800wall-clock seconds per goal
--max-kicks3times the loop may say "not done, continue"
Two of those are tripwires, not ceilings

--max-tokens is checked after a call returns, so the call that crosses the line is paid for in full. A real run overshot 500,000 and finished at 579,565. --timeout is checked at the top of an iteration, so it bounds when the loop declines to start another one rather than how long a goal takes; a tool waiting on a network that never answers is bounded only by that tool's own timeout. certified: the overshoot is in ~/.emma/sessions/sess-1786385316950-34808.jsonl, whose goal_finished record reads "tokens":579565.

Pick up where you left off

# continue the newest session started in this directory
emma --resume

# or a specific one
emma --resume sess-1786385316950-34808

The conversation comes back. The tools do not re-run. Nothing is replayed, so a file the previous session wrote is still written and a command it ran is not run again. Sessions covers what is restored and what is lost.

When something goes wrong

SymptomWhere to look
A setting you wrote had no effect emma config check, then Configuration, which lists the reasons in the order worth checking.
Emma keeps asking about the same thing Consent. A rule that can never match is reported at startup, and a rule written for a Unicode domain matches nothing.
A goal stopped early The ending line names which bound was hit. The loop explains all four.
The terminal looks wrong, or is left in a strange state EMMA_UI=inline falls back to the old inline viewport. The terminal covers the alternate screen and every exit path.
You want to know what a subagent actually did emma agents, and the footer described in Delegation, which is built from the harness's own record rather than the subagent's account.

What is not here yet

  • No installer, no published crate, no binary release. Building from source is the only route.
  • No emma stats. Emma records what every call cost and has no command that reads it back, so "what did today cost" has no answer short of parsing the session files yourself.
  • Nothing has been run on macOS. The suite is cross-platform by reading rather than by running, and one test could not be compiled anywhere. See What is not verified.
