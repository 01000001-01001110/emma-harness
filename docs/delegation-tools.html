resolve_tools, and the default that surprises people

Delegation The nested run One at a time Agent definitions resolve_tools The brief The footer Budgets & spend emma agents

An agent file that names no tools key inherits every candidate tool this build registers, Write, Edit and Bash included. So do tools: [] and tools: "". The design note for this feature specified a fixed read-only child registry instead, and that version never shipped.

crates/emma/src/delegate.rs — resolve_tools; crates/harness/src/claude.rs — Tools::allowlist

The function

/// The tools one agent file resolves to, and the names that matched nothing.
fn resolve_tools(def: &AgentDef, candidates: &[Arc<dyn Tool>]) -> (Registry, Vec<String>) {
    let mut registry = Registry::new();
    let Some(wanted) = def.tools.as_deref() else {
        // Absent and empty both mean inherit. See
        // `claude::Tools::allowlist`, which is where that ruling is argued.
        for tool in candidates {
            registry.register(tool.clone());
        }
        return (registry, Vec::new());
    };
    let mut dropped = Vec::new();
    for want in wanted {
        if !candidates
            .iter()
            .any(|t| t.name().eq_ignore_ascii_case(want))
        {
            dropped.push(want.clone());
        }
    }
    // Registry order rather than the file's order, for the reason
    // `select_tools` gives: the tool schema rides in the cached prompt prefix,
    // so the bytes must not depend on how somebody typed a list.
    for tool in candidates {
        if wanted.iter().any(|w| w.eq_ignore_ascii_case(tool.name())) {
            registry.register(tool.clone());
        }
    }
    (registry, dropped)
}
crates/emma/src/delegate.rs — resolve_tools, quoted entire

Three behaviours, and each is a decision somebody could have made the other way. None registers every candidate and reports nothing dropped. A present list is walked twice: once to collect the names that matched no candidate, once to register. The registration walk iterates candidates rather than the file's list, so the registry's order wins over the file's, because the tool schema rides in the cached prompt prefix and the bytes must not depend on how somebody typed a list.

Matching is eq_ignore_ascii_case on both walks. certified 14 of the 90 files in the library on this machine spell their tools read, write, edit; re-counted today by parsing each file's tools: block. Emma's own tool names differ by more than case, so nothing becomes ambiguous under the looser comparison.

Why absent means inherit

The ruling is argued one crate away, in Tools::allowlist, and resolve_tools cites it rather than restating it. tools: with no value parses as YAML null and never reaches the function; tools: [] and tools: "" do, and under Emma's own rules an empty allowlist means no tools at all. In Claude Code an absent tools means inherit everything, and a present-but-empty one is the same statement written differently: nobody writes tools: [] meaning "this agent may do nothing". So all three collapse to None, and None is the caller's signal to inherit.

crates/harness/src/claude.rs — Tools::allowlist
The design said read-only. The code went the other way.

notes/design/subagents-mechanism.md §5 specifies a fixed, read-only child registry (Read, Glob, Grep and no more), and its closing "what I could not resolve" list recommends that as the default. The interface note took the same position. Neither shipped. The registry is per agent type, built from the file's tools list, and an absent or empty list inherits the writers. That design note carries a dated header saying so, which is what keeps the refuted version legible as refuted rather than inviting it back.

What bounds it, and what does not

Two things bound the permissive default. The approval gate is shared, so a sub's Write or Bash asks the same question at the same keyboard the parent's would. And the persona's own allowlist is applied to the candidate list before any agent type is resolved, so an agent type cannot become a route to a tool the operator excluded from this run.

What does not bound it: nothing in the file format makes the permissive reading visible. A file with no tools: line looks like a file nobody has configured, and it is a file that can write.

Where the filter is applied

Delegate::new is the whole of construction: filter the candidates by persona, resolve each definition, note what was dropped, refuse a type left with nothing, compose the instructions, and build the description. It answers None when nothing survived, which is the same ruling Skill::new makes: offering a capability that cannot work is a trap with a description attached. 

    /// Resolve the agent files against this binary's tools, or answer `None`.
    ///
    /// `None` when nothing survived resolution, and it is the same ruling
    /// `Skill::new` makes: offering a capability that cannot work is a trap with
    /// a description attached. The notes say what was dropped and why, because a
    /// catalogue quietly shorter than the directory is the gap nobody notices
    /// until the model cannot find an agent that is plainly there.
    ///
    /// **Unknown tool names are filtered, not fatal, unlike
    /// `Harness::select_tools`.** A persona's list is the
    /// operator's own boot-time choice and a typo in it is worth refusing to
    /// start over. An agent library is ninety files somebody accumulated for a
    /// different program: measured against a real one, its files name
    /// `TodoWrite`, `Task`, `repl`, `artifacts` and `brave_web_search`, none of
    /// which this binary registers, and bailing would mean Emma does not start
    /// in that directory at all. A rule that fires on correct configuration is
    /// an outage, not a safety property.
    ///
    /// Matching is case-insensitive first, because 14 of those files spell them
    /// `read`, `write`, `edit`. Emma's tool names differ by more than case, so
    /// nothing becomes ambiguous.
    pub fn new(
        nest: Nest,
        defs: &[AgentDef],
        available: &[Arc<dyn Tool>],
        persona_allowed: Option<&[String]>,
        provider_for: &ProviderFor,
    ) -> (Option<Self>, Vec<String>) {
        let mut notes = Vec::new();
        // The persona's allowlist applies first and applies to everything: an
        // agent type must not be a route to a tool the operator excluded from
        // this run. `select_tools` will apply the same list to the parent's
        // registry a moment from now; this is the same filter, one level down.
        let candidates: Vec<Arc<dyn Tool>> = available
            .iter()
            .filter(|t| match persona_allowed {
                Some(allowed) => allowed.iter().any(|a| a == t.name()),
                None => true,
            })
            .cloned()
            .collect();

        let mut types = BTreeMap::new();
        for def in defs {
            let (tools, dropped) = resolve_tools(def, &candidates);
            if !dropped.is_empty() {
                notes.push(format!(
                    "agent `{}`: this build has no {} — the rest of its tools were kept",
                    def.name,
                    dropped.join(", ")
                ));
            }
            if tools.names().is_empty() {
                notes.push(format!(
                    "agent `{}` named no tool this build registers, so it could not do \
                     anything — not offered",
                    def.name
                ));
                continue;
            }
            debug_assert!(
                !tools.names().contains(&NAME),
                "the child registry contains {NAME}: recursion is prevented by this registry \
                 not containing it, so a future edit that builds it from the parent's has \
                 removed the only guard"
            );
            let instructions = match def.instructions.trim().is_empty() {
                true => nest.harness.instructions.clone(),
                false => format!("{}\n\n{}", nest.harness.instructions, def.instructions)
                    .trim_start()
                    .to_string(),
            };
            types.insert(
                def.name.clone(),
                AgentType {
                    name: def.name.clone(),
                    description: def.description.clone(),
                    instructions,
                    tools,
                    provider: provider_for(def.model.as_deref()),
                    max_iterations: def.max_turns.unwrap_or(SUB_ITERATIONS),
                    max_tokens: def.max_tokens,
                },
            );
        }
        if types.is_empty() {
            return (None, notes);
        }
        let description = describe(&types);
        (
            Some(Self {
                nest,
                types,
                description,
                permit: Semaphore::new(1),
                seq: AtomicU64::new(0),
            }),
            notes,
        )
    }

Unknown tool names are filtered rather than fatal, and that diverges from Harness::select_tools, which refuses to start over a name it does not recognise. The difference is who wrote the list. A persona's list is the operator's own boot-time choice. An agent library is ninety files somebody accumulated for a different program: measured against a real one, its files name TodoWrite, Task, repl, artifacts and brave_web_search, none of which this binary registers, and bailing would mean Emma does not start in that directory at all.

crates/emma/src/delegate.rs — Delegate::new; crates/harness/src/lib.rs — Harness::select_tools

Two notes come out of the loop and both name the agent. The first says which tools this build has no answer for and that the rest were kept; the second says a type named nothing this build registers and is not offered at all. They reach the operator through emma config check and the startup banner, which is what stops a catalogue quietly shorter than the directory.

Neither branch has a test

unverified The tests module's own region comment says it covers "how an agent file's tool list resolves against a build that does not have all of it", and no such test is in the file: the ten unit tests are all Facts and exit_status. Every integration test in tests/delegate.rs passes an explicit Some(vec![…]) through its agent_type helper, so the inherit branch, the one that hands a subagent Bash, is exercised by nothing at all.

crates/emma/src/delegate.rs — the tests region comment; crates/emma/tests/delegate.rs — agent_type

What would settle it: two unit tests over resolve_tools. One with tools: None, asserting the returned registry names every candidate and dropped is empty. One with a list mixing a known name, a known name in the wrong case and an unknown name, asserting the first two are registered in registry order and the third is the only entry in dropped. Both are pure functions over an AgentDef and a slice, so neither needs a loop, a provider or a temporary directory.

certified The gap is countable rather than asserted: grep -c "resolve_tools" crates/emma/src/delegate.rs returns 2, the definition and its one call site in Delegate::new, and neither is inside mod tests.
