Every other page in this chapter describes a format. This one describes the data that exists in it on the owner's machine, counted rather than remembered, with the script attached so the count can be redone rather than believed. One backlog item turns on these numbers, and it spent its first write-up blocked on the wrong one. It also covers the one thing that reads the store for a purpose other than continuing a session: the training exporter, which projects the same files into records a fine-tuning pipeline can read.

The directory moved while this page was being written

An earlier run of the same script, less than an hour before, read 100 files and 779 records, with 52 carrying a goal. The run above read 103 files and 791 records, with 55 carrying a goal. Three sessions were recorded in between, by whatever else was using this machine. observed during this write-up on 2026-08-16, and not repeatable: the earlier state is gone. What that means for every figure on this page is that it is a reading with a timestamp, not a property, and the number to distrust first is any one quoted without one.

Half the corpus is empty files

48 of 103 are zero bytes. SessionLog::open creates the file at startup, before anything has happened, so a run that never reaches a goal leaves one behind and nothing prunes them. certified: 55 files carry at least one goal record, and 48 are empty, which accounts for all 103. Every non-empty file in this corpus has a goal in it.

crates/emma/src/session.rs — SessionLog::open

All three readers cope. restore refuses a file with no goal record and says so. locate and the first-run scan read each one, find no matching record, and move on. What the empty files cost is a file read each in both scans, and what they cost a reader is that every count anyone quotes about this directory has to subtract them first.

Compaction has never fired here

certified: zero compacted records across 103 files and 177 model_call records. The largest input any call carried is 95,524 tokens against the 120,000 default cap, computed as input_tokens + cache_read_input_tokens + cache_creation_input_tokens over every model_call record in the directory. Close, and never over.

So everything about the trigger rests on tests with an artificially small cap and on reading the function. The mechanism is exercised, by tests that set max_context to 400 and to 1. The threshold, in ordinary use, is not.

The budget overshoot is in a file you can grep

The largest goal_finished.tokens in the directory is 579,565, against a 500,000 budget, and it is in sess-1786385316950-34808.jsonl. That file is also the largest in the corpus at 272,923 bytes. certified: grep the file for "kind":"goal_finished" and read the tokens field. It confirms from disk what agent.rs says about the token budget being tested after a call rather than before, so the call that crosses the cap is paid for in full.

One delegation record, and a backlog item that turned on it

A backlog entry, "every delegation pays an unamortisable cache write", needs a delegation-clustering number to decide whether moving deliver out of the SubagentClaim contract is worth it. The item recorded the corpus as "86 files, mostly 0 bytes, largest 4.7 KB" and concluded it would unblock itself with use.

Both halves were wrong in the same way. The directory is not thin: 103 files, largest 266 KB. And the blocking query returns one. certified: there is exactly one delegation record in the entire corpus, in sess-1786710409801-39600.jsonl. Delegation has barely been used on this machine, and ordinary session growth does not produce a clustering number, so the item is blocked on usage rather than on size. The correction is recorded in the entry itself and the lesson is a recorded one: a blocker recorded as a size problem was a usage problem. Record the count the blocking query returned, not a summary of the corpus it ran against.

Training material, read out of the same files

emma export-training [<id>] [--out <PATH>] [--min-ending <any|finished>] turns the store above into one JSONL record per assistant turn, under the schema emma.training.v1. With no id it sweeps every session; the output is ~/.emma/training/<id>.training.jsonl, or EMMA_TRAINING_DIR, or whatever --out names. There is also a standing half: a finished goal refreshes its own session's export, unless training_capture is false in settings.json. Absent means on, and nothing leaves the machine either way — a local file built from a local transcript.

The session log is read and never written. The request was to organise what is already recorded rather than to move it, so the transcript stays the audit trail it was and this is a projection of it. Each export is truncated and rewritten whole rather than appended to, so running it twice cannot double anything, and a filter that keeps nothing removes an earlier export rather than leaving two answers on disk. certified 159 sessions on this box, 2026-09-06: 76 files written, 250 records, and sha256sum *.jsonl | sha256sum over ~/.emma/sessions identical before and after (c88a6df279dd19ec… both times). Repeat by taking that digest, running the command, and taking it again.

messages is the ordinary chat format, so a supervised fine-tuning pipeline reads it with no transformation: messages is the prompt, and thinking plus output plus tool_calls is the completion. Tool results travel inside a user message as tool_result blocks, which is the shape the run actually sent.

context is the field that keeps the rest honest, and it has three values. per_turn means the message list is the one that turn's request carried, rebuilt by session::fold_prefixes, the same fold --resume spends. per_turn_shed is that same guarantee over a conversation a shed had already emptied: faithful to what was sent, and what was sent no longer holds the file contents and command outputs it names, which a trainer wants to know before learning from the turn. partial means the fold refused a damaged record somewhere in the turn's prefix, so the list may not be what was sent and nothing here can say how far off it is. An exporter that dropped the fold's own damage report would be claiming per_turn over a fold that had already said it could not. tested Both new values are proven against records constructed to the shape agent.rs writes, with the mutations run. unverified Neither has been seen on a real transcript: all 250 records in the sweep above say per_turn, because this corpus holds no shed record and no damaged compacted one. Settling it: drive a run past max_context on a small local model until it sheds, export it, and read the field; and truncate a session file mid-compacted and export that.

thinking is its own field, and null is not "". thinking_recorded separates "the model produced no thinking" from "this log does not carry it": a turn whose raw_content holds a thinking block is true even when the block is empty, and a turn from a build written before raw_content existed is false with thinking null. An empty string is never invented for either. thinking_signed says the block carried a provider signature; the signature itself is not exported, because it validates a replay and is worth nothing to a trainer. certified A real Anthropic turn in this store exports thinking_recorded=true, thinking_signed=true and a thinking of length 0, which is the distinction arriving in the wild rather than in a fixture. The same sweep also shows web_search_requests as null on an August session and 0 on a September one, because the field did not exist when the older log was written; a 0 there would have been a measurement nobody made.

A shed tool result exports as the text that was sent, not the text the tool_result record holds. A shed that landed before the next request means the model never saw the original, so exporting the original would teach it from a message nobody sent; a shed after that request rewrites nothing here, because by then the full output had gone out. The shed boolean on each result says which of the two a consumer has. tested unverified Which of the two windows is the right one is a judgement, not a fact: somebody building a corpus for context-management training would want the final state instead. Only the owner saying what the corpus is for settles it.

A record is one turn of one trajectory, and nothing in the file scores a turn. goal_ending is the only outcome signal and it labels the whole goal rather than the turn. --min-ending finished selects on that recorded ending and on nothing else; the default is any, because a trajectory that failed is training material too and a corpus of nothing but successes cannot teach recovery. unverified How many of the 250 records survive --min-ending finished is unmeasured: the sweep above ran with the default. One command settles it.

crates/emma/src/export.rs — module doc, SCHEMA, Filter, export, export_session, capture, capture_out_dir, default_out_dir; crates/emma/src/agent.rs — keep_training_material; crates/emma/src/cli.rs — Command::ExportTraining

One hazard the module carries in its own comment, because it has already happened: the standing capture used to resolve its destination from the process's home while reading a session log that was somewhere else, so an integration test driving an Agent over a fixture log in a temporary directory wrote into the developer's real ~/.emma/training. Twenty-one files named after test fixtures were found in a real corpus on 2026-08-27. capture_out_dir derives the destination from the session file's own store instead, which removes the class rather than teaching each test to clean up after itself.

What these numbers are good for, and what they are not

They are one machine on one evening. They settle questions of the form "does this ever happen in real use", which is the form that keeps turning out to matter here: compaction does not, delegation almost never does, the older-format assistant record still does, and the memo's orphan tool_result does. They settle nothing about how Emma behaves on anyone else's machine, and nothing about the future.

This is the third time the directory has been counted in a written record. The first count was a summary that did not answer the query it was cited for. The second, on 2026-08-16, was accurate and was overtaken within the day. That is why the timestamps are included.

What this page covers

The whole of ~/.emma/sessions/ as it stood at 2026-08-16 20:39 EDT: file count, empty count, largest file, record count, per-kind histogram, and the four queries the rest of the chapter cites. Since 2026-09-06 it also covers crates/emma/src/export.rs, the training exporter, which is a projection of the same store: the schema, the three context values, the thinking fields, the shed rule, the filter, and both destinations. What it does not cover is the exporter's internals below export_session — first_damaged_prefix and the per-turn assembly are read only through what they put in a record.

What is not verified here

  • unverified Whether this corpus is representative of anything. One user, one machine, about a week of use, and much of it made by agents working on Emma itself rather than by someone using Emma for other work. Settle it by counting a second machine's directory, which nobody has.
  • unverified Whether the 48 empty files have any cost worth measuring. The two scans read each one, and nobody has timed the difference. Settle it by timing startup before and after deleting them.
  • observed The mid-write-up growth from 100 files to 103. It happened, it is not repeatable, and the earlier state cannot be recovered to check the diff.
