The directory moved while this page was being written

An earlier run of the same script, less than an hour before, read 100 files and 779 records, with 52 carrying a goal. The run above read 103 files and 791 records, with 55 carrying a goal. Three sessions were recorded in between, by whatever else was using this machine. observed during this write-up on 2026-08-16, and not repeatable: the earlier state is gone. What that means for every figure on this page is that it is a reading with a timestamp, not a property, and the number to distrust first is any one quoted without one.

Half the corpus is empty files

48 of 103 are zero bytes. SessionLog::open creates the file at startup, before anything has happened, so a run that never reaches a goal leaves one behind and nothing prunes them. certified: 55 files carry at least one goal record, and 48 are empty, which accounts for all 103. Every non-empty file in this corpus has a goal in it.

crates/emma/src/session.rs — SessionLog::open

All three readers cope. restore refuses a file with no goal record and says so. locate and the first-run scan read each one, find no matching record, and move on. What the empty files cost is a file read each in both scans, and what they cost a reader is that every count anyone quotes about this directory has to subtract them first.

Compaction has never fired here

certified: zero compacted records across 103 files and 177 model_call records. The largest input any call carried is 95,524 tokens against the 120,000 default cap, computed as input_tokens + cache_read_input_tokens + cache_creation_input_tokens over every model_call record in the directory. Close, and never over.

So everything about the trigger rests on tests with an artificially small cap and on reading the function. The mechanism is exercised, by tests that set max_context to 400 and to 1. The threshold, in ordinary use, is not.

The budget overshoot is in a file you can grep

The largest goal_finished.tokens in the directory is 579,565, against a 500,000 budget, and it is in sess-1786385316950-34808.jsonl. That file is also the largest in the corpus at 272,923 bytes. certified: grep the file for "kind":"goal_finished" and read the tokens field. It confirms from disk what agent.rs says about the token budget being tested after a call rather than before, so the call that crosses the cap is paid for in full.

One delegation record, and a backlog item that turned on it

notes/improvements.md item 6, "every delegation pays an unamortisable cache write", needs a delegation-clustering number to decide whether moving deliver out of the SubagentClaim contract is worth it. The item recorded the corpus as "86 files, mostly 0 bytes, largest 4.7 KB" and concluded it would unblock itself with use.

Both halves were wrong in the same way. The directory is not thin: 103 files, largest 266 KB. And the blocking query returns one. certified: there is exactly one delegation record in the entire corpus, in sess-1786710409801-39600.jsonl. Delegation has barely been used on this machine, and ordinary session growth does not produce a clustering number, so the item is blocked on usage rather than on size. The correction is recorded in the item itself and the lesson is notes/lessons/a-blocker-recorded-as-a-size-problem-was-a-usage-problem.md: record the count the blocking query returned, not a summary of the corpus it ran against.

The one delegated session also carries the only sub.goal and sub.goal_finished records in the corpus, which is why the file name matters: it is the only place the sub. namespacing on Records can be checked against real data.

What these numbers are good for, and what they are not

They are one machine on one evening. They settle questions of the form "does this ever happen in real use", which is the form that keeps turning out to matter here: compaction does not, delegation almost never does, the older-format assistant record still does, and the memo's orphan tool_result does. They settle nothing about how Emma behaves on anyone else's machine, and nothing about the future.

This is the third time the directory has been counted in a written record. The first count was a summary that did not answer the query it was cited for. The second, on 2026-08-16, was accurate and was overtaken within the day. That is why the timestamps are included.

What this page covers

The whole of ~/.emma/sessions/ as it stood at 2026-08-16 20:39 EDT: file count, empty count, largest file, record count, per-kind histogram, and the four queries the rest of the chapter cites. It covers no source code. Everything here is a reading of data produced by the code the other pages describe.

What is not verified here

  • unverified Whether this corpus is representative of anything. One user, one machine, about a week of use, and much of it made by agents working on Emma itself rather than by someone using Emma for other work. Settle it by counting a second machine's directory, which nobody has.
  • unverified Whether the 48 empty files have any cost worth measuring. The two scans read each one, and nobody has timed the difference. Settle it by timing startup before and after deleting them.
  • observed The mid-write-up growth from 100 files to 103. It happened, it is not repeatable, and the earlier state cannot be recovered to check the diff.
