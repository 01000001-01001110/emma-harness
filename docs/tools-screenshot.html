Doing work

Screenshot: the screen, on whichever wire the provider has

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP screenshot screenshot

Screenshot captures the primary display, bounds the image so a capture is not a megabyte of base64, and hands the bytes to the model on the wire the running provider actually has. Three wires, not one, and the difference is not cosmetic: only Anthropic's format can say this picture belongs to that tool result.

Three shapes, because the providers have three

On Anthropic a tool result's content is an array, so the image is a block inside the result and the model is told which call produced it. On the two chat-completions hosts there is no such place, so the picture rides an image_url content part on a following user message. On Ollama it is an images array of base64 strings on the same following message. The last two are attachments beside a result rather than part of it, and whether the model looks at one depends on the model, which is what the tool says out loud rather than implying. tested one test per wire renders a result carrying one image and asserts the block, the media type and the payload; removing the image arm from any of them turns its test red.

A provider with no image path is told to the tool as “no”, so a provider added later gets an honest refusal in the result rather than a picture dropped on the floor. A platform with no capture backend registers the tool anyway and refuses in words at call time: telling the model I cannot capture the screen here is more useful than the tool being absent, because absence reads as a capability that was never mentioned.

The Windows backend is GDI, because the obvious one is blocked

Stock Defender refuses a PowerShell script that captures, resizes and encodes. ScriptContainedMaliciousContent, reproducibly, as -Command and as a .ps1 alike. It was bisected: capture alone is fine, resize alone is fine, JPEG alone is fine, and the three together are the signature. Finding a spelling the scanner misses is evasion, so the backend is in-process instead: BitBlt, StretchBlt and GDI+. certified reproduced and bisected on Windows 11 in the port report. This is worth writing down because it is the kind of finding that gets re-proposed by the next person who reads the recommendation it overturned.

The first GDI version returned a solid black image and passed every test it had. PNG signature, correct dimensions, JPEG magic, smaller than the original: all true of a black rectangle. The cause was that the source bitmap was already selected into another device context, so the second SelectObject returned null and StretchBlt copied a one-pixel default. Only opening the file found it. The test carries a size floor with both measured numbers now, and an environment variable that keeps the capture on disk so the next person can look at it. certified 1920×1080 PNG of 1,099,058 bytes and a legible 1280×720 JPEG of 159,551 bytes, about seventy milliseconds, opened and read, with layered windows composited.

A logged capture is a path, and a resume reads the file back

The session log records an image as its path, media type and size, never its bytes: a bounded screenshot is still several hundred kilobytes of base64, and a log line that size per capture makes the transcript unreadable and the fold slow for no gain. The fold reads the file back when a session is resumed, and when the file is gone it drops the image and appends [image not replayed: …] to the result's text. tested a fold over two captures, one file present and one deleted: the bytes come back for the first and the loss is said for the second. Making the fold keep the log's own value turns it red.

That is the honest half of a real trade. Replay depends on a file outside the log, and when the dependency is not met the transcript says so rather than quietly becoming a text-only conversation, which a model reading it would have no way to detect. Compaction, shedding and pruning all drop a result's images with its text for the mirror-image reason: leaving them would ship the bytes under a note saying they are gone, and would report a saving that was not taken.

Two hazards nothing can detect

unverified A macOS capture with no windows showing, and a Windows capture from a non-interactive window station (a service, or a locked session), both return a rectangle of the right size that is entirely black or entirely wallpaper, and both report success. There is no return value that distinguishes either from a legitimate capture of a plain screen. Settled only by looking at the file, which is why the size floor and the keep-the-file hook exist. Named on the roadmap rather than guarded in code.

unverified Not one line of the macOS backend has run. It shells out to screencapture and sips, and its argument lists are asserted against a scripted runner that agrees with the fork's spelling rather than with a real macOS. Settled by cargo test -p emma-tools-screenshot plus one real capture on the Mac.

unverified No live provider has been sent an image on any of the four wires. Three specific unknowns: whether Anthropic accepts a tool result whose content array is text then image in that order; whether OpenRouter passes the data URL through to every upstream; and whether a local vision model on Ollama reads the images array off a following user message rather than off the tool message. Settled by one call each.
