Retry

Providers & models The boundary Content blocks The turn back Model limits Caching The cache floor Retry Credentials

Four attempts, 500 ms doubling, a 20-second ceiling on any single wait including one the provider asked for. Three rules govern it, and the third governs visibility during an interactive run: a retry the user cannot see is indistinguishable from a hang, and a user who cannot tell hits Ctrl-C and loses the work.

The policy

crates/llm/src/retry.rs · struct Retry, impl Default

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Retry {
    /// Total tries, not extra tries: `3` means the original plus two retries.
    pub max_attempts: u32,
    /// First backoff; doubles per attempt.
    pub base: Duration,
    /// Ceiling on any single wait, including one the provider asked for. A
    /// `retry-after: 3600` is the provider saying "come back in an hour", which
    /// for an interactive tool means "tell the user now", not "sleep".
    pub cap: Duration,
}

impl Default for Retry {
    fn default() -> Self {
        Self {
            max_attempts: 4,
            base: Duration::from_millis(500),
            cap: Duration::from_secs(20),
        }
    }
}
crates/llm/src/retry.rs — Retry

max_attempts: 4 counts the original, so the default is one try plus three retries. Every field is pub so the provider tests build a policy with millisecond delays and exercise the retry path without making the suite slow.

Computing one delay

crates/llm/src/retry.rs · Retry::delay_for

/// How long to wait before attempt `attempt + 1`, or `None` to give up.
///
/// `attempt` is 1-based and counts the try that just failed.
pub fn delay_for(&self, err: &LlmError, attempt: u32) -> Option<Duration> {
    if !err.retryable() || attempt >= self.max_attempts {
        return None;
    }
    // A provider-supplied delay overrides the curve entirely: it is the
    // only party that knows when the bucket refills.
    if let Some(after) = err.retry_after() {
        return Some(after.min(self.cap));
    }
    let factor = 2u32.saturating_pow(attempt.saturating_sub(1));
    Some(self.base.saturating_mul(factor).min(self.cap))
}
crates/llm/src/retry.rs — delay_for

Four branches, in order. A non-retryable error gives up immediately. The attempt cap gives up. A provider-supplied retry-after overrides the curve and is then clamped to the cap. Otherwise the curve: base × 2^(attempt−1), clamped. Both arithmetic operations saturate, so a large attempt cannot overflow into a small delay.

The 20-second cap is never reached on the curve at the default settings. It exists for the retry-after path, where the provider can ask for an hour. a_retry_after_longer_than_the_cap_is_clamped sends 3,600 seconds and asserts 20 comes back. backoff_doubles_and_stops_at_the_attempt_cap pins the doubling and the None at the ceiling. retry_after_wins_over_the_curve pins the override with a comment saying why: waiting 100 ms just spends another attempt on a bucket that is still empty. nothing_retryable_is_never_retried pins a 400. tested, on the assertions as written; no mutation was run here.

Which failures are retryable

crates/llm/src/lib.rs · LlmError::retryable, LlmError::retry_after

/// Failures where the same request may succeed unchanged. A 400 is not one
/// of them — retrying a malformed request just spends the user's time.
pub fn retryable(&self) -> bool {
    matches!(
        self,
        Self::RateLimited { .. } | Self::Unavailable { .. } | Self::Transport(_)
    )
}

fn retry_after(&self) -> Option<Duration> {
    match self {
        Self::RateLimited { retry_after, .. } => *retry_after,
        _ => None,
    }
}
crates/llm/src/lib.rs — LlmError::retryable

Three variants of nine are retryable. The header is parsed on every response but carried on RateLimited alone, so a 5xx that happens to send one backs off on the curve instead. The module doc gives the reason: 429 is the case the API documents sending it for, and widening it would be guessing.

Parsing the header

crates/llm/src/retry.rs · retry_after_seconds

/// Parse a `retry-after` header value. Seconds only — the HTTP-date form is
/// legal but the Messages API sends seconds, and mis-parsing a date into a
/// duration is worse than ignoring it and backing off on the curve.
pub(crate) fn retry_after_seconds(raw: Option<&str>) -> Option<Duration> {
    raw?.trim().parse::<u64>().ok().map(Duration::from_secs)
}
crates/llm/src/retry.rs — retry_after_seconds

header_parsing_ignores_what_it_cannot_read covers all four cases in eight lines: "3", " 12 " with surrounding whitespace, an HTTP-date which yields None, and no header at all. tested An unparseable value is indistinguishable from an absent one downstream. That is the intended degradation: the curve takes over.

Turning a status into an error

crates/llm/src/anthropic.rs · AnthropicProvider::classify

async fn classify(&self, resp: reqwest::Response) -> LlmError {
    let status = resp.status();
    let retry_after = retry_after_seconds(
        resp.headers()
            .get(reqwest::header::RETRY_AFTER)
            .and_then(|v| v.to_str().ok()),
    );
    let body = resp.text().await.unwrap_or_default();
    let message = self.scrub(trim_body(&api_message(&body)));

    match status.as_u16() {
        401 => LlmError::Unauthorized { message },
        403 => LlmError::Forbidden { message },
        400 | 404 | 413 | 422 => LlmError::BadRequest { message },
        429 => LlmError::RateLimited {
            retry_after,
            retry_hint: match retry_after {
                Some(d) => format!("; the API asked for {}s", d.as_secs()),
                None => "; no retry-after was given".to_string(),
            },
            message,
        },
        code if code >= 500 => LlmError::Unavailable {
            status: code,
            message,
        },
        code => LlmError::Api {
            status: code,
            message,
        },
    }
}

404 and 413 sit under BadRequest rather than under Api, which is a judgement about what they mean here: a 404 from the Messages API is a wrong model id or a wrong path, and a 413 is a request too large. Both are the request being wrong, and neither is fixed by sending it again. A transport failure never reaches classify at all; execute turns it into Transport directly.

crates/llm/src/anthropic.rs · api_message

/// The provider's own error prose, or the whole body when it is not shaped the
/// way the API documents. "request failed" is never enough to act on; the
/// message the API wrote is.
fn api_message(body: &str) -> String {
    serde_json::from_str::<Value>(body)
        .ok()
        .and_then(|v| {
            v.pointer("/error/message")
                .and_then(|m| m.as_str())
                .map(str::to_string)
        })
        .unwrap_or_else(|| body.trim().to_string())
}
crates/llm/src/anthropic.rs — api_message

A body that is not JSON, or is JSON without /error/message, falls through to the trimmed body itself, so a proxy's HTML error page arrives as its own text rather than as a parse failure. trim_body in lib.rs then cuts it to 600 bytes on a character boundary and appends an ellipsis, so a multi-kilobyte body still fits a terminal line. a_400_is_surfaced_with_what_the_api_objected_to asserts the phrase roles must alternate survives into the message and that the stub saw exactly one request. tested

The loop, and where retrying stops

crates/llm/src/anthropic.rs · AnthropicProvider::execute

async fn execute(
    &self,
    body: Value,
    mode: Mode,
    events: Option<&mpsc::Sender<Event>>,
) -> Result<AssistantTurn, LlmError> {
    let mut attempt: u32 = 1;
    loop {
        let sent = self
            .http
            .post(&self.base_url)
            .header("x-api-key", self.key.expose())
            .header("anthropic-version", API_VERSION)
            .header("content-type", "application/json")
            .json(&body)
            .send()
            .await;

        let failure = match sent {
            Ok(resp) if resp.status().is_success() => {
                // Past this point bytes may already have reached the user,
                // so a mid-stream failure is surfaced rather than retried:
                // a retry would replay text the terminal has printed.
                return match mode {
                    Mode::Batch => self.read_batch(resp).await,
                    Mode::Stream => self.read_stream(resp, events).await,
                };
            }
            Ok(resp) => self.classify(resp).await,
            Err(e) => LlmError::Transport(self.scrub(e.to_string())),
        };

        let Some(delay) = self.retry.delay_for(&failure, attempt) else {
            return Err(failure);
        };
        notify(
            events,
            Event::Retrying {
                attempt,
                max_attempts: self.retry.max_attempts,
                delay,
                reason: failure.to_string(),
            },
        )
        .await;
        tokio::time::sleep(delay).await;
        attempt += 1;
    }
}
crates/llm/src/anthropic.rs — execute

The boundary that is drawn here rather than in the policy: once the response is a success, nothing is retried. A mid-stream error frame, a truncated tool argument, a body that will not parse, all of them return out of that return match mode and never see delay_for. Past that point bytes may already have reached the terminal, and a retry would replay text the user has read. a_mid_stream_error_frame_ends_the_turn asserts the stub saw exactly one request. tested

The same body is re-sent, byte for byte, on every attempt. That matters for caching: the second attempt has the same prefix as the first and may read an entry the first wrote, so a retried call is not a cache miss. unverified Nothing has measured that on a real 429; settling it means one retried live call with both usage rows kept.

crates/llm/src/anthropic.rs · notify

async fn notify(events: Option<&mpsc::Sender<Event>>, event: Event) {
    if let Some(tx) = events {
        // Best effort: a closed receiver means the turn is being cancelled,
        // which the caller already knows about.
        let _ = tx.send(event).await;
    }
}
crates/llm/src/anthropic.rs — notify

Every event Emma emits goes through it, so a caller that passed None costs one branch and a caller whose receiver has hung up costs one ignored error rather than a failed turn. The channel in the provider tests holds 256 events, which is more than any fixture produces.

Making every attempt visible

a_429_is_retried_after_the_delay_the_api_asked_for_and_is_visible is the test that carries the third rule. It queues three replies, a 429 with retry-after: 0, a 529, then a success, and asserts four things: the turn succeeded, the stub saw three requests, exactly two Retrying events arrived with the message a silent retry is a hang, and the first of those had a delay of exactly zero, so the provider's header was used rather than the curve. The second is asserted only as greater than zero (the curve). tested
