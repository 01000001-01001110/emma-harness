Consent & permissions

Emma writes files and runs commands. A tool surface that is read-only by construction bounds the worst a rogue turn can do to reading something the user was already entitled to read, and needs no gate to achieve that. Emma inverts that property, and this machinery stands in its place.

crates/emma/src/approval.rs — module doc
What the gate does not enforce

It is a consent interface, not a sandbox. It asks a tool two questions: can you damage this machine, do you send bytes off it. It believes both answers. Nothing here stops a tool from opening a socket or writing a file after declaring it would not. Bash declares read_only: false and reaches_network: false, and can do anything a shell can do, including curl. What the gate produces is that a human saw the command before it ran.

There is no unconditional deny anywhere in Emma. A permission rule can permit any command; --dangerously-skip-permissions turns prompting off wholesale. rm -rf / is a prompt like any other, and answering y runs it. See EXEMPT and the floor.

Other harnesses do enforce: codex-rs sandboxes with Seatbelt on macOS, Landlock on Linux and restricted tokens on Windows. Emma has no equivalent, and everything in this chapter describes what is checked and in what order, not what is prevented.

The shape of it

One call reaches the gate at a time. Before it does, the loop has already run any PreToolUse hooks and returned if one refused. What is left is two questions asked in sequence by one function: may bytes leave this machine for this host, and may this call change anything locally. Each has its own rules, its own session grant and its own prompt, and passing one is not passing the other.

Underneath that sit three sources of standing answers. A permission rule read from up to three JSON files. A grant a human gave earlier in this process. A flag on the command line. The order they are consulted in determines which answer wins.

Three sentences carry over every page below. The gate believes what a tool declares about itself. Bash can do anything. Nothing anywhere is an unconditional deny.

The pages

  1. The two axes a tool declares read_only and reaches_network, why one bit became two, and the NetworkTarget a tool answers with when the gate asks where a call is going. Also what a declaration is worth, which is nothing the gate can check.
  2. The precedence ladder, in full Approvals::decide quoted entire, the nine rungs it produces, the three gates, and the two placements pinned by tests written in the direction of their inversion. Includes what emma --help actually prints, which omits a rung.
  3. The egress question Approvals::egress quoted entire: the fail-closed branch for a tool that names no host, the per-host session grant, and why the two grant sets are two HashSets rather than one.
  4. The five answers, and which two write to disk y, n, a, r, t: what each grants and for how long, why an empty line is n, why a key that was not offered does not work, and what the prompt shows for each writing tool.
  5. EXEMPT, and the floor that is not there Two tool names skip the local question, keyed by name and not by any property. Then the opposite shape, an unconditional deny list, which three other projects have built and Emma has not.
  6. Permission rules, scopes and merging Tool and Tool(specifier), the three Spec variants including the one that never matches, deny before ask before allow, the three files rules are read from, and why the user scope gives up two of its three lists.
  7. Matching a host, label by label The length check and the strict-subdomain check that stop a rule matching a host an attacker can register, the tiny glob inside one label, and the two spellings that parse, are kept, and can never meet a real host.
  8. Hooks: three events, three failure rulings Containment, the six-name environment, the anchored matcher, what a hook may answer in either vocabulary, and the 2026-08-14 ruling that a hook may daemonize, with the pipe defect that ruling exposed.

What is not settled, across the chapter

  • Four guarantees were re-broken and the rest rest on their tests' own recorded mutations. What was run at commit 20ac400 by an earlier author, each reverted afterwards: neutering the deny-rule check in decide and egress; moving the Gate::Unattended denial above the allow/read_only/EXEMPT/grant block; flipping Spec::Unsupported => false to true; and relaxing the host label-count check from == to >=. The named tests and what went red are on the pages above. unverified None of it was repeated for this chapter, which does not change source. What would settle it: the same treatment on a branch for each other named test. certified The suite the mutations were run against still passes: cargo test -p emma --lib at commit a3eba74 reports 477 passed, 0 failed, 3 ignored, of which 31 are in approval:: and 25 in permissions::.
  • An allow rule under -p has no test, and the mode it produces is documented nowhere but this chapter.
  • Nothing here was observed from a real terminal. The prompts, the boot warnings and the notices are described from the source and from unit tests against a recording Term. A fully-tested drawing defect has shipped from this repository twice.
  • Which gate a run is in is decided above the tested seam. The Gate and Asker pair is chosen in main.rs, which the scripted-provider tests do not reach. notes/archive/map-architecture.md records that stretch as untested policy.
  • The floor is unbuilt and its source is about 96% unread. Above.
  • The unix half of the hook lifetime is compile-checked only. Above.
