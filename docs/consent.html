Consent & permissions

Emma writes files and runs commands. A tool surface that is read-only by construction bounds the worst a rogue turn can do to reading something you were already entitled to read, and needs no gate to achieve that. I inverted that property, and this machinery stands in its place.

crates/emma/src/approval.rs — module doc
What the gate does not enforce

It is a consent interface. It does not sandbox. It asks a tool two questions: can you damage this machine, do you send bytes off it. It believes both answers. Nothing here stops a tool from opening a socket or writing a file after declaring it would not. Bash declares read_only: false and reaches_network: false, and can do anything a shell can do, including curl. What the gate produces is that you saw the command before it ran.

There is no unconditional deny anywhere in Emma. A permission rule can permit any command; --dangerously-skip-permissions turns prompting off wholesale. rm -rf / is a prompt like any other, and answering y runs it. See EXEMPT and the floor.

Plan mode is a posture and not a sandbox either. Since 2026-09-06 a session has a Mode, set with /mode, and Mode::Plan is the third rung of the ladder: a call whose ToolMeta says it would write or would leave the machine is refused outright rather than turned into a question. It reads the same two declarations rules 2 and 3 already trust, for a different purpose, so a tool that lies about read_only defeats plan mode exactly as thoroughly as it defeats the prompt and no more. Anyone who needs the write to be impossible needs a sandbox, and this is not one. tested plan_denies_a_writer_and_names_the_mode goes red when Mode::refuse returns None, and again when the rung slides below the egress question; a_deny_rule_answers_before_the_mode_does goes red when it slides above the deny rule. Both were run in both directions. unverified Nothing here has watched plan mode stop a real write from a real model. Settling it: a scripted-provider goal in plan mode whose session log carries a denied record with "by": "mode", which no test in crates/emma/tests/loop.rs writes yet.

Other harnesses do enforce: codex-rs sandboxes with Seatbelt on macOS, Landlock on Linux and restricted tokens on Windows. I have not built an equivalent, and everything in this chapter describes what is checked and in what order, not what is prevented.

The shape of it

One call reaches the gate at a time. Before it does, the loop has already run any PreToolUse hooks and returned if one refused. What is left is two questions asked in sequence by one function: may bytes leave this machine for this host, and may this call change anything locally. Each has its own rules, its own session grant and its own prompt, and passing one is not passing the other.

Underneath that sit three sources of standing answers. A permission rule read from up to three JSON files. A grant a human gave earlier in this process. A flag on the command line. The order they are consulted in determines which answer wins.

Every page below repeats the same warnings. The gate believes what a tool declares about itself. Bash can do anything, and nothing in Emma is an unconditional deny.

The lesson in the chip itself. A quoted function is a snapshot, and it rots without any signal. I learned that the hard way: the page keeps a confident src line pointing at a file that has moved underneath it. Twelve of the twenty-five findings in the audit that prompted this were exactly that. Pages whose subject is the code still quote whole functions, and the cost is now written down where it can be weighed.

What is not settled, across the chapter

  • Four guarantees were re-broken and the rest rest on their tests' own recorded mutations. What was run at commit 20ac400 by an earlier author, each reverted afterwards: neutering the deny-rule check in decide and egress; moving the Gate::Unattended denial above the allow/read_only/EXEMPT/grant block; flipping Spec::Unsupported => false to true; and relaxing the host label-count check from == to >=. The named tests and what went red are on the pages above. unverified No mutation was repeated in this settlement because its scope forbids changing Rust files. What would settle it: on a disposable branch, apply one documented production mutation at a time, run only the named backing test and paste the red result, restore the Rust source, rerun the same test green, and only then move to the next chip. A passing suite without the red half does not settle a tested claim. certified The suite the mutations were run against still passes: cargo test -p emma --lib at commit a3eba74 reports 477 passed, 0 failed, 3 ignored, of which 31 are in approval:: and 25 in permissions::.
  • An allow rule under -p has no test, and the mode it produces is documented nowhere but this chapter.
  • Nothing here was observed from a real terminal. The prompts, the boot warnings and the notices are described from the source and from unit tests against a recording Term. A fully-tested drawing defect has shipped from this repository twice.
  • Which gate a run is in is decided above the tested seam. The Gate and Asker pair is chosen in main.rs, which the scripted-provider tests do not reach. The architecture map records that stretch as untested policy.
  • The floor is unbuilt and its source is about 96% unread. Above.
  • The unix half of the hook lifetime is compile-checked only. Above.
