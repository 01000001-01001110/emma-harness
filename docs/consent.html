Consent & permissions

Emma writes files and runs commands. A tool surface that is read-only by construction bounds the worst a rogue turn can do to reading something the user was already entitled to read, and needs no gate to achieve that. Emma inverts that property, and this machinery stands in its place.

crates/emma/src/approval.rs — module doc
What the gate does not enforce

It is a consent interface, not a sandbox. It asks a tool two questions: can you damage this machine, do you send bytes off it. It believes both answers. Nothing here stops a tool from opening a socket or writing a file after declaring it would not. Bash declares read_only: false and reaches_network: false, and can do anything a shell can do, including curl. What the gate produces is that a human saw the command before it ran.

There is no unconditional deny anywhere in Emma. A permission rule can permit any command; --dangerously-skip-permissions turns prompting off wholesale. rm -rf / is a prompt like any other, and answering y runs it. See the floor that is not there.

Other harnesses do enforce: codex-rs sandboxes with Seatbelt on macOS, Landlock on Linux and restricted tokens on Windows. Emma has no equivalent, and everything below describes what is checked and in what order, not what is prevented.

crates/tool-api/src/lib.rs — ToolMeta · notes/improvements.md item 9

The two axes a tool declares

ToolMeta carries two bits the gate reads before a tool runs. read_only asks whether the call can change local state: a file written, a process spawned. reaches_network asks whether it sends bytes off the machine. They are separate because they are separate risks: writing is something the model chooses, and egress is how a prompt-injected page turns a read tool into an exfiltration channel. A model that reads an attacker's page and then "searches" for the contents of a .env has written nothing and passes every local-damage check on the way out.

crates/tool-api/src/lib.rs — ToolMeta::read_only, ToolMeta::reaches_network

WebFetch and WebSearch declare read_only: true, since neither can damage anything on this machine, and both are how bytes leave it. Flipping them to read_only: false was the obvious alternative and was refused: a gate that fires on every page read teaches the operator to answer without reading, and the habit carries into the Write prompt. The second axis costs one prompt per host instead of one per page.

crates/tool-api/src/lib.rs — ToolMeta::read_only

ToolMeta has no Default, so adding a field breaks every construction site in the workspace and each tool must state the new bit. The predecessor added a defaulted field, which granted a safety property to every tool written afterwards without anyone choosing it.

crates/tool-api/src/lib.rs — ToolMeta

The gate does not parse a tool's arguments

To learn where a call is going, the gate calls Tool::network_target(args) and the tool answers with a NetworkTarget: a host, lowercased and stripped of a trailing dot, plus one line naming the errand for the human. The gate knows that some tools reach some host and knows nothing about how any of them spell it. Twice before, this loop acquired knowledge of one tool's argument shape, and both times "adding a tool is a crate plus one registry line" stopped being true. What each tool declares, and what it puts in detail, is on Tools.

crates/tool-api/src/lib.rs — Tool::network_target, NetworkTarget

A tool that declares reaches_network: true and returns None is denied. The gate cannot grant a destination nobody named, and the other reading, "no target, so nothing to gate", gives silent network access to whichever tool forgets to implement the method. The denial text tells the model this is a defect in that tool rather than something to work around. tested

crates/emma/src/approval.rs — Approvals::egress; tests::a_tool_that_declares_egress_and_names_no_host_is_denied

Per-host grants

An answer at the network prompt grants one host, for this process, not one call, and not one tool. The first fetch to docs.rs asks; every later fetch to docs.rs in this process does not; a fetch elsewhere asks again. A host approved while running WebSearch is approved for WebFetch as well, because the thing the human approved was a host. Tool grants and host grants are two HashSets rather than one: keying both on one set would mean approving WebFetch once approved every host it is later pointed at. tested

crates/emma/src/approval.rs — Approvals::hosts_allowed; tests::the_first_call_to_a_host_asks_and_later_ones_do_not, tests::a_grant_is_the_host_and_not_the_tool

The egress question covers where bytes go and nothing else. It says nothing about what comes back: an approved host is a destination the user chose, not a source they trust, and the page that arrives is attacker-controlled text entering the model's context. It does not cover a tool that reaches the network incidentally: Bash can curl and declares reaches_network: false. Bash is gated by the local question instead, which shows a human the command itself, and a command is more information than a host name. Declaring true would demand a destination it cannot name without parsing shell.

The precedence order

Read top to bottom; the first line that answers is the answer, and nothing below it is consulted. Two placements are pinned by tests written in the direction of their inversion, and both are called out under the diagram.

A deny rule outranks the bypass

The deny check is the first statement in decide and returns before if self.gate == Gate::SkipAll is evaluated; egress has the same two statements in the same order for the network question. --dangerously-skip-permissions used to be the first thing decide read and is now the third. The argument for moving it: a deny rule is something the operator wrote down and can go and read, and the bypass is a flag typed to get a script through. Claude Code makes the same ruling: if a tool is denied at any level, no other level can allow it. tested

crates/emma/src/approval.rs — Approvals::decide, Approvals::egress; tests::a_deny_rule_beats_the_bypass_flag

That test asserts both axes and also asserts the other half: the bypass still waves through everything nobody wrote a rule about. Without the second half the guarantee would be indistinguishable from the flag having stopped working.

An allow rule answers before the unattended denial

The block that consults the allow rule, read_only, EXEMPT and the session grant sits above if self.gate == Gate::Unattended. A -p run carrying "allow": ["Bash"] therefore runs Bash unprompted without the bypass flag, while every tool the file does not name still comes back with the "there is nobody to ask" denial.

crates/emma/src/approval.rs — Approvals::decide

So a narrower-than-bypass unattended mode already exists, and nothing announces it. It is tool-wide only: the narrowing somebody would reach for, Bash(git log:*), parses into Spec::Unsupported, matches nothing in any list, and is announced at boot as a rule that does nothing. The choice available to a script today is the whole tool unprompted, or nothing. unverified The block's position above the denial is mutation-proven: moving the Gate::Unattended return above it turns three tests red. All three exercise read_only or EXEMPT, and the allow-rule arm has no test at any gate but Gate::Ask. What would settle it: a test building Approvals with Gate::Unattended, an empty answer queue and an allow rule for a writing tool, asserting Allow.

Where rung 1 lives

The hook denial is not enforced in approval.rs. The loop runs PreToolUse, and on a denial it writes the record and returns before Approvals::request is reached, so no code in the gate can undo it, and no test in the gate can exercise it either. A source-order assertion was written inside approval.rs first and then removed: it passed against a mutation that disabled the denial outright. The guarantee is held behaviourally instead, in the integration tests. tested

What the prompt shows

A prompt the reader cannot evaluate manufactures consent and leaves a record saying they agreed. Bash shows the command, Write and Edit show a diff computed against the file on disk, Delegate shows the agent type and the first twelve lines of the brief, and the network question shows the host on one line and the errand, the URL, the query, on the next. Anything without an arm falls back to pretty JSON. tested

crates/emma/src/approval.rs — preview, network_preview, BRIEF_LINES

The Write arm used to print a path and a byte count and withhold the change. It now carries the diff, and every case that cannot be diffed (a binary file, one too large to read, a changed region too large to line up) becomes a sentence saying so rather than a rendering that looks like a diff and is not. The renderer is on the terminal.

EXEMPT: the hole, by name

// Writers that do not prompt, and the whole argument for each one.
const EXEMPT: &[&str] = &["TaskCreate", "TaskUpdate"];
crates/emma/src/approval.rs — EXEMPT

Two tools skip the local question. They declare what they are: the task tools rewrite .emma/tasks/tasks.md and were not declared read_only: true to dodge the gate, since a tool that misreports itself leaves the gate protecting nothing in general rather than only for that tool. The write is confined to the tool's own bookkeeping file, and it is the write a model performs several times per goal: "TaskUpdate wants to tick a checkbox, allow?" fifteen times in one goal is the prompt that teaches somebody to hold down y, including through the Bash call that follows it.

A bypass keyed by name, not by property

EXEMPT is a const &[&str] compared against tool.name(). Nothing about a listed tool is checked. A name added to that array stops prompting, whatever it writes. The test is written about what is not on the list: it asserts Bash, Write and Edit are absent and still gated, which is what would catch a later edit adding a tool that writes the user's source tree. tested

The comment on the list says the missing piece is an axis on ToolMeta for the scope of a write rather than its existence, and that when that lands the list is to be deleted, since tools would classify themselves. It has not landed. ToolMeta has since gained a second axis and it is a different one: reaches_network splits egress out of read_only and does nothing for these two tools. There is no backlog item for a write-scope axis either; it exists only as this comment.

crates/emma/src/approval.rs — EXEMPT, tests::the_exemption_covers_the_task_writers_and_nothing_that_touches_the_tree; notes/improvements.md (no item)

Two things bound it. A PreToolUse hook denial is resolved before approvals are consulted, so an operator can block these by name; and an ask rule reaches them, because rung 4 sits above rung 6. Every call, exempt or not, is written to the session log. tested

The floor that is not there

EXEMPT is an always-allow hole. The opposite shape, a small, hardcoded, non-overridable deny list that no rule, no flag and no remembered grant can relax, does not exist in Emma. It is notes/improvements.md item 14, and it is open.

Three unrelated projects have arrived at that shape. Zed's tool_permissions has three regex tiers plus built-in protections its documentation illustrates with rm -rf /, which no rule can override. avala-ai/agent-code blocks .git/ and node_modules/ unconditionally. And c4pt0r/pie, read at commit b725796 (MIT, plain, no rider, read from the repo-root LICENSE, so it can be copied with attribution), has it written in Rust already, in a 491-line module including tests: an unconditional-deny corpus where each entry carries a label naming what it protects and that label is carried into the denial reason; token-aware predicates for rm that survive flag permutations and one layer of quote stripping; clause splitting on ;, &&, || and |; and roughly forty dangerous-command cases beside a false-positive suite.

notes/improvements.md item 14 · notes/survey-pie.md §1.1 · notes/survey-harnesses-2.md §4
The counter-argument, recorded because it may win

An unconditional refusal that fires on a legitimate command is an outage, not a safety property. A rule that fires on correct configuration, which this codebase rejects elsewhere by name. If the floor is built, the list has to be short and every entry has to name what it protects.

That becomes a condition on copying: take pie's predicates and its corpus, not its regexes. Pie's are substring matches that accept false positives: \bsudo\b fires on echo "sudo", and reboot fires inside any quoted string containing the word. Pie's own module doc states the trade as "the permission layer must close, not minimize". That trade is the failure the counter-argument predicts.

One further idea from pie transfers even though its mechanism does not: it treats writes to the harness's own configuration as their own permission category. Emma has the same hazard in file form: a Write to .claude/hooks/, settings.local.json, agents/ or skills/ is a persistent behaviour change that classifies today as an ordinary file write, and it is the one edit that can disable the check that would have caught it.

notes/survey-pie.md §5

Permission rules

The format is Claude Code's, so an existing .claude/settings.json works here and a rule Emma writes is a rule the other program understands. The block is permissions: { allow: [], deny: [], ask: [] } and a rule is Tool or Tool(specifier). Emma's own .emma/config.json spine accepts the same block under the same names, and a block that had to be re-typed to move between the two directories would defeat the reason it is read at all.

crates/emma/src/permissions.rs — module doc; crates/harness/src/lib.rs — Spine::permissions, PermissionBlock

Persistent rules were once refused outright. approval.rs carried a section arguing there must be no persistent always-allow, because "a permission the user cannot see is a permission they have forgotten they granted, and the place they would not see it is a config file written six weeks ago". That was reversed against one goal, search the web for AI news, which cost five prompts and re-asked all five on the next run. What replaced it keeps the visibility the argument was actually about: a rule is written only when the user picks the answer that says so, it is shown before it is written, it lands in a JSON file that can be read, diffed and deleted, and emma config check lists every rule with the file it came from.

Taking only deny from the user scope diverges from Claude Code, where user settings carry all three lists and all three apply in every project. ~/.claude/settings.json is another program's global configuration, and a grant in it was made for that program, in a session Emma was not part of, possibly years ago. The owner's own file carries Bash(rm:*), Bash(bash:*) and Bash(powershell.exe:*) in its allow list, plus "defaultMode": "dontAsk"; honouring user-scope allow would have given Emma an unprompted shell in every repository on that machine on the first run after the feature shipped. A remembered grant lands in settings.local.json beside whichever harness the project loaded, not always .claude/, and never ~. crates/emma/src/permissions.rs — file_for

The write merges rather than replaces: the file is read, parsed as a whole document, and written back with every key it had: hooks, statusLine, env, anything else. A file that does not parse as JSON, or is not an object, or whose permissions or permissions.allow are the wrong shape, is not written to at all; the user is told which file and what is wrong with it, and the grant lasts the session instead. This project has been bitten once by a write path that replaced a shared configuration document and deleted another program's key. The write goes to a sibling temporary file and is renamed over the target, so an interrupted run cannot leave half a settings file behind. tested

Precedence inside the rule set

deny, then ask, then allow: the first list with a match wins, and rule specificity does not change that. A narrow allow does not carve an exception out of a broad deny; a broad allow still covers every host a narrow deny does not name. This is the clause people get wrong. If it inverted, every deny list in every settings file would become a default rather than a refusal. tested

crates/emma/src/permissions.rs — Rules::decide; tests::deny_beats_allow_however_specific_the_allow_is, tests::ask_sits_between_them_and_beats_allow

An ask rule outranks an allow rule, a read_only declaration, the EXEMPT list and a session grant, so "I allow this tool generally, and I want to be asked about it today" is expressible and cannot be undone by a y typed an hour ago. Nothing is offered at a prompt an ask rule forced: the allow that r would write is outranked by that same rule, so the keystroke would write a grant that does nothing. tested

The matcher was not changed

Converting the pattern instead of warning about it was the obvious fix and was rejected on three grounds. It moves the security surface: matching goes from comparing ASCII labels to running UTS-46 over attacker-influencable strings on both sides of every match, and a conversion bug can widen a match where a warning cannot. Wildcards are not valid IDNA input, so *.example.com would need a label-skipping policy nobody has asked for. And the rule stays live for a caller that hands the matcher a Unicode host directly, which the test matrix pins. idna is used at boot, in the warning path only. The matcher is unchanged byte for byte. tested

One premise of the plan that built this turned out false: idna returns Ok for a wrong answer: b*cherü.example converts to xn--b*cher-8ya.example, the wildcard swallowed into punycode with no error. "If idna refuses a label, omit the suggestion" caught nothing, and the shipped code checks each label itself.

Hooks

A hook is an operator-authored program the runtime runs at one of three dispatch sites. Running a program at the highest-privilege point of the turn means canonicalising and containment-checking the path, refusing a non-executable file, clearing the environment down to a six-name allowlist, hashing the executable, anchoring the matcher, bounding the wall clock, capping both pipes and deciding what a malformed answer means. That makes it a subprocess supervisor rather than configuration, which is why it is a file of its own.

crates/harness/src/hooks.rs — module doc

Hooks may daemonize

Ruled by the owner on 2026-08-14, reversing the first draft of the plan that was written to stop it: a hook that starts something meant to outlive it is a supported use, not a leak. notes/plan-process-lifetime.md §1, §7

The defect was never that a grandchild lives. It was that exec read stdout to end-of-file and then waited, so a hook that started a background process and exited 0 in milliseconds was reported as timed out after 5000ms with its output discarded, not because anything was slow, but because the process it started inherited the write end of the pipe and EOF never came. Reproduced as a rate: 20 of 20 invocations misreported before the fix, 0 of 20 after, with the daemon surviving 20 of 20 in both. observed: the before/after comparison ran once, 2026-08-14, logged in notes/plan-process-lifetime.md §6 — the "before" state needs the reverted code to reproduce. The "after" half is on demand: cargo test -p emma-harness --test exec_lifetime certify_the_misreport_rate_over_twenty_trials -- --ignored tested

notes/plan-process-lifetime.md header, §6; crates/harness/src/hooks.rs — exec

A budget rather than an event, because once a write end may outlive the child there is no observable event meaning "the hook's own output is complete". End-of-file arrives when the last writer closes, which may be days later, and a pipe cannot say which writer a byte came from. What is knowable is that everything the hook itself wrote completed into the pipe buffer before exit could run, so a grace long enough to drain a local buffer captures all of it. A daemon's bytes that land inside the grace ride along; that is bounded by the 64 KiB pipe cap and cannot be separated out without attribution the pipe does not offer.

Windows is what makes abandoning the pipe safe: there is no SIGPIPE. A write into a broken pipe returns ERROR_BROKEN_PIPE, an error code the writer may ignore. A staged grandchild that keeps writing to the inherited stdout after Emma walks away is still alive seconds later. tokio also gives a child's stdio overlapped I/O on Windows, so an unfinished read is a cancelled future rather than a thread stuck in a blocking ReadFile. tested

crates/harness/tests/exec_lifetime.rs; notes/plan-process-lifetime.md §2, §6
The unix edge

On unix, closing the read end means a daemon that later writes to that stdout gets SIGPIPE and, by default, dies. Two things bound it: this is not new, since the timeout path already dropped the pipe, and a long-lived reader was never on offer; and the daemon idiom exists because inherited stdio is borrowed. A hook that starts a daemon should redirect its stdio to /dev/null (or NUL) first. The alternative, Emma keeping a reader alive for as long as somebody else's daemon lives, is an unbounded obligation and is refused.

unverified The unix arm is compile-checked only. On Windows nothing pins the 200 ms grace either, because nothing makes its removal observable: deleting it leaves every fixture green, including a 100-trial probe of a hook whose last write and exit are the same instant: 0 of 100 lost either way. What would settle both: a Linux or WSL run of the same fixtures, where the readiness-based path means the bytes wait in the kernel for a poll the randomised select! may not reach before the wait wins, and where a write-looping daemon is expected to die on its first post-abandonment write unless it ignores SIGPIPE.

crates/harness/src/hooks.rs — EXEC_DRAIN_GRACE_MS; notes/plan-process-lifetime.md §2, §6

The lifetime rule, once: Emma supervises the direct child it spawned (its budget, its pipes, its exit code) and claims nothing about that child's descendants. On the timeout path kill_on_drop kills the hook and only the hook. Whatever the hook started is left, because Emma cannot tell a broken hook's orphans from the daemon the operator meant to start. The cost is stated as a cost: a hung hook's descendants are unreclaimable, nothing short of reaping bounds that, and the only available mitigation is a clause in the transcript telling the operator to look. That is a report, not a bound.
