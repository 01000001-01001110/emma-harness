Emma, the harness

Part of learning track is Rust, and since claude code is closed source, maybe we need a new harness. The goal of Emma is to be a codeing assistant harness. Right now, Emma is a coding assistant for one person on one machine, model-agnostic and written in Rust: with a goal-holding loop, its tools, a consent gate, and a terminal. It runs against any provider you point it at (a paid API or a model on your own machine), and every part of it is yours to extend. All of it in one binary you have complete control over.

What it is for

A harness decides what the model sees before you type anything, what it can reach for, and what you look at while it works. In most harnesses those decisions are made once, elsewhere, for everyone. Emma is the case where they are yours. Five things follow.

Spend less context on the harness

Claude Code is widely reported to send on the order of 30,000 tokens before the first user word. unverified: no request body from CC was measured here, and the figure is repeated from elsewhere rather than counted. Regardless, every token of that is one you paid for and cannot use for the actual work, and it is paid again on every uncached call.

Half of Emma's prompt is now counted, and the other half is the hard half

tested The tools array Emma sends is 29,505 bytes over 16 tools, measured on 2026-09-05 by crates/emma/tests/prompt_size.rs, which builds the registry the way main builds it and sums the wire definitions. That is a floor: it excludes the browser, WebSearch and Skill, none of which register without a Chrome, a Brave key or a harness.

This went uncounted for months on a stated reason that was mostly wrong. The claim was that settling it needed the /v1/messages/count_tokens endpoint with a real key, and a captured Claude Code request to compare against. Neither is needed for the byte count — the registry assembles with no network and no credential — and the difficulty of the comparison was doing the work of an excuse for the part that was easy. The endpoint had already been used against this project on 2026-08-11, on the Edit page.

unverified: bytes are not tokens, and the system field is not in this figure because it depends on which persona and which done-check a run selects. Submit the exact first-request body to count_tokens and record the returned input_tokens. The comparison with Claude Code is a separate piece of work and needs its request captured off the wire.

One related figure in the source is easy to misread. A bare Hello once cost 22,083 tokens, and that was behaviour rather than prompt size: Emma used to prepend "Work toward this goal. You have tools; use them" to every input, so a greeting sent the model to run pwd && ls -la and read the task file before answering. Moving that text into the standing contract fixed it. The rule it left behind: a preamble applied to every input is an instruction the user did not write and cannot see.

The browser is in the binary

Not an MCP server to install, configure and keep running beside it. WebFetch renders in real Chrome, and five tools drive a live page: open, read, act, fill, close. A harness that can only fetch HTML is guessing at anything rendered client-side. See Tools.

Any model, any provider

Emma has no provider compiled into its loop. A Provider is a trait with two required methods, and the loop builds its requests from Emma's own shapes rather than from any vendor's wire format, so a second provider is an implementation of that trait, not a fork of the agent.

Two exist. Anthropic over the Messages API, and Ollama against a model on your own machine, which needs no key and sends nothing off the box. certified: a goal run end to end on gemma4:12b over loopback read a file through the Read tool and answered in two calls at no cost, and the same binary pointed at another machine's Ollama named that destination before the first call. Anything speaking the OpenAI API, OpenRouter included, is not wired up yet.

The boundary is where the work went. Ollama does not speak the Messages API: a tool definition nests under function instead of carrying input_schema, a call arrives already decoded, and a result goes back as its own message rather than as a block inside a user turn. Adding Ollama changed three places in the trait, recorded in the provider boundary.

Rust, and what that buys a program a model drives

A model proposes edits faster than a person can review them, so the question is what catches a wrong one. Rust answers a large class of them at compile time: an added enum variant breaks every match that did not consider it, a moved value cannot be read afterwards, and an ignored Result is a warning rather than a silent branch. Each is a mistake an agent makes and a test suite might not.

The type system is also somewhere to put a rule so that breaking it stops the build. ApiKey has no Display and a Debug that prints nothing, so a key cannot reach a log through a {:?} three layers up; reading it takes expose(), which is a word a reviewer notices.

One binary follows from it too: no runtime to install, no interpreter version to match, and the same artefact on Windows, macOS and Linux.

Nothing hosted, nothing you cannot change

Every decision lives in the library rather than main.rs, so a scripted provider can drive the whole loop with no network, which is also what makes the deciding parts testable. There is no service to depend on, no account to keep, and no release to wait for.

The interface follows the project

Colours are named by role and loaded from JSON themes; the sidebar's tools launch real programs on your machine; the layout is changeable because it is ours. See The terminal.

What it reports

A tool that truncates names the limit that cut it, how much was lost, and how to get the rest, or says that no argument raises it. A tool that cannot compute something says so instead of returning a plausible substitute. A tool that fails returns a result the model reads and acts on, and the loop does not abort.

The approval gate is a consent interface rather than a sandbox. It enforces nothing a tool does not declare about itself, and Bash can do anything. The consent page says where that ends, in more detail than most readers will expect.

A subagent returns prose. Underneath it, the harness appends a footer built from the calls it recorded, not from the subagent's account, so the two can be compared. There is a test where a scripted subagent claims in fluent prose to have read two files and run the test suite while calling no tool at all.

The marks on these pages

certified proven, and a reader can repeat it: a file, a command, a count
observed seen once, live, not repeatable on demand
tested covered by a test shown to fail when the guarantee is removed
unverified believed, not checked, with what would settle it

Claims about behaviour name the file they came from, so they can be checked against the code rather than taken on trust.

Why the record is this detailed

Emma is built mostly by agents, in sessions. Context carries inside a session and the rules carry across them, but the person holding the reasoning changes constantly, so anything kept only in someone's head is gone by the next one.

The alternative to writing down what was measured and what was assumed is re-deriving it, and there are receipts for what that costs here: a strict wire decoder that passed 712 tests and then decoded no real tool call on its first live request; an editing technique adopted from a write-up that turned out to describe the reverse of what it did; a test-count command that reported green over a red test. The conventions on Records & house rules come from those.
