One function decides every local call, and the order of its statements is the whole of the policy. It is quoted here entire, because a summary of it loses the property: which line runs first is the only thing that says whether a deny rule survives a bypass flag.

crates/emma/src/approval.rs — Approvals::decide

The function

async fn decide(
    &self,
    name: &str,
    meta: ToolMeta,
    target: Option<NetworkTarget>,
    args: &Value,
    term: &Term,
) -> Verdict {
    // Only bare `Tool` rules answer this question; a `Tool(domain:…)` grant
    // is about a destination, and reading it as permission to run the tool
    // would let a narrow grant answer a question nobody asked it.
    let rule = self.rules.lock().await.for_tool(name);

    // A `deny` rule first, above the bypass. See the precedence block at the
    // top of the file: written policy outranks a flag somebody typed.
    if rule == Some(Decision::Deny) {
        return Verdict::Deny(format!(
            "A `deny` permission rule forbids {name}. It was not run, and no answer at a \
             prompt can change that — it is written down in a settings file. Do not retry \
             it; tell the user which rule is in the way if they need to know."
        ));
    }
    // Egress before the local question, and independent of it: a tool can
    // be read-only — genuinely, honestly read-only — and still be the way
    // something leaves this machine. Every arm below this line assumes the
    // network question has already been answered.
    if let deny @ Verdict::Deny(_) = self.egress(name, meta, target, term).await {
        return deny;
    }
    if self.gate == Gate::SkipAll {
        return Verdict::Allow;
    }
    // An `ask` rule puts the question back, over an `allow` rule, over
    // `read_only`, over the exemption and over a session grant. That is the
    // whole value of having a third list: "allowed in general, ask me today"
    // has to be expressible, and it cannot be undone by a `y` typed an hour
    // ago or it is not a rule, it is a preference.
    let forced = rule == Some(Decision::Ask);
    if !forced {
        if rule == Some(Decision::Allow) {
            return Verdict::Allow;
        }
        if meta.read_only {
            return Verdict::Allow;
        }
        // The named hole. See `EXEMPT`.
        if EXEMPT.contains(&name) {
            return Verdict::Allow;
        }
        if self.session_allowed.lock().await.contains(name) {
            return Verdict::Allow;
        }
    }
    if self.gate == Gate::Unattended {
        return Verdict::Deny(format!(
            "{name} needs approval and this is a non-interactive run (-p), so there is \
             nobody to ask. It was not run. Use a read-only tool, or tell the user what \
             needs approving and stop."
        ));
    }

    // On this question the narrow rule and the tool-wide one are the same
    // grant, so there is one remember key rather than two that do the same
    // thing. And nothing is offered when an `ask` rule forced the prompt: the
    // `allow` it would write is outranked by that very rule, so the keystroke
    // would write a grant that does nothing.
    let offers = match (forced, &self.file) {
        (false, Some(_)) => Offers {
            narrow: Some(Rule::every_call(name)),
            wide: None,
        },
        _ => Offers::default(),
    };

    term.prompt_header(name, &preview(name, args));
    // `ask` loops on unreadable input; by the time it answers, the answer is
    // one of the offered ones.
    match self.ask(name, term, Question::Tool, &offers).await {
        Some(Answer::Yes) => Verdict::Allow,
        Some(Answer::AlwaysThisTool) => {
            self.session_allowed.lock().await.insert(name.to_string());
            term.note(&format!(
                "{name} is approved for the rest of this session (this process only)"
            ));
            Verdict::Allow
        }
        Some(Answer::RememberNarrow | Answer::RememberWide) => {
            // Both keys mean the same rule here, and the fallback covers the
            // scripted asker, which can hand back an answer the terminal
            // would not have offered.
            let rule = offers
                .narrow
                .clone()
                .unwrap_or_else(|| Rule::every_call(name));
            self.keep(rule, term).await;
            Verdict::Allow
        }
        Some(Answer::No) => Verdict::Deny(format!(
            "The user declined this {name} call. It was not run. Do not retry it \
             unchanged — take a different approach, or ask what they would prefer."
        )),
        // End of input, or a scripted run that ran out of answers. Silence
        // is not consent.
        None => Verdict::Deny(format!(
            "No approval was given for this {name} call, so it was not run."
        )),
    }
}

The order it produces

Read top to bottom. The first line that answers is the answer, and nothing below it is consulted. Rung 1 is not in this file; the loop resolves it and returns before request is reached.

Three gates, and no fourth

Gate is a closed enum with three members, chosen in main.rs and never afterwards.

GateSet byEffect
Ask the default, reachable with no flag rungs 1 to 7 answer, or the human does
SkipAll --dangerously-skip-permissions, or --yes alongside -p rung 3 allows everything rungs 1 and 2 did not refuse
Unattended -p with no bypass rung 8 denies anything rungs 1 to 7 did not settle, with a sentence the model reads
crates/emma/src/approval.rs — Gate; crates/emma/src/cli.rs — Opts::skip_permissions

The doc on Gate::Unattended states the two alternatives it was chosen over. Proceeding silently would make -p the way to get unattended writes without saying so. Prompting anyway would hang on a question nobody can see, which in a CI job is a timeout an hour later with no output explaining it.

crates/emma/src/approval.rs — Gate::Unattended

The bypass cannot be set from configuration or the environment. The short --yes spelling is accepted only alongside -p, so the interactive path cannot reach the bypass without typing the whole word. tested Rejecting bare --yes is asserted in cli.rs, which checks the error names --dangerously-skip-permissions.

A deny rule outranks the bypass

The deny check is the first statement in the body and returns before if self.gate == Gate::SkipAll is evaluated. egress has the same two statements in the same order for the network question. --dangerously-skip-permissions used to be the first thing decide read and is now the third.

The argument for moving it: a deny rule is something the operator wrote down and can go and read, and the bypass is a flag typed to get a script through. Claude Code makes the same ruling, that if a tool is denied at any level no other level can allow it. tested a_deny_rule_beats_the_bypass_flag builds a Gate::SkipAll gate with an empty answer queue, asserts Bash is denied on the local axis and WebFetch(domain:evil.example) on the network one, and then asserts that docs.rs is still allowed. Without that third assertion the guarantee would be indistinguishable from the flag having stopped working.

An allow rule answers before the unattended denial

The block that consults the allow rule, read_only, EXEMPT and the session grant sits above if self.gate == Gate::Unattended. So a -p run carrying "allow": ["Bash"] runs Bash unprompted with no bypass flag, while every tool the file does not name still comes back with the "there is nobody to ask" denial.

That is a narrower-than-bypass unattended mode, and nothing announces it. It is tool-wide only: the narrowing somebody would reach for, Bash(git log:*), parses into Spec::Unsupported, matches nothing in any list, and is announced at boot as a rule that does nothing. The choice available to a script today is the whole tool unprompted, or nothing.

Where the rung is missing from the prose

The module doc at the top of approval.rs prints an eight-line ladder. It lists the hook denial, the deny rule, the bypass, the ask rule, the allow rule, read-only or EXEMPT, a session grant, and the human. The Gate::Unattended denial is not one of the eight, and the egress question is not either, although both are in the code the doc sits above.

emma --help prints its own ladder, and it has the same shape and the same gap. Two lines of the shipped 0.1.0 binary, read on this machine: 

  The order, and the first line that answers wins: a PreToolUse hook denial, a
  deny rule, --dangerously-skip-permissions, an ask rule, an allow rule,
  read-only, a session grant, then you. A hook denial and a deny rule cannot be
  approved away, and neither is waved through by the bypass flag.

Where rung 1 lives

The hook denial is not enforced in approval.rs. The loop runs PreToolUse, and on a denial it draws the blocked line, writes the record and returns a failed tool result before Approvals::request is reached. No code in the gate can undo it, and no test in the gate can exercise it either.
