Steering: typing while a goal runs

Until 2026-09-06 the keyboard was dead while a goal ran, and that was not an oversight: the approval gate drains the line channel before every question, because a y left over from one question must never answer the next. Steering adds a second channel no prompt can read, so words typed mid-goal reach the model at the next turn without ever being able to become an answer.

The invariant it had to survive

approval.rs drains LineSource before every prompt. The reason is in that file's own history: a y typed before a question existed once became a goal, and a leftover answer arriving at the next question is the same defect from the other side. That drain is why nothing read the keyboard during a goal at all.

Steering does not reopen it. The queue here is a second channel, and no prompt reads it: Approvals::ask and Approvals::read_line read LineSource and only LineSource, and nothing in steering.rs is reachable from either. A queued steer cannot answer an approval by construction rather than by care, which is the difference between a guarantee and a habit. tested a_queued_steer_never_answers_a_later_approval queues an emphatic y, scripts one No, and both writes are refused.

The other direction is a decision rather than a construction, and it is taken at the seam in term/input.rs. While a question is on screen, typed input is the answer path, so nothing is queued at all. mid_goal is handed prompt_pending for exactly that ruling, and it is the one guard standing between an answer and this queue. tested a_line_typed_while_a_question_is_pending_never_reaches_the_queue goes red when the guard is removed.

Where a typed line goes, decided on the reader thread

crates/emma/src/session_command.rs · mid_goal

pub fn mid_goal(line: &str, goal_active: bool, prompt_pending: bool) -> MidGoal {
    if !goal_active {
        return MidGoal::Send;
    }
    match parse(line) {
        // Nothing typed. There is no steer here to queue and no command to
        // rule on, so it goes where an empty line has always gone: down the
        // channel, where the next drain discards it.
        None if line.trim().is_empty() => MidGoal::Send,
        // **The poisoning invariant, and it is this line.** A question is on
        // screen, so what is being typed is an answer to it, and an answer
        // belongs to `Approvals::ask` on the line channel. Nothing reaches the
        // steering queue in this state, which is why a `y` can never come back
        // four turns later as an instruction to the model.
        None if prompt_pending => MidGoal::Send,
        None => MidGoal::Queue,
        Some(SessionCommand::Exit) => MidGoal::Interrupt,
        Some(SessionCommand::Help) => MidGoal::Help,
        // A command typed under a question is not an answer to it, so it is not
        // sent; and it is not queued either, because the queue is closed in
        // this state and a command that vanished into it would be the drain
        // hole reopened from the other side. It waits, in the box, exactly as
        // every non-immediate command did before boundary commands existed.
        Some(other) if prompt_pending => MidGoal::Wait(name_of(&other)),
        Some(other) => match boundary_of(&other) {
            Some(name) => MidGoal::Boundary(name),
            None => MidGoal::Wait(name_of(&other)),
        },
    }
}
crates/emma/src/session_command.rs — mid_goal, MidGoal

The routing happens on the thread that owns the keyboard, in the same breath as goal_active, because that is the only place both facts are current. submit_line in term/input.rs acts on the answer: Send pushes down the channel as before, Interrupt is /exit reaching the same path Alt+q takes, Help prints the same constant /help prints between goals, Queue empties the input box and pushes the text, Boundary does the same with a parsed command, and Wait pastes the line back into the box with a notice saying what did not happen.

Two details of that list carry an argument. A queued line leaves the box and lands in the transcript immediately, because a queued line that left no trace is the silently-eaten line this seam exists to stop being. And the Wait path pastes the text back rather than holding it somewhere: the editor has no restore, the remedy is one keystroke, and the evidence is on screen.

Which commands may run between two turns

boundary_of is exhaustive, like name_of beside it, and that is the guard doing its work: a new SessionCommand variant will not compile until somebody has decided whether it is safe to apply between two model calls of a goal that is still running. The test each arm has to pass is not "is it useful mid-goal" but "does it change something the running goal is standing on".

The boundary set is mainline's own command table rather than the fork's. Boundary carries the harness root and the theme in force at startup as well as the terminal, the approvals and the home, because mainline's /theme lists project themes and marks the one on screen; the agent takes theme_at_start through steered_by so a listing drained at a boundary is not a lie. /compact is answered by the agent rather than by run_boundary, because it is the agent's own operation, and the two compact texts moved into pure functions so the drain point and /compact say the same thing. tested a_boundary_command_applies_at_the_turn_boundary.

The drain, and what the model is shown

Agent::drain_the_steering_queue runs at the top of each loop iteration, which is a boundary that already existed. Text and commands come off one queue in the order they were typed, because that is the order they were meant in: somebody who types /mode plan and then "stop editing and explain" means the second under the first, and two queues would apply them in an order nobody chose. Commands run in place, between the sentences around them.

The text is accumulated rather than injected line by line. Several sentences typed during one turn are one interjection, and one attributed block reads as a person talking where three would read as three interruptions. tested a_steer_typed_during_iteration_one_is_in_iteration_twos_request and several_steers_arrive_together_in_the_order_they_were_typed. Removing the drain from the top of the loop turns four of the five tests in crates/emma/tests/steering.rs red.

crates/emma/src/steering.rs · attributed

/// The bracketed register injected steering arrives in.
///
/// **Attributed, in the same style [`crate::goal::Goal::opening_turn`] uses for
/// hook context, and for the mirror-image reason.** There, text the user did not
/// write must not read as theirs. Here, text the user *did* write arrives in a
/// place they could not have written it, after tool results, inside a turn the
/// loop composed, and a model that cannot tell the difference reads a mid-task
/// correction as part of a tool's output.
///
/// One string rather than a second content block, and it rides the user turn
/// that is already there, because two user turns in a row is a 400 and an
/// assistant turn would be words put in the model's mouth. See
/// [`crate::session::append_user_text`], which is the rule and is shared with
/// the fold.
pub fn attributed(lines: &[String]) -> String {
    let mut s = String::from(
        "[The user typed this while you were working, after the results above. It is them \
         speaking mid-task: treat it as their current instruction and adjust.]\n",
    );
    for line in lines {
        s.push_str(line.trim());
        s.push('\n');
    }
    // The trailing newline goes: what this is appended to already separates
    // itself, and a turn ending in blank lines is bytes paid for twice.
crates/emma/src/steering.rs — attributed; crates/emma/src/session.rs — append_user_text

Two constraints shape that function. The register is bracketed and attributed, mirroring the style Goal::opening_turn uses for hook context and for the mirror-image reason: there, text the user did not write must not read as theirs; here, text the user did write arrives somewhere they could not have written it, after tool results, inside a turn the loop composed. A model that cannot tell the difference reads a mid-task correction as part of a tool's output. And it is one string appended to the user turn that is already there, rather than a new turn: two user turns in a row is a 400 from the Messages API, and an assistant turn would be words put in the model's mouth. tested Replacing the join with a pushed user turn turns two tests red, one of them the roles-alternate assertion, which is the 400 in test form.

The block is written to the session log as the steer record it is, at the position it entered, so a --resume replays the conversation that was actually sent rather than one without the interjection. The record stores the composed string as well as the lines, for the reason compacted stores its replacement: the fold replays what happened rather than re-deriving it. See Records and The fold.

The line typed during the last model call

A goal's final drain happens before its final model call, so anything typed after that point is still in the queue when the goal ends. It is not discarded and it does not meet the prompt's own drain: main.rs empties the queue between goals, turns whatever text was in it into the next goal, and says so. A queued command gets the full dispatcher there rather than the boundary subset, because at that point it really is between goals, so /model and /clear are ordinary commands again.

That is the promise the whole seam is built to keep: typing while a goal runs must never be silently dead. Every path either sends the line, queues it with a receipt, runs it, or puts it back in the box with a notice.

The queue itself

/// The queue itself: a handle, cloneable, shared between the reader thread that
/// fills it and the loop that empties it.
///
/// A `std::sync::Mutex` rather than tokio's because both sides hold it for the
/// length of a `push` or a `take` and neither awaits inside it. The reader is a
/// plain OS thread and cannot await at all.
#[derive(Clone, Default)]
pub struct Steering(Arc<Mutex<Vec<Steer>>>);
crates/emma/src/steering.rs — Steering, Steer, global

A std::sync::Mutex rather than tokio's, because both sides hold it for the length of a push or a take and neither awaits inside it; the reader is a plain OS thread and cannot await at all. The real run uses one process global, for the reason approval::publish_mode is one: the two ends are a detached thread reading the keyboard and a loop several frames down main's stack, and threading a handle between them would touch every file in between. Tests never touch the global. They build their own Steering and hand it to the agent, so nothing here is shared state between test cases.

The transcript row a queued line leaves has two wordings, because two things are true and which one holds depends on the engine. queued_notice says "queued for the next turn" where Emma's own loop will inject it, and "queued for after this goal" where it will not: the claude engine cannot be reached mid-run, so its queue drains when the goal ends, and a row promising the next turn there would be a promise the code does not keep. tested the_queued_row_says_which_promise_is_being_made. unverified Nothing sets that flag false yet: set_steerable(false) for the claude engine arrives with the engine package, so today every run promises the next turn and every run means it. Settling it: land that wiring and read the row on a claude goal.

What is not settled

  • unverified The reader thread against a real console. submit_line runs there, and every scrollback defect this crate has shipped was on that thread. The tests drive mid_goal and the agent's drain directly. Settling it: type during a real goal on Windows Terminal and on Terminal.app, and watch the box empty, the row appear and the answer change.
  • unverified What a model does with an interjection. The tests assert the attributed block is in the next request, in order, attributed. Whether a model actually adjusts is a claim about the model, and nothing here measures it.
  • unverified A boundary /mode under a question that arrives in the same instant. The argument is that the queue is shut while a question is on screen, so the switch cannot land between a question and its answer. That is read off mid_goal rather than raced. Settling it: a test that pushes a mode command while prompt_pending is true and asserts the queue stays empty, which is the pending-question guard's test extended to the command arm.
