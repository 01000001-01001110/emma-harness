Sessions & context

One file, one writer

Sessions & context The file Records The fold Resume Continuity Compaction The corpus

A session is one JSONL file under ~/.emma/sessions/, opened at startup and appended to as the run happens. This page covers the type that owns it: how an id is made, where the file goes, what one append does, and the two ways the writing can go wrong — a write that starts failing mid-run, and a line that will not parse coming back. Both used to be silent; both now say so once.

The id, and why it is not an mtime

// crates/emma/src/session.rs
/// A session id that sorts by time and cannot collide between two `emma`
/// processes started in the same millisecond.
pub fn new_id() -> String {
    let ms = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .map(|d| d.as_millis())
        .unwrap_or(0);
    format!("sess-{ms:013}-{}", std::process::id())
}

Thirteen digits of unix milliseconds, zero-padded, then the process id. The padding is what makes a plain lexical sort a chronological one, and it is relied on twice: locate walks candidates .rev() after a sort(), and the first-run check reads only the tail of the same ordering. Both name the same reason for preferring the id to the modification time. Copying a file moves its mtime and does not move its id. tested ids_sort_by_time takes two ids two milliseconds apart and asserts a < b as strings.

crates/emma/src/session.rs — SessionLog::new_id, locate, first_run

A clock that cannot be read yields 0 rather than an error, so the id is sess-0000000000000-<pid> and the process id is the only thing keeping two such runs apart. Nothing in the tree exercises that branch. unverified: settle it by making duration_since(UNIX_EPOCH) fail, which needs a system clock set before 1970, and checking that two concurrent runs still get separate files.

Where the file goes

// crates/emma/src/session.rs
/// `~/.emma/sessions/`, or `EMMA_SESSION_DIR` when set — which is how a
/// test writes somewhere other than the developer's real history.
pub fn default_dir(home: Option<&Path>) -> Option<PathBuf> {
    if let Some(dir) = std::env::var_os("EMMA_SESSION_DIR") {
        return Some(PathBuf::from(dir));
    }
    home.map(|h| h.join(".emma").join("sessions"))
}

The environment variable wins over the home directory unconditionally, and --session-dir on the command line wins over both, because main.rs resolves the flag first and only falls back to this. An Option comes back rather than a guess, and the caller that gets None is the one case SessionLog::none exists for.

// crates/emma/src/session.rs
pub fn open(dir: &Path, id: impl Into<String>) -> Result<Self> {
    let id = id.into();
    fs::create_dir_all(dir).with_context(|| format!("creating {}", dir.display()))?;
    let path = dir.join(format!("{id}.jsonl"));
    let file = OpenOptions::new()
        .create(true)
        .append(true)
        .open(&path)
        .with_context(|| format!("opening {}", path.display()))?;
    Ok(Self {
        id,
        path,
        file: Arc::new(Mutex::new(Some(file))),
        prefix: None,
        stamp: Vec::new(),
        tap: None,
        write_failed: Arc::new(AtomicBool::new(false)),
    })
}

create(true).append(true) is what makes a resume continue the same file instead of truncating it: main.rs resolves the restore before the log is opened, hands open the restored id, and every record of the second leg lands after the first. It is also why a run that starts and stops without doing anything leaves a zero-byte file behind, which is most of what is in the directory today. See The corpus.

The log that records nothing

// crates/emma/src/session.rs
/// Records nothing. For tests that are not about persistence, and for the
/// case where the home directory cannot be determined — an agent that
/// refuses to run because it cannot write a transcript would be trading a
/// working tool for a diary.
pub fn none() -> Self {
    Self {
        id: "sess-none".into(),
        path: PathBuf::new(),
        file: Arc::new(Mutex::new(None)),
        prefix: None,
        stamp: Vec::new(),
        tap: None,
        write_failed: Arc::new(AtomicBool::new(false)),
    }
}

file is Option<File> so that this variant needs no separate type and no trait: every append walks the same code and returns at the let Some(file) = guard.as_mut() else { return } line. The id is the literal sess-none and the path is empty, so anything that prints the transcript location for a run in this state prints nothing useful. main.rs reaches it two ways: no session directory at all, and an open that failed, where it warns no session transcript: {e} and carries on. tested a_log_with_no_file_is_not_an_error appends to one and asserts nothing by not panicking.

id() and path() are one-line accessors over those two fields, and nothing else on the type is public that is not described on this page or on Records.

A blocking file in an async program

// crates/emma/src/session.rs — the SessionLog fields
pub struct SessionLog {
    id: String,
    path: PathBuf,
    /// A plain `std::fs::File` behind a `std::sync::Mutex`, in an async
    /// program, on purpose: a record is a few hundred bytes and is written
    /// between a model call and a subprocess. Making it async would buy
    /// nothing measurable and would make "append the record, *then* do the
    /// thing" — the ordering the whole file exists for — an await point where
    /// a cancellation can land.
    ///
    /// `Arc` because [`SessionLog::subagent`] hands out a second view of the
    /// *same* file rather than a second file. One process, one writer, one
    /// mutex — the module doc's "a second writer" caveat is about a second
    /// process, not a second logical run inside this one.
    file: Arc<Mutex<Option<File>>>,

The ordering that argument protects is the one the whole format is for. A record goes down before the thing it describes happens, so a run killed between the two leaves a claim that a tool was about to run and no claim that it did. Reverse the order and the file would sometimes assert a tool ran when the process died first. An await between the append and the tool call is where a cancelled future would land, and tokio::select! in call_model is a cancellation of exactly that shape, happening elsewhere in the same loop.

Why not SQLite

The module doc argues it rather than assuming it. SQLite pays for itself against concurrent writers and against a crash-recovery fold that has to decide whether a side-effecting tool already ran. Emma has one process, one user, one writer, and no recovery requirement: a crashed run is re-run, because what it was doing is in the working tree where you can see it. A database would add a dependency, a schema, a migration story and a binary file you cannot grep.

Three things would reverse it, and the doc says the reversal should happen the same day any of them arrives. A second writer, because O_APPEND survives concurrent small writes on unix and does not on Windows. Exactly-once tool semantics across a crash, which needs a transaction rather than a line. Queries across sessions, which today mean folding every file in the directory. The third already costs something: locate is a directory scan, and its own doc names it as the cost the module doc predicted.

One append

pub fn append(&self, kind: &str, mut payload: Value) {
    let kind = match self.prefix {
        Some(prefix) => format!("{prefix}.{kind}"),
        None => kind.to_string(),
    };
    if let Some(obj) = payload.as_object_mut() {
        obj.insert("kind".into(), json!(kind));
        obj.insert(
            "at_ms".into(),
            json!(SystemTime::now()
                .duration_since(UNIX_EPOCH)
                .map(|d| d.as_millis() as u64)
                .unwrap_or(0)),
        );
        for (key, value) in &self.stamp {
            obj.insert(key.clone(), value.clone());
        }
    }
    if let Some(tap) = &self.tap {
        if let Ok(mut seen) = tap.lock() {
            seen.push(payload.clone());
        }
    }
    // **A poisoned lock is recovered, not treated as a reason to stop
    // writing.** The lock is poisoned when some thread panicked while
    // holding it, which says nothing about whether the file is still
    // writable -- and this returned instead, silently dropping every record
    // from that moment on. Worse than the silence: `write_failed` was never
    // set on this path, so `transcript_failed` went on reporting that the
    // transcript was fine while the session stopped being recorded. The one
    // observable that exists to make this visible said the opposite.
    //
    // Recovering is what the rest of this tree does -- twenty-five
    // `unwrap_or_else(|e| e.into_inner())` sites across `term`, `agent` and
    // `input` -- and this file was the outlier. The data inside is a `File`
    // handle, which a panic elsewhere cannot leave torn.
    let mut guard = self.file.lock().unwrap_or_else(|e| e.into_inner());
    // `None` is the no-log constructor and is the one silence here that is
    // correct: a run with no session directory has nothing to append to.
    let Some(file) = guard.as_mut() else { return };
    let mut line = payload.to_string();
    line.push('\n');
    // Not `let _ =`. This file is the only record of the run: resume folds
    // it, `emma agents` reads it, and the exit line names it as the place
    // the conversation went. A full disk or a revoked handle used to lose
    // all of that in silence, for the whole rest of the session, because
    // every append discarded its own error.
    //
    // Reported once and then never again — a failing write fails on every
    // record, and a warning per record would bury the run in its own
    // complaint. Still not fatal: losing the transcript is not a reason to
    // throw away the work the user is in the middle of.
    if let Err(e) = file.write_all(line.as_bytes()).and_then(|()| file.flush()) {
        if !self.write_failed.swap(true, Ordering::SeqCst) {
            eprintln!(
                "emma: this session's transcript can no longer be written: {e}. The run \
                 continues, but it will not be resumable and `emma agents` will not see it."
            );
        }
    }
}

Five things happen in a fixed order. The kind gets its prefix, which is None for a session's own records and Some("sub") for a delegation's. kind and at_ms are inserted into the payload, which is why every record in every file carries those two and only those two universally. The stamp is merged, which is how a delegation's records carry sub_id, parent_turn_id and agent. The record goes into the in-memory tap if there is one. Then the line is written and flushed, and the first write that fails is reported on stderr; every one after it is swallowed, because a failing write fails on every record and a warning per record would bury the run in its own complaint. write_failed is an Arc<AtomicBool> shared with every subagent view, so a delegation does not repeat a complaint about a file its parent already reported.

kind is inserted rather than written by the caller, so no call site can forget it or spell it differently. Where it lands in the rendered line is serde_json's business, which is why a grep for '"kind":"goal"' is a substring search over a whole file rather than a field query. It agrees with a parse today: grep -h -o '"kind":"goal"' *.jsonl | wc -l returns 61 in ~/.emma/sessions/ and a JSON parse of the same directory finds 61 records of that kind, with zero of the matches sitting inside some other record's payload. certified, 2026-08-16 20:28 EDT; the script is on The corpus. The agreement is not structural. A tool_result that carried the text of a session file, or of this page, would put the substring in a record that is not a goal.

A payload that is not a JSON object skips the whole insert block and is written as it stands, with no kind and no at_ms. Every caller in the tree passes json!({…}), so no such line exists in the corpus, and both readers would treat one as a record whose kind is the empty string and skip it.

A poisoned mutex is recovered rather than treated as the end of the transcript, and until 2026-08-23 it was not. The lock is poisoned when some thread panics while holding it, which says nothing about whether the file is still writable. append returned early instead, so every record from that moment was discarded for the rest of the process.

The silence was the smaller half. write_failed was never set on that path, so transcript_failed went on reporting that the transcript was fine while the session stopped being recorded — the one observable built to make this visible said the opposite of what had happened. Recovering with unwrap_or_else(|e| e.into_inner()) is what the rest of the tree does at twenty-five other sites, and the data behind this lock is a File handle, which somebody else's panic cannot leave half-updated. tested a_poisoned_lock_does_not_silently_stop_the_transcript poisons the lock for real, by joining a thread that panics while holding it, and asserts the lock is poisoned before appending so the case cannot pass without testing anything. Restoring the early return turns it red with only the first record on disk.

The remaining early return is the one silence here that is correct: guard.as_mut() is None for the no-log constructor, and a run with no session directory has nothing to append to.

Mid-run write failures used to be silent, and this page said so

An earlier version of append ended in two let _ = discards, and its doc claimed the caller "has already been told once by open" — which covers a directory that cannot be created or a file that cannot be opened, and says nothing about a volume that fills up or a mount that goes read-only during the run. That class of failure was silent everywhere: no warning, no record, and a session file that simply stops while resume, emma agents and the exit line all keep pointing at it. The warn box that used to sit here made that argument, and the code now agrees with it: the first failed write prints one line on stderr saying the transcript can no longer be written, and every later failure is swallowed on the write_failed flag. certified by reading append: the if let Err(e) around write_all and flush is quoted above and greppable. Whether that line is actually seen — a full volume has not been staged, and in the framed UI stderr lands on the alternate screen — is unverified: settle it by filling the volume holding ~/.emma/sessions/ during a goal and reading what appears.

Reading it back, and what a crash can do

// crates/emma/src/session.rs
/// Every well-formed record in a session file, in order.
///
/// A trailing partial line — the one thing a crash mid-write can leave — is
/// skipped rather than failing the read, which is the property that makes
/// this format survivable without a transaction.
///
/// **A malformed line anywhere else is not that, and is not silent.** The
/// doc above described the tail case and the code dropped *any* line that
/// would not parse, so real corruption in the middle of a file — the case
/// where a resumed conversation is genuinely missing turns — read as a
/// clean success. The read still returns what it could recover, because
/// refusing outright would make a damaged session unresumable and that is
/// worse; but it says how many records it lost and where.
pub fn read(path: &Path) -> Result<Vec<Value>> {
    let raw =
        fs::read_to_string(path).with_context(|| format!("reading {}", path.display()))?;
    let lines: Vec<&str> = raw.lines().collect();
    let last = lines.len().saturating_sub(1);
    let mut out = Vec::new();
    let mut lost = Vec::new();
    for (n, line) in lines.iter().enumerate() {
        match serde_json::from_str(line) {
            Ok(v) => out.push(v),
            // A blank line is not damage, and neither is the torn tail.
            Err(_) if line.trim().is_empty() || n == last => {}
            Err(_) => lost.push(n + 1),
        }
    }
    if !lost.is_empty() {
        // … prints one stderr line naming the count, the file, and up to
        // five of the lost line numbers. Quoted in full in the source.
    }
    Ok(out)
}

This used to be a one-line filter_map(…ok()), which dropped any line that would not parse — not only the torn tail the doc described — and counted nothing. Silent loss in the middle of a file looked identical to no loss at all, and this page said so. The shape of the fix keeps the property that mattered and adds the one that was missing: a bad line anywhere still costs only itself, because a reader that failed outright would turn one corrupt record into an unresumable session, but a bad line that is neither blank nor last is now counted and named on stderr as damage, "not the partial last line a crash leaves behind." tested a_torn_tail_is_silent_and_damage_in_the_middle_is_not in tests/resume.rs feeds it both shapes and asserts both recover; the stderr line itself is asserted by nothing, and only reading the eprintln! says it fires.

fn a_torn_final_line_costs_only_that_line() {
