Sessions & context

One file, one writer

Sessions & context The file Records The fold Resume Continuity Compaction The corpus

A session is one JSONL file under ~/.emma/sessions/, opened at startup and appended to as the run happens. This page covers the type that owns it: how an id is made, where the file goes, what one append does, and two failure modes (a write that starts failing mid-run, and a line that will not parse on read). Both used to fail silently; both now report once.

The id, and why it is not an mtime

// crates/emma/src/session.rs
/// A session id that sorts by time and cannot collide between two `emma`
/// processes started in the same millisecond.
pub fn new_id() -> String {
    format!("sess-{:013}-{}", now_ms(), std::process::id())
}

Thirteen digits of unix milliseconds, zero-padded, then the process id. The padding is what makes a plain lexical sort a chronological one, and it is relied on twice: locate walks candidates .rev() after a sort(), and the first-run check reads only the tail of the same ordering. Both name the same reason for preferring the id to the modification time. Copying a file moves its mtime and does not move its id. tested ids_sort_by_time takes two ids two milliseconds apart and asserts a < b as strings.

crates/emma/src/session.rs — SessionLog::new_id, locate, first_run

A clock that cannot be read yields 0 instead of an error, so the id is sess-0000000000000-<pid> and the process id is the only thing keeping two such runs apart. Nothing in the tree exercises that branch. unverified: settle it by making duration_since(UNIX_EPOCH) fail, which needs a system clock set before 1970, and checking that two concurrent runs still get separate files.

Where the file goes

// crates/emma/src/session.rs
/// `~/.emma/sessions/`, or `EMMA_SESSION_DIR` when set — which is how a
/// test writes somewhere other than the developer's real history.
pub fn default_dir(home: Option<&Path>) -> Option<PathBuf> {
    if let Some(dir) = std::env::var_os("EMMA_SESSION_DIR") {
        return Some(PathBuf::from(dir));
    }
    home.map(|h| h.join(".emma").join("sessions"))
}

The environment variable wins over the home directory unconditionally, and --session-dir on the command line wins over both, because main.rs resolves the flag first and only falls back to this. An Option comes back instead of a guess. The caller that gets None is the case SessionLog::none exists for.

// crates/emma/src/session.rs
pub fn open(dir: &Path, id: impl Into<String>) -> Result<Self> {
    let id = id.into();
    fs::create_dir_all(dir).with_context(|| format!("creating {}", dir.display()))?;
    let path = dir.join(format!("{id}.jsonl"));
    let file = OpenOptions::new()
        .create(true)
        .append(true)
        .open(&path)
        .with_context(|| format!("opening {}", path.display()))?;
    Ok(Self {
        handle: Arc::new(Mutex::new(Handle {
            id,
            path,
            file: Some(file),
        })),
        prefix: None,
        stamp: Vec::new(),
        tap: None,
        write_failed: Arc::new(AtomicBool::new(false)),
    })
}

create(true).append(true) is what makes a resume continue the same file instead of truncating it: main.rs resolves the restore before the log is opened, hands open the restored id, and every record of the second leg lands after the first. It is also why a run that starts and stops without doing anything leaves a zero-byte file behind, which is most of what is in the directory today. See The corpus.

The log that records nothing

// crates/emma/src/session.rs
/// Records nothing. For tests that are not about persistence, and for the
/// case where the home directory cannot be determined — an agent that
/// refuses to run because it cannot write a transcript would be trading a
/// working tool for a diary.
pub fn none() -> Self {
    Self {
        handle: Arc::new(Mutex::new(Handle {
            id: "sess-none".into(),
            path: PathBuf::new(),
            file: None,
        })),
        prefix: None,
        stamp: Vec::new(),
        tap: None,
        write_failed: Arc::new(AtomicBool::new(false)),
    }

file is Option<File> so that this variant needs no separate type and no trait: every append walks the same code and returns where the handle has no file. The id is the literal sess-none and the path is empty, so anything that prints the transcript location for a run in this state prints nothing useful. main.rs reaches it two ways: no session directory at all, and an open that failed, where it warns no session transcript: {e} and carries on. A move on a log in this state moves the identity and stays silent, because a move that opened a file would make the one path promising to record nothing start recording. tested a_log_with_no_file_is_not_an_error appends to one and asserts nothing by not panicking.

read is one line over read_reporting, and the split is the argument. The loss used to reach an eprintln! and nowhere else, so the test named a_torn_tail_is_silent_and_damage_in_the_middle_is_not asserted only that the readable records came back, which is true whether or not the damage was noticed: an adversarial reviewer removed the counting entirely and the test stayed green across the whole crate. Printing is a presentation choice; knowing is not, so the damage is returned as well. torn_tail is decided by ends_with('\n') rather than by the last line's position, because a truncated record can be valid JSON and only the trailing byte tells the two apart. tested That last rule was found by mutation, in a pass that was not allowed to fix it.

id() and path() return owned values rather than borrows, and that changed on 2026-09-06 when an in-place /resume became possible. The identity now lives behind the same lock as the file, because the two change together and must never disagree: an id left pointing at the abandoned file would stamp the resumed session's records with the wrong name, which is a transcript claiming to be a session it is not. A borrow out of a MutexGuard cannot outlive the guard, so the accessors clone. That is the whole cost of the move being possible at all. See Resume.

lock() is the fourth thing that changed with it: the poisoned-lock recovery used to sit inside append and now has four callers, so it is one function. A panic on some other thread says nothing about whether this file is still writable, and what is inside the mutex is a File and two strings, which a panic elsewhere cannot leave torn.

A blocking file in an async program

/// Which file this log is on, and the handle open on it.
///
/// **One struct rather than three fields because they change together and must
/// never disagree.** An in-place `/resume` closes one session's file and opens
/// another's, and an id left pointing at the abandoned file would stamp the
/// resumed session's records with the wrong name — which is a transcript that
/// says it is a session it is not. See [`SessionLog::move_to`].
///
/// The file stays `Option` for the reason it always was: [`SessionLog::none`]
/// records nothing and has no handle to hold.
struct Handle {
    id: String,
    path: PathBuf,
    file: Option<File>,
}

// ... a type alias and the module's constants elided ...

pub struct SessionLog {
    /// A plain `std::fs::File` behind a `std::sync::Mutex`, in an async
    /// program, on purpose: a record is a few hundred bytes and is written
    /// between a model call and a subprocess. Making it async would buy
    /// nothing measurable and would make "append the record, *then* do the
    /// thing" — the ordering the whole file exists for — an await point where
    /// a cancellation can land.
    ///
    /// `Arc` because [`SessionLog::subagent`] hands out a second view of the
    /// *same* file rather than a second file, and because the process shares
    /// the log as `&SessionLog`: nothing anywhere holds a `&mut`, so moving
    /// the session onto another file has to happen through here. One process,
    /// one writer, one mutex — the module doc's "a second writer" caveat is
    /// about a second process, not a second logical run inside this one.
    handle: Arc<Mutex<Handle>>,

Record-before-action ordering is what the format requires. A record goes down before the thing it describes happens, so a run killed between the two leaves a claim that a tool was about to run and no claim that it did. Reverse the order and the file could assert a tool ran when the process died first. An await between append and tool call is where a cancelled future would land; tokio::select! in call_model can cancel in exactly that shape elsewhere in the same loop.

Why not SQLite

The module doc compares JSONL to SQLite. SQLite pays off with concurrent writers and a crash-recovery fold that must decide whether a side-effecting tool already ran. Emma has one process, one user, one writer, and no recovery requirement: a crashed run is re-run from the working tree. A database would add a dependency, a schema, migrations, and a binary file you cannot grep.

Three conditions would reverse the choice, and the doc says to switch the same day any of them arrives: a second writer (O_APPEND on unix vs Windows), exactly-once tool semantics across a crash (needs a transaction), or queries across sessions (today a directory fold). locate is already a directory scan; its doc names that cost.

One append

/// Append one record.
///
/// Failures are swallowed after the first, deliberately: a full disk must
/// not be the thing that kills a run halfway through editing someone's
/// source tree. The caller has already been told once by `open`.
pub fn append(&self, kind: &str, mut payload: Value) {
    let kind = match self.prefix {
        Some(prefix) => format!("{prefix}.{kind}"),
        None => kind.to_string(),
    };
    if let Some(obj) = payload.as_object_mut() {
        obj.insert("kind".into(), json!(kind));
        obj.insert("at_ms".into(), json!(now_ms()));
        for (key, value) in &self.stamp {
            obj.insert(key.clone(), value.clone());
        }
    }
    if let Some(tap) = &self.tap {
        if let Ok(mut seen) = tap.lock() {
            seen.push(payload.clone());
        }
    }
    // **A poisoned lock is recovered, not treated as a reason to stop
    // writing.** The lock is poisoned when some thread panicked while
    // holding it, which says nothing about whether the file is still
    // writable -- and this returned instead, silently dropping every record
    // from that moment on. Worse than the silence: `write_failed` was never
    // set on this path, so `transcript_failed` went on reporting that the
    // transcript was fine while the session stopped being recorded. The one
    // observable that exists to make this visible said the opposite.
    //
    // Recovering is what the rest of this tree does -- twenty-five
    // `unwrap_or_else(|e| e.into_inner())` sites across `term`, `agent` and
    // `input` -- and this file was the outlier. The data inside is a `File`
    // handle, which a panic elsewhere cannot leave torn.
    //
    // The recovery is `Self::lock` now rather than an `unwrap_or_else`
    // here, because `move_to` and the two accessors take the same lock and
    // one of them writing `.unwrap()` would reintroduce exactly this.
    let mut guard = self.lock();
    // `None` is the no-log constructor and is the one silence here that is
    // correct: a run with no session directory has nothing to append to.
    let Some(file) = guard.file.as_mut() else {
        return;
    };
    let mut line = payload.to_string();
    line.push('\n');
    // Not `let _ =`. This file is the only record of the run: resume folds
    // it, `emma agents` reads it, and the exit line names it as the place
    // the conversation went. A full disk or a revoked handle used to lose
    // all of that in silence, for the whole rest of the session, because
    // every append discarded its own error.
    //
    // Reported once and then never again — a failing write fails on every
    // record, and a warning per record would bury the run in its own
    // complaint. Still not fatal: losing the transcript is not a reason to
    // throw away the work the user is in the middle of.
    if let Err(e) = file.write_all(line.as_bytes()).and_then(|()| file.flush()) {
        if !self.write_failed.swap(true, Ordering::SeqCst) {
            eprintln!(
                "emma: this session's transcript can no longer be written: {e}. The run \
                 continues, but it will not be resumable and `emma agents` will not see it."
            );
        }
    }
}

The kind gets a prefix (None for the session, Some("sub") for a delegation). kind and at_ms are inserted into the payload, which is why every record carries those two fields. The stamp merges in delegation fields (sub_id, parent_turn_id, agent). The record goes into the in-memory tap when present. Then the line is written and flushed; the first write failure prints on stderr, and later failures are swallowed so one complaint does not flood the run. write_failed is an Arc<AtomicBool> shared with every subagent view, so a delegation does not repeat a complaint the parent already printed.

kind is inserted by append, not by callers, so no call site can omit or misspell it. Where it appears in the rendered line is serde_json's ordering, which is why grep '"kind":"goal"' is a substring search, not a field query. It agrees with a parse today: grep -h -o '"kind":"goal"' *.jsonl | wc -l returns 61 in ~/.emma/sessions/ and a JSON parse of the same directory finds 61 records of that kind, with zero of the matches sitting inside some other record's payload. certified, 2026-08-16 20:28 EDT; the script is on The corpus. The agreement is not structural. A tool_result that carried the text of a session file, or of this page, would put the substring in a record that is not a goal.

A payload that is not a JSON object skips the whole insert block and is written as it stands, with no kind and no at_ms. Every caller in the tree passes json!({…}), so no such line exists in the corpus, and both readers would treat one as a record whose kind is the empty string and skip it.

A poisoned mutex is recovered instead of stopping the transcript (before 2026-08-23 it was not). The lock is poisoned when a thread panics while holding it, which does not imply the file is unwritable. append returned early instead, discarding every later record for the rest of the process.

On that path write_failed was never set, so transcript_failed kept reporting a healthy transcript while recording had stopped. Recovery uses unwrap_or_else(|e| e.into_inner()), matching twenty-five other sites in the tree; the data behind this lock is a File handle that another thread's panic cannot leave half-updated. tested a_poisoned_lock_does_not_silently_stop_the_transcript poisons the lock for real, by joining a thread that panics while holding it, and asserts the lock is poisoned before appending so the case cannot pass without testing anything. Restoring the early return turns it red with only the first record on disk.

The remaining early return is the one silence here that is correct: guard.as_mut() is None for the no-log constructor, and a run with no session directory has nothing to append to.

Mid-run write failures used to be silent, and this page said so

An earlier version of append ended in two let _ = discards, and its doc claimed the caller "has already been told once by open". That covers a directory that cannot be created or a file that cannot be opened, not a volume that fills up or a mount that goes read-only during the run. That failure was silent everywhere: no warning, no record, and a session file that stops while resume, emma agents and the exit line still point at it. The code now prints one stderr line on the first failed write; later failures are suppressed on the write_failed flag. certified by reading append: the if let Err(e) around write_all and flush is quoted above and greppable. Whether that line is visible in practice (no staged full volume; framed UI stderr on the alternate screen) is unverified: fill the volume holding ~/.emma/sessions/ during a goal and read what appears.

Reading it back, and what a crash can do

// crates/emma/src/session.rs
/// Every well-formed record in a session file, in order.
///
/// A trailing partial line — the one thing a crash mid-write can leave — is
/// skipped rather than failing the read, which is the property that makes
/// this format survivable without a transaction.
///
/// **A malformed line anywhere else is not that, and is not silent.** The
/// doc above described the tail case and the code dropped *any* line that
/// would not parse, so real corruption in the middle of a file — the case
/// where a resumed conversation is genuinely missing turns — read as a
/// clean success. The read still returns what it could recover, because
/// refusing outright would make a damaged session unresumable and that is
/// worse; but it says how many records it lost and where.
pub fn read(path: &Path) -> Result<Vec<Value>> {
    Self::read_reporting(path).map(|(records, _lost)| records)
}

// ... the doc on read_reporting, quoted below ...

/// The same read, with the damage handed back rather than only printed.
///
/// **A guarantee nothing can observe is not a guarantee.** The loss used to
/// reach an `eprintln!` and nowhere else, so the test named
/// `a_torn_tail_is_silent_and_damage_in_the_middle_is_not` asserted only
/// that the readable records came back — which is true whether or not the
/// damage was noticed. An adversarial reviewer removed the counting
/// entirely and the test stayed green across the whole crate.
///
/// That is the false-receipt shape this repository is most often bitten by,
/// and the fix is not a better assertion on stderr: it is that the caller
/// should have been told. Printing is a presentation choice; knowing is not.
pub fn read_reporting(path: &Path) -> Result<(Vec<Value>, Vec<usize>)> {
    let raw =
        fs::read_to_string(path).with_context(|| format!("reading {}", path.display()))?;
    let lines: Vec<&str> = raw.lines().collect();
    // **A torn tail is a file that stops mid-line, and that is a fact about
    // the trailing byte rather than about the line's position.** Until
    // 2026-08-23 the last line was exempt from damage reporting whatever
    // the file looked like, which is right after a crash — the writer was
    // interrupted between the record and its newline — and wrong for a file
    // that ends cleanly, where the last line is a whole record like any
    // other. Corruption there was dropped in silence and the resume came
    // back a turn short saying nothing, which is the silent-data-loss shape
    // this file's own reporting exists to refuse. Found by mutation, in a
    // pass that was not permitted to fix it.
    //
    // `ends_with('\n')` rather than a check on the last line's contents: a
    // truncated record can be valid JSON, so nothing about the text
    // distinguishes the two cases and only the byte does.
    let torn_tail = if raw.ends_with('\n') {
        usize::MAX
    } else {
        lines.len().saturating_sub(1)
    };
    let mut out = Vec::new();
    let mut lost = Vec::new();
    for (n, line) in lines.iter().enumerate() {
        match serde_json::from_str(line) {
            Ok(v) => out.push(v),
            // A blank line is not damage, and neither is the torn tail.
            Err(_) if line.trim().is_empty() || n == torn_tail => {}
            Err(_) => lost.push(n + 1),
        }
    }

// ... one eprintln! naming the count, the file and up to five
// lost line numbers, then `Ok((out, lost))` ...

This used to be a one-line filter_map(…ok()), which dropped any line that would not parse, not only the torn tail the doc described, and counted nothing. Silent loss in the middle looked like no loss. The fix keeps one bad line costing only itself (a reader that failed outright would make one corrupt record unresumable) and counts and names other bad lines on stderr as damage, not the partial last line a crash leaves behind. tested a_torn_tail_is_silent_and_damage_in_the_middle_is_not in tests/resume.rs feeds it both shapes and asserts both recover; the stderr line itself is asserted by nothing, and only reading the eprintln! says it fires.
