Sessions & context

One file, one writer

Sessions & context The file Records The fold Resume Continuity Compaction The corpus

A session is one JSONL file under ~/.emma/sessions/, opened at startup and appended to as the run happens. This page covers the type that owns it: how an id is made, where the file goes, what one append does, and the two ways the writing can stop being reliable without anyone finding out.

The id, and why it is not an mtime

// crates/emma/src/session.rs
/// A session id that sorts by time and cannot collide between two `emma`
/// processes started in the same millisecond.
pub fn new_id() -> String {
    let ms = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .map(|d| d.as_millis())
        .unwrap_or(0);
    format!("sess-{ms:013}-{}", std::process::id())
}

Thirteen digits of unix milliseconds, zero-padded, then the process id. The padding is what makes a plain lexical sort a chronological one, and it is relied on twice: locate walks candidates .rev() after a sort(), and the first-run check reads only the tail of the same ordering. Both name the same reason for preferring the id to the modification time. Copying a file moves its mtime and does not move its id. tested ids_sort_by_time takes two ids two milliseconds apart and asserts a < b as strings.

crates/emma/src/session.rs — SessionLog::new_id, locate, first_run

A clock that cannot be read yields 0 rather than an error, so the id is sess-0000000000000-<pid> and the process id is the only thing keeping two such runs apart. Nothing in the tree exercises that branch. unverified: settle it by making duration_since(UNIX_EPOCH) fail, which needs a system clock set before 1970, and checking that two concurrent runs still get separate files.

Where the file goes

// crates/emma/src/session.rs
/// `~/.emma/sessions/`, or `EMMA_SESSION_DIR` when set — which is how a
/// test writes somewhere other than the developer's real history.
pub fn default_dir(home: Option<&Path>) -> Option<PathBuf> {
    if let Some(dir) = std::env::var_os("EMMA_SESSION_DIR") {
        return Some(PathBuf::from(dir));
    }
    home.map(|h| h.join(".emma").join("sessions"))
}

The environment variable wins over the home directory unconditionally, and --session-dir on the command line wins over both, because main.rs resolves the flag first and only falls back to this. An Option comes back rather than a guess, and the caller that gets None is the one case SessionLog::none exists for.

// crates/emma/src/session.rs
pub fn open(dir: &Path, id: impl Into<String>) -> Result<Self> {
    let id = id.into();
    fs::create_dir_all(dir).with_context(|| format!("creating {}", dir.display()))?;
    let path = dir.join(format!("{id}.jsonl"));
    let file = OpenOptions::new()
        .create(true)
        .append(true)
        .open(&path)
        .with_context(|| format!("opening {}", path.display()))?;
    Ok(Self {
        id,
        path,
        file: Arc::new(Mutex::new(Some(file))),
        prefix: None,
        stamp: Vec::new(),
        tap: None,
    })
}

create(true).append(true) is what makes a resume continue the same file instead of truncating it: main.rs resolves the restore before the log is opened, hands open the restored id, and every record of the second leg lands after the first. It is also why a run that starts and stops without doing anything leaves a zero-byte file behind, which is most of what is in the directory today. See The corpus.

The log that records nothing

// crates/emma/src/session.rs
/// Records nothing. For tests that are not about persistence, and for the
/// case where the home directory cannot be determined — an agent that
/// refuses to run because it cannot write a transcript would be trading a
/// working tool for a diary.
pub fn none() -> Self {
    Self {
        id: "sess-none".into(),
        path: PathBuf::new(),
        file: Arc::new(Mutex::new(None)),
        prefix: None,
        stamp: Vec::new(),
        tap: None,
    }
}

file is Option<File> so that this variant needs no separate type and no trait: every append walks the same code and returns at the let Some(file) = guard.as_mut() else { return } line. The id is the literal sess-none and the path is empty, so anything that prints the transcript location for a run in this state prints nothing useful. main.rs reaches it two ways: no session directory at all, and an open that failed, where it warns no session transcript: {e} and carries on. tested a_log_with_no_file_is_not_an_error appends to one and asserts nothing by not panicking.

id() and path() are one-line accessors over those two fields, and nothing else on the type is public that is not described on this page or on Records.

A blocking file in an async program

// crates/emma/src/session.rs — the SessionLog fields
pub struct SessionLog {
    id: String,
    path: PathBuf,
    /// A plain `std::fs::File` behind a `std::sync::Mutex`, in an async
    /// program, on purpose: a record is a few hundred bytes and is written
    /// between a model call and a subprocess. Making it async would buy
    /// nothing measurable and would make "append the record, *then* do the
    /// thing" — the ordering the whole file exists for — an await point where
    /// a cancellation can land.
    ///
    /// `Arc` because [`SessionLog::subagent`] hands out a second view of the
    /// *same* file rather than a second file. One process, one writer, one
    /// mutex — the module doc's "a second writer" caveat is about a second
    /// process, not a second logical run inside this one.
    file: Arc<Mutex<Option<File>>>,

The ordering that argument protects is the one the whole format is for. A record goes down before the thing it describes happens, so a run killed between the two leaves a claim that a tool was about to run and no claim that it did. Reverse the order and the file would sometimes assert a tool ran when the process died first. An await between the append and the tool call is where a cancelled future would land, and tokio::select! in call_model is a cancellation of exactly that shape, happening elsewhere in the same loop.

Why not SQLite

The module doc argues it rather than assuming it. SQLite pays for itself against concurrent writers and against a crash-recovery fold that has to decide whether a side-effecting tool already ran. Emma has one process, one user, one writer, and no recovery requirement: a crashed run is re-run, because what it was doing is in the working tree where you can see it. A database would add a dependency, a schema, a migration story and a binary file you cannot grep.

Three things would reverse it, and the doc says the reversal should happen the same day any of them arrives. A second writer, because O_APPEND survives concurrent small writes on unix and does not on Windows. Exactly-once tool semantics across a crash, which needs a transaction rather than a line. Queries across sessions, which today mean folding every file in the directory. The third already costs something: locate is a directory scan, and its own doc names it as the cost the module doc predicted.

One append

// crates/emma/src/session.rs
/// Append one record.
///
/// Failures are swallowed after the first, deliberately: a full disk must
/// not be the thing that kills a run halfway through editing someone's
/// source tree. The caller has already been told once by `open`.
pub fn append(&self, kind: &str, mut payload: Value) {
    let kind = match self.prefix {
        Some(prefix) => format!("{prefix}.{kind}"),
        None => kind.to_string(),
    };
    if let Some(obj) = payload.as_object_mut() {
        obj.insert("kind".into(), json!(kind));
        obj.insert(
            "at_ms".into(),
            json!(SystemTime::now()
                .duration_since(UNIX_EPOCH)
                .map(|d| d.as_millis() as u64)
                .unwrap_or(0)),
        );
        for (key, value) in &self.stamp {
            obj.insert(key.clone(), value.clone());
        }
    }
    if let Some(tap) = &self.tap {
        if let Ok(mut seen) = tap.lock() {
            seen.push(payload.clone());
        }
    }
    let Ok(mut guard) = self.file.lock() else {
        return;
    };
    let Some(file) = guard.as_mut() else { return };
    let mut line = payload.to_string();
    line.push('\n');
    let _ = file.write_all(line.as_bytes());
    let _ = file.flush();
}

Five things happen in a fixed order. The kind gets its prefix, which is None for a session's own records and Some("sub") for a delegation's. kind and at_ms are inserted into the payload, which is why every record in every file carries those two and only those two universally. The stamp is merged, which is how a delegation's records carry sub_id, parent_turn_id and agent. The record goes into the in-memory tap if there is one. Then the line is written and flushed.

kind is inserted rather than written by the caller, so no call site can forget it or spell it differently. Where it lands in the rendered line is serde_json's business, which is why a grep for '"kind":"goal"' is a substring search over a whole file rather than a field query. It agrees with a parse today: grep -h -o '"kind":"goal"' *.jsonl | wc -l returns 61 in ~/.emma/sessions/ and a JSON parse of the same directory finds 61 records of that kind, with zero of the matches sitting inside some other record's payload. certified, 2026-08-16 20:28 EDT; the script is on The corpus. The agreement is not structural. A tool_result that carried the text of a session file, or of this page, would put the substring in a record that is not a goal.

A payload that is not a JSON object skips the whole insert block and is written as it stands, with no kind and no at_ms. Every caller in the tree passes json!({…}), so no such line exists in the corpus, and both readers would treat one as a record whose kind is the empty string and skip it.

crates/emma/src/session.rs — SessionLog::append; crates/emma/src/agent.rs, delegate.rs, main.rs — every call site

A poisoned mutex returns without writing, permanently, for the rest of the process. That needs a panic while the lock is held, and the only code under the lock is two std::io calls whose results are discarded.

The doc's account of swallowed failures is wrong about who was told

append says the caller "has already been told once by open". open reports failures at open time: create_dir_all and the OpenOptions::open. A write that fails afterwards, on a volume that filled up during the run or a mount that went read-only, was never reported by open, because at open time it had not happened. The two let _ = discards are the whole of the handling, so that class of failure is silent everywhere: no warning on screen, no record, and a session file that simply stops. certified by reading the two functions together: open's only with_context calls are on create_dir_all and open, and append has no error path that reaches a caller. The claim that follows from that, that a mid-run write failure is invisible, is unverified: settle it by filling the volume holding ~/.emma/sessions/ during a goal, or by making the directory read-only after startup, and reading what Emma says.

Reading it back, and what a crash can do

// crates/emma/src/session.rs
/// Every well-formed record in a session file, in order.
///
/// A trailing partial line — the one thing a crash mid-write can leave — is
/// skipped rather than failing the read, which is the property that makes
/// this format survivable without a transaction.
pub fn read(path: &Path) -> Result<Vec<Value>> {
    let raw =
        fs::read_to_string(path).with_context(|| format!("reading {}", path.display()))?;
    Ok(raw
        .lines()
        .filter_map(|l| serde_json::from_str(l).ok())
        .collect())
}

filter_map(…ok()) drops any line that will not parse, not only the last one. That is broader than the doc's claim and it is the right breadth for the format: a reader that failed on one bad line anywhere would turn a single corrupt record into an unresumable session. The cost is that silent loss in the middle of a file looks identical to no loss at all. Nothing counts what it skipped.

certified: no line in the real corpus is currently unparseable. A JSON parse of all 103 files on this machine at 2026-08-16 20:28 EDT read 791 records and rejected zero lines, torn or otherwise. Redo it with the script on The corpus. 

// crates/emma/src/session.rs — the test module
#[test]
fn a_torn_final_line_costs_only_that_line() {
    // The crash this format is chosen to survive: the process died between
    // two write syscalls. Everything before it must still read.
    let dir = tempfile::tempdir().unwrap();
    let path = dir.path().join("torn.jsonl");
    fs::write(
        &path,
        "{\"kind\":\"goal\",\"text\":\"a\"}\n{\"kind\":\"assis",
    )
    .unwrap();
    let records = SessionLog::read(&path).unwrap();
    assert_eq!(records.len(), 1);
    assert_eq!(records[0]["text"], "a");
}

tested, and the fixture is written by hand, which is the limit of what it proves. It shows the reader survives a truncated tail. It does not show that a real kill produces one. unverified whether a Windows write of a few hundred bytes through write_all plus flush can be torn mid-line at all: settle it by killing a run during a large tool_result append and reading the last line of the file.
