The retained transcript

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools

Inline, the transcript was never Emma's. insert_before handed each line to the terminal, which wrapped it, kept tens of thousands of them in scrollback, scrolled them with the user's own keys and reflowed them on resize, for no code and no memory here. The alternate screen took all of that, and transcript.rs is the whole of the replacement: append, cap, scroll, follow the tail, re-wrap. chat.rs paints the visible window of it and decides nothing.

Defect: the module doc describes a world that ended

transcript.rs's doc says “It is not wired into the live UI. Nothing constructs one outside tests. The inline viewport still writes through insert_before and still gets its scrollback for free; this is here so that the flip, when it comes, is a change of caller rather than a change of design.” The flip came. App::new constructs Transcript::new(Cap::default()), App::render drives it, chat::render paints it, and frame.rs binds six methods on it to keys. That paragraph sits at the head of the subsystem's most consequential new module. certified: one non-test construction site, crates/emma/src/term/app.rs, App::new.

An entry keeps its source, not its pixels

crates/emma/src/term/transcript.rs · EntryKind

/// One block in the conversation.
#[derive(Debug, Clone)]
pub enum EntryKind {
    /// What the user typed, verbatim — a goal or a command line.
    User(String),
    /// Assistant prose, as the markdown it arrived as. The last entry may still
    /// be growing: `done` is false until the turn ends.
    Assistant { source: String, done: bool },
    /// Tool traffic — the `◆ ✓ ✗ ⊘ ⊗` vocabulary and diff hunks — already
    /// line-shaped by [`Skin`] and [`super::diff`].
    Activity(Vec<Line<'static>>),
    /// Notes, warnings, endings, the welcome, an answered prompt. Also [`Skin`]
    /// output; separate from `Activity` because the two get different gutters
    /// when the two-column transcript is built.
    Note(Vec<Line<'static>>),
}
crates/emma/src/term/transcript.rs — EntryKind, Voice

An Assistant entry holds the markdown it arrived as, so a resize re-runs the same renderer streaming uses. Two renderers of the same text would drift. Activity and Note have no source: they arrive already line-shaped from Skin, so re-wrapping them means splitting the styled line rather than re-styling a split one, which is what render::wrap_line is for. The doc says what would change that and when: search will want plain source for those too, “and that is a change to this type, made when search is built, not guessed at now.”

Voice is derived from the kind here rather than in chat.rs, and the reason is a failure mode: “the alternative is the pane sniffing styled spans to guess who is talking — which works until the day Skin restyles anything, and then fails silently.”

Entry::render is the one place a kind becomes rows, and it ends by stripping leading and trailing blanks: 

        // A block that ends in blank rows of its own would double the separator
        // the next block gets — the defect `super::spacing` was written for,
        // arriving here from a different direction.
        while self.lines.last().is_some_and(is_blank) {
            self.lines.pop();
        }
        while self.lines.first().is_some_and(is_blank) {
            self.lines.remove(0);
        }

An Assistant entry always gets a fresh Markdown per render, because Markdown carries an open-fence bit across lines: “re-running an entry means re-running all of it — starting mid-way would render the inside of a code block as prose.” tested: no_entry_carries_a_blank_row_of_its_own, and blocks_are_separated_by_exactly_one_blank_row for the other half.

The scroll position is measured from the bottom

The design proposed an offset from the tail rather than an index into the buffer, so that dropping the oldest entries at the cap cannot move what the user is looking at. The module says that is half the answer, and names where the other half came from:

“An offset from the tail is stable against the front, and slides forward by every row that arrives at the back. A view scrolled up ten rows that receives ten more rows of tool output is no longer looking at the same text, which is the failure the whole latch exists to prevent, arriving from the direction the plan did not check. So a scrolled view has its offset grown by whatever was appended below it, and stays still. The tests here found that; the design document did not.”

    fn appended(&mut self, rows: usize) {
        if self.follow {
            self.scroll = 0;
        } else {
            self.scroll = (self.scroll + rows).min(self.max_scroll());
        }
    }

…

    /// The half-open row range a pane of this height is looking at.
    ///
    /// **The scroll cannot lift the window off the top of the buffer.** The
    /// offset is counted from the bottom and knows nothing about the pane's
    /// height, so the clamp has to happen where the height is known: scrolled
    /// all the way up, the window is the *first* `height` rows rather than a
    /// sliver of them. Home showing one row of a twenty-row pane is the kind of
    /// arithmetic that looks right in the type and wrong on the screen.
    fn window(&self, total: usize, height: u16) -> (usize, usize) {
        let height = usize::from(height);
        if height == 0 || total == 0 {
            return (0, 0);
        }
        let end = total.saturating_sub(self.scroll).max(height.min(total));
        (end.saturating_sub(height), end)
    }
crates/emma/src/term/transcript.rs — appended, window, max_scroll

tested: scrolling_up_survives_everything_that_arrives_afterwards scrolls up ten rows, pushes ten more blocks, and asserts the visible rows are byte-identical to before, then asserts behind(3) is thirty rather than ten. the_cap_binding_does_not_move_the_readers_page does the same from the front, with a cap tight enough to bind. scrolling_cannot_pass_the_top_or_the_bottom holds the clamp, and its comment explains why top.len() == 3 is the assertion that matters: without the clamp the top of the buffer draws as one row in a three-row pane, and first() == "line 0" is true either way.

Five methods move the view. scroll_up breaks the follow latch; scroll_down re-latches on arrival at the tail, because “arriving at the bottom and not being pinned there is a state nobody asked for and nobody can see”; follow_tail is the End key and every submit; to_top is Home. max_scroll is one row short of everything, so behind cannot claim rows nobody can scroll past.

The cap, and how it names what it dropped

crates/emma/src/term/transcript.rs · Cap

/// How much is kept. Whichever binds first.
///
/// **Both numbers are guesses and are written down as such.** The plan proposes
/// them, the evaluation calls them a guess, and neither is wrong: terminal
/// scrollback was effectively unbounded and this is a ceiling that did not exist
/// before. What makes it honest rather than a silent loss is [`Transcript::dropped`]
/// and the marker row it produces — the cap is allowed to bind, it is not
/// allowed to bind quietly. The measurement that should set them is a real
/// session's memory footprint, and it has not been taken.
#[derive(Debug, Clone, Copy)]
pub struct Cap {
    pub entries: usize,
    pub rows: usize,
}
crates/emma/src/term/transcript.rs — Cap, enforce_cap, dropped_marker

2,000 entries or 50,000 rendered rows. When the cap binds the dropped entries are gone entirely; what survives is two counters and a marker row rendered at the top of the buffer, naming the loss and the remedy. The marker is never removed, “because the fact that output is missing does not expire”, and it wraps rather than truncating. An earlier version cut it to one row, and what fell off the end at eighty columns was the path to the complete record, which is the whole remedy the row exists to carry. tested: the_marker_keeps_its_remedy_at_every_width runs at 24, 40, 60, 80 and 120 columns and also asserts height() equals total(), so the marker's measured height and its rendered height cannot disagree.

enforce_cap stops while self.entries.len() > 1 on the row half, so a single block taller than the whole budget survives: it is still the block the user is looking at. tested: the_row_budget_binds_without_emptying_the_buffer pushes a 400-character line into a two-row cap and asserts the buffer still holds it and reports nothing lost.

Two defects around the cap

set_width re-renders every entry and recomputes self.rows, but never calls enforce_cap. Narrowing the window multiplies rows, so the buffer sits above cap.rows until the next append. The row half of the cap is a ceiling checked on append rather than a ceiling. certified: set_width's body is eighteen lines and contains no call to enforce_cap.

dropped_rows accumulates gone.lines.len() at whatever width was current when each entry was dropped, and dropped_marker prints the running sum as one figure. After a resize that figure corresponds to no width the user ever had, in the one row whose job is to be accurate about loss. unverified as a visible symptom; the arithmetic is plain in enforce_cap. A test that drops entries at 120 columns, resizes to 40, drops more, and compares the marker's count against a re-render would settle it.

crates/emma/src/term/transcript.rs — set_width, enforce_cap, dropped_marker

Eager rendering, and the number behind it

The plan proposed rendering lazily from the tail on resize. That needs a height estimate for the entries nobody has rendered yet, “and an estimate that is ever wrong is a view that jumps under the reader.” Rendering everything is exact, keeps the row total the cap is enforced against always true, and is bounded by the cap itself.

“Cheap at transcript scale” was the plan's assertion, and the module turned it into a measurement rather than leaving it. a_full_buffer_rewraps_faster_than_a_frame builds 1,000 entries of a realistic mix and re-wraps 120 columns to 80. 

$ cargo test -p emma --lib \
    term::transcript::tests::a_full_buffer_rewraps_faster_than_a_frame -- --nocapture

rewrap: 1000 entries, 5000 rows, 21.1768ms

certified 2026-08-16 at 62ab9c3, debug build, Windows 11, and repeatable with the command above. That reproduces the module's recorded 21 ms debug figure exactly; its companion 3.5 ms release figure was not re-run for this page. unverified: the module extrapolates linearly to roughly 35 ms at the full 50,000-row cap, which would be two frames rather than none, and nobody has measured at the cap. Building 10,000 entries and timing one set_width would settle it.

The assertion's bound is a hundred milliseconds rather than sixteen, and the doc says why: “this runs on whatever machine CI has and a flaky timing test gets deleted, which would lose the measurement entirely.” The real number is printed on every run.

Defect: the whole buffer is cloned once per paint

visible_tagged calls tagged, which walks every entry and calls render::owned on every line, building a Vec<TaggedRow> of the entire buffer, and then truncates and drains it to the pane's window. chat::render calls it once per paint, and Frame::paint is called from the keyboard reader, from the clock thread twice a second, from every transcript write and from the middle of a streamed answer. At the default 50,000-row cap that is 50,000 line clones per frame to show about forty rows. The measured claim in this module covers resize cost, not per-frame assembly. unverified as a felt symptom: no measurement of the paint path exists. Timing visible_tagged at the cap, the way the resize test times set_width, would settle it.

crates/emma/src/term/transcript.rs — tagged, visible_tagged; crates/emma/src/term/chat.rs — render

One assembly, two readers

rows and visible are both cut from tagged, and the doc names what two assemblies would cost: “two assemblies of the same rows is how a label and the scroll arithmetic drift apart.” A TaggedRow carries its line and Option<(usize, Voice, bool)>: the block's index, its voice, and whether this row opens it. None is the cap marker and the blank separators, which belong to no block. tested: tagged_rows_are_the_same_rows_with_the_speaker_attached asserts the two assemblies produce identical text, that no separator was given to a block, and that each block's first row is flagged once with the right voice.

total() exists so the scroll bounds do not have to materialise the buffer to answer “how far can I scroll”. It sums self.rows, the separators, and marker_rows, which is measured by remeasure_marker whenever the marker could have changed rather than estimated: “an estimate that is ever wrong is a scroll bound that is wrong, and a scroll bound that is wrong is a row of the transcript nobody can reach.”

The pane that paints it

chat.rs holds no state, opens no terminal, and decides nothing about scrolling. It takes the visible window and places it. The whole file is five functions and 544 lines, most of them module doc and tests.

crates/emma/src/term/chat.rs · the columns

/// The speaker column: `Emma` plus breathing room, the widest label first.
pub const GUTTER: u16 = 7;

/// The message column is never squeezed below this to pay for the gutter.
///
/// 61 puts the collapse where the design's §9 puts it — a 70-column window
/// minus its border and the gutter — but stated in the pane's own
/// coordinates, because this module sees an area, not a window.
const MIN_MESSAGE: u16 = 61;

/// The gutter this pane will draw at this width. Zero when the pane cannot
/// afford one.
pub fn gutter(width: u16) -> u16 {
    if width >= GUTTER + MIN_MESSAGE {
        GUTTER
    } else {
        0
    }
}
crates/emma/src/term/chat.rs — GUTTER, MIN_MESSAGE, gutter, message_width

Which voices get a label is the file's main judgement, and each arm has an argument. You and Emma get one. Tool traffic does not, because “an Emma label beside ✗ Bash failed would claim the failure as prose”, and the ◆ ✓ ✗ ⊘ ⊗ vocabulary already says what each line is at every fidelity. Notes, warnings, endings and the welcome get the same treatment, as the harness talking about itself. The approval panel is not here at all: it is fixed chrome, precisely so no amount of transcript can move it.

The label rides the block's first visible row rather than its first row, so a long answer scrolled halfway off the top still says who is speaking. One rule covers both cases, “so the cut case cannot be the untested one.” tested: a_block_cut_at_the_top_keeps_its_speaker streams thirty paragraphs, scrolls up ten rows, and asserts the pane's top row is a middle paragraph and that the gutter beside it says Emma.

The gutter is in tension with markdown.rs's refusal to insert anything into copied text, and the module resolves it rather than ignoring it: native selection over a cell grid already interleaves sidebar columns, borders and gutter into every line, “so per-line purity is gone before this module draws anything, and /export is the honest copy path.” Given that, the gutter contains only spaces and, on a first visible row, the speaker's name: no rail, no vertical bar, no glyph.

The scroll indicator is one dim right-aligned overlay on the pane's last row: ↓ N rows below · End. It uses Transcript::behind, which takes the pane height because “the offset alone over-reports at the top of a short buffer… An indicator that promises rows the End key does not produce is a readout that lies.” tested: the_indicator_appears_only_behind_the_tail_and_names_the_count, and a sibling for the ASCII arrow.

Defect: the indicator can be cut without saying so

indicator computes width = cols(&text).min(usize::from(area.width)) and calls buf.set_stringn, which truncates with no ellipsis. On a pane narrower than  ↓ 12 rows below · End , about twenty-four columns, the row is silently cut against the standing rule that a cut says it was cut. The two indicator tests both run at eighty columns. unverified: a render at width 16 with a scrolled buffer would settle it.

crates/emma/src/term/chat.rs — indicator

The pane clamps rather than wrapping. render intersects the area with the buffer first, “a caller handing an area that leaks past the buffer would turn every set below into a panic”, and then buf.set_line(area.x + gutter, y, &row.line, area.width - gutter) guarantees nothing paints past the pane whatever width the transcript happened to be wrapped at. tested: nothing_paints_outside_the_pane wraps at 200, far wider than the pane, and paints into a 30-column sub-rectangle of a 60-column buffer, then checks every cell outside it.

Coverage

Both files were read in full. transcript.rs is 1,117 lines and declares 30 function items above the test boundary: EntryKind::voice, Entry::render, is_blank, Cap::default, and 26 Transcript methods. All 30 are named on this page: 30 of 30. chat.rs is 544 lines and 5 functions, gutter, message_width, render, label, indicator: 5 of 5. Eleven of the transcript's twenty tests and six of the pane's eleven are cited by name; the rest are the wrapping cases (three), the streaming cases (three) and the pane's colour and ASCII degradation checks.

Not settled here. Everything above reads a Vec<Line> or a Buffer. Whether the buffer feels like scrollback, whether the wheel at three rows a notch is the right speed, and whether a scrolled reader can find their place again are questions no test in this repository asks. unverified: a long real session, scrolled by every bound key and by the wheel, in each target terminal.
