Four of the six tools in tools/fs. Three of them declare read_only: true and run without a prompt, and the fourth is the one that refuses to work blind. Edit and Bash have pages of their own.

One spelling for every malformed call

Every argument in the crate goes through a private args module, so the model learns the shape of one error message and can then read all of them. Six extractors, all pure, all callable from validate_args before any filesystem is touched.

Two conventions run through the file. An explicit JSON null is treated as absent rather than as a wrong type, because that is what a model emits when it means "not this time". And a float in an integer slot is refused with its own sentence, because a float there means the model computed the value rather than stating it.

Any of the three sets the flag, and render states each one that fired rather than merging them, because "truncated" alone does not tell the model whether to page forward, narrow the range, or stop expecting the rest of a line. tools/fs/src/read.rs — render

A caller that passed limit can raise its own number; a caller that passed none has met the fixed ceiling and would learn nothing from raising anything. Both are told to page, which is the remedy that works either way. last advances only for a line that was actually emitted, so a line counted but dropped by the byte cap cannot make the continuation offset skip a line the model never saw.

A clipped line gets a marker, not a hash

fn clip(line: &str, max_chars: usize) -> (String, bool) {
    let mut chars = line.chars();
    let head: String = chars.by_ref().take(max_chars).collect();
    if chars.next().is_none() {
        (head, false)
    } else {
        (format!("{head} … [line clipped]"), true)
    }
}

Taken in chars so a multi-byte character is never cut in half. The peek at the next character is what distinguishes a line of exactly 2000 from one that was clipped: taking and comparing lengths would call the first one truncated and set the flag that stops Write from working. The clipped line's label slot gets #---- rather than a hash, and Edit refuses that marker by name, because the model has seen the front of that line and not its end.

The recorded line hashes are the window that was rendered and nothing more, so an addressed Edit reaching into lines 101-onwards after a read of 1-100 is refused for want of a record. That is the same "you have not seen this" rule as the completeness flag, at line resolution instead of file resolution.

The read tracker, which is what makes the next refusal mean something

ReadTracker is a Mutex<HashMap<(String, PathBuf), Sighting>>, keyed by session so a resumed process cannot inherit an earlier session's claim. A sighting holds a stamp, a completeness flag, and the hashes of the lines that were shown. 

/// Whether a path may be written without the write being blind.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ReadState {
    /// Never read in this session.
    Never,
    /// Read, but the file has changed since — the agent's picture is stale.
    Stale,
    /// Read, but the read was truncated, so most of the file is still unseen.
    Partial,
    /// Read in full, and unchanged since.
    Fresh,
}

The arm order in state is a priority order and it is commented as one: a file read only in part and changed since reports Stale, because re-reading fixes both, whereas being told "you only saw part of it" would send the model to Edit against text that may no longer be there.

tools/fs/src/session.rs — ReadState, ReadTracker::state

The stamp is length, mtime, and a hash of the content. content is the one that makes this a check rather than a formality: length and mtime alone are forgeable by accident, because a formatter that rewrites a file to the same byte length inside one filesystem tick produces an identical (len, mtime) pair, and Write then overwrote the other edit believing the file was untouched. No adversary required. It is FNV-1a over the whole file — the hash hashline already uses for Edit's line anchors, cheap enough to run on a file Read was going to load anyway — and None when the file was never read, because a Write to a path nobody opened has no content to remember.

An independent review rated the same-tick collision unlikely on NTFS specifically, where mtime resolution is 100ns. That is a reason to call this a lost-update risk rather than a certainty, and it is not a reason to keep a check that cannot see the change it is checking for.

A missing file stamps as zero-length with no mtime, which is deliberate: two consecutive stats of a file that does not exist agree, so "read a file that is not there, then create it" is not reported as a stale clobber. forget exists and nothing calls it, which its own doc says plainly rather than describing it as though it were wired up; there is no delete or move tool yet.

tools/fs/src/write.rs — Write::run

The write itself is a rename, and the temp name is not guessable

Write and both Edit paths used std::fs::write, which truncates and then streams — so a crash mid-write left somebody's source empty or partial. They now build a complete sibling and rename it over the target, which is the pattern tools/tasks had used since it was written, one crate away.

The first version of this fix lost data in a new way

The sibling was named <target>.emma-tmp, deterministically. So a user who happened to own config.toml.emma-tmp had it truncated and then renamed away by a write to config.toml — a function whose entire purpose is not losing a file, losing one. Two more in the same twenty lines: concurrent writes to one target raced through the same temp path, so a caller could be told its content was written when the other call's content landed; and the temp file took the process umask, so renaming it over a 0600 file widened it to 0644.

The name now carries the process id and a counter — the counter makes two writes in one process distinct, the pid makes two processes distinct, and neither is enough alone — and on unix the target's permissions are copied onto the temp before the rename. None of the three was found by the commit message, the test, the mutation, or reading it again; all three came from a second reader told to attack rather than confirm. certified against the real filesystem for the reserved-name case below; unverified for the permission arm, which is #[cfg(unix)] and has never run here. What would settle it: the suite on any unix host.

And it breaks a hard link, which is the price of the fix

A rename replaces the directory entry rather than writing through it. That is what makes the write atomic, and it is also what severs a hard link: the edited name gets the new content, every other name keeps the old, and the link count drops to one on each. A plain fs::write — what this did before — writes through the inode, so both names change together. certified on this machine's NTFS by probe, both halves: plain write, both names change, count stays 2; temp-and-rename, one name changes, count drops to 1.

This is not an argument for going back. Most editors do the same thing, and a torn file after a crash is worse than a broken link. It is a real consequence that the commit which introduced it did not mention, and somebody who hard-links a config into two places and edits it through Emma would otherwise get silent divergence.

So the outcome says it, and does not refuse: “this file had 2 names on disk (hard links); writing it replaces the directory entry, so the other name keeps the old content and the link is broken”. The count is read before the write, because after the rename it is one and the fact is gone. tested write_says_when_it_has_just_broken_a_hard_link creates a real link and asserts both the sentence and the severance — a note describing something the write did not do would be its own defect, and the sentence alone cannot tell the two apart. an_ordinary_write_says_nothing_about_links is the other half: a note that fires on every file is noise, which is the same as not having one. Mutation: raising the threshold above any real count turns both link tests red and leaves the ordinary one green.

Getting the count on Windows needs an open handle — GetFileInformationByHandle. std wraps exactly that in MetadataExt::number_of_links and keeps it behind the unstable windows_by_handle feature, so path::hard_links makes the call itself; unix reads nlink off the stat it already has. None from that function means could not be told, never one name, and nothing prints a 1 for it.

A Windows reserved device name (NUL, CON, COM1) or a name ending in a dot or a space gets a warning note on the outcome. Emma's root is a verbatim path, which is what makes those real files here rather than the devices they would otherwise be — a blind audit refuted the data-loss claim originally filed against this, and the warning is what survived it: the file is real, and it is a file most other tools on the system will not be able to open.

Creating a file that does not exist needs no prior read; there is nothing to lose, and requiring a read of a missing file would be a rule that only ever produces confusion. Existence is checked with symlink_metadata, so a dangling symlink counts as something that exists and the read requirement applies to it. A path naming a directory is BadArguments: {raw} is a directory.

Nothing before the refusal touches the filesystem, not even create_dir_all, which is what makes a refusal actually a refusal. The parents are created after the check and unconditionally, which is safe because target is already contained, so every directory made is inside the root by construction.

After a successful write the tracker records the file as complete with the hashes of what was just authored, because the agent produced every byte. That is what lets Write then Edit proceed without a Read in between. Write declares idempotent: true: the same bytes twice leave the same file, and the mtime moves, which nothing here consults.

Glob

pattern (required), matched against paths relative to the search root, and an optional path directory that must be a directory or the call is {p} is not a directory. A malformed pattern is refused in validate_args, before anything is walked: {pattern} is not a valid glob: {e}. The compiler is shared with Grep's glob filter, so the two cannot come to disagree about what ** means.

Matching nothing succeeds with an empty list. "There are no .proto files here" is a fact about the repository and often the exact fact being checked.

Results come back modification-time descending with the path as the tiebreak, so two calls over an unchanged tree return identical bytes. The determinism is not cosmetic: the output rides in the conversation, the conversation rides in the cached prefix, and a set that reordered between calls would move prefix bytes for no reason. The tiebreak is what supplies it, because mtime alone leaves files written in the same instant free to swap places.

One traversal so that "what does Emma consider part of the tree" has a single answer. Two walkers drift, and the day they disagree is the day Grep finds a file Glob swears does not exist.

MAX_VISITED is 200,000 and counts entries the walker yielded, directories and unreadable entries included, because the traversal is what costs. Counting only returned files would let a tree of a million empty directories run unbounded while the counter stayed at zero. An unreadable subdirectory is skipped rather than failing the call, so a single permission bit cannot hide a whole tree of results.

No hits is a successful search, and that is why this tool exists alongside Bash. rg pattern . through a shell answers "no matches" with exit code 1, and telling "no matches" from "ripgrep is not installed" then becomes a matter of parsing stderr. Here they are structurally different outcomes.

Candidates are sorted by path rather than by mtime as Glob's are, because a grep result is read as a list of places and neighbouring files sitting together is worth more than recency. Either way it has to be deterministic, for the same cached-prefix reason.

Known rough edge, flagged in the source

The glob filter matches against the path relative to the search base. When path names a single file that relative path is empty, so passing path and glob together for one file matches nothing. Naming one file and then filtering the set of one is a redundant call, which is why it has not bitten. It is still an asymmetry rather than a rule.
