The status bar

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Run control Copying out

One row, and it inherits the inline row's one law: everything on it is true. A field whose value was never measured is absent rather than zero, and a row that runs out of room drops whole cells in a stated order rather than cutting a number in half. Beside it, statusline.rs lets a configured program take that row instead, translating its bytes into styles rather than letting them through.

Two kinds of number, drawn as different pictures

ctx_* is a snapshot: how full the context window is right now, and it rises and falls. total_* is an accumulation: what the goal has been billed for, and it only rises. The inline row put both on screen as used/cap pairs and the owner read them as inverted, because a total is usually larger than a level and two identically-shaped numbers invite comparison.

The inline row answered with a rename, spend to total. This row goes further: the snapshot is a percentage and a meter, the shape of a level, and the accumulation is raw grouped counts, the shape of a bill. “Two different pictures cannot be read as each other's inverse.”

tested: the_snapshot_and_the_accumulation_have_different_shapes pins it as shape rather than as literals. It slices the rendered row at the vertical rules and asserts the context cell contains no / and the tokens cell no %. That is what must not regress. The label itself was free to become TOKENS once shape carried the guard, which is what the mockup says and what the owner asked for after measuring the built bar against the image.

The drop order, as a ladder

compose walks eleven steps and returns the first that fits. Each is strictly poorer than the one before, so what survives at any width is a statement of priority.

crates/emma/src/term/statusbar.rs · compose and its ladder

/// 1. the env value is shortened (a name may be fitted; a number never is)
/// 2. the help hints go (they are the only cell that is not a measurement)
/// 3. the ↑/↓ split goes (the TOKENS figure it details survives)
/// 4. the meter shrinks to five segments (still a proportion)
/// 5. the env cell goes whole
/// 6. the tokens cell goes whole (a fact to know; the level is a decision to
///    make)
/// 7. the meter goes, keeping the percentage
/// 8. the mode cell goes, clock and all
/// 9. the context label goes, keeping the bare percentage — last thing
///    standing, because running out of context forces the next action
/// 10. nothing: an empty row rather than a cut number
fn compose(width: u16, bar: &Bar, skin: &Skin) -> Line<'static> {
    for step in 0..=10 {
        if let Some(line) = attempt(step, width, bar, skin) {
            return line;
        }
    }
    unreachable!("the last step always fits: it is empty")
}
crates/emma/src/term/statusbar.rs — compose, attempt

Read that list downward and you have the priority. Everything above step 9 can go, and the bare context percentage stays, because that is the number that forces your next move.

A cell's separator is part of the cell for this purpose, so when a cell goes its rule goes with it and the rules can never be what pushes a row over its width.

tested, and both tests are properties rather than thresholds. what_survives_at_any_width_respects_the_order walks widths 0 to 220 and asserts six implications of the form “if this poorer thing survived, this richer thing survived too”, so a reordering of the ladder breaks one of them at some width whatever the exact thresholds are. no_width_overflows_the_row_or_cuts_a_number walks the same range and asserts both that the composed width never exceeds the row and that wherever a cell's marker appears, its number appears whole.

That second test is also the proof that the two width computations agree. row_width and layout each compute the help cell's fixed cost, and the comment says what a disagreement would do: “the env-room arithmetic hands out columns the layout will refuse, and some width overflows. The property test walks every width precisely to catch that drift.”

Which counter belongs to the goal and which to the session

Status holds five numbers and exactly one of them is goal-scoped. spend is the running goal's weighted bill against Budgets::max_tokens, the budget that ends the goal; it only rises within a goal and starts empty at the next one, because a budget nothing is measured against is not a budget. It is the pair the inline row draws as total used/cap, and it is the same number agent.rs tests the goal against, so widening it to the session would mean moving that accounting too.

up, down and session_tokens are the session's, and they survive goal_started. The first two are the provider's raw input_tokens and output_tokens summed across every call this process has made, which is why they are bare i64: a session that has not called yet has measured zero traffic, and zero is a fact rather than a guess about a cap. They are uncached, so up + down is traffic charged at full price and is not expected to equal session_tokens, which is weighted the way spend is.

session_tokens has no cap in its cell because there is no session budget for it to be a proportion of, it never falls, and no goal boundary clears it. /clear keeps it, along with the session id and the transcript that command already says it keeps, because clearing a conversation does not unspend what the conversation cost. Only a fresh process starts it at zero.

Both scopes come out of one number. Frame::spent hands record_spend the goal's running total, and goal_started folds the goal that just ended into session_base before dropping its meter, so the next goal counts from there.

Zeroing the arrows and the session total on submit was the owner-visible bug of 2026-08-26, and it was the second time this scoping had been wrong: the bar was reading one goal while the owner read it as the session's running story. The argument that put them there was right about the cell (the split does sit beside the total) and wrong about the scope, because that cell is the session's. tested: a_new_goal_never_clears_the_sessions_token_counts, only_a_fresh_process_starts_the_session_counts_at_zero and the_goal_meter_still_starts_each_goal_empty, which together hold both halves: the session's three survive a goal boundary and spend clears. Making goal_started zero the session input fails with session input survives a new goal, left: 0, right: 8128.

Absence, encoded three ways

Bar's counts are bare i64 because that is the shared contract with the shell, so absence is encoded in the values: a cap that is not positive is no cap, so no percentage or meter is drawn against it, and a cell with neither a positive count nor a positive cap does not appear at all. up, down and elapsed keep a type that can say unknown: None is unknown, Some(0) is a measured zero, and the two render differently because they are different facts.

A negative count is treated as absent rather than clamped, and the comment gives the reason in one clause: “a clamped zero would claim a measured zero.” tested: an_unknown_count_is_absent_and_a_measured_zero_is_zero checks all three cases in one test.

A label is never drawn over an empty value. “The mockup's MODE and ENV are placeholder content, and rendering their labels regardless would be the bar pretending Emma has features it does not.”

MODE stopped being placeholder content on 2026-09-06. An idle bar draws approval::current_mode_label(), which is ASSIST, AUTO or PLAN: the posture the session is in, read at draw time rather than at startup, so /mode plan changes the word without a redraw of anything else. A running goal still says WORKING, because a working state is what the cell says while there is one. The word is the posture's and not the gate's, and after /mode the two say different things: a run started with --dangerously-skip-permissions says AUTO, and the same run put into plan says PLAN while the gate it started with has not moved. tested: the_status_label_is_assist_until_a_run_says_otherwise goes red when the label is computed from the gate instead of the mode. unverified Nobody has read the cell off a real console since the word changed, and the widths moved: ASK (3) became ASSIST (6), and UNATTENDED (10) became AUTO (4). The longest label got shorter, so an overrun is unlikely rather than ruled out. An 80-column and a 60-column terminal with a goal running settles it.

The meter's arithmetic errs in one direction

crates/emma/src/term/statusbar.rs · percent, filled

fn percent(used: i64, cap: i64) -> i64 {
    let used = used.max(0);
    // Manual ceiling: `i64::div_ceil` is unstable on this toolchain, and both
    // operands are non-negative with a positive divisor, where this form is
    // exact.
    let p = (used * 100 + cap - 1) / cap;
    if used < cap {
        p.min(99)
    } else {
        p
    }
}

/// Filled segments: a partial segment rounds up — so anything used shows as at
/// least one — but the last segment fills only at the cap. Floor would do the
/// opposite: at 99% it shows nine of ten and offers a segment of room that
/// does not exist.
fn filled(used: i64, cap: i64, segments: usize) -> usize {
    let used = used.max(0);
    if used >= cap {
        return segments;
    }
    let f = ((used * segments as i64 + cap - 1) / cap) as usize;
    f.min(segments - 1)
}
crates/emma/src/term/statusbar.rs — the meter's arithmetic region

Both roundings may overstate what is used and never what is left, and the region comment prices the asymmetry: “A meter that reads full at 99% panics nobody into anything worse than an early compaction; a meter that shows a free segment at the cap invites one more call that the budget machinery then eats. Overstating room is the lie that costs money, so it is the one this arithmetic cannot produce.” Past the cap the real figure shows, because a level over its cap is a fact you should see. tested at the edges, and by two property tests: the_meter_never_reads_full_below_the_cap and anything_used_fills_at_least_one_segment.

The filled glyph is ▊, the left three-quarters block, rather than █. Ten adjacent full blocks fuse into one solid bar and the proportion stops being countable, which was the owner's “separators between the segments” report. The three-quarters glyph buys the gap without spending an extra column, and it matches the image, where each meter block inks about 7px of a 9.3px cell. The empty glyph is ░ rather than a grey block, a deviation from the mockup: filled and empty must differ by shape, not colour alone, “or the meter dies at Level::None. The mock was never run on a colourless terminal.” tested: the_filled_segments_stay_individually_countable goes red if █ ever returns.

Defect, unreachable today: filled underflows at zero segments

f.min(segments - 1) on a usize panics when segments is zero. context_cell guards it with if segments > 0, and the ladder only ever passes 10, 5 or 0, so nothing reaches it today. It is named because the same file's tests argue the opposite standard for a sibling helper: group is tested on negative input with the comment “a helper that panics or garbles on an input it ‘never gets’ is a trap for the next caller.” certified: read filled's last line and context_cell's guard.

The rules, and where the slack goes

The mockup divides the bar with vertical rules at every cell boundary, including the help cell's, because “right-aligned hints with only air before them read as loose text, not as a divided bar.” The row's slack is spread evenly across the gaps rather than piled up in front of the hints, and the extra columns split around the glyph so the rule stays near the middle of its gap.

Without a help cell nothing anchors the right edge, so the row stays left-packed at minimum gaps: “trailing background is invisible, widened gaps between survivors are not.” With nothing measured at all there is no rule, because a divider needs two sides. tested: every_cell_boundary_carries_a_rule_and_the_slack_is_shared counts four rules for four cells plus help, and asserts the largest gap exceeds the smallest by at most one, so no gap can hoard the leftover width. a_dropped_cell_takes_its_rule_with_it holds the other end.

Two other numbers earn a sentence each. SEGMENTS_FULL is 10, though the image shows eleven blocks; the doc calls that “the mock's artist losing count, not a specification.” ENV_MIN is 6, below which the env value is dropped whole rather than fitted: “clau… still identifies a model, cl… identifies nothing.” The env cell is the only one whose value may be shortened, because it is a name, and “a fitted name still identifies, a fitted number misleads.”

group writes 12,842 rather than 12k, and the region comment says why it does not match render.rs's human: the inline row shared one line with everything else and had to abbreviate; this bar drops whole cells instead, “so abbreviation here would be precision surrendered with nothing bought.” clock is a knowing four-line duplicate of render.rs's, kept local because that file was under concurrent edit, and pinned to the same outputs by both test suites so the two cannot drift.

The cell that the prose got wrong three times

The ↑/↓ parenthetical inside the TOKENS cell was described wrongly in the design note repeatedly, so the styles are pinned span by span from the image instead. The up arrow and its figure are one green span, one space apart. Two spaces separate the up figure from the down arrow. The down arrow is accent and its figure is plain foreground, “the image is unambiguous (the digits sample neutral grey-white, the arrow pink), and the doc's ‘↓ in accent’ describes only the arrow. Painting the figure accent was this cell's third prose-derived error.” tested: the_down_arrow_is_accent_but_its_figure_is_foreground asserts three spans by content and by style.

Cell labels are accent and bold, not grey. The prose description said grey; the picture says accent, and the file's rule is that the picture wins. Bold so the label still stands apart at Level::None. Two spaces separate every label from its value, measured off the image's character grid.

The ASCII set is a second vocabulary chosen off the skin's rather than added to it, and the two sets are told apart by skin.glyphs == ASCII, which works because Glyphs derives PartialEq. It wraps the meter in [ ] “so a run of # and - still reads as a gauge rather than as punctuation”; the block glyphs need no frame. tested: the_ascii_meter_is_a_bracketed_gauge asserts [#######---] and that no Unicode-only glyph survives.

Somebody else's program in the same row

statusline.rs owns the two things the terminal is responsible for when a status program is configured: keeping it off the paint path, and turning its bytes into cells.

Running it can never be part of drawing

Frame::paint is called from the keyboard reader, from the clock thread, from every transcript write and from the middle of a streamed answer. If any of those could wait on a subprocess, a status script that blocks becomes “a terminal that has stopped echoing what the user types.” So paint reads a value and never produces one: it copies whatever string is in View::custom_status and returns.

Producing it is a task fed by a one-slot channel. Sending is try_send and a full channel is dropped on the floor, which is the coalescing: while a run is in flight, every trigger that arrives collapses onto the request already queued. The debounce is 300ms, Claude Code's number, “for the same reason: a burst of assistant messages should cost one invocation, not eight.” After the sleep the loop drains the channel and keeps the newest payload.

The Weak<Frame> is upgraded per iteration rather than held, “so a frame torn down mid-sleep ends this task at the next turn of the loop.” A failure message is spoken once per distinct message through note_once, so a script broken on every invocation says so once rather than five times a second.

A timeout that was not a timeout

Until 2026-08-14 the “timed out” message also caught a program that had exited in milliseconds but had started something which inherited its stdout: the supervisor was waiting for the pipe to close rather than for the program to exit, so the row said statusLine timed out after 2000ms on every debounced repaint of a script that had answered every time. The fix is in emma_harness::hooks::exec, and nothing in this file changed, “which is the argument for the status line reusing that supervisor rather than owning one.”

crates/emma/src/term/statusline.rs module doc

Only the first non-empty line is taken. Claude Code renders every printed line as its own row; Emma cannot, because the inline viewport's height is fixed at install and “a status line that could claim two rows would be a viewport that resizes under a running program. That is the class of bug that ate the last two attempts at this file.” The limit is stated here rather than left for you to discover when your two-line script silently loses its second line. tested: a_program_that_prints_several_lines_yields_the_first_of_them, including that a program printing nothing yields None and so leaves the built-in row alone.

Bytes are parsed rather than printed

Claude Code honours ANSI colour in a status script's stdout by letting the bytes through. Emma cannot, because these bytes go into a ratatui cell buffer: “an escape byte written into a cell is a byte ratatui counts as one column and the terminal counts as none, and from that moment the diff is wrong about every row below it.”

crates/emma/src/term/statusline.rs · consume_escape

fn consume_escape(chars: &mut std::iter::Peekable<std::str::Chars<'_>>) -> Option<Vec<i64>> {
    match chars.next() {
        // CSI: parameters, then one final byte in `@`–`~`.
        Some('[') => {
            let mut params = String::new();
            for c in chars.by_ref() {
                if ('\x40'..='\x7e').contains(&c) {
                    return (c == 'm').then(|| parse_params(&params));
                }
                params.push(c);
            }
            None
        }
        // OSC: runs to a BEL or an ST (`ESC \`). This is where a hyperlink
        // lives, and where an unterminated one would otherwise eat the line.
        Some(']') => {
            while let Some(c) = chars.next() {
                if c == '\x07' {
                    break;
                }
                if c == '\x1b' && chars.peek() == Some(&'\\') {
                    chars.next();
                    break;
                }
            }
            None
        }
        // Anything else is a two-byte sequence, already consumed.
        _ => None,
    }
}
crates/emma/src/term/statusline.rs — to_line, consume_escape, apply_sgr

The iterator is left just past the sequence either way, “which is what makes ‘no escape byte survives’ true rather than approximate: an unrecognised sequence is consumed and discarded, never emitted a character at a time.” A status script emitting an OSC 8 hyperlink gets its text and not its link, which is a feature not arriving. The same sequence in the raw buffer would be a corrupted frame.

apply_sgr understands bold, dim, italic, underline, reversed and their offs, the sixteen named colours in both ranges, both extended forms, and the two resets. 0 returns to base, the palette's own idea of a status row, rather than to the terminal's raw default, “otherwise \033[0m halfway through a script's output would drop the row onto whatever colours the user's shell happens to have.” Unknown parameters are ignored rather than guessed at.

tested: no_escape_byte_or_control_character_ever_reaches_a_cell runs ten hostile inputs including an OSC 8 hyperlink, an ST-terminated OSC, a truncated escape, raw control bytes, and \x1b[2;20r, the scroll-region sequence this project's own scrollback defect was made of. The doc says why it is one test over everything rather than one per case: “the property is universal and a per-case test passes the moment somebody adds a sequence nobody thought of.” A sibling asserts the text around a dropped sequence survives, “otherwise the safe thing would be to render nothing, which is not a status line.”

Defect: the ITU-T subparameter form parses to the wrong colour

parse_params splits on ; and : alike, so 38:2::250:189:47 becomes [38, 2, 0, 250, 189, 47], because the empty colour-space field parses as zero. extended then reads (rest[1], rest[2], rest[3]) as (0, 250, 189), a visibly wrong colour, and consumes four parameters leaving 47 to be read as an unknown SGR. No escape byte survives either way, so this is a wrong answer rather than a leak. Accepting : at all is what makes the subparameter form parse instead of being dropped, so the fix is to treat a colon-separated run differently rather than to stop splitting on it. unverified: reasoned from parse_params and extended, not reproduced. A status script emitting \x1b[38:2::250:189:47m, or a test asserting the resulting Color::Rgb, would settle it.

What Emma says about itself

payload builds the stdin document, and every field is a measurement or a fact. Emma has one name for a model and no prettier one to offer, so id and display_name both carry it, “a script reading display_name, which is what every published example reads, gets something real.” Emma does not change directory mid-session and has no /add-dir, so current_dir and project_dir are the same and added_dirs is empty. exceeds_200k_tokens is fixed at 200k regardless of the actual window, and copying Claude Code is the point: “a script branching on it here must branch the same way it does there.”

A program that answers replaces the built-in line entirely. Anything it does not print is gone. tested from view.rs: a_configured_status_line_takes_the_last_row_and_the_builtin_one_goes asserts no fragment of the built-in survives anywhere, and nothing_a_status_program_prints_can_write_an_escape_into_the_viewport proves the translator is actually on the render path rather than merely correct in isolation.

Coverage

Both files were read in full. statusbar.rs was 1,144 lines when this page was written; it is unverified 1,171 lines now (wc -l, 2026-09-06), and the function list below was not re-walked against the 27-line difference. It declares 18 function items: render, bar_glyphs, compose, attempt, layout, sep_width, row_width, label, three cell builders, env_value, help_cell, percent, filled, meter, group, clock. All 18 are named here: 18 of 18, along with its three constants and both types. Fourteen of its twenty-one tests are cited.

statusline.rs is 574 lines and 11 function items: spawn, note_once, first_line, payload, to_line, consume_escape, parse_params, apply_sgr, basic, extended, clamp. All 11 named: 11 of 11. Five of its seven tests are cited.

Not settled here. Nobody has configured a status program and watched the row. The translator is proven against strings and the scheduling is proven by construction, but the whole feature is unverified end to end: a script that prints a coloured branch name, configured in settings, run against a live session, with the debounce watched under a fast turn.
