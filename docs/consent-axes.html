The two axes a tool declares

Before a call runs, the gate reads two booleans off the tool and asks the tool where the call is going. It believes all three answers. Nothing in this chapter stops a tool from opening a socket after declaring it would not.

crates/tool-api/src/lib.rs — ToolMeta, Tool::network_target
What a declaration is worth

read_only and reaches_network are fields on a struct the tool fills in itself. The gate has no way to check either one. Bash declares read_only: false and reaches_network: false, and a Bash call can run curl. What the gate produces in that case is that a human read the command first, not that the command could not reach the network.

crates/tool-api/src/lib.rs — ToolMeta::reaches_network, final bullet

ToolMeta, and why one bit was split into two

read_only asks a single question: can this call change local state, meaning a file written or a process spawned. It was once documented as also meaning "cannot reach the network", and that reading was never true of the tools as they were written. WebFetch and WebSearch declare read_only: true, because neither can damage this machine, and both are how bytes leave it.

crates/tool-api/src/lib.rs — ToolMeta::read_only 
/// Cannot change local state: no file written, no process spawned.
pub read_only: bool,
/// Sends bytes off this machine, by construction.
pub reaches_network: bool,
crates/tool-api/src/lib.rs — ToolMeta (field declarations, doc abridged)

The two axes are separate because they are separate risks. A write is something the model chooses to do. Egress is how a prompt-injected page turns a read tool into an exfiltration channel: a model that reads an attacker's page and then "searches" for the contents of a .env has written nothing, damaged nothing, and passes every local-damage check on the way out.

crates/tool-api/src/lib.rs — ToolMeta::reaches_network

Flipping the web tools to read_only: false was the obvious alternative and was refused. A gate that fires on every page read teaches the operator to answer without reading, and that habit carries into Write prompts that can authorise file changes. The second axis costs one prompt per host instead of one per page.

ToolMeta has no Default

Adding a field to ToolMeta breaks every construction site in the workspace, and each tool has to state the new bit. The predecessor project added a defaulted field, which granted a safety property to every tool written afterwards without anybody choosing it for that tool.

The gate does not parse a tool's arguments

To learn where a call is going, the gate calls Tool::network_target(args) and the tool answers. The default implementation on the trait returns None, so a tool that reaches nothing implements nothing. 

fn network_target(&self, _args: &serde_json::Value) -> Option<NetworkTarget> {
    None
}
crates/tool-api/src/lib.rs — Tool::network_target, default body

A NetworkTarget is a host plus one line naming the errand. The host is what a grant is keyed on. The detail is what makes the prompt readable: a host name alone cannot distinguish a search for a crate name from a search for the contents of a file. 

pub struct NetworkTarget {
    /// The host bytes leave for, lowercased and without a trailing dot.
    pub host: String,
    /// One line naming the errand, for the human reading the prompt — the URL,
    /// the query.
    pub detail: String,
}
crates/tool-api/src/lib.rs — NetworkTarget (docs abridged)

NetworkTarget::new normalises the host as trim, then strip trailing dots, then to_ascii_lowercase. Docs.RS. and docs.rs are therefore one grant. docs.rs and www.docs.rs are two, because deciding they are the same is a policy nobody asked for. The rule matcher in permissions.rs applies the same three steps to a host handed to it, so a second caller cannot inherit a hole from the first. See Matching a host.

crates/tool-api/src/lib.rs — NetworkTarget::new; crates/emma/src/permissions.rs — normalise

The asymmetry is the reason this method exists on the tool rather than in the gate: approval.rs knows that some tools reach some host, and knows nothing about how any of them spell it. Twice before, this loop acquired knowledge of one tool's argument shape, and both times "adding a tool is a crate plus one registry line" stopped being true.

crates/emma/src/approval.rs — Approvals::request

Where the two axes are read

request is the only public entry point, and the only place network_target is called. It takes the &dyn Tool rather than a name and a boolean, so both axes and the destination are read off the tool that is about to run. A caller passing its own idea of whether something writes would be the gate protecting a claim instead of a fact. 

pub async fn request(&self, tool: &dyn Tool, args: &Value, term: &Term) -> Verdict {
    // **Guarded for the same reason `validate_args` is**: this is a tool's
    // own code reading model-written JSON, and a panic here took the
    // session down while `DEF-007` claimed the class was closed. Denying is
    // the safe answer -- a tool that cannot say where it would connect is a
    // tool nobody can approve.
    let Ok(target) =
        std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| tool.network_target(args)))
    else {
        return Verdict::Deny(
            Decider::Unevaluable,
            format!(
                "{} panicked when asked where it would connect, so it was not run. That is \
                 a bug in the tool; nothing about the call can be approved on its word.",
                tool.name()
            ),
        );
    };
    let verdict = self
        .decide(tool.name(), tool.meta(), target, args, term)
        .await;
    self.seen
        .lock()
        .await
        .push((tool.name().to_string(), verdict.clone()));
    verdict
}
crates/emma/src/approval.rs — Approvals::request

Every verdict is pushed onto seen, readable through Approvals::decisions. No caller in the workspace calls decisions, so the field is write-only today; the record a run depends on is the session log, which the loop writes on every denial and every call it lets through. The comment on the field says so.

crates/emma/src/approval.rs — Approvals::seen, Approvals::decisions

What the egress axis does not cover

  • What comes back. An approved host is a destination the user chose, not a source they trust. The page that arrives is attacker-controlled text entering the model's context, and nothing in the gate reads it.
  • Incidental network access. Bash declares false and can curl. It is gated by the local question instead, which shows a human the command, and a command carries more information than a host name. Declaring true would demand a destination Bash cannot name without parsing shell.
  • Enforcement of any kind. Both bits are declarations. What keeps them true is the tool crates' own tests, not this file.

What is not settled here

certified The tests do not pin every declaration. Skill is registered as a tool and declares read_only: true, but its module contains no test: 

rg -n 'read_only: true' crates/emma/src/skill.rs
71:            read_only: true,

rg -n '#\[cfg\(test\)\]|#\[test\]|tokio::test' crates/emma/src/skill.rs
# exit 1; no output

This refutes the page's former claim that each declaration has a test which fails when its bit is flipped. The network tools and the other read-only tools have declaration tests, but Skill's bit can drift without a tool-local test noticing.
