Permission rules, scopes and merging

A rule is Tool or Tool(specifier), in Claude Code's JSON shape, read from up to three files and merged into one set of three lists. Which list a match lands in is the whole of the answer; how specific the rule was does not enter into it.

crates/emma/src/permissions.rs — Rule, Rules; crates/harness/src/lib.rs — PermissionBlock

The format, and why it is somebody else's

The block is permissions: { allow: [], deny: [], ask: [] }. An existing .claude/settings.json works here, and a rule Emma writes is a rule the other program understands. Emma's own .emma/config.json spine accepts the same block under the same names; a block that had to be re-typed to move between the two directories would defeat the reason it is read at all.

crates/emma/src/permissions.rs — module doc; crates/harness/src/lib.rs — PermissionBlock

Persistent rules were once refused outright. approval.rs carried a section arguing there must be no persistent always-allow, because "a permission the user cannot see is a permission they have forgotten they granted, and the place they would not see it is a config file written six weeks ago". That was reversed against one goal, search the web for AI news, which asked for api.search.brave.com, then www.reuters.com, then tech.yahoo.com, then openai.com, then apnews.com: five prompts, and all five asked again on the next run.

What replaced it keeps the visibility the argument was about. A rule is written only when the user picks the answer that says so, it is shown before it is written, it lands in a JSON file that can be read, diffed and deleted, and emma config check lists every rule with the file it came from.

Parsing one rule

pub fn parse(raw: &str) -> Result<Self> {
    let raw = raw.trim();
    if raw.is_empty() {
        bail!("a permission rule cannot be empty");
    }
    let Some(open) = raw.find('(') else {
        return Ok(Self {
            tool: check_tool(raw)?,
            spec: Spec::All,
        });
    };
    let (tool, rest) = raw.split_at(open);
    let tool = check_tool(tool)?;
    let inner = rest
        .strip_prefix('(')
        .and_then(|r| r.strip_suffix(')'))
        .with_context(|| format!("`{raw}` is missing its closing `)`"))?;
    let inner = inner.trim();
    // Claude Code documents `Bash(*)` as equivalent to `Bash`. Reading them
    // as two things would make the shorter spelling the safe one by
    // accident.
    if inner.is_empty() || inner == "*" {
        return Ok(Self {
            tool,
            spec: Spec::All,
        });
    }
    if let Some(pattern) = inner.strip_prefix("domain:") {
        let pattern = pattern.trim();
        if pattern.is_empty() {
            bail!("`{raw}` names no domain — a `domain:` rule with nothing after the colon");
        }
        // `domain:*` is documented as equivalent to the bare tool name. It
        // is written back as `Spec::All` rather than kept as a pattern that
        // happens to match everything, so there is one shape in the code
        // that means "everything" and it is easy to grep for.
        let spec = match pattern {
            "*" => Spec::All,
            _ => Spec::Domain(DomainPattern::parse(pattern)?),
        };
        return Ok(Self { tool, spec });
    }
    // **A path-shaped specifier is decided by the tool, and by nothing else.**
    // Only `Bash` runs a command; everything else addresses a path.
    if tool != "Bash" {
        if inner.contains('\\') {
            bail!("`{raw}` contains a backslash, which means an escape on unix and a separator on Windows — write the path with `/`");
        }
        if inner.split(['/', '\\']).any(|seg| seg == "..") {
            bail!("`{raw}` contains `..`, which cannot be matched before the path is resolved — write the path without it");
        }
        if let Ok(g) = globset::GlobBuilder::new(&normalise_pattern(inner))
            .case_insensitive(cfg!(windows))
            .build()
        {
            return Ok(Self { tool, spec: Spec::Path(inner.to_string(), g.compile_matcher()) });
        }
    }
    // A command prefix. `git *`, `npm run test:*`, and the bare `git` form.
    let prefix = inner.strip_suffix(":*").or_else(|| inner.strip_suffix('*')).unwrap_or(inner);
    let prefix = normalise_command(prefix);
    if !prefix.is_empty() {
        return Ok(Self { tool, spec: Spec::Command(inner.to_string(), prefix) });
    }
    Ok(Self {
        tool,
        spec: Spec::Unsupported(inner.to_string()),
    })
}

Spec::Unsupported, the third variant

A specifier that is well-formed but outside this build's vocabulary is kept as a value rather than dropped, so the boot can announce it. Rules::parse writes a note about each and then continues, so an unsupported rule never reaches a list at all.

This variant used to hold the two shapes people actually write. Bash(git *) and Read(./src/**) both parsed to Spec::Unsupported, which means they were announced at boot and then matched nothing — including in deny lists. Measured against a real settings file: 62 of its 64 rules were inert. ARCH-002 gave both shapes real matchers, and what remains here is the genuinely unknown specifier rather than the common case. tested the_shapes_that_used_to_be_inert_now_evaluate parses a Claude-Code-shaped deny list and asserts a rm call is denied and a ./src read is allowed, with no boot note left to make — an announcement that fires on a rule which works is how announcements stop being read.

Its matcher arm is Spec::Unsupported(_) => false, reachable only through adopt, and that is the way in the test uses. An arm nothing can reach is an arm nothing checks: a mutation flipping it to true went undetected until the test existed, and that is how Bash(rm *) would one day start matching every call to Bash. tested an_unsupported_rule_that_reaches_a_list_anyway_still_matches_nothing adopts Bash(git log:*) and asserts for_tool and two for_egress calls all answer None. Flipping the arm to true turned that test red at 20ac400.

Precedence inside the rule set

/// **deny, then ask, then allow — the first list with a match wins, and rule
/// specificity never changes that.** Same order Claude Code documents, and
/// the reason is the same: a `deny` that could be narrowed away by a more
/// specific `allow` is not a deny, it is a default.
fn decide(&self, matches: impl Fn(&Rule) -> bool) -> Option<Decision> {
    if self.deny.iter().any(&matches) {
        return Some(Decision::Deny);
    }
    if self.ask.iter().any(&matches) {
        return Some(Decision::Ask);
    }
    if self.allow.iter().any(&matches) {
        return Some(Decision::Allow);
    }
    None
}

A narrow allow does not carve an exception out of a broad deny. A broad allow still covers every host a narrow deny does not name. This is the clause people get wrong, and if it inverted, every deny list in every settings file would become a default rather than a refusal. tested deny_beats_allow_however_specific_the_allow_is checks both arrangements and then asserts the broad allow still answers for a host the narrow deny does not name. ask_sits_between_them_and_beats_allow holds the middle rung from both sides.

Parsing a whole set never fails the boot

Rules::parse returns the rules and one sentence per entry that will not do anything. It cannot fail. .claude/settings.json is written for a program with a larger vocabulary, and refusing to start because one of forty rules is Read(./secrets/**) would be an outage of the kind this workspace rules against elsewhere. The notes are what compensates, and main prints every one through the warning channel at startup rather than the note channel, since each is a line somebody wrote that is not doing what they think. tested a_bad_rule_costs_that_rule_and_not_the_boot parses WebFetch( beside WebSearch and asserts the good rule still answers and the note names the source file.

Why the user scope gives up two of its three lists

Taking only deny from ~/.claude/settings.json diverges from Claude Code, where user settings carry all three lists and all three apply in every project. The file is another program's global configuration, and a grant in it was made for that program, in a session Emma was not part of, possibly years ago.

The doc names a live example rather than a hypothetical: the owner's own file carries Bash(rm:*), Bash(bash:*) and Bash(powershell.exe:*) in its allow list, plus "defaultMode": "dontAsk". Honouring user-scope allow would have given Emma an unprompted shell in every repository on that machine on the first run after the feature shipped.

ask is left out with allow rather than with deny: it is not restrictive enough to be worth importing and not permissive enough to be dangerous. A file that cannot be read is skipped rather than fatal, since the only thing taken from it is restrictions, so failing to read it can only make Emma ask more often. home is threaded as a parameter rather than read from the environment, because a test that reads the real HOME either mutates shared state in a threaded test binary or answers differently on different machines, and both have happened here. tested in crates/harness/tests/permissions.rs.

Writing a rule down

file_for(root) is root.join("settings.local.json"), and the root is whichever harness the project loaded, not always .claude/, and never ~. Three arguments decided it. Claude Code documents settings.local.json as git-ignored and as where it saves permanent approvals, so writing into settings.json would commit one developer's convenience as everybody's policy on the next git add. A project that has .emma/ should not acquire a .claude/ directory because somebody answered a prompt, which would be Emma creating configuration for a different program without being asked. And a grant made in one repository is not a grant everywhere.

crates/emma/src/permissions.rs — file_for

remember merges rather than replaces. The file is read, parsed as a whole document, and written back with every key it had: hooks, statusLine, env, anything else. It returns true when a line was added and false when the rule was already there, which is what makes the prompt able to say "saved" or "already had". This project has been bitten once by a write path that replaced a shared configuration document and deleted another program's key.

Four shapes are refused outright, and in each case nothing is written: a file that is not valid JSON, a document that is not an object, a permissions key that is not an object, and a permissions.allow that is not an array. The message names the file and what is wrong with it, and the grant lasts the session instead. kind_of exists to name the shape found before the mutable borrow starts, so the refusal can say "holds a JSON number" rather than only "is not an object". tested a_file_that_cannot_be_parsed_is_left_exactly_as_it_was writes all four shapes, asserts each error names its file, and asserts the bytes on disk are unchanged.

What a prefix and a glob cannot see

Both matchers read argument text. Bash hands that text to a shell, and the fs tools resolve their path long after the gate has decided — so a rule can be evaded by writing the same thing differently, and that is a property of the shape rather than a bug in it.

The command half. Bash(git *) does not match env git push, cd . && git push, GIT_SSH_COMMAND=x git push, echo hi | git push, or /usr/bin/git push — every one of which plainly runs git. The fix is not a shell parser: quoting, substitution and operator precedence are the shell's business, and a half-parser gives rules a meaning that differs from what the shell actually does. What happens instead is narrower. When a deny rule for the tool carries a command prefix and the command is composed — chained, piped, substituted, led by an environment assignment, a wrapper such as env or sh, or a path-qualified binary — and no deny actually matched, the answer is Ask. Not Deny: the rule genuinely did not match, and claiming it did would be the same dishonesty pointing the other way. What is refused is passing quietly. tested a_composed_command_cannot_slip_past_a_deny_prefix walks seven evasions and asserts each becomes a question.

is_composed is deliberately over-broad. A false positive costs a question a human answers; a false negative is a deny rule that did not fire.

One command evasion is not caught, and cannot be by this shape. git -C . push against a rule reading Bash(git push *) is an ordinary spelling with nothing suspicious in it — a genuine prefix mismatch. Treating an option sitting between two words a rule names as unjudgeable would make every flag a prompt. That is the boundary of prefix matching over argument text; the honest options are to widen the heuristic endlessly, to match after resolution, or to say plainly that a command-prefix deny narrows to the spellings it names. This paragraph is the third. unverified What would settle it: nothing settles it — it is a statement about what the shape can express, not a claim about a run.

The path half. ./src/x and src/x are one file to the tool and were two strings to the matcher, so a deny protected only the spelling the operator happened to use. Both the rule pattern and the call's path are now normalised before matching — separators become /, repeated separators collapse, ./ segments go — so the rule and the call meet in one spelling. tested a_path_rule_is_not_defeated_by_respelling_the_same_file crosses two rule spellings with five call spellings and asserts all ten deny. Removing the normalisation on the call side turns it red, along with two older tests that had been relying on it without saying so.

Normalisation stops short of .., because a/link/../b is a/b only when link is a directory, and a matcher that guesses wrong gets a deny wrong in whichever direction the guess fell. A .. component in the call, or an absolute call against a relative rule, is refused rather than resolved: the same Ask the composed commands get. A .. in the rule is a different matter and gets a different answer — it is a parse error, because a pattern that can never be evaluated is not a rule. An earlier version asked the question of both sides, and one .. in one rule then turned every unrelated read into a prompt. tested a_path_a_rule_cannot_be_compared_against_asks_rather_than_passes asserts three such paths answer Deny or Ask and never silence, and that an ordinary relative path is still judged — a gate that asks about everything is a gate nobody reads.

What is still open: an absolute call and a relative rule become a question rather than a match, because the gate does not hold the project root that would settle whether they are the same file. Closing that means matching after resolution, which needs the gate to run later than it does. unverified What would settle it: a design that moves the path decision to the tool, where the resolved path exists.

Which shape a specifier gets, and the seven ways it went wrong

The tool decides, not the punctuation. Only Bash runs a command, so only Bash(...) is a prefix; every other tool addresses a path, so its specifier is a glob. The first version asked whether the text contained a separator or a glob character instead — which made Read(Cargo.toml) a command prefix, matched against a command argument that a Read call does not have. It matched nothing at all, silently, on a rule naming one file by name.

That was one of seven bypasses a cross-model review returned against the first version of the path matcher, all seven with exact inputs. Five were holes; two were the opposite — a rule answering where it should have stayed quiet, which matters as much, because a gate that asks about everything is a gate nobody reads.

This page quoted the defective condition for half a day

The Rule::parse block above read if tool != "Bash" || inner.contains('/') || … until 2026-08-23. That disjunct was the fix for the previous defect — shape chosen by punctuation, which made Read(Cargo.toml) a command prefix that matched nothing — and it rebuilt the identical defect facing the other way: every Bash rule containing a separator compiled to a path glob, and a Bash call carries command rather than file_path, so the rule could never fire. Measured on the owner's real settings.json: 24 of 53 Bash rules silently inert, deny rules among them, and worse than the state it replaced because Spec::Unsupported is announced at boot and Spec::Path is not.

Two independent reviewers found the code defect on the same afternoon; a third found that this page was still quoting the broken condition after the code was fixed, on the page a reader consults about security, with nothing marking it as historical. Both halves are the same lesson: a row is not done when its code lands, and a page that quotes code is a claim about the code that has to be re-checked when the code moves.
