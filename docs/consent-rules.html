Permission rules, scopes and merging

Consent & permissions The two axes The ladder The egress question The five answers EXEMPT and the floor Permission rules Matching a host Hooks

A rule is Tool or Tool(specifier), in Claude Code's JSON shape, read from up to three files and merged into one set of three lists. Which list a match lands in is the whole of the answer; how specific the rule was does not enter into it.

crates/emma/src/permissions.rs — Rule, Rules; crates/harness/src/lib.rs — PermissionBlock

The format, and why it is somebody else's

The block is permissions: { allow: [], deny: [], ask: [] }. An existing .claude/settings.json works here, and a rule Emma writes is a rule the other program understands. Emma's own .emma/config.json spine accepts the same block under the same names; a block that had to be re-typed to move between the two directories would defeat the reason it is read at all.

crates/emma/src/permissions.rs — module doc; crates/harness/src/lib.rs — PermissionBlock

Persistent rules were once refused outright. approval.rs carried a section arguing there must be no persistent always-allow, because "a permission the user cannot see is a permission they have forgotten they granted, and the place they would not see it is a config file written six weeks ago". That was reversed against one goal, search the web for AI news, which asked for api.search.brave.com, then www.reuters.com, then tech.yahoo.com, then openai.com, then apnews.com: five prompts, and all five asked again on the next run.

What replaced it keeps the visibility the argument was about. A rule is written only when you pick the answer that says so, and it is shown to you before it is written. It lands in a JSON file you can read, diff and delete, and emma config check lists every rule with the file it came from.

That last row has a consequence: “deny everything” has to be written out, one tool at a time. There is no rule that denies every tool, so a preset meaning that has to name all of them, and a list that silently missed one would be a protection you believed you had. Emma's own Deny All preset carries a list of 26 tool names for exactly this reason, and it is kept in step with what the binary registers by a test rather than by memory. That list was wrong on arrival, missing the two background-execution tools, so the test is not a formality; the run-control page has the account.

Parsing one rule

pub fn parse(raw: &str) -> Result<Self> {
    let raw = raw.trim();
    if raw.is_empty() {
        bail!("a permission rule cannot be empty");
    }
    let Some(open) = raw.find('(') else {
        return Ok(Self {
            tool: check_tool(raw)?,
            spec: Spec::All,
        });
    };
    let (tool, rest) = raw.split_at(open);
    let tool = check_tool(tool)?;
    let inner = rest
        .strip_prefix('(')
        .and_then(|r| r.strip_suffix(')'))
        .with_context(|| format!("`{raw}` is missing its closing `)`"))?;
    let inner = inner.trim();
    // Claude Code documents `Bash(*)` as equivalent to `Bash`. Reading them
    // as two things would make the shorter spelling the safe one by
    // accident.
    if inner.is_empty() || inner == "*" {
        return Ok(Self {
            tool,
            spec: Spec::All,
        });
    }
    if let Some(pattern) = inner.strip_prefix("domain:") {
        let pattern = pattern.trim();
        if pattern.is_empty() {
            bail!("`{raw}` names no domain — a `domain:` rule with nothing after the colon");
        }
        // `domain:*` is documented as equivalent to the bare tool name. It
        // is written back as `Spec::All` rather than kept as a pattern that
        // happens to match everything, so there is one shape in the code
        // that means "everything" and it is easy to grep for.
        let spec = match pattern {
            "*" => Spec::All,
            _ => Spec::Domain(DomainPattern::parse(pattern)?),
        };
        return Ok(Self { tool, spec });
    }
    // **A path-shaped specifier is decided by the tool, and by nothing
    // else.** The first version asked whether the text held a separator or
    // a glob character, which made `Read(Cargo.toml)` a *command* prefix —
    // matched against a `command` argument that a `Read` call does not
    // have, so it matched nothing at all, silently. A review supplied it as
    // a working bypass of a deny rule naming one file.
    //
    // **The fix for that kept the punctuation test as an extra disjunct for
    // `Bash`, and thereby rebuilt the same defect facing the other way.**
    // `Bash(rm -rf /)`, `Bash(curl https://*)`, `Bash(./deploy.sh)` — every
    // one contains a separator, so every one compiled to a `Spec::Path`
    // glob, and a `Bash` call carries `command` rather than `file_path`, so
    // `path_of` returned `None` and the rule could never fire. Two
    // independent reviewers found it on the same afternoon; one measured the
    // owner's real `settings.json` and reported **24 of 53 `Bash` rules
    // silently inert**, deny rules among them. It was worse than the state
    // it replaced: `Spec::Unsupported` is announced at boot, `Spec::Path` is
    // not, so the rules went from loud-and-inert to silent-and-inert.
    //
    // Claude Code has no path form for `Bash` — the inner text is a command,
    // always. So the tool decides alone, with no punctuation clause to grow
    // an exception back into.
    if tool != "Bash" {
        // **A backslash in a path rule means two different things on two
        // platforms, so it means nothing here.** `globset` escapes with it
        // on unix and treats it as a separator on Windows — so
        // `Read(src/a\*b)` names a literal asterisk on one machine and the
        // directory `src/a` on the other, from the same settings file. A
        // cross-model review found the first half of that and reported it
        // as a plain bug; it is worse than a bug, because either reading is
        // defensible and the file cannot say which it meant. Refused, with
        // the fix in the message, rather than resolved by guessing.
        if inner.contains('\\') {
            bail!(
                "`{raw}` contains a backslash, which means an escape on unix and a separator on Windows — write the path with `/`"
            );
        }
        // A `..` cannot be matched before the path is resolved, and a rule
        // that can never be evaluated is refused loudly rather than kept as
        // something that quietly matches nothing.
        if inner.split(['/', '\\']).any(|seg| seg == "..") {
            bail!(
                "`{raw}` contains `..`, which cannot be matched before the path is resolved — write the path without it"
            );
        }
        // The compiled pattern is normalised and the raw text is kept for
        // display, so a rule reads back exactly as written while matching
        // the same file however the call spells it.
        // Case-insensitive on Windows because the filesystem is: a rule
        // naming `src/main.rs` and a call naming `SRC/Main.rs` are one file
        // there, and a case-sensitive matcher is one the operating system
        // disagrees with. Done in the builder rather than by folding the
        // pattern, which would rewrite a `[A-Z]` class into a different one.
        if let Ok(g) = globset::GlobBuilder::new(&normalise_pattern(inner))
            .case_insensitive(cfg!(windows))
            .build()
        {
            return Ok(Self {
                tool,
                spec: Spec::Path(inner.to_string(), g.compile_matcher()),
            });
        }
    }
    // A command prefix. `git *`, `npm run test:*`, and the bare `git` form
    // that people write meaning the same thing.
    let prefix = inner
        .strip_suffix(":*")
        .or_else(|| inner.strip_suffix('*'))
        .unwrap_or(inner);
    let prefix = normalise_command(prefix);
    if !prefix.is_empty() {
        return Ok(Self {
            tool,
            spec: Spec::Command(inner.to_string(), prefix),
        });
    }
    Ok(Self {
        tool,
        spec: Spec::Unsupported(inner.to_string()),
    })
}

Spec::Unsupported, the third variant

A specifier that is well-formed but outside this build's vocabulary is kept as a value rather than dropped, so the boot can announce it. Rules::parse writes a note about each and then continues, so an unsupported rule never reaches a list at all.

This variant used to hold the two shapes people actually write. Bash(git *) and Read(./src/**) both parsed to Spec::Unsupported, which means they were announced at boot and then matched nothing, including in deny lists. Measured against a real settings file: 62 of its 64 rules were inert. Precedence inside the rule set

/// **deny, then ask, then allow — the first list with a match wins, and rule
/// specificity never changes that.** Same order Claude Code documents, and
/// the reason is the same: a `deny` that could be narrowed away by a more
/// specific `allow` is not a deny, it is a default.
fn decide(&self, matches: impl Fn(&Rule) -> bool) -> Option<Decision> {
    if self.deny.iter().any(&matches) {
        return Some(Decision::Deny);
    }
    if self.ask.iter().any(&matches) {
        return Some(Decision::Ask);
    }
    if self.allow.iter().any(&matches) {
        return Some(Decision::Allow);
    }
    None
}

Why the user scope gives up two of its three lists

Taking only deny from ~/.claude/settings.json diverges from Claude Code, where user settings carry all three lists and all three apply in every project. The file is another program's global configuration, and a grant in it was made for that program, in a session Emma was not part of, possibly years ago.

The doc names a live example rather than a hypothetical: the owner's own file carries Bash(rm:*), Bash(bash:*) and Bash(powershell.exe:*) in its allow list, plus "defaultMode": "dontAsk". Honouring user-scope allow would have given Emma an unprompted shell in every repository on that machine on the first run after the feature shipped.

ask is left out with allow rather than with deny: it is not restrictive enough to be worth importing and not permissive enough to be dangerous. An absent file or a path that is not a file is skipped; invalid JSON grants nothing and emits a note. home is threaded as a parameter rather than read from the environment, because a test that reads the real HOME either mutates shared state in a threaded test binary or answers differently on different machines, and both have happened here. the_user_scope_contributes_deny_and_never_allow and a_missing_or_unreadable_user_settings_file_is_not_a_failure cover those cases. tested crates/harness/tests/permissions.rs unverified Despite its name, the second test does not create an existing file whose read fails; its own comment records that gap. What would settle it: on Unix create the settings file, apply chmod 000, call user_permissions, assert no entries and one note naming the file and lost deny rules, then restore its mode in cleanup. On Windows do the equivalent with a temporary denying ACL and restore the ACL before deleting the fixture.

Writing a rule down

file_for(root) is root.join("settings.local.json"), and the root is whichever harness the project loaded, not always .claude/, and never ~. Three arguments decided it. Claude Code documents settings.local.json as git-ignored and as where it saves permanent approvals, so writing into settings.json would commit one developer's convenience as everybody's policy on the next git add. A project that has .emma/ should not acquire a .claude/ directory because you answered a prompt, which would be Emma creating configuration for a different program without being asked. And a grant made in one repository is not a grant everywhere.

What a prefix and a glob cannot see

Both matchers read argument text. Bash hands that text to a shell, and the fs tools resolve their path long after the gate has decided. So a rule can be evaded by writing the same thing differently. That is a property of the shape, not a bug in it.

The command half. Bash(git *) does not match env git push, cd . && git push, GIT_SSH_COMMAND=x git push, echo hi | git push, or /usr/bin/git push. Every one plainly runs git. The fix is not a shell parser: quoting, substitution and operator precedence are the shell's business, and a half-parser gives rules a meaning that differs from what the shell actually does. What happens instead is narrower. When a deny rule for the tool carries a command prefix and the command is composed (chained, piped, substituted, led by an environment assignment, a wrapper such as env or sh, or a path-qualified binary), and no deny actually matched, the answer is Ask. Not Deny: the rule did not match, and claiming it did would be false. What is refused is passing quietly. tested crates/emma/src/permissions.rs a_composed_command_cannot_slip_past_a_deny_prefix walks seven evasions and asserts each becomes a question.

is_composed is over-broad. A false positive costs a question a human answers; a false negative is a deny rule that did not fire.

Three ordinary spellings walked past it in silence until 2026-08-23, and the page said at the time that only one evasion was uncaught. An independent reviewer drove the matcher directly against a Bash(git *) deny and got None: no deny, no question, and no boot note for a newline separator, a bare subshell, and the command builtin.

The newline bypass happened because the evidence was being destroyed before the check ran. command_of normalises with split_whitespace().join(" ") so a prefix can be compared against the result, and that collapse turns a newline into a space: echo hi\ngit push arrived at is_composed as echo hi git push, one command whose first word is echo. Adding the token alone would have fixed nothing. The call site now passes the raw argument, and the token is in the list as well. is_composed now receives the raw input rather than one caller's normalised form. tested crates/emma/src/permissions.rs an_ordinary_shell_spelling_cannot_walk_past_a_deny_rule asserts the decision rather than is_composed, because the bug lived in the seam between the two. Four mutations go red: the call site handing back the normalised string, the newline tokens, the grouping brackets, and the wrapper list.

( and { now join $(, and the wrapper list gained command, exec, sudo, doas, su, nohup, timeout, setsid, stdbuf, ionice and busybox. The cost is a question on a command containing a bracket for some other reason, and only where a deny prefix rule for that tool already exists. The test's control asserts three plain commands stay unprompted under a live deny rule, because a prompt that fires when it should not is how you learn to answer without reading.

One command evasion is still not caught, and cannot be by this shape. git -C . push against a rule reading Bash(git push *) is an ordinary spelling with nothing suspicious in it: a genuine prefix mismatch. Treating an option sitting between two words a rule names as unjudgeable would make every flag a prompt. That is the boundary of prefix matching over argument text; the options are to widen the heuristic endlessly, to match after resolution, or to say plainly that a command-prefix deny narrows to the spellings it names. Then change the prefix matcher to recognize that spelling and require the second assertion to fail before restoring it. That demonstrates the expressiveness boundary without claiming the command did not run.

The path half. ./src/x and src/x are one file to the tool and were two strings to the matcher, so a deny protected only the spelling you happened to use. Both the rule pattern and the call's path are now normalised before matching: separators become /, repeated separators collapse, and ./ segments go. The rule and the call then meet in one spelling. tested crates/emma/src/permissions.rs a_path_rule_is_not_defeated_by_respelling_the_same_file crosses two rule spellings with five call spellings and asserts all ten deny. Removing the normalisation on the call side turns it red, along with two older tests that had been relying on it without saying so.

Normalisation stops short of .., because a/link/../b is a/b only when link is a directory, and a matcher that guesses wrong gets a deny wrong in whichever direction the guess fell. A .. component in the call, or an absolute call against a relative rule, is refused rather than resolved: the same Ask the composed commands get. A .. in the rule is a different matter and gets a different answer: it is a parse error, because a pattern that can never be evaluated is not a rule. An earlier version asked the question of both sides, and one .. in one rule then turned every unrelated read into a prompt. tested crates/emma/src/permissions.rs a_path_a_rule_cannot_be_compared_against_asks_rather_than_passes asserts three such paths answer Deny or Ask and never silence, while an ordinary relative path is still judged. A gate that asks about everything is a gate nobody reads.

Which shape a specifier gets, and the seven ways it went wrong

The tool decides, not the punctuation. Only Bash runs a command, so only Bash(...) is a prefix. Every other tool addresses a path, so its specifier is a glob. The first version asked whether the text contained a separator or a glob character, which is how Read(Cargo.toml) became a command prefix that matched nothing.

That was one of seven bypasses a cross-model review returned against the first version of the path matcher, all seven with exact inputs. Five were holes. Two were the opposite: a rule answering where it should have stayed quiet.
