The frame, and the three absolutes

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages Copying out

This is the only module in term/ that owns a terminal. It installs one of two viewports, holds the locks, writes the entry and leave bytes, and gives the terminal back on every path out of the process that in-process code can see. It spent its whole life arguing against the alternate screen and then entered it, and the file says so in the first paragraph rather than quietly dropping the argument.

The reversal, and what it did to the manifest test

2026-08-12

The rule was Viewport::Inline only, never the alternate screen, and this file spent its life arguing for it: it costs terminal scrollback and native mouse selection, and Emma's output is a transcript people read after the run. The owner reversed it on the ground that the multi-pane layout he specified cannot be drawn inline. The module doc records the outcome in six words: “That argument was true and it lost.”

crates/emma/src/term/frame.rs module doc; notes/design/tui-fullscreen.md §0, §2

The test that had asserted “no alternate-screen entry anywhere” was rewritten rather than deleted, and its doc comment names which assertion died and why. Three claims survive in it. Two of them are about counting occurrences in this file's own source, so both needles are assembled at runtime, “because this file is its own haystack and a literal would match itself.”

Stripping comment lines before the manifest search is what makes the assertion mean something. crates/emma/Cargo.toml explains at length why the feature is off, so the string appears in it several times over; without the filter the test would fail on the explanation. certified that the manifest declares no such feature: grep -n ratatui crates/emma/Cargo.toml at 62ab9c3 shows one dependency line, ratatui = { version = "0.29", default-features = false, features = ["crossterm"] }, and nothing else.

The reason the feature stays off outlives the reversal. With it on, the inline path's insert_before is implemented with ESC[{top};{bottom}r, and a DEC scrolling region whose top margin is below row 1 discards the lines that leave it. That shipped here once, and the owner's first complaint was that he could not scroll. The inline path survives as an escape hatch, so the hazard survives with it.

The third assertion counts the alternate screen's enter and leave sequences, comments stripped, and demands one of each. tested A second occurrence of the enter bytes would be “an entry outside the latch's knowledge”, which is exactly what the restore path cannot survive.

Absolute 1: the plain fallback never touches the alternate screen

ALT_ENTER is a constant, written at one place, inside Frame::install, after fallback_reason has returned None and, on Windows, after VT has been proved. There is no other emitter, and the manifest test above is what keeps it that way.

crates/emma/src/term/frame.rs · ALT_ENTER, ALT_LEAVE

/// The alternate screen. `?1049h` switches to a cleared second buffer and
/// `?1049l` restores the first, prior content and all — which is what makes
/// the full-screen exit story *simpler* than the inline one: there is nothing
/// to erase. Kept out of [`enter_modes`] because it is entered *before* the
/// `Terminal` is built (ratatui must measure the screen it will draw on) and
/// left conditionally (see [`restore_terminal`]); the pairing test scans both
/// pairs, so the split cannot hide an unmatched `h`.
///
/// The `2J`+`H` after the switch is deliberate: xterm clears on entry, but
/// "cleared" is the terminal's promise, not DEC's, and one explicit erase is
/// cheaper than certifying every console's reading of 1049.
const ALT_ENTER: &str = "\x1b[?1049h\x1b[2J\x1b[H";
const ALT_LEAVE: &str = "\x1b[?1049l";
crates/emma/src/term/frame.rs — the Terminal modes region

A run without a Frame cannot emit those bytes, and the surface page covers the three constructors that never build one. The second half of the guarantee, that nothing else Emma writes to a pipe is an escape byte either, rests on render::for_stream branching on the palette level.

Absolute 2: every exit path leaves it

restore_terminal is idempotent, global, and takes no arguments. All three follow from one constraint: “a panic hook has no self.” The state it undoes lives in five process-global atomics rather than in a struct, because only one of the callers has a Frame in hand.

crates/emma/src/term/frame.rs · restore_terminal

pub fn restore_terminal() {
    // **Each latch answers for itself.** This used to return early unless
    // `FRAME_ON` was set — and `FRAME_ON` is set *last*, after raw mode, the
    // alternate screen and mouse capture are already on. So a panic anywhere in
    // that window left every one of them enabled with the only thing that turns
    // them off refusing to run: a shell with no echo, on a screen that is not
    // the user's, which is the failure `CLAUDE.md` says people uninstall over.
    //
    // The comment at the install site claimed the `ALT_ON` latch prevented
    // exactly this. It could not, because it never reached the code that reads
    // it.
    let was_frame = FRAME_ON.swap(false, Ordering::SeqCst);
    if !was_frame
        && !RAW_ON.load(Ordering::SeqCst)
        && !ALT_ON.load(Ordering::SeqCst)
        && !MOUSE_ON.load(Ordering::SeqCst)
    {
        return;
    }
    if RAW_ON.swap(false, Ordering::SeqCst) {
        let _ = disable_raw_mode();
    }
    if MOUSE_ON.swap(false, Ordering::SeqCst) {
        // Through crossterm rather than a string on purpose: on Windows the
        // enable was a console-mode change, and only the matching command
        // undoes it. On unix this writes the `?100x` lows.
        let _ = execute!(std::io::stdout(), DisableMouseCapture);
    }
    // Leaving the alternate screen restores the prior shell content wholesale,
    // which is the erase arithmetic's whole job done by the terminal; the
    // inline path still erases its own rows. The `?1049l` is written only when
    // `?1049h` was: a leave on the normal screen carries an implicit cursor
    // restore that nothing saved, and terminals answer that by moving the
    // cursor somewhere surprising.
    let mut out = if ALT_ON.swap(false, Ordering::SeqCst) {
        CURSOR_ROW.store(u16::MAX, Ordering::SeqCst);
        ALT_LEAVE.to_string()
    } else {
        erase_frame()
    };
    out.push_str(&leave_modes());
    let mut stdout = std::io::stdout();
    let _ = stdout.write_all(out.as_bytes());
    let _ = stdout.flush();
    #[cfg(windows)]
    {
        super::restore_console_mode();
        // The code page Emma set for itself. Restored last, after the last
        // byte this function writes has gone out, so the escape sequences above
        // are decoded by the console we were drawing under.
        super::restore_console_cp();
    }
}

Every latch is cleared with swap, which is why the panic hook and Drop racing each other costs nothing: the second caller reads false and returns. FRAME_ON guards the whole function, so a restore on a run that never drew writes not one byte. tested: restoring_a_terminal_that_was_never_drawn_on_writes_nothing and restore_runs_once_however_many_times_it_is_called, the second of which flips FRAME_ON and ALT_ON by hand, because a test binary has no terminal and install correctly refuses to run in one.

Three orderings inside install that change the outcome

  • ALT_ON is stored before the enter bytes are written. A panic in between would otherwise strand the alternate screen behind a restore that refuses to run. The failed-write branch clears it again and drops raw mode, because “half-installed is the worst state to leave a terminal in.”
  • The private modes are enabled after FRAME_ON, since FRAME_ON is what makes the restore willing to turn them off. “Being late costs nothing; being early costs a shell that pastes escape markers into itself.”
  • The Windows code page is restored last, after the final byte has gone out, so the escapes above it are decoded by the console they were written for.

Adding a mode to enter_modes without adding it to leave_modes fails in CI rather than on somebody else's terminal. Today enter_modes is PASTE_ON alone and leave_modes is {PASTE_OFF}{SYNC_END}\x1b[?25h\x1b[0m: paste off, any synchronized update ended, the cursor shown, and every attribute dropped. A frame torn down mid-paint could otherwise leave a shell prompt bold, invisible, or not repainting at all until the terminal's own timeout fired.

The cost of bracketed paste left on is worth stating plainly, because it outlives the process: a shell inheriting it receives ESC[200~ around everything anybody pastes into it, forever, from a program that has exited. Mouse capture cannot ride in the pairing test, because on Windows the enable is a console-mode change rather than bytes, so its pairing is asserted on the source instead. The test says so of itself: “Weak as assertions go, and said so; the live pairing is a certification item.” unverified: exit a framed run and check the shell reports mouse events normally.

What the restore does not cover, per the code

SIGKILL, a stack overflow that skips the hook, and std::process::abort. Those strand raw mode already and strand the alternate screen now, “and no in-process code can do otherwise.” The design note adds a class the inline design could not have: a multiplexer or ssh session detached mid-frame, or a dropped connection with the alternate screen still entered. unverified: no tmux or ssh certification exists in the tree. Detaching mid-frame, resizing the pane and reattaching would settle it.

What install does, in order

Frame::install is the longest function in the file and every step of it can refuse. In order: fallback_reason; enable_vt on Windows; the EMMA_UI read; a \r\n to stdout so the viewport is not drawn over the shell prompt; the panic hook; enable_raw_mode; the alternate-screen enter when not inline; open_viewport or open_fullscreen; FRAME_ON; enter_modes; mouse capture when not inline; the user-tool catalogue; and finally the Arc<Frame>, a first draw, and a clock thread.

The hook moved, and where it sits is the whole of the property. It used to go on after the modes were enabled — and a hook installed afterwards cannot answer for a panic in between, which is several fallible writes long. Combined with the old FRAME_ON-only restore guard, a panic in that window stranded raw mode and the alternate screen with nothing willing to undo them. Each failing step now unwinds the latches it set, so a refusal partway through leaves the terminal as it found it.

Two of those deserve a sentence. Mouse capture is enabled only on the full-screen path, and the comment is unusually blunt about the reason: “on the alternate screen the wheel does nothing at all without it — not ‘less useful’, nothing.” Inline, the terminal owns the wheel, and taking it would break scrollback that still works. And the catalogue is probed here against the directory Emma was started in, so the TOOLS section is never a placeholder on the first paint; set_identity re-probes it when the run's real working directory arrives.

spawn_clock holds a Weak<Frame> and redraws twice a second while a goal is running, so the elapsed field is a clock rather than a timestamp from the last thing that happened. It is a plain thread rather than a tokio task “so it keeps ticking through a blocking tool call”, and the Weak is what lets the thread die with the frame.

Synchronized output

ESC[?2026h asks the terminal to stop presenting frames until the matching l, so a repaint made of several writes reaches the eye as one picture instead of as its steps. synchronized writes both straight to stdout rather than through the backend, because they are not drawing operations and both go into the same global buffer, so the order they were written in is the order they go out in.

On a terminal that does not implement it, nothing happens: DECSET with an unrecognised parameter is defined to be ignored, and 2026 is registered, so a terminal either honours it or drops it. The file names which terminals honour it (Windows Terminal, WezTerm, kitty, foot, iTerm2, Ghostty) and which ignores it (legacy conhost). unverified here: that list is not sourced in the file and was not re-checked for this page. Reading each terminal's release notes, or writing the sequence and watching for a paused frame, would settle it.

The failure worth naming is an unmatched h: a terminal that never sees the l stops updating. Every terminal implementing the mode implements a timeout for that reason, and SYNC_END is also on the restore path. tested: a_synchronized_update_is_always_ended_including_on_the_way_out pins both constants and then asserts that leave_modes() actually contains SYNC_END.

It used to assert on this file's own source text — that the string out.push_str(SYNC_END) still appeared — and that is a false receipt of the exact kind this repository has a name for: the grep matched a literal that also existed inside the assertion itself, so the test could not fail. Behaviour is checked now, not spelling.

Anchoring, which is now only the resize path

The inline viewport's top row is computed by ratatui from wherever the cursor is when the Terminal is built, and every insert_before moves it one row further down until it reaches the bottom. So the box is under the last line of output at all times, which is the only definition of “pinned to the bottom” that is true on the first frame as well as the hundredth.

The version this replaces walked the cursor down to height - view_rows before handing over the backend. That put the box on the last row immediately and, on a fresh shell, left every row it walked over blank. The region comment records the outcome: “The owner sent a screenshot of that, too. The walk cost the transcript nothing, which was the property that mattered and the property that was tested; what it cost was the screen.”

So install now anchors nothing, and there is a test asserting that on this file's source, because install cannot run in a test binary: install_hands_the_terminal_to_ratatui_without_moving_the_cursor_first slices the source between pub fn install( and PANIC_HOOK.call_once, strips comments, and refuses anchor(. Both expect messages say the assertion has become vacuous if the anchor points move, which is the honest failure mode for a source-grep test. tested

What is left of anchoring is the resize path, and it is one bit:

crates/emma/src/term/frame.rs · anchor_row, resize_target

/// The row the viewport's top belongs on: the window's height, less the frame's.
fn anchor_row(screen_rows: u16, view_rows: u16) -> u16 {
    screen_rows.saturating_sub(view_rows)
}

/// Where a resize should put the viewport's top row, or `None` to leave it on
/// the row the erase left the cursor on.
///
/// The whole of the resize decision, as a function of one bit, so that what
/// [`Inner::reanchor`] does and what the tests assert are the same code rather
/// than two statements of it — `reanchor` itself writes to the process's real
/// stdout and cannot be called from a test binary.
///
/// `None` is not "do nothing safe": it is the answer for a frame still sitting
/// under the two lines of output it belongs to, which a taller window must not
/// drag to the bottom. That is the startup void arriving through the resize
/// path.
fn resize_target(pinned: bool, screen_rows: u16, height: u16) -> Option<u16> {
    pinned.then(|| anchor_row(screen_rows, height))
}
crates/emma/src/term/frame.rs — the Anchoring region

pinned is a latch rather than a comparison, because a window dragged taller makes the old bottom row an ordinary middle row and there is then nothing left on screen to work it out from. It is set in Inner::paint from ratatui's own idea of where the viewport is, “because that is the number insert_before moves and the only one that can answer ‘has it arrived yet’.” tested: a_resized_window_puts_a_pinned_frame_back_on_its_last_rows over three size changes, and a_resized_window_leaves_an_unpinned_frame_under_its_own_output for the other bit.

reanchor also names a hazard it cannot remove. Asking where the cursor is costs a round trip through the terminal on unix, and by the time a resize happens the reader thread is on stdin too, so the answer can go to the wrong reader. The exposure is not new: ratatui's own autoresize asks the same question on the first draw after any resize. When it fails, anchor moves nothing and the frame stays where it was, “untidy, not broken.” unverified: nobody has provoked the race. A resize storm on a unix terminal while a goal streams would settle it.

Two paints, one function each

Inner::paint branches on Ui. Inline, it calls paint_into, then updates the pinned latch and stores CURSOR_ROW, which is the climb count the erase uses. Full-screen, it builds a statusbar::Bar from the view's status and hands the whole window to App::render, leaving CURSOR_ROW parked at “nothing drawn” because the full-screen restore leaves the alternate screen rather than erasing rows.

The Bar construction encodes one rule worth reading. An unmeasured context or spend becomes (0, 0), never (0, real_cap), “which would draw an invented ‘0% of the budget’ before the first model call reports.” The up/down raw token split is None because the loop does not carry it yet: absent, not zero.

Four functions are generic over Backend so a TestBackend can drive the same ratatui code a real terminal runs: open_viewport, open_fullscreen, emit_block and paint_into, plus emit_into under them. Without that, “output goes above and the question stays below” would be a claim about a mechanism nobody in this repository can observe.

emit_into computes the row count in advance because that is what insert_before makes room for: guess low and the last row of a wrapped line lands on top of the viewport. It measures with rows_used, which counts display columns rather than characters, and caps a single insert at MAX_INSERT_ROWS = 500, the backstop for a tool that returns fifty thousand lines. tested: a_wrapped_transcript_line_gets_all_the_rows_it_needs asserts that a hundred-character line arrives whole across three rows and that the viewport under it is unbroken.

The one cell where the test screen and a real terminal disagree

ratatui clears a moved inline viewport by putting the cursor on its top-left and asking for ClearType::AfterCursor. crossterm sends ESC[J, which clears from and including the cursor cell; TestBackend implements it as content[index + 1..], which leaves that cell alone. So every time the frame moves down a row the cell buffer keeps a stale ╭ at column zero of the row the border used to be on, and a real console does not. The test helper boxes_in counts a whole corner rather than one glyph to get past it, and the doc says which way round it is: “for once the test screen shows a defect the terminal will not have, rather than hiding one it will.” tested that a genuinely duplicated box still fails, because a duplicated box brings its border with it.

The Frame's public surface

GroupMethods, and what is decided in them
Writing draw, write_lines, user_line, prose, flush_prose, separate, note_line. user_line exists so the full-screen chat pane can label a row You rather than guessing the speaker back from styling. prose forks hard: full-screen it streams into the transcript's tail entry, inline it holds the fragment after the last newline in View::partial, because a fragment inserted above the viewport could never be extended. separate is a no-op full-screen, where the transcript buffer's own separators are the rule.
View state set_input, set_prompt, set_menu, prompt_pending, set_identity. set_prompt closes the menu when a question arrives, which is the second half of the rule the reader enforces from the other side.
Meters goal_started, goal_ended, spent, set_budgets. Each takes the lock, mutates, paints, drops the lock, and then calls request_status. The scoping is not tidiness: request_status takes the same lock, and a method holding it across the call would deadlock the first time anybody typed a goal.
Status program set_status_source, request_status, set_custom_status. request_status builds a payload and try_sends it into a one-slot channel; a full channel means a fresher request is already queued and the right answer is to do nothing. status_requests is a separate mutex from inner, because “one mutex for two unrelated things is how a repaint ends up waiting on a subprocess.”
Keys and mouse scroll_rows, scroll_page, scroll_top, scroll_tail, toggle_sidebar, click, launch_tool. Every one is a no-op on the inline path. They are called from the reader thread and never enter the line channel, which is what keeps the drain guarantee untouched by construction. click returns early while a prompt is pending, and launch_tool spawns a thread because a keystroke handler that waits on a process is an event loop that has stopped.
Plumbing lock (carries on through a poisoned mutex, because the frame is already being torn down and a second panic helps nobody), session_pointer, view_rows, Inner::emit, Inner::reanchor.

view_rows(screen_rows) is (screen_rows / 3).clamp(5, 10), and the two bounds are argued: ten rows holds a status line, a hint, an input box and five rows of a diff; five is the least that can hold a question and the keys to answer it. Below that the fallback is a better product than a viewport occupying most of the screen, which is why fallback_reason refuses under eight rows outright. tested: the_viewport_is_a_third_of_the_window_within_reason, at 40, 24, 9 and 120.
