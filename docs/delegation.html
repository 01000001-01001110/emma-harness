Doing work

Delegation

A subagent is Agent::run_goal running a second time, inside one Tool::invoke call, with its own registry, its own instructions and its own budget. Only text comes back. Under that text is a record of what the run actually did, composed by the harness from the loop's own log rather than from anything the subagent said.

The shape of it

Delegate is an ordinary Tool and the loop does not know it exists. Nothing in agent.rs branches on a tool's name, on ToolError::kind, or on exit status, and that holds here too: everything nesting needs, the shared token meter, the namespaced log, the subordinate terminal, is a value passed into Setup rather than a branch inside the loop.

crates/emma/src/delegate.rs — module doc; crates/emma/src/agent.rs

One delegation runs at a time, held by a one-permit semaphore, because two approval prompts racing for one stdin is a screen showing the second call's evidence above the first call's question. A subagent cannot delegate, and that is a property of construction order rather than a depth counter: child registries are built from tools resolved before Delegate exists.

The part that makes any of it checkable is the footer. A subagent's deliverable is by construction a description of work rather than the work, and asking it to cite what it read produces an assertion that looks like a verification. So the parent composes the record itself, out of what the loop wrote while the child ran, and the child's own words are never an input to it. There is a test whose scripted subagent claims in fluent prose to have read two files and run the test suite while calling no tool at all; the footer under that claim says files touched: none.

crates/emma/src/delegate.rs — the footer region; crates/emma/tests/delegate.rs::the_footer_is_the_harnesss_record_and_not_the_subagents_account

Roughly half of the tool's own description is about when not to call it. The measured direction of the effect on code-centric tasks is negative, and the description says so in its own words: reach for it when the answer is small and the evidence is large, and never delegate the check that verifies your own work.

Where the evidence stands
