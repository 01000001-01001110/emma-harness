Doing work

Delegation

A subagent is Agent::run_goal running a second time, inside one Tool::invoke call, with its own registry, its own instructions and its own budget. Only text comes back — and under that text, a record of what the run actually did, composed by the harness from the loop's own log rather than from anything the subagent said.

What a subagent is

Delegate is an ordinary Tool, and the loop does not know it exists. Nothing in agent.rs branches on a tool's name, on ToolError::kind, or on exit status, and that holds here too: everything nesting needs — the shared token meter, the namespaced log, the subordinate terminal — is a value passed into Setup, not a branch inside it. It lives in crates/emma/src/ rather than tools/ because a tool that runs the loop needs Agent, Setup, Approvals, SessionLog and Term, and putting it under tools/ inverts the dependency into a cycle Cargo refuses.

crates/emma/src/delegate.rs — module doc; crates/emma/src/agent.rs

It is not called Task. TaskCreate, TaskGet, TaskList and TaskUpdate already exist, and a fifth Task collides three times: in the model's tool list, where a nearest-neighbour mistake costs a whole subagent rather than a checkbox; in hooks.rs, where a Task.* matcher written to guard delegation would also guard every checkbox tick; and beside approval::EXEMPT, which is a const &[&str] one careless edit from exempting delegation from the gate.

The subordinate terminal is the reason a delegation does not stream. Its Mode is Batch: a delegation reports once at the end, and a subordinate Term swallows prose anyway, so streaming it would be bytes nobody reads. The sub's tool lines, notes and approval prompts still land on the parent's transcript as ordinary lines.

One at a time, and what that costs

A one-permit Semaphore is acquired before the nested run starts and held for all of it. Two subagents would mean two approval prompts racing for one stdin: decide calls prompt_header and only then ask, so two concurrent approvals interleave as A's header, B's header, A's question, B's question — a screen showing B's evidence above A's question, with one y going to whichever holds the mutex. LineSource::drain makes it worse rather than better: the second prompt discards the line typed in answer to the first. tested

crates/emma/src/delegate.rs — module doc, Delegate::permit; crates/emma/tests/delegate.rs::two_delegations_never_overlap

That test launches two invoke calls with tokio::join! and asserts the peak number of subagents inside the tool surface is 1. Removing the acquire() makes it fail — and the test's own comment records that an earlier version of it passed with the permit removed, because its script let the second run finish without ever entering the shared tool. The fix was two tool calls at the front of the script rather than one.

crates/emma/tests/delegate.rs::two_delegations_never_overlap

The cost is the obvious one: there is no fan-out. Ten independent questions are ten delegations end to end, each paying the next one's startup, and the wall clock is their sum. The permit buys nothing today — run_goal already awaits its tool calls one at a time — and what it is for is a future parallelisation of that loop failing loudly rather than quietly. The nearest prior art resolved the same collision the other way: goose refuses to run subagents at all unless approval is switched off, which is the escape hatch Emma's design rules out.

crates/emma/src/delegate.rs — module doc

Recursion is prevented by construction rather than by a depth counter. Each agent type's registry is built from tools resolved before Delegate exists, so there is nothing to forget at a call site. An inner model that asks for Delegate gets the ordinary no_such_tool observation and routes around it — including when the agent file names Delegate explicitly. tested

The boundary, and the two things that cross it

The parent sees one message. What makes that message checkable is that a second thing arrives beside it, from a different place: the parent composes the footer itself, out of the records the loop wrote while the child ran, and the child's own words are never an input to it.

Agent definitions

A delegation target is a file: <harness>/agents/<name>.md, in Claude Code's format, unchanged. The same file can also be selected as a persona by a human at startup, and the two uses have opposite selection rules — a persona is chosen by the operator, an AgentDef is chosen by the model from a closed list — so they have separate accessors and no function takes a boolean saying which it is.

Where they are found

There is no user scope for agent files, and this is the part most likely to surprise someone arriving from Claude Code. discover walks up from the working directory like git looking for .git; the nearest ancestor wins, and within one directory .emma/ beats .claude/ outright — the loser is ignored, never merged. At the home directory the rules change: ~/.claude/ is skipped so completely that it never reaches the list of places searched. It is another program's user-scope configuration — global permissions, global agents, global skills — and adopting it would hand Emma standing instructions from a directory the user never associated with this project. Only agents/ directly under the harness root is read, and only top-level *.md: a real library has subdirectories (23 of them, 205 files, on the machine this was measured against) and walking into them would flatten two namespaces into one where a collision is resolved by directory iteration order.

crates/harness/src/lib.rs — discover_in; crates/harness/src/claude.rs — agents

Permission rules are the exception that proves the rule: those are read from ~/.claude/settings.json, and only the deny list. See Consent & permissions for why. Nothing else in the user's home reaches a run.

Nothing here fails the boot. A persona is the operator's own choice at startup and a bad one is their mistake; an agent library is a directory somebody accumulated over months, and refusing to start because one file in ninety has no description is an outage. The dropped files are named instead, at startup and in emma config check.

The CRLF defect, and why nothing failed

split_agent required ---\n exactly. Every CRLF agent file therefore fell through to "this file has no frontmatter": its tools was ignored, its description was invisible so it was never offered, and its name:, model: and category: lines were handed to the model as standing instructions. Nothing errored. The file simply did not mean what it said.

crates/harness/src/claude.rs — split_agent, open_frontmatter

Counted from disk on the machine this was found on: of the 90 files in ~/.claude/agents/, 86 contain CRLF and 4 do not — so under the old opener exactly 4 of 90 parsed, and 86 were silently inert. certified The count was re-run against the real directory while writing this page.

crates/harness/src/claude.rs — split_agent (its own doc records 90 out of 90 measured as CRLF; the byte count on that directory today is 86)

What kept it invisible was the error handling, not the parser. The YAML result was unwrap_or_default(), so an unreadable frontmatter and an absent one produced the same empty value and neither said anything. split_agent now returns the YAML error as a third element, and load_agents turns it into a note naming the file — which is what surfaced the two malformed files in the run above. A leading byte-order mark is stripped for the same reason: it is the same class of silent miss, arriving from the same editors.

resolve_tools, and the default that surprises people

An agent file that names no tools key inherits every candidate tool — Write, Edit and Bash included. So do tools: [] and tools: "": all three collapse to None, and None is the signal to inherit. The argument is in Tools::allowlist — in Claude Code an absent tools means inherit everything, a present-but-empty one is the same statement written differently, and nobody writes tools: [] meaning "this agent may do nothing". An agent that really should have no tools is expressed by not registering it.

crates/harness/src/claude.rs — Tools::allowlist; crates/emma/src/delegate.rs — resolve_tools
The design said read-only. The code went the other way.

notes/design-subagents-mechanism.md §5 specifies a fixed, read-only child registry — Read, Glob, Grep and no more — and its closing "what I could not resolve" list recommends that as the default. The interface note took the same position. Neither shipped. The registry is per agent type, built from the file's tools list, and an absent or empty list inherits the writers. The design note carries a dated header saying so, so the refuted version is legible as refuted.

What bounds it: the approval gate is shared, so a sub's Write or Bash asks the same question at the same keyboard the parent's would; and the persona's own allowlist is applied to the candidate list before any agent type is resolved, so an agent type cannot be a route to a tool the operator excluded from this run. What does not bound it: nothing in the file format makes the permissive reading visible. A file with no tools: line looks like a file that has not been configured, and it is a file that can write.

notes/design-subagents-mechanism.md — header, §5, "What I could not resolve"; crates/emma/src/delegate.rs — Delegate::new, resolve_tools

When a file does name tools, unknown names are filtered rather than fatal, and this diverges from Harness::select_tools on purpose. A persona's list is the operator's own boot-time choice and a typo in it is worth refusing to start over. An agent library is ninety files accumulated for a different program: measured against a real one, its files name TodoWrite, Task, repl, artifacts and brave_web_search, none of which this binary registers, and bailing would mean Emma does not start in that directory at all. What is dropped is said out loud, per agent, in the notes emma config check prints. A type left with no tools at all is not offered.

crates/emma/src/delegate.rs — Delegate::new, resolve_tools

Matching is case-insensitive, because 14 of those 90 files spell the tools read, write, edit; Emma's tool names differ by more than case, so nothing becomes ambiguous. Registration follows registry order rather than the file's, because the tool schema rides in the cached prompt prefix and the bytes must not depend on how somebody typed a list.

The brief, and what the sub is told to deliver

The tool takes four arguments: agent (a closed enum of the resolved names), task, context (an array of short facts) and deliver. agent and task are required, and the enum is enforced in validate_args as well as declared to the model — a provider that ignores an enum must not turn this into something that runs a prompt nobody wrote. A free-text system prompt or a free-text tool list would make Delegate a self-modifying-prompt tool with a friendly description.

crates/emma/src/delegate.rs — input_schema, validate_args

brief() composes the sub's opening message: the task, then "What the agent that sent you already knows:" and the context as a bullet list, then "Your answer must contain: …" from deliver. It is composed here rather than in Goal::opening, which is the user's words and nothing else and has to stay that way — this text is not a user's words, it is a work order the calling model wrote.

crates/emma/src/delegate.rs — brief, Goal::opening

The sub runs under SubagentClaim, the second DoneCheck in the codebase and the seam goal.rs left for it. Its contract() is MarkerClaim's plus the one thing a subagent has to be told that a parent does not — that its final message is the only thing that reaches the caller, and that it will be shown a record of the files read and commands run, so a claim that disagrees with the record is worse than no claim. Its verdict() is MarkerClaim's and nothing more: a check that also judged the answer against deliver would be a heuristic in a mechanism's clothes, and a model that learns running a command ends the loop will run one. The place a deliver gets checked is the footer, by the parent.

crates/emma/src/delegate.rs — SubagentClaim; crates/emma/src/goal.rs — DoneCheck, MarkerClaim
deliver is said twice — backlog item 6

brief() appends deliver to the sub's opening message, and SubagentClaim::contract() restates it in the system prompt. The contract is cached; the brief is not. Every delegation therefore pays a cache write for a sentence the sub already has, and the fix recorded in notes/improvements.md item 6 is a pure deletion of the restatement, costing duplicate emphasis rather than the deliverable.

It is open, and blocked on measurement rather than on design: the item wants a clustering number from real sessions, and the session corpus holds one delegation record in total. Delegation is barely used, so "it unblocks itself with use" — the earlier conclusion — was false for the metric this item needs.

notes/improvements.md item 6; crates/emma/src/delegate.rs — brief, SubagentClaim::contract

The footer, which the subagent did not write

A subagent's deliverable is a description of work rather than the work. The failure that produces is documented rather than hypothetical, in Claude Code's own tracker: "subagents imply they read file content but demonstrably did not — they infer behavior from filenames, variable names, or comments instead of tracing actual code logic" (anthropics/claude-code#40339, closed as not planned). Requiring the subagent to cite what it read is an improvement and is still an assertion wearing a verification's clothes: a run that hallucinated a conclusion will hallucinate a plausible list of files to go with it.

The ending is the first line

Ending::Tokens and Ending::Done leave the same confident final paragraph, and without this line the parent cannot tell a finished run from a truncated one. Anything that is not done or answered also gets a sentence saying to read what follows as partial, and a run with no record of how it stopped says "unknown — no record of how this run stopped" rather than implying success. tested

Files touched, not files read

The word changed because Write and Edit carry file_path too, so a written file has always landed in that list — and under the inherit-everything default above, a subagent with Write is the ordinary case rather than the exotic one. Splitting read from written would need the tool-name knowledge this file has refused; the neutral word costs nothing and stops the over-claim. The JSONL field kept its old name files_read, because emma agents reads these keys and renaming a field to match a rewording breaks a consumer for nothing.

crates/emma/src/delegate.rs — Facts::footer, the delegation record

An exit status is read only from where Bash puts it

Bash writes exit status <n> as the first line of its result content, and exit_status parses that line and nothing else. Prose that merely mentions an exit status — "the command exited with status 0", which is what a model writes — yields None. A footer line reading cargo test → exit 101 beside a final message reading "the tests pass" is a contradiction the parent can see, and it is the most common lie a coding subagent can tell. tested

The test asserts four things. That the sub's tool was called zero times. That the claim reaches the parent verbatim — it is not censored, because the subagent's own account is what the caller asked for. That the footer says files touched: none and commands run: none. And that the string cargo test → exit appears nowhere, so the footer has not echoed the model's account of a command back as if it were a record. What the footer proves, and what it does not

It proves what was looked at, what was run, and how the run ended. It does not prove the conclusion follows from any of it. The worst case of this design is that the footer becomes the thing everyone trusts: done · 14 files · 3 commands reads like verification and is only attendance. It reports counts rather than adjectives for that reason, and nothing anywhere claims the conclusion was checked.

How the spend charges the parent

Spend::child makes a meter of its own that also charges its parent. add walks up the chain — the parent is charged first, then the child's own counter — so the sub's spend appears in both numbers at once. set does not walk: it is the per-goal reset, and it is local. That asymmetry is the whole point. If set propagated, a nested goal starting would zero the process's meter; if add did not, a delegation would be a way to spend past the parent's cap. A 100-token parent call, a 7,000-token sub call, a 300-token sub answer and a 100-token parent answer come to 7,500 on the parent's meter and 7,500 in the goal's outcome. tested The agent loop covers Spend, the three different token numbers and what a resume restores.

What the gate sees

Delegate declares read_only: false unconditionally, including when the agent type's tools are entirely read-only: the tool set is configuration, and a meta() varying with it would mean the gate's answer depends on a file the reviewer is not looking at. The prompt shows the agent type and the first twelve lines of the brief. reaches_network: false is the arguable one — a delegation certainly calls the model — and it is Bash's precedent: egress is gated at the leaf, where the host is known, in the same process against the same hosts_allowed set, not at the delegation, where the host is not known. Declaring true would produce a prompt to approve api.anthropic.com whose only possible answer is yes, which is how an operator learns to answer without reading. tested

emma agents

emma agents reads every *.jsonl in the session directory, keeps the delegation records, and prints what each agent type has actually cost. It calls no model, loads no harness and needs no API key — it returns from main before the runtime is even built, which is what lets it answer when the thing being investigated is why a run will not start. certified — run below from a directory with no harness above it.

When the model is told not to reach for this

Roughly half the tool's description is about when not to call it. The measured direction of the effect on code-centric tasks is negative — 49–54% single-agent against 10% and 3% multi-agent on SWE-bench Lite, at nine times the spend — and Anthropic's own multi-agent write-up carves coding out of its own headline result. A feature nobody calls costs a paragraph of prompt; a feature called for two-file questions costs a multiple of every goal. The description's own rule: reach for it when the answer is small and the evidence is large, and never delegate the check that verifies your own work — run that yourself and read its exit status.
