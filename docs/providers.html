Providers & models

One trait, one implementation, and a lot of care about bytes. Everything Emma knows about the Anthropic Messages API lives in crates/llm; the loop sees a Request go in and an AssistantTurn come out. Two of the mistakes documented here were invisible to a green test suite. One was invisible to everything except the invoice.

The shape of it

Rust has no official Anthropic SDK, so I had this crate speak the Messages API over raw HTTP, the documented path for unsupported languages. Four providers exist now: Anthropic, Ollama, and OpenRouter and OpenAI over one OpenAI-compatible wire, ported from the fork on 2026-09-06. The seam I wanted is that a second provider is a new file rather than a refactor of the loop: nothing outside anthropic.rs knows the wire shape, and ollama.rs is what proved it. That took deleting a serde_json::Value field off the turn type and typing every content block instead.

Two things you should carry into the sub-pages. First, the ordering: a Request names instructions, tools, history and query in that order because the provider's cache is an exact prefix match, and anything varying per turn has to sit after everything that does not. Second, the direction of a guess: when Emma does not know a model, it guesses a low output ceiling and a high cache floor. The first failure is a 400 you see. The second is a bill nobody sees.

The pages

  1. The boundary, and the request that crosses it Two methods on one trait, the four-part request whose field order the cache depends on, and render, the last point every request passes through however it was built.
  2. Typed content blocks The module that deletes one field, and the strict decoder that passed 712 tests, produced identical bytes, and then decoded no real tool call because every tool_use carries a key nothing here had read about.
  3. The turn that comes back Usage, whose input_tokens field is not the input, and the SSE state machine that has to assemble the same turn a single JSON body would have produced, signature included.
  4. What a model will take Ten rows of ceilings and effort sets, why the effort levels are a set rather than a maximum, and why an unknown model gets 8,192 tokens rather than the newest row's 128,000.
  5. Prompt caching, and the three breakpoints The arithmetic that put caching on by default, where the three cache_control markers land and what each is gated on, and the query that would settle whether any of it is paying.
  6. The cache floor, and why there are two tables A provider feature that is accepted, inert, and invisible except on the invoice; the ten floors, of which two have been measured; and the three reasons the two per-model tables are not one.
  7. Retry Four attempts, a doubling curve capped at twenty seconds, which HTTP statuses are worth sending again, and the rule that nothing after a successful response is ever retried.
  8. Where the key comes from The claude engine: a goal handed to another program Environment, then ~/.emma/credentials.json, never the project directory. The write that silently deleted a key belonging to another part of the program, and the redaction that moved into Display after an audit found two paths it never covered.

What is not verified

Ten claims across this chapter carry an amber mark, and they cluster. Two tables were transcribed from documentation on 2026-08-11 and never measured: every row of models::TABLE, and eight of the ten rows of MIN_CACHEABLE. Two live measurements exist and cannot be reproduced, because no request or response body from them survives: the cache-floor bisections, and the credentials write that lost a key. Four clauses of the caching contract, including the API's 20-block backward lookback and the TTL clock starting at request start, are read from documentation and have never been run against. And two questions wait on a corpus that does not exist: whether breakpoint 3 pays for itself, and whether the 5-minute TTL beats the 1-hour one for Emma's cadence.

Each page states what would settle its own; the site-wide collection is on what is not verified.
