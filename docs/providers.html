crates/llm

Providers & models

One trait, one implementation, and a great deal of care about bytes. Everything Emma knows about the Anthropic Messages API lives in crates/llm; the loop sees a Request go in and an AssistantTurn come out. This page is mostly about the two places that boundary has been wrong in ways a green test suite could not see.

certifiedproven, and a reader can repeat it: a file, a command, a frozen fixture
observedseen once, live, not repeatable on demand
testeda test that has been shown to fail
unverifiedbelieved, not checked

The boundary

Provider has two methods: model_id() and send(request, mode, events). That is the whole surface between the agent loop and any model anywhere. Mode chooses between one JSON body and a stream of SSE frames, and both produce the same AssistantTurn. The difference is only whether the caller receives Event::TextDelta on the way. The events channel is optional in both modes, and a Batch call still emits Event::Retrying, because a retry the user cannot see is indistinguishable from a hang.

crates/llm/src/lib.rs — Provider, Mode, Event

A request names its four parts in prefix order

Request is instructions, tools, history, query, in that order, as four fields rather than one message list. The reason is the provider's cache, which is an exact prefix match: anything that varies per turn has to sit after everything that does not. Keeping history and query apart is what lets the renderer find the end of the stable part without guessing.

why a struct and not a convention

The ordering is a type rather than a comment in the renderer specifically so that building a request with a per-turn byte at position zero is not expressible. A convention in a comment is one that a struct literal elsewhere in the loop can ignore, and one did, for max_tokens, which is why the model clamping below happens at the wire boundary instead.

crates/llm/src/lib.rs — module doc, Request

Two of a Request's fields are asks rather than settings. max_tokens: 32_000 and effort: XHigh are what Emma would like; AnthropicProvider::render lowers both to what the chosen model will actually take, because Request does not know which model it will be sent to and render is the last point every request passes through however it was built.

crates/llm/src/anthropic.rs — AnthropicProvider::render

What comes back, and the field that is not what it says

An AssistantTurn is Vec<ContentBlock> plus a stop reason plus Usage. text() and tool_calls() are views onto the block list rather than fields beside it. They used to be stored separately, which is two things that can disagree about what the model said.

usage.input_tokens is not the input

With caching in play the API splits input three ways and input_tokens carries only the uncached remainder. In tustle-agent, where this was learned, a 72,549-token turn was recorded as input_tokens: 2. The figure meaning "the context this call carried" is billable_input_tokens(): input + cache_creation + cache_read; a cap folded from the bare field instead loosens by up to ~10× once caching starts hitting. Usage carries no total(), so the two summing methods are the only ways to get one. tested

crates/llm/src/lib.rs — Usage, billable_counts_all_three_input_fields

A scripted provider drives the loop with no socket and no key

Because Provider is the whole boundary, the agent loop's test suite runs against Fake, a struct holding a VecDeque<Say> of scripted turns and a Vec<Request> of everything it was sent. Each Say is some text, some tool calls, a token count, and an optional fail that answers with LlmError::BadRequest instead of a turn. Running out of script is itself a BadRequest, so a test that calls the model more times than it meant to fails rather than quietly ending the goal.

Two details of the fake come from things that went wrong live. It emits a signed thinking block on every turn, so the assertion that the loop hands a turn back untouched is asserting about a turn with something fragile in it. And every scripted tool_use block carries extra: {"caller": {"type": "direct"}}, because the real API sends that key and a fake without it would not reach the path a live run found broken. That path is the next section.

crates/emma/tests/support/mod.rs — Fake, Say

Typed content blocks, and the most expensive test pass in this repository

content.rs exists to delete one field. AssistantTurn used to carry raw_content: serde_json::Value, Anthropic's content array, echoed back on the next call without ever being read, and the loop built its own {"type":"tool_result",…} objects to answer it. Between them, those two facts meant a second provider would have been a refactor of the loop rather than a second file beside anthropic.rs.

The blob was not laziness. This model family rejects a thinking block whose signature has been re-derived, so a turn rebuilt from text plus tool calls makes the next call fail, and the cheapest way to guarantee byte-fidelity is to never look inside. The shape that replaces it is taken from goose (Block, Apache-2.0): opaque provider state becomes a narrow named field on an otherwise fully typed block: ThinkingBlock { thinking, signature }.

crates/llm/src/content.rs — module doc, ThinkingBlock

The strict version. 712 tests, clean clippy, identical bytes, dead agent.

The first version of this module decoded strictly: deny_unknown_fields everywhere, and any block carrying a key the client did not model was demoted to Passthrough, kept whole, kept verbatim, but no longer a typed thing the loop could act on. It passed everything. All 712 tests, clippy clean, and the rendered request bytes identical to the version it replaced.

Then it was called for real. The Messages API returns every tool_use block with a caller key, documented nowhere this client had read: 

{"caller":{"type":"direct"},"id":"toolu_01FJxk…","input":{…},"name":"Read","type":"tool_use"}

Under strict decoding that block was not a tool call. It was an unrecognised blob. The bytes round-tripped perfectly, the loop saw zero tool calls in a turn that contained one, took the success path, and a real goal ended on turn one reported as "answered — no tools were needed". certified, observed on a live call, 2026-08-11; the exact block is frozen as a fixture in a_real_tool_use_block_is_a_tool_call_and_still_round_trips.

crates/llm/src/content.rs — module doc; commit 482a2cc

Nothing was malformed, nothing errored, no status code was wrong, and the harness reported success. A green suite is not evidence that a wire format still talks to the provider. The suite agreed with its author about what a tool_use block contains, and its author was out of date by one undocumented key. The detector was a live call.

Two escape hatches

There are two mechanisms rather than one, covering opposite failures:

  • An unknown block type becomes ContentBlock::Passthrough, kept exactly as it arrived. There is nothing to interpret, so nothing is lost by not interpreting it. server_tool_use and web_search_tool_result are the next real instances arriving.
  • An unmodelled key on a known type keeps its variant, and the key goes into that block's extra map, echoed back untouched. This is the case the live call above failed on: the bytes were kept and "this is a tool call" was lost.

extra is written only by ContentBlock::from_value, read only by to_value, and nothing branches on its contents. A key Emma needs to act on becomes a field promoted out of it rather than a lookup into it. with_extra inserts rather than merges, with a debug_assert! that fires if a provider key would overwrite one the typed block already renders.

crates/llm/src/content.rs — from_value, with_extra

The bytes were compared rather than assumed: commit 4645d5e was rebuilt from git archive, both trees rendered one request exercising every content shape: all three cache breakpoints, signed and unsigned thinking, redacted thinking, an unknown block type, tool_result with and without is_error, and a caller key. The two outputs were compared. 6,410 bytes, identical. certified That request is frozen as the_whole_request_body_is_pinned_byte_for_byte, a single golden string. It catches the class of change the placement tests cannot see: a byte that moved inside a block, such as a signature that stopped being emitted or an is_error that started being emitted as false.

Whether a signature survives a mid-session model change is untested here, and an in-session /model is the first thing that would need to know. What a model will take

models.rs answers one question: which of the values in this request are properties of the model rather than of the request? Two are. max_tokens has a per-model ceiling and a request above it is an HTTP 400 before a token is generated. output_config.effort names a level not every model implements, and an unimplemented level is the same 400. Both were single constants until a user could choose a model, at which point the first call on the wrong choice failed for a reason nobody had asked about.

crates/llm/src/models.rs — module doc

efforts is a set, not a ceiling

Limits { max_tokens, efforts } stores the effort levels as a slice rather than a maximum, because the ladder has holes. Opus 4.6 supports max but not xhigh, which arrived one model later with 4.7. A ceiling comparison would look at "supports max" and send xhigh, which is a 400. Effort::rank() is a method rather than a derived PartialOrd for the same reason: a < b would compile everywhere and mean nothing, since a model's supported set has gaps.

clamp_effort therefore returns the best supported level at or below the ask, or None. An xhigh ask on Opus 4.6 lands on high, not on max. None means send no output_config at all, never "send low". On Sonnet 4.5 and Haiku 4.5 the field's presence is itself the error, and clamping upward to "the nearest supported" would send a model harder than the caller asked for, which on a Low request for a cheap subagent is the bill they were avoiding. tested

crates/llm/src/models.rs — clamp_effort, a_model_without_xhigh_is_never_sent_xhigh

clamp_max_tokens only ever goes down. A request asking for 32,000 on a 128,000 model still sends 32,000: the ask is a budget as well as a limit, and raising it would spend the user's money for them. tested

crates/llm/src/models.rs — the_ask_is_never_raised_to_the_ceiling

Longest-prefix keyed, and the unknown model guesses low

The table is keyed by prefix rather than equality, so claude-haiku-4-5-20251001, the dated spelling the console hands a user, resolves to the same row as its alias. max_by_key(id.len()) makes the longest match win, and no_row_shadows_another asserts that no id currently prefixes another, because a row like claude-opus added later would silently swallow every Opus and no other test in the file would notice. tested

A model the table has never heard of gets UNKNOWN { max_tokens: 8_192, efforts: &[] }. Three answers were available and the asymmetry between their failures picks the winner:

Answer What goes wrong
Assume it is as capable as the newest known model HTTP 400 on the first call. No answer at all, and an error naming a value the user never set.
Refuse to run against an unknown model Every new model release becomes a bug in Emma. The user who typed the id is likelier to be current than the table is.
A conservative floor (chosen) A long answer truncates at 8,192 and effort falls to the provider's default. Degraded, but it still produces a turn, and one row fixes it.

8,192 is the smallest output ceiling any Anthropic model has shipped with, so no known model rejects it; efforts: &[] means no output_config is sent, which every model accepts. The cost is stated where the constant lives: a user on a brand-new Opus gets 8,192 tokens and default effort until somebody edits the file. This fallback guesses low; the cache table below guesses high, from the same reasoning about which failure is recoverable.

Prompt caching

Emma has no corpus. The only stable prefix is the instructions plus the tool schema, a few thousand tokens, not fifty, so caching had to be argued rather than assumed. At list price, with the published multipliers (write 1.25×, read 0.1×) and a 512-token floor on claude-opus-5:

  • A 2,000-token prefix costs +500 token-equivalents to write once.
  • Every later call that reads it saves 1,800.
  • Break-even is therefore P(at least one more call reads this entry inside the 5-minute TTL) ≳ 0.28.

A coding turn is never one model call: the model reads a file, gets the result, and is called again seconds later. P is effectively 1.0, so the write pays back on the second call of the first turn. That is why caching is On by default, and why --no-cache exists: so the claim can be measured rather than believed. The saving is smaller than tustle-agent's measured 84%, because there the cached prefix was a 33k-token corpus; here the prefix is small and the real money is in the conversation, which is why the history gets a breakpoint too.

crates/llm/src/anthropic.rs — module doc §"Caching, and whether it is worth it here"

Where the three breakpoints sit

crates/llm/src/anthropic.rs — system_field, messages_field, mark_breakpoint

The placement is pinned in three directions: breakpoints_land_on_the_stable_prefix_and_nowhere_else asserts exactly two markers before any tool call and none on the query; a_turn_already_using_tools_marks_its_newest_result asserts the third appears on the tool_result once a round-trip is in flight; and the golden-body test pins all three as literal bytes. tested

The 0.28 threshold says a marker on the query needs P(another call) ≳ 0.28 to pay for its write, and the reason for gating on query.len() > 1 is that a coding turn which has already called one tool usually calls another: reads, then edits, then runs the tests. That second half is a judgement, not a measurement. unverified It is settled by counting first-call cache_read_input_tokens against cache_creation_input_tokens in real session records; the arithmetic is below, and the corpus to run it on does not exist yet.

The TTL is the 5-minute default rather than the 1-hour variant, which doubles the write price and only pays at three or more reads per entry. unverified Emma has no measured session cadence that would justify it; the note in the code says to revisit with cache_read_input_tokens data rather than with intuition.

crates/llm/src/anthropic.rs — ephemeral; notes/research-caching-mechanics.md §TTL

Three of the four markers, and two constraints nobody here has tested against

The API allows four explicit breakpoints per request, counted across tools, system and messages together, and exceeding it is a hard 400. Emma uses three and keeps one spare. The fourth was considered and declined: there is no stable boundary left for it to sit on.

Three other clauses of the caching contract go unaccounted for. unverified in every case: they are read from Anthropic's documentation as fetched 2026-08-11 and nothing here has been run against them.

  • A cache read walks back at most 20 content blocks looking for an entry a prior request wrote. A single agentic turn with many tool_use/tool_result pairs can add more than 20 blocks, which would push the new breakpoint out of range of the last write; the documented remedy is an intermediate breakpoint roughly every 15 blocks in long turns. Emma places breakpoint 3 on the newest result only, however many rounds a turn has taken. Settling it means a long tool-heavy turn against the real API, watching whether cache_read_input_tokens collapses past the twentieth block.
  • The TTL clock runs from request start, not response end. A five-minute entry written by a call that then thinks for four minutes leaves about one minute of usable life. High-effort turns on Opus 5 are exactly that shape, so some fraction of writes may be expiring before the next call begins.
  • An entry is readable only once the first response begins streaming. N identical requests fired in parallel all pay the full write price. Emma's own loop is serial, but delegation means several subagents can be in flight at once.
notes/research-caching-mechanics.md §3, §TTL; notes/audit-caching-emma.md §"Explicitly not proposed"

The floor: a feature that is accepted and inert

Below a model's minimum cacheable prefix a cache_control marker is accepted and silently does nothing. Not rejected. Not warned about. HTTP 200, a normal response body, and cache_creation_input_tokens: 0. The marked span is billed at the uncached rate, and there is no symptom anywhere except the invoice.

observed, not argued

A 3,001-token prefix on claude-haiku-4-5 with the marker present returned 200 OK and cache_creation_input_tokens: 0, twice. Each floor was then bracketed by a pair of prefill calls about 30 tokens either side of the documented value, sized with count_tokens so that "3,000 tokens" meant real tokens rather than chars/4: 

claude-haiku-4-5: 4069 tokens, marker present -> cache_creation = 0
claude-haiku-4-5: 4129 tokens, marker present -> cache_creation = 4122

Haiku 4.5's gate opens between 4,069 and 4,129 real tokens; Opus 5's between 483 and 543. Consistent with the documented 4,096 and 512. Under a cent for both models. observed: bisected live against the API, 2026-08-14; no raw request or response body was kept, only the printed pass/fail lines above.

What is written down is the result, not a transcript. No raw request or response body from those calls survives in notes/: the record is the status line above and the two-line table, which is the whole of it.

notes/lessons/a-provider-feature-can-be-accepted-and-inert.md; commit bb78857

Every reflex in this codebase for catching a wrong request is tuned for a 400. models.rs exists because too high a max_tokens is a 400; retry.rs classifies by status; the wire tests assert the bytes that avoid a 400. None of that machinery can see this one, because there is nothing to see: the same status, the same body shape, and a field that is 0 instead of a number. A single MIN_CACHEABLE_TOKENS = 512 had been wrong for every non-Opus-5 model since it was written, and no test, no log line and no status row had a way to say so.

The generalisable part: when a provider feature is advisory rather than mandatory, its failure mode is silence, and the only detector is the usage counter it was supposed to move. A test asserting that the marker was sent passes forever; a test asserting that the marker moved the counter runs only against the real API.

One detail the project's own notes disagree on, so this page will not pretend otherwise: whether an ignored marker costs anything directly. notes/plan-caching-defects.md describes it as "+25% on the marked span, forever"; notes/research-caching-mechanics.md says a below-minimum prefix is "cost-neutral (marker ignored), not negative — but they add the false belief that caching is on". unverified The reconciliation that fits both is that the marker is ignored, so no write premium is charged, and the loss is the read discount that never arrives on a span the user believed was cached. Which of the two is literally true is settled by one usage row from a below-floor call: if cache_creation_input_tokens is 0 and the span appears in input_tokens at base rate, the research doc is right.

An unknown model guesses high here

MIN_CACHEABLE_UNKNOWN = 4_096, the highest floor anyone ships. That is the opposite direction from models::UNKNOWN's low ceiling. The two failures:

  • Guess too low and the defect comes back: markers on prefixes under the real floor, the span billed uncached, no symptom anywhere except the invoice, unbounded in time.
  • Guess too high and an unknown model whose real floor is lower goes unmarked while its estimated prefix sits under 4,096 tokens (~16 KB rendered). The cost is a forgone read discount, cents per call, and it ends by itself, because history grows past the threshold within a few turns.

an_unknown_model_is_gated_at_the_highest_known_floor pins both halves: an unknown model gets no markers on a ~700-token prefix, and gets them back once the prefix clears 4,096. That is a gate, not a refusal. tested

Why there are two tables and not one

models::TABLE and anthropic::MIN_CACHEABLE name the same ten models, and a model release adds a row to each. Merging them is the obvious tidy-up. Three things break if they are merged:

  • Limits is the struct GET /v1/models parses into. A discovery stage swaps the lookup for that call and leaves the clamping alone; a merged struct could not be swapped, because the endpoint cannot fill it.
  • That endpoint reports no cache minimum. The floor cannot follow the other values into discovery, so it would remain hand-maintained inside a struct that had otherwise stopped being.
  • The two fallbacks argue in opposite directions. models::UNKNOWN guesses low because too high a ceiling is a 400; MIN_CACHEABLE_UNKNOWN guesses high because too low a floor silently overpays. One shared UNKNOWN would carry a doc comment arguing both ways at once.
crates/llm/src/models.rs and crates/llm/src/anthropic.rs — module docs; notes/lessons/a-provider-feature-can-be-accepted-and-inert.md §"Fallback direction"

What the split costs

A model release means a row in both tables, and for a while nothing in the compiler noticed when only one was added. Each table had an internal-consistency test and neither could see the other, so adding a model to one and forgetting the other compiled, passed, and went wrong quietly. The architecture map found that gap the same day the second table shipped, in the same work that argued for the split.

both_per_model_tables_name_the_same_models is the guard. It compares the two row sets and fires in either direction with a different message, because the two failures are not symmetric:

Missing from What happens Who notices
MIN_CACHEABLE Gated at 4,096; caches less than it could have. Visible on an invoice, self-heals as history grows.
models::TABLE Clamped to the 8,192 ceiling; a legitimate long answer is silently truncated. Nobody. This is the one that costs a user something they cannot see.

Both directions were mutation-proven: dropping the Haiku row names it and says the floors table is short; adding a model to the floors table alone names it and says the limits table is. Is caching actually paying?

The three usage fields make this answerable exactly, from records already on disk, with no second run and no estimation. Against the no-cache counterfactual, the same request with no markers, which sends byte-identical content by construction: 

// p = the model's base input price
actual          = p · (1.0·input + 1.25·write + 0.1·read)
counterfactual  = p · (1.0·(input + write + read))

savings         = p · (0.9·read − 0.25·write)

write is cache_creation_input_tokens, read is cache_read_input_tokens. The multipliers are the two premiums: a cached read costs 0.1× of base, so it saves 0.9×; a cached write costs 1.25×, so it loses 0.25×. Emma sends only 5-minute markers, so the general form's − 1.0·write_1h term drops out.

The number goes negative exactly when the harness is paying write premiums it never reads back. That is what a broken prefix produces, and what the accepted-and-inert defect above produced for every non-Opus-5 model. It does not credit latency, and it assumes the no-cache run would send the same bytes, which is true here because it is the same request.

notes/plan-caching-defects.md §"Stage A — measure, from data already on disk"

Two companion views sit alongside it. Cached fraction, read / (input + creation + read), is a health gauge rather than a cost claim, and reads low at the start of a session where history is small, so the tail is the part that means anything. And an expected-hit regression: within a TTL, call N should read at least what call N−1 established, which catches a change that silently breaks the prefix.

For a sense of the target: Claude Code sessions measured in the wild ran a 97.2% cache hit ratio, 40M cache-read tokens against 653K direct input tokens across eight sessions. unverified That is a third party's number for a different harness, quoted as a magnitude to aim at rather than a bar Emma has been held to, and nobody has computed the same ratio for a real Emma session.

One known thing will drag that number down and cannot be fixed with breakpoints: compaction invalidates the message half of the prefix entirely, every time it fires. The first call afterwards re-writes what it would have read, at 1.25× instead of 0.1×. No placement of markers avoids it, because the bytes genuinely changed. That mechanism belongs to sessions & context; it is named here because it is the largest single term in Emma's caching bill and a reader watching the arithmetic go negative should suspect it first.

notes/audit-caching-emma.md §"Does it invalidate the cached prefix?"

Retry

Four attempts, 500 ms base doubling per attempt, 20-second cap. max_attempts counts the original: 4 means the first try plus three retries. Three rules, and the third is the one that matters for a terminal program:

  • Only retry what a retry can fix. 429, 5xx and transport failures. A 400 is the request being wrong, and sending it again is a slower way to get the same error. tested
  • Believe retry-after. It overrides the curve entirely, because the provider is the only party that knows when the bucket refills, but is still clamped to the 20-second cap, because retry-after: 3600 for an interactive tool means "tell the user now", not "sleep for an hour". The header is carried on RateLimited only; a 5xx that happens to send one backs off on the curve, since 429 is the case the API documents sending it for and widening it would be guessing. tested
  • Make every attempt visible. Event::Retrying carries the attempt, the ceiling, the delay and the reason, in both batch and streaming mode. A forty-second silence is indistinguishable from a hang, and a user who cannot tell hits Ctrl-C and loses the work.

retry_after_seconds parses the seconds form only. The HTTP-date form is legal and the Messages API does not send it; mis-parsing a date into a duration is worse than ignoring it and backing off on the curve. tested

crates/llm/src/retry.rs — Retry::delay_for, retry_after_seconds

One boundary is drawn in execute rather than in the policy: once the response is a success, nothing is retried. Past that point bytes may already have reached the terminal, and a retry would replay text the user has read. A mid-stream failure is surfaced.

crates/llm/src/anthropic.rs — AnthropicProvider::execute

Where the key comes from

Two sources, in order: the environment variable for that provider, then ~/.emma/credentials.json. Never the project directory. Emma works inside repositories, and a key written next to the code is a key that gets committed. The first person to notice is usually the scanner that finds it in a public push. Nothing in auth.rs resolves a path relative to the current directory: the home path is computed, never searched upward, and a_credentials_file_in_the_project_directory_is_ignored plants a real credentials.json in a scratch cwd and asserts it is not found. tested

An exported-but-empty variable is not a key. ANTHROPIC_API_KEY= in a forgotten .env falls through to the stored file rather than authenticating with "" and earning a 401 the user cannot explain. tested

crates/llm/src/auth.rs — resolve, from_env

Two shapes in the file, and only one is written

The current shape is keyed by provider: 

{
  "providers": { "anthropic": { "api_key": "…" } },
  "brave_search_api_key": "…"          // the web tools', same file
}

The file used to hold exactly one key under a flat top-level api_key, and read_keys still reads that spelling, for as long as anybody has a file written by the old emma api, which is one machine and no expiry date. It can only ever have meant Anthropic, since nothing else was implemented when it was written. Reading is what migrates; nothing rewrites the file for having been read. The keyed shape wins over the legacy field for the same provider, and the first store carries the legacy value across and drops the flat key, so there is never a file with two answers for Anthropic. tested

crates/llm/src/auth.rs — read_keys, store, a_key_written_by_the_old_emma_api_still_reads
the scar: a write that deleted a key it did not know about

store used to write a fresh document. The Brave Search key lives in that same file, at the top level, put there by an unrelated part of the program, so every emma api call silently deleted it. Nothing errored. The symptom arrived later as a tool that had stopped being registered, with no connection to the command that caused it.

store now reads, replaces one provider's entry, and writes back everything else. It also refuses a credentials file it cannot parse rather than overwriting it, for the same reason: overwriting is exactly how the other keys got lost. observed: checked once against the owner's real ~/.emma/ around the da0352a fix (2026-08-11), backed up and restored by hand, with the Brave key intact afterwards. The same shape is covered on demand by a_key_written_by_the_old_emma_api_still_reads (crates/llm/src/auth.rs), which writes a fixture file carrying both keys and asserts the Brave key survives a write. tested

crates/llm/src/auth.rs — store; commit da0352a

Every key in the file is built through ApiKey::new at load, including the ones nobody asked for. That constructor registers the secret in a process-wide scrub list, so a provider switched away from an hour ago cannot have its key printed by an error raised now. Loading them and dropping them would be the same read with the protection turned off. tested

The scrubbing itself lives in LlmError's Display and Debug impls rather than at each site that builds a variant. It moved there after an audit: AnthropicProvider holds the key and scrubbed what it built; Assembly::apply and turn_from_message are free functions the key was never handed to, so they built Api variants out of raw provider prose, and the class-level promise read as held while two paths did not hold it. Formatting is the one path every variant from every site takes to reach a terminal or a log.

Three things it does not cover, named in the code: reading err.message directly still gets the provider's bytes on those two paths; a key this process never wrapped in ApiKey is not in the list; and an echo that is not byte-identical (base64ed, truncated, re-cased by a gateway) defeats a substring replace.

crates/llm/src/lib.rs — impl Display for LlmError, remember_secret

The scrub list recovers a poisoned lock rather than propagating the poison, and a test poisons the lock from another thread and then checks that formatting still scrubs. The first version propagated, which meant one unrelated panic anywhere in the process turned redaction off for every error printed for the rest of the run: a security control degrading to no control, on a condition nobody observes. The recovery holds only while the data behind the lock has no invariant a panic could break, which a Vec<String> does not. tested

crates/llm/src/lib.rs — secrets, a_poisoned_scrub_list_still_redacts

On disk the file is created 0600, created that way rather than created-then-chmodded, because between those two calls the key is world-readable, and a file whose mode allows group or other access is refused rather than warned about. On Windows there are no mode bits: check_permissions returns Ok(()) and write_private is a plain write into the user's profile, whose default ACL already excludes other users. unverified The two unix permission tests have never been run on the owner's machine: they are compile-checked only. Settling that takes one cargo test on a unix box.

crates/llm/src/auth.rs — write_private, check_permissions

Which provider, as a value

ProviderKind is separate from Provider because it answers questions that come before a key or a model exists: a name, an environment variable, a default model, and how to build one. emma set-provider has a name and nothing else. KINDS holds one entry, and that list is what an unknown name is measured against and what the error message quotes.

An unknown name is an error, never a fallback. emma set-provider antropic quietly running on Anthropic would look exactly like a correctly-set one until the bill or the output said otherwise, and there is no way to notice in between. Names are matched case-insensitively (Anthropic is not a different provider) and nothing else is normalised: a typo is a typo and gets the list. tested

crates/llm/src/kind.rs — kind, a_misspelled_provider_is_refused_and_told_what_exists

base_url is never read from the environment. It is settable only through with_base_url, at construction. An environment variable that redirects where the key is sent is a credential-exfiltration switch, and Emma runs inside repositories with whatever environment the shell carries.
