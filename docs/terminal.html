Surface

The terminal

Emma draws two different things. One is a full-screen application on the alternate screen, with a sidebar, a retained conversation buffer, a pinned input dock and a status bar. The other is a stream of lines with no escape byte in it. The second one runs whenever the first cannot, and most of the rules in this subsystem are about the seam between them — and about giving the terminal back exactly as it was found.

Two surfaces, one vocabulary

Every write to the screen goes through one Term, and one field decides which surface it lands on: frame: Option<Arc<Frame>>. Some is the drawn frame; None is the whole fallback. Both paths render the same Line values from the same Skin, so a change to the vocabulary reaches both or neither. render.rs gives the reason for the single renderer: “Two renderers would mean the frame and the fallback drifting apart, and the fallback is the product.”

crates/emma/src/term.rs — struct Term; crates/emma/src/term/render.rs module doc

Whether to draw at all is a pure function of five inputs, kept separate from the drawing. Getting it wrong in one direction is invisible; getting it wrong in the other produces “a garbled terminal on somebody else’s machine, or a file full of escape sequences.”

stdout not a tty "stdout is not a terminal" Escape sequences ending up in somebody’s file.

crates/emma/src/term.rs — fallback_reason, MIN_ROWS, MIN_COLS

Windows adds a sixth gate that is not a question but a change. Frame::install reads the console mode, sets the virtual-terminal bit, reads it back, and falls back unless it stuck. The read-back matters because the bit also selects which of crossterm’s two code paths runs: with VT on it writes escape sequences, and without it makes WinAPI calls in screen-buffer coordinates — and on Windows the buffer is usually far taller than the window, so a repaint aimed at “row 40” of a nine-thousand-row buffer goes somewhere invisible. The UTF-8 output code page follows the same shape: set it, read it back, believe only the read-back. Detection alone was tried and was useless — a normal PowerShell window reports code page 437, so the answer was always no and the box was always +---+. The code page is changed only for a run that will draw; “changing a code page on a console nobody is looking at is a change to somebody’s shell for no benefit at all.” tested

The regions

The full-screen frame carves the window in one function: regions(area, sidebar_w, dock_h) -> Regions. The two inputs that depend on state — how wide the sidebar is, how tall the dock needs to be — are computed before the call, so the carve itself is arithmetic over three numbers and runs without a terminal.

crates/emma/src/term/app.rs — regions, struct Regions

The proportions come from pixel measurements of notes/mockup-tui.png rather than from any description of it. app.rs gives the reason for going back to the image: “the prose description of that image was wrong in five recorded places, and the design note’s §1.1 sampled table, though pixel-derived, still missed three facts.” One of the three is the two columns of ground between the panes — “sidebar right edge ≈338px, main pane left edge ≈362px, at ≈11.3px per cell — two columns, not shared borders.” tested

crates/emma/src/term/app.rs — PANE_GAP_COLS, test the_pane_gaps_measured_from_the_mockup_are_in_the_carve

The dock is not a widget of its own. It is a rectangle that View’s existing renderers paint into — the same render_input and render_prompt the inline viewport uses, marked pub(crate) with the argument attached: “a consent interface with two renderings is two interfaces.” When a question is pending the approval panel replaces the input box in that rectangle, so no amount of output can move either. tested

crates/emma/src/term/app.rs — App::render; crates/emma/src/term/view.rs — render_input, render_prompt; test a_pending_question_replaces_the_input_box_and_stays_on_screen

The sidebar collapses on a latch. Below 100 columns it collapses automatically; Ctrl-B sets by_user, which wins in both directions. An automatic collapse un-collapses when the window widens again, and that follows from by_user being false rather than from a second rule. A collapsed sidebar has no cells and therefore no click target; the way back is the key. The SESSIONS header row is also a click target, and the whole row rather than the [+]’s three cells, because “the affordance’s exact columns are the sidebar’s internal layout, which this file does not own, and a three-cell target at a guessed offset is a miss magnet.”

The three absolutes

Three things about this surface hold without exception. Each is checked against the code below.

1. The plain fallback never touches the alternate screen

The alternate screen is entered by one constant, written at one place — inside Frame::install, after fallback_reason has returned None and, on Windows, after VT has been proved. A run without a Frame cannot emit those bytes because there is no other emitter. Term::printing (the -p constructor) and Term::silent set frame: None in their initialisers; they do not decline to draw, they have nothing to draw with. tested

crates/emma/src/term/frame.rs — ALT_ENTER, install; crates/emma/src/term.rs — Term::printing, test printing_never_draws_a_viewport

The one-emitter half is pinned by counting occurrences of the sequence in frame.rs’s own source, comments stripped, and asserting one enter and one leave: “a second occurrence is an entry outside the latch’s knowledge.” The no-escape-bytes half rests elsewhere. Term::side writes through render::for_stream, which branches on the palette level: at Level::None — which a pipe, NO_COLOR and --print all produce — it emits plain(line) and never sgr(line). Four modules carry a test named with_no_colour_not_one_escape_byte_is_emitted. tested

crates/emma/src/term/render.rs — for_stream, plain; crates/emma/src/term.rs — Term::side; tests in term/{render,markdown,diff,statusline}.rs
One residual escape route, and it is upstream

Term::delta passes the model’s own characters through untouched on the fallback path — which is what keeps emma … | tee free of anything Emma invented, and also means an escape sequence written by the model is not filtered there. Inside the frame it is: markdown::sanitise drops every control character before a cell is written, and an_escape_byte_in_the_models_prose_never_reaches_a_cell covers it. On the pipe, the bytes are the model’s. unverified — reported from a reading of Term::delta; a run piping a model reply containing \x1b would settle it.

crates/emma/src/term.rs — Term::delta; crates/emma/src/term/markdown.rs — sanitise

2. Every exit path leaves it

restore_terminal is idempotent, global, and takes no arguments. All three follow from one constraint: “a panic hook has no self.” The state it undoes lives in five process-global atomics (FRAME_ON, RAW_ON, ALT_ON, MOUSE_ON, CURSOR_ROW) rather than in a struct, because only one of the callers has a Frame in hand.

crates/emma/src/term/frame.rs — the Restoring region

Drop during unwind The same impl; racing the panic hook costs nothing, because the flag is cleared with a swap.
panic A hook installed by PANIC_HOOK.call_once in install. It restores before chaining to the previous hook, so the message lands on the normal screen in a terminal that is echoing again.
Ctrl-C Raw mode turns off the terminal’s signal generation on both platforms — ISIG on unix, ENABLE_PROCESSED_INPUT on Windows — so tokio::signal will not fire and the keystroke is the only delivery there is. term/input.rs owns it; the run then unwinds through the paths above.
process::exit main.rs calls restore_terminal() first, with the comment “process::exit runs no destructors, so Term’s would not run here.”
crates/emma/src/term.rs — impl Drop for Term; crates/emma/src/term/frame.rs — install, restore_terminal; crates/emma/src/term/input.rs — Editor::key; crates/emma/src/main.rs

Three orderings inside install and restore change the outcome:

  • ALT_ON is set before the enter bytes are written. A panic in between would otherwise strand the alternate screen behind a restore that refuses to run.
  • The private modes are enabled after FRAME_ON, because FRAME_ON is what makes the restore willing to turn them off. “Being late costs nothing; being early costs a shell that pastes escape markers into itself.”
  • The Windows code page is restored last, after the final byte has gone out, so the escapes above it are decoded by the console they were written for.
crates/emma/src/term/frame.rs — install, restore_terminal

ESC[?1049l is written only when ESC[?1049h was. An unpaired leave on the normal screen “carries an implicit cursor restore that nothing saved, and terminals answer that by moving the cursor somewhere surprising.” A pairing test walks the enter strings, extracts every mode number and demands the matching disable exists in the leave strings, so adding a mode to the way in without adding it to the way out fails in CI rather than on somebody else’s terminal. The reason a mode left on matters: bracketed paste surviving the process means the inheriting shell receives ESC[200~ around everything anybody pastes into it, forever, from a program that has exited. tested

crates/emma/src/term/frame.rs — every_terminal_mode_the_frame_sets_is_unset_on_the_way_out, PASTE_ON/PASTE_OFF
What the restore does not cover, per the code

SIGKILL, a stack overflow that skips the hook, and std::process::abort. Those strand raw mode already and strand the alternate screen now, “and no in-process code can do otherwise.”

The design note adds a class the inline design could not have: a multiplexer or ssh session detached mid-frame, or a dropped connection with the alternate screen still entered. “§2.4’s restore path covers the exits this process can see; it cannot cover the ones where the process is still alive and the terminal is not.” unverified — no tmux or ssh certification exists in the tree.

crates/emma/src/term/frame.rs module doc; notes/design-tui-fullscreen.md §2.1

3. EMMA_UI=inline is an escape hatch with an expiry

The old inline viewport was not deleted. One environment variable selects it, tested narrowly — eq_ignore_ascii_case("inline") — so that “anything else, including the variable being unset, which is the ordinary case, is the full-screen app.” It is kept for one release, as a soak period, so the flip’s cost can be discovered against a real terminal rather than in theory.

crates/emma/src/term/frame.rs — install, enum Ui; notes/design-tui-fullscreen.md §2.3

The two are different code, not a flag inside one renderer. Inline, transcript lines go out through ratatui’s Terminal::insert_before — “cursor to the last row, newlines, the one mechanism a terminal captures into scrollback” — the frame drifts to the bottom rather than being walked there, a streamed fragment is held back in the viewport because “a fragment inserted above the viewport could never be extended” (so a paragraph streamed without newlines would otherwise arrive as a column of one-word lines), and spacing.rs decides blank rows. Full-screen, the transcript is an owned buffer that re-renders whole on every paint, the held-back partial line is gone, and separators come from the buffer’s own structure. Mouse capture is enabled only on the full-screen path: inline, the terminal owns the wheel, and taking it would break scrollback that still works.

crates/emma/src/term/frame.rs — Frame::prose, Frame::separate, install

What the alternate screen cost

The reversal

For the whole life of this module the rule was Viewport::Inline only, never the alternate screen, and frame.rs spent that life arguing for it. On 2026-08-12 the owner reversed it, on the ground that the multi-pane layout he specified cannot be drawn inline. frame.rs records the outcome without softening: “That argument was true and it lost.” The manifest test that asserted “no alternate-screen entry anywhere” was rewritten rather than removed, and its doc comment names which assertion died and why.

crates/emma/src/term/frame.rs module doc and the_scrolling_regions_feature_is_never_enabled; notes/design-tui-fullscreen.md §0, §2

§2 of the design note prices every cost, including the one line where the flip is a gain: the “a fragment can never be extended” streaming constraint disappears, because an owned buffer can restyle and reflow the entry being streamed on every frame. Three of the costs reach a user.

Lost What replaces it Standing
Terminal scrollback. Inline, insert_before handed each line to the terminal, which kept tens of thousands of them for no code and no memory here. term/transcript.rs: an owned buffer with append, cap, scroll, follow-the-tail and re-wrap at a new width. The largest piece of new code in the flip. Scrolled by PgUp/PgDn, Ctrl-↑/Ctrl-↓, Home/End (only on an empty editor) and the wheel at three rows a notch. tested at the buffer; unverified on a console
Native mouse selection. Mouse capture is on for the wheel, which takes plain drag-selection away. Shift-drag, listed in the quick-help table because it is the one fact a user cannot guess. It selects the raw cell grid, so it is clean only with the sidebar collapsed: a drag across the pane otherwise captures sidebar columns, borders and gutter interleaved into every line. /export is the intended copy path and has not landed. unverified
Re-reading the styled run after exit. Leaving the alternate screen restores the prior shell content and the run visually vanishes. Nothing replaces it: “scrolling the shell up an hour later to re-read styled output. Gone.” What exists is a pointer — Term’s Drop prints session: <path> onto the restored normal screen, after the alt screen has left, naming the session JSONL. On the inline path the pointer is None, because the transcript is already in the shell’s scrollback. unverified by eye
notes/design-tui-fullscreen.md §2.1; crates/emma/src/term/transcript.rs; crates/emma/src/term/input.rs — pane_key, WHEEL_ROWS; crates/emma/src/term.rs — impl Drop for Term

Four further losses were added to §2.1 on 2026-08-11 from the red-team evaluation, because the original table asked what frame.rs stops doing rather than what the terminal stops doing. The wheel was one, and mouse capture answered it. The other three are open: the terminal’s own cross-run search is gone and in-app search would be one field over one Emma buffer rather than a replacement; screen readers need work that has not been done — a full-screen app paints cells where inline output was ordinary text, and “a question nobody hears is consent nobody gave”; and multiplexers add the restore-failure class named above.

notes/design-tui-fullscreen.md §2.1, from notes/eval-tui-fullscreen-kimi.md §1.5

How the cap names what it dropped

The retained buffer holds 2,000 entries or 50,000 rendered rows, whichever binds first. Both numbers are written down as guesses: “The measurement that should set them is a real session’s memory footprint, and it has not been taken.” When the cap binds, the dropped entries are gone entirely; what survives is two counters and a marker row rendered at the top of the buffer — … older output dropped (N blocks, M rows) — all of it is in {path}. The marker is never removed, “because the fact that output is missing does not expire,” and it wraps rather than truncating: an earlier version cut it to one row, and what fell off the end at eighty columns was the path to the complete record, which is the whole remedy the row exists to carry. tested — the_marker_keeps_its_remedy_at_every_width.

crates/emma/src/term/transcript.rs — Cap, enforce_cap, dropped_marker

Scroll position is measured in rows up from the tail rather than as an index into the buffer, so dropping the oldest entries cannot move what the reader is looking at. That is half the problem; the other half arrives from the back, and the module records that its tests found it and the design note did not. A view scrolled up ten rows that receives ten more rows of tool output is no longer over the same text, so a scrolled view has its offset grown by whatever was appended below it. Reaching the bottom re-latches follow-tail. Scrolling stays live while a goal runs and while a question is pending — “reading the evidence above an approval prompt is exactly when scrolling matters most.” tested

crates/emma/src/term/transcript.rs — appended, scroll_up, follow_tail; tests scrolling_up_survives_everything_that_arrives_afterwards, the_cap_binding_does_not_move_the_readers_page

The feature that stays off

ratatui’s scrolling-regions feature is not enabled, and the reversal above does not change that. With it on, the inline path’s insert_before is implemented with ESC[{top};{bottom}r, and a DEC scrolling region whose top margin is below row 1 discards the lines that leave it. That shipped here once; the owner’s first complaint was that he could not scroll.

crates/emma/Cargo.toml (the ratatui dependency comment); crates/emma/src/term/frame.rs module doc

Colour

Roles, not hues

Nothing names a colour at the point of use. Text is given a role — Text, Dim, Ok, Err, Warn, Info, Accent, Ground — and the role is resolved at one point, Palette::color. A terminal that cannot render a value substitutes there and nowhere else, which is what makes the 16-colour fallback one function rather than a change at every call site.

crates/emma/src/term/palette.rs — enum Role, Palette::color

Three rules sit above the roles, each with a failure behind it.

  • Ordinary text is never given a colour. Emma cannot ask the terminal what its background is. Gruvbox’s foreground is #ebdbb2, a cream that is invisible on white, so body text is Color::Reset — whatever the user already chose.
  • Colour is never the only signal. Every event that gets a colour also gets its own glyph and weight. A terminal rendering #b8bb26 as a muddy olive still shows ✓ where a success was, and this also covers the readers who cannot distinguish the red from the green.
  • Nothing paints a lone background. The two places a background exists — the approval prompt’s answer keys, the sidebar’s selection band — set foreground and background together, which is what makes them legible against an unknown ground. Both degrade to reversed video at Level::None.
crates/emma/src/term/palette.rs module doc, chip, band; tests ordinary_text_is_never_given_a_colour_at_any_fidelity, nothing_paints_a_background_except_the_named_pairs tested

Level::of: six inputs

How much colour a terminal gets is one function of six arguments: whether the stream is a terminal, NO_COLOR, EMMA_COLORS, COLORTERM, TERM, and whether this is Windows Terminal — which does 24-bit and sets neither a useful COLORTERM nor a useful TERM. The environment is an argument rather than a global, which is what makes the whole ladder testable.

crates/emma/src/term/palette.rs — Level::of, Level::detect

The order is “so the honest signals beat the hopeful ones”: an explicit override first, since the person setting it is looking at a terminal Emma guessed wrong about; then NO_COLOR and “this is not a terminal at all”; then the environment’s own claims. An unreadable override value resolves to Ansi16 rather than to truecolor — “an unreadable value is not permission to guess loudly.” A theme is not one of the six inputs, which is what stops /theme from promoting a sixteen-colour console.

Why NO_COLOR cannot be overridden

Palette::color returns before it reads the theme: 

pub fn color(&self, role: Role) -> Color {
    if self.level == Level::None || role == Role::Text {
        return Color::Reset;
    }
    // … only now is the theme consulted
}
crates/emma/src/term/palette.rs — Palette::color

Level::None is what NO_COLOR, a pipe and --print all produce, so there is no path on which a theme is consulted and NO_COLOR applies. The alternative was a check inside the theme loader, and it is weaker for a specific reason: the loader “can only refuse data it has thought of,” and a check can be omitted by whoever adds the next method here. The same early return is what keeps Role::Text out of a theme’s reach.

The guarding test names the mutation it must survive — moving the theme lookup above the short-circuit — and its assertion is what fails under it: every role would then come back as a hex, an index or a named colour, none of which equals Color::Reset. It therefore holds for any theme, not for the one the fixture carries. tested

crates/emma/src/term/palette.rs — with_no_colour_nothing_a_theme_could_say_reaches_the_screen

Themes: data on disk, applied at next start

A theme is a JSON file of numbers, resolved once at load into fixed-size Copy data. Strings are parsed and discarded there. The constraint behind that: Palette and Skin are passed by value into roughly thirty call sites, and a theme holding a String would end Copy and cascade through every signature in term/. tested — a_palette_is_still_copy.

crates/emma/src/term/theme.rs module doc, struct Theme; crates/emma/src/term/palette.rs tests

/theme selects; it does not switch. A theme is read once at startup, so the command writes a key to ~/.emma/settings.json and touches no Palette, no Skin and no frame. The owner ruled the scope — “we can set theme and restart the console to see it” — and the alternative is priced in the file: a live swap has to reach every drawn surface at once, and the transcript holds rows already styled under the old colours, so “the realistic outcome of repainting is a half-recoloured screen.” There is also no --save flag, because selecting is what writing it down means.

crates/emma/src/session_command.rs — the /theme region, write_theme

Three rules survive that cut.

  • A bad theme costs colour and never the program. load returns notices, never an error: a bad hex loses one role, an unreadable file loses the theme, and Emma says so in words. Nothing in the loader returns a Result, because “a ? anywhere in it would throw away the seven roles that parsed because the eighth did not.” Notices stop at five — past that the count and the path are what a reader needs, since the file is where they are going to go and look. tested — a_wrecked_file_cannot_fill_the_screen_with_warnings.
  • The 256-colour index is derived; the 16-colour name is inherited. Derivation reproduces five of the seven shipped indices exactly and misses two by a shade of the same hue, which is close enough to compute. At sixteen colours the same nearest-distance arithmetic makes Accent LightRed — and Role::Err owns red at that level, so every goal line would read as an error. A name is therefore either declared by the theme author or kept from the built-in role. tested — the_256_derivation_reproduces_the_measured_table pins both divergences (167 against 203, 245 against 246) instead of smoothing them, and the_accent_is_never_the_colour_that_means_failure asserts the distinctness rather than a literal, so an edit moving the accent to LightRed for being nearer the hue cannot pass.
  • Role::Text cannot be themed. The loader refuses roles.text by name — while still listing it among the valid names, so “a typo of text should be told about text, not about seven names that do not include it” — and Palette::color returns before the theme is read. A theme author has one terminal; their foreground is what makes Emma unreadable for the person with the opposite background, who reads it as Emma being broken. tested
crates/emma/src/term/theme.rs — load, ROLE_NAMES, SETTABLE, MAX_NOTICES, derive_index

Two smaller rules with the same shape. A project cannot select a theme — only ~/.emma/settings.json can — so on a name collision the user’s theme wins, closing the one route by which a cloned repository could repaint somebody’s screen. And the name emma is reserved, so shipping themes/emma.json cannot change what stock Emma looks like. tested — a_project_theme_never_shadows_a_user_theme_of_the_same_name.

crates/emma/src/term/theme.rs — load, RESERVED; crates/emma/src/session_command.rs — theme_dirs

The TOOLS section launches real programs

The sidebar’s middle section lists seven entries in a fixed order: Shell, Code, File Browser, Search, Memory, Data Explorer, Settings. Five start a program on the machine. Search and Memory run inside Emma, and launch refuses them with a sentence saying so rather than returning success: “returning Ok for a launch that never happened is a fake receipt.”

crates/emma/src/usertools.rs — enum Tool, Tool::in_app, catalogue

An unavailable tool stays in the list with available: false and a detail naming what was looked for, because “a key that is absent teaches nothing, a key that says ‘none of code, cursor, subl, zed, nvim is on PATH’ is a to-do list.” The sidebar draws n/a where the chord would be and dims the label, so the row reads as switched off rather than as a key that would do nothing when pressed. The catalogue can run on every draw, so PATH lookups are cached for the life of the process — which also makes “a program installed mid-session appears after a restart” true by construction rather than intermittently — while settings.json is re-read each call, so the Settings tool’s own writes show up on the next frame.

crates/emma/src/usertools.rs — struct Entry, catalogue; crates/emma/src/term/sidebar.rs — TOOL_MISSING; crates/emma/src/term/app.rs — tool_rows

Why the keys are Alt+<key>

The mockup showed bare s / c / f bindings. The design refused them — “a bare letter that acts while the input box exists is a footgun” — and the softer rule, only when the editor is empty, fails on a fact the approval-gate keys never meet:

“The first character of every goal lands on an empty editor, so a bare s binding makes any goal beginning with s start a shell instead.”

crates/emma/src/term/input.rs — tool_key

An Alt chord types nothing, which puts it in Ctrl-B’s class: safe whatever the editor holds, so the editor’s content is not consulted. Ctrl is excluded from the match because AltGr arrives as Ctrl+Alt on Windows layouts and produces real characters. Which letters are bound is the catalogue’s knowledge rather than the key handler’s — tool_key returns the character and the frame looks it up — and every chord is dead while a question is pending, as is Ctrl-B. Scrolling is the exception, and it is argued rather than assumed: “a scroll offset cannot answer a question.” tested — a_bare_letter_is_never_a_tool_shortcut, whose doc says “if this test goes red, that refuted idea is back,” and alt_chords_launch_tools_and_die_under_a_prompt.

crates/emma/src/term/input.rs — tool_key, pane_key; crates/emma/src/term/frame.rs — Inner::tools

The defect that forced raw CreateProcessW

The interactive frame owns the alternate screen, so a child process that writes to that console wrecks the display — and unlike a dead key, the user cannot tell what happened. On Windows, every spawn shape std::process can express fails that requirement, and each was refuted by measurement.

Shape What was measured
CREATE_NEW_CONSOLE + default stdio A new window whose handles still point at Emma’s console: Rust sets STARTF_USESTDHANDLES whenever the parent has std handles at all. The first certify run’s canary landed in this process’s own output stream.

crates/emma/src/usertools.rs — the Certification against the real machine region

The non-console case takes the ordinary path: CREATE_NO_WINDOW plus null stdio, which gives a GUI program — or a .cmd shim like VS Code’s, which runs through cmd.exe and would otherwise flash or attach — a console with no window. On unix every spawn gets null stdio and its own process group, and anything needing a terminal is refused at planning time rather than launched into a wrecked screen. That is why the unix Shell tool opens the terminal application (open -a Terminal, or a probed emulator) and lets it pick the shell, rather than spawning $SHELL with nowhere to put it; nvim is available on Windows for the same reason and refused on unix.

crates/emma/src/usertools.rs — spawn_detached (both cfgs), plan, the module doc

One more rule: a configured value is one program name or one absolute path, never a command line. Splitting a string on spaces is the first half of running text through a shell, and a path with a space in it is not an argument boundary. A value that does not resolve produces an error naming it — never word-split, never swapped for a probed default, because “a substitution looks identical to success right up until the wrong program opens.” $VISUAL/$EDITOR get one concession, since the wider world does put command lines in them: a value there that does not resolve as a whole is skipped and the chain continues — skipped, not split. tested

One shape recurs across the directory: the modules that decide take no terminal and hold no lock, and the modules that touch a console stay small. app.rs gives the reason for keeping the split where it is — “the terminal, the locks and the entry/leave bytes stay in frame.rs, which has already shipped two invisible-to-tests defects and does not need a third file’s worth of chances.”

Four names that overlap

render.rs, view.rs, statusbar.rs and statusline.rs sound interchangeable and are not. render.rs is the vocabulary: an event becomes Lines, with no Rect and no Buffer in sight, and it also owns the inline status row (Skin::status). view.rs is the inline viewport’s layout — it takes a rectangle and a buffer and arranges the box, menu, panel, hint and status row. statusbar.rs is the full-screen successor to Skin::status, and names the inheritance itself: “it inherits that row’s one law: everything on it is true.” statusline.rs is somebody else’s program — a configured script whose first line replaces whichever built-in row is in play, its ANSI bytes parsed into styles rather than passed through, because “an escape byte written into a cell is a byte ratatui counts as one column and the terminal counts as none, and from that moment the diff is wrong about every row below it.”

The full-screen render path is frame.rs → app.rs → sidebar / chat / statusbar, plus two borrowed methods from view.rs for the dock; View::render itself is not on it. The inline path is frame.rs → View::render. Both consume render.rs.

Why spacing.rs is a module and not a join

A blank row is a boundary between two blocks, and it is written only when there is a block on both sides of it. The failure it fixes was distributed: two emitters each asking for the same boundary pushed their own Line::default() and the screen got two blank rows, and “there was no single place to notice it because the two callers never met.” A blank row was also landing first, under the shell prompt the user typed emma at, where “a gap reads as output that went missing.”

crates/emma/src/term/spacing.rs module doc

It is a state machine of three booleans rather than a filter over finished output, because the terminal is irreversible: “once a row is written it is the terminal’s and cannot be taken back, so the decision about a blank row has to be made before it is emitted.” separate() is idempotent, which is what stops two callers stacking separators; blanks the content wrote are never removed, since a blank line inside a fenced code block is part of what the reader copies out. tested — six tests, including blank_rows_a_block_wrote_itself_are_left_alone, whose doc frames it as the assertion that stops “collapse blank runs” from looking like a reasonable simplification.

Two rules from markdown.rs and diff.rs that contradict each other

markdown.rs inserts nothing into what a reader copies: no gutter down a code block, no │ in front of a quote, no added indent. The > of a quote is kept rather than swapped for │, because the swap “would put a character into the copy that the model never wrote.” A fenced block is split at the exact column and never at a word — wrapping code at a word boundary changes what it says — and the rows concatenate back to the source.

crates/emma/src/term/markdown.rs module doc, code_rows; test a_fenced_code_block_is_never_reflowed_and_never_loses_a_character

diff.rs writes a gutter on every row, and states the distinction rather than the exception: “a diff is not the file. It is a report about a change, in the format every reader already knows from git diff, and pasting it into a bug report is the use — pasting it into a compiler is not.” The gutter is also the only distinction that survives NO_COLOR, a sixteen-colour terminal and the ASCII glyph set, and it is written in one function so that the approval panel and the transcript line cannot disagree about which side a row is on.

crates/emma/src/term/diff.rs module doc, text_of

Four limits keep the diff off the interactive path’s critical list: 2 MiB read, 50,000 lines a side, 250,000 LCS cells, and 40 drawn body rows. Exceeding the third produces a coarse patch — one block of removals then one block of additions, labelled as such rather than guessed at — and the row budget is then split down the middle, because taking the first forty rows of a coarse patch would take forty removals and show no additions at all, drawing a thousand-line rewrite as a thousand-line deletion. The summary and the notes sit outside the budget: a cut diff that no longer said -1,412 lines would withhold the fact the prompt exists to supply. tested
