Doing work

Edit, and its two ways of saying where

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP

One tool, two addressing modes: quote the text, or name the line and the four characters Read printed beside it. A call supplying neither is refused. A call supplying both is resolved by agreement rather than by precedence, and refused when the two do not agree.

ArgumentTypeMeaning
file_path requiredstringRelative to the working directory, or absolute inside it.
new_string requiredstringThe replacement. With lines, empty deletes.
old_stringstringExact text, must occur once. This, or lines, or both when they agree.
linesstring12#a3f9, or 12#a3f9-15#b7c1 for an inclusive range. Wins when both are sent.
replace_allbooleanDefault false. Only valid with old_string.

read_only: false, reaches_network: false, idempotent: false. The last is correct rather than pessimistic: running the same edit twice fails the second time, because after the first the anchor is gone. A tool that reported success for a no-op would be lying about what it did. Its one reader is Registry::register, and read_only: false is what makes idempotent: false a legal thing to say here rather than a contradiction.

Why one tool and not two

//! **Why not a second tool.** A `EditLines` alongside `Edit` would cost its
//! whole description in every request, on every turn, forever, and would hand
//! the model a choice it has no good basis for making — the two are not for
//! different jobs, they are two spellings of the same job. It would also break
//! the one compatibility promise this crate makes: the six tool names are
//! Claude Code's exactly, so a hook matcher or an allow-list written for one
//! works for the other, and a seventh name is outside that set. **Why not
//! replace `old_string`.** Every model that has ever been trained on a
//! Claude-Code-shaped tool surface already knows how to drive `old_string`, and
//! the addressing scheme here can only be driven by a model that has seen a
//! `Read` from *this* harness in *this* conversation.

The refusals decidable without a file

All of these live in validate_args, and a test proves it by pointing them at a path that does not exist.

CallRefusal
neitherEdit needs somewhere to change: old_string with the exact text to replace, or lines with an address from Read such as 12#a3f9
empty old_stringEdit.old_string is empty; use Write to create a file
old_string equal to new_stringEdit.old_string and Edit.new_string are identical; the edit would do nothing
replace_all with linesEdit.replace_all applies to old_string only; a lines address already names exactly one place
malformed linesEdit.lines + one of the parser's five messages, below

replace_all is refused rather than ignored against an address. Accepting and ignoring it would teach the model the flag does nothing, which is the lesson it must never learn about the old_string form.

Both forms at once, which used to be a seventh refusal

Sending old_string and lines was refused outright until 2026-09-06, with Edit takes old_string or lines, not both; they are two ways of saying where, and supplying both does not say where twice. That was wrong, and it is off this table because the decision needs the file and so cannot be made in validate_args. The usual reason a model sends both is that it addressed the lines and then quoted the same lines back, which is redundant rather than contradictory.

What happens now: the addressed text is read out of the file, the quoted text has Read's labels stripped from it, and the two are compared with trailing whitespace ignored. If they agree the edit goes ahead and the address wins, because the address is the form checked against content hashes. If they disagree the call is refused with Edit.lines addresses {a} but Edit.old_string quotes different text, so the two disagree about where to edit. The addressed lines are: … Drop whichever one is wrong. Quoting the addressed text back is what makes the refusal actionable, because the model can see which of its own two instructions was the wrong one. There is still no precedence: picking one silently would edit a place the model did not name. tested — both_forms_that_agree_name_one_place and both_forms_that_disagree_are_still_refused, each shown to go red when the agreement check is removed.

Read's labels, tolerated in both strings

A model that has just read a file will sometimes quote the file back with the labels still attached, and the labels are not in the file. So an anchor is tried as the bytes given first, and only if that misses is the same anchor retried with the labels stripped. Order matters here: an anchor that already matched never reaches the fallback, so nothing that worked changes shape. The stripping is all-or-nothing, applying only when every non-empty line carries a label, so a file that genuinely contains something label-shaped is not mangled.

The same tolerance applies to new_string, and that is the half that matters more. A labelled anchor fails loudly. A labelled replacement is written verbatim into the source and the file stops compiling. certified for the mechanism: the tool is driven end to end through both paths in the port's own run. unverified for the two model measurements behind it, both quoted from the fork's comments and dated 2026-08-24: nemotron-3.5-lightning:30b-mlx sending eight labelled anchors in one run, and ornith:35b losing a run to 1088#f011\t #[test] as replacement text. Neither was reproduced here. A keyless local run against Ollama with a model of that class, driving Read then Edit, would settle them.

The literal anchor

old_string occurring three times and the model meaning one of them is the case every design gets wrong. Taking the first edits code the model was not looking at; taking the last is the same bug with different luck; editing all three is a refactor nobody asked for. All three return Ok, and the damage surfaces later as a test failure in a file the transcript never mentions.

tools/fs/src/edit.rs — by_anchor

The zero-match message names the two things a model gets wrong at this point: the match is byte for byte, and Read's line labels are not part of the file. A model that copies a labelled line straight into old_string would otherwise be told only that its text is absent.

This form accepts Partial and refuses Stale. A partial read licenses an anchored edit because the anchor came from what was shown; a literal anchor on a drifted file can match text that moved somewhere it does not belong, and nothing about the match would reveal it. The Stale refusal names the cheaper way out: address the lines you want with Edit.lines, which checks each one against what it said when you read it.

The address, and what it is made of

A line number on its own is a promise the filesystem never made. The model reads line 12, thinks for four turns, and edits line 12, but the user saved a file in between and an import got added at the top. A line-numbered edit applies cleanly to the wrong line and returns Ok. 

/// FNV-1a over the line's bytes, with the line terminator excluded.
///
/// The terminator is excluded so that the same text hashes the same whether it
/// is the last line of the file or not, and whether the file is CRLF or LF.
/// Callers strip it; this function does not look for it. What *is* included is
/// leading and trailing whitespace, deliberately: trailing whitespace is real
/// content, a formatter stripping it is a real change to the line, and a hash
/// that ignored it would let exactly that change slip past unnoticed.
pub fn hash_line(line: &str) -> u64 {
    let mut h: u64 = 0xcbf2_9ce4_8422_2325;
    for b in line.as_bytes() {
        h ^= *b as u64;
        h = h.wrapping_mul(0x0000_0100_0000_01b3);
    }
    h
}

Four hex characters rendered, 64 bits stored, and they defend different things. The rendered hash is copied by the model on every addressed edit and printed on every line of every Read, so its width is a token cost paid thousands of times. The stored hash costs eight bytes in a map nobody pays tokens for. Because the tracker checks the stored hash over the whole edited range while the model supplies only the two endpoints, the endpoints end up checked twice: at 16 bits by the model's claim and at 64 bits by the tracker's record.

FNV-1a is trivially collidable by anyone who wants to, and that does not matter. What is defended against is accident. An attacker who can rewrite the file being edited already has everything a collision would buy.

A measurement that refuted its own justification

short folds the hash before truncating it, and the obvious reason for that turns out to be wrong. FNV-1a's lowest bit is a parity of the input bytes and its low bits are conventionally called weak, which suggests truncating directly would collide badly on near-identical source lines. Over every .rs and .md line in this repository (50,621 distinct lines), folded and unfolded truncation both land within 1% of what a uniform 16-bit hash would produce. The fold buys nothing measurable here and is kept because it costs two instructions.

One number that framing makes easy to misread: 19,531 colliding pairs in that corpus sounds alarming and is irrelevant. Nothing here asks whether two lines in a file share a hash. It asks whether the line now at position 12 hashes to what the model expected at position 12, which is one comparison against one value, and 1 in 65,536 is the whole exposure.

The parser, and its five refusals

InputMessage, prefixed Edit.lines
emptyis empty; it should look like 12#a3f9, or 12#a3f9-15#b7c1 for a range
12is 12, which has no #hash; copy the whole `line#hash` label from the left-hand column of Read's output — a line number on its own does not say which text you meant
12#----is 12#----, and ---- is what Read prints when it had to clip a line that was too long to show. You have not seen the end of that line…
12#zzzwhose hash "zzz" is not the four hex characters Read prints
15#b7c1-12#a3f9which ends before it starts; a range runs from the lower line number to the higher one

The bare-line-number case gets its own message because it is the overwhelmingly likely mistake. Telling the model "syntax error" would send it to re-read the description; telling it the hash is in the Read output it already has sends it straight to the fix.

Splitting a range is more delicate than it looks, because the clipped marker is four hyphens: 

    // The range separator is a hyphen *followed by a digit*, and it has to be
    // identified that precisely because [`CLIPPED`] is four hyphens: splitting
    // on the first hyphen anywhere turns `12#----` into the range `12#` to
    // `---`, and the model gets told its hash is malformed instead of being
    // told the line was clipped. Neither a line number nor a hex hash can
    // contain a hyphen, so "hyphen, then digit" is unambiguous.
    let split = text
        .char_indices()
        .find(|(idx, c)| *c == '-' && text[idx + 1..].starts_with(|n: char| n.is_ascii_digit()));
tools/fs/src/hashline.rs — parse, anchor

Case is normalised on the way in, so 12#A3F9 and 12#a3f9 compare equal, but the claimed hash is kept as text rather than parsed to a number so a refusal can quote back the model's own typo.

Three checks stand between an address and the disk

  1. The endpoints still say what the model says they say. Catches a model aiming with a line number it worked out four turns ago. This is the only check the model's own quoted hash can make. The tracker knows what the world last looked like and has no idea what the model thinks it looks like.
  2. Every line in the range is text this harness has shown. The model sends two hashes; this is the other ninety-eight, matched against the tracker's record. It closes the known failure of per-line hashing, which is that a range can drift in the middle while both its ends look untouched.
  3. No line in the range is longer than Read will show. Replacing a line whose end nobody has seen discards text nobody read. Measured against the file rather than remembered from the read, because it is a property of the line and not of the sighting.

Check 2 asks whether the text changed, not whether it moved

When check 2 fails, the record is consulted a second time so the refusal can tell two problems apart. A gap means the line was never shown: Edit.lines covers line {n} of {raw}, which is outside the part of the file you have read. A mismatch with no gap means it was shown and has changed: line {n} of {raw} changed on disk after you read it, and it is inside the range {first}-{last} you asked to replace. It now reads {…}. The second lookup is only reached on the failure path.

Because the checks are per-line, lines accepts a Stale file where old_string still refuses one. That is a sharper rule rather than a weaker one.

The message has three shapes, chosen by how many other lines in the file still hash to what the model was aiming at. Zero: the text is genuinely gone, read the file again. Exactly one: The line you meant is intact and is now line {only}: retry with lines "{only}#{hash}". You only need to Read {raw} again if you also need to see what else changed around it. Several: which one you meant is not decidable here.

What the reword fixed, and what it did not

The first draft opened with "Edit.lines addressed 5#73b2, but line 5 now reads …" and closed by offering a re-read as a coequal option. Sonnet 4.5 replied "I see — I made an error. Let me re-read the file" and spent the whole Read the hint existed to save. Two faults, both in the prose. It did not say the file changed, which reads as you counted wrong, and the fix for counting wrong is to look again. And it offered the re-read as an equal option, which a model under uncertainty takes every time.

observed The reword stopped the model calling it its own error and started it acting on the corrected address. It did not stop the re-read. In both runs the author watched, Sonnet 4.5 read the file again anyway before retrying. The claim made here is therefore the smaller one: the corrected address the refusal offers is one this tool accepts. No token saving is claimed from it, and the source says so in as many words.

tools/fs/src/edit.rs — moved

The write itself

Lines are split with split_inclusive('\n'), so each keeps its own terminator. Rebuilding from str::lines would convert every CRLF file to LF on the first one-line edit and add a newline to a file that never had one, both whole-file rewrites disguised as one-line changes. Replacement lines take the terminator of the last line being replaced.

An empty new_string deletes the lines rather than leaving a blank one behind. Both readings are defensible; the result says "deleted" in so many words, so a model that meant the other thing finds out immediately rather than from a diff three turns later.

A splice that produces the file it started with is refused: the replacement for lines {first}-{last} of {raw} is byte for byte what is already there; nothing would change. That check sits after the file is read because it cannot be known before, where the old_string form catches the same thing in validate_args.

What a successful addressed edit hands back

The summary, then up to ECHO_LIMIT = 20 replacement lines with their new numbers and new hashes, then a sentence saying how far everything below moved. Past twenty it says more than 20 lines, so Read {first}-{last} for their labels. If the file ends without a newline it says so, because a model that assumes one is there will build its next edit wrong and nothing else in the output would reveal it.

Every edit shifts the numbering underneath it, and a model working from pre-edit numbers aims its next one wrong. That cascade was reported against the project this scheme came from and closed there as not planned.

What the addressing actually costs, measured

The labels are a real cost paid on every Read to make some edits cheaper, and the measurement is closer than the idea's reputation suggests. Counted with Anthropic's count_tokens endpoint on 2026-08-11.

MeasuredResult
Addressed edit against old_string, 14 real single-line edits from this repository 26% fewer output tokens: 842 against 1140, because the anchor stops having to be long enough to be unique
Labelling, over 2000 lines of this repository's Rust +3.6 tokens a line, +23% on every read. Irreducible: base36 at the same width is worse at 3.97, dropping the # saves 0.5, and three hex characters saves 0.7 at four times the collision exposure
Break-even, at list prices ≈14 edits per read uncached; ≈1.5 once the read is cached, which it normally is within a turn

observed Those numbers were produced by the author of read.rs against the live count_tokens endpoint on 2026-08-11, and the run was not kept. They are repeatable in principle and not from anything in this repository, because neither the fourteen edits nor the 2000-line sample is recorded.

So on tokens alone it is close to a wash, and the case does not rest on it. It rests on the call that no longer happens: an old_string edit against a drifted file was refused outright and cost a full re-read plus a re-emitted edit every time. On a machine where somebody has the file open in an editor, that was the common case.

The 61% figure is not this change's number

The widely-quoted −61% is the format author's own benchmark of their own scheme, 180 tasks × 3 runs over roughly 16 models, and −61% is Grok 4 Fast, the best case, not a median. The README does not say which of two baselines it is against. It also does not describe Emma's implementation, which is a different scheme: the source project tags each file with one hash and addresses lines by bare number, and normalises trailing whitespace away before hashing, so a formatter stripping trailing spaces is invisible to its staleness check. Emma hashes per line, including trailing whitespace, and catches that.
