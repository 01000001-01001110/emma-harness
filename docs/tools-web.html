The web: two tools, five more, and a browser

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP

WebSearch opens a search engine's results page in real Chrome and returns the places it points at. WebFetch renders one page the same way and throws the browser away. The five Browser* tools keep it, which is a different capability: inside a session the model acts as the user, on a page that may hold their login.

Nothing is registered unless it can work

pub fn web_tools() -> WebSurface {
    let mut tools: Vec<Arc<dyn Tool>> = Vec::new();
    let mut skipped = Vec::new();

    match fetch::WebFetch::detect() {
        Ok(t) => tools.push(Arc::new(t)),
        Err(why) => skipped.push(format!("WebFetch is not available: {why}")),
    }

WebSearch and the five browser tools ride the same verdict: one Chrome check, and everything that needs a Chrome registers or is reported missing together.

The predecessor shipped a web_search that registered with no key and failed on every call. A turn that touched it died, and the model had no way to learn the tool was decoration, because a failed call looks exactly like a hard problem. Each omission comes back as one line for a human, which main.rs prints, so the absence is reported rather than silent.

WebFetch::detect builds a BrowserConfig and throws the result away, which looks pointless and is not: building the config is where chromiumoxide resolves the Chrome executable, so the failure surfaces at startup with a message a human can act on rather than on a first fetch several turns into a task. Its verdict is reused for the browser tools rather than asked again, because two detections that could disagree is a surface where WebFetch is present and BrowserOpen is not for no visible reason.

The pool must be held for the length of the run

WebSurface::browser hands the caller an Arc<BrowserPool>. Dropping it kills every open Chrome, which is right at exit and wrong in the middle of a goal. It is handed back rather than kept inside the tools because there is no other way for a binary to end the sessions itself.

Why a browser and not an API

This tool existed once before, over a search vendor's JSON API, and it needed that vendor's key in ~/.emma/credentials.json. I ruled on 2026-09-05 that no search-vendor key comes back. What Emma already had was a real Chrome, driven by the code WebFetch uses, and a results page is a page: open it, take the links, throw the browser away. No key, no account, nothing billed per search, and it works on a local model exactly as on a paid one, which the provider-side alternative I built first could not.

What was tried, so nobody repeats it

Four engines from a fresh headless Chrome, 2026-09-05, this machine. DuckDuckGo's HTML and Lite endpoints both served a “bots use DuckDuckGo too” challenge. Startpage served “Access Temporarily Suspended”. Bing served a results page that looked right and was not: three runs returned Army PDFs, vacation packages and Bing's own version page for a query about ratatui. That last one is the shape this project refuses everywhere, a plausible fabrication rather than a refusal. certified: the four digests are reproducible with browser-miner digest <url>, and the probe that settled the fix is tests/search_probe.rs, driven by environment variables.

The one difference that fixed Bing was the User-Agent. Headless Chrome announces itself as HeadlessChrome/N and Bing degrades that client silently. The same launch sending an ordinary Chrome User-Agent got About 59,500 results with ratatui.rs first, with navigator.webdriver still true; a persistent profile and a visible window also worked and were not needed. DuckDuckGo challenged the ordinary User-Agent too, so it is out. The string is built from the installed Chrome's own major version, read once per process, so it does not age into a tell of its own.

tools/web/src/search.rs — user_agent, installed_chrome_major; tools/web/tests/search_probe.rs

One engine, no silent fallback

The gate grants a host per call, before anything runs. A tool that tried a second engine when the first blocked would reach a host the human never saw in a prompt, which is the redirect hazard WebFetch refuses one function over. So the engine is one constant and the prompt names it. When it blocks, the output says so and names the way through: BrowserOpen on the same URL with headful: true, then BrowserRead. A visible window is one a person can pass a challenge in. tested: a_challenge_page_is_reported_as_a_block_and_not_as_results asserts a blocked digest's links never reach the output and the BrowserOpen instruction does.

A results page into places to look

Bing does not link to results directly. Every result anchor is a click-tracking redirect, www.bing.com/ck/a?…&u=a1<base64url>, so “a link that leaves the engine's host” finds nothing and the redirect is decoded; the model is shown the destination and never the tracking URL. Titles and snippets are not on the anchors chromehand collects, which carry the cite line. They are in the page text, four lines per result, and the cite line is matched by host and first path segment to read the two lines after it. A result the text does not mention keeps its anchor text as a title, because a URL with a poor title is a place to look and dropping it is the silent kind of loss. tested: hits_decode_the_redirects_and_read_titles_from_the_text against a fixture cut from the page Bing served, and a_click_redirect_decodes_to_the_page_it_tracks.

The other search, opt-in

"web_search": true in ~/.emma/settings.json also lets the model search through the provider's own server-side tool, on the same key, billed apart from tokens. It is off unless asked because this tool covers the need without a bill, and because a search the provider runs on its own side never reaches the egress gate. When it is on, every run says so at startup and the loop prints what was searched for. Anthropic only; Ollama has none and the startup line says so. The egress page carries the consent argument.

Zero in either budget is refused rather than read as unlimited. read_only: true, because the throwaway Chrome profile lives in the system temp directory and is removed on teardown, and the tool cannot modify the working directory, submit a form, or run anything the model chose. reaches_network: true carries the whole of the risk. idempotent: true claims that two reads have the same effect as one, which is none, and is explicitly not a claim that the page will say the same thing twice.

Why a browser rather than an HTTP client

Pages worth reading are often JavaScript shells that serve an empty <div> to curl. Many refuse plain fetches outright; WorkAtAStartup answers a bare request with 406 and renders fine in Chrome. What comes back is not a DOM dump either: chromehand strips boilerplate and pre-extracts the interactive inventory.

The cost is stated: this spawns Chrome, and a stateless read is two to three seconds of launch before any bytes are read.

The page-text remedy used to be re-read with max_chars={total}, and it was a lie in two directions. On a long page it asked for a quarter of the model's context in one message; on a longer one it named a number above the 200,000 ceiling, so the advice could not be followed at all. What replaced it on 2026-09-06 is the filesystem Read contract: name this window, name the whole document's size, and name the exact call that returns the next window. offset is that call's argument, and the notice says the second fetch is a real page load rather than a cached slice, because nothing here is cached and a reader who assumes a free seek has budgeted wrongly. An offset past the end is arithmetic rather than an empty page, so it says where the last window starts instead of returning nothing. BrowserRead gains the same argument under the same contract. tested — a_text_cut_names_the_window_and_the_call_that_continues_it. unverified against a live page: the two-window continuation has only been driven over fixtures here. cargo test -p emma-tools-web --test fetch -- --ignored a_long_page needs network and Chrome twice, and would settle it.

chromehand's failures into Emma's

pub(crate) fn map_error(e: MinerError) -> ToolError {
    match e {
        MinerError::Refused(m) => ToolError::BadArguments(m),
        MinerError::Browser(m) => ToolError::Failed(m),
        MinerError::Unavailable(m) => ToolError::Unavailable(m),
    }
}

One function with one arm per variant rather than a chain of string checks at the call site. A refused URL is something the model can fix, a browser that broke can be retried, and a machine with no browser is neither. Upstream signalled all three with process exit codes and spent one code on two of them; splitting Unavailable out is the one change.

BrowserAct never returns page content. Its result is a snapshot line and an instruction to call BrowserRead, and a test asserts the content is under 400 characters. A negative answer is Ok: Condition NOT met within {n} ms — the page never reached that state; this is the answer, not a failure to look. The same holds for a click that matched nothing and a select with no matching option, which additionally lists the options that exist.

The cross-origin re-ask

The same argument applied to WebFetch, and until 2026-08-23 nobody had applied it. One call, so it cannot re-ask the gate from inside itself. Chrome follows redirects, and a persisted WebFetch(domain:example.com) rule answers every later call with no prompt at all. The page that came back could be from anywhere that host chose to send us, and on a hostile page the page chooses. It now compares the digest's final_url with the host the gate was asked about and refuses when they differ, naming both and saying nothing was read back; the way through is to call WebFetch on the destination, so the host being read is the host in the prompt. tested tools/web/src/fetch.rs a_redirect_to_another_host_is_refused_and_an_ordinary_one_is_not asserts the silent cases first (a scheme upgrade, a path change, a case difference) because a guard that fired on those would be switched off within a day. Two mutations go red: the comparison removed, and the comparison weakened to a suffix match. Ran cargo test -p emma-tools-web --lib a_redirect_to_another_host on 2026-09-02: ok. That no test drives a real Chrome through a real redirect is a named hazard, listed under named hazards rather than described here.

The gate reads a destination from network_target before the call, out of its arguments, and a session call's arguments say session=abc rather than where abc now points. So these tools answer from the pool, with the host the session is on now, and the pool records the final_url after every verb.

tested tools/web/src/fetch.rs a_session_read_names_the_host_the_session_is_on_now moves a session to evil.example and asserts the gate is told the new host. Its failure message names the defect it guards against: "the gate was told the original host after the session navigated away from it". acting_asks_about_the_session_host_and_navigating_asks_about_the_destination covers the one verb whose destination is knowable before the bytes.

What the gate does not cover, stated by the source

The re-ask is one call late. The bytes for a redirect or a click-through have gone by the time the pool learns the host changed. A remembered rule means what it says, too: BrowserRead(domain:example.com) allows reading a session while it is on example.com and does not travel with the session.

And prompt injection is not solved. A page can contain text that persuades the model to click a button on that page, and nothing here prevents that. The gates bound the blast radius; they do not read what comes back.

Sessions, and the three teardowns

MAX_SESSIONS is 2. A persistent Chrome is 200 to 400 MB resident for as long as the session lives; two on a laptop already running rust-analyzer is noticeable, and three is where the user discovers the limit as swap. The third open is refused with the cap named, so the model learns the rule instead of discovering a slow machine.

A leaked Chrome is not untidiness. chromehand's own note is that a session's CDP websocket is unauthenticated on localhost, so while it lives any local process can puppet that browser, with a profile that may hold a login. This crate has leaked one before, and tools/lsp wrote it down: "tools/web leaked a Chrome per session because its teardown ran in main. Correct for a binary, wrong for a library." So the teardown is three mechanisms, each covering a way the previous one does not run.

MechanismCovers
BrowserPool::closethe ordinary path: a polite CDP Browser.close, then a hard kill by pid, then the profile directory
Dropnormal exit and panic-unwind. It cannot await, so it kills by pid, which is why the pid is recorded at open time
sweep_stale_profiles at constructionabort(), SIGKILL and a power cut, none of which run Drop. A profile untouched for two hours belonged to a run that is gone

A profile the removal gives up on is now named rather than left to the backstop in silence. remove_profile waits for the process to exit and then retries ten times over roughly three seconds, because on Windows the files stay locked until the process actually goes. If it still cannot remove the directory it returns false, the pool records the path, and BrowserPool::leaked_profiles reports it; the end of a goal turns that into a warning naming the directory. Until 2026-08-23 it returned () and the ten attempts ran out, with no value, no record and no line anywhere.

The backstop is real and unchanged: sweep_stale_profiles clears it at the next start. "Not fatal" and "not worth mentioning" are different claims, and a profile directory holds the session's cookies. This module's own note is that a browser Emma opened may hold a login. tested tools/web/src/fetch.rs a_profile_that_cannot_be_removed_is_recorded_and_a_removed_one_is_not produces the failure rather than mocking it, by putting a file where the directory should be so remove_dir_all fails for a reason the filesystem supplies, and it asserts the clean cases too. An implementation that reported a leak every time would warn after every goal, and a warning that fires when it should not is how an operator learns to skip it. Three mutations go red on three different assertions.

That test proved the decision and not the delivery, and a reviewer found the gap the same day. Neither it nor the recording test called close or kill_all_now, so both call sites that turn a failed removal into a recorded one could be deleted with the suite green. The warning itself was assembled inline in main.rs, where reaching it needed a real browser, a really stranded profile and a real terminal. Nothing reached it. The text now lives in pool::leaked_profile_warning, which returns Option<String> so the silence of an ordinary run is testable too. tested tools/web/src/fetch.rs close_reports_a_profile_it_could_not_remove and kill_all_now_reports_a_profile_it_could_not_remove drive the two teardowns end to end with a file parked where the profile should be; a_teardown_that_removed_its_profile_reports_nothing is the control. Deleting either note_leak call, or making the warning return None, turns a different one of the three red (a mutation receipt in the owner’s records). This is the third instance of the shape in this repository: a decision tested in the library, a delivery nothing exercises.

kill_all_now is the second mechanism exposed as a public synchronous call, for an interrupt handler that must not await, and it is idempotent. chromehand's own 30-minute idle TTL is kept as a second line of defence rather than the primary one, because a TTL doing the real work means a Chrome lives up to half an hour past the process that wanted it.

The session registry is in memory rather than on disk. chromehand records sessions in .browser-miner/session-<id>.json relative to the working directory, which inside Emma is the user's repository. BrowserPool::open therefore calls chromehand's session::open, which does the hard part of a detached spawn with no inherited handles, and then deletes the session file it wrote.

BrowserClose declares read_only: true

That departs from the letter of the field, which says no process spawned; this ends one. The only processes it can touch are the ones this surface started, an id not in the pool is refused, and the effect is to undo the change BrowserOpen made, including closing an unauthenticated CDP port. Two reasons, and neither is a matter of effort. chromehand's second key, allow_auto_submit, lives in data/browser-miner-config.json resolved against the process's working directory, which inside Emma is the user's repository, and Bash can write it. The vendored files, named

The admission below stands: the four chromehand modules are upstream code and the rest of this page takes their behaviour on the surrounding code's word. What follows is a shallow read of each one, enough to say what it is, and it does not turn any claim elsewhere on this page into a checked claim.

tools/web/src/chromehand/digest.rs is the digest primitive: render one page in the shared Chrome, run a deterministic in-page extraction, and assemble the output contract. No model anywhere in it. Every extraction is a DOM walk, and the extraction itself is one long string of JavaScript, the largest single thing in the crate, returning meta, boilerplate-stripped main text, structured data from JSON-LD and tables, and an inventory of forms, fields, buttons and links each carrying a stable selector for later use. The comments inside that string are scars: a truncated selector path that clicked the wrong element, hidden elements whose selectors could not be acted on, page chrome that ate the whole link budget before the article appeared. Every section is bounded, because a digest that does not fit a context window is not a digest. certified: DEFAULT_TIMEOUT_MS is 45,000 and DEFAULT_MAX_TEXT_CHARS is 8,000, both declared in that file.

tools/web/src/chromehand/digest.rs — module doc, DIGEST_JS, DEFAULT_TIMEOUT_MS, DEFAULT_MAX_TEXT_CHARS

tools/web/src/chromehand/actions.rs holds the session action verbs: navigate, back and forward, wait-for, click, type, select, screenshot, and an in-session digest. Policy splits them in two. The read verbs follow the ordinary URL policy, and the interaction verbs additionally require a user-owned allowlist, because reading the web is ordinary and acting on it is opt-in. Two refusals are structural rather than configurable: click refuses submit-type controls, since submission is its own verb, and type refuses password fields, so the action vocabulary has no code path into credentials. The file also carries a selector resolver written as JavaScript rather than Rust, because a CSS selector cannot cross a shadow boundary or an iframe document, and the digest emits two delimiters of its own that this resolves back.

tools/web/src/chromehand/actions.rs — module doc, RESOLVE_JS, selector_needs_in_page

tools/web/src/chromehand/forms.rs is form extraction and filling. Extraction deepens the digest's field inventory with real label resolution, fieldset grouping, radio and checkbox groups collapsed into one logical field with options, ARIA custom widgets, and wizard-step signals, all by DOM walk with nothing inferred by a model. Filling types like a user, with focus and key events so page validation fires, then re-reads every targeted field from the live DOM and reports what was requested against what the field now contains. It has no submit path and refuses password fields structurally. Submit is a separate verb behind a two-key rule: the calling agent passes a flag and the user has set a key in a config file no agent may edit on their behalf. Either key missing and it exits naming the one that is missing. Without the flag, submit is an observe mode that requires a headful session, focuses the window, and waits for a human to click. unverified The two-key rule is read off this module's own doc. Whether Emma's tools can reach the submit path at all was not traced here, and the page's own account of the browser tools says nothing submits a form. Following the call graph from Emma's tool surface into this file would settle it.

tools/web/src/chromehand/forms.rs — module doc

tools/web/src/chromehand/session.rs makes Chrome itself the session daemon, with no custom IPC server. Opening a session spawns a detached Chrome with an ephemeral CDP port and an isolated profile, records the id, pid, websocket URL and target in a JSON file under .browser-miner/, and exits. Every later verb reconnects over that websocket, acts on the recorded page target, and disconnects, so the page and its state persist between commands. A session id becomes a path component, so it is constrained to hex before any path is built from it, and every read and write goes through that check. The security note is recorded in every session file rather than only in the source: a live session's CDP websocket is unauthenticated on localhost, so while it exists any local process can puppet that browser. tools/web/src/bin/browser-miner.rs is the standalone CLI over this fork: argv in, one JSON object on stdout, an exit code for the verdict. Upstream had only this; here the work lives in the library and the binary is the thin shell that turns argv into a call and an error back into an exit code, kept so standalone use still works and so the vendored integration tests can exercise the whole stack through a real process. The exit codes are upstream's, unchanged, because 22 integration tests assert them directly: 0 is a result including honest negatives such as a blocked page, a rendered 404 or a timed-out wait; 2 is bad input, a policy refusal or an expired session; 3 is browser failure. That is the only place in the crate where those integers still exist, and the library states the same taxonomy as an error type. One thing the CLI does not share with Emma's tools: it loads policy itself, keeping upstream's fall back to an allowlist file under the process's working directory, which is right for a program a user runs from their own project and wrong for a library. Two upstream features went with the fork, a batch verify harness and the job-board adapters.

A killed Chrome that answers “alive”

On Unix, spawning a detached Chrome used to end in drop(child), commented “do not wait, Chrome outlives this command”. That is true of the command-line binary and wrong of Emma. Child::drop does not reap on Unix, so a child that has been killed but never waited on becomes a zombie: the process is dead and its pid stays in the table until its parent collects it. kill -0 succeeds on a zombie, so every liveness check in the crate went on answering “still running” about a Chrome that had already taken a SIGKILL. The fork measured 181 leaked Chromes on macOS on 2026-08-26, and ps reported Z <defunct> while kill -0 returned 0 for the whole ten seconds the lifecycle test waits. reap_when_it_exits now moves the handle onto a thread that blocks in wait for the life of the browser, so the CLI is unchanged and Emma's pid table is not. It is the same shape tools/lsp recorded: correct for a binary, wrong for a library.
