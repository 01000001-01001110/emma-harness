The web: two tools, five more, and a browser

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP

WebSearch returns places to look. WebFetch renders one page in real Chrome and throws the browser away. The five Browser* tools keep it, which is a different capability: inside a session the model acts as the user, on a page that may hold their login.

Neither is registered unless it can work

pub fn web_tools() -> WebSurface {
    let mut tools: Vec<Arc<dyn Tool>> = Vec::new();
    let mut skipped = Vec::new();

    match fetch::WebFetch::detect() {
        Ok(t) => tools.push(Arc::new(t)),
        Err(why) => skipped.push(format!("WebFetch is not available: {why}")),
    }
    match search::WebSearch::detect() {
        Ok(t) => tools.push(Arc::new(t)),
        Err(why) => skipped.push(format!("WebSearch is not available: {why}")),
    }

The predecessor shipped a web_search that registered with no key and failed on every call. A turn that touched it died, and the model had no way to learn the tool was decoration, because a failed call looks exactly like a hard problem. Each omission comes back as one line for a human, which main.rs prints, so the absence is reported rather than silent.

WebFetch::detect builds a BrowserConfig and throws the result away, which looks pointless and is not: building the config is where chromiumoxide resolves the Chrome executable, so the failure surfaces at startup with a message a human can act on rather than on a first fetch several turns into a task. Its verdict is reused for the browser tools rather than asked again, because two detections that could disagree is a surface where WebFetch is present and BrowserOpen is not for no visible reason.

tools/web/src/lib.rs — web_tools; tools/web/src/fetch.rs — detect
The pool must be held for the length of the run

WebSurface::browser hands the caller an Arc<BrowserPool>. Dropping it kills every open Chrome, which is right at exit and wrong in the middle of a goal. It is handed back rather than kept inside the tools because there is no other way for a binary to end the sessions itself.

WebSearch

ArgumentDefaultCeiling

Twenty is Brave's limit rather than a preference. Asking for more is silently clamped by the API, which would make the count in the result disagree with the request. read_only: true, reaches_network: true, idempotent: true.

The key travels in an X-Subscription-Token header and never in the query string, because a key in a URL ends up in every proxy log between here and Brave. It is resolved once at construction from the environment then ~/.emma/credentials.json, never the project directory, and on unix a credentials file whose mode allows group or other access is refused rather than warned about.

tools/web/src/search.rs — classify_status

Places to look, not an answer

Zero results is Ok, and the content says so in words: No results. The query found nothing — this is an answer, not a failure. Brave sometimes omits the web block entirely rather than sending an empty array, and both shapes take that branch. Every non-empty result opens with a standing sentence: These are places to look, not an answer. The snippets are the search engine's summaries; use WebFetch on a URL before relying on what it says.

Snippets arrive as HTML, because Brave wraps matched terms in <strong>. strip_markup removes tags first and decodes entities second, so an entity-encoded bracket in the page's own text survives as a character instead of being re-read as the start of a tag. The tag stripper is a two-state scan rather than a regex, so an unbalanced < swallows the rest of the string; the alternative is a parser for a field that exists to bold three words.

tools/web/src/search.rs — render, strip_markup

network_target takes the host from base_url rather than a constant, so a run pointed at a loopback stub gates on the stub. Its detail is search for: {query}, verbatim, because the query is the thing leaving the machine and a prompt that names a host without saying what is being sent there cannot distinguish a search for a crate name from a search for the contents of a file.

WebFetch

ArgumentDefaultCeiling
url requirednonehttp/https only; loopback, file: and chrome: refused
max_chars8000200,000; bounds the prose only
max_links50120, which is also the most this browser collects from one page

Zero in either budget is refused rather than read as unlimited. read_only: true, because the throwaway Chrome profile lives in the system temp directory and is removed on teardown, and the tool cannot modify the working directory, submit a form, or run anything the model chose. reaches_network: true carries the whole of the risk. idempotent: true claims that two reads have the same effect as one, which is none, and is explicitly not a claim that the page will say the same thing twice.

Why a browser rather than an HTTP client

Three reasons, in the order they bite. A large share of the pages worth reading are JavaScript shells that serve an empty <div> to curl. A further share refuse plain fetches outright; WorkAtAStartup answers a bare request with 406 and renders fine in Chrome. And what comes back is not a DOM dump, because chromehand strips boilerplate and pre-extracts the interactive inventory.

The cost is stated: this spawns Chrome, and a stateless read is two to three seconds of launch before any bytes are read.

tools/web/src/fetch.rs — module doc

What comes back

Markdown: title, URL, status, an anti-bot warning placed above the prose, content, tables, JSON-LD, links main-content-first, interactive elements as counts, and a "Not read" section for cross-origin iframes. The status line is HTTP 404, … or HTTP status not observed, … and is never invented. A blocked page, a rendered 404 and an empty page are all Ok.

Selectors are off for this tool. It cannot click what it finds, and addresses for a thing nothing can address are a thousand tokens of noise; BrowserRead is where they come back.

tools/web/src/digest_md.rs — module doc, Limits::reading

The cuts this tool taught the workspace

CutSays
page text page text cut to {shown} of {total} characters by max_chars={n}; re-read with max_chars={total} for the whole page
links {n} of {total} links shown (main-content links first), {dropped} dropped by max_links={n}; re-read with max_links={total} for the rest. At 120: — 120 is the most this browser collects from one page, so links beyond that were never captured
JSON-LD, 2000 chars cut by a fixed cap no argument raises; the page's text and links are the whole of what this tool can return

max_links exists because the two budgets cut different things and a page can hit one while nowhere near the other. A news hub is four thousand characters of prose and a hundred links, so max_chars was never the cap that bound and raising it returned the same fifty links. Before the argument existed there was no way to ask for the rest at all, which made the notice's advice unfollowable: the honesty defect and the missing knob were the same defect.

tested tools/web/src/fetch.rs the_renderers_reason_reaches_the_outcome_intact guards the join where the reason can be dropped on the floor. every_cap_that_bound_is_reported_not_only_the_first drives two caps at once and asserts both appear. Its comment is the argument: reporting only the first is how a reader raises max_chars, sees the prose return, and never learns the link list is still short.

chromehand's failures into Emma's

pub(crate) fn map_error(e: MinerError) -> ToolError {
    match e {
        MinerError::Refused(m) => ToolError::BadArguments(m),
        MinerError::Browser(m) => ToolError::Failed(m),
        MinerError::Unavailable(m) => ToolError::Unavailable(m),
    }
}

One function with one arm per variant rather than a chain of string checks at the call site. A refused URL is something the model can fix, a browser that broke can be retried, and a machine with no browser is neither. Upstream signalled all three with process exit codes and spent one code on two of them; splitting Unavailable out is the one change.

The five browser tools

The surface is split where the approval question changes rather than where it would be convenient.

ToolArgumentsread_onlyThe question a human is answering
BrowserOpenurl, headful (default false)falsemay a browser start, and reach this host
BrowserReadsession, delta (default true), max_chars, max_links, selectorstruemay bytes keep flowing from the host this session is on now
BrowserActsession, action, plus selector / text / value / url / timeout_msfalsemay the model change state on somebody else's server
BrowserFillsession, fields: each a selector with value or checkedfalsemay the model put data into somebody else's form
BrowserClosesession, optionaltruenone; it only ends what this surface started

One Browse tool with an action argument was considered and refused. It would be one schema describing eight mutually exclusive argument shapes, which JSON Schema expresses badly and models follow badly, and one read_only bit covering both "read this page again" and "type into this form". It would also be one name for permission rules to match, so BrowserRead(domain:example.com), meaning read there and do not act there, would be inexpressible.

tools/web/src/browser/tools.rs — module doc

BrowserAct's seven verbs

VerbNeedsRefusal when it is missing
clickselectorBrowserAct.click needs selector
typeselector, textBrowserAct.type needs text
selectselector, valueBrowserAct.select needs value
navigateurlBrowserAct.navigate needs url
back, forwardnothingnone
wait_fornothing; a selector or text, or neither, which waits for the network to go quietnone

The enum lists seven strings against six named verbs, because back and forward share one implementation. timeout_ms defaults to 10,000 and is capped at 60,000, because a wait is a turn the user is watching nothing happen in. An unknown action lists the ones that exist.

BrowserAct never returns page content. Its result is a snapshot line and an instruction to call BrowserRead, and a test asserts the content is under 400 characters. A negative answer is Ok: Condition NOT met within {n} ms — the page never reached that state; this is the answer, not a failure to look. The same holds for a click that matched nothing and a select with no matching option, which additionally lists the options that exist.

tools/web/src/browser/render.rs — act, outcome_lines
The hole navigate would otherwise be

chromehand::actions::navigate runs no URL policy of its own, because upstream's CLI checked before calling it. Without an explicit check in BrowserAct::run, navigate is the one verb that reaches file:/// and localhost, from a session the user opened for something else. tested tools/web/src/fetch.rs navigating_a_session_is_held_to_the_same_url_policy_as_opening_one drives four refused URLs through the real run and asserts bad_arguments each time, then the same two through pool.open.

The cross-origin re-ask

The same argument applied to WebFetch, and until 2026-08-23 nobody had applied it. One call, so it cannot re-ask the gate from inside itself — but Chrome follows redirects, and a persisted WebFetch(domain:example.com) rule answers every later call with no prompt at all. The page that came back could be from anywhere that host chose to send us, and on a hostile page the page chooses. It now compares the digest's final_url with the host the gate was asked about and refuses when they differ, naming both and saying nothing was read back; the way through is to call WebFetch on the destination, so the host being read is the host in the prompt. tested tools/web/src/fetch.rs a_redirect_to_another_host_is_refused_and_an_ordinary_one_is_not asserts the silent cases first — a scheme upgrade, a path change, a case difference — because a guard that fired on those would be switched off within a day. Two mutations go red: the comparison removed, and the comparison weakened to a suffix match. Ran cargo test -p emma-tools-web --lib a_redirect_to_another_host on 2026-09-02: ok. unverified No test drives a real Chrome through a real redirect. What would settle it: a loopback stub serving a 302 to a different host, run through WebFetch::run with a browser attached.

The gate reads a destination from network_target before the call, out of its arguments, and a session call's arguments say session=abc rather than where abc now points. So these tools answer from the pool, with the host the session is on now, and the pool records the final_url after every verb.

tested tools/web/src/fetch.rs a_session_read_names_the_host_the_session_is_on_now moves a session to evil.example and asserts the gate is told the new host. Its failure message names the defect it guards against: "the gate was told the original host after the session navigated away from it". acting_asks_about_the_session_host_and_navigating_asks_about_the_destination covers the one verb whose destination is knowable before the bytes.

What the gate does not cover, stated by the source

The re-ask is one call late. The bytes for a redirect or a click-through have gone by the time the pool learns the host changed. A remembered rule means what it says, too: BrowserRead(domain:example.com) allows reading a session while it is on example.com and does not travel with the session.

And prompt injection is not solved. A page can contain text that persuades the model to click a button on that page, and nothing here prevents that. The gates bound the blast radius; they do not read what comes back.

tools/web/src/browser/tools.rs and mod.rs — module docs

Sessions, and the three teardowns

MAX_SESSIONS is 2. A persistent Chrome is 200 to 400 MB resident for as long as the session lives; two on a laptop already running rust-analyzer is noticeable, and three is where the user discovers the limit as swap. The third open is refused with the cap named, so the model learns the rule instead of discovering a slow machine.

A leaked Chrome is not untidiness. chromehand's own note is that a session's CDP websocket is unauthenticated on localhost, so while it lives any local process can puppet that browser, with a profile that may hold a login. This crate has leaked one before, and tools/lsp wrote it down: "tools/web leaked a Chrome per session because its teardown ran in main — correct for a binary, wrong for a library." So the teardown is three mechanisms, each covering a way the previous one does not run.

MechanismCovers
BrowserPool::closethe ordinary path: a polite CDP Browser.close, then a hard kill by pid, then the profile directory
Dropnormal exit and panic-unwind. It cannot await, so it kills by pid, which is why the pid is recorded at open time
sweep_stale_profiles at constructionabort(), SIGKILL and a power cut, none of which run Drop. A profile untouched for two hours belonged to a run that is gone

A profile the removal gives up on is now named rather than left to the backstop in silence. remove_profile waits for the process to exit and then retries ten times over roughly three seconds, because on Windows the files stay locked until the process actually goes. If it still cannot remove the directory it returns false, the pool records the path, and BrowserPool::leaked_profiles reports it; the end of a goal turns that into a warning naming the directory. Until 2026-08-23 it returned () and the ten attempts simply ran out, with no value, no record and no line anywhere.

The backstop is real and unchanged — sweep_stale_profiles clears it at the next start — but "not fatal" and "not worth mentioning" are different claims, and a profile directory holds the session's cookies. This module's own note is that a browser Emma opened may hold a login. tested tools/web/src/fetch.rs a_profile_that_cannot_be_removed_is_recorded_and_a_removed_one_is_not produces the failure rather than mocking it, by putting a file where the directory should be so remove_dir_all fails for a reason the filesystem supplies, and it asserts the clean cases too — an implementation that reported a leak every time would warn after every goal, and a warning that fires when it should not is how an operator learns to skip it. Three mutations go red on three different assertions.

That test proved the decision and not the delivery, and a reviewer found the gap the same day. Neither it nor the recording test called close or kill_all_now, so both call sites that turn a failed removal into a recorded one could be deleted with the suite green — and the warning itself was assembled inline in main.rs, where reaching it needed a real browser, a really stranded profile and a real terminal. Nothing reached it. The text now lives in pool::leaked_profile_warning, which returns Option<String> so the silence of an ordinary run is testable too. tested tools/web/src/fetch.rs close_reports_a_profile_it_could_not_remove and kill_all_now_reports_a_profile_it_could_not_remove drive the two teardowns end to end with a file parked where the profile should be; a_teardown_that_removed_its_profile_reports_nothing is the control. Deleting either note_leak call, or making the warning return None, turns a different one of the three red (verification/mutations/def056-leak-delivery.json). This is the third instance of the shape in this repository: a decision tested in the library, a delivery nothing exercises.

kill_all_now is the second mechanism exposed as a public synchronous call, for an interrupt handler that must not await, and it is idempotent. chromehand's own 30-minute idle TTL is kept as a second line of defence rather than the primary one, because a TTL doing the real work means a Chrome lives up to half an hour past the process that wanted it.

The session registry is in memory rather than on disk. chromehand records sessions in .browser-miner/session-<id>.json relative to the working directory, which inside Emma is the user's repository. BrowserPool::open therefore calls chromehand's session::open, which does the hard part of a detached spawn with no inherited handles, and then deletes the session file it wrote.

tools/web/src/browser/pool.rs — module doc, MAX_SESSIONS

BrowserClose declares read_only: true

That departs from the letter of the field, which says no process spawned; this ends one. The only processes it can touch are the ones this surface started, an id not in the pool is refused, and the effect is to undo the change BrowserOpen made, including closing an unauthenticated CDP port. The alternative is a prompt on cleanup, where somebody answers n and a browser survives with a live remote-control port.

An unknown id there is a result rather than an error, because the session being gone is what the caller wanted: There is no open browser session '{id}' — nothing to close. Omitting session closes every session this run opened.

tools/web/src/browser/tools.rs — BrowserClose

Nothing here submits a form

Two reasons, and neither is a matter of effort. chromehand's second key, allow_auto_submit, lives in data/browser-miner-config.json resolved against the process's working directory, which inside Emma is the user's repository, and Bash can write it. A second key both parties can turn is one key. Separately, "the payload was shown" cannot be guaranteed from inside a tool: the prompt is rendered by the approval gate, and an allow rule or an a answer skips it. A tool cannot force its own gate.

tested tools/web/src/fetch.rs no_tool_in_this_surface_offers_a_way_to_submit_a_form walks every property name in every schema, however deeply nested, because the hazard is a submit flag appearing inside fields[] where a shallow check would miss it. It also asserts BrowserFill's description says so, since a capability the model believes exists is a wasted turn per attempt. BrowserFill passes file: None always; attaching a local file to a form is a different capability, because it sends a file off this machine.

BrowserFill re-reads each field from the live page afterwards, so what it reports is what is actually there rather than what was sent, and its approval prompt carries the field values rather than a count of them, clipped at 60 characters each. "Fill 4 fields?" is not a question anybody can evaluate, and an unevaluatable prompt manufactures consent.

Suspected defect: the allowlist refusal names a file Emma never reads

Click, type and select require a user-owned domain allowlist, and with none they are refused outright. The refusal is produced by the vendored policy module: 

            return Err(format!(
                "refused: interaction verbs require a user-owned domain allowlist — create {} ({{\"domains\": [\"example.com\"]}}) or pass --allowlist <path>",
                DEFAULT_ALLOWLIST_PATH
            ));

DEFAULT_ALLOWLIST_PATH is data/browser-allowlist.json and there is no --allowlist flag anywhere in Emma. Emma reads ~/.emma/browser-allowlist.json, and only that, via fetch::home_allowlist. So a user following the message writes a file that will never be consulted, in their repository rather than their home directory. The tool descriptions the model sees name the correct path; the runtime refusal does not.

tools/web/src/chromehand/policy.rs — check_interaction, DEFAULT_ALLOWLIST_PATH; tools/web/src/fetch.rs — home_allowlist

certified Neither the flag nor the path reaches Emma. grep -rn -- '--allowlist' crates/ tools/ at commit a3eba74 returns nineteen lines and every one of them is the vendored browser-miner CLI, its own docs, that CLI's integration tests, or the policy module's message. Emma's binary has no such argument. grep -rn 'browser-allowlist' crates/ tools/ returns ten, of which the only path Emma computes is the ~/.emma one in fetch.rs.

The fallback is closed on Emma's side, and the divergence is written down. load_policy passes the home path or no allowlist at all, and its doc calls this "the single sharpest divergence from upstream": a file in the repository silently changing which domains are reachable is the same class of surprise as a credentials file in the repository being read. So the message is wrong about the remedy rather than about the restriction.
