Prompt caching, and the three breakpoints

Providers & models The boundary Content blocks The turn back Model limits Caching The cache floor Retry Credentials

Emma has no corpus. The stable prefix is the instructions plus the tool schema, a few thousand tokens instead of fifty, so caching needed an explicit argument. The loop is multi-call; the implementation is four small functions and one number divided by four.

Whether it is worth it here

At list price, with the published multipliers of 1.25× to write and 0.1× to read, and a 512-token floor on claude-opus-5:

  • A 2,000-token prefix costs +500 token-equivalents to write once.
  • Every later call that reads it saves 1,800.
  • Break-even is therefore P(at least one more call reads this entry inside the 5-minute TTL) ≳ 0.28.

A coding turn is never one model call: the model reads a file, gets the result, and is called again seconds later. P is effectively 1.0, so the write pays back on the second call of the first turn and every call after that is 90% off on the prefix. Caching defaults to On; use --no-cache to measure the claim. The saving is smaller than tustle-agent's measured 84%, because there the cached prefix was a 33k-token corpus. Here the prefix is small and the real money is in the conversation, which is why the history gets a breakpoint too.

Where the three breakpoints sit

crates/llm/src/anthropic.rs — system_field, messages_field, mark_breakpoint

Breakpoint 1, on the system block

crates/llm/src/anthropic.rs · system_field

/// `system` as a block array carrying the cross-turn anchor.
///
/// This block is byte-identical for every call of every turn until the
/// instructions or the tool registry change, so it is written once and read
/// for the rest of the session. Nothing here introduces bytes of its own: the
/// text is `instructions` verbatim.
///
/// `tools_chars` counts toward the minimum because the server renders
/// `tools → system → messages`, so the prefix this breakpoint captures already
/// includes the tools array.
fn system_field(instructions: &str, tools_chars: usize, caching: Caching, floor: usize) -> Value {
    if instructions.is_empty() {
        // An empty text block is rejected outright; send the bare string.
        return Value::String(String::new());
    }
    let mut block = json!({ "type": "text", "text": instructions });
    if caching == Caching::On && clears_minimum(tools_chars + instructions.len(), floor) {
        block["cache_control"] = ephemeral();
    }
    json!([block])
}
crates/llm/src/anthropic.rs — system_field

Three outcomes. Empty instructions send a bare JSON string, because an empty text block is rejected outright. Non-empty instructions always send a one-element block array, marked or not, which a_prefix_below_the_minimum_is_never_marked asserts by checking the small system prompt still arrives as [{"type":"text","text":"short instructions"}] with zero markers. tested One shape for both paths means turning caching on or off does not change the message structure, only the marker.

Breakpoints 2 and 3, in the message list

crates/llm/src/anthropic.rs · messages_field

/// `messages` as `history ++ query`, with up to two more breakpoints.
///
/// **End of history.** Byte-stable for the whole session up to the last
/// completed turn, so it is read by every remaining call of this turn and by
/// every later turn.
///
/// **End of the query, but only once a tool round-trip is already in flight.**
/// A marker here is written on this call and can only be read if the model
/// calls another tool, so it needs P(another call) ≳ 0.28 to pay for its 1.25×
/// write. Before the first tool call that is a coin flip; after one it is what
/// a coding agent does all day — it reads, then edits, then runs the tests.
/// The gate is that evidence, and it is a judgement, not a measurement: when
/// `cache_read_input_tokens` data exists for real sessions, check it.
fn messages_field(
    req: &Request,
    prefix_chars: usize,
    floor: usize,
) -> Result<Vec<Value>, LlmError> {
    let render = |m: &Message| {
        serde_json::to_value(m).map_err(|e| LlmError::Protocol(format!("render message: {e}")))
    };
    let mut rendered: Vec<Value> = req
        .history
        .iter()
        .chain(req.query.iter())
        .map(render)
        .collect::<Result<_, _>>()?;

    if req.caching == Caching::Off {
        return Ok(rendered);
    }

    let history_chars = chars_of(&req.history);
    if !req.history.is_empty() && clears_minimum(prefix_chars + history_chars, floor) {
        if let Some(content) = rendered[req.history.len() - 1].get_mut("content") {
            mark_breakpoint(content);
        }
    }

    // More than one message in `query` means the user turn plus at least one
    // tool round-trip.
    if req.query.len() > 1
        && clears_minimum(prefix_chars + history_chars + chars_of(&req.query), floor)
    {
        let last = rendered.len() - 1;
        if let Some(content) = rendered[last].get_mut("content") {
            mark_breakpoint(content);
        }
    }
    Ok(rendered)
}
crates/llm/src/anthropic.rs — messages_field, chars_of

Five conditions decide the two markers. Caching::Off returns early with none. Breakpoint 2 needs a non-empty history and a prefix, of tools plus instructions plus history, clearing the floor. Breakpoint 3 needs more than one message in query, which is the user turn plus at least one tool round-trip, and the whole prefix clearing the floor. Both use get_mut("content"), so a message that somehow rendered without a content key is skipped rather than panicking.

Note the gate for breakpoint 3 counts all of query when sizing the prefix, including the part after the marker. That over-counts relative to what the marked prefix actually contains, in a direction that opens the gate slightly early. unverified Whether that matters depends on how close a real prefix runs to the floor at the moment of the second tool call; settling it means comparing the gated estimate against cache_creation_input_tokens on a live run near the boundary.

Attaching the marker

crates/llm/src/anthropic.rs · mark_breakpoint, ephemeral

/// 5-minute TTL. Not the 1-hour variant: that doubles the write price and only
/// pays at ≥3 reads per entry, and Emma has no measured session cadence to
/// justify it. Revisit with `cache_read_input_tokens` data, not with intuition.
fn ephemeral() -> Value {
    json!({ "type": "ephemeral" })
}

/// Attach a breakpoint to the last content block of `content`, promoting a
/// plain string to a one-element block array because `cache_control` only
/// exists on blocks.
fn mark_breakpoint(content: &mut Value) -> bool {
    match content {
        Value::String(s) => {
            if s.is_empty() {
                return false;
            }
            *content = json!([{ "type": "text", "text": s.clone(), "cache_control": ephemeral() }]);
            true
        }
        Value::Array(items) => match items.last_mut().and_then(|b| b.as_object_mut()) {
            Some(obj) => {
                obj.insert("cache_control".to_string(), ephemeral());
                true
            }
            None => false,
        },
        _ => false,
    }
}
crates/llm/src/anthropic.rs — mark_breakpoint, ephemeral

Marking can refuse: an empty string, or an array whose last element is not an object. A non-empty string is promoted to a one-element block array carrying the marker (the only case where marking changes a message's shape, not only its keys). Anything else (a number or null that should never appear) returns false. The return value is not read by either caller.

A marked user string therefore renders as [{"type":"text","text":…,"cache_control":{"type":"ephemeral"}}] while an unmarked one stays a bare string. Both forms are in the golden request body, which is why that literal appears in the golden body test. certified: read the_whole_request_body_is_pinned_byte_for_byte, where the history user message is "content":"<<H>>" and the marker instead lands on the assistant turn's last block.

The size gate

crates/llm/src/anthropic.rs · CHARS_PER_TOKEN, clears_minimum, chars_of

/// Conservative chars-per-token, used only to decide whether a prefix clears
/// the minimum. Over-estimating tokens would waste a marker, so the estimate
/// leans low.
const CHARS_PER_TOKEN: usize = 4;

fn clears_minimum(chars: usize, floor: usize) -> bool {
    chars / CHARS_PER_TOKEN >= floor
}

/// How many bytes a message list renders to.
///
/// The *rendered* length, not the length of the text inside — the quotes and
/// the escapes are bytes the provider tokenises too, and this number is only
/// ever compared against the model's row in [`MIN_CACHEABLE`]. It was
/// `m.content.to_string().len()` over `serde_json::Value` and is the same
/// arithmetic over the typed form, deliberately: a breakpoint that moved
/// because the estimator changed units would be a caching regression nothing
/// on screen would report.
fn chars_of(messages: &[Message]) -> usize {
    messages.iter().map(|m| m.content.wire_len()).sum()
}
crates/llm/src/anthropic.rs — clears_minimum, chars_of; crates/llm/src/content.rs — wire_len

Dividing characters by four leans low, so a prefix that would in fact cache can go unmarked but a prefix that would not cache is never marked. The cost of that lean is a band of prefixes wide enough to cache and narrow enough to be gated out, and it is wider on high-floor models. unverified Nobody has measured how wide. Settling it means comparing count_tokens against chars_of over real session content, per model.

Three of the four markers, and one held back

The API allows four explicit breakpoints per request, counted across tools, system and messages together, and exceeding it is a hard 400. The research note cites a real harness that emitted five and had every request fail. Emma uses three and keeps one spare. A fourth was considered and declined: there is no stable boundary left for it to sit on.

The placement is pinned in three directions. breakpoints_land_on_the_stable_prefix_and_nowhere_else asserts exactly two markers before any tool call, one on system and one on the last history message, and none on the query. a_turn_already_using_tools_marks_its_newest_result asserts the third appears on the tool_result once a round-trip is in flight, and that the assistant tool_use message between them gets none. The golden-body test pins all three as literal bytes. caching_off_sends_no_markers_at_all holds the other end. tested

Three clauses of the contract that go unaccounted for

unverified in every case. They are read from Anthropic's documentation as fetched 2026-08-11 and nothing here has been run against them.

  • A cache read walks back at most 20 content blocks looking for an entry a prior request wrote. A single agentic turn with many tool_use and tool_result pairs can add more than 20 blocks, which would push the new breakpoint out of range of the last write; the documented remedy is an intermediate breakpoint roughly every 15 blocks in long turns. Emma places breakpoint 3 on the newest result only, however many rounds a turn has taken. Settling it means a long tool-heavy turn against the real API, watching whether cache_read_input_tokens collapses past the twentieth block.
  • The TTL clock runs from request start, not response end. The docs are quoted in the research note: if a response takes four minutes to stream, a follow-up reusing the same prefix must start within about one minute of that response completing. High-effort turns on Opus 5 are exactly that shape, so some fraction of writes may be expiring before the next call begins. Reading an entry refreshes its TTL at no extra write cost, so a session calling at least every five minutes keeps an entry alive indefinitely; the risk is the single long call, not the long session.
  • An entry is readable only once the first response begins streaming. N identical requests fired in parallel all pay the full write price. Emma's own loop is serial, but delegation means several subagents can be in flight at once.
notes/research/caching-mechanics.md §"What can and cannot carry a marker", §TTL, §Concurrency

One more clause Emma satisfies: changes invalidate their own tier and below. Touching the tool array or switching model invalidates everything; changing a message invalidates only the messages cache. Caches are model-scoped, so there is no cross-model reuse at all. unverified from the same documentation snapshot.

Is caching actually paying?

The three usage fields make this answerable exactly, from records already on disk, with no second run and no estimation. Against the no-cache counterfactual, which sends byte-identical content by construction because it is the same request: 

// p = the model's base input price
actual          = p · (1.0·input + 1.25·write + 0.1·read)
counterfactual  = p · (1.0·(input + write + read))

savings         = p · (0.9·read − 0.25·write)

write is cache_creation_input_tokens, read is cache_read_input_tokens. A cached read costs 0.1× of base, so it saves 0.9×; a cached write costs 1.25×, so it loses 0.25×. Emma sends only 5-minute markers, so the general form's − 1.0·write_1h term drops out. The number goes negative when the harness pays write premiums it never reads back: a broken prefix, or the accepted-and-inert defect on the next page for every non-Opus-5 model. It does not credit latency.

The inputs are persisted per call: sub.model_call records in ~/.emma/sessions/*.jsonl carry all four usage fields. A starting query, from the caching plan: 

jq -s '[.[] | select(.kind=="sub.model_call")] | group_by(.sub_id)
  | map(sort_by(.at_ms) | {sub_id: .[0].sub_id, agent: .[0].agent,
      first_write: .[0].cache_creation_input_tokens, calls: length,
      net: (map(0.9*.cache_read_input_tokens - 0.25*.cache_creation_input_tokens)|add)})' \
  ~/.emma/sessions/sess-*.jsonl

notes/plans/caching-defects.md §"Stage A — measure, from data already on disk"

Two companion views sit alongside it. Cached fraction, read / (input + creation + read), is a health gauge, not a cost claim; it reads low early in a session when history is small. An expected-hit regression checks that within a TTL, call N reads at least what call N−1 established, catching a change that silently breaks the prefix.

For a sense of the target: Claude Code sessions measured in the wild ran a 97.2% cache hit ratio, 40M cache-read tokens against 653K direct input tokens across eight sessions. unverified That is a third party's number for a different harness, quoted as a magnitude to aim at rather than a bar Emma has been held to, and nobody has computed the same ratio for a real Emma session.

Compaction invalidates the message half of the prefix every time it fires. The first call afterwards re-writes what it would have read, at 1.25× instead of 0.1×. No marker placement avoids that because the bytes changed. See sessions & context; it is named here because it is often the largest term in Emma's caching bill when the arithmetic goes negative.
