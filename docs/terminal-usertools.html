The tools a person launches

The terminal Surface Frame Layout Colour Themes Vocabulary Transcript Markdown Diffs Status Sidebar Dock User tools Pages

The sidebar's middle section lists seven entries in a fixed order. Three start a program on the machine; four run inside Emma and say so rather than pretending to launch — Search, and the three tool pages. Three rules carry the design, and every one exists because breaking it fails silently. The sharpest of them cost twenty-two green tests and a canary in the wrong stream to find.

Three of these used to launch programs and now do not. Settings opened ~/.emma/settings.json in the configured editor, the Data Explorer opened the file manager on ~/.emma, and Memory opened nothing at all while claiming it would. Each is a page in the frame now — see the tool pages. The launches were deliberate and correct as built; the owner ruled on 2026-08-23 that they should be pages, which is a different thing from their having been wrong.

Tool::in_app says a tool runs inside Emma; Tool::routed says the frame actually takes its key. They were one predicate, and the gap between them was a defect. in_app's doc has always said “the shell routes their keys itself”, which was true of Search and false of Memory: nothing routed Memory, so launch_tool sent it to launch, which refused it with the words “the frame owns the m key” — a key the frame had never claimed. The sidebar advertised Alt+M and pressing it produced a warning.

launch still refuses an in-app tool rather than returning success, because “returning Ok for a launch that never happened is a fake receipt”. What changed is that the frame now intercepts all three before they reach it. tested the_catalogue_lists_all_seven_tools_with_their_fixed_keys, whose assertion has been through all three states and carries the history: it first claimed both in-app tools were available because their keys are live in the frame — the claim rather than the behaviour, which is what held the defect in place — was then inverted with a note saying the day a Memory page existed it should be flipped back, and was flipped back on the day that happened.

An unavailable tool stays in the list with available: false and a detail naming what was looked for, because “a key that is absent teaches nothing, a key that says ‘none of code, cursor, subl, zed, nvim is on PATH’ is a to-do list.” The sidebar draws n/a where the chord would be and dims the label.

catalogue may run on every draw, so PATH lookups are cached for the life of the process. That also makes “a program installed mid-session appears after a restart” true by construction rather than intermittently. settings.json is re-read on every call, one small file read, so the Settings tool's own writes show up on the next frame.

The machine is a trait

Everything the decision layer wants to know about the world sits behind trait Machine: os, env, find, exists, tools, home. os() returns data rather than being a cfg, and the region comment says why: “the unix refusal rules are asserted by tests that run on Windows.”

The test fixture's own helper carries the seam's honest limit, and it is worth reading because it is the kind of thing usually left undiscovered:

crates/emma/src/usertools.rs · the test helper host

    /// The machine under test is fake — `Fake::new(Os::Windows)` models a
    /// Windows box on any host, which is the whole point of `Machine` — but
    /// `plan` resolves the paths it is handed with real `std::path`, and
    /// `std::path` only knows the separator of the platform it was compiled
    /// for. So a literal `C:\pwsh\pwsh.exe` is one filename on unix, whose
    /// `file_stem` is `C:\pwsh\pwsh` and which `is_absolute` denies. That does
    /// not make these tests fail on unix so much as make them assert something
    /// else: `what` reads `C:\pwsh\pwsh in …`, a configured program is looked
    /// for on `PATH` instead of on disk, and `nvim` stops being recognised as a
    /// terminal editor. **The fake OS decides the behaviour; the host decides
    /// the spelling**, and this is the second half.

The defect that forced raw CreateProcessW

The interactive frame owns the alternate screen, so a child process that writes to that console wrecks the display. Unlike a dead key, the user cannot tell what happened. On Windows, every spawn shape std::process can express fails that requirement, and each was refuted by measurement rather than by review.

ShapeWhat was measured
CREATE_NEW_CONSOLE + default stdio A new window whose handles still point at Emma's console: Rust sets STARTF_USESTDHANDLES whenever the parent has std handles at all. The first certify run's canary landed in this process's own output stream.
CREATE_NEW_CONSOLE + null stdio An interactive shell reads a NUL stdout as redirection and dies. Measured: a conhost-hosted client under NUL handles exits instantly without running.
hosting under conhost.exe Flips modes on the same axis, a real window with no handle info, a headless ConPTY renderer when handed pipes, so it inherits the same problem.
raw CreateProcessW, bInheritHandles = FALSE, no hStd fields The OS builds the console and binds the child's handles to it, and nothing of Emma's can reach the child even in principle. This is what ships. tools/web spawns its detached Chrome the same way.

lpApplicationName is passed as well as the command line's first token, “the program to run is then never re-derived by parsing the line, spaces or no spaces.” append_arg implements the documented CommandLineToArgvW quoting rules, the same algorithm std uses, and the doc says why the effort is warranted even though Windows paths cannot contain a quote: “an argument is not always a path, and a quoting bug here is an argv boundary moving — exactly the class of failure this module refuses everywhere else.” tested: quoting_matches_the_commandlinetoargvw_rules pins seven cases including a trailing backslash inside quotes and an embedded quote with backslashes in front of it.

What the certification actually asserts, and what it cannot

Twenty-two green tests said nothing about any of this, and could not have: an inherited handle bypasses the test harness's own capture, so the write reaches the console without passing through anything an assertion can see. What caught it was a canary, a known string the spawned child prints, and a human reading the run's scrollback for its absence. That method is now the test, and it says so of itself:

“run by hand… and read the OUTPUT, not just the pass: the NewConsole test's claim is that the canary does NOT appear anywhere in the run's output, which the assertion cannot see (an inherited handle bypasses the test harness's capture) — the reader checking the scrollback is the certification.”

The other three spawn shapes

Windows Detached uses std, with CREATE_NO_WINDOW plus null stdio. The window flag is needed because “a .cmd shim like VS Code's runs via cmd.exe, a console program that would otherwise flash or attach”, and the null stdio is so nothing it prints can reach any console Emma owns.

Unix gets null stdio on every spawn, “the corruption channel is writes to this terminal, and null closes it”, plus its own process group so a signal aimed at Emma's group is not also aimed at the child. Window is not consulted there, because both variants detach the same way and NewConsole is never planned on unix. tested: gui_launches_are_detached_and_shells_get_their_own_console walks five tools on both unix flavours and asserts every plan is Detached.

adopt is how a child is let go. Dropping a handle never kills a process; on unix an unreaped child becomes a zombie if it exits before Emma does, so a throwaway thread waits on it, “and if Emma exits first the child is init's problem, which is the point.”

A configured value is one program, never a command line

crates/emma/src/usertools.rs · resolve_value

fn resolve_value(m: &dyn Machine, value: &str, origin: &str) -> Result<PathBuf, String> {
    let p = Path::new(value);
    if p.is_absolute() {
        if m.exists(p) {
            Ok(p.to_path_buf())
        } else {
            Err(format!("{origin} is set to {value}, which does not exist"))
        }
    } else if let Some(found) = m.find(value) {
        Ok(found)
    } else if value.chars().any(char::is_whitespace) {
        Err(format!(
            "{origin} is set to {value}, which is not on PATH (a configured value is one \
             program name or absolute path, never a command line)"
        ))
    } else {
        Err(format!("{origin} is set to {value}, which is not on PATH"))
    }
}
crates/emma/src/usertools.rs — resolve_value

Splitting a string on spaces is the first half of running text through a shell, and a path with a space in it is not an argument boundary. A value that does not resolve produces an error naming it, never a fall-through to a probe, because “a substitution looks identical to success right up until the wrong program opens.” The extra clause for a value with whitespace in it exists so the rule the user broke is named rather than merely reported.

$VISUAL and $EDITOR get one concession, because the wider world does put command lines in them: a value there that does not resolve as a whole is skipped and the chain continues. Skipped, not split. tested: an_editor_env_var_holding_a_command_line_is_skipped_not_split sets EDITOR=vim -u NONE with vim on PATH and asserts the chain falls through to code, so “split, this would be vim (with args smuggled somewhere); skipped whole, the chain falls through to the probe.” the_editor_chain_is_setting_then_visual_then_editor_then_probe walks all four rungs.

Refusing at planning time rather than at the keypress

plan is pure: a tool and a machine in, a Launch value or an error string out. Nothing in the region starts a process, which is what makes every branch testable on any OS, and it is also why the catalogue can say a tool is unavailable before the key is pressed.

Two refusals are worth reading. A terminal editor on unix is refused rather than launched, and the message names the editor and where it came from so the fix is obvious. is_terminal_editor is a list rather than a heuristic, and the asymmetry is priced: “a wrong ‘GUI’ guess corrupts the screen, a wrong ‘terminal’ guess costs one settings line, so unknown names are assumed GUI and the list holds only the certain cases.” That is also why the unix probe list omits nvim entirely: probing for it would manufacture an unavailability two lines later.

A .cmd or .bat bound for a new console is refused by console_hostable, because CreateProcessW cannot execute a cmd script and routing one through cmd.exe would re-open the handle question the raw spawn exists to close. It is checked twice, at planning time so the catalogue can say so, and again inside new_console::spawn, “which is the layer that must hold even if a future plan forgets to ask.” tested: a_cmd_script_cannot_be_promised_a_console_window also asserts the other half, that a GUI editor as a .cmd shim stays fine, because it takes the Detached path where std handles cmd.exe itself.

Settings used to have a sanctioned fallback and no longer has one. fallback_opener tried notepad, open -t or xdg-open when the editor chain came up empty, and the file argued it was not a substitution smuggled past the report-don't-swap rule: “the tool's promise is ‘edit your settings’, not ‘open your chosen editor’.” That argument still holds; it is simply not a launch any more. The chain, both plan functions and the fallback went out together on 2026-08-23, and git log has them.

The PATH probe has to agree with the spawner

On Windows a launcher is often a .cmd shim and Rust's Command does not consult PATHEXT, so the probe must, “or available: true would name a program the spawn cannot start.” candidates tries exe, com, cmd, bat in that order, matching the common PATHEXT prefix, and takes a name that already carries an extension literally.

On unix there are no extensions to resolve and the thing separating a program from a file is the executable bit, which is_program consults. The test for it names what it is defending: “Without this, that mode & 0o111 had no test on any platform, and dropping it would have turned every readable file on PATH into an installed editor.” tested, one cfg-gated test per platform, both against a real temporary directory.

search_in takes the PATH explicitly rather than reading it, “so tests can probe a constructed directory without mutating the process environment other tests share.” The cache lives in RealMachine::find above it, so the pure walk stays testable.

One string, two tenses

Launch::what is present tense with no verb, pwsh in C:\src\emma. The catalogue shows it as-is; launch prefixes opened . “One string, two tenses, so the promise and the receipt cannot drift apart.” tested: launch_returns_what_happened_in_words compares against format!("opened pwsh in {}", cwd().display()), and three sibling tests prove no spawner is reached for an in-app tool, an unavailable tool, or after a failed spawn.

ensure_settings_file is gone too. It created settings.json through settings.rs so the file an editor opened was the file every other reader would have produced, and left an existing one byte-for-byte alone — “load/save would reformat it, and a settings file that mutates on open is one nobody can diff.” Nothing opens that file on Emma's behalf now, so nothing needs to create it first. The consequence is worth stating: a machine that has never had a settings.json written still has none after opening the Settings page, and the page shows the resolved defaults rather than a file.

Coverage

usertools.rs was 1,736 lines when this page was written and is 1,649 now: the two page tools took four functions and three tests out with them.
