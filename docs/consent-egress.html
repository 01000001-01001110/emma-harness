The egress question

Consent & permissions The two axes The ladder The egress question The five answers EXEMPT and the floor Permission rules Matching a host Hooks

A second gate, with its own grant, its own scope and its own prompt. It runs inside decide, between the deny rule and the bypass, and a tool that passes it can still be refused by the rungs below.

crates/emma/src/approval.rs — Approvals::egress

The function

Its first statement returns Allow for any tool that does not declare egress, so decide calls it unconditionally and no arm added above it later can skip the network question. 

async fn egress(
    &self,
    name: &str,
    meta: ToolMeta,
    target: Option<NetworkTarget>,
    term: &Term,
) -> Verdict {
    if !meta.reaches_network {
        return Verdict::Allow;
    }
    let Some(target) = target else {
        // Fail closed. A tool that declares egress and cannot say where is
        // asking for a grant nobody can write down, and the alternative
        // reading — "no target, so nothing to gate" — hands silent network
        // access to whichever tool forgets to implement one method.
        return Verdict::Deny(
            Decider::Unevaluable,
            format!(
                "{name} reaches the network but did not name the host this call would \
             contact, so there was nothing for the user to approve and it was not run. \
             That is a defect in {name}; it is not something to work around from here."
            ),
        );
    };
    // Bare `Tool` rules and this tool's `domain:` rules both answer here.
    let rule = self.rules.lock().await.for_egress(name, &target.host);
    if rule == Some(Decision::Deny) {
        return Verdict::Deny(
            Decider::Rule,
            format!(
                "A `deny` permission rule forbids {name} from contacting {}. It was not run, \
             no answer at a prompt can change that, and a different host to reach the \
             same content is not a workaround — it is the thing the rule is about.",
                target.host
            ),
        );
    }
    // The bypass, here as well as in `decide`. Both questions are waved
    // through by one flag; a `deny` rule is what neither of them waves.
    if self.gate == Gate::SkipAll {
        return Verdict::Allow;
    }
    let forced = rule == Some(Decision::Ask);
    if !forced {
        if rule == Some(Decision::Allow) {
            return Verdict::Allow;
        }
        if self.hosts_allowed.lock().await.contains(&target.host) {
            return Verdict::Allow;
        }
    }
    if self.gate == Gate::Unattended {
        return Verdict::Deny(
            Decider::NoOneToAsk,
            format!(
                "{name} would send a request to {} and this is a non-interactive run (-p), \
             so there is nobody to approve that host. It was not run. Work from what is \
             already on this machine, or tell the user which host needs approving and \
             stop.",
                target.host
            ),
        );
    }

    // The two grants on offer, and they are deliberately different sizes.
    // The narrow one is the host the user is looking at — the natural answer
    // for a `WebFetch` on `apnews.com`. The wide one is every call to this
    // tool, any host, which is "all web searches in the directory" as it was
    // asked for; it is a separate keystroke because guessing which one
    // somebody meant is how they end up granting more than they read.
    let offers = match (forced, &self.file) {
        (false, Some(_)) => Offers {
            narrow: Some(Rule::domain(name, &target.host)),
            wide: Some(Rule::every_call(name)),
        },
        _ => Offers::default(),
    };

    term.prompt_header(name, &network_preview(&target));
    match self
        .ask(name, term, Question::Network(&target.host), &offers)
        .await
    {
        // `a` grants no more here than `y` does — see `Question::Network`.
        Some(Answer::Yes | Answer::AlwaysThisTool) => {
            self.hosts_allowed.lock().await.insert(target.host.clone());
            term.note(&format!(
                "{} is approved for the rest of this session (this process only)",
                target.host
            ));
            Verdict::Allow
        }
        Some(answer @ (Answer::RememberNarrow | Answer::RememberWide)) => {
            let rule = match answer {
                Answer::RememberWide => offers.wide.clone(),
                _ => offers.narrow.clone(),
            };
            self.keep(
                rule.unwrap_or_else(|| Rule::domain(name, &target.host)),
                term,
            )
            .await;
            Verdict::Allow
        }
        Some(Answer::No) => Verdict::Deny(
            Decider::Human,
            format!(
                "The user declined to let {name} contact {}. It was not run. Do not retry it \
             unchanged and do not try a different host to reach the same content — ask \
             what they would prefer.",
                target.host
            ),
        ),
        // End of input, or a scripted run that ran out of answers.
        None => Verdict::Deny(
            Decider::NoAnswer,
            format!(
                "No approval was given for {name} to contact {}, so it was not run.",
                target.host
            ),
        ),
    }
}

A declared reach with no named host is denied

The let ... else is the one fail-closed branch in the file. The other reading, "no target, so nothing to gate", would hand silent network access to whichever tool forgets to implement network_target. The denial text tells the model this is a defect in that tool rather than something to route around. tested crates/emma/src/approval.rs a_tool_that_declares_egress_and_names_no_host_is_denied queues two Yes answers, so a gate that fell through to a prompt would have allowed the call, and asserts the reason contains "did not name the host".

crates/emma/src/approval.rs — tests::a_tool_that_declares_egress_and_names_no_host_is_denied

A grant is one host, for the process

hosts_allowed is a HashSet<String> separate from session_allowed. The first fetch to docs.rs asks; every later fetch to docs.rs in this process does not; a fetch elsewhere asks again. A host approved while running WebSearch is approved for WebFetch too, because what the human approved was a host.

Keying both grants on one set would mean approving WebFetch once approved every host it is later pointed at, which the field's own comment names as the grant this design refuses to offer. tested crates/emma/src/approval.rs the_first_call_to_a_host_asks_and_later_ones_do_not queues one Yes for three calls. a_second_host_is_a_second_question queues one for two hosts and expects the second to be denied. a_grant_is_the_host_and_not_the_tool approves a host under WebSearch and then calls WebFetch with an empty queue.

crates/emma/src/approval.rs — Approvals::hosts_allowed; tests as named
A search the provider runs never reaches this gate

WebSearch reaches the engine from this machine and this gate asks about it like any other network tool. There is a second, opt-in search that does not: "web_search": true in settings lets the model search through its provider, on the provider's side of the wire inside the same API call, and nothing here sees it. What leaves is the model's query, to the same place the whole conversation already goes. While it is on, every run says so at startup, which is disclosure rather than consent per call, because by the time the loop sees the turn the search has already run. It is off by default for exactly that reason. The web page carries the rest.

Why a means y here

On the network question Answer::Yes and Answer::AlwaysThisTool land in the same match arm, because a y already covers this host for the rest of the session. Accepting a and giving it a different meaning would be a keystroke that silently grants a tool where the reader thinks they granted a host. The enum that carries this distinction is Question, whose only job is to keep the wording on screen from drifting from the set the answer is filed under.

crates/emma/src/approval.rs — Question::Network, Approvals::egress

The two rules on offer

On the network question the narrow rule is Rule::domain(name, host) and the wide rule is Rule::every_call(name). Both are None when there is nowhere to write, or when an ask rule forced the prompt: in the second case an allow written by r would be outranked by that very rule, so the keystroke would write a grant that does nothing.

The unwrap_or_else under the remember arm covers the scripted asker, which can hand back an answer the terminal would never have offered. It falls back to the narrow rule, not the wide one.

crates/emma/src/approval.rs — Offers, Approvals::egress

Which rules answer here

Rules::for_egress(tool, host) matches a bare Tool rule for that tool and any of its domain: rules. Rules::for_call(tool, args), which answers the local question, matches bare rules plus the command and path shapes, and its Spec::Domain arm is false, so a domain: rule never becomes permission to run a tool. The local question now reads the arguments, so Bash(git *) and Read(./src/**) answer it. for_tool still exists and is no longer what the gate consults. No tool in the surface both writes and names a host today. tested crates/emma/src/approval.rs a_domain_rule_does_not_become_permission_to_run_the_tool constructs a hypothetical Uploader with read_only: false, reaches_network: true, allows Uploader(domain:docs.rs), and asserts the call is denied.

A tool that both writes and reaches answers twice

The two questions are asked in sequence, so a tool declaring both bits faces both. tested crates/emma/src/approval.rs a_tool_that_both_writes_and_reaches_answers_for_both queues one Yes, which the host question consumes, and asserts the call is still denied when the write question finds an empty queue. Its comment says why it exists: a stray return Allow in the first arm would make the second unreachable, and nothing else in the file would notice.

Under -p

The unattended denial names the host as well as the reason, because a message saying only "approval was needed" leaves the model unable to tell the user what to approve. tested crates/emma/src/approval.rs unattended_denies_egress_and_names_the_host asserts the sentence contains both docs.rs and -p.
