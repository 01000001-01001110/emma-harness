The agent loop

The kick

The agent loop One turn Failure The memo Endings The kick Budgets Done Seams

The kick is what makes this a loop rather than a chat client. The model stopped, the check said the goal is not met, so the loop pushes a user message and goes round again. The message states why the goal is not recorded as done, restates the goal verbatim, and lists up to five calls that have already failed.

What it says

// crates/emma/src/goal.rs
/// Compose the kick: why it is not done, the goal restated, and what has
/// already broken.
///
/// The last part matters. Without it the honest reading of "continue" is "try
/// again", and the first thing a model retries is the thing that just failed.
pub fn kick(goal: &Goal, why: &str, failed: &[String]) -> String {
    let mut s = format!(
        "The goal is not recorded as done: {why}. Nothing has been lost — you still have every \
         tool, and the goal is unchanged:\n\n{}\n\nContinue working on it.",
        goal.text.trim()
    );
    if !failed.is_empty() {
        s.push_str(&format!(
            "\n\nThese calls failed earlier in this goal — change the approach rather than the \
             spelling:\n- {}",
            failed.join("\n- ")
        ));
    }
    s
}

Composed, with one failure to quote, it reads: 

The goal is not recorded as done: your last message did not end with the
completion line. Nothing has been lost — you still have every tool,
and the goal is unchanged:

port the middleware

Continue working on it.

These calls failed earlier in this goal — change the approach rather
than the spelling:
- Bash(cargo build --release)
crates/emma/src/goal.rs — kick, MarkerClaim::verdict

goal.text.trim() rather than goal.opening_turn(), so a kick restates what the person typed and does not repeat whatever a UserPromptSubmit hook injected in front of it. The why comes from the DoneCheck, so a different check produces a different first sentence with no change here. tested crates/emma/src/goal.rs a_kick_states_the_reason_the_goal_and_what_already_failed asserts all three parts are present.

The failure list, and why it is not optional

Without it the plain reading of "continue" is "try again", and the first thing a model retries is the thing that just failed. The labels come from label_of, the same rendering the memo key is built from, so what a kick shows and what the memo refuses describe the same call. See Failure for how a label is shortened. 

// crates/emma/src/agent.rs
fn tail(v: &[String], n: usize) -> Vec<String> {
    v.iter().rev().take(n).rev().cloned().collect()
}

/// How many distinct failed calls a goal remembers. Four times what a kick
/// shows, so the cap is a bound on the collection rather than a second, quieter
/// version of the kick's own limit.
const FAILED_EVER_MAX: usize = 20;

/// Drop the oldest entries past the cap. See where the list is seeded for why
/// oldest-first is the right end to lose.
fn trim_oldest(v: &mut Vec<String>) {
    if v.len() > FAILED_EVER_MAX {
        v.drain(..v.len() - FAILED_EVER_MAX);
    }
}

tail(&failed_ever, 5) bounds what one kick shows, keeping the five most recent in their original order. FAILED_EVER_MAX bounds the collection at four times the kick's limit so the cap is not a quieter duplicate of the same number. The list is written into a session record and read back by --resume, so an unbounded collection would be a growing payload rather than a transient one.

crates/emma/src/agent.rs — tail, trim_oldest, FAILED_EVER_MAX

The oldest go first. A kick's job is to stop the model repeating what it just tried, and a failure twenty calls ago that has not recurred is the least likely to be the one it is about to repeat. trim_oldest runs in two places: once when the resumed list is seeded, so a file written by a build with a larger cap is trimmed on arrival, and once after each new label is pushed.

crates/emma/src/agent.rs — Agent::run_goal

Labels are deduplicated by if !failed_ever.contains(&label), so a call that fails in the same way three times occupies one slot. Two calls that differ only past the 60-character cut share a label and therefore one slot, while remaining distinct to the memo, whose key uses the full arguments. certified by reading label_of and memo_key_of side by side: the first passes its arguments through compact, the second interpolates the whole Value.

Sending one

// crates/emma/src/agent.rs — Agent::run_goal
kicks += 1;
kicked = true;
tool_calls_since_kick = 0;
let kick_text = goal::kick(goal, &why, &tail(&failed_ever, 5));
self.s.log.append(
    "kick",
    json!({ "turn_id": turn_id, "n": kicks, "why": why, "text": kick_text }),
);
self.s.term.kick(kicks, self.s.budgets.max_kicks);
place(&mut query, &mut pending_turn, Vec::new());
query.push(Message::user(kick_text));
continue;

The held assistant turn is placed with no results, because a turn that called nothing is answered by nothing, and only then is the kick pushed as a user message. Doing it the other way round would put a user turn before the assistant turn it is answering. The record carries both why and text: why is the reason a human reads in the file, text is the bytes the model was sent, and the fold has to put the second back rather than recomposing it.

crates/emma/src/agent.rs — Agent::run_goal, place

term.kick(kicks, max_kicks) is what the user sees, so a nudge is never silent, and it carries both numbers so a run that is about to stop looks different from one that has two nudges left.

Kick bounds

A kick that fires forever is worse than no kick. A hard count and a stall rule stop it, and the goal ends the moment either is reached: max_kicks, default 3, a hard count for the whole goal, and the stall rule, which needs no cooperation from the model at all. Both sit under the iteration, token and wall-clock budgets, so the worst case is bounded by arithmetic rather than by good behaviour.

crates/emma/src/goal.rs — module doc; crates/emma/src/agent.rs — Agent::run_goal

The cost is that a goal genuinely needing a fourth nudge stops one step early. It says which limit stopped it, so the user can raise it with --max-kicks. tested crates/emma/tests/loop.rs the_kick_is_bounded_by_its_budget sets max_kicks = 2 and asserts the seventh scripted turn was never requested, so the bound is enforced in code, not only in the ending message. the_kick_fires_when_the_model_stops_without_claiming_completion covers the other direction. Both pass at this checkout: cargo test -p emma --test loop printed test result: ok. 35 passed; 0 failed on 2026-09-02. certified for that run.

A kick is a full model call

Each nudge sends the whole request again: instructions, tool definitions, history and the goal in flight with the kick on the end. So three kicks are three iterations off max_iterations and three calls' worth of spend against max_tokens. The kick budget bounds how many times the loop will argue; it does not bound what arguing costs. See Budgets. certified by reading run_goal: the kick branch ends in continue, which re-enters the loop at the guards and rebuilds a full Request.

What is not verified here

unverified Whether a kick carrying five failed labels changes a real model's approach rather than its spelling. The sentence asks for it and nothing measures the answer. This is what the failure list is for, and it is about the model rather than the loop. What would settle it: a live session driven into repeated failures with --max-kicks raised, and the session JSONL read to compare the calls before and after each kick.

unverified Whether five is a better number than three or ten. Nothing in the tree records a measurement behind it, and no test would fail if it changed. What would settle it: a comparison across live runs, which nobody has run.
