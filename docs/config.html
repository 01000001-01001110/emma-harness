Surface

Configuration

Emma reads seven kinds of file across three scopes, and they do not all fail the same way. A mistake in the project's harness refuses the boot and names the file; a mistake in a personal preference costs the preference and says so; a key belonging to another program is ignored on purpose. This page is the one to read when something you configured did not happen, so it goes through every file, every key, and the order they are consulted in.

certified proven against the real thing
tested a test that was shown to fail
unverified believed, not checked

What is read, from where

There is no single configuration file and no merged view of one. Two different crates read from three scopes, and the reason a reader gets lost is that the project's configuration and the person's are different files with different names in different places. The table is the whole map.

filescoperead bywhat it decidesif it is malformed
.emma/config.json project emma-harness default_persona, personas, hooks, statusLine, permissions refuses to start, naming the file and the key
.claude/settings.json project emma-harness hooks, statusLine, permissions. Every other key is ignored refuses to start if it is not JSON, or if the hooks block is wrong
<harness>/settings.local.json project, local emma-harness permissions only. Where a remembered grant is written refuses to start
~/.claude/settings.json user emma-harness permissions.deny only — never allow, never ask skipped in silence; the run continues with no user-scope rules
~/.emma/settings.json user emma (the binary) provider, models, validated, tools, theme read as if empty; every value falls back to its default
~/.emma/credentials.json user emma-llm the API key per provider an error naming the file when a key is needed; a write refuses rather than replacing it
~/.emma/themes/<n>.json
<harness>/themes/<n>.json		 user, then project emma colours, per role a notice above the prompt; the built-in theme is drawn
crates/harness/src/lib.rs (load_selecting, read_permissions, user_permissions); crates/emma/src/settings.rs; crates/llm/src/auth.rs; crates/emma/src/term/theme.rs

The split between rows 1–3 and rows 5–7 is stated in settings.rs's own module doc and is worth carrying: the project's configuration is shared by everyone who clones the repository, so a personal default written there would be two files answering one question with no rule for disagreeing — and the answer that won would be the repository's, on somebody else's screen. Nothing personal is settable from the project, and nothing about the project is settable from the home directory.

Discovery, and where it stops

The harness is found the way git finds .git: walk up from the working directory until a directory named .emma/ or .claude/ turns up. Nearest ancestor wins, and within one directory .emma/ beats .claude/ outright — the loser is ignored entirely, never merged. Merging would mean "which file did this instruction come from" stops having an answer.

crates/harness/src/lib.rs — discover_in

Why the home directory has its own rules

~/.claude/ is never adopted as a harness, and it is skipped so completely that it does not even appear in the not-found error — a refusal listing a path Emma declined to consider reads as a bug in the search. It is another program's user-scope configuration: global permissions, global agents, global skills, chosen in sessions Emma was not part of. Booting on it would be standing instructions from a directory nobody associated with this project. certified — ~/.claude/ exists on this machine (ls -d ~/.claude → /c/Users/owner/.claude/) and the search list below ends without it.

~/.emma/ gets the second rule, and it was paid for. It used to be eligible for existing — and emma api creates it to store a key. From the moment somebody saved a credential, every project without a harness of its own adopted the home directory and booted with no instructions, no persona and the full write-capable tool surface. Nobody chose that; it was the side effect of saving a key. What makes a directory a harness now has to be something a person put there on purpose: config.json or personas/. credentials.json, sessions/ and settings.json are Emma's own bookkeeping and say nothing about how Emma is configured. certified — the line above is that rule firing on the owner's real ~/.emma/, which holds settings.json and nothing else that counts.

crates/harness/src/lib.rs — configured_by_hand, and the comment in discover_in
The comparison that decides "is this the home directory"

Both sides are canonicalised rather than compared as strings. Case is only one of the ways two spellings of one directory differ — a trailing separator, a .. in the middle, a Windows 8.3 short name and a home reached through a symlink are the others. The case bug is the one that actually bit: C:\Users\Owner against C:\Users\owner left the skip inert, and Emma adopted the user's global .claude/.

Overriding it

EMMA_ROOT=<dir> replaces the whole walk, and a value that is not a directory is an error rather than a fall-back to searching — an override that quietly searched would boot the agent on configuration nobody asked for. Which flavour the directory is read as comes from its name: a directory called .claude is read as Claude Code's layout, anything else as Emma's.

crates/harness/src/lib.rs — ROOT_ENV, Flavor::of

EMMA_PERSONA=<name> selects a persona for one run, beating the spine's default_persona. Selection is never the model's: a model choosing its own persona is a self-modifying prompt, so there is no tool and no command that does it.

The project's spine

Whichever directory was found, exactly one file in it is configuration rather than prompt text. In .emma/ that file is config.json; in .claude/ it is settings.json. They are not the same format and Emma reads different amounts of each.

.emma/config.json — every key

keytypewhat it does
default_persona string Which personas/<name>/ supplies the prompt. EMMA_PERSONA beats it.
personas object Per persona: description (prose, nothing branches on it), tools (a real allowlist), skills (absent = every skill; present = exactly these), hooks.
hooks object name → {event, command, matcher, timeout_ms, text}. event is one of PreToolUse, PostToolUse, UserPromptSubmit; command must canonicalise to inside <root>/hooks/.

.claude/settings.json — three keys of many

Emma reads hooks, statusLine and permissions from this file and ignores everything else. The three are taken separately, so one unreadable key cannot cost another: a status line that will not resolve must not stop a hook from resolving.

crates/harness/src/claude.rs — Settings; crates/harness/src/lib.rs — load_selecting, the Flavor::Claude arm
deny_unknown_fields cannot go on this file

It carries keys Emma has no opinion about, written by a program Emma does not run, and denying them would mean refusing to boot in essentially every real Claude Code repository. A rule that fires on correct configuration is an outage, not a safety property. So the outer object is permissive, and the hooks block inside it is strict — which is where a silently-ignored key would cost something.

This matters if you are adding a key Emma should read: adding it to the struct changes nothing about the other keys, and a misspelling of your key will be swallowed exactly like the rest. There is no spelling check available here at all, which is the price of the format being somebody else's. The compensations that exist are the strict inner blocks and emma config check, which prints what was actually taken.

The same relaxation is made in two further places for the same reason: skill frontmatter under .claude/skills/, and agent frontmatter under .claude/agents/. The agent struct's doc states it outright — measured against a real library of 90 agent files, category and version appear throughout and every one of them would have been a boot failure.

What a hook command may be

Claude Code's command is a shell string: it may pipe, expand variables, or name any executable on the box. Emma canonicalises a path, containment-checks it inside <root>/hooks/, and execs an argv with a cleared environment. So $CLAUDE_PROJECT_DIR/.claude/hooks/x.sh, .claude/hooks/x.sh and hooks/x.sh all resolve, and anything carrying whitespace, a shell metacharacter or an absolute path is a startup error that says what to do about it. Quietly dropping a guard the operator believes they have is the one outcome ruled out.

crates/harness/src/claude.rs — translate_command, SHELL_METACHARACTERS

An event name Emma does not implement is the same class of error rather than a skip. Emma has three events; Claude Code has more, and a Stop guard copied across would never fire while looking configured. One conversion is silent and worth knowing: Claude Code's timeout is seconds and Emma's timeout_ms is milliseconds, so the reader multiplies by a thousand when it flattens the block.

crates/harness/src/claude.rs — Settings::into_hook_defs; crates/harness/src/hooks.rs — HookEvent::parse

settings.local.json

One filename in both flavours, sitting beside whichever spine loaded. It carries a permissions block and nothing else Emma reads, and it is where a grant you ask Emma to remember is written — beside the harness that actually loaded, so answering a prompt in a .emma/ project cannot conjure a .claude/ directory for a program that is not running.

crates/harness/src/lib.rs — LOCAL_SETTINGS_FILE, read_permissions, permissions_file

A malformed one fails the boot, which is a different ruling from a rule Emma cannot evaluate — that is only a note. An unevaluatable rule is a file written correctly for a program with a larger vocabulary; unparseable JSON is a file that says nothing at all, and booting past it would mean running with a deny list the operator believes is in force.

Permission rules live here and are explained elsewhere

The harness reads the rule strings and does not understand them. Each one comes out tagged with the list it was in and the file it was written in, because the two sentences an operator needs when a rule does not fire are "which file" and "which list". What the strings mean, which specifiers this build can evaluate, and how deny beats allow at match time are all Consent & permissions.

crates/harness/src/lib.rs — the Permission rules region; crates/emma/src/permissions.rs

Two facts about reading them belong here, though. Permission lists merge across scopes rather than override — nearest-wins is not how these compose — and the merge is safe because deny beats allow at match time, so a restrictive rule in any file survives a permissive rule in any other. And from the user scope, only deny crosses.

Why user-scope allow is dropped

It is the one judgement call in the feature and it diverges from Claude Code, where all three lists apply in every project. A grant made in ~/.claude/settings.json was made for another program, in a session Emma was not part of, possibly years ago. The source comment names the live consequence: the owner's file carried Bash(rm:*), Bash(bash:*) and Bash(powershell.exe:*) in allow. Honouring those would have handed Emma an unprompted shell in every repository on the machine, granted by nobody, on the first run after the feature shipped.

deny only ever removes a capability, cannot be the mechanism of a surprise, and a host somebody blocked globally is a host they meant. ask is left out with allow: not restrictive enough to be worth importing, not permissive enough to be dangerous.

certified — that file today holds 64 allow rules, "defaultMode": "auto", and no deny list at all. Emma's config check in this repository accordingly prints permissions (none). Sixty-four standing grants for another program, contributing nothing.

crates/harness/src/lib.rs — user_permissions; crates/emma/src/main.rs, the two-scope merge

Skills, commands and agents

All three are directories under the harness root, and all three use the same layout in .emma/ and .claude/ — which is the whole point of reading the second directory name at all. A skill or command already written for Claude Code works unchanged.

Skills — skills/<name>/SKILL.md

Markdown with YAML frontmatter. Emma reads two fields, name and description, and the body after the frontmatter is the skill. The catalogue is keyed and sorted by the frontmatter name, never by directory iteration order, because the catalogue rides in the prompt prefix that the provider caches as an exact byte match. A persona's skills array is therefore a set, not an ordering.

crates/harness/src/lib.rs — load_skills, split_skill, Harness::skills

What a skill can do is add text to one turn. It is loaded by a tool call, so its body reaches the model only when the model asks for it by name from a closed enum — a tool that took a model-supplied path would be an arbitrary-file-read tool with a friendly description. Nothing the runtime branches on may live in a skill; that belongs in the spine.

Strictness splits by flavour, and this is the same ruling as settings.json one level down. Under .emma/ the frontmatter is strict and both fields are required, so a bad file fails the boot. Under .claude/ unknown keys are ignored and a file that cannot be read at all is skipped with a warning on stderr — real skills carry model-role, version and allowed-tools, and under the strict struct every one of them took the whole boot down. Two further tolerances exist for .claude/ only: an HTML comment (a licence header) above the frontmatter is stepped over, and comments and blank lines are the only things that may precede it. Not covered: a ---\r\n opener or a byte-order mark on a skill file — both are skipped-with-a-warning rather than fatal, which is the property that mattered.

crates/harness/src/lib.rs — Front, ClaudeFront, after_licence_header

A harness with no skills does not register the Skill tool at all. Offering a capability that cannot work is a trap with a description attached. certified — the tools line from config check in this repository (no skills) has no Skill; the same line in a scratch harness carrying one SKILL.md reads … DocumentSymbols, Skill, WebFetch, ….

crates/harness/src/lib.rs — Harness::skill_catalog, and its None case

Commands — commands/<name>.md

Top-level *.md only; the file stem is the name. Typing /name rest of the line substitutes the file's body, with the tail appended after a blank line when there is one. The body is trimmed at both ends, which is the second of the two places the "nothing is trimmed" prompt rule is bent, and it is bent because a command body is not always-on prompt text — it is text a person typed a /name to summon.

crates/harness/src/lib.rs — load_commands, expand_command

Expansion happens at intake and the model never learns commands exist. An unknown /word is not an error: it passes through as ordinary text.

Agents — agents/<name>.md

One file format doing two jobs with opposite selection rules. As a persona it is chosen by a human at startup through EMMA_PERSONA; as a delegation target it is chosen by the model at call time from a closed list. They have separate accessors and no function takes a boolean saying which it is. The delegation half is Delegation; what belongs here is how the files are found.

  • Top-level *.md only, and the file stem is the name. A name: in frontmatter that disagrees loses and produces a note — the stem is what EMMA_PERSONA names and the only one of the two guaranteed unique. Subdirectories are not walked: a real library had 23 of them holding 205 files, and flattening two namespaces would resolve a collision by directory iteration order.
  • Nothing here fails the boot. An agent library is a directory somebody accumulated over months; refusing to start because one file in ninety has no description is the outage this crate keeps ruling against. Dropped files are named instead, in config check and at startup.
  • A persona directory nobody selected is fatal in .emma/ and fine in .claude/. There personas are the prompt, so unselected persona content means Emma would have started without a prompt somebody wrote. In .claude/ the prompt is CLAUDE.md and agents/ is optional — a normal repository has a dozen and selects none.
  • tools: [] means inherit, not nothing. That is the trap in the format: under Emma's rules an empty allowlist would mean no tools at all, and nobody writes tools: [] meaning "this agent may do nothing". A YAML list and a comma-separated string are both accepted, because both are common and silently ignoring one would produce exactly that empty list.
crates/harness/src/claude.rs — agents, load_agents, Tools::allowlist, split_agent; crates/harness/src/lib.rs — select_persona

Line endings on an agent file are tolerated, and that is a scar rather than tidiness. The parser required ---\n exactly, so every CRLF agent file — every one of them on a Windows machine, and 90 out of 90 in the library it was measured against — fell through to "no frontmatter": its tools was ignored, its description was invisible, and its name:, model: and category: lines were handed to the model as standing instructions. Nothing failed; the file simply did not mean what it said. A byte-order mark is stepped over for the same reason, and unreadable YAML now produces a note where it used to produce the same empty value as a file with no frontmatter at all.

The personal file — ~/.emma/settings.json

Never in the working tree, for the same reason the key is not: Emma runs inside repositories, and anything it writes beside the code is something the next git add . publishes. A model id is not a secret, but a file Emma creates in someone's repository without being asked is a surprise either way.

The tools block

Four optional strings, all read by usertools — the sidebar keys a person presses, not anything the model can reach.

keywhat it points atabsent means
shell The shell the Shell tool opens. Windows honours it directly. Probe the machine. On mac/linux the terminal application is opened and lets the user's shell be picked, because Emma holds this terminal and has nowhere to put a child that wants one.
editor The editor the Code and Settings tools open. $VISUAL, then $EDITOR, then a probe of code, cursor, subl, zed (and nvim on Windows only, where a new console can hold it).

crates/emma/src/settings.rs — ToolSettings; crates/emma/src/usertools.rs — resolve_value, resolve_editor

Every value is one program name or one absolute path, and never a command line. A bare name is looked up on PATH; an absolute path is checked for existence. Splitting a string on spaces is the first half of running text through a shell, and a path with a space in it is not an argument boundary — so a value carrying arguments is not split, it fails, and the failure names the rule: 

tools.editor is set to code --wait, which is not on PATH
  (a configured value is one program name or absolute path, never a command line)
crates/emma/src/usertools.rs — resolve_value, the whitespace arm

That message exists because the generic one — "which is not on PATH" — sends somebody to check their PATH for a program that was never the problem. A value that does not resolve is an error naming it and is never quietly swapped for a probed default: a silent substitution looks identical to success right up until the wrong program opens. unverified — the two messages are read off the source and the resolution layer is pure and testable, but nothing on this page ran the sidebar. Settle it by setting tools.editor to code --wait and pressing c in the frame.

$VISUAL and $EDITOR get the one concession, and it is a concession to the world rather than to the rule: those variables really do hold command lines, so a value there that does not resolve as a whole is skipped and the chain continues to the probe. Skipped, not split.

Two smaller behaviours worth knowing. A .cmd or .bat target is refused with a sentence saying to point the setting at the underlying .exe — a script cannot own a console window. And settings.json is re-read on every call rather than cached, so the Settings tool's own writes appear on the next frame; PATH lookups are cached for the life of the process, so a program installed mid-session appears after a restart.

crates/emma/src/usertools.rs (module doc, "Probing must not lie")

Credentials

Two sources, in order: the provider's environment variable, then ~/.emma/credentials.json. Never the project directory. Nothing in auth.rs resolves a path relative to the working directory — the home path is computed, not searched upward. A key written next to the code is a key that gets committed, and the first person to notice is usually the scanner that finds it in a public push. tested — a_credentials_file_in_the_project_directory_is_ignored plants a real credentials.json in a scratch cwd, runs both providers, and asserts the error names a path under the fake home.

crates/llm/src/auth.rs — resolve, credentials_path

The environment wins because that is how CI and one-off overrides work. The variable it wins with is the provider's — that is why resolution takes a ProviderKind rather than a name, so there is no way to check the wrong variable. An exported-but-empty variable is not a key: a forgotten ANTHROPIC_API_KEY= falls through to the stored file rather than authenticating with "" and earning a 401 nobody can explain.

The shape on disk, and the older one

{"providers": {"anthropic": {"api_key": …}}}. It used to hold exactly one key under a top-level api_key, and that spelling is still read, for as long as anybody has a file written by the old emma api — one machine, no expiry date. Reading migrates; nothing rewrites the file for having been read. The keyed shape wins over the legacy field for the same provider, and the first write carries the legacy value into providers and drops the flat key, so there is never a file with two answers for Anthropic.

crates/llm/src/auth.rs — read_keys, store
The scar: a write that deleted a key it never knew about

This file holds more than one program's secrets. The web tools keep brave_search_api_key at its top level, beside the provider entries. A write that serialised a fresh document — the obvious implementation — deleted whichever keys the caller did not happen to know about, silently, and the symptom arrived hours later as a tool that had stopped being registered.

What it does now: store reads the file, replaces one provider's entry, and writes back everything else it found. And a file that cannot be parsed is an error rather than something to overwrite — for exactly the same reason, since overwriting is how the other keys are lost.

tested — a_key_written_by_the_old_emma_api_still_reads plants the owner's live file (a flat api_key and a Brave key beside it), stores a key for a different provider, and asserts brave_search_api_key survived, with the failure message "a key this module does not own was destroyed by a write". malformed_credentials_name_the_file_rather_than_being_overwritten writes not json, asserts the store call fails, and asserts the file's bytes are unchanged afterwards.

Two more properties. Every key in the file is built through ApiKey::new at load — including the ones nobody asked for — because that constructor is what registers a secret for scrubbing, so a key belonging to a provider this run is not using still cannot appear in an error message. And an ApiKey has no Display and a Debug that prints ApiKey([redacted]), so it cannot reach a log through a {:?} on some struct three layers up. tested — a_key_never_prints_itself and a_key_belonging_to_another_provider_is_still_scrubbed.

On Windows the file is not owner-only, and the code says so rather than implying otherwise. On unix it is created 0600 in the open call rather than chmodded afterwards (between those two calls the key is world-readable on disk), and a file whose mode has loosened is refused at read rather than warned about. Windows has no mode bits: the file lands in the user's profile, whose default ACL already excludes other users, and tightening it further would mean an ACL API this crate has no other reason to link. The Windows test asserts what can be asserted — that the round trip works and that the absent check does not fail closed — and its doc explains that the thinness is the point.

crates/llm/src/auth.rs — write_private, check_permissions, and their cfg(not(unix)) arms

emma config check prints api key found (stored file) or the environment, by name and never by value — it answers "did I store that key?" without being a way to read one back.

Themes

A theme is a JSON file of colours. Two directories are searched, in this order: ~/.emma/themes/<name>.json, then <harness root>/themes/<name>.json. Themes ride the discovery that already happened, so in a .claude/ project the project's themes live in .claude/themes/.

crates/emma/src/term/theme.rs — load; crates/emma/src/session_command.rs — theme_dirs

Yours beats the project's on a name collision, which follows the same argument as skipping ~/.claude/: a project cannot select a theme, so shadowing a name you already chose is the only way a repository could repaint your screen. The reverse is not a risk, it is the preference working. The name emma is reserved so a cloned repository cannot silently change what stock Emma looks like by shipping a themes/emma.json; a file of that name gets a notice saying to copy it to another name.

Selection lives only in ~/.emma/settings.json under theme, and the project's config.json has no counterpart — the same ruling as the model, applied a second time. Theme files may live in either place; the choice is personal.

/theme lists what is available and which is selected; /theme <name> selects one. It takes effect at the next start. There is no --save, and that is not an omission: a theme is read once at startup, so selecting one is writing it down. A live swap would have to reach every drawn surface at once while the retained transcript still holds rows already styled under the old colours, so the realistic outcome of repainting is a half-recoloured screen. The name is checked before the write, so a selection known to be broken is never written; the write itself is a load-mutate-save round trip through the same shared settings document, for the reason the credentials scar above gives.

crates/emma/src/session_command.rs — the /theme region, theme, write_theme
A broken theme costs colour and never the boot

load returns notices and no error, and the granularity is per-field. A hex that is not a hex loses that role and leaves the other seven applied — a theme thrown away over one character is a theme its author cannot debug. A file that is not JSON loses the theme and keeps the boot, quoting serde's own line and column. A key that is not a theme key is noted and ignored, because a build that adds a key should not make the file unreadable to the build beside it. At most five notices are printed; past that the count and the path are what you need, because the file is where you are going to go and look.

Two things a theme may not do, and both concern a screen nobody here can see. It may not set roles.text: a foreground chosen against one background is invisible on the opposite one, and the person it breaks for reads it as Emma being broken. And it may not set a bare background — backgrounds are declared as pairs (chip, selection), fg and bg together, because a pair is legible whatever is behind it and a lone background is a colour against an unknown one.

crates/emma/src/term/theme.rs — apply, apply_roles, role_entry, MAX_NOTICES

The colour model itself — the roles, the three fidelities, what NO_COLOR does, and why the 16-colour name is inherited rather than derived — is The terminal. One consequence belongs here: under NO_COLOR, /theme writes the preference and says plainly that the screen will not change, rather than refusing. The person may well be setting up for a terminal they will use later.

Why did my setting not apply

In the order worth checking, because each step rules out the ones below it.

1 · A different directory was loaded than the one you edited

This is the common one, and it has three causes: .emma/ beat a .claude/ sitting beside it, a nearer ancestor had a harness you forgot about, or EMMA_ROOT is exported in that shell. Run emma config check and read the first three lines — cwd, harness, flavor. If harness is not the directory you edited, nothing below matters.

2 · The key is real, but it belongs in a different file

The four confusions, all of which look like a setting being ignored:

if you wrote…in…it belongs in…
theme, provider, model, tools .emma/config.json ~/.emma/settings.json — and the spine would have refused to start over it, so if Emma booted, that is not what happened
permissions.allow ~/.claude/settings.json the project's spine or settings.local.json. User scope contributes deny only, silently
a hook for SessionStart, Stop, PreCompact either spine nowhere — Emma has three events, and this is a startup error rather than a skip, so again: if Emma booted, this is not it
a skill or agent in a subdirectory agents/<sub>/x.md top level. agents/ reads *.md at the top only; skills/ wants <name>/SKILL.md exactly

3 · The key was swallowed rather than refused

Two files ignore keys they do not know: .claude/settings.json at its outer level, and ~/.emma/settings.json entirely. In both, a misspelling is silence. .emma/config.json is the opposite and would have named the key and the whole valid vocabulary. So: if you edited a permissive file, compare your key against the tables above by eye — there is no spelling check available, and that is the price of one format belonging to another program and the other being a preference store that must not refuse to start.

The lower-level version of the same thing: a value can be swallowed by shape. tools: [] in an agent file means inherit, not nothing. A theme role spelled wrongly is a notice, not a failure. A skill under .claude/ whose frontmatter will not parse is skipped with a line on stderr that scrolls past on a busy start — emma config check is where to see the surviving list.

4 · It applied, and it does not take effect until the next start

/theme is the one that surprises people, and the command says so itself. Everything the harness reads is resolved once at startup into a value the loop consumes; nothing re-reads a configuration file mid-run. The exception runs the other way: ~/.emma/settings.json is re-read on every usertools call, so an editor changed through the Settings tool is live on the next frame.

5 · It loaded, and was rejected at use

A rule Emma cannot evaluate is the clearest case: it is in the file, it is listed by config check, and it approves nothing. That is a note rather than a refusal, because a file written correctly for a program with a larger vocabulary is not a broken file — see the Bash(ls:*) line in the certified output above. A configured editor that is not on PATH, an agent with no description, and a status-line program outside hooks/ are the same shape: loaded, named, and doing nothing. config check prints all of them.

Two failures that are not configuration at all

Approval. If Emma keeps asking about something you granted, the rule may be right and simply not matching — that is Consent & permissions, not this page. And the gate is a consent interface, not a sandbox: it enforces nothing a tool does not honestly declare.

An unknown /word. It is not an error and not a missing command. Anything that is not a known command file passes through to the model as ordinary text, which is indistinguishable from a command that "did nothing" if you were expecting an expansion.
