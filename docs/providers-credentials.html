Where the key comes from, and where it must never appear

Providers & models The boundary Content blocks The turn back Model limits Caching The cache floor Retry Credentials

Two sources, in order, and one place that is never consulted. Emma works inside repositories, so a key written next to the code is a key that gets committed, and the first person to notice is usually the scanner that finds it in a public push. The rest of this page is about a write that deleted a key it did not know about, and the redaction that moved after an audit found two paths it had never covered.

Environment, then the stored file, never the project

crates/llm/src/auth.rs · resolve, from_env

/// Resolve one provider's key: environment first, then the stored file.
///
/// Takes the environment value rather than reading it, so the decision is a
/// pure function of its inputs — a test can pin either source without mutating
/// process state that every other test shares.
///
/// The environment wins because that is how CI and one-off overrides work, and
/// because a user who exports a key expects it to be the one used. The variable
/// it wins with is the *provider's*, which is the whole reason this takes a
/// [`ProviderKind`] rather than a name: there is no way to ask for a provider
/// this build cannot run, and no way to check the wrong variable for it.
pub fn resolve(
    kind: &dyn ProviderKind,
    env_key: Option<&str>,
    home: &Path,
) -> Result<ApiKey, AuthError> {
    match from_env(env_key) {
        Some(key) => Ok(key),
        None => load_file(&credentials_path(home), kind),
    }
}

/// An exported-but-empty variable is not a key: `ANTHROPIC_API_KEY=` in a
/// forgotten `.env` must fall through to the stored file rather than
/// authenticate with `""` and get a 401 the user cannot explain.
fn from_env(env_key: Option<&str>) -> Option<ApiKey> {
    env_key
        .map(str::trim)
        .filter(|k| !k.is_empty())
        .map(ApiKey::new)
}

credentials_path is a function rather than a constant because every caller must pass the home it means, tests included, which is the only reason they can run without touching the developer's real credentials. home_dir reads HOME, falls back to USERPROFILE, and filters out an empty value, so an exported but blank home is the same as none.

the_environment_beats_the_stored_file pins all three rules in one test: an exported key wins over the file, a whitespace-only variable falls through to the file, and one provider's variable does not answer for another. a_credentials_file_in_the_project_directory_is_ignored runs for both a real and a fixture provider, because the keyed file shape added a second lookup path and only one of them had been pinned. tested

crates/llm/src/auth.rs · read_keys

/// Every key the file holds, by provider, in whichever shape it is written.
///
/// **All of them are built through [`ApiKey::new`], including the ones nobody
/// asked for.** That constructor is what registers a secret for scrubbing, so a
/// key belonging to a provider this run is not using still cannot appear in an
/// error message. Loading them and dropping them would be the same read with
/// the protection left off.
fn read_keys(path: &Path) -> Result<BTreeMap<String, ApiKey>, AuthError> {
    let mut keys = BTreeMap::new();
    let Some(doc) = read_json(path)? else {
        return Ok(keys);
    };
    let mut take = |provider: &str, value: Option<&Value>| {
        if let Some(raw) = value.and_then(Value::as_str) {
            if !raw.trim().is_empty() {
                keys.insert(provider.to_string(), ApiKey::new(raw));
            }
        }
    };
    // The shape `emma api` wrote. Read forever; see the module doc.
    take(LEGACY_PROVIDER, doc.get(LEGACY_FIELD));
    if let Some(providers) = doc.get("providers").and_then(Value::as_object) {
        for (provider, entry) in providers {
            // The keyed shape wins over the legacy field for the same provider:
            // it is the one a later `store` wrote.
            take(provider, entry.get(LEGACY_FIELD));
        }
    }
    Ok(keys)
}
crates/llm/src/auth.rs — read_keys, LEGACY_PROVIDER, LEGACY_FIELD

The legacy shape held exactly one key under a flat top-level api_key, and it can only ever have meant Anthropic, since nothing else was implemented when it was written. It is read for as long as anybody has a file the old emma api wrote, which is one machine and no expiry date. The insertion order in read_keys is what makes the keyed shape win: the legacy field is taken first and a keyed entry for the same provider overwrites it. Reading is what migrates; nothing rewrites the file for having been read.

read_json returns Ok(None) for a file that does not exist, because "no credentials yet" is the ordinary state of a new install and only the caller knows whether that is a failure. Anything else that fails to read is Unreadable, and anything that is not valid JSON is Malformed, both naming the path. The permission check runs between reading the bytes and parsing them. stored_providers is the names-only view, so config check can answer "did I store that key?" without being a way to read one back.

The scar: a write that deleted a key it did not know about

store used to write a fresh document. The Brave Search key lives in that same file, at the top level, put there by an unrelated part of the program, so every emma api call silently deleted it. Nothing errored. The symptom arrived later as a tool that had stopped being registered, with no connection to the command that caused it.

observed: checked once against the owner's real ~/.emma/ around the da0352a fix on 2026-08-11, backed up and restored by hand, with the Brave key intact afterwards. No transcript of that check survives, which is why this is amber. The same shape is covered on demand by a_key_written_by_the_old_emma_api_still_reads, which writes a fixture file carrying both keys and asserts the Brave key survives a write. tested

crates/llm/src/auth.rs — store

store reads, replaces one provider's entry, and writes back everything else. It refuses a credentials file it cannot parse rather than overwriting it, for the same reason: overwriting is exactly how the other keys got lost. malformed_credentials_name_the_file_rather_than_being_overwritten writes the two words not json, asserts the read fails naming the file, asserts the write fails, and then asserts the file still contains not json. tested

#[cfg(unix)]
fn write_private(path: &Path, body: &str) -> std::io::Result<()> {
    use std::io::Write;
    use std::os::unix::fs::OpenOptionsExt;
    // Created 0600 rather than created-then-chmodded: between those two calls
    // the key would be world-readable on disk.
    let mut f = std::fs::OpenOptions::new()
        .write(true)
        .create(true)
        .truncate(true)
        .mode(0o600)
        .open(path)?;
    f.write_all(body.as_bytes())
}

A key that cannot print itself

crates/llm/src/auth.rs · ApiKey

/// No `Display`, and a `Debug` that shows nothing — so a key cannot reach a
/// log through a `{:?}` on some struct three layers up that happens to hold
/// one. Reading it takes [`ApiKey::expose`], which is a word you notice in
/// review.
#[derive(Clone, PartialEq, Eq)]
pub struct ApiKey(String);

impl ApiKey {
    pub fn new(key: impl Into<String>) -> Self {
        let key = key.into();
        // The one place every key in this process is built, which is what makes
        // it the place to register it for scrubbing. `LlmError`'s formatting
        // consults that list, so a message assembled somewhere the key was
        // never passed — a mid-stream `error` frame, an error-shaped batch body
        // — still cannot print it. See the note on `LlmError`'s impls.
        crate::remember_secret(&key);
        Self(key)
    }

    pub fn expose(&self) -> &str {
        &self.0
    }
}

impl fmt::Debug for ApiKey {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str("ApiKey([redacted])")
    }
}
crates/llm/src/auth.rs — ApiKey

a_key_never_prints_itself checks both directions: the key formatted alone, and the key inside a struct somebody else derived Debug on. tested expose has three callers in the crate: the auth header in execute, the scrub in AnthropicProvider::scrub, and the value written by store.

Redaction as a property of the type

The scrubbing lives in LlmError's Display and Debug impls rather than at each site that builds a variant. It moved there after an audit, and the comment above the impls says what the audit found:

crates/llm/src/lib.rs · the comment above impl Display for LlmError

// The reason is that construction sites are where the guarantee kept failing.
// `AnthropicProvider` holds the key and scrubbed what it built; `Assembly::apply`
// and `turn_from_message` are free functions the key was never handed to, so
// they built `Api` variants out of raw provider prose — and the class-level
// promise on `LlmError` read as held while two paths did not hold it, until an
// audit went looking.
// Threading the key into those two functions would fix those two, and the third
// one somebody adds next year would leak again, silently, exactly as these did.
// Formatting is the one thing every variant from every site must pass through
// to reach a terminal or a log, so putting the scrub here makes the property
// structural rather than a habit each new call site has to remember.
crates/llm/src/lib.rs — impl Display for LlmError, impl Debug for LlmError

Debug is hand-written for the same reason: unwrap_err() in a test and {:?} in a log both print it, and a derived Debug would print the fields raw. It prints the variant name plus the redacted sentence, which is what a reader of {:?} wants. sentence is private and its only callers are those two impls, so a raw message cannot escape by another route; variant supplies the name.

Four things the arrangement does not cover, all named in the code. Reading a field directly: err.message is pub and still carries the provider's bytes verbatim on the two audited paths, which is why classify also scrubs at construction, where a key is in scope. A key this process never wrapped in ApiKey. An echo that is not byte-identical, because a gateway that base64s, truncates or re-cases the key defeats a substring replace. And forgetting: the list is process-wide and append-only, which suits a CLI holding one key for its lifetime and is state a long-lived host would have to think about.

Three tests hold the guarantee from three different construction sites. a_formatted_error_never_contains_the_key goes through classify, where the key is in scope. a_mid_stream_error_frame_never_contains_the_key goes through Assembly::apply, where it is not. an_error_shaped_batch_body_never_contains_the_key goes through turn_from_message on an HTTP 200, which never reaches classify at all. A fourth, no_variant_can_print_a_key_whoever_built_it, builds a variant in the test itself with no provider involved. tested

The poisoned lock

crates/llm/src/lib.rs · secrets, remember_secret, scrub_secrets, redact

/// Poison means some thread panicked while holding the guard. It says nothing
/// about the data — and a `Vec<String>` cannot be left in a state that is
/// unsafe to read. …
///
/// The alternative is what this code did first, and it was a bug: propagating
/// the poison meant one unrelated panic anywhere in the process turned
/// redaction off for every error printed for the rest of the run — a security
/// control degrading silently to no control, on a condition nobody observes.
/// If the data here ever grows an invariant that a panic *could* break, this
/// must fail closed — redact everything — rather than go back to passing the
/// text through.
fn secrets() -> &'static RwLock<Vec<String>> { … }

/// Short strings are ignored. A scrub list is a substring replace over every
/// error message the user ever sees, so an entry like `"x"` would corrupt them
/// all; a real key is far longer than this floor, and a "key" that is not is
/// not one worth protecting.
pub(crate) fn remember_secret(key: &str) {
    const MIN_LEN: usize = 8;
    if key.len() < MIN_LEN {
        return;
    }
    let mut list = secrets().write().unwrap_or_else(|e| e.into_inner());
    if !list.iter().any(|k| k == key) {
        list.push(key.to_string());
    }
}

Which provider, as a value

crates/llm/src/kind.rs · ProviderKind, KINDS, kind

/// Provider identity and capability, separable from a configured instance.
pub trait ProviderKind: Send + Sync {
    fn name(&self) -> &'static str;

    /// The environment variable that outranks the stored key for this provider.
    /// One name per provider, because `ANTHROPIC_API_KEY` cannot mean two
    /// things.
    fn env_var(&self) -> &'static str;

    fn default_model(&self) -> &'static str;

    fn build(&self, key: ApiKey, model: Option<String>) -> Arc<dyn Provider>;
}

/// Every provider this build can actually run. One entry, and the list is the
/// point: it is what an unknown name is measured against and what the error
/// message quotes, so a second provider becomes reachable by appending to it.
static KINDS: &[&'static dyn ProviderKind] = &[&Anthropic];

/// Look a provider up by name.
pub fn kind(name: &str) -> Result<&'static dyn ProviderKind, UnknownProvider> {
    KINDS
        .iter()
        .copied()
        // Case-insensitive because the name is typed by a human and `Anthropic`
        // is not a different provider. Nothing else is normalised: a typo is a
        // typo and gets the list.
        .find(|k| k.name().eq_ignore_ascii_case(name.trim()))
        .ok_or_else(|| UnknownProvider {
            name: name.to_string(),
        })
}
crates/llm/src/kind.rs — ProviderKind, kind, known

ProviderKind is separate from Provider because it answers questions that come before a key or a model exists: a name, an environment variable, a default model, and how to build one. emma set-provider has a name and nothing else. AnthropicProvider::new used to be called by name in main.rs, twice, which is fine with one provider and a problem with two, because the name would live in the binary's wiring where a setting cannot reach it.

An unknown name is an error, never a fallback. emma set-provider antropic quietly running on Anthropic would look exactly like a correctly-set one until the bill or the output said otherwise, and there is no way to notice in between. known() is what the error message quotes, so the list of what exists and the list that is matched against are the same list. a_misspelled_provider_is_refused_and_told_what_exists asserts the message contains both the typo and the real name, and that openai does not resolve. the_known_provider_resolves_however_it_is_capitalised covers three spellings including one with surrounding spaces. a_built_provider_carries_the_model_it_was_given covers build in both directions, with a model and without. tested

One detail belongs here rather than on the boundary: base_url is never read from the environment. An environment variable that redirects where the key is sent is a credential-exfiltration switch, and Emma runs inside repositories with whatever environment the shell carries.
