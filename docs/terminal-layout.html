app.rs owns what happens on the alternate screen once frame.rs has entered it. Everything here is pure over a Buffer, so a test can hold the layout still, and the file says why the split sits where it does: the terminal, the locks and the entry bytes stay in frame.rs, “which has already shipped two invisible-to-tests defects and does not need a third file's worth of chances.”

One function carves the window

regions(area, sidebar_w, dock_h) -> Regions is arithmetic over three numbers. The two inputs that depend on state, how wide the sidebar is and how tall the dock needs to be, are computed before the call, so the carve itself runs without a terminal and without a View.

This section quoted code that is not in the tree. It showed inset_x/inset_y insetting the window by a cell on each side against an INSET_MIN_ROWS threshold, and a gap_h/gap_w pair spending a row and a PANE_GAP_COLS of columns on a gutter between the panes. None of those five names exist in layout.rs — a whole-tree grep for any of them returns nothing — and the extraction section below already flagged the same fabrication once, for the constant and the test, without this block being caught alongside it. What follows is the function actually in the tree on 2026-09-06. certified: pasted from crates/emma/src/term/layout.rs, not retyped.

crates/emma/src/term/layout.rs · regions

pub fn regions(area: Rect, sidebar_w: u16, dock_h: u16) -> Regions {
    let status_h = if area.height < SLIM_STATUS_ROWS { 1 } else { 3 };
    let [content, status] =
        Layout::vertical([Constraint::Min(0), Constraint::Length(status_h)]).areas(area);
    let [sidebar, main] =
        Layout::horizontal([Constraint::Length(sidebar_w), Constraint::Min(0)]).areas(content);
    let main_bordered = area.width >= UNBORDERED_COLS && main.width >= 3 && main.height >= 3;
    let inner = if main_bordered {
        main.inner(Margin::new(1, 1))
    } else {
        main
    };
    let (header_h, rule_h) = if area.height < SLIM_HEADER_ROWS {
        (1, 0)
    } else {
        (2, 1)
    };
    let [header, rule, chat, dock, hint] = Layout::vertical([
        Constraint::Length(header_h),
        Constraint::Length(rule_h),
        Constraint::Min(1),
        Constraint::Length(dock_h),
        Constraint::Length(1),
    ])
    .areas(inner);
    Regions { sidebar, main, main_bordered, header, rule, chat, dock, hint, status }
}

How tall the dock is

crates/emma/src/term/layout.rs · dock_height

/// How many rows the dock needs: three for the input box, more while the menu
/// is up, and the approval panel's evidence when a question is pending. Capped
/// at half the pane — the prompt may grow upward into transcript rows (§4.6),
/// not through them.
///
/// **`width` is what makes the input box grow with what is typed**, and it was
/// dropped by the TUI import: the incoming `layout.rs` took `(view, room)`
/// only, so a message longer than one line was hidden behind a three-row box.
/// The wrapping is `super::view::dock_rows`' — the same function the box paints
/// with, so the height and the paint cannot disagree. `None` is "the caller
/// does not know the width yet" and answers with the old three-row floor.
pub fn dock_height(view: &View, room: u16, width: Option<u16>) -> u16 {
    let room = room.max(1);
    // The ceiling would like to be half the window and must never exceed the
    // window: on a degenerate frame half-of-room is below the floors, and a
    // clamp whose min exceeds its max is a panic, not a layout.
    let ceiling = (room / 2).max(5).min(room);
    let bounded = |want: u16, floor: u16| want.clamp(floor.min(ceiling), ceiling);
    match &view.prompt {
        Some(p) => bounded((p.preview.len() as u16).saturating_add(3), 5),
        None => match &view.menu {
            Some(m) => {
                let extra = (m.rows.len() as u16 + u16::from(m.note.is_some())).min(8);
                bounded(3 + extra, 3)
            }
            // The typed message decides, through the same function the box
            // paints with. Absent a width nothing can be wrapped, so the old
            // three rows are the floor and the answer when the caller does not
            // know yet.
            None => match width {
                Some(w) => bounded(super::view::dock_rows(view, w), 3),
                None => 3.min(ceiling),
            },
        },
    }
}
crates/emma/src/term/layout.rs — dock_height

unverified This block was quoted with a two-argument signature, (view, room). It is three now, (view, room, width): the third argument lets the box grow with a typed message that wraps past one line, through the same view::dock_rows the input box paints with, and answers with the old three-row floor when the caller does not know the width yet. The three cases below it are otherwise unchanged, and the clamp guard in the middle is there because a clamp whose minimum exceeds its maximum panics: on a degenerate frame half of room falls below the floors, so ceiling is itself capped at room and every floor is floor.min(ceiling). tested: the_dock_grows_for_the_menu_and_the_prompt_but_never_past_half_the_pane (in app.rs, calling dock_height(&v, 30, None)) pins 3, 7 and 15 at room = 30, and degenerate_windows_are_survived renders at 0×0, 1×1, 5×3, 24×8 and 200×2. Neither test covers the Some(w) arm.

Defect: the dock is measured against the window, not the pane

App::render calls regions(area, sb_w, dock_height(view, area.height)). area.height is the window height; dock_height's doc says the cap is half the pane, and half the window exceeds half the pane once the header, the rule, the hint, the status bar and the vertical float are subtracted. At 30 rows and a 40-line preview, dock_height returns 15 while the inner pane has about 22 rows to give, so the chat pane is squeezed to what is left. Layout::vertical clamps rather than panicking, so the symptom is a chat area driven toward zero rather than a crash. certified: read at the call site in App::render, one line, and the only caller.

The sidebar latch

crates/emma/src/term/app.rs · Latch, hidden

/// Whether the sidebar is collapsed, and whether that was a person's decision.
#[derive(Debug, Clone, Copy, Default)]
pub struct Latch {
    pub collapsed: bool,
    pub by_user: bool,
}

/// Is the sidebar hidden at this width?
///
/// The user's latch wins outright; below it, the width decides. An automatic
/// collapse un-collapses when the window widens past the threshold again — it
/// was never a choice — which falls out of `by_user` being false rather than
/// being a rule of its own.
pub fn hidden(total_cols: u16, latch: Latch) -> bool {
    if latch.by_user {
        latch.collapsed
    } else {
        total_cols < sidebar::AUTO_COLLAPSE_COLS
    }
}
crates/emma/src/term/app.rs — Latch, hidden; crates/emma/src/term/sidebar.rs — AUTO_COLLAPSE_COLS

Two bits: one for the posture, one for whose posture it is. The same shape as frame.rs's pinned latch, and for the same reason: distinguish where the system put it from where the user put it. toggle_sidebar always sets by_user: true, so a keypress or a click wins in both directions and keeps winning when the window is resized.

Defect: one assertion in the latch test cannot fail

the_sidebar_latch_honours_the_user_over_the_width builds a binding named user_open with collapsed: false, by_user: false and then asserts hidden(80, user_open). With by_user false, hidden ignores collapsed entirely and answers from the width, so that line re-tests the automatic branch already asserted three lines above rather than the user-opinion branch its name claims. The guarantee is covered later in the same test through App::toggle_sidebar, and again in a_user_expand_below_the_threshold_survives_the_automatic_rule, so nothing is uncovered; the misleading binding is. certified: read the three lines and the body of hidden above.

The click, and the row it aims at

The collapse defect this fixes was reported as “+ and - does not seem to work”: the owner aimed at the affordance with the mouse and nothing routed a click anywhere.

crates/emma/src/term/app.rs · App::click

    pub fn click(&mut self, x: u16, y: u16, total_cols: u16) -> bool {
        let r = self.side_rect;
        // Under three cells either way the sidebar drew nothing (its own
        // rule), so there is no affordance on screen to have been aimed at.
        if r.width < 3 || r.height < 3 {
            return false;
        }
        let header_row = r.y + 1;
        if y == header_row && x > r.x && x < r.right().saturating_sub(1) {
            self.toggle_sidebar(total_cols);
            return true;
        }
        false
    }
crates/emma/src/term/app.rs — App::click, side_rect

side_rect is written down during render, because a mouse aims at what was on screen at the last paint and only the layout knows which cells were the sidebar's. The whole header row is the target rather than the [+]'s three cells, and the doc gives the reason: “the affordance's exact columns are the sidebar's internal layout, which this file does not own, and a three-cell target at a guessed offset is a miss magnet.” A collapsed sidebar has no cells and therefore no click target; the way back is Ctrl-B, which the hint row names. tested: a_click_on_the_sessions_header_toggles_the_sidebar_and_latches also widens the window afterwards to prove the automatic rule does not reopen what the user closed, and a_click_anywhere_but_the_header_row_toggles_nothing tries four near misses.

Defect: header_row = r.y + 1 assumes an ordering the sidebar does not promise

The hit-test hard-codes the SESSIONS header as the sidebar's first inner row. Nothing in sidebar.rs pins that: content() happens to push the SESSIONS header first, and the click test happens to pass, but the two files agree by coincidence rather than by contract. Adding a row above the first header, or reordering the sections, moves the affordance and leaves the click on whatever is now on row one. unverified as a live symptom, since the ordering has not changed. A constant exported from sidebar.rs naming the header's row offset, consulted here, would settle it.

What App::render does, in order

Nine steps; two are seams. It refuses a zero-sized area; asks hidden and sidebar::width; carves; writes down side_rect; draws the sidebar; draws the main pane's border, header and rule; sets wrap_width and chat_height and re-wraps the transcript; draws the chat pane; draws the dock through View's own renderers; draws the hint; and finally draws the status bar, or the configured status program's row in its place.

The first seam is the wrap width. Retained transcript entries are wrapped by this file and painted by chat.rs at a gutter offset, so both numbers are derived from one function of the pane's own rectangle: 

        self.wrap_width = chat::message_width(r.chat.width.max(1));
        self.chat_height = r.chat.height.max(1);
        self.transcript.set_width(skin, self.wrap_width);
        chat::render(r.chat, buf, &self.transcript, skin);

The test that guards it says what would happen otherwise: “if the two widths are derived separately, every wrapped row is clipped by the gutter's width and no test in either file notices.” tested: the_wrap_width_is_the_chat_panes_message_width_exactly, which also asserts the two differ at 120 columns so the equality is not a tautology.

The second is the dock. It is not a widget of its own: it is a rectangle that View's existing renderers paint into, the same render_input and render_prompt the inline viewport uses, marked pub(crate) with the argument attached: “a consent interface with two renderings is two interfaces.” When a question is pending the approval panel replaces the input box in that rectangle. tested: a_pending_question_replaces_the_input_box_and_stays_on_screen pushes 200 blocks of output first, then asserts the title, the evidence and the keys are all on screen and the input box is not.

Where the arithmetic lives now

The carve, the latch and the dock height are no longer declared in app.rs. They sit in crates/emma/src/term/layout.rs, 442 lines, and app.rs imports them: line 77 of that file reads dock_height, hidden, regions, Latch, Regions, SLIM_HEADER_ROWS, SLIM_STATUS_ROWS from the module. So the functions this page quotes are the same functions, in a different file, and a reader grepping app.rs for fn regions will find nothing. certified: grep -n "^pub fn " crates/emma/src/term/layout.rs lists hidden, regions, dock_height, compose and bar_for; the same grep over app.rs finds none of them.

crates/emma/src/term/layout.rs — regions, hidden, dock_height, Latch, Regions

The extraction has a reason the module doc states. The full-screen frame is a sidebar, a main region and a bottom status bar, and which screen occupies the main region varies while the chrome around it does not. compose is the one seam that paints the chrome and hands the main region to whichever screen is up. It exists because the settings screen had already grown its own copy of the status-bar rendering and had quietly stopped honouring a configured status program, which is the drift the seam ends. bar_for chooses the status bar's contents from the View, so the choice happens once rather than per screen. unverified Whether every screen now goes through compose rests on reading the call sites, not on a test that fails when one does not. A test that renders each Mode and asserts the status row is present would settle it, and that test is not in the file.

crates/emma/src/term/layout.rs — module doc, compose, bar_for

Three constants in layout.rs encode the small-window thresholds: SLIM_STATUS_ROWS at 14 rows, below which the status bar loses its border and becomes one row rather than three; SLIM_HEADER_ROWS at 12 rows, below which the header is one line and the rule disappears; and UNBORDERED_COLS at 60 columns, below which the main pane loses its border. certified: the three pub const items are declared with those values.
