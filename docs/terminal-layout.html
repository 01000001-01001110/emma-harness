One function carves the window

regions(area, sidebar_w, dock_h) -> Regions is arithmetic over three numbers. The two inputs that depend on state, how wide the sidebar is and how tall the dock needs to be, are computed before the call, so the carve itself runs without a terminal and without a View.

It showed inset_x/inset_y insetting the window by a cell on each side against an INSET_MIN_ROWS threshold, and a gap_h/gap_w pair spending a row and a PANE_GAP_COLS of columns on a gutter between the panes. crates/emma/src/term/layout.rs · regions

/// Carve the window. `sidebar_w` comes from [`sidebar::width`] and `dock_h`
/// from [`dock_height`], so the two decisions that depend on *state* are made
/// before the arithmetic that does not.
pub fn regions(area: Rect, sidebar_w: u16, dock_h: u16) -> Regions {
    let status_h = if area.height < SLIM_STATUS_ROWS { 1 } else { 3 };
    let [content, status] =
        Layout::vertical([Constraint::Min(0), Constraint::Length(status_h)]).areas(area);
    let [sidebar, main] =
        Layout::horizontal([Constraint::Length(sidebar_w), Constraint::Min(0)]).areas(content);
    let main_bordered = area.width >= UNBORDERED_COLS && main.width >= 3 && main.height >= 3;
    let inner = if main_bordered {
        main.inner(Margin::new(1, 1))
    } else {
        main
    };
    let (header_h, rule_h) = if area.height < SLIM_HEADER_ROWS {
        (1, 0)
    } else {
        (2, 1)
    };
    let [header, rule, chat, dock, hint] = Layout::vertical([
        Constraint::Length(header_h),
        Constraint::Length(rule_h),
        Constraint::Min(1),
        Constraint::Length(dock_h),
        Constraint::Length(1),
    ])
    .areas(inner);
    Regions {
        sidebar,
        main,
        main_bordered,
        header,
        rule,
        chat,
        dock,
        hint,
        status,
    }
}

How tall the dock is

crates/emma/src/term/layout.rs · dock_height

/// How many rows the dock needs: three for the input box, more while the menu
/// is up, and the approval panel's evidence when a question is pending. Capped
/// at half the pane — the prompt may grow upward into transcript rows (§4.6),
/// not through them.
///
/// **`width` is what makes the input box grow with what is typed**, and it was
/// dropped by the TUI import: the incoming `layout.rs` took `(view, room)`
/// only, so a message longer than one line was hidden behind a three-row box.
/// The wrapping is `super::view::dock_rows`' — the same function the box paints
/// with, so the height and the paint cannot disagree. `None` is "the caller
/// does not know the width yet" and answers with the old three-row floor.
pub fn dock_height(view: &View, room: u16, width: Option<u16>) -> u16 {
    let room = room.max(1);
    // The ceiling would like to be half the window and must never exceed the
    // window: on a degenerate frame half-of-room is below the floors, and a
    // clamp whose min exceeds its max is a panic, not a layout.
    let ceiling = (room / 2).max(5).min(room);
    let bounded = |want: u16, floor: u16| want.clamp(floor.min(ceiling), ceiling);
    match &view.prompt {
        Some(p) => bounded((p.preview.len() as u16).saturating_add(3), 5),
        None => match &view.menu {
            Some(m) => {
                let extra = (m.rows.len() as u16 + u16::from(m.note.is_some())).min(8);
                bounded(3 + extra, 3)
            }
            // The typed message decides, through the same function the box
            // paints with. Absent a width nothing can be wrapped, so the old
            // three rows are the floor and the answer when the caller does not
            // know yet.
            None => match width {
                Some(w) => bounded(super::view::dock_rows(view, w), 3),
                None => 3.min(ceiling),
            },
        },
    }
}

Defect: the dock is measured against the window, not the pane

App::render calls regions(area, sb_w, dock_height(view, area.height)). area.height is the window height; dock_height's doc says the cap is half the pane, and half the window exceeds half the pane once the header, the rule, the hint, the status bar and the vertical float are subtracted. At 30 rows and a 40-line preview, dock_height returns 15 while the inner pane has about 22 rows to give, so the chat pane is squeezed to what is left. Layout::vertical clamps rather than panicking, so the symptom is a chat area driven toward zero rather than a crash. certified: read at the call site in App::render, one line, and the only caller.

The sidebar latch

crates/emma/src/term/app.rs · Latch, hidden

/// Whether the sidebar is collapsed, and whether that was a person's decision.
#[derive(Debug, Clone, Copy, Default)]
pub struct Latch {
    pub collapsed: bool,
    pub by_user: bool,
}

/// Is the sidebar hidden at this width?
///
/// The user's latch wins outright; below it, the width decides. An automatic
/// collapse un-collapses when the window widens past the threshold again — it
/// was never a choice — which falls out of `by_user` being false rather than
/// being a rule of its own.
pub fn hidden(total_cols: u16, latch: Latch) -> bool {
    if latch.by_user {
        latch.collapsed
    } else {
        total_cols < sidebar::AUTO_COLLAPSE_COLS
    }
}
crates/emma/src/term/app.rs — Latch, hidden; crates/emma/src/term/sidebar.rs — AUTO_COLLAPSE_COLS

Two bits: one for the posture, one for whose posture it is. The same shape as frame.rs's pinned latch, and for the same reason: distinguish where the system put it from where the user put it. toggle_sidebar always sets by_user: true, so a keypress or a click wins in both directions and keeps winning when the window is resized.

Defect: one assertion in the latch test cannot fail

the_sidebar_latch_honours_the_user_over_the_width builds a binding named user_open with collapsed: false, by_user: false and then asserts hidden(80, user_open). With by_user false, hidden ignores collapsed entirely and answers from the width, so that line re-tests the automatic branch already asserted three lines above rather than the user-opinion branch its name claims. The line now carries the comment “precondition: auto would hide it”, which is an honest label for what it does, and the guarantee is covered twice over: later in the same test through App::toggle_sidebar, and by the same-named test in guarantees.rs, whose user_open binding sets by_user: true and asserts !hidden(80, user_open). That is the assertion that goes red if the user branch is dropped from hidden; the one in app.rs is not. certified: read the three lines in each file and the body of hidden above.

The click, and the row it aims at

The control on that row changed owner, and this section used to describe the one that left. The defect that started it was reported as “+ and - does not seem to work”: the owner aimed at the affordance with the mouse and nothing routed a click anywhere. The fix at the time was App::click, which hit-tested the whole SESSIONS header row against a side_rect recorded during render and called toggle_sidebar. Neither the function nor the field is in the tree: the 2026-08-27 TUI import put the mock's [+] New Session control on that row instead, and collapsing is a keyboard toggle. Ctrl-B is the only way in and out, which the hint row names.

The guarantee survived the swap even though the method did not: the pointer hits what the reader saw, and nothing else. Two functions carry it, and the split is what keeps the hit test from agreeing with itself and disagreeing with the screen. new_session_hit is the geometry, re-derived from the three rules sidebar::header paints by; App stores the rectangle its last paint produced and tests presses against that stored copy rather than recomputing one.

crates/emma/src/term/app.rs · new_session_hit

/// Where the SESSIONS header's `[+]` sits, given the sidebar's own rectangle.
///
/// **Geometry, not a question asked of `sidebar.rs`.** That module renders and
/// reports nothing back, so this re-derives the three facts its header row is
/// built from: the pane is bordered, so its content starts one cell in on both
/// axes; the header is the content's first row; and the affordance is
/// right-aligned in it, dropped whole when it does not fit rather than clipped
/// to a `[+` that is not a control. Those are the rules in `sidebar::header`,
/// and the test that both agree is the one that reads the rect off a real
/// paint.
pub fn new_session_hit(sidebar: Rect) -> Option<Rect> {
    // The same floor `sidebar::render` refuses to draw below.
    if sidebar.width < 3 || sidebar.height < 3 {
        return None;
    }
    let width = sidebar::COLLAPSE_HINT.chars().count() as u16;
    let inner_w = sidebar.width - 2;
    if inner_w < width {
        return None;
    }
    // `sidebar::header` leaves its right pad after the affordance, and drops
    // the pad whole — never the glyph — when the two together will not fit.
    // The same two rules, in the same order, or the rectangle is not where the
    // glyph is.
    let pad = if width + sidebar::HEADER_RIGHT_PAD > inner_w {
        0
    } else {
        sidebar::HEADER_RIGHT_PAD
    };
    Some(Rect::new(
        sidebar.x + 1 + inner_w - width - pad,
        sidebar.y + 1,
        width,
        1,
    ))
}

What App::render does, in order

It refuses a zero-sized area; asks hidden and sidebar::width; builds the sidebar's state; clears the control rectangles a closing page would otherwise leave catching clicks; hands the carve to layout::compose, which paints the sidebar, the main border and the bottom bar; and lets the open screen fill the main region. On the chat screen that is chat_screen: header, rule, wrap_width and chat_height, a re-wrap, the chat pane, the dock through View's own renderers, and the hint.

This paragraph named a side_rect written down during render until 2026-09-07, and there is no such field. It went with App::click in the TUI import; what the paint records now is sessions_add for the [+], sidebar_hits for the rows, and chat_rect for the selectable pane. See the click section.

The wrap width is a seam. Retained transcript entries are wrapped by this file and painted by chat.rs at a gutter offset, so both numbers are derived from one function of the pane's own rectangle: 

        self.chat_height = r.chat.height.max(1);
        self.wrap_width = chat::message_width(r.chat.width.max(1));
        self.transcript.set_width(skin, self.wrap_width);

The test that guards it says what would happen otherwise: “if the two widths are derived separately, every wrapped row is clipped by the gutter's width and no test in either file notices.” tested: the_wrap_width_is_the_chat_panes_message_width_exactly, which also asserts the two differ at 120 columns so the equality is not a tautology.

The second is the dock. It is not a widget of its own: it is a rectangle that View's existing renderers paint into, the same render_input and render_prompt the inline viewport uses, marked pub(crate) with the argument attached: “a consent interface with two renderings is two interfaces.” When a question is pending the approval panel replaces the input box in that rectangle. tested: a_pending_question_replaces_the_input_box_and_stays_on_screen pushes 200 blocks of output first, then asserts the title, the evidence and the keys are all on screen and the input box is not.

crates/emma/src/term/layout.rs — regions, hidden, dock_height, Latch, Regions

The extraction has a reason the module doc states. The full-screen frame is a sidebar, a main region and a bottom status bar, and which screen occupies the main region varies while the chrome around it does not. compose is the one seam that paints the chrome and hands the main region to whichever screen is up. It exists because the settings screen had already grown its own copy of the status-bar rendering and had quietly stopped honouring a configured status program, which is the drift the seam ends. bar_for chooses the status bar's contents from the View, so the choice happens once rather than per screen. unverified Whether every screen now goes through compose rests on reading the call sites, not on a test that fails when one does not. A test that renders each Mode and asserts the status row is present would settle it, and that test is not in the file.
