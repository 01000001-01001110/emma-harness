The Tool trait, and what a tool declares

Tools the trait outcomes truncation ToolCtx containment files Edit Bash tasks web LSP screenshot

crates/tool-api/src/lib.rs is 688 lines (wc -l, 2026-09-06; 632 when this page was written) and one file. It holds the error taxonomy, the success type, the two structs the runtime reads before it runs anything, the trait, and a registry. Nothing else lives there, which is what keeps adding a tool down to a crate plus one registry line.

That promise has been broken twice, both times by the approval gate learning something about a particular tool's arguments: once a hard-coded check on a query argument, once inferring retrieval from an empty chunks array. Both are recorded on NetworkTarget as the reason the gate asks and the tool answers rather than the gate parsing.

crates/tool-api/src/lib.rs — module doc, NetworkTarget

Seven methods, five of them mandatory

#[async_trait::async_trait]
pub trait Tool: Send + Sync {
    /// Matches Claude Code's names — `Read`, `Write`, `Edit`, `Glob`, `Grep`,
    /// `Bash` — so a hook matcher or allow-list written for one works for the
    /// other. Better names would cost compatibility and buy nothing.
    fn name(&self) -> &'static str;

    /// Shown to the model verbatim. The built-in tools hold theirs in a
    /// markdown file next to the source and `include_str!` it, so a prose
    /// change is reviewable as a diff and lands in [`Registry::schema_hash`].
    /// Returning `&str` rather than `&'static str` is what lets `Skill` be a
    /// tool too — its description is composed at load time from the skill file
    /// on disk.
    fn description(&self) -> &str;

    fn input_schema(&self) -> serde_json::Value;

    fn meta(&self) -> ToolMeta;

The remaining three carry the arguments. network_target and validate_args both default, so a tool that touches no network and needs no cheap checks implements four methods and invoke. 

    /// Where this particular call would send bytes, if anywhere.
    ///
    /// Answered by the tool because the approval gate must not learn what any
    /// tool's arguments look like — see [`NetworkTarget`] for the two times
    /// that went wrong here. `None` is the default and is right for every tool
    /// that declares `reaches_network: false`.
    ///
    /// **`None` from a tool that declares `reaches_network: true` is a
    /// refusal, not a pass.** The gate cannot grant a destination nobody
    /// named, so it denies the call and says so. Fail-closed, because the
    /// alternative is that a tool which forgets to answer gets silent egress.
    fn network_target(&self, _args: &serde_json::Value) -> Option<NetworkTarget> {
        None
    }

    /// Cheap, synchronous, no I/O. Anything requiring the filesystem belongs
    /// in `invoke` and comes back as `BadArguments`.
    fn validate_args(&self, _args: &serde_json::Value) -> Result<(), ToolError> {
        Ok(())
    }

    /// The outer `Result` is for faults that should end the turn. The inner is
    /// for failures the model should see and route around. Almost everything
    /// is the inner one — a tool that ends the turn is claiming the session
    /// cannot continue, which is rare and should feel rare to write.
    async fn invoke(
        &self,
        ctx: &ToolCtx,
        args: serde_json::Value,
    ) -> anyhow::Result<Result<ToolOutcome, ToolError>>;
}

How a call reaches a tool

The order matters in two places. validate_args runs before the approval prompt, so a malformed call never spends your attention. The PreToolUse hook runs before it too, because a policy denial is not something you get a vote on at the keyboard, and a gate you can wave through is advice.

ToolMeta: three bits, and one that was deleted

The predecessor's equivalent struct had a needs_approval field that nothing ever read. It was not ported. A declaration pretending to be a mechanism is worse than no declaration, because reviewers stop asking the question the field appears to answer. 

/// **There is deliberately no `Default`.** Adding a field here breaks every
/// construction site in the workspace, and that is the feature: a tool must
/// *state* each of these rather than inherit it. The predecessor added a
/// defaulted field and thereby granted a safety property to every tool written
/// afterwards, chosen by nobody, noticed by no review.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct ToolMeta {
    pub read_only: bool,
    pub reaches_network: bool,
    pub idempotent: bool,
}
crates/tool-api/src/lib.rs — ToolMeta
FieldAsksRead by
read_only Can this damage this machine: no file written, no process spawned. Not "cannot reach the network". WebFetch and WebSearch both declare true and both talk to the outside, by driving a browser. the approval gate
reaches_network Sends bytes off this machine by construction. A separate axis because writing is a risk the model states in the call, while egress is how a prompt-injected page turns a read tool into an exfiltration channel, and that channel passes every local-damage check on the way out. the approval gate, per host
idempotent Running it twice has the same effect as once. Edit declares false and means it. Registry::register, and nothing else

The last row is the one with a history. idempotent was for a while declared by every tool and consulted by nothing, which is the exact shape the needs_approval deletion rejects. It was not deleted, because the answer is a genuine per-tool fact. It was given a reader instead.

Its own doc names what the field is still not: a replay mechanism. Emma has no crash-recovery fold, and nothing consults this to decide whether to re-run a call.

The coherence check

    pub fn register(&mut self, tool: Arc<dyn Tool>) {
        let meta = tool.meta();
        assert!(
            // Reads as the entailment it is: read_only ⟹ idempotent.
            !meta.read_only || meta.idempotent,
            "{} declares read_only: true with idempotent: false — a call that \
             changes no local state cannot have a different effect the second \
             time, so one of the two is wrong",
            tool.name()
        );
        self.tools.push(tool);
    }
crates/tool-api/src/lib.rs — Registry::register

A panic rather than an error, because this is a wiring mistake in a const a human wrote: it is the same on every boot, it is reached by every test that builds a registry, and there is no sensible way to continue with a tool surface whose safety declarations do not cohere. read_only is the one the gate is about to trust to skip a human, so the pair is refused rather than half-believed.

tested a_read_only_tool_cannot_also_declare_itself_unsafe_to_repeat is a #[should_panic(expected = "declares read_only: true with idempotent: false")], and the_two_honest_shapes_both_register is the positive control that stops the check being satisfied by refusing everything. tools/lsp runs its four declarations through a real Registry for the same reason.

An error is a fact about the call

Three variants, a stable kind string the model routes on, and prose kept separate from it so rewording a message never changes the taxonomy. The enum is #[non_exhaustive], so a new variant cannot silently fall into an existing arm at a call site written before it existed.

kind()VariantMeans
tool_unavailable Unavailable The machinery is absent or unconfigured: no key, no binary, no permission. Phrased "I cannot do this", never "this cannot be done".
tool_failed Failed It ran and did not succeed. A command that started and exited non-zero is not here.
bad_arguments BadArguments Wrong arguments, including the kind only discoverable at run time, because validate_args cannot stat a path or know whether a string occurs once in a file.

Emptiness is a result. A read of an empty file succeeds and returns nothing. A glob matching zero paths succeeds with an empty list. A grep with no hits succeeds. Blurring that turns "I could not look" and "I looked and there was nothing" into one message, and the model cannot route around a failure it has been told is an answer.

That rule was written about the filesystem and did not survive contact with Bash. A non-zero exit had been documented as Failed, which makes grep -q answering "no" a tool failure. The loop refuses to repeat a call that already failed with nothing changed since, so one legitimate miss would have blocked that command for the rest of the turn. The line is now whether the command ran. It was not resolved as "Bash is the documented exception", because "except X" is how a rule starts becoming folklore. The full argument is on the Bash page.

The registry, and the surface it renders

Registry is a Vec<Arc<dyn Tool>> and six methods. get is a linear scan by name over twenty-one entries, which is not worth a map. names, iter and new are uninteresting and are listed here so the file is covered rather than sampled. The two that carry decisions are register, above, and: 

    /// A digest of every byte of the tool surface the model is shown — names,
    /// descriptions and schemas — so a change to a description is attributable
    /// rather than invisible. The loop records it on the `goal` event at the
    /// start of a run, and `emma config check` prints it.
    ///
    /// Truncated to 16 hex characters: this is a change detector for a human
    /// reading a log, not a collision-resistant identifier.
    pub fn schema_hash(&self) -> String {
        use sha2::{Digest, Sha256};
        let mut hasher = Sha256::new();
        for def in self.wire_definitions() {
            hasher.update(def.to_string().as_bytes());
        }
        format!("{:x}", hasher.finalize())[..16].to_string()
    }
crates/tool-api/src/lib.rs — Registry::schema_hash, wire_definitions

Because the hash covers descriptions, two tool crates carry a test asserting nothing machine-specific reaches it: no shell path, no server binary, no Program Files. A description that named the local shell would make the hash a property of the box, and attribution would stop meaning anything. Both tests also assert the positive half, that the description still tells the model where the machine-specific answer is.

NetworkTarget, and one grant per host

    /// Normalises the host so the gate's `HashSet` and the tool agree on what
    /// "the same host" means. `Docs.RS.` and `docs.rs` are one grant; `docs.rs`
    /// and `www.docs.rs` are deliberately two, because deciding they are the
    /// same is a policy nobody asked for.
    pub fn new(host: impl AsRef<str>, detail: impl Into<String>) -> Self {
        Self {
            host: host
                .as_ref()
                .trim()
                .trim_end_matches('.')
                .to_ascii_lowercase(),
            detail: detail.into(),
        }
    }

detail is one line naming the errand, and it is what you read under the host. WebSearch puts the query there verbatim, BrowserFill puts every field and value. A prompt that names a host and not what is being sent there is a prompt nobody can evaluate.
