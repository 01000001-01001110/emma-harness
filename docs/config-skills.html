Skills and commands

Configuration Discovery Every file The spine Reading .claude/ Skills & commands Agents Your own files Themes It did not apply

Two directories with the same layout in both flavours, which is the whole point of reading a second directory name at all. A skill is text the model asks for by name; a command is text a person summons with a slash. Neither can change what the runtime does, and the strictness each is read with depends on whose format the file is written in.

Skills: skills/<name>/SKILL.md

A directory per skill, each holding a file called SKILL.md exactly. Markdown with YAML frontmatter; Emma reads two fields and the body after the frontmatter is the skill. A subdirectory without a SKILL.md is skipped without complaint, and a loose file directly in skills/ is ignored.

crates/harness/src/lib.rs · load_skills

fn load_skills(
    root: &Path,
    spine_path: &Path,
    flavor: Flavor,
    elected: Option<&[String]>,
) -> Result<Vec<SkillDef>> {
    let dir = root.join("skills");
    // A `BTreeMap` keyed on the front-matter name gives the sorted catalogue the
    // prompt prefix needs, whatever order the directory iterated in.
    let mut found: BTreeMap<String, SkillDef> = BTreeMap::new();
    if dir.is_dir() {
        for entry in
            std::fs::read_dir(&dir).with_context(|| format!("reading {}", dir.display()))?
        {
            // A subdirectory without a `SKILL.md` is skipped without complaint,
            // and a loose file in `skills/` is ignored.
            let path = entry?.path().join("SKILL.md");
            if !path.is_file() {
                continue;
            }
            let text = std::fs::read_to_string(&path)
                .with_context(|| format!("reading {}", path.display()))?;
            let (front, body) = match (split_skill(&text, &path, flavor), flavor) {
                (Ok(v), _) => v,
                // Emma's own format: a file this loader cannot read is a mistake
                // in a file the operator wrote for Emma, and it stops the boot
                // like every other one.
                (Err(e), Flavor::Emma) => return Err(e),
                // A foreign format. The skill is unusable either way; the choice
                // is only whether it costs the operator this skill or every
                // skill. It is named on stderr rather than dropped, because a
                // catalogue quietly one shorter than the directory is the kind of
                // gap nobody notices until the model cannot find a skill that is
                // plainly there.
                (Err(e), Flavor::Claude) => {
                    eprintln!("emma: skipping skill {}: {e:#}", path.display());
                    continue;
                }
            };
            found.insert(
                front.name.clone(),
                SkillDef::new(front.name, front.description, body),
            );
        }
    }
crates/harness/src/lib.rs — load_skills

The catalogue is keyed and sorted by the frontmatter name rather than by the directory name, and never by directory iteration order, because the catalogue rides in the prompt prefix that the provider caches as an exact byte match. Two skills declaring the same name still collapse to one — but the collapse is reported now, naming both files and saying that which one wins depends on the order the filesystem returned the directory in, so it may differ between runs. It used to happen in silence, while the sibling agent loader had been printing exactly that note for months. Two skills declaring the same name collapse to one, with the later iteration winning.

The strictness split, and what it cost to learn

Two structs, two fields each, and the difference between them is one attribute.

crates/harness/src/lib.rs · Front, ClaudeFront

/// Only `name` and `description` are read. A skill is markdown; anything the
/// runtime must branch on belongs in the spine.
///
/// **Strict for `.emma/`.** Both fields are required and `deny_unknown_fields`
/// is on, so a `SKILL.md` missing either — or carrying any third key — fails the
/// load and takes the boot with it. In Emma's own format an unknown key can only
/// be the user's typo, and this is the attribute that catches it.
#[derive(Deserialize)]
#[serde(deny_unknown_fields)]
struct Front {
    name: String,
    description: String,
}

/// The same two fields, read from a `.claude/skills/` file, where the rest of the
/// frontmatter is somebody else's business.
///
/// **The ruling, and it is the `settings.json` argument one level down.** Real
/// skills on a working machine carry `model-role`, `version` and
/// `allowed-tools`; under the strict struct above, every one of them took the
/// whole boot down. A rule that fires on correct configuration is an outage, not
/// a safety property — and unlike `.emma/`, an unrecognised key here is not a
/// typo in Emma's format, it is a key Emma has no opinion about in someone
/// else's. So unknown keys are ignored, and a file that cannot be read at all is
/// skipped with a warning rather than taken as a reason not to start.
///
/// `name` and `description` stay required, because they are not decoration: they
/// are the catalogue line the model chooses the skill from, and a skill with no
/// name cannot be asked for.
#[derive(Deserialize)]
struct ClaudeFront {
    name: String,
    description: String,
}

Splitting the file

crates/harness/src/lib.rs · split_skill

fn split_skill(text: &str, path: &Path, flavor: Flavor) -> Result<(Front, String)> {
    let named = |what: &str| format!("{}: {what}", path.display());
    let text = match flavor {
        Flavor::Emma => text,
        Flavor::Claude => after_licence_header(text),
    };
    // `claude::open_frontmatter`, not a local byte-exact opener. The exact
    // form dropped 101 of 323 real skills on this machine — every one written
    // by an editor that ends lines with CRLF — while the agent parser one file
    // away had already been fixed for precisely that. See its doc.
    let rest = crate::claude::open_frontmatter(text)
        .with_context(|| named("expected YAML frontmatter"))?;
    let end = rest
        .find("\n---")
        .with_context(|| named("frontmatter is not closed"))?;
    let front: Front = match flavor {
        Flavor::Emma => serde_yaml::from_str(&rest[..end]),
        Flavor::Claude => serde_yaml::from_str::<ClaudeFront>(&rest[..end]).map(Front::from),
    }
    .with_context(|| named("bad frontmatter"))?;
    Ok((front, rest[end + 4..].trim_start().to_string()))
}
crates/harness/src/lib.rs — split_skill

The opener goes through claude::open_frontmatter, which tolerates ---\r\n and a leading byte-order mark. It used to be "---\n" byte for byte, and this page used to describe that as the design. It was not a design; it was the same defect the agent parser had already been fixed for, sitting one file away and unvisited because nobody was holding both files at once. Measured against the owner's real library: 101 of 323 skills silently missing, every one written by an editor that ends lines with CRLF. certified on that corpus — 207 of 324 loaded before, 306 of 324 after.

The lesson filed with the fix is the general one: when you fix a parser, grep for its siblings before you finish, and make both callers reach one function rather than copying it. This defect recurred once precisely because the first fix was a local edit instead of a shared function. open_frontmatter now has three callers and its doc asks the next person not to inline a copy.

crates/harness/src/lib.rs · after_licence_header

/// Step over an HTML comment before the frontmatter, `.claude/` only.
///
/// A licence header above the `---` is common enough to be worth handling rather
/// than skipping: the file is well-formed, it simply does not open with its own
/// first line, and refusing it would drop a skill for a reason the operator can
/// do nothing about. It steps over comments and blank lines and nothing else — a
/// file with real prose above its frontmatter is not a skill with a header, it is
/// a file whose frontmatter is somewhere in the middle, and guessing at that is
/// how a parser starts reading text nobody meant as configuration.
///
/// A `---\r\n` opener and a byte-order mark **are** covered, by
/// `claude::open_frontmatter`, which every caller now reaches. This comment used
/// to say they were not, and it was written when that was true: the byte-exact
/// `---\n` opener silently dropped 101 of 323 real skill files on a machine whose
/// editor writes CRLF.
fn after_licence_header(text: &str) -> &str {
    let mut rest = text.trim_start();
    while let Some(body) = rest.strip_prefix("<!--") {
        let Some(end) = body.find("-->") else {
            return rest;
        };
        rest = body[end + 3..].trim_start();
    }
    rest
}
crates/harness/src/lib.rs — after_licence_header

trim_start is what steps over blank lines, and the loop handles several stacked comments. An unterminated <!-- returns the text unchanged, which then fails the frontmatter check with the ordinary message rather than looping. certified: a scratch skill opening with <!-- (c) somebody 2026 --> and a blank line before its --- loads and appears in the catalogue as licenced.

What the CRLF fix cost to find, kept because the shape recurs

split_agent in claude.rs had already been fixed for this: requiring ---\n exactly made 90 out of 90 agent files in a real library parse as having no frontmatter at all. split_skill, two hundred lines away, still required it. The fixtures were the reason nobody saw it. They were written by the same author as the parser, in the same editor, with the same line endings — so the suite was green while a third of a real corpus was being dropped. That is why this repository certifies against a real library rather than a fixture directory, and why a green suite is not evidence. tested a_skill_written_with_windows_line_endings_loads (crates/harness/tests/claude_compat.rs:455); removing the tolerance turns it red.

crates/harness/src/lib.rs — SkillDef, SkillDef::new

Four accessors sit on Harness. skills() returns the sorted slice, skill(name) finds one, skill_names() gives the closed enum a tool schema puts in its name argument, and skill_catalog() composes the description lines. The last one is the interesting one, because its return type carries a decision.

crates/harness/src/lib.rs · Harness::skill_catalog

    /// The catalogue lines a `load_skill` description is composed from, or
    /// `None` when there are no skills.
    ///
    /// `None` is the signal not to register the tool at all. Offering a
    /// capability that cannot work is a trap with a description attached, and
    /// returning an empty string instead would make that mistake invisible at
    /// the call site. The preamble is the tool's own prose and stays in the
    /// tool's crate; only the part that varies with the loaded harness is here.
    pub fn skill_catalog(&self) -> Option<String> {
        if self.skills.is_empty() {
            return None;
        }
        let mut out = String::new();
        for s in &self.skills {
            out.push_str(&format!("\n- `{}` — {}", s.name, s.description.trim()));
        }
        out.push('\n');
        Some(out)
    }
crates/harness/src/lib.rs — Harness::skill_catalog, skill_names

A harness with no skills does not register the Skill tool. certified: the tools line from config check in this repository, which has no skills, runs … Hover, DocumentSymbols, WebFetch, …; the same line in the scratch .claude/ harness with two skills reads … Hover, DocumentSymbols, Skill, WebFetch, …. Twenty-one tools against twenty-two, and the tool schema hashes differ accordingly.

skill_names's doc carries the reason the argument is an enum rather than a path: a tool that reads a model-supplied path is an arbitrary-file-read tool with a friendly description. What a skill can do is add text to one turn, and it is loaded by a tool call, so its body reaches the model only when the model asks for it by name.

Commands: commands/<name>.md

Top-level *.md only, and the file stem is the name. There is no frontmatter, no strictness question, and no failure mode beyond a file that cannot be read.

crates/harness/src/lib.rs · load_commands

fn load_commands(root: &Path) -> Result<BTreeMap<String, String>> {
    let dir = root.join("commands");
    let mut out = BTreeMap::new();
    if !dir.is_dir() {
        return Ok(out);
    }
    for entry in std::fs::read_dir(&dir).with_context(|| format!("reading {}", dir.display()))? {
        let path = entry?.path();
        if path.extension().and_then(|e| e.to_str()) != Some("md") {
            continue;
        }
        let name = path.file_stem().unwrap_or_default().to_string_lossy();
        let body = std::fs::read_to_string(&path)
            .with_context(|| format!("reading {}", path.display()))?;
        out.insert(name.into_owned(), body.trim().to_string());
    }
    Ok(out)
}
crates/harness/src/lib.rs — load_commands

body.trim() is the second of the two places the "nothing is trimmed" prompt rule is bent, and the module doc says why: a command body is not always-on prompt text, it is text a person typed a /name to summon. A subdirectory under commands/ is skipped by the extension test rather than walked.

Expansion happens at intake, and the model never learns commands exist.

crates/harness/src/lib.rs · Harness::expand_command

    /// Server-side expansion at intake. `None` for anything that is not a known
    /// command, including an unknown `/word`, which passes through as ordinary
    /// text. The model never learns commands exist.
    pub fn expand_command(&self, raw: &str) -> Option<Expansion> {
        let rest = raw.strip_prefix('/')?;
        let end = rest.find(char::is_whitespace).unwrap_or(rest.len());
        let (name, tail) = rest.split_at(end);
        let body = self.commands.get(name)?;
        let tail = tail.trim();
        Some(Expansion {
            command: name.to_string(),
            raw: raw.to_string(),
            text: if tail.is_empty() {
                body.clone()
            } else {
                format!("{body}\n\n{tail}")
            },
        })
    }
crates/harness/src/lib.rs — expand_command, Expansion

The tail is appended after a blank line when there is one, and both halves are kept on the Expansion so the session log can record what the person typed as well as what the model was asked. An unknown /word is not an error and not a missing command: it returns None and passes through to the model as ordinary text, which is indistinguishable from a command that "did nothing" if an expansion was expected.

A built-in of the same name wins, and says so

main matches its own commands before expand_command is reached, so a commands/exit.md has never been reachable. emma config check names any project command that a built-in shadows, with the sentence "is shadowed by Emma's own /name and cannot be reached. Rename the file." The alternative, a checkout being able to shadow /model or /clear, would let a repository take away Emma's own control surface. unverified: no shadowing command file was built here. Settle it by putting a commands/exit.md in a scratch harness and re-running config check.
